📌 概念题 · Q1

考点标签

LLMOps 监控指标 · 难度：⭐⭐⭐

📝 题目

在 LLMOps 运维监控体系中，除了常规的 GPU 温度和利用率外，为什么必须重点监控 TTFT（首字延迟时间） 和 TPOT（每个 Token 生成时间）？这两个指标分别反映了系统的什么瓶颈？如果 TTFT 正常但 TPOT 异常偏高，问题可能出在哪里？

💡 参考答案

▎一句话结论

TTFT 反映的是“用户感知的响应快慢”，TPOT 反映的是“模型推理的真实速度”；两者解耦监控才能精准定位性能瓶颈，而不是笼统地说“模型慢”。

▎核心原理

  • TTFT（Time To First Token）：从用户发送请求到第一个 Token 生成出来的时间，包含了网络延迟、Prompt 处理（Prefill）、调度排队等所有前置开销。
  • TPOT（Time Per Output Token）：第一个 Token 之后，平均每个后续 Token 的生成时间，直接反映模型推理引擎的纯计算效率。
  • 解耦的价值：TTFT 高可能是网络/排队问题，TPOT 高可能是显存带宽不足或量化策略不当，混在一起看 GPU 利用率根本看不出来。

▎深入解释

想象你去餐厅吃饭。TTFT 相当于“从你坐下点完菜到第一道菜上桌的时间”——这取决于服务员有没有及时下单、厨房有没有及时接单、前菜是不是预制好的。TPOT 则相当于“第一道菜之后，每道菜之间的上菜间隔”——这才是厨房炒菜速度的真实体现。

在 LLM 推理中，TTFT 包含了 Prompt 的 Prefill 阶段（把整个输入上下文一次性喂给模型做矩阵运算），这个阶段是 Compute-bound，吃 GPU 算力。TPOT 则是 Decode 阶段（逐 Token 自回归生成），这个阶段是 Memory-bound，吃显存带宽。如果你用 vLLM 部署 Qwen 3.5-32B，TTFT 突然从 200ms 飙到 2s，很可能是 Prefill 的并发请求太多导致排队；如果 TPOT 从 20ms/token 涨到 80ms/token，很可能是 KV Cache 打满了显存，触发了换页（Swapping）。

▎面试加分点

  • 提到 vLLM 的 Continuous Batching 可以优化 TTFT，因为它在 Prefill 阶段可以批量处理多个请求。
  • 提到 AWQ/INT4 量化主要影响 TPOT，因为 Decode 阶段对权重的读取速度极度敏感，量化后显存占用减少，反而可能让 TPOT 降低。
  • 实战经验：生产环境建议对 TTFT 和 TPOT 分别设置 P99 告警阈值，而不是看平均值。

▎常见误区

  • 误区：只看 GPU 利用率。GPU 利用率 100% 不代表用户体验好，可能是在低效地做无用功。
  • 误区：把 TTFT 和 TPOT 混为一谈，说“模型响应慢”就盲目升级硬件，结果发现是网络代理层的问题。

📌 概念题 · Q2

考点标签

JSONB 与 GIN 索引 · 难度：⭐⭐⭐⭐

📝 题目

在 Agent 的对话记忆存储设计中，为什么推荐使用 PostgreSQL 的 JSONB 字段存储半结构化数据（如对话上下文、用户标签），而不是普通 JSON 字段？JSONB 上的 GIN 索引 和传统 B-Tree 索引在查询能力上有什么本质区别？

💡 参考答案

▎一句话结论

JSONB 是“预处理好的二进制 JSON”，查询时无需重复解析，配合 GIN 索引可以实现对 JSON 内部任意 Key-Value 的穿透式高速搜索，这是普通 JSON 和 B-Tree 索引做不到的。

▎核心原理

  • JSON vs JSONB：JSON 存的是纯文本字符串，每次查询都要从头解析整个 JSON 结构；JSONB 存的是二进制格式，写入时已完成解析和键值排序，查询直接索引定位。
  • GIN（Generalized Inverted Index）本质是“倒排索引”，它会把 JSONB 文档内部的每一个 Key 和 Value 拆出来单独建索引，而不是像 B-Tree 那样只能对整列排序。
  • B-Tree 只能加速 WHERE column = 'value' 这类整列匹配；GIN 可以加速 WHERE jsonb_column @> '{"user_intent": "high"}' 这种“钻进 JSON 内部找”的查询。

▎深入解释

把 JSON 想象成一本书的扫描件（图片），每次查东西都要 OCR 识别一遍。JSONB 则是把这本书重新排版成电子书，每个章节、段落都打了标签，可以瞬间跳转。

在 Agent 场景中，一轮对话的上下文可能是这样的：

{
  "turn_id": 3,
  "user_intent": "schedule_interview",
  "extracted_slots": {"candidate_name": "张三", "position": "前端"},
  "rag_retrieved_docs": ["doc_123", "doc_456"]
}

如果存为普通 JSON，你想查“所有 user_intent 为 schedule_interview 的对话”，数据库只能全表扫描，逐行解析 JSON 字符串。用 JSONB + GIN 索引，你可以用 @> 操作符瞬间命中，即使表里有几百万行对话记录也能毫秒级返回。

▎面试加分点

  • 提到 GIN 索引的代价：写入性能会下降约 20-30%，因为每次 INSERT/UPDATE 都要更新倒排索引，所以适合“写少读多”的 Agent 对话日志场景。
  • 实战组合：传统 SQL 列存固定字段（时间、用户 ID），JSONB 存动态变量，GIN 索引加速 JSONB 内部查询——这是“结构化存骨架，半结构化存血肉”的最佳实践。

▎常见误区

  • 误区：以为 GIN 索引和 B-Tree 一样，对所有查询都有效。GIN 只对 @>（包含）、?（键存在）、?|（任意键存在）等特定操作符生效。
  • 误区：滥用 JSONB 存所有数据。高频查询的固定字段（如 user_id）还是应该用传统列 + B-Tree 索引，查询计划更稳定。

📌 概念题 · Q3

考点标签

悲观锁与 Agent 并发 · 难度：⭐⭐⭐⭐

📝 题目

在社媒内容运营 Agent 中，多个 Worker 节点同时从 PostgreSQL 的“热点选题表”领取任务时，为什么推荐使用 SELECT ... FOR UPDATE（悲观锁）而不是乐观锁（如版本号机制）？悲观锁在 Agent 高并发场景下的核心优势是什么？会带来什么代价？

💡 参考答案

▎一句话结论

悲观锁通过“先锁后读”的机制，在数据库层面强行将并发操作串行化，100% 避免多个 Agent 同时领取同一任务导致的数据覆盖；代价是并发吞吐量会下降，但在 Agent 任务领取这种“低频但强一致性要求”的场景下，这是最稳妥的选择。

▎核心原理

  • SELECT ... FOR UPDATE 会在事务中给查询到的行加排他锁，其他事务的 SELECT ... FOR UPDATE 必须等待当前事务提交或回滚后才能继续。
  • 乐观锁（如版本号 UPDATE ... WHERE version = old_version）是“先读后写，提交时检查”，如果冲突就重试；但在高冲突场景下，重试次数可能激增，反而更慢。
  • Agent 任务领取是典型的“单消费者”模式：一条任务只能被一个 Worker 领取，冲突概率本身就不低，悲观锁的“排队等待”比乐观锁的“失败重试”更高效。

▎深入解释

想象一个公告栏上贴满了待领取的任务便签。乐观锁的做法是：你看到一张便签，记下它的编号，伸手去撕——结果发现已经被别人撕走了，你只能再找下一张。悲观锁的做法是：你走到公告栏前，先把整个公告栏锁起来，慢慢挑一张，撕下来，再解锁。显然，如果同时有 10 个人在抢便签，乐观锁会导致大量“伸手撕空”的无效操作。

在 PostgreSQL 中，SELECT ... FOR UPDATE 必须包裹在事务（BEGIN/COMMIT）中使用：

BEGIN;
SELECT * FROM hot_topics WHERE status = 'pending' LIMIT 1 FOR UPDATE;
-- 这里做业务处理，标记为 'processing'
UPDATE hot_topics SET status = 'processing' WHERE id = ...;
COMMIT;

事务期间，其他 Worker 执行到同样的 SELECT ... FOR UPDATE 时会被阻塞，直到第一个 Worker 提交事务释放锁。

▎面试加分点

  • 提到 SKIP LOCKED 子句：SELECT ... FOR UPDATE SKIP LOCKED 可以让等待的 Worker 跳过已被锁定的行，直接领取下一条未锁定的任务，大幅提升并发吞吐量。
  • 强调事务要短：悲观锁持有时间越长，阻塞越严重，所以锁内只做“领取 + 标记状态”，不要做耗时的 LLM 调用。
  • 实战经验：Agent 任务领取推荐 FOR UPDATE SKIP LOCKED，结合 LIMIT 1，实现高效的 FIFO 任务队列。

▎常见误区

  • 误区：认为悲观锁一定比乐观锁慢。在低冲突场景下乐观锁确实更好，但 Agent 任务领取是高冲突场景，悲观锁的排队机制反而避免了乐观锁的“重试风暴”。
  • 误区：忘记加索引。FOR UPDATE 的 WHERE 条件列如果没有索引，会导致全表锁，性能灾难。

📌 概念题 · Q4

考点标签

向量数据库降级策略 · 难度：⭐⭐⭐

📝 题目

在企业内网 AI Agent 平台设计中，为什么必须为向量数据库（如 Milvus）设计“逃生通道”降级方案（如自动切换至 PostgreSQL 全文检索）？这种降级设计的核心价值是什么？在实现时需要注意哪些关键点？

💡 参考答案

▎一句话结论

降级方案的核心价值不是“向量库会经常挂”，而是“当向量库真的挂了，员工的基本搜索业务不能断”——这是企业级系统的底线思维，用 20% 的语义能力损失换取 100% 的业务连续性。

▎核心原理

  • 单点故障风险：在中小型企业的私有化部署中，Milvus 通常是单机 Docker Compose 部署，没有 K8s 的高可用（HA）保障，宿主机宕机、磁盘满、Docker 服务异常都可能导致向量库不可用。
  • 语义检索 vs 全文检索：语义检索依赖向量相似度，能理解“公积金提取条件”和“住房补贴申领流程”是相关的；全文检索只能做关键词匹配，但至少能搜到包含“公积金”的文档。
  • 降级不是“降级到零”：PostgreSQL 的 tsvector + tsquery 全文检索能力并不弱，配合倒排索引能快速返回包含关键词的结果，虽然排序不如语义检索精准，但能满足基本的“找到相关文档”需求。

▎深入解释

把向量库想象成你办公室里的智能文件柜——你问它“去年那个关于加班的政策”，它能理解你的意图，直接找出最相关的文件。全文检索则像传统的标签分类柜——你只能搜“加班”这个关键词，可能返回一大堆包含“加班”但不一定是你想要的文件，但至少不会空手而归。

降级开关的实现通常放在应用层（如 FastAPI 中间件或 LangGraph 的 Tool 节点中）：

try:
    results = milvus_client.search(query_vector, top_k=10)
except MilvusException:
    logger.warning("Milvus unavailable, falling back to PostgreSQL FTS")
    results = pg_client.full_text_search(query_text, limit=10)

▎面试加分点

  • 提到“降级演练”的必要性：每季度手动关停一次 Milvus 容器，验证降级逻辑是否真的生效，而不是等线上出问题才第一次触发。
  • 健康检查机制：在应用层维护一个 milvus_healthy 的布尔标志，通过定时 Ping Milvus 的 /health 接口来动态切换，避免每次请求都超时等待。
  • 监控告警：降级触发时，必须同时发出告警通知运维人员，不能“静默降级”导致问题长期不被发现。

▎常见误区

  • 误区：以为降级方案是“备胎”，平时不用管。实际上降级逻辑的代码路径很少被执行，最容易出现 Bug，需要定期测试。
  • 误区：降级后的全文检索结果直接返回给用户，不做任何标注。应该在 UI 上提示“当前搜索模式为关键词匹配，语义排序暂时不可用”，管理用户预期。

📌 概念题 · Q5

考点标签

大模型输出模式选型 · 难度：⭐⭐⭐

📝 题目

在 Agent 开发中，结构化输出（JSON Mode）和工具调用（Function Calling）都返回 JSON 格式的数据，但它们的定位和使用场景完全不同。请解释两者的本质区别，以及在什么场景下应该选择结构化输出，什么场景下应该选择工具调用？

💡 参考答案

▎一句话结论

结构化输出是“让模型直接给你一个格式正确的答案”，工具调用是“让模型告诉你它想用什么工具，但不给最终答案”——前者是终点，后者是起点。

▎核心原理

  • 结构化输出（JSON Mode / Structured Outputs）：模型直接生成符合 JSON Schema 的最终结果，整个推理过程在模型内部完成，不涉及外部系统交互。例如“从这段文本中提取姓名、手机号、地址”。
  • 工具调用（Function Calling / Tool Use）：模型不生成最终答案，而是生成一个函数调用请求（包含函数名和参数），由外部代码执行该函数后，将结果返回给模型，模型再继续推理。例如“帮我查一下成都今天的天气”。
  • 本质区别：结构化输出是“一问一答”的闭环；工具调用是“多轮对话 + 外部执行”的开环。

▎深入解释

把结构化输出想象成你让助理帮你整理一份报告——你给他一堆资料，他直接给你一份格式完美的 Excel 表格。工具调用则是你让助理去帮你查资料——你问他“今天天气怎么样”，他回答“我需要用天气 API 查一下成都”，然后你帮他调了 API，把结果告诉他，他再告诉你“今天成都晴天，25 度”。

在 Agent 架构中，工具调用是 Agent 的“行动能力”核心——Agent 通过 Function Calling 来调用向量数据库检索、调用 SQL 查询、调用邮件发送接口。结构化输出则更多用于 Agent 内部节点间的标准化数据传递——比如 Router Agent 把意图分类结果以固定 JSON 格式传给下游的 Data Agent。

▎面试加分点

  • 提到 OpenAI 的 Structured Outputs 是从底层 Token 采样层面约束输出的，100% 保证 JSON 格式合法，而早期的 JSON Mode 只是 Prompt 约束 + 后校验，仍有小概率翻车。
  • 实战经验：工具调用需要处理“多轮迭代”——模型可能在一轮中调用多个工具，或者根据工具返回结果决定是否继续调用，这需要 LangGraph 等框架的状态管理能力。
  • 选择建议：如果目标是从文本中“抽取”信息，用结构化输出；如果目标是“触发外部动作”，用工具调用。

▎常见误区

  • 误区：认为工具调用就是“返回 JSON”。工具调用的 JSON 是给代码解析的，不是给用户看的；结构化输出的 JSON 是给前端渲染或数据库存储的。
  • 误区：在不需要外部交互的场景下也用工具调用，导致多一轮甚至多轮无效的 LLM 调用，增加延迟和成本。

📌 概念题 · Q6

考点标签

vLLM 推理框架 · 难度：⭐⭐⭐⭐

📝 题目

在本地部署大模型时，vLLM 框架相比传统的 Hugging Face Transformers 推理，在吞吐量和 GPU 利用率上有数量级的提升。请解释 vLLM 的核心创新 PagedAttention 是如何解决 KV Cache 显存碎片化问题的？为什么这个问题在长上下文（如 128K）场景下尤为严重？

💡 参考答案

▎一句话结论

PagedAttention 借鉴了操作系统的虚拟内存分页机制，把 KV Cache 从“一整块连续显存”变成“按需分配的小块（Page）”，彻底解决了显存碎片化和预留空间浪费的问题，让长上下文推理的并发吞吐量提升 10-20 倍。

▎核心原理

  • 传统 KV Cache 管理：每个请求的 KV Cache 是一整块连续显存，必须在请求开始时按最大可能长度（max_length）预留。如果用户实际只生成 100 个 Token，预留的 2048 个 Token 空间就全浪费了；而且不同请求的 KV Cache 块混在一起，释放后留下碎片。
  • PagedAttention：把 KV Cache 切分成固定大小的 Block（如 16 个 Token 一个 Block），每个请求按需动态申请 Block，不需要连续显存，用完即释放。
  • 内存共享：多个请求如果共享同一个 Prompt 前缀（如 System Prompt），它们的 KV Cache Block 可以物理上共享同一块显存，进一步节省空间。

▎深入解释

把传统 KV Cache 想象成停车场——每个请求来了，管理员必须给它预留一整排连续车位（比如 100 个），不管它实际停几辆车。结果停车场很快就满了，但实际利用率不到 20%。PagedAttention 则像共享单车的停车点——每个请求需要几个车位就占几个，用完立刻释放，不同请求还可以共享同一个 System Prompt 的“公共车位区”。

在 128K 长上下文场景下，这个问题的严重性成倍放大。一个 128K 上下文的请求，KV Cache 可能占用几十 GB 显存。如果 10 个并发请求每个都预留 128K 的空间，总显存需求直接爆炸。PagedAttention 让每个请求只占用实际使用的 Token 数对应的显存，让单卡 H200 能同时处理几十个长上下文请求。

▎面试加分点

  • 提到 vLLM 的 Continuous Batching：传统批处理必须等一个 Batch 内所有请求都生成完才能释放，vLLM 可以在一个请求生成完后立刻把它踢出 Batch，换入新请求，GPU 利用率更高。
  • 实战数据：在双卡 4090 部署 Qwen 3.5-32B INT4 时，vLLM 可以支撑 5-10 个并发用户流畅访问；用 Transformers 可能 2-3 个就卡了。
  • 提到 vLLM 的 Prefix Caching：对于 Agent 场景中反复使用的 System Prompt，vLLM 会自动缓存其 KV Cache，后续请求直接复用，TTFT 大幅降低。

▎常见误区

  • 误区：以为 vLLM 只是“更快的 Transformers”。两者的架构设计哲学完全不同，vLLM 是为高并发服务设计的推理引擎，Transformers 更适合单请求的离线推理。
  • 误区：以为 PagedAttention 会带来额外开销。实际上 Block 管理的开销极小（<1%），远小于碎片化带来的浪费。

📌 概念题 · Q7

考点标签

Docker 镜像分层与多 Dockerfile 策略 · 难度：⭐⭐⭐

📝 题目

在 LangGraph 自研多智能体系统中，为什么推荐使用“多 Dockerfile 方案”分别为 Router Agent（轻量 CPU 任务）和 Data Agent（重量级 GPU 任务）构建独立镜像，而不是将所有依赖打入一个通用镜像？这种策略对 K8s 弹性伸缩的容器冷启动时间有何影响？

💡 参考答案

▎一句话结论

多 Dockerfile 方案的核心价值是“按需打包依赖”——让轻量 Agent 的镜像保持小巧（几百 MB），避免 GPU 依赖（torch、CUDA 驱动等几个 GB）拖慢镜像拉取速度，从而在 K8s 弹性伸缩时实现秒级冷启动。

▎核心原理

  • 镜像体积对冷启动的影响：K8s 在扩容新 Pod 时，需要先从镜像仓库拉取镜像到节点。一个包含 torch + CUDA 的镜像通常 5-10 GB，拉取可能需要 1-3 分钟；而一个纯 Python 的轻量镜像只有 300-500 MB，拉取只需 10-30 秒。
  • 依赖隔离：Router Agent 只需要 FastAPI + LangGraph 核心库，Data Agent 还需要 torch、pandas、numpy、CUDA 驱动。如果全打在一起，Router Agent 的容器也要被迫承载这些“死重”。
  • Docker 镜像分层：即使多个镜像共享相同的基础层（如 python:3.10-slim），一旦上层有差异（如安装了 torch），整个层就会分叉，体积差异巨大。

▎深入解释

把 Docker 镜像想象成搬家用的纸箱。多 Dockerfile 方案相当于给不同的房间准备不同大小的箱子——书房的书籍用小箱子（Router Agent），厨房的锅碗瓢盆用大箱子（Data Agent），各取所需。通用镜像方案则是把所有东西全塞进一个巨无霸箱子，即使你只需要一本书，也得把整个箱子搬过去。

在 LangGraph 多智能体架构中，Router Agent 通常只做意图分类和路由分发，纯 CPU 计算，不需要 GPU。Data Agent 则需要加载本地模型做推理或执行复杂的数据分析。两者的资源需求、依赖环境完全不同，强行合并镜像不仅浪费存储和带宽，还会在 K8s 调度时造成资源浪费——Router Agent 的 Pod 被调度到 GPU 节点上，占着 GPU 资源却不用。

▎面试加分点

  • 提到阿里云 ACR（容器镜像服务）的镜像加速能力，可以进一步缩短拉取时间。
  • 实战经验：CI/CD 流水线中通过 docker build -f Dockerfile.router 和 docker build -f Dockerfile.data_agent 分别构建，推送到同一个命名空间下的不同仓库。
  • 解耦的关键：每个 Agent 通过 FastAPI 封装成独立服务，通过 K8s Service 进行网络通信，镜像独立不影响业务逻辑。

▎常见误区

  • 误区：以为“镜像越多管理越复杂”。实际上，多 Dockerfile 都在同一个代码仓库中维护，构建脚本统一管理，复杂度可控。
  • 误区：为了省事把所有依赖都写在 requirements.txt 中。应该拆分为 requirements-base.txt（公共依赖）和 requirements-gpu.txt（GPU 专用依赖），让轻量镜像只装基础依赖。

📌 概念题 · Q8

考点标签

模型量化与显存数学 · 难度：⭐⭐⭐⭐

📝 题目

企业计划使用 2 张 NVIDIA RTX 4090 D（共 48GB 显存）运行 Qwen 3.5-32B 的 INT4 量化版模型。请从显存数学角度分析：32B 参数模型在 INT4 量化下理论占用多少显存？剩余的显存能否支撑 128K 上下文的 KV Cache 和并发请求？如果不够，瓶颈在哪里？

💡 参考答案

▎一句话结论

32B 模型 INT4 量化后模型权重约占用 16-18 GB 显存，剩余约 30 GB 可用于 KV Cache；在 128K 上下文场景下，单个请求的 KV Cache 就可能吃掉 10-15 GB，双卡 48GB 总显存在长上下文高并发下仍然吃紧，瓶颈在于 KV Cache 的线性膨胀而非模型权重。

▎核心原理

  • 模型权重计算：32B 参数 × 4 bit（0.5 Byte）= 16 GB（理论值）。实际部署中，由于量化开销、推理框架元数据等，通常占用 18-20 GB。
  • KV Cache 计算：KV Cache 大小 = 2 × 层数 × 隐藏维度 × 上下文长度 × 精度。Qwen 3.5-32B 约 64 层，隐藏维度约 4096，128K 上下文在 FP16 精度下：2 × 64 × 4096 × 131072 × 2 bytes ≈ 137 GB（理论最大值，实际通过分页和共享会少很多）。
  • 显存分配：双卡 4090 D 共 48GB，模型权重占 18GB，剩余 30GB。30GB 在 128K 上下文下，大概只能支撑 2-3 个并发请求的 KV Cache。

▎深入解释

把显存想象成一个书桌。模型权重是一套 32 卷的百科全书，占了你书桌的 1/3 空间（18GB）。KV Cache 是每个读者（请求）摊开的笔记本——读者的上下文越长，笔记本摊得越大。128K 上下文相当于一个读者摊开了半张书桌那么大的笔记本。来 3 个读者，书桌就满了。

在 vLLM 的实际部署中，PagedAttention 会优化 KV Cache 的分配，但 128K 上下文仍然是巨大的显存杀手。如果业务场景确实需要长上下文，可以考虑：
- 限制最大上下文长度到 32K 或 64K，业务上通过 RAG 检索来弥补上下文窗口的不足。
- 升级到单卡 48GB 的 RTX 6000 Ada 或 A6000，或者使用 4 卡 H200 集群。
- 采用 INT4 + 上下文压缩（如 LLMLingua）的组合策略。

▎面试加分点

  • 显存数学是面试官最爱追问的点，能现场口算模型权重 + KV Cache 的显存占用，直接体现工程功底。
  • 提到 AWQ 量化相比普通 INT4 的优势：AWQ 保留了对推理精度影响大的权重通道，在几乎不损失效果的前提下实现 4-bit 量化。
  • 实战经验：vLLM 的 --gpu-memory-utilization 参数可以限制显存使用比例（如 0.90），留出余量防止 OOM。

▎常见误区

  • 误区：只看模型权重占用，忽略了 KV Cache 才是长上下文场景的显存杀手。
  • 误区：认为 INT4 量化后模型效果会大幅下降。对于 32B 级别的模型，AWQ INT4 的精度损失通常不到 1%，在 RAG 和 Agent 场景下几乎无感知。

📌 概念题 · Q9

考点标签

Agent 数据清洗优先级 · 难度：⭐⭐⭐

📝 题目

在企业本地部署 Agent 的落地建议中，知识库强调“将 80% 的精力花在清洗企业内部私有数据上，效果提升远比把模型从 32B 升级到 70B 显著”。请从技术原理角度解释：为什么数据清洗（如消除乱码、做好文本切片 Chunking）对 RAG 检索质量的提升，可能远超模型参数量的增加？

💡 参考答案

▎一句话结论

RAG 系统的质量天花板由“检索到的上下文质量”决定，而不是模型大小——如果检索回来的文档是乱码、截断的、文不对题的，即使 70B 模型也无法给出正确答案；反之，精准的切片和干净的文本能让 7B 模型也表现出色。

▎核心原理

  • Garbage In, Garbage Out：LLM 的推理能力再强，也无法从一堆乱码或无关文本中提取出正确答案。RAG 的本质是“给模型正确的参考资料”，资料质量直接决定输出质量。
  • Chunking 的语义完整性：如果切片切断了上下文（比如把一个政策的“适用条件”和“执行标准”切到了两个 Chunk 里），向量检索时可能只召回其中一半，模型看到的是一份残缺的文档。
  • 数据清洗消除噪声：PDF 中的页眉页脚、水印、表格错位、OCR 识别错误等，都会污染 Embedding 向量的语义表达，导致检索时“答非所问”。

▎深入解释

把 RAG 系统想象成一个开卷考试。模型是考生，检索到的文档是参考资料。如果你给考生一本印刷清晰、目录完整、段落分明的参考书，他很快就能找到答案。如果你给他一堆被水泡过、页码混乱、缺页漏页的废纸，即使他是博士生也无能为力。

在实际的企业数据清洗中，常见的问题包括：
- PDF 中的双栏排版导致段落顺序错乱。
- 扫描件 OCR 后产生的乱码和错别字。
- 企业内部 Wiki 中的 Markdown 格式错误。
- 合同文档中的页眉页脚混入正文。

这些问题的修复，远比把模型从 32B 换成 70B 便宜且有效。一个 32B 模型 + 高质量数据的 RAG 系统，往往比 70B 模型 + 脏数据的系统表现更好。

▎面试加分点

  • 提到具体的清洗工具：Unstructured.io 用于 PDF/Word 解析，LangChain 的 RecursiveCharacterTextSplitter 用于智能切片。
  • 实战经验：切片大小（Chunk Size）和重叠量（Overlap）需要根据文档类型调参——政策文档适合 512 Token 的较小切片，技术手册适合 1024 Token 的较大切片。
  • 提到“数据飞轮”概念：Agent 上线后，用户的行为反馈（点击、点赞、纠错）可以反哺数据质量，形成正向循环。

▎常见误区

  • 误区：认为“模型越大效果一定越好”。在 RAG 场景下，检索质量才是瓶颈，模型大小是次要因素。
  • 误区：数据清洗是一次性工作。企业数据是持续增长的，需要建立数据管道的自动化清洗流程，而不是手动处理。

📌 概念题 · Q10

考点标签

ACK Serverless 与 SAE 选型 · 难度：⭐⭐⭐⭐

📝 题目

在阿里云上部署 LangGraph 自研多智能体系统时，ACK Serverless（Serverless K8s）和 SAE（微服务应用引擎）都是 Serverless 形态，但定位不同。请解释两者的核心区别，以及为什么复杂的 Multi-Agent 系统更适合 ACK Serverless 而不是 SAE？

💡 参考答案

▎一句话结论

ACK Serverless 是“有 K8s API 的 Serverless”，保留了完整的 K8s 编排能力（如 GPU 调度、自定义 CRD、Helm Chart）；SAE 是“屏蔽 K8s 复杂性的 Serverless”，只提供应用级抽象。复杂 Multi-Agent 系统需要异构算力调度、有状态存储挂载、多服务编排，必须用 ACK Serverless。

▎核心原理

  • 控制粒度不同：ACK Serverless 暴露完整的 K8s API，你可以用 YAML 精确控制每个 Agent 容器的资源规格（CPU/GPU）、挂载 NAS 存储、配置网络策略；SAE 只提供“传个镜像，帮你跑起来”的应用级抽象，无法做细粒度的 K8s 级配置。
  • GPU 调度能力：ACK Serverless 原生支持 GPU 节点的弹性伸缩，可以通过 nvidia.com/gpu 资源声明为 Data Agent 分配 GPU；SAE 对 GPU 的支持有限，不适合需要 GPU 推理的 Agent 节点。
  • 生态兼容性：LangGraph 的很多生产部署方案（如 Helm Chart、KubeRay 分布式调度）都基于 K8s 生态，ACK Serverless 可以直接复用这些方案；SAE 则需要重新适配。

▎深入解释

把 ACK Serverless 想象成租用了一个全功能的专业厨房——你可以自由配置灶台（GPU）、冰箱（NAS 存储）、排烟系统（网络策略），想做什么菜都可以。SAE 则像是一个共享厨房的“代炒”服务——你把食材（Docker 镜像）交给师傅，他帮你炒好端出来，但你不能控制他用什么锅、开多大火。

在 LangGraph Multi-Agent 系统中，Router Agent 只需要 0.5 核 CPU + 512MB 内存，Data Agent 需要 1 张 GPU + 8GB 显存，Code Sandbox Agent 需要独立的安全沙箱（ECI 隔离）。ACK Serverless 可以为每个 Agent 节点定义独立的 Pod 规格和调度策略，SAE 则很难优雅地处理这种异构需求。

▎面试加分点

  • 提到 ACK Serverless 的“缩容到 0”能力：当 Agent 服务没有请求时，Pod 数量可以缩到 0，完全不产生计算费用（只保留 NAS 存储费用），这对非 7×24 运行的内部系统极为省钱。
  • 实战经验：ACK Serverless + ECI（弹性容器实例）可以实现 Agent 代码执行沙箱的“用完即毁”隔离，比 SAE 更安全。
  • 选型建议：如果只是跑一个简单的 Dify 前端或单 Agent 对话服务，SAE 够用；一旦涉及 Multi-Agent 编排、GPU 推理、有状态存储，必须上 ACK Serverless。

▎常见误区

  • 误区：以为“Serverless = 简单”。ACK Serverless 虽然不需要管理服务器节点，但仍需要懂 K8s 的 YAML 语法和网络概念，学习曲线比 SAE 陡。
  • 误区：认为 SAE 比 ACK Serverless 便宜。SAE 按应用实例计费，ACK Serverless 按 Pod 实际资源占用计费，对于间歇性运行的 Agent 服务，ACK Serverless 的“缩容到 0”可能更省钱。

🛠 应用题 · Q1 · 架构设计

题型

架构设计

场景标签

LLMOps 推理加速 成本优化

📝 题目

你正在设计一个面向 3000 名客户经理的“财富管理 Agent 助手”，需要模型具备极高的逻辑推理能力以准确调用理财接口并计算收益。团队内部有两种技术声音：
- 方案 A：使用 vLLM 部署 72B 模型，保持 BF16 高精度，依赖 4 卡 H200 的强大算力硬抗。
- 方案 B：引入 TensorRT-LLM 对 72B 模型进行 FP8 量化，并利用其优化过的 Kernel 和 In-flight Batching 机制，部署在 2 卡 H200 上。

作为架构师，请你从推理吞吐、延迟、显存利用率、长期运维成本四个维度，对比这两种方案的优劣，并给出你的最终选型建议。

💡 参考答案

▎解题思路

  1. 明确业务核心约束：金融场景下，精度是生命线，任何量化带来的精度损失都可能导致计算错误，这是首要评估点。其次才是推理速度和成本。
  2. 拆解技术栈差异：方案 A 的核心是“高精度 + 大显存带宽”，方案 B 的核心是“极致优化 + 量化”。需要理解 TensorRT-LLM 相比通用框架 vLLM 在 Kernel 融合和推理调度上的独特优势。
  3. 建立评估维度：
    • 推理吞吐：是否能承载 3000 人并发下的高 QPS？
    • 延迟：复杂推理任务（如多步收益计算）的 TPOT 是否在可接受范围内？
    • 显存利用率：如何最大化利用昂贵的 H200 显存，避免碎片和浪费？
    • 长期运维成本：硬件投入、电力消耗、模型升级迭代的灵活性。

▎详细方案

  • 方案 A（vLLM + BF16）：这是最“简单粗暴”但稳健的方案。

    • 优势：BF16 精度无损，完全规避了量化带来的精度风险。vLLM 的 PagedAttention 机制能高效管理 KV Cache，配合 4 卡 H200 的 NVLink 互联，在 128K 长上下文下表现稳定，不会出现卡顿。
    • 劣势：成本高昂。4 卡 H200 服务器的采购、电力和散热成本是 2 卡方案的一倍。显存虽然大（564GB），但 BF16 模型本身占用就很高，留给 KV Cache 的显存空间被压缩，限制了极限并发下的批处理能力。

  • 方案 B（TensorRT-LLM + FP8）：这是追求极致性能与成本平衡的方案。

    • 优势：首先，TensorRT-LLM 通过算子融合和图优化，能榨干 GPU 的计算潜力。其次，其 In-flight Batching 机制比 vLLM 的 Continuous Batching 更激进，能将不同请求的推理阶段（Prefill/Decode）混合调度，极大提升 GPU 利用率。FP8 量化在 H200 上能获得硬件级加速，使模型显存占用近乎减半，从而在仅 2 卡 H200 上就能装下模型并留出巨大 KV Cache 空间，支撑更高并发。
    • 劣势：FP8 量化存在理论上的精度损失，需要经过严格的模型精度评测（如使用 lm-evaluation-harness 跑金融相关的基准测试）。TensorRT-LLM 的部署和调试相对复杂，对工程师能力要求更高。

▎关键细节 & 踩坑点

  • 精度验证是前提：在选择方案 B 前，必须进行 A/B 测试。准备 1000 个典型的、包含复杂计算逻辑的理财产品查询 case，分别让两个方案回答，并自动比对结果。只有当 FP8 量化模型的准确率达到 99.9% 以上，才能被金融场景接受。
  • NVLink 的价值：在方案 B 中，2 卡 H200 之间如果没有 NVLink 桥接器，张量并行（TP=2）的效率会因 PCIe 带宽瓶颈而大打折扣，直接抵消掉部分优化收益。必须确保硬件配置支持 NVLink。

▎可扩展优化

  • 动态模型加载：未来如果引入多个专家模型（如一个专精保险，一个专精基金），可以基于 TensorRT-LLM 的 Triton 推理服务器，实现模型的动态加载和卸载，进一步提升资源利用率。
  • 请求优先级调度：在 LLMOps 平台（如 TrueFoundry）层，为 VIP 客户经理或紧急交易请求设置高优先级，确保其推理延迟不受普通查询请求的影响。

🛠 应用题 · Q2 · 场景分析

题型

场景分析

场景标签

本地部署 ROI 分析 架构演进

📝 题目

一家大型上市汽车集团计划打造一个“超级中央大脑”，用于联动研发、销售、车机和售后系统，日常有上万名员工和智能体并发调用。CIO 看到了两个落地路径：

LangGraph 容器化 CI/CD

📝 题目

你正在使用 LangGraph 构建一个多智能体系统，包含 Router Agent（轻量 CPU 任务）和 Data Agent（需加载 PyTorch、Pandas 等重量级 GPU 依赖）。你需要将它们打包并部署到 K8s 集群上。请设计一套基于多 Dockerfile 的工程化方案，并重点说明：
1. 如何组织你的代码仓库目录结构。
2. 如何编写这两个 Agent 的 Dockerfile 以实现镜像体积和构建效率的最优化。
3. 在 CI/CD 流水线中，如何实现当仅修改 router_agent.py 时，只触发 Router Agent 镜像的构建和部署？

💡 参考答案

▎解题思路

  1. 镜像分离：利用多 Dockerfile 方案，从物理上隔离两个 Agent 的依赖。让轻量的 Router 镜像保持几十 MB 级别，实现秒级拉取和快速弹性伸缩；让重量级 Data Agent 镜像包含所有 GPU 库，虽然体积大，但功能完整。
  2. 构建优化：利用 Docker BuildKit 的缓存挂载和多阶段构建特性，优化构建速度。关键在于正确编排 COPY 指令的顺序，将不常变的 requirements.txt 放在前面，代码放在后面，最大化利用层缓存。
  3. CI/CD 精准触发：利用 Git Diff 来判断哪些文件被修改，并结合 CI 工具的 rules:changes 或 paths-filter 功能，实现仅构建和部署变更的服务。

▎详细方案

  1. 代码仓库目录结构：
    my-langgraph-app/ ├── agents/ │ ├── router_agent.py │ └── data_agent.py ├── server/ │ ├── run_router.py # FastAPI 入口 │ └── run_data_agent.py # FastAPI 入口 ├── requirements.txt # 两个 Agent 的公共基础依赖 ├── requirements-data.txt # Data Agent 专有依赖(torch, pandas等) ├── Dockerfile.router └── Dockerfile.data_agent

  2. 编写 Dockerfile：

    • Dockerfile.router (轻量)：
      dockerfile FROM python:3.10-slim WORKDIR /app # 先复制依赖文件，利用 Docker 层缓存 COPY requirements.txt . RUN pip install --no-cache-dir -r requirements.txt # 最后复制代码，代码变更不会导致依赖层重建 COPY . . CMD ["python", "server/run_router.py"]
    • Dockerfile.data_agent (重量级)：
      dockerfile FROM nvidia/cuda:12.1.0-runtime-ubuntu22.04 RUN apt-get update && apt-get install -y python3-pip python3-dev WORKDIR /app COPY requirements.txt requirements-data.txt ./ RUN pip install --no-cache-dir -r requirements.txt -r requirements-data.txt COPY . . CMD ["python", "server/run_data_agent.py"]

  3. CI/CD 流水线配置（以 GitLab CI 为例）：
    ```yaml
    # .gitlab-ci.yml
    stages:

    • build

    build-router:
    stage: build
    rules:
    # 仅当 router_agent.py 或其 Dockerfile 变更时触发
    - changes:
    - agents/router_agent.py
    - server/run_router.py
    - Dockerfile.router
    script:
    - docker build -f Dockerfile.router -t $REGISTRY/router:$CI_COMMIT_SHA .
    - docker push $REGISTRY/router:$CI_COMMIT_SHA

    build-data:
    stage: build
    rules:
    - changes:
    - agents/data_agent.py
    - server/run_data_agent.py
    - Dockerfile.data_agent
    - requirements-data.txt # 依赖变更也要触发
    script:
    - docker build -f Dockerfile.data_agent -t $REGISTRY/data:$CI_COMMIT_SHA .
    - docker push $REGISTRY/data:$CI_COMMIT_SHA
    ```

▎关键细节 & 踩坑点

  • .dockerignore 至关重要：必须在项目根目录创建 .dockerignore 文件，排除 __pycache__、.git、venv 等无关文件夹，否则会污染构建上下文，导致 COPY . . 时复制了无用文件，并破坏 Docker 缓存。
  • GPU 驱动依赖：Data Agent 的 Dockerfile 中，必须使用与宿主机（K8s Node）CUDA 版本兼容的 NVIDIA 基础镜像，否则容器将无法调度和使用 GPU 资源。

▎可扩展优化

  • 多阶段构建：对于 Data Agent，可以引入多阶段构建。第一阶段安装所有依赖，第二阶段只复制必要的运行时库和代码，这样可以进一步减小最终镜像的体积。
  • 通用基础镜像：如果团队有多个类似项目，可以构建一个内部公用的 base-gpu-agent:latest 基础镜像，预装 PyTorch 等通用库，各个项目的 Dockerfile 直接 FROM 这个基础镜像，能极大缩短构建时间。

LLMOps 显存管理 推理框架

📝 题目

你的团队负责维护一个基于 vLLM 部署的 Qwen 3.5-32B 量化模型服务，运行在 2x NVIDIA RTX 4090 D (48GB) 上。某天业务高峰时，用户反馈对话响应极慢，甚至出现超时报错。你通过 nvidia-smi 和 LLMOps 监控平台发现以下现象：
1. GPU 利用率在 20% ~ 80% 之间剧烈波动，没有稳定在 100%。
2. 显存占用率持续在 98% 以上，接近满载。
3. TPOT（每个 Token 生成时间）飙升至正常值的 5-10 倍。
4. dmesg 命令显示无硬件报错。

请根据以上现象，分析最可能的根本原因，并给出排查步骤和优化方案。

💡 参考答案

▎解题思路

  1. 现象关联分析：高显存占用 + 低且波动的 GPU 利用率 + 高延迟，这是典型的显存成为瓶颈，导致计算资源空转的现象。GPU 在等待显存空间被释放，无法高效地加载新的计算任务。
  2. 定位根本原因：vLLM 的核心是 PagedAttention，它管理着 KV Cache。98% 的显存占用率说明 KV Cache 几乎被耗尽。这通常由两个原因导致：
    • 并发请求过高：大量用户同时发起请求，每个请求的 KV Cache 把显存池占满。
    • 长序列请求：某个或某些请求的上下文（Context）非常长（例如用户上传了超长文档进行问答），导致单个请求占用了巨大的 KV Cache 块。
  3. 制定排查与优化策略：需要先定位是哪个请求是“元凶”，然后从调度、限制和硬件三个层面进行优化。

▎详细方案

  • 排查步骤：

    1. 查看 vLLM 日志：vLLM 在显存压力大时会打印日志，如 “Waiting for sequence group to be swapped in...” 或 “Preempting...”。这会直接证实显存不足导致请求被抢占和排队。
    2. 分析请求序列长度：在 LLMOps 平台（如 W&B Weave）中，筛选出 TPOT 最高的那几个请求，查看它们的 prompt_tokens 数量。如果发现某个请求的 prompt 长度高达几十 K，那它就是“显存杀手”。
    3. 验证 KV Cache 使用情况：vLLM 的 /metrics 接口会暴露 vllm:gpu_cache_usage_perc 指标，确认其是否长期处于 100%。

  • 优化方案：

    1. 应用层限流与熔断：立即在应用网关层（如 Nginx 或 API Gateway）实施最大并发请求数限制（Rate Limiting），将超出服务能力的请求直接快速失败，避免压垮推理服务。
    2. 限制最大输入长度：在 vLLM 启动参数中，明确设置 --max-model-len 为一个合理值（如 8192 或 4096）。这会强制拒绝或截断那些过长的请求，从源头保护显存。
    3. 启用 Prefix Caching：vLLM 支持 Automatic Prefix Caching（APC），如果多个请求共享相同的 System Prompt 或长文档前缀，APC 可以让它们复用同一份 KV Cache，显著节省显存。确保启动时已开启此功能。
    4. 调整 gpu_memory_utilization：vLLM 默认的显存利用率可能过高（如 0.9）。可以尝试将其调低到 0.85，为 KV Cache 的分配和回收预留更多缓冲空间，避免因碎片化导致 OOM。

▎关键细节 & 踩坑点

  • 波动的 GPU 利用率是核心线索：如果只是单纯的高显存占用，但 GPU 利用率持续 100%，说明系统在高效运行。而剧烈波动说明 GPU 核心大部分时间在“等待”显存控制器搬运数据，这是显存瓶颈的典型特征。
  • 不要盲目增加 max_num_seqs：这个参数控制最大并发序列数。在显存已经不足的情况下，盲目增大此参数会加剧 KV Cache 争抢，导致系统更频繁地进行“抢占”（Preemption），性能反而会断崖式下跌。

▎可扩展优化

  • 异构请求路由：在架构中引入一个 Router Agent，对请求进行分类。将短平快的闲聊路由到当前 4090 集群，而将需要长文档分析的“重”请求路由到一个专门的、显存更大的 H200 推理节点上，实现资源的物理隔离和最优匹配。

HR Agent 数据库设计 安全合规

📝 题目

你作为项目负责人，需要为一家中型企业从 0 到 1 交付一个“HR 简历筛选与智能推荐 Agent”。核心需求如下：
1. 数据安全：简历库涉及大量个人隐私，数据严禁外流。
2. 核心功能：Agent 能自动分析岗位 JD，从公司内部一个月内的简历库中筛选出 Top 5 候选人，并生成一份包含匹配度、优劣势分析的推荐报告。
3. 人机协同：报告生成后，必须推送给 HR 进行人工审阅，HR 可以一键通过系统联系候选人，并被告知推荐的岗位信息和面试技巧。
4. 状态持久化：所有筛选、推荐、HR 操作记录都必须有日志可查。

请你设计一套完整的技术方案，重点阐述：① 本地模型选型与部署架构；② 基于 PostgreSQL 的混合数据存储设计（如何同时存储简历、向量、对话日志和任务状态）；③ 实现“人机协同”工作流的核心逻辑。

💡 参考答案

▎解题思路

  1. 满足数据安全：所有数据处理必须在企业内网完成，采用本地部署的开源模型和数据库，杜绝任何 API 调用。
  2. 技术选型：基于知识库，采用“方案 A”的轻量化本地部署方案，成本低，见效快。
  3. 数据库设计：利用 PostgreSQL 的“三位一体”能力（传统 SQL + JSONB + pgvector），用一个数据库解决结构化存储、向量检索和半结构化日志三大需求，简化架构。
  4. 工作流设计：利用 LangGraph 编排一个“机审 -> 人审 -> 行动”的有状态工作流，并在关键节点引入 Human-in-the-loop 机制。

▎详细方案

  1. 模型选型与部署：

    • 硬件：1 台配备 2x RTX 4090 D (48GB) 的服务器。
    • 推理框架：vLLM，支持并发和高效推理。
    • 模型：Qwen 3.5-32B INT4 量化版，用于简历解析、JD 分析和报告生成。再部署一个轻量的 bge-large-zh-v1.5 Embedding 模型用于向量化。
    • 前端：AnyIn 或自研的轻量 Web UI。

  2. PostgreSQL 混合数据存储设计：

    • 简历向量库：创建表 resume_vectors，包含字段 id, candidate_id, chunk_text, embedding vector(1024)。使用 pgvector 插件，并在 embedding 列上建立 HNSW 索引，用于语义检索。
    • 结构化业务表：
      • candidates：存储候选人 ID、姓名、联系方式等固定信息。
      • job_descriptions：存储岗位 JD ID、标题、要求等。
      • tasks：任务表，核心字段包括 task_id, status (processing/pending_human_review/completed), jd_id, result_jsonb (JSONB 类型，存储 Top 5 候选人的 ID 和评分)。
    • 对话与日志表：agent_logs，核心字段 log_id, task_id, timestamp, event_type, payload JSONB。event_type 记录 “jd_analysis_started”, “candidate_selected”, “report_sent_to_hr” 等事件，payload 用 JSONB 存储每步的详细输入输出。

  3. “人机协同”工作流核心逻辑（基于 LangGraph）：

    • 节点 1：JD 解析与向量检索。Agent 接收 JD，解析出关键技能和需求，生成向量并在 resume_vectors 中检索。
    • 节点 2：深度分析与报告生成。将检索到的 Top 10 简历和 JD 一起送入 LLM，生成初步推荐报告（Top 5）。
    • 节点 3：Human-in-the-loop 中断点。这是一个关键节点。LangGraph 执行到此处会 interrupt，将任务状态更新为 pending_human_review，并将生成的报告通过 UI 推送给 HR。此时，Agent 工作流挂起，等待人的指令。
    • 节点 4：HR 审阅与行动触发。HR 在 UI 上看到报告，可以修改候选人排序，或直接点击“确认并联系”。这个操作会触发一个 API，恢复 LangGraph 工作流，并传入 HR 的指令。
    • 节点 5：执行与通知。Agent 接收到 HR 的“确认”指令后，使用 FOR UPDATE 悲观锁更新 tasks 表状态，防止重复操作。然后调用内部邮件或 IM 接口联系候选人，并将最终结果和 HR 的操作一并记录到 agent_logs 中。

▎关键细节 & 踩坑点

  • 数据库操作安全：Agent 在操作 candidates 和 tasks 表时，必须遵循“读放行、写拦截”原则。任何增删改操作（如更新任务状态、记录日志）都应通过独立的、经过严格校验的 Tool 函数执行，而绝不能直接给 Agent 裸 SQL 权限。
  • 悲观锁的必要性：在“HR 审阅”环节，必须使用 SELECT ... FOR UPDATE 锁定任务行。防止多个 HR 或系统重试机制导致对同一个任务重复下发指令，造成候选人被重复联系的事故。

▎可扩展优化

  • 人才画像沉淀：Agent 运行一段时间后，可以从 agent_logs 和 tasks 表中分析出高频筛选维度和最终入职候选人的特征，反哺 JD 解析节点，让 AI 的推荐越来越精准。
  • 降级方案：如果向量检索负载过高，可以在应用层设计一个开关，临时降级为使用 PgSQL 自带的全文检索（tsvector）进行关键词匹配，保证核心筛选流程不中断。
