📌 概念题 · Q1

考点标签

Agent 架构 · 高可用 · 难度：⭐⭐⭐⭐

📝 题目

在分布式多 Agent 集群中，知识库提到了“不要做一个总 Agent 来路由分发”，而应采用“统一网关 + 平级协作”模式。请问，在这个架构下，当智能客服 Agent 需要调用自媒体文案 Agent 的能力时，为什么不能简单地通过网关进行同步 HTTP 调用？这种跨 Agent 协作中，如何处理“长耗时任务”（如生成一组配图需要 2 分钟）可能导致的调用超时和资源阻塞问题？

💡 参考答案

▎一句话结论

跨 Agent 协作应避免同步 HTTP 调用，必须采用“异步委托 + 结果回调”或消息队列模式，将长耗时任务从请求-响应链路中剥离，防止级联阻塞和资源耗尽。

▎核心原理

  • 同步调用的级联故障风险：如果客服 Agent 同步等待自媒体 Agent 2分钟，其自身的 HTTP 连接、线程和内存会一直被占用，高并发下会迅速耗尽资源，导致整个客服系统不可用。
  • 超时控制的困境：为同步调用设置一个小于任务执行时间的超时（如 30s）会导致任务失败；设置一个过长超时（如 3min）则失去了超时保护的意义，且调用方无法区分任务是“正在执行”还是“已经挂了”。
  • 计算资源与IO等待的不匹配：Agent 是计算与IO密集型应用，同步等待本质上是让昂贵的计算资源（CPU/GPU）空转，等待网络IO（等待文案生成），这是巨大的成本浪费。

▎深入解释

这个问题触及了分布式系统设计的核心：如何将异步的、耗时不确定的任务与同步的、期望快速响应的用户请求解耦。
正确的做法是，客服 Agent 在自己的 LangGraph 工作流中，到达“需要生成文案”的节点时，不直接发起同步 HTTP 请求，而是做三件事：
1. 异步委托：向一个消息队列（如 Redis Streams， RabbitMQ）或任务队列发送一条消息，内容是：“请为user_id=123生成一份关于岗位X的小红书文案”。
2. 状态中断：客服 Agent 调用 LangGraph 的 interrupt 机制，将当前状态持久化到数据库，并立即释放计算资源。同时向前端用户返回一个友好的等待提示，如“正在为您构思文案，大约需要1-2分钟，请稍候...”。
3. 回调唤醒：自媒体 Agent 作为消费者，从队列中取出任务并执行。完成后，它会通过一个 Webhook 回调客服系统的特定接口，携带任务结果。客服系统的 Webhook 接收端根据 task_id 从数据库恢复会话状态，将文案注入，并主动向前端推送完成的消息。

▎面试加分点

  • 能清晰区分“同步协作”与“异步协作”的业务场景：查询类（如查天气）可以同步；生成类、审批类必须异步。
  • 能提出具体的技术栈组合：如“LangGraph Interrupt + Redis Streams + Webhook 回调”或“Celery 任务队列 + WebSocket 主动推送”。
  • 提到最终一致性思想：不强求实时返回结果，而是保证任务最终完成并通知用户。

▎常见误区

  • 误区：认为加上足够的超时重试机制就能解决同步调用问题。重试只会加剧系统负担，在任务本身就很慢的情况下，重试大概率也会失败。
  • 误区：过度设计，为了一个简单的文案生成引入一套复杂的消息中间件。对于低频、非核心的联动，一个带状态回调的异步 HTTP 请求池也足够。

📌 概念题 · Q2

考点标签

架构设计 · 多租户 · 难度：⭐⭐⭐

📝 题目

知识库在“外部系统集成”部分提到了多租户环境下，通过 project_id 在向量数据库中划分独立 Collection 实现“知识库物理隔离”。请问，这种“物理隔离”与在同一个 Collection 内通过 metadata 字段进行过滤的“逻辑隔离”相比，在数据安全、性能和运维成本上有何本质区别？为什么企业级应用更倾向于物理隔离？

💡 参考答案

▎一句话结论

物理隔离提供了更强的数据安全边界和性能确定性，从根本上避免了租户间数据泄露和“噪声邻居”效应；逻辑隔离虽然成本低，但在安全审计和性能隔离上存在天然缺陷，不适合数据敏感的企业级场景。

▎核心原理

  • 安全隔离级别：物理隔离是“库级别”或“表级别”的隔离，权限控制更直接；逻辑隔离是“行级别”的隔离，完全依赖应用层代码的正确性，一旦过滤条件出现Bug，就会发生灾难性的数据泄露。
  • 性能的“噪声邻居”效应：在逻辑隔离下，一个租户的突发大量查询会消耗同一Collection的CPU、内存和IO，直接影响其他所有租户的响应速度。物理隔离可以将资源争抢限制在单个租户内部。
  • 数据管理与合规：物理隔离使得按租户进行数据导出、备份、迁移或删除变得极其简单和安全。对于GDPR等要求“被遗忘权”的法规，物理隔离可以做到原子化的数据清除，而逻辑隔离需要扫描全量数据进行删除，效率低且易出错。

▎深入解释

我们可以用一个公寓楼的比喻来理解：
- 逻辑隔离就像一栋大公寓里的不同房间，大家共用一个大门和水电总管线。安全完全依赖于每个房间的门锁（代码中的 project_id 过滤）。一旦楼管（应用层）搞错了钥匙，任何人都能进错房间。如果一个房间开派对（高负载），整栋楼的水压（性能）都会下降。
- 物理隔离就像是给你每个租户一栋独立的别墅。别墅之间有物理围墙，拥有完全独立的水电系统。你的安全不依赖于管家是否记性不好，你的生活也不会被邻居的派对干扰。当要拆除一栋别墅时（删除租户数据），直接拆掉就行，不会影响到其他别墅的一砖一瓦。
在企业级产品中，尤其是金融、医疗、政务领域，客户的第一诉求永远是“绝对安全”。物理隔离是向客户和审计机构证明数据安全性的最有力方式。

▎面试加分点

  • 能结合具体技术实现：如 “在 Milvus 中，我们用 Partition 或独立的 Collection 实现物理隔离；在 PostgreSQL 中，我们使用 Schema 或独立 Database。”
  • 提出折中方案：对于小微客户或免费试用版，使用逻辑隔离以节省成本；对于付费大客户，强制使用物理隔离以满足合同要求。
  • 强调 DevOps 成本：承认物理隔离会增加基础设施和运维的复杂度，但这是为了满足非功能性需求（安全、合规）必须付出的代价。

▎常见误区

  • 误区：认为只要代码写得严谨，逻辑隔离就足够安全。这忽视了人为失误、零日漏洞和内部恶意行为等风险。
  • 误区：认为物理隔离成本极高。现代云原生向量数据库的隔离成本已经很低，其带来的安全和运维收益远超其成本。

📌 概念题 · Q3

考点标签

LangGraph · 状态管理 · 容错 · 难度：⭐⭐⭐⭐

📝 题目

知识库在“稳定性与异常容错”部分提到了 LangGraph 的“节点级精准回滚（Time-travel）”，通过 get_state_history 和 update_state 实现。请问，这种“时间旅行”机制与我们常说的“检查点（Checkpoint）恢复”有何本质不同？它在什么场景下是必须的，而简单的“从头重试”无法解决？

💡 参考答案

▎一句话结论

“检查点恢复”是线性的、被动的，只能从失败点重试；而“时间旅行”是非线性的、主动的，允许开发者像操作Git分支一样，从任意历史状态创建一条新的执行路径，用于修复逻辑错误或应对不可重试的副作用。

▎核心原理

  • 恢复的目标不同：检查点恢复的目标是“容错”，假设系统崩溃了，从最近的存档点继续跑；时间旅行的目标是“纠错”或“分支”，假设之前的逻辑走错了，需要回溯并换一条路走。
  • 操作的粒度不同：检查点恢复通常是恢复到最近的一个全局快照；时间旅行可以精确选择历史上任何一个节点执行完毕后的状态点（checkpoint_id），即使那个节点后来被判定为“走错了路”。
  • 对“副作用”的处理不同：这是最关键的区别。如果一个节点执行了不可逆的副作用（如发送了一封邮件、扣减了库存），从头重试或从检查点重试会导致副作用再次发生。时间旅行允许你从副作用发生之前的状态点，修改状态并走一条不包含该副作用的路径。

▎深入解释

想象一个复杂的审批流程 Agent：
1. Agent 走到“自动审批”节点，因为金额小于1万元，它调用了 approve_request 工具，该工具在数据库中标记为“已批准”，并发送了通知邮件。
2. 几秒钟后，一个“风控复核”节点发现该请求存在异常模式，判定应该人工复核。
3. 此时，如果简单地“重试”或“回滚”，系统会尝试再次调用 approve_request，导致重复操作。
4. 而使用“时间旅行”，我们可以：
* 通过 get_state_history 找到“自动审批”节点执行前的那个 checkpoint_id。
* 通过 update_state 将状态机的状态直接修改为“需要人工审批”，并从这个新的状态点继续执行。
* 这样，Agent 就会直接走向“通知人工审批”的路径，完美跳过了已经执行过的、有副作用的节点。我们还需要一个补偿逻辑来处理已发送的通知邮件（如发送一封“撤回”邮件），但核心业务状态被正确修复了。

▎面试加分点

  • 能清晰阐述“副作用”这个核心难点，并给出补偿事务（Compensating Transaction）的思路。
  • 与 Git 操作类比：checkpoint 像 git commit，get_state_history 像 git log，update_state 像 git checkout -b new-branch。
  • 提到在 Human-in-the-Loop 场景的应用：审核人员可以“时光倒流”到流程的任意一步，修改错误的输入信息后，让流程重新执行。

▎常见误区

  • 误区：认为时间旅行是万能的回滚魔法。它只能逆转状态，不能自动逆转现实世界已经发生的副作用。处理副作用需要额外的补偿机制。

📌 概念题 · Q4

考点标签

模型推理 · 成本优化 · 难度：⭐⭐⭐⭐

📝 题目

知识库在“性能优化”中提到了通过“固定 RAG 检索片段排序、合并 System Prompt”等手段来“深度触发模型前缀缓存（Prefix Caching）与 KV Cache 机制”。请详细解释，为什么固定和合并这些前缀内容能够触发缓存？这种优化对于同时处理成千上万个不同用户请求的 Agent 系统，其成本节省的本质是什么？

💡 参考答案

▎一句话结论

大模型的 KV Cache 以 Token 序列的“前缀”为键进行缓存复用。通过精心设计，让所有请求共享一段完全相同的、尽可能长的前缀，可以将这部分计算量从“每次推理”降为“首次推理”，从而节省大量算力和时间。

▎核心原理

  • KV Cache 的工作原理：Transformer 模型在生成每个新 Token 时，需要计算之前所有 Token 的 Key 和 Value 矩阵。为了避免重复计算，推理引擎会将这些 Key 和 Value 缓存下来。
  • 前缀匹配的复用机制：当一个新的请求到来，其初始 Token 序列与缓存中某个已存在的序列的前缀完全一致时，推理引擎可以直接复用该前缀对应的 KV Cache，无需再次计算。
  • 缓存命中率决定成本：节省的成本与缓存前缀的长度成正比。如果你的 System Prompt + Few-Shot Examples + 固定的 RAG 上下文结构有 2000 个 Token，且每个请求都完全一样，那么每次请求都能节省这 2000 个 Token 的计算量。

▎深入解释

想象一个图书馆管理员，每次有人来问“关于AI的书在哪”，他都要从头开始在电脑系统里查询一遍。但后来他发现，每个人问问题前都会先说一句“你好，我是XX大学的学生，我正在进行一项研究”。于是，他一听到这个固定的开场白，就直接跳到“研究”这个关键词之后，从那里开始查询，速度大大提升。
在我们的 Agent 场景中，这个“固定的开场白”就是我们精心构造的、对所有请求都相同的 Prompt 前缀。它包括：
1. 固定的 System Prompt：定义 Agent 的角色、行为准则。
2. 固定的 Few-Shot 示例：教给模型如何思考和输出。
3. 固定的检索片段结构：例如，我们不按相关性动态排序，而是固定为“【背景知识1】...【背景知识2】...”，或者将所有检索到的文档合并成一个长字符串，确保其结构在 Token 层面是固定的。

如果不做此优化，每个用户的请求可能因为检索到的文档顺序不同，导致整个 Prompt 序列完全不同，缓存命中率为零。通过固定化，我们牺牲了极少量的 Prompt 灵活性，换来了巨大的成本和延迟收益。

▎面试加分点

  • 能量化收益：“通过该优化，我们将高并发场景下 80% 的请求前缀缓存命中率提升到 95% 以上，平均首字延迟（TTFT）降低 60%，LLM 推理成本降低约 30%。”
  • 提到与 RAG 策略的结合：这是一种“系统层面”的优化，与“算法层面”的优化（如更好的检索排序）互补。
  • 理解其局限性：前缀缓存对“完全匹配”要求苛刻，任何细微的差异（如多一个空格、时间戳、用户ID）都会导致缓存失效。必须使用模板引擎严格控制 Prompt 的生成。

▎常见误区

  • 误区：认为所有长得像的 Prompt 都能命中缓存。缓存机制是基于 Token ID 序列的精确匹配，不是语义相似度。
  • 误区：只关注 System Prompt 而忽略了 RAG 上下文的顺序和格式。

📌 概念题 · Q5

考点标签

Agent 架构 · 协议设计 · 难度：⭐⭐⭐⭐

📝 题目

知识库中提到了 MCP（模型上下文协议）用于 Agent 向下连接工具，以及 A2A（智能体间通信协议）用于 Agent 之间的横向协同。请问，从架构层面看，MCP 和 A2A 要解决的核心问题有何本质不同？为什么不能直接用 MCP 来实现 Agent 之间的通信，而要单独设计一个 A2A 协议？

💡 参考答案

▎一句话结论

MCP 是为“客户端-服务器”模式设计的工具调用协议，解决的是“如何用”的问题；而 A2A 是为“对等网络”模式设计的协作协议，解决的是“找谁做、做什么、怎么做”的问题。二者的角色、交互模式和抽象层次完全不同。

▎核心原理

  • 角色与拓扑不同：MCP 是一个主从协议。Agent（Client）是主导者，明确知道自己要调用哪个工具（Server）。A2A 是一个对等协议，Agent 之间是平等的，一个 Agent 可能不知道另一个 Agent 的具体能力，需要“发现”。
  • 交互模式不同：MCP 是同步的请求-响应模式，适合短平快的工具调用。A2A 必须支持异步、长周期的任务委托和协商，因为它处理的是“任务”，而不是“函数调用”。
  • 抽象层次不同：MCP 抽象的是“工具”，如 get_weather，search_documents。A2A 抽象的是“智能体能力”和“任务”，如“一个擅长生成小红书文案的 Agent”，它传递的是任务卡片（Task Card），包含任务描述、输入输出格式、截止时间等。

▎深入解释

我们可以用公司内部的协作来类比：
- MCP 就像员工（Agent）使用各种工具：你要查资料，就去用“内部知识库系统”（MCP Server）；你要发邮件，就去用“邮箱客户端”（MCP Server）。你很清楚这些工具在哪，怎么用。
- A2A 就像是员工之间的跨部门协作：你（客服 Agent）需要一份市场分析报告，但你自己不会做。你不能像使用“邮箱客户端”那样去“调用”市场部的小李。你需要做的是：在公司通讯录里发现小李是负责市场分析的（能力发现），然后给他发一个任务：“请在下班前提供一份关于竞品X的分析报告，格式要求见附件”。小李收到任务后，可能会接受、可能会拒绝、可能会问你更多细节（协商），然后他开始异步执行，完成后把报告发给你。

显然，你不能用操作工具的协议去管理人与人之间的复杂协作。同理，MCP 无法处理 Agent 之间的能力发现、任务协商、状态同步和异步回调等复杂需求。A2A 协议正是为了标准化这种“Agent 之间的工作流”而生的。

▎面试加分点

  • 能清晰定义两个协议的边界：MCP 向下，连接数据和工具；A2A 横向，连接其他 Agent。
  • 能预见到未来生态：未来的 Agent 生态中，MCP Server 和 A2A Agent 会像现在的微服务和 API 网关一样成为标准组件。
  • 提到非功能性需求：A2A 需要内置安全认证、任务状态追踪、计费等企业级功能，这些都是 MCP 协议不关心的。

▎常见误区

  • 误区：认为 A2A 是 MCP 的替代品或升级版。它们是解决不同层面问题的互补协议。
  • 误区：认为可以用一个复杂的 MCP Server 来模拟另一个 Agent。这会把 Agent 的智能和状态管理复杂性错误地塞进一个无状态的工具里。

📌 概念题 · Q6

考点标签

Agent 测试 · 工程化 · 难度：⭐⭐⭐

📝 题目

在 Agent Harness 的讨论中，知识库建议使用 pytest 结合 assert 来构建测试用例。请问，与传统软件的单元测试相比，为 AI Agent 编写 assert 断言的难点在哪里？为什么说对 Agent 的测试不能仅仅依赖“精确匹配”（如 assert result == expected），而必须引入“LLM-as-a-Judge”或“模糊匹配”？

💡 参考答案

▎一句话结论

传统软件的输出是确定性的，而 Agent 的输出是非确定性的。因此，Agent 测试的断言不能基于“字符串精确匹配”，必须基于“语义正确性”和“事实一致性”，这需要引入 LLM-as-a-Judge 或设计多维度的模糊评估指标。

▎核心原理

  • 输出的非确定性：同一个问题，Agent 可能给出措辞不同但语义完全正确的答案。assert "您好，很高兴为您服务" == "你好，有什么可以帮您？" 会错误地报告失败。
  • 评估维度的复杂性：Agent 的“正确”是多维度的。对于一个需要调用工具的 Agent，我们不仅要看最终答案对不对，还要看它是否调用了正确的工具、调用的参数是否正确、整个过程的逻辑是否合理。这远不是一个单一返回值能覆盖的。
  • “幻觉”的隐蔽性：Agent 的答案可能在语法上流畅、在风格上专业，但在关键事实上是编造的。这种错误无法通过简单的规则匹配发现，必须依赖外部知识库或更强的模型进行事实核查。

▎深入解释

想象你有一个“建材报价 Agent”。你不可能用 assert result == 100万 来测试，因为：
1. 输出格式不固定：Agent 可能返回“总价是100万元”，也可能是“根据计算，您的报价为1,000,000元”。
2. 正确答案是一个范围：由于市场价波动，合理的报价可能在 95万到105万之间。你需要用 assert 950000 <= result <= 1050000 这种模糊断言。
3. 需要校验过程：Agent 是调用了“计算器工具”算出来的，还是直接编了一个数字？一个更好的测试会去检查 Agent 的执行轨迹（Trace），assert calculator_tool_called == True。
4. 需要评估文本质量：对于客服 Agent，我们无法断言“最佳回复”，但可以断言“回复中不能包含竞品名称”、“回复必须包含解决方案”、“回复语气不能是愤怒的”。这些都需要专门的评估模型。

因此，Agent Harness 中的断言逻辑更像是一套评估规则集。你可以写一个 evaluate_answer(answer, context) 函数，内部调用一个快速的评估模型（LLM-as-a-Judge）来打分，然后用 assert score > 0.8。

▎面试加分点

  • 提出分层测试策略：单元测试测工具函数（确定性），集成测试测 Agent 轨迹（半确定性），端到端测试测最终答案（非确定性，用 LLM-as-a-Judge）。
  • 引入 RAGAS 等评估框架：提到 Faithfulness（忠实度）、Answer Relevancy（答案相关性）、Context Recall（上下文召回率）等具体指标。
  • 强调测试是“护栏”：测试集是防止系统退化（Regression）的唯一手段。

▎常见误区

  • 误区：试图为 Agent 写出完美的、覆盖所有情况的精确断言。这通常是徒劳的，且会让测试极其脆弱。
  • 误区：完全放弃自动测试，依赖人工肉眼评估。这无法规模化，也无法集成到 CI/CD 流程。

📌 概念题 · Q7

考点标签

架构设计 · 状态机 · 难度：⭐⭐⭐⭐

📝 题目

知识库在“企业垂直领域变化”中提到，技术栈正从“重框架”转向“轻量状态机（Graph/Harness）”，并强调利用确定性的状态机来限制 Agent 的跳转路由。请问，这里所说的“确定性的状态机”在 LangGraph 中是如何体现的？它如何解决让“大模型盲猜”下一步动作所带来的不可靠问题？

💡 参考答案

▎一句话结论

在 LangGraph 中，“确定性的状态机”通过“条件边（Conditional Edges）”中的“纯代码函数”来实现，它取代了大模型对工作流路由的控制权，将“下一步做什么”的决策权从非确定性模型转移给确定性的工程代码。

▎核心原理

  • 模型决策 vs. 代码决策：在 ReAct 等早期 Agent 模式中，大模型输出一个“Thought: I need to use a tool, Action: Search”，框架解析这个文本并执行。这是“模型决策”，模型可能在 Thought 中胡说八道，导致调用错误的工具。而状态机通过代码函数 def route(state): if state['intent'] == 'search': return 'search_node' 来决定路由，这是“代码决策”，100% 确定。
  • 定义“合法”的路径图：LangGraph 的图结构（StateGraph）本身就定义了一个有限状态机。节点是状态，边是允许的转换。Agent 只能在这个预定义的“地图”上行走，不能想去哪就去哪。这为 Agent 的行为划定了硬性的安全边界。
  • 分离“思考”与“导航”：这是一种关注点分离。大模型被限制在节点内部进行“思考”（如生成文本、推理参数），但它没有权限决定整个流程的“导航”（下一步去哪个节点）。导航是图结构的事。

▎深入解释

想象一个自动驾驶系统。早期方案是让一个“端到端”大模型直接看路况图片，输出方向盘转角。这很危险，因为模型是个黑盒，你不知道它为什么突然打方向。
更好的方案是模块化设计：
1. 感知模块（Agent节点）：用模型识别出“前方有行人”。
2. 规划/导航模块（状态机/图）：由确定性的代码逻辑决定：“如果前方有行人，则执行刹车流程”。
3. 控制模块（Agent节点）：由模型精确计算刹车力度。
LangGraph 就扮演了“规划/导航模块”的角色。它定义了一个“刹车流程”的子图，当状态机接收到“前方有行人”这个事件时，它会强制将流程路由到“刹车流程”子图。在这个子图内部，Agent 可以用大模型来生成具体的刹车指令，但它绝不能自己决定“忽略行人，继续播放音乐”。这个“忽略行人”的路径，在状态机中根本就不存在。

▎面试加分点

  • 能结合 LangGraph 的具体 API 解释：如 add_conditional_edges 函数，其第一个参数就是纯 Python 函数，这是确定性路由的关键。
  • 提出“大模型只做填空题，不做选择题”：将大模型的职责限制在生成内容（填空），而流程的选择（选择）由代码完成。
  • 强调可测试性：确定性的状态机路径可以像传统软件一样被完整测试，覆盖所有分支。而依赖模型决策的流程则几乎无法穷举测试。

▎常见误区

  • 误区：认为用了 LangGraph 就失去了 Agent 的灵活性。实际上，你可以在条件路由函数里调用大模型来为“意图分类”服务，但最终的“根据意图跳转”这个动作依然由代码完成，这是一种可控的灵活性。
  • 误区：把所有逻辑都硬编码在图中，导致图变得极其复杂和僵化。需要平衡代码决策和模型决策的粒度。

📌 概念题 · Q8

考点标签

微服务 · 架构演进 · 难度：⭐⭐⭐

📝 题目

知识库在讨论仓库设计时，推荐采用“多仓库独立部署”模式，将底层的 MCP 公共服务与上层的业务 Agent 分离。请问，这种拆分模式除了实现“团队开发隔离”和“独立发布”外，在故障隔离和资源弹性伸缩方面带来了哪些更深层次的架构优势？

💡 参考答案

▎一句话结论

多仓库独立部署将单体 Agent 的“全有或全无”式故障模式，转变为微服务的“部分降级”模式，并为不同性质的负载（计算密集型 vs. IO密集型）提供了独立、精细化的弹性伸缩能力，从而大幅提升系统整体可用性和资源利用率。

▎核心原理

  • 故障隔离（Failure Containment）：在单体应用中，一个业务 Agent 的内存泄漏或死循环可能拖垮整个进程，导致所有业务不可用。独立部署后，自媒体 Agent 的故障被限制在它自己的 Pod 内，智能客服 Agent 完全不受影响。底层的 RAG 服务故障只会影响“知识问答”功能，但 Agent 的核心对话能力依然可以降级运行。
  • 独立伸缩（Independent Scaling）：不同的服务有不同的性能瓶颈。RAG 检索服务是计算和内存密集型，可能需要根据查询量（QPS）来水平扩容；而大模型网关是 IO 密集型，瓶颈在于大模型 API 的并发限制，需要根据连接数来扩容。独立部署允许我们为每种服务选择最合适的机器规格和扩缩容策略。
  • 异构技术栈支持：MCP Server 可能用性能更高的 Go 或 C++ 编写，而业务编排层用 Python。多仓库独立部署让每个组件都能使用最适合的语言和框架，不被单体仓库的技术栈所束缚。

▎深入解释

我们可以将单体 Agent 比作一艘巨大的游轮。一个舱室漏水（一个功能出 Bug），如果隔离不好，整艘船都可能沉没。当游客增多时，你无法单独加长餐厅或增加客房，只能换一艘更大的船。
而多仓库独立部署就像是一支分工明确的舰队：
- 补给舰（MCP RAG Server）：专门负责运送给养（知识）。如果它出了问题，战斗舰（业务 Agent）还能用自己储备的弹药（本地知识）继续作战，只是补给能力受限。
- 航空母舰（自媒体 Agent）：负责空中打击（内容生成），任务繁重时可以快速增加舰载机（扩容 Pod）。
- 驱逐舰（客服 Agent）：负责反潜护航（客户沟通），需要高机动性，可以独立部署在离用户更近的边缘节点。
一艘船出故障，不会导致整个舰队瘫痪。你可以根据战斗任务的需要，灵活地增派特定类型的舰船，而不是每次都出动整个舰队。这种架构的韧性（Resilience）和弹性（Elasticity）是单体应用无法比拟的。

▎面试加分点

  • 能提出具体的降级策略：如“当 RAG 服务不可用时，Agent 自动切换到一个不依赖知识库的、基于 LLM 自身知识的兜底回复模板”。
  • 结合 Kubernetes 等编排工具：描述如何利用 HPA（水平 Pod 自动伸缩）为不同服务设置基于 CPU、内存或自定义指标的扩缩容规则。
  • 强调成本意识：独立伸缩可以避免为不忙的服务过度配置资源，直接节省云成本。

▎常见误区

  • 误区：盲目拆分，导致微服务过多，增加了运维复杂度和网络延迟。拆分应遵循单一职责原则，按业务能力或变更频率来划分边界。

📌 概念题 · Q9

考点标签

数据工程 · RAG · 难度：⭐⭐⭐

📝 题目

知识库在“数据检索与知识库技术”中提到了“Contextual Retrieval（上下文前缀拼接）”，通过在入库前为每个 Chunk 自动生成一段包含母档核心信息的“前缀补全”来提升模糊查询的召回率。请问，这种“前缀补全”具体补全的是什么信息？它是如何与向量检索的语义匹配机制协同工作，从而解决“信息碎片化”问题的？

💡 参考答案

▎一句话结论

“前缀补全”是将 Chunk 所在文档的全局背景信息（如文档标题、章节摘要、产品名称等）显式地拼接到 Chunk 文本之前，使这个孤立的片段在语义空间中重新获得全局定位，从而在向量检索时能与宏观问题产生有效匹配。

▎核心原理

  • 解决“上下文丢失”问题：一个 Chunk 内容可能是“它的价格为 100 万元”。当用户问“产品A的价格是多少？”时，这个 Chunk 因为没有包含“产品A”，其语义向量与问题向量的相似度极低，无法被召回。
  • 语义注入与对齐：通过一个小模型或规则，我们分析出这个 Chunk 来自 product_A_spec.pdf 文档，并且属于“定价”章节。于是，我们为它生成一个前缀：“文档：产品A规格说明书 | 章节：定价”。补全后的文本变为“文档：产品A规格说明书 | 章节：定价 它的价格为 100 万元。”。
  • 提升向量检索的召回率：这个新文本的 Embedding 向量，因为包含了“产品A”和“定价”等关键信息，现在可以轻松匹配到用户的查询，从而被成功召回。

▎深入解释

这就像图书馆的索引卡片。以前，你只是把书中的一页内容（Chunk）复印下来放进目录柜。当别人问“关于AI的书在哪”时，这张只写着“...是一种模拟人类智能的技术...”的纸片，很难被归类到“AI”这个查询下。
“上下文前缀补全”就像是你在每张复印的纸片最上方，都用红笔醒目地写上：“来源：《人工智能导论》，作者：李华，第三章：AI的定义”。这样一来，当别人查询“李华写的AI的书”时，这张纸片上的“李华”、“AI”等关键词就能立刻命中。这个前缀起到了“全局定位”的作用，把一个孤立的片段重新放回了它原本的知识体系中。在实际操作中，这个前缀可以由一个廉价快速的 LLM（如 GPT-3.5）在文档处理时自动生成，成本很低，但对召回率的提升效果显著。

▎面试加分点

  • 能将其与 GraphRAG 对比：Contextual Retrieval 是一种低成本、易实现的“伪图”方案，通过文本注入来模拟实体关系；而 GraphRAG 是显式构建知识图谱，能力更强但成本更高。
  • 提到具体的实现流程：在 Ingestion Pipeline 中，增加一个“上下文生成”的步骤，放在 Chunking 之后、Embedding 之前。
  • 强调“小模型干杂活”：这个生成前缀的任务非常适合用 SLM（小语言模型）来完成，速度快、成本低。

▎常见误区

  • 误区：认为这个前缀是给用户看的。它是给 Embedding 模型和向量检索过程“看”的，是纯粹的幕后工作。
  • 误区：过度补全，导致前缀信息过长，稀释了 Chunk 本身的核心内容。前缀需要精简、关键。

📌 概念题 · Q10

考点标签

架构思维 · 系统设计 · 难度：⭐⭐⭐⭐⭐

📝 题目

知识库的“终面通关金句”提到：“我们搭建的分布式架构，本质上是在用‘确定性’的软件工程代码，去包裹和驯服大模型的‘非确定性’。”请从状态管理、流程控制、安全风控、资源调度四个维度，分别举出一个具体的“确定性”工程手段，并解释它是如何“驯服”大模型的“非确定性”的。

💡 参考答案

▎一句话结论

这句话是 AI 工程化的核心哲学。我们通过状态快照将非确定性的上下文固化为确定的数据；通过状态机将非确定性的决策路径收敛为确定的图；通过正则和安全网关将非确定性的输出过滤为合规的内容；通过计数器和熔断器将非确定性的资源消耗限制在确定的预算内。

▎核心原理

  • 状态管理（Checkpointer）：大模型的输出是非确定的，导致 Agent 的“思考状态”也是非确定的。我们通过 PostgreSQL Checkpointer，在每次模型调用后，将整个会话的上下文、变量、状态图位置等所有信息，序列化为一个确定性的 JSON 快照存入数据库。这样，无论何时发生崩溃，我们都能从这个确定的“存档点”恢复，而不是依赖模型重新进行非确定性的思考。
  • 流程控制（LangGraph 状态机）：大模型可能会“幻想”出一个不存在的工具调用，或跳转到一个不合理的步骤。我们通过 LangGraph 的图结构和条件边，定义了一个确定性的有限状态机。Agent 只能在预设的节点间跳转，它的“下一步”由我们写的 Python 代码函数决定，而不是由模型的非确定性输出决定，这从根本上杜绝了流程失控。
  • 安全风控（Guardrails & 正则）：大模型可能会生成包含敏感词、幻觉事实或违规内容的文本。我们通过在模型输出后增加一层确定性的安全护栏，如正则表达式过滤手机号、基于 NER 模型识别并脱敏人名，以及调用一个独立的合规判断模型进行打分。这些规则和模型的判断逻辑是确定的，不依赖主 Agent 大模型的自觉性。
  • 资源调度（计数器 & 熔断器）：大模型的 Token 消耗和推理时间是动态且非确定性的，可能导致死循环和成本爆炸。我们在代码层面设置确定性的硬上限，如 max_loops=5 的循环计数器，以及基于连续失败次数的熔断器。当计数值达到预设的确定阈值时，系统会强制中断任务或切换降级方案，而不是等待模型自己“想通”。

▎深入解释

这就像是在驯服一匹野马（大模型）。你不能指望野马自己知道要去哪、跑多快、什么能吃什么不能吃。你需要给它套上：
- 缰绳（流程控制）：告诉它只能走这条路，不能乱跑。
- 马蹄铁（状态管理）：保护它的脚，即使踩到石头（崩溃）也不会受致命伤，能继续赶路。
- 眼罩（安全风控）：防止它被路边的诱惑（有害信息）带偏。
- 马鞭和缰绳的力度（资源调度）：控制它的速度，不能让它跑到累死（Token 刷爆）。
我们 AI 架构师的工作，就是为这匹强大的“野马”设计并打造一整套精良的“马具”（Agent Harness），让它从一个不可控的猛兽，变成能够承载商业任务的千里马。

▎面试加分点

  • 这是架构师级别的总结性回答，展现了从具体技术到宏观哲学的思想高度。
  • 每个维度都能用一个技术名词精确对应一个工程问题，逻辑清晰，说服力强。
  • 能升华主题：指出 AI 工程化的本质是“软件工程 2.0”，核心挑战从处理“逻辑的复杂性”变成了处理“概率的复杂性”。

▎常见误区

题型

架构设计

场景标签

多仓库独立部署 MCP 服务中台化 网关路由

📝 题目

你在知识库中提到“多仓库独立部署”优于“把所有 Agent 塞进同一个大仓库”，并建议将底层的 MCP 公共服务（如 RAG 检索、会话记忆）与上层的业务 Agent（如智能客服、自媒体运营）分离。请你以“新增一个企业内部 IT 助手 Agent”为场景，详细设计这个新业务 Agent 的仓库结构、它如何复用已有的 MCP 公共服务、以及如何通过网关实现与现有 Agent 的隔离与路由。请对比这种架构与“单体大仓库”模式在团队协作、发布风险、资源扩缩容三个维度的优劣。

💡 参考答案

▎解题思路

  1. 明确分层：将系统分为两层，底层是稳定、共享的 MCP 公共服务，上层是独立、多变的业务 Agent 应用。
  2. 新业务接入：新 Agent 只需关注自身业务逻辑编排，通过标准 HTTP/MCP 协议调用底层服务，无需重复造轮子。
  3. 网关路由：在网关层通过 URL 路径（如 /api/v1/it-support）或 API Key 来识别和路由请求，实现业务隔离。

▎详细方案

1. 仓库结构设计：
我们采用三个独立的 Git 仓库：
- 仓库 A：公共服务仓库（mcp-shared-services）
- 包含 4 个独立的 MCP Server 项目：llm-gateway、rag-server、memory-server、prompt-manager。
- 每个 Server 独立打包成 Docker 镜像，对外暴露稳定的 HTTP API。
- 这个仓库由基础架构团队维护，发布周期长，要求极高稳定性。
- 仓库 B：自媒体运营业务仓库（media-agent-app）
- 只包含自媒体业务的 LangGraph 编排逻辑、特定 Prompt 模板和业务专属工具（如调用头条 API）。
- requirements.txt 中声明依赖 mcp-client-lib（一个内部封装的用于调用 MCP 服务的客户端库）。
- 仓库 C：新 IT 助手业务仓库（it-support-agent-app）
- 完全新建的仓库。仅包含 IT 助手相关的 LangGraph 状态图，如“密码重置”、“电脑报修”等工作流节点。
- 它同样依赖 mcp-client-lib 来调用底层的 RAG 检索（查询知识库里的 IT 手册）和会话记忆服务（记住员工是谁）。

2. 服务调用与网关路由：
- 启动过程：it-support-agent-app 启动时，会通过环境变量获取所有 MCP 公共服务的地址（如 RAG_SERVER_URL=http://rag-server:8001）。
- 请求路由：所有用户请求统一打到 API 网关（如 Nginx 或 FastAPI Gateway）。
- 前端请求 /api/v1/media-ops/generate，网关根据路径前缀 /media-ops 将流量转发到自媒体业务 Pod。
- 前端请求 /api/v1/it-support/ticket，网关根据路径前缀 /it-support 将流量转发到新的 IT 助手业务 Pod。
- 服务发现：网关的配置只需增加一条新的路由规则，指向新部署的 it-support-agent-app 服务。

▎关键细节 & 踩坑点

  • 统一客户端库：必须开发并维护一个标准的 MCP 客户端库（mcp-client-lib），封装服务发现、认证、重试、熔断逻辑，否则每个业务仓库都要重复实现一遍，成为新的耦合点。
  • MCP Server 的向后兼容性：公共服务升级接口时，必须保证向后兼容，不能影响已上线的老业务 Agent。这是多仓库架构成功的关键契约。

▎可扩展优化

  • 按需独立扩缩容：如果 IT 助手业务访问量激增，只需对 it-support-agent-app 的 Pod 进行水平扩容，完全不影响自媒体业务和底层 MCP 服务的资源配额，实现了精细化的资源成本控制。
  • 独立 CI/CD 流水线：每个业务仓库拥有自己独立的 CI/CD 流水线。IT 助手的一个 Bug 修复可以秒级上线，而无需像单体仓库那样，因为等待自媒体业务的一个大功能测试完成而被阻塞发布。

🛠 应用题 · Q2 · 场景分析题

题型

场景分析

场景标签

长周期任务 Human-in-the-Loop 状态中断与唤醒

📝 题目

你正在开发一个“内容合规审核 Agent”，它负责审核自媒体运营 Agent 生成的图文内容。审核流程是：Agent 自动机审 -> 发现疑似违规内容 -> 创建人工审核工单并挂起 -> 等待审核员在后台点击“通过”或“驳回” -> Agent 根据结果继续执行（发布或重写）。请对比分析，为什么不能用一个简单的同步等待循环（如 while(!approved) { sleep(10) }）来实现此功能？详细阐述基于 LangGraph 的 Interrupt 信号 + Webhook 回调 的实现方案，并分析它在资源利用率和系统可靠性上的优势。

💡 参考答案

▎解题思路

  1. 识别问题本质：这是一个典型的“长周期、人机协同”任务，核心挑战是将长时间挂起的任务从内存中安全移除，并在外部事件触发时精确恢复。
  2. 批判错误方案：分析同步等待循环为何失败（占用连接、不持久、无法跨进程）。
  3. 构建正确方案：利用状态持久化 + 中断信号 + 异步回调的组合，实现“休眠与唤醒”机制。

▎详细方案

错误方案分析：同步等待循环

# 这是一个灾难性的实现
async def review_content(content):
    task_id = create_human_review_task(content)
    while True:
        status = check_review_status(task_id)
        if status == "approved":
            break
        elif status == "rejected":
            # 处理驳回...
            break
        await asyncio.sleep(10) # 阻塞 10 秒
    # 继续后续逻辑...
  • 资源浪费：长达数小时甚至数天的等待期间，该进程/协程会一直被占用，耗尽服务器连接数和内存。
  • 极不可靠：服务器一旦重启或发布新版本，所有等待状态瞬间丢失，所有待审核任务全部失败。
  • 不可扩展：该状态与运行实例强绑定，无法迁移到其他机器，无法实现高可用。

正确方案：LangGraph 中断 + Webhook 唤醒
1. 状态持久化与中断：在 LangGraph 工作流中，当 Agent 识别到需要人工介入时，它进入一个特定节点（如 human_review_node）。这个节点内部调用一个 Tool，该 Tool 在外部工单系统创建任务并获取唯一 task_id。随后，Agent 代码显式调用 interrupt("等待人工审核") 信号。LangGraph 框架捕获此信号后，立即将当前完整的图状态（State）、上下文、历史消息通过 Checkpointer（如 PostgreSQL）序列化并持久化存储，然后彻底释放当前工作线程/进程的所有资源。
2. 异步唤醒与恢复：当审核员在外部系统完成审批操作后，该系统后端向我们的 Agent 服务发送一个 Webhook 请求，例如 POST /api/callbacks/review，请求体中携带 task_id 和审批结果。我们的 FastAPI 接口接收到回调后，根据 task_id 从数据库中查询到之前持久化的状态。然后，使用 LangGraph 的 graph.astream(None, config) 方法，以该历史状态作为起点，并将审批结果作为新的输入（通过 Command 对象）重新提交给图，Agent 便从 human_review_node 的下一跳“醒来”，无缝衔接后续逻辑。

▎关键细节 & 踩坑点

  • task_id 的关联：必须将 LangGraph 的 thread_id（会话ID）与外部工单的 task_id 在数据库中建立映射关系，这是唤醒时找回正确状态的唯一凭证。
  • 幂等性处理：Webhook 可能因网络问题重复发送。唤醒 Agent 的逻辑必须保证幂等性，即同一个审批结果被多次接收，不会导致内容被重复发布或重复驳回。

▎可扩展优化

  • 超时自动处理：可以在创建工单时设置一个 TTL（生存时间）。如果审核员在 24 小时内未处理，可以启动一个定时任务，扫描这些超时的工单，并向 Agent 发送一个“超时自动驳回”的 Webhook 事件，驱动流程继续，避免任务永久卡死。
  • 通知机制：在挂起前，可集成企业微信/钉钉等，主动向审核员发送通知消息，加速审批流程。

🛠 应用题 · Q4 · 排障优化题

题型

排障优化

场景标签

性能优化 Token 成本 前缀缓存

📝 题目

你负责的自媒体 Agent 系统上线后，监控发现两个问题：1. 首字延迟（TTFT）极高：在复杂的 RAG 场景下，从用户发请求到看到第一个字，常常需要等待 10-15 秒。2. Token 成本失控：随着多轮对话的进行，每次请求携带的历史消息越来越长，导致单次对话的 Token 消耗呈线性增长。请结合知识库中提到“深度触发模型前缀缓存（Prefix Caching）”和“分层内存管理”两个策略，详细阐述你如何定位并解决这两个问题。请解释为何简单地将所有历史记录全量塞给大模型是行不通的。

💡 参考答案

▎解题思路

  1. 问题定位：TTFT 高通常源于长上下文导致模型推理计算量大；Token 成本失控源于无差别的全量历史消息传递。
  2. 核心策略一：分层记忆，斩断线性成本增长：引入近期记忆（原始对话）和长期记忆（摘要）的概念，将上下文长度控制在 O(1) 的常量级。
  3. 核心策略二：固定前缀，激活模型缓存：通过精心设计 System Prompt 和 RAG 检索结果的拼接顺序，确保每次请求的 Token 前缀高度一致，从而命中大模型服务端的 KV Cache。

▎详细方案

问题 1：Token 成本失控与长上下文延迟
- 错误做法：直接将过去 50 轮对话的原始文本全部拼接进 Prompt。这导致 Prompt 长度 N 随对话轮次线性增长，模型计算复杂度（Attention）是 O(N^2)，延迟和成本会急剧恶化。
- 优化方案：分层内存管理
1. 近期记忆（Short-term Memory）：在 LangGraph 的 State 中，只保留最近 3-5 轮对话的精确原文。这部分信息保证了对当前话题的精确理解和连贯性。
2. 长期记忆（Long-term Memory）：创建一个异步的“记忆摘要”任务。每当对话达到一定轮次（如 10 轮），后台自动将第 6-10 轮的对话压缩成一句精炼的摘要，例如“用户偏好科技类产品，预算在 5000 元左右，对续航有高要求”。摘要作为用户画像的一部分，存入数据库。
3. Prompt 拼接：最终发给 LLM 的 Prompt 结构变为：
[System Prompt] [用户长期画像摘要: ...] [近期精确对话: 最近3轮] [用户当前问题]
这样，无论对话进行了多少轮，每次请求的上下文长度都保持在一个可控的、近似恒定的范围，彻底解决了 Token 成本和长上下文延迟问题。

问题 2：复杂 RAG 场景下的高首字延迟（TTFT）
- 问题定位：即使上下文不长，每次 RAG 检索出的文档顺序是随机的，导致整个 Prompt 的前缀（System Prompt + 检索结果）每次都不一样，模型无法利用 KV Cache，每次都需要重新计算整个 Prompt 的注意力矩阵。
- 优化方案：深度触发前缀缓存
1. 固定 System Prompt：确保所有用户请求的 System Prompt 部分在 Token 级别完全一致。
2. 固定 RAG 检索结果的拼接顺序：这是关键。不要按相关性分数从高到低动态排序后直接拼接。而是先按文档类型或固定逻辑排序（如：先放“产品手册”，再放“常见问题”，最后放“用户评价”），然后在每种类型内部再按相关性分数排序。或者，将所有检索到的 Chunk 进行哈希，按固定字典序排列。
3. 效果：通过这种方式，大部分请求的开头部分（[System Prompt] + [结构化排序后的检索块]）在 Token 序列上会高度一致。大模型服务端（如 vLLM）会自动识别并缓存这些前缀的计算结果（KV Cache）。当新请求到来时，只需计算最后一个不同的 Token（即用户问题）部分，从而将首字延迟（TTFT）从 15 秒暴力压缩至 1-2 秒。

▎关键细节 & 踩坑点

  • 摘要的时效性：长期记忆摘要需要定期或在关键信息更新时重新生成，避免过时的用户画像误导 Agent。
  • 缓存命中率监控：不能假设缓存总是生效。必须监控大模型 API 返回的 usage 字段中关于缓存命中 Token 数的指标（如果厂商提供），或者通过对比相似请求的延迟时间来间接判断。

▎可扩展优化

  • 多级缓存：除了模型端的 KV Cache，还可以在 Agent 服务端引入应用级缓存。对于完全相同的用户问题，可以直接返回缓存的答案，连 LLM 都不用调用。
  • 动态前缀优化：可以编写脚本，自动分析线上请求的 Prompt 前缀，找出差异点，并调整代码逻辑以消除这些差异，持续提高缓存命中率。

🛠 应用题 · Q5 · 综合落地题

题型

综合落地

场景标签

0到1交付 Agent 生命周期 架构师视角

📝 题目

你作为 AI 架构师，需要从 0 到 1 交付一个“建材报价 Agent”，它能根据用户上传的 PDF 图纸，自动识别材料清单并生成报价 Excel。作为项目负责人，你需要规划从“技术选型”到“上线运维”的完整生命周期。请结合知识库中“确定性状态机驯服非确定性 LLM”的理念，详细阐述你在开发阶段、测试阶段、上线阶段的核心任务与决策。特别是，在测试阶段，你如何利用 Agent Harness 确保 95% 以上的报价准确率？在上线阶段，你如何设计优雅关闭和分层发布策略，实现零停机更新？

💡 参考答案

▎解题思路

  1. 开发阶段：核心是架构选型，用确定性的工程框架包裹非确定性的 LLM。
  2. 测试阶段：核心是建立自动化评估基准（Harness），将“感觉准不准”变成“数据准不准”。
  3. 上线阶段：核心是保障服务高可用，实现无损发布和自动容错。

▎详细方案

阶段一：开发阶段 - 确定性的骨架
- 技术选型：选择 LangGraph 作为状态机编排器，而非自由度过高的 ReAct Agent。将报价流程拆解为确定性的步骤节点：解析图纸 -> 识别材料 -> 计算工程量 -> 匹配价格库 -> 生成 Excel。
- 职责分离：
- 确定性的活儿交给代码：图纸解析（调用 OCR API）、匹配价格库（查询 MySQL）、生成 Excel（使用 openpyxl 库）这些步骤由确定的 Python 函数完成，结果 100% 可控。
- 不确定的活儿交给 LLM：仅在“识别材料”这一步，将裁剪后的图纸局部图片发给多模态大模型，让它识别“这是Φ12的螺纹钢还是Φ10的圆钢”。LLM 只做它最擅长的模糊识别，不参与流程控制。
- 工具设计：所有 Tool（如 query_price_db）都设计成幂等的、只读的。任何写操作（如最终生成报价单）都在状态机的最后一个确定节点执行，不交给 LLM 决策。

阶段二：测试阶段 - 用数据说话
- 构建 Agent Harness：
1. 准备测试集：收集 100 份真实的、不同复杂度的 PDF 图纸，并由资深造价员人工标注出“标准答案”（一份准确的 Excel 报价单）。
2. 编写测试脚本：使用 pytest 编写 Harness。脚本批量读取图纸，调用 Agent 生成报价，然后对比生成的 Excel 与标准答案 Excel 的差异，计算每个材料项的误差率。
3. 设定质量门禁：设定硬性指标，如“总体报价误差率 < 3%”、“单项材料误差率 < 5%”。只有通过所有测试用例，代码才被允许合并。
4. 熔断与边界测试：在 Harness 中加入异常测试用例，如“上传一张猫的图片”、“上传一份损坏的 PDF”、“瞬间 100 个并发请求”，验证 Agent 的熔断、降级和限流机制是否正常触发，确保系统不会崩溃。

阶段三：上线阶段 - 无损发布与高可用
- 优雅关闭：在 FastAPI 应用中使用 lifespan 异步上下文管理器。当收到新版本发布的 SIGTERM 信号时，不立即杀死进程，而是：
1. 停止接收新请求。
2. 检查全局计数器 active_tasks，等待所有正在进行的报价任务完成并将中间状态持久化到数据库。
3. 所有在途任务安全完成后，再退出进程。
- 分层发布：在 Docker Compose 或 K8s 中配置 depends_on 和 healthcheck。
1. 底层服务：先启动并等待 mcp-price-db-server（价格数据库 MCP 服务）的健康检查通过。
2. 上层应用：再启动 building-quote-agent，并等待它自身的 /health 端点返回 200 OK。
3. 滚动更新：结合 K8s 的 Rolling Update 策略，先启动新版本的 Pod，待其健康检查通过后，再将流量从旧 Pod 逐步切换到新 Pod，最后优雅关闭旧 Pod，实现用户无感知的零停机发布。

▎关键细节 & 踩坑点

  • 标准答案的准确性：Harness 的效果高度依赖测试集中“标准答案”的质量。必须由业务专家反复校验，否则“垃圾进，垃圾出”。
  • 数据库迁移：新版本如果涉及数据库 Schema 变更，必须先执行向后兼容的数据库迁移脚本，再发布应用代码，否则会导致线上故障。

▎可扩展优化

  • 金丝雀发布：先让新版本只服务 1% 的用户，观察其错误率、报价准确率、延迟等指标。如果一切正常，再逐步扩大流量比例，最终全量上线。这是比分层发布更安全的发布策略。
  • 全链路可观测性：集成 LangSmith 或 Arize Phoenix，为 Agent 的每一次报价任务生成完整的 Trace 日志，记录每一步的耗时、Token 消耗、LLM 输入/输出。当线上出现报价不准的投诉时，可以根据 thread_id 快速回溯整个决策过程，精准定位问题。
