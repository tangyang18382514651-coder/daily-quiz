📌 概念题 · Q1

考点标签

Agentic RAG · 难度：⭐⭐

📝 题目

请解释什么是 Agentic RAG，它和传统 RAG 的核心差异是什么？

💡 参考答案

▎一句话结论

Agentic RAG 是把传统硬编码的固定检索流程，升级为由 LLM 自主决策、可循环调用工具、具备反思纠错能力的智能检索增强范式，核心区别是“模型决定去哪查、查几次”，而不是“程序查完喂给模型”。

▎核心原理

  • 工具注册：把向量库、SQL 数据库、外部 API、搜索引擎等封装成带描述的工具
  • 模型决策：LLM 根据问题自主判断是否调用工具、调用哪个、参数是什么
  • 执行闭环：工具结果回传模型，模型可继续检索、反思、重写 Query，直到答案完备

▎深入解释

传统 RAG 的流程是线性且死板的：用户提问 → 程序固定去向量库做 TopK 检索 → 把结果拼进 Prompt 给模型生成。整个检索逻辑是开发者提前写死的，模型没有任何选择权，遇到跨库、多跳、需要实时数据的问题就会失效。
而 Agentic RAG 把 LLM 放在了“驾驶员”位置，给它一个工具箱，让它像人类研究员一样工作：遇到简单问题可以直接回答，遇到财务报表问题知道去查 SQL，遇到企业文化问题知道去查向量库，遇到天气问题知道调外部 API，检索到无关内容会自动剔除，信息不足会重写检索词二次查询。本质上是把“单次检索+生成”升级成了“思考-行动-观察-反思”的循环。

▎面试加分点

  • 能准确说出 Agentic RAG 的三大核心能力：工具调用、任务拆解、自我反思
  • 能点明它不是要完全替代传统 RAG，而是应对复杂场景的升级方案

▎常见误区

  • 误区：Agentic RAG 就是“RAG + 联网搜索”。错，联网只是工具之一，核心是自主决策和纠错循环，不是多接一个接口。

📌 概念题 · Q2

考点标签

Agentic RAG · 难度：⭐⭐⭐

📝 题目

Agentic RAG 相比传统 RAG 虽然效果更好，但生产落地时存在三个核心工程挑战，请分别说明它们的成因和影响。

💡 参考答案

▎一句话结论

Agentic RAG 的三大落地痛点是长延迟、高 Token 成本、复杂状态管理，本质是用更多的计算和架构复杂度换来了回答质量的提升，不能盲目在所有场景使用。

▎核心原理

  • 长延迟：多轮 LLM 推理、工具调用、反思评估叠加，端到端耗时远高于单次检索
  • Token 消耗：循环迭代中反复注入系统提示、工具返回结果、历史状态，输入 Token 阶梯式增长
  • 状态持久化：多轮对话、分支循环、图结构工作流需要维护执行轨迹、中间结果、记忆，对存储一致性要求极高

▎深入解释

传统 RAG 通常只需要1次 Embedding 检索 + 1次 LLM 生成，TTFT（首字延迟）可以控制在几百毫秒级别。但 Agentic RAG 为了保证准确率，可能需要经历“意图路由→第一次检索→文档打分→发现信息不足→重写 Query→第二次检索→幻觉检测→生成回答”的完整链路，中间每一步都要调用 LLM，总耗时可能达到数秒甚至十几秒。
同时，每一次循环都要把之前的所有对话历史、工具返回的长文本、系统规则全部拼进 Prompt，Input Token 会随着迭代次数快速上涨，调用成本可能是传统 RAG 的3-10倍。
更麻烦的是状态管理：如果 Agent 执行到一半网络中断、或者用户中途修改问题，系统需要知道它之前已经查过什么、拿到了什么结果、下一步该做什么，不能从头开始，这就需要高可靠的状态存储（通常用 PostgreSQL 或 LangGraph 自带的 Checkpoint 机制），架构复杂度大幅上升。

▎面试加分点

  • 能给出选型建议：高并发单跳查询（如名词解释）用传统 Advanced RAG 足够，跨文档比对、幻觉敏感的复杂场景再用 Agentic RAG
  • 能提到延迟优化手段：小模型做路由/打分、缓存高频路由结果、限制最大迭代次数

📌 概念题 · Q3

考点标签

结构化输出 · 难度：⭐⭐⭐

📝 题目

工业界解决大模型输出 JSON 格式不稳定的问题，为什么必须采用“软约束→硬约束→兜底层”的三层防御体系，而不是只靠写 Prompt？

💡 参考答案

▎一句话结论

没有任何单一方案能100%保证大模型输出合法 JSON，三层防御是从“引导生成→过程强制→异常兜底”全链路堵漏洞，是生产环境唯一可靠的工程方案。

▎核心原理

  • 软约束层：通过强指令、Few-Shot 示例、Schema 声明引导模型输出正确格式，成本最低但稳定性有限
  • 硬约束层：利用模型原生 response_format 参数或约束解码技术，在 Token 生成过程中直接过滤非法字符，从根源杜绝格式错误
  • 兜底层：通过正则提取、JSON 自动修复、Pydantic 校验+错误重试，处理所有漏网的异常情况

▎深入解释

很多初级开发者以为只要在 Prompt 里写“请输出 JSON”就够了，但大模型本质是概率生成模型，即使提示写得再清楚，也有小概率输出解释性文字、Markdown 代码块、中文引号、括号不匹配等问题，在高并发场景下哪怕1%的错误率也会导致线上故障。
三层防御的思路是层层设防：首先用 Prompt 把模型的输出自由度压到最低，给它看正确示例，告诉它字段要求；然后如果模型支持结构化输出参数，直接开启，让模型在生成每一个 Token 时就只能选符合 JSON 语法的候选，从生成过程保证合规；最后即使前两层都失效了，后处理环节会先把多余的文字剥离，用修复库补全括号、修正引号，再用 Pydantic 校验字段类型和范围，如果还是失败就把错误信息返回给模型让它自我修正，直到输出合法结果。

▎面试加分点

  • 能回答开源模型不支持 response_format 的解决方案：用 Outlines/Guidance 做约束解码、加反例 Prompt、微调适配、后处理兜底
  • 能指出约束解码的原理：在每一步生成时根据 JSON 语法状态机屏蔽非法 Token，比如对象开头必须是{，字符串必须用双引号闭合

▎常见误区

  • 误区：开启了 response_format 就不用做后处理。错，该参数只能保证输出是合法 JSON，但无法保证字段齐全、类型正确、枚举值符合要求，必须加 Schema 校验。

📌 概念题 · Q4

考点标签

KV Cache · 难度：⭐⭐⭐⭐

📝 题目

大模型推理中的 KV Cache 技术为什么只缓存 Key 和 Value，而不缓存 Query？它解决了什么核心问题？

💡 参考答案

▎一句话结论

KV Cache 是大模型自回归生成场景下“用显存换速度”的核心优化，只缓存 K/V 是因为历史 Token 的 Query 没有复用价值，只有 K 和 V 会在后续每一步生成中被反复使用。

▎核心原理

  • 自回归生成特性：大模型逐 Token 输出，每生成一个新 Token 都需要和所有历史 Token 做注意力计算
  • Q 的角色：Query 代表当前最新 Token 的“提问”，每个新 Token 都有全新的 Q，历史 Q 用完即弃
  • K/V 的角色：Key 是历史 Token 的“身份标签”，Value 是历史 Token 的“语义内容”，推理过程中不会改变，必须缓存复用

▎深入解释

如果没有 KV Cache，模型生成第 N 个 Token 时，需要把前 N-1 个 Token 全部重新计算一遍 Q/K/V，再做注意力计算，时间复杂度是 O(N²)，文本越长生成越慢，长上下文场景下根本无法使用。
引入 KV Cache 后，已经处理过的历史 Token 的 K 和 V 矩阵会被直接存在显存里，每次生成新 Token 时，只需要计算这一个新 Token 的 Q、K、V，然后把新的 K/V 追加到缓存里，再用新的 Q 和所有历史 K/V 做注意力计算即可，时间复杂度直接降到 O(N)，生成速度提升数倍到数十倍。
之所以不缓存 Q，是因为 Q 永远只代表“当前正在处理的那个 Token”，当这个 Token 处理完成为历史的一部分后，它的身份就从“提问者”变成了“被提问的历史信息”，后续的新 Token 不会再用到旧的 Q，只会用到它的 K 和 V，缓存 Q 纯粹是浪费显存。

▎面试加分点

  • 能说出 KV Cache 带来的新问题：显存占用随上下文长度和并发量线性增长，长文本场景下 KV 显存甚至会超过模型权重本身
  • 能列举主流 KV 优化技术：PagedAttention 解决显存碎片、MQA/GQA 减少 KV 头数量、KV 量化降低存储精度、Context Cache 复用公共前缀

📌 概念题 · Q5

考点标签

KV Cache · 难度：⭐⭐⭐⭐

📝 题目

vLLM 框架的核心技术 PagedAttention 是借鉴了操作系统的虚拟内存管理思想，请说明它解决了 KV Cache 的什么痛点，核心原理是什么？

💡 参考答案

▎一句话结论

PagedAttention 通过把 KV Cache 切分成固定大小的块、非连续存储，彻底解决了传统 KV Cache 显存碎片化、利用率低的问题，将推理并发吞吐量提升了数倍。

▎核心原理

  • 传统 KV Cache 缺陷：为每个请求预先分配连续的大显存块，不同请求的长度差异大，产生大量无法利用的显存碎片
  • 块式管理：把连续的 KV Cache 切分成固定大小的 Block（类似操作系统的内存页），通过块表记录逻辑位置到物理位置的映射
  • 非连续存储：Block 可以分散存放在显存的任意位置，不需要连续空间，同一请求的 KV 块通过指针串联
  • 高效共享：相同前缀（如 System Prompt）的请求可以共享 KV 块，无需重复存储

▎深入解释

传统推理框架为了存储 KV Cache，会给每个请求按照最大上下文长度预先分配一块连续的显存，比如给每个请求预留 8k 长度的 KV 空间，但实际上大部分请求可能只有几百个 Token，剩下的显存就被白白浪费了；同时不同请求的生成长度动态变化，请求结束后释放的显存块大小不一，很容易产生大量零散的显存碎片，明明总剩余显存很多，但无法分配给新的连续块，导致显存利用率通常只有40%左右，并发能力上不去。
PagedAttention 完全借鉴了操作系统虚拟内存和分页管理的思路：把显存分成一个个大小固定的 Block（比如每个 Block 存16个 Token 的 KV），每个请求的 KV Cache 不需要连续存放，系统维护一个块表，记录这个请求的第几个逻辑块对应显存里的哪个物理块，写满一个块就找一个空闲块接上。这样几乎不会产生显存碎片，显存利用率可以提升到96%以上。同时，对于多个请求共享相同 System Prompt 或者多轮对话公共前缀的场景，这些前缀的 KV Block 可以直接被所有请求共享，通过引用计数管理，不需要重复计算和存储，进一步大幅降低显存占用。

▎面试加分点

  • 能对比操作系统内存管理：PagedAttention 的 Block 对应内存页，块表对应页表，共享内存机制对应写时复制（COW）
  • 能说明 PagedAttention 对在线推理的价值：同样的显卡可以支撑2-4倍的并发量，是目前大模型推理服务的事实标准技术

📌 概念题 · Q6

考点标签

PostgreSQL · 难度：⭐⭐⭐

📝 题目

在 Agent 架构中，PostgreSQL 经常被用作“向量数据库+状态中心+任务队列”的复合体，而不仅仅是传统的关系型数据库，请说明它支撑这些场景的核心特性。

💡 参考答案

▎一句话结论

PostgreSQL 能在 Agent 架构中身兼数职，核心靠四大特性：pgvector 插件支持向量检索、JSONB 类型支持灵活的状态存储、SKIP LOCKED 支持高并发任务队列、LISTEN/NOTIFY 支持实时状态推送，实现技术栈收敛。

▎核心原理

  • 向量混合检索：pgvector 插件让 PG 原生支持向量相似度计算，可在单条 SQL 中同时做权限、时间等业务字段过滤和向量检索
  • 灵活状态存储：JSONB 是二进制存储的 JSON 类型，支持 GIN 倒排索引，可高效查询和更新嵌套的 Agent 状态结构，不需要固定表结构
  • 分布式任务队列：利用 SELECT ... FOR UPDATE SKIP LOCKED 语法，多个 Worker 并发抢任务时自动跳过已锁定行，无锁冲突、不重复消费
  • 实时通知：内置的 LISTEN/NOTIFY 发布订阅机制，可在状态变更时实时推送消息给后端服务，无需轮询数据库

▎深入解释

很多团队在做早期 Agent 应用时，会同时引入 MySQL 存业务数据、Milvus 存向量、Redis 存状态、RabbitMQ 做任务队列，整个架构非常重，运维成本极高，还存在跨库数据一致性问题。
而 PostgreSQL 凭借极强的扩展性，可以用一套数据库解决大部分中小规模 Agent 场景的需求：比如做 RAG 时，文档的权限、所属部门、更新时间等结构化字段和向量存在同一张表，检索时直接加 WHERE 条件过滤有权限的文档，再做向量相似度排序，不需要先去向量库查ID再回业务库过滤，避免了跨库同步延迟和数据不一致；存储 Agent 运行状态时，LangGraph 的 State 是嵌套的 JSON 结构，字段经常变化，用 JSONB 不需要提前改表结构，加 GIN 索引后可以直接对嵌套字段做毫秒级查询；做异步任务时，不需要单独部署消息队列，用 SKIP LOCKED 就能实现高性能的分布式任务消费，配合 NOTIFY 还能在任务状态变化时实时推送给前端做流式输出。

▎面试加分点

  • 能准确说出选型边界：当向量规模达到数亿级、对检索延迟有极端要求时，还是需要专用向量库；千万级以下向量用 pgvector 完全足够，运维成本低很多
  • 能区分 JSON 和 JSONB：JSON 是纯文本存储，每次读取都要重新解析，不支持索引；JSONB 是二进制存储，读取快、支持索引，存储 Agent 状态必须选 JSONB

📌 概念题 · Q7

考点标签

架构设计 · 难度：⭐⭐⭐⭐

📝 题目

大规模 Agent 系统经常采用“专用向量库存静态知识库 + PostgreSQL 存动态会话状态”的混合架构，请说明这种“动静分离”设计的核心原因。

💡 参考答案

▎一句话结论

这种混合架构的核心是让不同数据库做自己最擅长的事：专用向量库应对海量、静态、重语义检索的知识库数据，PostgreSQL 应对高频、动态、重事务的会话状态数据，避免互相干扰、兼顾性能和稳定性。

▎核心原理

  • 静态知识库特性：文档量大（千万/亿级 Chunk）、更新频率低（天/周级）、核心需求是高并发低延迟的语义向量检索
  • 动态状态数据特性：会话和状态数据量相对小、更新频率极高（秒级读写）、核心需求是强事务、精确点查、灵活结构更新
  • 避免资源抢占：如果把两类数据混存，知识库批量导入、重建索引会占用大量内存和IO，影响在线会话的读写性能；高频的会话写入也会干扰向量检索的稳定性

▎深入解释

很多人会疑惑“既然 pgvector 能做向量检索，为什么还要引入 Milvus/Qdrant 这类专用向量库”，本质是数据特性的差异决定了存储选型。企业的规章制度、产品手册这类静态知识库，数据量往往达到千万甚至上亿条 Chunk，这类数据的核心操作是批量导入、构建向量索引、高并发语义检索，更新很少，专用向量库的分布式架构可以把索引分片到多个节点，水平扩展能力极强，专门为向量检索做了硬件级优化。
而用户的会话历史、Agent 运行时的中间状态、任务列表这类动态数据，核心操作是按 Session ID 精确查询、追加写入、更新中间状态、事务回滚，不需要做复杂的向量检索，但要求极高的写入性能和数据一致性，这恰恰是 PostgreSQL 这类关系型数据库的强项。
如果强行把高频写的会话数据往专用向量库里灌，会导致向量库频繁做 Compaction（段合并），写入性能急剧下降，还容易出现读写冲突；如果把海量静态向量塞进 PG，HNSW 索引会占用大量业务内存，知识库批量更新时还会拖垮在线业务的数据库性能。动静分离后，两类数据的读写链路完全隔离，各自发挥优势，系统稳定性大幅提升。

▎面试加分点

  • 能说清完整的数据流：用户提问→先从 PG 查会话历史上下文→再去向量库检索相关知识→组装 Prompt 调用 LLM→结果写回 PG 更新会话状态
  • 能提到这种架构的优势：既保证了业务数据的 ACID 一致性，又保留了向量检索的水平扩展能力，运维复杂度远低于全栈用单一数据库

💡 参考答案

▎一句话结论

Redis 在 Agent 架构中是天然的“短时记忆中心+轻量状态机+协同消息总线+限流控制器”，凭借内存级的读写性能，完美匹配 Agent 对低延迟、高并发状态操作的需求。

▎核心原理

  • 短时记忆管理：用 List/Hash 存储用户最近 N 轮对话，配合 TTL 自动清理不活跃会话，也可通过 RedisVSS 实现毫秒级语义记忆检索
  • 工作流状态缓存：用 Hash/JSON 结构存储 Agent 执行任务的中间状态、当前步骤、临时结果，节点故障时可快速恢复
  • 多 Agent 协同通信：用 Stream 结构构建可靠的轻量任务队列，支持 ACK 机制，实现多 Agent 之间的任务派发和结果通信
  • 成本与流量控制：用 String 计数器或 ZSet 滑动窗口，实现用户级、全局级的 LLM API 限流，防止超成本和触发服务商配额限制

▎深入解释

Agent 和传统的无状态 API 最大的区别是它有“记忆”、有“执行过程”、需要多组件协同。如果所有状态都存在 PostgreSQL 这类磁盘数据库里，高频的状态读写会给数据库带来巨大压力，延迟也高，而 Redis 的内存读写性能可以达到10W+ QPS，延迟在亚毫秒级，非常适合存储访问频率极高的短时数据。
比如多轮对话中，用户最近10轮的对话历史需要每次请求都读取，存在 Redis 里可以大幅降低 PG 的查询压力；LangGraph 这类编排框架执行长流程任务时，每一步的中间结果可以先存在 Redis 里，整个任务完成后再持久化到 PG，减少磁盘IO；多个专业 Agent（如搜索Agent、代码Agent、写报告Agent）协同工作时，不需要部署重量级的 Kafka，用 Redis Stream 就能实现可靠的任务投递和消费，架构更轻量；LLM API 调用成本很高，用 Redis 做滑动窗口限流，可以在网关层直接拦截超量请求，避免产生巨额账单。

▎面试加分点

  • 能区分长短期记忆的存储选型：短期热记忆（最近几轮对话、当前任务状态）存在 Redis，追求速度；长期冷记忆（历史会话归档、用户画像）存在 PostgreSQL，追求持久化和一致性
  • 能提到 Redis 做 Agent 状态存储的优势：支持过期自动清理，不需要写定时任务删冷数据，天然适合会话类临时数据的生命周期管理

📌 概念题 · Q9

考点标签

pgvector · 难度：⭐⭐⭐

📝 题目

pgvector 支持 HNSW 和 IVFFlat 两种向量索引，在 Agent/RAG 场景下应该如何选型？两者的核心差异是什么？

💡 参考答案

▎一句话结论

绝大多数企业级 Agent/RAG 场景优先选择 HNSW 索引，它的检索速度快、召回率高、性能稳定；IVFFlat 仅适合内存极度紧张、对召回率要求不高的纯离线场景。

▎核心原理

  • HNSW（层次化导航小世界）：基于多层图结构的索引，检索时从上层图快速定位到下层的近邻区域，再做精确查找
  • IVFFlat（倒排文件聚类）：先把所有向量通过 K-Means 聚类成若干个桶，检索时只查找离查询向量最近的几个桶里的向量
  • 核心差异维度：建索引速度、内存占用、检索延迟、召回率、对数据分布的敏感度

▎深入解释

HNSW 索引的原理类似“多层高速公路网”：最上层是稀疏的“高速路”，可以快速跨越大范围区域定位到目标附近，下层是密集的“普通道路”，做精确的近邻查找。这种结构的优势是检索速度极快，即使数据量增长到百万、千万级，查询延迟也能保持在毫秒级，召回率非常高，不需要提前对数据做训练，数据增删时性能也稳定。缺点是建索引速度慢，内存占用高，因为需要存储图的所有边连接关系。
IVFFlat 索引的原理是“先聚类再查找”：提前把所有向量分成 N 个聚类中心，检索时只计算离查询向量最近的几个聚类里的向量，不需要遍历全量数据。它的优势是建索引快、内存占用小，但缺点非常明显：检索速度和召回率高度依赖聚类的质量，如果查询向量落在两个聚类的边界上，很容易漏召回相关结果；如果数据分布变化大，还需要定期重新训练聚类中心，维护成本高。
对于 Agent 和 RAG 场景来说，检索的召回率直接决定了回答的准确性，如果因为索引漏召导致大模型拿不到关键信息，就会产生幻觉，因此只要服务器内存能够承载，HNSW 是绝对的首选。

▎面试加分点

  • 能说出 HNSW 的调优参数：M 参数控制每个节点的边数，越大召回率越高、内存占用越大；ef_construction 控制建索引时的搜索宽度，越大索引质量越高、建索引越慢；ef_search 控制查询时的搜索宽度，越大召回率越高、查询越慢
  • 能说明 IVFFlat 的适用场景：纯离线的批量相似性计算、内存极度受限的嵌入式场景，在线生产环境很少使用

📌 概念题 · Q10

考点标签

大模型架构 · 难度：⭐⭐⭐⭐

📝 题目

现代大模型（如 Llama 3、Mistral）普遍采用 GQA（分组查询注意力）架构，而不是传统的 MHA（多头注意力）或极端的 MQA（多查询注意力），这种设计解决了什么核心问题？

💡 参考答案

▎一句话结论

GQA 是在 MHA 的效果和 MQA 的效率之间做的最优平衡，通过让多组 Query 头共享一组 KV 头，在几乎不损失模型效果的前提下，把 KV Cache 的显存占用降低了数倍，是当前大模型长上下文推理的标配架构。

▎核心原理

  • MHA（多头注意力）：每个 Q 头对应独立的 K 头和 V 头，效果最好，但 KV Cache 显存占用最大
  • MQA（多查询注意力）：所有 Q 头共享同一个 K 头和 V 头，KV Cache 显存占用最小，推理速度最快，但模型效果会有明显损失
  • GQA（分组查询注意力）：把 Q 头分成若干组，每组内的 Q 头共享一组 K/V 头，显存占用和效果介于两者之间

▎深入解释

在传统的 MHA 架构中，比如 Llama 2 70B 有80个注意力头，就需要存储80份 K 和 V 的缓存，KV Cache 占用的显存非常大，上下文长度越长、并发越高，显存压力越大，很难支撑长上下文推理。
后来有人提出了 MQA，让所有80个 Q 头共享1个 K 头和1个 V 头，这样 KV Cache 的显存占用直接降到原来的1/80，推理速度大幅提升，但代价是模型的注意力表达能力变弱，生成质量下降明显，尤其是复杂推理和长文本理解的效果损失较大。
GQA 则找到了一个完美的平衡点：比如把80个 Q 头分成8组，每组10个 Q 头共享1组 K/V 头，总共只需要8组 K/V 头，KV Cache 显存占用降到原来的1/10，和 MQA 接近，但因为每组 K/V 头只需要服务10个 Q 头，表达能力比 MQA 强很多，效果几乎和完整的 MHA 持平。这种设计让模型可以在有限的显存下支撑更长的上下文、更高的并发，同时不会明显降低生成质量，因此从 Llama 3、Mistral 到 GPT-3.5/4 之后的新模型，几乎全部采用了 GQA 架构。

▎面试加分点

  • 能关联 KV Cache 优化体系：GQA 是从模型架构层面减少 KV 头数量，和 PagedAttention（显存管理优化）、KV 量化（存储精度优化）、Context Cache（缓存复用）是互补关系，工业界通常会同时使用这几种技术
  • 能说明 GQA 对推理的价值：不仅减少显存占用，因为 KV 数据量变小了，显存带宽的压力也大幅降低，推理生成速度会有明显提升，是大模型落地性价比极高的架构优化。

二、应用题（5 道 · 分类型）

🛠 应用题 · Q1 · 架构设计

题型

架构设计

场景标签

Agentic RAG 选型、传统RAG对比、企业知识库分层

📝 题目

你所在的公司计划上线一套全场景内部知识助手，需要同时支撑三类完全不同的业务查询：1）高并发的员工标准政策查询（如“年假有多少天”“加班费怎么算”，日请求量10w+，要求响应时间<500ms）；2）复杂的跨文档流程咨询（如“我从上海分公司调岗到北京，社保、公积金、劳动合同需要走哪些流程，分别找哪个部门审批”，需要跨3-5份制度文档整合答案）；3）实时数据查询（如“我这个月的工资条明细”“当前剩余年假天数”，需要对接内部HR系统接口）。CTO要求你设计一套分层检索架构，不能直接全量上Agentic RAG导致成本和延迟失控，也不能只用传统RAG导致复杂问题回答准确率不足。请说明你的架构设计思路，以及不同流量的路由逻辑。

💡 参考答案

▎解题思路

  1. 第一步先做流量分层：根据查询复杂度、延迟要求、数据来源三个维度，把三类请求做物理隔离，避免“大炮打蚊子”，用最低成本匹配最合适的检索链路。
  2. 第二步设计三级检索能力池：从快到慢、从低成本到高成本依次部署「缓存层→传统Advanced RAG层→Agentic RAG层→工具调用层」，每一层只处理自己能力范围内的请求。
  3. 第三步设计前置路由网关：用轻量小模型做意图分类，把请求精准分发到对应链路，同时设置降级和兜底逻辑，避免高复杂度请求拖垮整个系统。
  4. 第四步做全链路监控：统计每类请求的命中率、准确率、延迟、Token成本，持续迭代路由规则和各层能力边界。

▎详细方案

整个架构采用“漏斗式分层路由”设计，从入口到后端共分为四层：
第一层是入口缓存层：所有高频标准问题（如年假天数、社保缴纳比例）提前把标准答案存在Redis，请求进来后先做Embedding语义匹配缓存，命中直接返回，这部分请求占总流量的60%以上，平均响应时间<100ms，几乎不消耗LLM Token。
第二层是传统Advanced RAG层：针对单跳、答案明确在单篇文档内的查询，走固定流程：Query改写→向量检索+关键词检索→Rerank重排→单次LLM生成，不引入任何循环和工具调用逻辑，这部分覆盖30%左右的流量，平均响应时间<500ms，Token成本仅为Agentic RAG的1/5。
第三层是Agentic RAG层：针对跨文档、多跳推理的复杂流程类问题，基于LangGraph部署带反思纠错的Agent链路，内置三个核心能力：动态路由（判断需要检索哪几类文档）、多跳拆解（把复杂问题拆成多个子问题依次检索）、质检循环（对检索到的Chunk做相关性打分、对生成的答案做幻觉检测，不满足要求则重写Query二次检索），这部分仅处理8%左右的复杂流量。
第四层是工具调用层：针对需要实时数据的查询，Agent自动判断需要调用的内部API（如工资系统、年假系统），拿到结构化数据后整合生成回答，这部分处理剩下2%的实时查询流量。
前置路由网关用7B参数的开源小模型做意图分类，分类维度包括：是否为高频标准问、是否需要跨文档推理、是否需要调用实时接口，分类置信度高于90%直接转发到对应链路，置信度低于90%默认先降级到传统RAG层，如果检索到的上下文相似度低于阈值，再自动升级到Agentic RAG层处理。

▎关键细节 & 踩坑点

  • 绝对不能把所有请求都打到Agentic RAG链路：Agentic RAG因为有多次LLM调用、循环反思逻辑，平均响应时间是传统RAG的3-5倍，Token成本是传统RAG的4-10倍，如果高并发的简单请求走这个链路，不仅用户体验差，成本会直接失控。
  • 路由模型不能用GPT-4等大模型：意图分类是非常简单的任务，用轻量开源小模型甚至传统的文本分类模型就能做到95%以上的准确率，每次分类成本不到大模型的1%，延迟低一个数量级。
  • 必须设置降级开关：当大模型API限流或者Agentic RAG链路负载过高时，可以自动把非核心的复杂请求暂时降级到传统RAG层，返回“当前咨询人数较多，复杂问题建议稍后再试或查看对应制度文档”的提示，保证核心的高频查询链路不受影响。
  • 缓存层不能只做精确匹配：员工问“年假多少天”和“我一年能休几天年假”语义完全一致，必须用向量语义匹配做缓存，否则缓存命中率会非常低，起不到削峰作用。

▎可扩展优化

  • 可以引入用户反馈闭环：用户对回答点“踩”的问题，自动标记为路由错误或者回答质量差，定期微调路由模型和优化各层的检索逻辑，持续提升准确率。
  • 可以给Agentic RAG层设置最大迭代次数：比如最多允许2轮重检索，超过次数直接返回当前能找到的最优答案，并提示用户问题比较复杂可以转人工，避免陷入死循环导致延迟无限升高。
  • 可以做冷热数据分离：3个月以上的历史制度文档存在低成本的对象存储，近1年的高频访问文档存在内存向量库，进一步提升检索速度。

🛠 应用题 · Q2 · 场景分析题

题型

场景分析

场景标签

LLM结构化输出、JSON稳定性、工程防御体系

📝 题目

你所在团队开发的Agentic RAG系统中，有一个核心节点是“检索结果相关性打分”：需要让LLM对每一个检索回来的Chunk输出严格的JSON格式，包含三个字段：relevance_score（0-10的整数，代表相关性分数）、is_noise（布尔值，代表是否为无关噪声）、reason（字符串，说明打分理由），后续业务代码会根据这个JSON结果过滤噪声Chunk。但上线后频繁出现故障：有时候模型输出Markdown代码块包裹的JSON、有时候字段名写错、有时候分数超出0-10范围、甚至输出一堆解释性文字，导致后续JSON解析失败，整个Agent链路直接崩溃。运维同学说“干脆每次解析失败就重试”，但重试会导致延迟和成本翻倍。请你设计一套完整的方案，从根源上解决这个JSON输出不稳定的问题，把解析失败率降到0.1%以下。

💡 参考答案

▎解题思路

  1. 第一步按照“软约束→硬约束→兜底防御”的三层工业级方案搭建体系，从模型生成的源头、过程、事后三个环节层层设防，而不是只靠事后重试。
  2. 第二步优先用最低成本的方案解决99%的问题，把高成本的重试和纠错作为最后一道防线，尽可能减少额外的延迟和Token消耗。
  3. 第三步针对这个打分场景做定向优化，因为输出结构固定、字段简单，可以用比通用JSON输出更严格的约束手段。
  4. 第四步建立监控体系，统计每一层的拦截率，持续优化Prompt和约束规则，把重试率压到最低。

▎详细方案

整个方案分为四层防御，层层递进：
第一层是Prompt软约束（解决80%的基础问题）：首先写死强指令，明确告诉模型“你是严格的JSON打分器，仅输出符合RFC 8259标准的纯JSON对象，禁止任何解释性文字、禁止Markdown代码块、禁止注释，第一个字符必须是{，最后一个字符必须是}”；然后前置Schema声明，把三个字段的类型、取值范围写得清清楚楚：relevance_score是0-10的整数，不能是小数也不能超出范围；is_noise是布尔值，只能是true或false，小写；reason是不超过50字的字符串；最后加2个Few-Shot示例，一个是相关Chunk的正确输出样例，一个是噪声Chunk的正确输出样例，让模型照抄格式。
第二层是API原生硬约束（解决15%的格式问题）：调用大模型API时直接开启官方的response_format={"type": "json_object"}参数，如果用的是支持JSON Schema传入的模型（如GPT-4o、Claude 3），直接把三个字段的Schema、取值范围、枚举值传给模型，从生成层面强制模型输出符合Schema的内容，不会出现多余文字或者字段缺失。
第三层是约束解码（针对开源模型场景）：如果用的是本地部署的开源模型不支持response_format参数，就用Outlines或者vLLM的结构化输出功能，把JSON Schema传给推理框架，模型生成每个Token的时候实时过滤非法字符，比如字段名必须严格匹配、分数只能是0-10的数字、布尔值只能是小写的true/false，从语法层面100%杜绝格式错误。
第四层是后处理兜底（解决剩下5%的异常）：首先用正则表达式提取内容，不管模型输出了Markdown代码块还是前后加了多余文字，都用正则把{}包裹的JSON核心内容提取出来；然后用json-repair库自动修复常见错误，比如补全缺失的括号、修正中文引号、删除 trailing comma；接着用Pydantic定义严格的数据模型，校验字段类型、取值范围，如果校验失败，不要直接全量重试，而是把具体的错误信息（比如“relevance_score字段值为15，超出0-10范围”）传给模型，让它只修正错误部分，而不是重新生成整个内容；最后如果连续2次修正都失败，再触发降级逻辑，用简单的向量相似度分数代替LLM打分，保证链路不崩溃。

▎关键细节 & 踩坑点

  • 不要一开始就全量靠重试解决问题：重试不仅会翻倍延迟和Token成本，还会因为模型的随机性导致同样的错误反复出现，必须把防线往前移，尽可能在生成阶段就避免错误。
  • Few-Shot示例绝对不能少：哪怕开了response_format，很多模型还是会出现字段值不符合业务要求的问题（比如分数打15分、布尔值输出“是/否”），有正确的示例引导，模型的格式符合率会提升30%以上。
  • Pydantic校验不能只做类型校验：必须加业务规则校验，比如relevance_score必须在0-10之间、reason长度不能超过100字，否则哪怕JSON格式合法，业务逻辑还是会出错。
  • 不要用大模型做JSON修复：json-repair这类规则库修复常见格式错误的成功率超过95%，速度比大模型快100倍，成本几乎为0，只有规则修复不了的情况才考虑让大模型修正。

▎可扩展优化

  • 可以收集所有解析失败的Bad Case，定期整理成反例加入Few-Shot，让模型知道哪些输出是错误的，进一步降低错误率。
  • 如果这个打分节点的调用量非常大，可以专门微调一个小模型来做这个打分任务，用几千条标注好的JSON数据微调后，格式准确率可以达到99.9%以上，成本只有大模型的1/10，延迟低一个数量级。
  • 可以给JSON解析加链路埋点，统计每一层的错误拦截率，如果某一层的拦截率突然升高，及时告警，比如发现模型突然开始大量输出Markdown代码块，可能是模型版本更新导致的，需要及时调整Prompt。

🛠 应用题 · Q3 · 工程实现题

题型

工程实现

场景标签

KV Cache优化、推理成本优化、高并发推理

📝 题目

你所在公司的内部知识助手上线后，遇到了严重的推理性能问题：大模型推理服务用了8张A10显卡，在早高峰100并发的时候就出现了严重的排队，平均响应时间超过10秒，GPU显存占用长期在95%以上，其中KV Cache占用了超过60%的显存。监控数据显示：80%的请求都是多轮对话，平均每轮对话带有1500Token的固定System Prompt（包含公司知识库回答规范、安全规则等），以及平均1000Token的历史对话上下文，用户每一轮新提问只有不到100Token。请你设计一套基于KV Cache优化的工程改造方案，把并发吞吐量提升至少3倍，平均响应时间降到3秒以内，同时尽可能降低改造成本。

💡 参考答案

▎解题思路

  1. 第一步先分析显存占用的瓶颈来源：从监控数据看，KV Cache占了60%的显存，且80%的请求有大量公共前缀（固定System Prompt）和可复用的历史上下文，核心优化方向就是提升KV Cache的利用率、减少重复计算。
  2. 第二步按照“架构层→框架层→模型层→算法层”的优先级依次做优化，优先改造成本低、收益大的方案，最后再考虑加机器。
  3. 第三步每一步优化都做压测验证，确保优化后不影响回答效果，避免为了性能牺牲回答质量。
  4. 第四步建立推理性能监控体系，持续跟踪KV Cache命中率、显存利用率、吞吐量等指标。

▎详细方案

具体优化分四个落地步骤，前三个步骤不需要换模型，改造成本极低，就能实现3倍以上的吞吐量提升：
第一步：替换推理框架为vLLM，启用PagedAttention机制。原来的推理框架把每个请求的KV Cache存在连续的显存块里，因为请求长度不一，会产生大量的显存碎片，实际显存利用率通常不到40%；PagedAttention模仿操作系统的虚拟内存管理，把KV Cache切成固定大小的Block，非连续存储，彻底解决内存碎片化问题，显存利用率可以提升到90%以上，仅这一步就能把并发吞吐量提升2-3倍，不需要改任何业务代码。
第二步：启用前缀缓存（Context Cache/Prefix Caching）功能。针对所有请求共享的1500Token固定System Prompt，在第一个请求计算完它的KV Cache后，直接固化在显存里，后续所有请求只要System Prompt完全一致，就可以直接命中缓存，不需要重复计算这部分的KV，这部分占每个请求总KV长度的60%，直接减少60%的KV显存占用和计算量；针对同一个Session的多轮对话，把之前轮次的历史对话KV Cache也存在缓存里，用户下一轮提问时，只需要计算新提问的Token对应的KV，不需要重新计算所有历史上下文的KV，这部分又能减少30%以上的重复计算。
第三步：开启KV Cache量化。把原本用FP16存储的KV Cache压缩为INT8精度，vLLM等框架已经支持开箱即用的KV INT8量化，几乎没有精度损失，KV Cache的显存占用直接减半，相当于在原来的显卡上能多承载一倍的并发量。
如果做完前三步还不满足性能要求，再考虑第四步模型层优化：把现有模型替换为采用GQA（分组查询注意力）架构的版本，比如Llama 3、Qwen 2等现代模型，GQA让多个Q头共享同一组KV头，KV Cache的显存占用可以直接降到原来的1/4，吞吐量还能再提升2倍左右，这一步需要做模型效果验证，确保回答准确率不下降。

▎关键细节 & 踩坑点

  • 前缀缓存必须保证System Prompt完全一致：哪怕多一个空格、多一个换行符，都会导致前缀匹配失败，缓存无法命中，所以必须把System Prompt做成固定的模板，不要动态拼接随机内容。
  • KV量化不要一开始就上INT4：INT4量化会带来比较明显的精度损失，尤其是长上下文场景下容易出现回答混乱，优先用INT8量化，精度损失几乎可以忽略，显存减半的收益已经足够大。
  • 不要盲目开过长的上下文窗口：很多团队为了支持长文本把上下文窗口开到32k甚至128k，但实际上90%的请求上下文长度都在4k以内，过长的上下文窗口会导致每个Block预留的显存变大，反而降低KV Cache利用率，应该根据实际业务的上下文长度分布设置合理的窗口大小。
  • 多轮对话的KV缓存要设置合理的过期时间：比如会话超过30分钟不活跃就自动清理对应的KV缓存，避免冷会话长期占用显存。

▎可扩展优化

  • 可以做层级化KV缓存：把公共System Prompt的KV Cache固化在显存里，把活跃用户的历史对话KV Cache存在显存，把不活跃用户的KV Cache压缩后存在CPU内存或者SSD上，用户再次访问时再加载到显存，进一步提升显存利用率。
  • 可以针对高频用户的会话做缓存预热：比如早高峰前把前一天活跃用户的最近几轮对话KV Cache提前加载到显存，进一步提升高峰时的缓存命中率。
  • 可以配合请求批处理（Continuous Batching）机制：vLLM默认支持动态批处理，把不同请求的生成阶段合并计算，进一步提升GPU的利用率，吞吐量还能再提升30%以上。

🛠 应用题 · Q4 · 排障优化题

题型

排障优化

场景标签

Agentic RAG延迟优化、成本优化、线上故障排查

📝 题目

你们团队基于LangGraph开发的Agentic RAG合同审核助手上线一周后，收到大量用户投诉：平均一个合同审核请求要等25秒才能出结果，且每次审核消耗的Token成本是预期的5倍。排查链路日志后发现三个异常现象：1）平均每个请求会触发4.2次工具调用，其中有2次调用返回的Chunk和问题完全不相关，但系统还是把这些内容注入到了上下文里；2）很多时候Agent已经检索到了足够的信息，但还是会触发“重写Query补充检索”的循环，最多的一个请求循环了8次才进入生成阶段；3）每次工具调用都会把之前所有的检索结果、思考过程全部重新拼接到Prompt里，上下文长度从最开始的1k Token很快膨胀到12k Token。请你定位问题根源，并给出具体的优化方案，把平均响应时间降到8秒以内，Token成本降低70%，同时保证审核准确率不下降。

💡 参考答案

▎解题思路

  1. 第一步先拆解整个Agent链路的耗时和Token消耗分布：从日志看，核心问题是无效循环过多、无关内容没有及时过滤、上下文无限制膨胀，导致LLM调用次数多、每次调用的上下文长，是延迟和成本高的根本原因。
  2. 第二步按照“前置拦截→循环终止→上下文压缩”的顺序优化，先砍掉无效的工具调用和循环，再压缩每次调用的上下文长度，从根源上减少LLM调用次数和单次调用的Token量。
  3. 第三步每一步优化都做AB测试，对比优化前后的审核准确率，避免为了速度和成本牺牲回答质量。
  4. 第四步增加链路的可观测性，对每个请求的循环次数、Token消耗、检索相关性做监控，出现异常及时告警。

▎详细方案

针对三个核心问题逐个击破：
第一个问题：无效工具调用返回无关Chunk。根源是没有在工具返回后做及时的质检过滤，导致垃圾内容进入上下文，误导后续Agent判断。优化方案是在每次工具调用返回结果后，立刻加一个轻量的文档打分节点：用小模型（或者用向量相似度阈值过滤）判断返回的Chunk和当前子问题是否相关，相关性低于阈值的Chunk直接丢弃，不注入上下文，避免垃圾内容干扰Agent判断，也减少后续上下文的Token长度。同时在工具注册时优化工具的Description描述，明确每个工具的适用场景，给Agent举几个正确调用和错误调用的例子，减少Agent选错工具的概率，从源头减少无效工具调用。
第二个问题：无限制的检索循环。根源是反思节点的终止条件设置太模糊，Agent不知道什么时候“已经检索到足够信息”，导致反复重写Query检索。优化方案是设置明确的循环硬终止规则：① 最多允许2轮补充检索，达到次数直接进入生成阶段，绝对不允许循环超过3次；② 每次反思判断“是否需要补充检索”时，必须给出明确的判断依据，如果现有上下文已经覆盖了问题需要的所有要素，直接终止循环，不能模糊地说“可能需要更多信息”就触发检索；③ 加一个早停机制：如果新一轮检索返回的结果和上一轮的内容重复度超过80%，说明已经没有新的相关信息了，直接终止循环，不需要再检索。
第三个问题：上下文无限制膨胀。根源是每次调用LLM都把所有历史状态、所有检索结果全量拼接，导致上下文越来越长。优化方案是做上下文的分层管理：① 固定不变的System Prompt、工具Schema只在第一次调用时传入，后续循环调用不需要重复拼接；② 已经被判定为无关的Chunk直接丢弃，不保留在状态里；③ 每完成一个子问题的检索，就把对应的检索结果压缩成一段简短的摘要，而不是把原始Chunk全文一直留在上下文里，只有进入最终生成阶段时，才把所有相关的原始Chunk全量取出来注入Prompt；④ 历史的思考过程、工具调用的错误返回只保留最近1轮的，更早的中间状态直接清理，不需要一直带入上下文。
按照上面三个方案优化后，平均每个请求的工具调用次数会从4.2次降到1.5次左右，循环次数从平均3次以上降到1次以内，平均上下文长度从12k降到3k以内，Token成本可以降低70%以上，延迟也会因为LLM调用次数减少降到8秒以内。

▎关键细节 & 踩坑点

  • 绝对不能无限制允许Agent循环：很多开发者写LangGraph的时候只设置了流转逻辑，没设置最大循环次数，Agent很容易陷入“检索→觉得信息不够→再检索”的死循环，不仅延迟高，还会把Token耗尽，必须在框架层设置全局的最大步数限制，超过就强制终止。
  • 文档打分节点不要用大模型：判断Chunk和问题是否相关是非常简单的任务，用向量余弦相似度做初筛，相似度低于0.6的直接丢弃，剩下的用7B参数的小模型打分，成本只有大模型的1/20，延迟极低，不要每次都用GPT-4做打分。
  • 上下文压缩不能过度：中间循环过程中可以用摘要代替原始Chunk，但最终生成回答的时候必须把所有相关的原始Chunk注入上下文，不能只用摘要，否则会因为摘要的信息损失导致幻觉，影响审核准确率。
  • 不要把所有工具调用的返回结果都存在State里：LangGraph的State会在每一个节点之间传递，无关的内容存在State里会导致每次节点调用都多传很多无用Token，必须及时清理State里的无效数据。

▎可扩展优化

  • 可以引入查询路由缓存：对于常见的合同审核问题，提前缓存对应的检索Query和需要调用的工具，相同类型的问题直接走固定检索路径，不需要Agent每次都思考选什么工具、怎么拆Query，进一步减少LLM调用次数。
  • 可以把高频的合同条款提前整理成结构化的知识库，比如“违约金上限”“管辖法院约定”等常见审核点直接存在结构化数据库里，Agent遇到这些问题直接查结构化数据，不需要做向量检索，速度更快、准确率更高。
  • 可以做流式输出：检索完成后，模型生成答案的时候就逐字流式返回给用户，用户感知到的首字响应时间（TTFT）会从8秒降到2秒以内，大幅提升用户体验，哪怕总生成时间还是5秒，用户也不会觉得慢。

题型

综合落地

场景标签

Agent产品交付、存储架构选型、从0到1落地

公司要求你带领一个4人小团队，用8周时间从0到1交付一套面向中小企业的“销售助理Agent”产品，核心功能包括：1）销售可以用自然语言查询客户的历史订单、跟进记录、应收款余额等实时CRM数据；2）销售跟进客户前，Agent自动整合客户的历史沟通记录、公司最新的产品报价、相关的销售话术，生成个性化的跟进建议；3）销售和客户沟通后，可以口述沟通内容，Agent自动整理成结构化的跟进记录存入CRM；4）支持多轮对话上下文记忆，销售可以连续追问，不需要每次重复客户名字。CTO要求初期不需要追求极致的大规模性能，优先保证快速上线、功能稳定、运维简单，不要引入过多复杂的中间件，等用户量超过1万再考虑架构升级。请你设计整套系统的落地技术方案，包括存储选型、核心模块设计、8周排期规划，确保按时高质量交付。

💡 参考答案

▎解题思路

  1. 第一步做技术选型的核心原则：优先用成熟、简单、运维成本低的技术栈，拒绝过度设计，尽可能用最少的组件实现所有功能，把精力放在核心业务逻辑上，而不是搭复杂的分布式架构。
  2. 第二步拆分核心模块：按照“用户层→Agent编排层→工具层→存储层”四层架构拆分，每个模块职责清晰，团队成员可以并行开发。
  3. 第三步做分阶段排期：先做最小可用版本（MVP）跑通核心流程，再做功能完善和体验优化，最后做测试上线，确保8周内可以交付。
  4. 第四步提前设计好架构的扩展点，等后续用户量涨上来之后可以平滑升级，不需要推倒重来。

▎详细方案

首先是技术选型，严格遵循“少组件、易运维”原则：
- Agent编排层直接用LangGraph，不需要自己手写异步编排和状态流转，内置的Checkpoint机制可以直接搞定状态持久化，开发效率最高。
- 存储层不搞复杂的多库分离，直接用PostgreSQL作为唯一的核心数据库，不需要单独部署Milvus等专用向量库、不需要单独部署Redis，把运维成本降到最低：① 用pgvector插件存储产品资料、销售话术等知识库向量，支持关系字段过滤+向量相似度混合检索，初期百万级向量完全够用；② 用JSONB类型存储用户会话历史、Agent运行状态、结构化的跟进记录，配合GIN索引查询速度极快；③ 用SELECT ... FOR UPDATE SKIP LOCKED实现异步任务队列，用来处理CRM数据同步、跟进记录异步入库等后台任务，不需要单独部署RabbitMQ等消息队列；④ CRM的业务数据（客户信息、订单、应收款）也存在PostgreSQL里，初期数据量不大完全不需要分库分表。
- LLM调用层直接用成熟的大模型API（如通义千问、DeepSeek），不需要自己部署开源模型，配合前面提到的三层JSON防御体系保证结构化输出稳定。
核心模块拆分四个部分，团队4个人可以并行开发：① Agent核心编排模块：负责意图识别、任务拆解、工具调用、反思纠错，实现多轮对话逻辑；② 工具集模块：封装三个核心工具——CRM数据查询工具（查客户订单、应收款）、知识库检索工具（查产品报价、销售话术）、CRM写入工具（把整理好的跟进记录存入系统）；③ 数据处理模块：负责产品资料、销售话术的解析、切片、向量化入库，以及语音转文字的对接（销售口述内容先转成文本再给Agent处理）；④ 前端交互模块：做Web端和企业微信端的对话界面，支持流式输出、跟进记录一键确认存入CRM。

▎关键细节 & 踩坑点

  • 初期绝对不要过度设计：不要一开始就上微服务、分布式向量库、Redis集群、消息队列这些组件，对于初期用户量不到1万的产品，一台4核8G的服务器跑PostgreSQL+应用服务完全足够，多一个组件就多一倍的运维成本和故障点，创业团队小步快跑优先。
  • 不要一开始就做太复杂的Agent能力：初期不要搞多Agent协作、复杂的反思循环，核心的三个功能用单Agent+三个工具就能实现，Agent逻辑越简单，稳定性越高，出问题越容易排查。
  • 数据安全必须提前考虑：因为涉及客户订单、应收款等敏感商业数据，所有工具调用必须做权限校验，销售只能查询自己负责的客户数据，向量检索时必须加owner_id的过滤条件，绝对不能出现A销售查到B销售的客户数据的情况。
  • 跟进记录自动生成后必须加人工确认环节：Agent生成的跟进记录不能直接存入CRM，必须在前端让销售确认、可以修改，点击确认后再存入，避免大模型幻觉生成错误的记录污染业务数据。

▎可扩展优化

  • 架构预留好扩展点：PostgreSQL的pgvector初期足够用，等后续知识库向量超过千万级、检索延迟升高时，再把静态知识库向量迁移到Milvus等专用向量库，会话和业务数据还是存在PG，实现平滑升级，不需要重构整个系统；后续并发量涨上来之后，再引入Redis做高频问答缓存、限流、分布式锁，不需要一开始就上。
  • 后续可以增加销售话术推荐的个性化优化：根据销售和客户的历史沟通记录，自动学习不同销售的说话风格，生成的跟进建议更符合销售的个人习惯，提升采纳率。
  • 可以增加风险预警功能：Agent自动识别客户沟通中的风险信号（如客户提到“要换供应商”“对价格不满意”），自动给销售主管发告警，提前介入跟进，提升成单率。
  • 后续用户量上来之后，可以把异步任务从PG的SKIP LOCKED队列迁移到专业的消息队列，把热点数据缓存到Redis，一步步平滑升级，不需要一开始就做复杂架构。
