10 道 AI Agent 概念型面试题

📌 概念题 · Q1

考点标签

Skill 架构 · 难度：⭐⭐⭐

📝 题目

在构建多功能 AI Agent 系统时，知识库提出了"技能专用的局部 Prompt"（Skill 文件）的设计理念。请问：将系统拆分为多个独立的 .skill 配置文件（如 trend_analyzer.skill、media_planner.skill、platform_pusher.skill），与把所有功能写在一个巨大的主 Prompt 中相比，在上下文管理、模块迭代、团队协作三个维度上分别有什么核心优势？为什么说 Skill 文件是"包装了灵魂的能力包"？

💡 参考答案

▎一句话结论

Skill 文件是将"角色设定 + 行为准则（SOP）+ 绑定工具"封装为独立配置单元的模块化架构，它让 Agent 从"一个大脑硬扛所有事"进化为"主调度 + 专家坐席"的协同体系。

▎核心原理

  • 上下文隔离：每个 Skill 只加载自己的局部 Prompt，避免主 Agent 的上下文被无关指令污染
  • 热插拔与解耦：技能文件独立存储、独立修改，某个环节效果不好只需替换一个 YAML 文件，不影响全局
  • 动态路由挂载：主 Agent 作为"前台接待"，根据用户意图动态加载对应 Skill，实现按需激活

▎深入解释

想象一个公司：如果所有员工共用一个大脑，财务、销售、客服的知识全塞在一起，每次做决策时这个大脑都要在海量无关信息中筛选，效率极低且容易出错。Skill 架构的本质就是给每个"专家"一个独立的大脑（局部 System Prompt），主 Agent 只做调度，不做具体执行。在工程落地时，这意味着每个 Skill 文件可以独立版本管理、独立测试、独立优化。比如你的小红书文案改写效果不好，你只需要打开 xhs_style_transformer.yaml 调整 Prompt 里的"震惊体"描述，而不需要触碰热点分析和平台发布模块。这种设计还天然支持多流水线协作——热点分析 Skill 的输出可以作为内容脚本 Skill 的输入，形成一条可编排的生产线。

▎面试加分点

  • 能点出"Skill 是 Prompt + SOP + Tool 的三位一体封装"，而 Tool 只是裸函数，这是两者最本质的区别
  • 能结合 LangGraph 等框架说明 Skill 的"动态加载"本质上是运行时 Prompt 拼接（final_system_prompt = main_prompt + skill_prompt）
  • 能提到 Skill 架构对非技术人员的友好性：运营可以只改 YAML 文件而不碰代码

▎常见误区

  • 误以为 Skill 就是 Tool 的别名——实际上 Tool 是"手"，Skill 是"带着脑子的人"
  • 误以为拆分 Skill 越多越好——过度拆分会导致路由决策本身变得复杂，增加分类错误的概率
  • 误以为 Skill 文件只能用于简单场景——实际上多 Skill 的流水线协作可以支撑复杂的自媒体运营全链路

📌 概念题 · Q2

考点标签

动态路由 · 难度：⭐⭐⭐⭐

📌 题目

在智能客服系统中，知识库描述了三种 Skill 的动态路由场景：政策解答（policy_expert.skill）、业务操作（order_handler.skill）和客诉安抚（empathy_complaint.skill）。当用户输入"老子昨天就申请退款了，到现在还没动静，你们是不是骗子系统？！"时，系统会优先激活客诉安抚 Skill 而非订单处理 Skill。请问：这种基于情绪优先级的路由决策背后的设计逻辑是什么？如果路由分类器无法准确判断应该激活哪个 Skill，会带来什么工程风险？

💡 参考答案

▎一句话结论

动态路由的核心不是"找对 Skill"，而是"在多个可能正确的 Skill 中，按业务优先级选择那个能最大化用户满意度的 Skill"——情绪安抚的优先级必须高于业务处理，因为带着怒火的用户无法接受冷冰冰的流程查询。

▎核心原理

  • 情绪识别优先于意图识别：当检测到强烈负面情绪时，先激活安抚 Skill，让用户"被理解"后再转入业务处理
  • Skill 行为统治权：一旦某个 Skill 被激活，Agent 的行为完全受该 Skill 的 System Prompt 统治，保证行为一致性
  • 可回退与衔接：安抚 Skill 完成任务后，可以顺畅地调用订单处理 Skill 查询状态，实现 Skill 间的接力

▎深入解释

这个场景揭示了一个关键的产品哲学：用户说的内容（退款查询）和用户真正需要的（情绪被回应 + 问题被解决）往往不是同一件事。如果路由直接匹配"退款"关键词激活订单处理 Skill，Agent 可能会机械地回复"请提供订单号"，这会让愤怒的用户更加愤怒。正确的做法是先用安抚 Skill 做情绪认同（"非常理解您的心情"），再引导用户提供必要信息，最后转入业务处理。这种设计类似医院的分诊台：一个胸口疼的患者来了，分诊护士不会直接让他去挂号排队，而是先做紧急评估。路由分类器的误判风险在于：如果错误地将愤怒用户路由到订单处理 Skill，不仅解决问题失败，还可能引发投诉升级甚至舆情危机。

▎面试加分点

  • 能提出"情绪分数阈值"的量化设计：比如情绪分类器输出 anger_score > 0.7 时强制路由到安抚 Skill
  • 能说明"安抚 Skill 不是终点，而是桥梁"——它的最终目标是让用户愿意配合后续的业务流程
  • 能提到多 Skill 协作中的状态传递：安抚 Skill 记录的用户诉求和情绪标签需要传递给订单处理 Skill，避免用户重复描述

▎常见误区

  • 误以为路由决策只基于语义相似度——实际上情绪、权限、业务优先级都是路由的输入信号
  • 误以为安抚 Skill 和订单 Skill 是互斥的——实际上它们应该是可编排的流水线关系
  • 误以为动态路由可以完全自动化——在高风险场景下应该保留人工审核的兜底通道

📌 概念题 · Q3

考点标签

本地部署 · 难度：⭐⭐⭐⭐

📌 题目

知识库中提出了企业本地部署大模型的三级方案：轻量级（双卡 RTX 4090 D + Qwen 3.5-32B INT4）、中量级（4 卡 H200 + Qwen 3.5-72B BF16）、重量级（8 卡 B200 + DeepSeek-R1 671B MoE FP4）。请问：为什么在"轻量级方案"中推荐使用 INT4 量化，而在"中量级方案"中却推荐保持 BF16 原生精度？这种精度选择差异背后的业务场景逻辑是什么？

💡 参考答案

▎一句话结论

量化精度的选择不是技术炫耀，而是"精度损失容忍度"与"业务场景要求"的匹配——日常公文辅助可以容忍 INT4 的 1~2% 性能损失，但金融计算和合同审查必须保持 BF16 的高精度以确保逻辑严密性。

▎核心原理

  • INT4 量化的本质：将模型权重的数值精度从 16 位浮点压缩到 4 位整数，显存占用降低 50%~75%，但推理精度有轻微损失
  • BF16 的优势：保留足够的数值精度，确保复杂逻辑推理和多步计算不出错，适合需要严密推理的场景
  • 业务场景决定精度：文案生成、代码助手等"容错性高"的场景适合量化；金融计算、合同合规等"零容忍"场景必须保精度

▎深入解释

可以类比为"压缩图片"：如果你只是发朋友圈分享日常，用 JPEG 压缩后的图片完全够用，文件小、加载快；但如果你是在做医学影像诊断，任何有损压缩都可能导致误判。INT4 量化就像"有损压缩"，它在绝大多数生成任务中表现良好，但在需要精确数值计算（如理财产品收益计算）或多步逻辑推理（如合同条款的因果分析）时，量化误差可能被逐步放大。中量级方案选择 BF16 而非 INT8/INT4，是因为 H200 的 141GB 超大显存已经可以完整容纳 72B 模型的 BF16 权重，不需要为了省显存而牺牲精度。这是一种"算力充裕时优先保精度"的工程决策。

▎面试加分点

  • 能提到 AWQ/GPTQ 等量化算法的核心思想是"保护重要权重"，不是简单的均匀压缩
  • 能说明 MoE 模型（如 DeepSeek-R1）在 FP4 精度下依然表现优异的原因：每次只激活 37B 参数，量化误差被稀疏激活稀释
  • 能结合"ROI 验证"思路：先用量化模型跑通业务验证价值，再根据实际效果决定是否升级硬件保精度

▎常见误区

  • 误以为量化一定导致效果显著下降——实际上 AWQ 4-bit 的性能损失通常在 1~2% 以内
  • 误以为显存越大就越不需要量化——实际上即使有 141GB 显存，如果要跑多个模型实例或支持高并发，量化仍然是有效的优化手段
  • 误以为所有场景都需要最高精度——这是一种"算力焦虑"，大多数办公辅助场景的容错率远高于金融场景

📌 概念题 · Q4

考点标签

模型选型 · 难度：⭐⭐⭐

📌 题目

知识库中提到，2026 年的开源模型矩阵中，MoE（混合专家模型） 如 DeepSeek-V3/R1（671B 参数，约 37B 激活）和 Gemma 4（26B-A4B MoE）成为企业部署的重要选项。请问：MoE 架构为什么能在参数量巨大的同时保持推理速度可控？与传统 Dense 模型（如 Qwen 3.5-32B 密集模型）相比，MoE 在企业部署中的核心优势和潜在挑战分别是什么？

💡 参考答案

▎一句话结论

MoE 架构的核心魔法是"大参数、小激活"——虽然模型总参数量高达 671B，但每次推理只激活其中约 37B 参数，用"专家的专精"换取"通才的广度"，同时保持推理成本可控。

▎核心原理

  • 稀疏激活机制：MoE 将模型拆分为多个"专家"子网络，每次推理时路由器只选择 Top-K 个专家参与计算（如 DeepSeek-R1 每次激活约 37B 参数）
  • 参数与计算解耦：总参数量决定了模型的"知识容量"，激活参数量决定了"推理速度"，MoE 实现了两者的分离
  • FP4 精度加持：Blackwell 架构的原生 FP4 引擎进一步加速了 MoE 模型的推理吞吐

▎深入解释

可以类比为一家大型咨询公司：公司有 671 位专家（总参数），但每个客户项目只会被分配给最相关的 37 位专家（激活参数）。客户不需要等待所有 671 位专家都发表意见，所以响应速度取决于 37 位专家的工作效率，而不是 671 位的总和。这就是 MoE 的"稀疏激活"魔力。对于企业部署，这意味着：你可以拥有一个"知识极其渊博"的模型（671B 参数的知识容量），同时推理成本只相当于一个 37B 的密集模型。但挑战也很明显：MoE 模型的显存占用仍然巨大（所有专家都要常驻显存），这就是为什么需要 8 卡 B200（1440GB 显存）来承载。此外，MoE 的路由机制也可能出现"专家负载不均"的问题——某些专家被频繁调用，其他专家则长期闲置。

▎面试加分点

  • 能点出"激活参数 vs 总参数"的区别是理解 MoE 的关键，而不是被 671B 这个数字吓到
  • 能说明 MoE 模型在多任务泛化能力上的优势：不同专家可以专精不同领域，避免知识干扰
  • 能提到负载均衡（Load Balancing）是 MoE 训练和推理中的核心工程挑战

▎常见误区

  • 误以为参数量大就一定推理慢——MoE 的推理速度取决于激活参数而非总参数
  • 误以为 MoE 模型一定比 Dense 模型好——在单任务场景下，一个精心训练的 32B Dense 模型可能比 671B MoE 表现更好
  • 误以为 MoE 模型可以在消费级硬件上运行——实际上 671B 的总参数需要巨大的显存来存储，即使激活参数很少

📌 概念题 · Q5

考点标签

RAG vs 微调 · 难度：⭐⭐⭐⭐

📌 题目

知识库中提出了一个明确的工程原则："90% 的场景优先使用 RAG，10% 的场景使用 LoRA 微调"。请问：在什么具体场景下，RAG 方案会失效或不够用，必须转向 LoRA 微调？请从"知识更新频率、输出格式要求、领域术语深度"三个维度分析 RAG 与微调的边界划分逻辑。

💡 参考答案

▎一句话结论

RAG 解决的是"知识从哪里来"的问题，微调解决的是"模型怎么说话"的问题——当需求从"检索正确的知识"升级为"改变模型的行为模式和表达风格"时，就必须从 RAG 转向微调。

▎核心原理

  • RAG 的边界：RAG 擅长注入事实性知识（如政策条款、产品参数），但无法改变模型的语言风格、推理模式或输出格式偏好
  • LoRA 微调的优势：可以改变模型的"说话语气"（如律师腔调）、强制特定输出格式（如固定 JSON Schema）、吸收高深行业黑话
  • 知识更新频率决定方案：RAG 支持秒级知识更新（增删向量即可），微调则需要重新训练，更新周期以天或周计

▎深入解释

想象你在培养一个新人客服：RAG 相当于给他一本随时可以翻的《产品手册》——手册内容更新了，他马上就能查到最新信息。但如果你需要他像老员工一样说话——用特定的语气、遵循特定的响应模板、能理解"这个客户说'再看看吧'其实是嫌贵"这类行业黑话——光给手册是不够的，你需要对他进行"上岗培训"（微调）。这就是 RAG 和微调的本质区别：RAG 改变的是模型的"知识输入"，微调改变的是模型的"行为模式"。在实际工程中，一个成熟的 Agent 系统往往是两者结合：用 RAG 提供实时知识，用 LoRA 微调确保模型输出符合企业的特定格式和语气要求。

▎面试加分点

  • 能提出"先 RAG 后微调"的渐进式策略：先用 RAG 快速验证业务价值，积累足够的高质量标注数据后再考虑微调
  • 能说明 LoRA 微调的资源需求：8x H200 级别的硬件，并非所有企业都需要
  • 能点出微调的数据质量要求远高于 RAG——微调需要高质量、格式统一的标注数据，而 RAG 只需要原始文档

▎常见误区

  • 误以为微调可以替代 RAG 来解决知识更新问题——微调后的模型知识是"冻结"的，无法实时更新
  • 误以为 RAG 和微调是互斥的——实际上最优方案往往是"微调模型 + RAG 知识库"的组合
  • 误以为所有行业黑话都需要微调——很多时候在 Prompt 中提供术语表就能解决，不需要动模型权重

📌 概念题 · Q6

考点标签

LLMOps · 难度：⭐⭐⭐

📌 题目

知识库中强调，企业级 LLM 部署必须监控 TTFT（首字延迟时间） 和 TPOT（每个 Token 生成时间），而不仅仅是 GPU 温度和利用率。请问：TTFT 和 TPOT 分别衡量的是什么？为什么在 AI Agent 的多轮交互场景中，TTFT 的优化优先级往往高于 TPOT？这两个指标对硬件选型和架构设计有什么指导意义？

💡 参考答案

▎一句话结论

TTFT 衡量的是"用户发出请求到看到第一个字的时间"，TPOT 衡量的是"第一个字之后每个 Token 的生成速度"——在交互式 Agent 场景中，TTFT 直接决定用户的"等待焦虑感"，因此优化优先级更高。

▎核心原理

  • TTFT 的构成：包括请求排队、Prompt 处理（Prefill 阶段）、KV Cache 初始化等，是用户感知延迟的核心指标
  • TPOT 的构成：主要取决于模型推理速度（Decode 阶段），表现为"打字机效果"的流畅度
  • 交互体验的心理学：用户对"第一个字的等待"比"后续文字的速度"更敏感——3 秒的首字延迟比 10 秒的总生成时间更让人焦虑

▎深入解释

可以类比为餐厅点餐：TTFT 相当于"你坐下后多久服务员给你倒第一杯水"，TPOT 相当于"上菜后你吃每一道菜的速度"。如果你等了 10 分钟才有人来倒水，即使后面上菜很快，你的整体体验已经很差了。在 AI Agent 的多轮对话中，TTFT 高的原因往往是：模型需要先处理完整的 Prompt（包括系统提示、历史对话、检索到的知识），这个 Prefill 阶段的计算量远大于单 Token 生成。优化 TTFT 的手段包括：语义缓存（相似问题直接命中缓存，跳过 GPU 计算）、Prompt 压缩（减少无关上下文）、流式输出（边计算边返回）。硬件选型上，高带宽显存（如 HBM3e）对降低 TTFT 至关重要，因为 Prefill 阶段是带宽密集型计算。

▎面试加分点

  • 能区分 Prefill 和 Decode 两个阶段对硬件的不同需求：Prefill 是计算密集型，Decode 是带宽密集型
  • 能提出"TTFT 的 P50/P95/P99 分位数监控"比平均值更有意义的观点
  • 能结合 LLM Gateway 的语义缓存（如 GPTCache）说明如何在不升级硬件的情况下大幅降低 TTFT

▎常见误区

  • 误以为 TTFT 和 TPOT 是同一个指标——实际上它们衡量的是生成过程的不同阶段
  • 误以为 GPU 利用率高就代表用户体验好——GPU 利用率高可能意味着请求在排队，TTFT 反而更差
  • 误以为 TTFT 优化只需要升级硬件——实际上语义缓存、Prompt 优化等软件手段往往能带来更大的改善

考点标签

基础设施 · 难度：⭐⭐⭐⭐

📌 题目

知识库中反复强调一个"避坑指南"：购买最新硬件（如 B200 SXM、H200）时，必须确认企业机房的单机柜供电能力和散热系统是否匹配。请问：为什么 8 卡 B200 服务器的功耗会"直逼 15kW"，这个功耗水平对传统企业机房意味着什么？在规划本地部署方案时，基础设施评估应该先于硬件选型还是后于硬件选型？为什么？

💡 参考答案

▎一句话结论

8 卡 B200 服务器的 15kW 功耗相当于 10 台家用空调同时运行，远超传统企业机柜 3~5kW 的供电设计上限——基础设施评估必须先行，否则会出现"买得起服务器，带不动电网"的尴尬局面。

▎核心原理

  • 功耗来源：B200 单卡功耗约 1000~1200W，8 卡加上 CPU、内存、NVLink 交换芯片等，整机功耗轻松突破 14kW
  • 传统机房的局限：大多数企业机房的单机柜供电设计在 3~5kW，只有新建或改造的数据中心才能支撑 15kW 的 AI 服务器
  • 散热挑战：15kW 的功耗需要液冷散热，传统的风冷方案无法有效带走如此高的热密度

▎深入解释

这是一个典型的"木桶效应"问题：你花几百万买了最先进的 B200 服务器，结果发现机房的电路只能支撑 5kW 的负载，插上去就跳闸。更糟糕的是，即使解决了供电，传统的空调系统也无法应对 15kW 的热密度——服务器会因过热降频，性能大打折扣。这就是为什么知识库强调"基础设施配套"是本地部署的核心维度之一。正确的规划顺序应该是：先评估机房的供电能力、散热能力、空间尺寸，再根据这些约束选择合适的硬件方案。如果机房无法支撑 B200，可以选择 H200（功耗更低）或者考虑托管到专业的数据中心。很多企业犯的错误是"先买硬件，再改机房"，结果发现改造成本比硬件本身还高。

▎面试加分点

  • 能提出"功耗/性能比"的评估视角：不是买最贵的硬件，而是买"在现有基础设施约束下性能最优"的硬件
  • 能说明液冷散热的两种方案：直接芯片液冷（Direct-to-Chip）和浸没式液冷（Immersion Cooling），以及各自的成本差异
  • 能结合"ROI 验证"思路：先用低功耗的方案 A 跑通业务，再根据实际需求决定是否升级基础设施

▎常见误区

  • 误以为功耗只影响电费——实际上功耗决定了供电、散热、空间等一系列基础设施需求
  • 误以为所有数据中心都能承载 AI 服务器——传统数据中心的设计标准远低于 AI 服务器的需求
  • 误以为液冷是可选方案——在 15kW 功耗水平下，液冷是必需品而非奢侈品

考点标签

数据清洗 · 难度：⭐⭐⭐

📌 题目

知识库中提出了一个极具冲击力的观点："将 80% 的精力花在清洗企业内部 PDF、Excel、企业 Wiki 等垃圾数据上，其效果提升远比你把模型从 32B 升级到 70B 要显著得多。"请问：为什么在 RAG 系统中，数据清洗的质量对最终效果的影响远大于模型规模的选择？"垃圾数据"具体指的是哪些类型的质量问题？请从 Chunking（文本切片）的角度解释数据清洗与检索质量的关系。

💡 参考答案

▎一句话结论

RAG 系统的效果上限由"检索到的知识质量"决定，而不是由"模型的理解能力"决定——如果检索到的文档片段本身是乱码、碎片或不完整的，再强大的模型也无法给出正确答案，这就是"垃圾进，垃圾出"的铁律。

▎核心原理

  • RAG 的检索瓶颈：模型只能基于检索到的上下文生成答案，如果检索结果质量差，模型的"聪明"无处施展
  • 垃圾数据的典型问题：PDF 中的乱码和格式错乱、Excel 中的合并单元格和公式残留、Wiki 中的过期信息和重复内容
  • Chunking 的敏感性：文本切片的质量直接影响向量化的语义完整性和检索的准确率

▎深入解释

可以类比为图书馆：如果图书馆的书架上的书都是缺页、乱序、重复的，即使你请了全世界最聪明的学者来做研究，他也无法从这些垃圾书中提取有价值的信息。RAG 系统也是如此——Embedding 模型把文档片段变成向量，然后通过相似度检索找到"最相关"的片段。如果文档片段本身就是不完整的（比如一个段落在中间被硬生生切断），或者包含大量格式噪声（如 PDF 转换产生的乱码），那么向量化的结果就会失真，检索到的"最相关"片段实际上并不相关。这就解释了为什么数据清洗比模型升级更重要：模型升级只能提升"理解能力"，但无法弥补"知识输入"的质量缺陷。一个好的 Chunking 策略（如按语义边界切分、保留标题层级、设置合理的重叠窗口）可以让检索质量提升数倍，而模型从 32B 升级到 70B 可能只带来几个百分点的提升。

▎面试加分点

  • 能提出"数据清洗的 ROI 远高于模型升级"的量化观点：清洗数据的成本是人力时间，升级模型的成本是硬件采购 + 推理成本增加
  • 能说明 Chunking 的常见策略：固定长度切分、语义切分、递归切分、基于文档结构的切分
  • 能结合"重排模型"（Reranker）说明数据清洗与检索精度的联动优化

▎常见误区

  • 误以为只要模型够强就能克服数据质量问题——实际上模型无法"无中生有"，检索不到的信息模型无法回答
  • 误以为数据清洗是一次性工作——实际上数据是持续更新的，清洗需要建立长效机制
  • 误以为 Chunking 只是简单的文本切割——实际上 Chunking 策略直接影响语义完整性和检索准确率

📌 概念题 · Q9

考点标签

向量检索 · 难度：⭐⭐⭐⭐

📌 题目

知识库中提到了在 PostgreSQL 中使用 pgvector 插件实现向量检索，并配合 HNSW 索引和余弦相似度操作符（<=>） 进行语义搜索。同时，知识库还强调了"混合检索（Hybrid Search）"的优势——在向量检索的基础上，通过 WHERE 语句叠加硬性业务条件过滤。请问：为什么在真实业务场景中，纯向量检索往往不够用？混合检索是如何解决"语义相似"与"业务约束"之间的矛盾？

💡 参考答案

▎一句话结论

纯向量检索只能回答"哪些内容在语义上最相似"，但无法回答"哪些内容既语义相似又满足业务条件"——混合检索通过"向量相似度 + SQL 条件过滤"的组合，同时满足语义相关性和业务约束性两个维度的需求。

▎核心原理

  • 向量检索的局限：向量相似度衡量的是"语义距离"，但它不关心业务属性（如时间、地域、状态、权限）
  • 混合检索的实现：先用向量检索找到语义最相似的 Top-K 结果，再用 SQL 的 WHERE 条件过滤掉不满足业务约束的结果
  • 过滤顺序的考量：是先过滤再检索，还是先检索再过滤？这取决于数据规模和过滤条件的选择性

▎深入解释

想象一个招聘场景：HR 想找"有 3 年以上 Java 经验的成都本地候选人"。纯向量检索会找到所有"Java 经验丰富"的候选人，但可能包含北京、上海、深圳的候选人。如果 HR 的查询条件是"必须是成都本地"，那么向量检索的结果中有一大半是不符合要求的。混合检索的做法是：在向量检索的同时，用 SQL 的 WHERE city = '成都' AND experience >= 3 来过滤。这样，最终的结果既满足"语义相似"（Java 经验丰富），又满足"业务约束"（成都本地、3 年以上）。在 PostgreSQL 中实现混合检索非常优雅：因为 pgvector 和传统的 SQL 查询在同一个数据库中，你可以用一条 SQL 语句同时完成向量相似度计算和业务条件过滤。

▎面试加分点

  • 能提出"过滤策略"的工程细节：当过滤条件的选择性很高时（如过滤掉 90% 的数据），应该先过滤再检索；当过滤条件选择性低时，应该先检索再过滤
  • 能说明"单数据库方案"的优势：PostgreSQL + pgvector 避免了在多个数据库之间同步数据的延迟和运维成本
  • 能结合"多租户权限隔离"说明混合检索在安全合规中的重要性

▎常见误区

  • 误以为向量检索可以替代所有查询方式——实际上结构化查询（如精确匹配、范围查询）用 SQL 更高效
  • 误以为混合检索就是简单的"先向量后过滤"——实际上过滤顺序对性能和结果质量有显著影响
  • 误以为必须使用专用的向量数据库——实际上 PostgreSQL + pgvector 在中小规模场景下完全可以胜任

📌 概念题 · Q10

考点标签

降级方案 · 难度：⭐⭐⭐⭐

📌 题目

知识库中在讨论 Milvus 单机部署时，提出了一个关键的"逃生通道"设计："在业务代码中留一个开关，万一 Milvus 挂了，系统自动降级切换到 PostgreSQL / MySQL 的传统全文检索，确保员工基本搜索业务不断线。"请问：为什么在看似稳定的内网环境中，仍然需要设计降级方案？这种"降级思维"在 AI Agent 架构设计中的普适价值是什么？请从可用性、用户体验、运维成本三个角度分析。

💡 参考答案

▎一句话结论

降级方案的本质是"承认任何系统都可能失败，但失败不能等于业务中断"——即使在内网环境中，Milvus 也可能因 OOM、磁盘故障或版本升级失败而宕机，此时自动切换到传统全文检索，虽然语义搜索效果可能下降，但基本业务可以继续运转。

▎核心原理

  • 可用性优先于完美性：一个"效果略差但可用"的系统远好于一个"效果完美但不可用"的系统
  • 降级的触发条件：通过健康检查（Health Check）检测 Milvus 的状态，超时或错误率超过阈值时自动切换
  • 降级的目标：保证核心业务（如员工搜索、基础问答）不断线，而非追求降级后的体验与正常状态完全一致

▎深入解释

这个设计可以类比为汽车的"备胎"：你希望永远用不上它，但如果轮胎爆了，有备胎你还能慢慢开到修理厂，没有备胎你就只能被困在路上。在 AI Agent 系统中，降级思维的价值更加重要，因为 Agent 系统往往依赖多个外部组件（向量数据库、LLM API、工具服务等），任何一个组件故障都可能导致整个 Agent 不可用。一个成熟的架构师会在设计阶段就考虑"每个组件的失败模式"以及对应的降级策略。例如：LLM API 超时怎么办？可以降级到本地小模型。向量数据库宕机怎么办？可以降级到全文检索。工具服务不可用怎么办？可以降级为"告知用户当前功能不可用，建议稍后重试"。这种"优雅降级"的能力，是区分"Demo 系统"和"生产系统"的关键标志。

▎面试加分点

  • 能提出"降级不是非黑即白"的观点：可以设计多级降级（如向量检索 → 全文检索 → 静态 FAQ）
  • 能说明"降级开关"的工程实现：通过配置中心动态切换，无需重启服务
  • 能结合"监控告警"说明降级的完整闭环：降级触发后必须通知运维人员，并在 Milvus 恢复后自动切回

▎常见误区

  • 误以为内网环境不会出问题——实际上内网环境的硬件故障、软件 Bug、人为误操作同样会导致服务不可用
  • 误以为降级方案只是"备胎"，优先级不高——实际上降级方案是生产系统的必备设计，而非可选优化
  • 误以为降级后的用户体验必须与正常状态一致——实际上降级的目标是"保底可用"，而不是"完美体验"

架构设计

场景标签

Skill 文件 多智能体 动态路由 Prompt 拼接

📝 题目

你在负责一个「自媒体内容运营 Agent」系统，主 Agent 需要同时具备热点分析、脚本撰写、违禁词校对三大能力。团队中一位初级工程师提议：直接把这三种能力的 Prompt 全部写进主 System Prompt，用 if...else 判断用户意图来切换行为。但你在知识库中看到了「Skill 文件矩阵」的架构方案。

请从主 Agent 上下文污染、模块可维护性、工具绑定隔离三个维度，系统阐述为什么必须将每个能力拆分为独立的 .skill 文件（如 trend_analyzer.skill、media_planner.skill、platform_pusher.skill），并给出你在代码层面实现「动态加载 + Prompt 拼接」的核心架构设计。同时，请说明当某个 Skill 的效果不佳需要迭代时，这种架构相比「大而全 Prompt」的工程优势在哪里。

💡 参考答案

▎解题思路

  1. 先分析「大而全 Prompt」方案的三个致命缺陷：上下文干扰、工具权限混乱、迭代成本高。
  2. 基于知识库中的 Skill 文件架构，设计一个 AgentEngine 核心类，实现 Skill 的 YAML 配置加载、运行时 Prompt 融合、工具动态绑定。
  3. 对比两种方案在迭代效率上的差异，强调「局部修改不牵动全局」的工程价值。

▎详细方案

第一步：定义 Skill 文件的标准结构。 每个 .skill 文件是一个 YAML 配置，包含四个核心字段：skill_id（唯一标识）、name（技能名）、system_prompt（该技能的局部 Prompt，只描述当前任务的规则）、bound_tools（该技能可以调用的工具列表）。以 trend_analyzer.skill 为例，它的 Prompt 只写「你是热点捕手，分析爬虫数据，提炼前 3 个最具传播价值的话题」，绝不掺入「写脚本」或「查违禁词」的内容。

第二步：设计 AgentEngine 的运行时融合逻辑。 核心代码逻辑（伪代码）如下：

class AgentEngine:
    def __init__(self, main_prompt):
        self.main_prompt = main_prompt   # 主 Agent 的通用设定，极简
        self.skills = {}                  # skill_id -> skill_config

    def load_skill(self, yaml_path):
        skill = yaml.safe_load(open(yaml_path))
        self.skills[skill['skill_id']] = skill

    def run_with_skill(self, skill_id, user_input):
        skill = self.skills[skill_id]
        # 核心：主 Prompt 只做「身份声明」，具体行为规范完全由 Skill 局部 Prompt 接管
        final_prompt = f"{self.main_prompt}\n\n【当前技能模式：{skill['name']}】\n{skill['system_prompt']}"
        # 关键：只把该 Skill 绑定的工具传给 LLM，而不是全部工具
        return call_llm(system=final_prompt, prompt=user_input, tools=skill['bound_tools'])

第三步：主 Prompt 保持极简。 主 System Prompt 只写一句「你是一个自媒体运营助手，根据用户需求自动切换技能模式」。所有具体的「怎么做」全部下沉到各个 Skill 文件中。这样主 Agent 的上下文窗口永远不会被无关规则撑爆。

▎关键细节 & 踩坑点

  • 工具隔离是硬性要求：platform_pusher.skill 绑定了 douyin_upload_api（发布工具），但 trend_analyzer.skill 绝不能看到这个工具。如果所有工具都暴露给 LLM，模型可能在分析热点时误触发发布动作，造成生产事故。Skill 架构天然实现了「工具权限最小化」。
  • YAML 中 Prompt 的转义问题：Skill 的 Prompt 中如果包含特殊字符（如 {}、#），在 YAML 里必须正确转义或使用 | 块标量语法，否则加载时会解析失败。
  • Skill 热更新：将 .skill 文件放在外部存储（如 NAS 或配置中心），load_skill 支持运行时重新加载，这样修改 Prompt 后无需重启服务即可生效，大幅提升迭代速度。

▎可扩展优化

  • Skill 版本管理：每个 Skill 文件增加 version 字段，支持 A/B 测试——同一个 skill_id 可以有多个版本，主引擎根据流量比例路由到不同版本，用真实数据验证 Prompt 修改的效果。
  • Skill 依赖链：引入 input_from 字段，声明该 Skill 的输入来源（如 media_planner 依赖 trend_analyzer 的输出），让主引擎自动编排多 Skill 的流水线执行顺序。
  • Skill 执行监控：在 run_with_skill 中埋入 Token 消耗、耗时、工具调用次数的监控打点，为后续优化提供数据依据。

「老子昨天就申请退款了，到现在还没动静，你们是不是骗子系统？！」

如果直接把这句消息交给 order_handler.skill 处理，它只会冷冰冰地引导用户提供身份信息，大概率会进一步激怒用户。知识库中提到了一个关键的 empathy_complaint.skill（客诉安抚与危机处理技能）。

请分析：这个场景中「先安抚、后办事」的路由策略是如何通过 Skill 动态挂载实现的？主分类器在检测到负面情绪后，系统内部经历了怎样的状态流转？并解释为什么不能让 order_handler.skill 直接在 Prompt 里加一句「如果用户情绪激动，先安抚」来解决这个问题。

💡 参考答案

▎解题思路

  1. 识别核心矛盾：情绪安抚和业务操作是两种完全不同的行为模式，混在一个 Prompt 中会导致指令冲突。
  2. 基于知识库中的「动态路由挂载」逻辑，描述从情绪识别 → 激活 empathy_complaint.skill → 安抚完成 → 转回 order_handler.skill 的完整状态流转。
  3. 解释为什么「在 order_handler 里加一句安抚」不可行——这是 Prompt 工程中典型的「职责混淆」错误。

▎详细方案

第一步：主分类器识别情绪信号。 主 Agent 的入口处有一个轻量级的情绪分类器（可以是关键词匹配 + 小模型判断，也可以直接让 LLM 做一次快速分类）。输入「老子…骗子系统」后，分类器输出 {intent: "complaint", emotion: "anger", confidence: 0.97}。关键点：这一步只做「判断」，不做「回复」。

第二步：动态加载并激活 empathy_complaint.skill。 主引擎收到 emotion: "anger" 信号后，从 Skill 池中加载 empathy_complaint.skill，将其 System Prompt 与主 Prompt 融合。此时 Agent 的行为完全被该 Skill 统治——它的 Prompt 明确要求：「无论用户说什么，第一步必须先情绪认同（如：非常理解您的心情...），然后给出具体的补偿安抚方案（如赠送积分），禁止用生硬的机器话术」。同时，该 Skill 绑定了 crm_vip_gift_api（赠送积分工具），Agent 可以在安抚过程中直接调用工具给用户发积分补偿。

第三步：安抚完成后平滑切换到 order_handler.skill。 当 empathy_complaint.skill 判断用户情绪已经平复（例如用户回复「好吧，那你们快点帮我查」），主引擎根据新的意图信号，将当前 Skill 从 empathy_complaint 切换为 order_handler。此时 Agent 的行为模式切换为「引导用户提供身份信息 → 校验 → 调用 update_order_api 查询退款状态」。两个 Skill 之间的上下文（用户原始诉求、已安抚的话术）通过主引擎的共享 State 传递，确保切换后不需要用户重复描述问题。

▎关键细节 & 踩坑点

  • 为什么不能把安抚逻辑塞进 order_handler.skill？ 因为 order_handler 的核心任务是「准确调用工具完成订单操作」，它的 Prompt 中如果加入「先安抚情绪」的指令，会和「严格校验身份信息」的规则产生冲突。大模型在处理时容易出现两种错误：要么在用户还没提供身份信息时就乱送积分，要么在安抚时忘了还要查订单。职责单一原则在这里是刚需，不是洁癖。
  • 情绪识别不能只靠关键词：用户说「你们是不是骗子」是明显的负面信号，但有用户说「你们这个功能有点意思，就是退款太慢了」也带有不满情绪。建议用 LLM 做一次轻量级的情绪打分（0-10 分），超过阈值才触发安抚 Skill，避免过度反应。
  • 安抚 Skill 中的工具权限要克制：crm_vip_gift_api 只能赠送积分或小礼品，绝不能绑定「退款审批」工具。否则一个情绪激动的用户可能诱导 Agent 在安抚过程中越权操作。

▎可扩展优化

  • 情绪分级路由：将情绪细分为 irritated（轻度不满）、angry（愤怒）、furious（极度愤怒）三个级别，不同级别对应不同的安抚策略和补偿力度（如积分数量不同）。
  • 安抚效果评估：在 empathy_complaint.skill 执行后，增加一个「用户情绪回落检测」节点，如果检测到用户仍然愤怒，自动升级为「转接人工」或「升级补偿方案」。
  • Skill 切换的平滑度优化：在 State 中保存「安抚阶段已使用的措辞」，避免切换到 order_handler 后用户产生「变脸」的感觉。

场景标签

LangGraph Dockerfile K8s 镜像构建

📝 题目

你的团队正在将一套 LangGraph 自研多智能体系统部署到阿里云 ACK Serverless。该系统包含两个节点：router_agent（纯 CPU 轻量级，负责意图路由）和 data_agent（需要 PyTorch、pandas、NumPy、CUDA 驱动进行本地模型推理）。团队中有人提议：为了省事，只写一个 Dockerfile，把所有依赖打包成一个镜像，然后在 K8s 部署时通过 args 参数区分启动入口。

但你在知识库中看到了明确的建议：推荐使用多 Dockerfile 方案。请详细阐述多 Dockerfile 方案的具体工程实现步骤（包括目录结构、两个 Dockerfile 的关键差异、CI/CD 构建流程），并从 K8s 弹性伸缩时的容器拉取速度 和 镜像体积对 GPU 节点调度的影响 两个角度，解释为什么单一镜像方案在生产环境中会带来严重的性能问题。

💡 参考答案

▎解题思路

  1. 先明确问题本质：router_agent 和 data_agent 的依赖差异巨大，前者只需要几十 MB 的基础 Python 环境，后者需要数 GB 的 CUDA + PyTorch 依赖。
  2. 给出多 Dockerfile 方案的完整目录结构和构建流程。
  3. 从「镜像拉取时间」和「GPU 节点亲和性」两个维度分析单一镜像方案的工程代价。

▎详细方案

第一步：规划代码仓库目录结构。 在同一个 Monorepo 中，为不同 Agent 角色创建独立的启动入口和依赖文件：

my-langgraph-app/
├── agents/
│   ├── __init__.py
│   ├── router_agent.py          # 路由智能体逻辑（纯 Python）
│   └── data_agent.py            # 数据分析智能体逻辑（依赖 torch/pandas）
├── server/
│   ├── run_router.py            # 路由服务入口（FastAPI）
│   └── run_data_agent.py        # 数据服务入口
├── requirements.txt             # 基础依赖（fastapi、langgraph 等）
├── requirements-gpu.txt         # GPU 专属依赖（torch、pandas、numpy）
├── Dockerfile.router            # 针对路由 Agent 的轻量 Dockerfile
└── Dockerfile.data_agent        # 针对数据 Agent 的重量级 Dockerfile

第二步：编写两个差异化 Dockerfile。 Dockerfile.router 使用极简的 python:3.10-slim 基础镜像（约 50MB），只安装 requirements.txt 中的基础依赖，启动命令指向 server/run_router.py。最终镜像体积控制在 200-300MB 以内。

Dockerfile.data_agent 则使用 nvidia/cuda:11.8.0-runtime-ubuntu22.04 作为基础镜像（约 2-3GB），额外安装 requirements-gpu.txt 中的 torch、pandas、numpy 等依赖，启动命令指向 server/run_data_agent.py。最终镜像体积可能在 5-8GB。

第三步：在 CI/CD 流程中分别构建和推送。 在 GitHub Actions 或阿里云效中，配置两条独立的构建流水线：

# 构建路由 Agent 镜像
docker build -f Dockerfile.router -t registry.cn-chengdu.aliyuncs.com/ns/router-agent:v1 .
docker push registry.cn-chengdu.aliyuncs.com/ns/router-agent:v1

# 构建数据 Agent 镜像
docker build -f Dockerfile.data_agent -t registry.cn-chengdu.aliyuncs.com/ns/data-agent:v1 .
docker push registry.cn-chengdu.aliyuncs.com/ns/data-agent:v1

第四步：在 K8s 中分别部署。 router-agent 的 Deployment 只请求 CPU 资源（如 requests: cpu: 250m, memory: 512Mi），且不声明 GPU 资源。data-agent 的 Deployment 则声明 limits: nvidia.com/gpu: 1，确保它只被调度到有 GPU 的节点上。

▎关键细节 & 踩坑点

  • 容器拉取速度的量化差异：假设 router_agent 镜像 250MB，data_agent 镜像 6GB。在 K8s 弹性伸缩场景中，当流量突增需要快速扩容 router_agent 的副本数时，如果使用单一 6GB 镜像，每个新 Pod 都需要从镜像仓库拉取 6GB 数据，在 100Mbps 带宽下需要约 8 分钟。而多 Dockerfile 方案下，router_agent 的 250MB 镜像只需约 20 秒即可拉取完成，扩容响应速度提升 20 倍以上。
  • GPU 节点调度的隐性成本：如果 router_agent 和 data_agent 使用同一个 6GB 镜像，但 router_agent 的 Pod 被调度到了 GPU 节点上（因为镜像里带了 CUDA 驱动，K8s 调度器可能误判），它虽然不申请 GPU 资源，但白白占用了 GPU 节点的 CPU 和内存，导致真正需要 GPU 的 data_agent 无法调度。多 Dockerfile 方案天然规避了这个问题。
  • 基础镜像的选择要谨慎：nvidia/cuda 镜像的 Tag 必须和 GPU 节点的驱动版本匹配，否则容器启动时会报 CUDA driver version is insufficient 的错误。

▎可扩展优化

  • 镜像分层缓存优化：在 Dockerfile 中先 COPY requirements.txt 再 RUN pip install，最后才 COPY . .，这样代码变更时不会触发依赖层的重新构建，大幅加速 CI/CD。
  • 使用 BuildKit 的多阶段构建：在 data_agent 的 Dockerfile 中使用多阶段构建，在构建阶段安装完整依赖，在运行阶段只复制必要的产物，进一步减小最终镜像体积。
  • 引入镜像预热机制：在 K8s 中使用 DaemonSet 或 ACK 的镜像缓存功能，在 GPU 节点上预先拉取 data_agent 镜像，避免首次调度时的冷启动延迟。

场景标签

本地部署 GPU 算力 量化 ROI

📝 题目

你所在的中型律师事务所（约 50 名律师）需要部署一个本地 RAG 系统，用于检索和摘要内部几万份历史诉讼文书。公司 IT 负责人看到某技术博客上说「DeepSeek-R1 671B 是 2026 年最强大的开源模型」，坚持要求采购 8 卡 B200 服务器来跑满血版模型。但你在知识库中看到了明确的「避坑指南」：切忌算力焦虑，建议先用轻量方案验证 ROI。

请从显存需求与硬件成本的匹配关系、实际并发需求与算力供给的差距、数据质量对效果的影响权重三个维度，有理有据地说服 IT 负责人放弃 B200 方案，改用双卡 RTX 4090 D（48GB）+ Qwen 3.5-32B INT4 量化版 + vLLM 的轻量方案。同时，请说明这个轻量方案在该业务场景下的具体性能表现预期。

💡 参考答案

▎解题思路

  1. 先算一笔「显存账」：671B 模型需要多少显存 vs. 32B INT4 模型需要多少显存，让 IT 负责人直观感受到资源浪费的量级。
  2. 再算一笔「并发账」：50 人律所的真实并发需求 vs. B200 集群的算力供给，暴露「用大炮打蚊子」的荒谬。
  3. 最后强调「数据质量 > 模型规模」的实践规律，将 IT 负责人的注意力从「模型大小」转移到「数据清洗」上。

▎详细方案

第一步：显存与成本的对比分析。 DeepSeek-R1 671B 模型即使采用 FP4 量化，仅模型权重就需要约 340GB 显存，加上推理时的 KV Cache 和中间激活值，8 卡 B200（总 1440GB）确实是合理配置。但 8 卡 B200 服务器的硬件成本在 200-300 万元人民币，加上机房液冷改造（B200 8 卡单机功耗约 15kW，普通机房的电网和空调根本带不动），总投入可能超过 400 万元。相比之下，Qwen 3.5-32B INT4 量化后模型权重仅约 20GB，双卡 RTX 4090 D（48GB 总显存）绰绰有余，硬件成本仅 4-8 万元，差距是 50 倍。

第二步：实际并发需求的评估。 50 名律师的律所，日常同时在线的检索人数通常不超过 10 人，峰值 QPS 可能不到 5。双卡 4090 D + vLLM 框架可以轻松支撑 5-10 人的并发访问，首字延迟在 1-2 秒以内。而 8 卡 B200 的算力可以支撑数千并发——这意味着 99% 的算力在 99% 的时间里处于闲置状态。这种「为了 1% 的峰值需求，承担 50 倍的成本」的决策，在 CFO 面前是站不住脚的。

第三步：数据质量才是真正的瓶颈。 知识库中明确强调：「将 80% 的精力花在清洗企业内部 PDF、Excel、企业 Wiki 等垃圾数据上，其效果提升远比你把模型从 32B 升级到 70B 要显著得多。」律所的历史诉讼文书如果存在扫描件乱码、段落切分不合理、元数据缺失等问题，即使换成 671B 的模型，检索效果也不会好。相反，如果花 2-3 个月时间做好文本清洗、Chunking 优化和向量索引调优，32B 模型的表现完全能满足业务需求。

▎关键细节 & 踩坑点

  • INT4 量化的精度损失可接受：AWQ 或 GPTQ 4-bit 量化的性能损失通常在 1%-2% 以内，对于法律文书的检索和摘要任务，这个损失用户几乎无感知。但显存占用直接砍掉了 50%-75%，这是性价比的核心来源。
  • vLLM 的 PagedAttention 是必选项：不要用 Ollama 的默认推理引擎跑生产环境，vLLM 的 PagedAttention 显存管理技术可以大幅提升并发能力，避免显存碎片导致的 OOM。
  • 机房供电检查：即使是双卡 4090 D，单机功耗也在 800-1000W 左右，需要确认办公室的电路能否承受。但相比 B200 的 15kW，这个门槛低得多。

▎可扩展优化

  • 分阶段升级路径：先用双卡 4090 D 跑通业务，验证 ROI 后，如果确实需要更大的模型（如 Qwen 3.5-72B），可以平滑升级到单台 4 卡 H200 服务器（约 40-60 万元），模型精度从 INT4 提升到 BF16，推理质量进一步提升。
  • 引入语义缓存：在 LLM 网关层部署 GPTCache，当多个律师查询相似的法律问题时，直接命中缓存，不经过 GPU 计算，进一步降低算力消耗。
  • 建立数据质量评估指标：定期评估向量检索的召回率和准确率，用数据驱动数据清洗工作的优先级排序。

从 0 到 1 HR 智能语音客服 PostgreSQL Skill 路由 本地部署

📝 题目

你作为项目负责人，需要从 0 到 1 交付一个「HR 智能语音客服」系统，服务对象是公司内部 2000 名员工。系统需要处理三类核心需求：① 请假/公积金/退换货等政策咨询（需要 RAG 知识库检索）；② 订单修改/退款申请等业务操作（需要调用内部 API）；③ 员工投诉和情绪安抚（需要识别负面情绪并给予补偿）。数据安全要求：所有员工对话数据和知识库内容必须完全私有化，不允许任何数据外流。

请设计一套完整的落地架构方案，包括：Skill 文件矩阵的设计、PostgreSQL 作为统一存储底座的使用策略、本地部署的硬件选型，以及从开发到上线的里程碑规划。重点说明你如何在「数据私有化」的硬约束下，平衡系统性能和开发效率。

💡 参考答案

▎解题思路

  1. 先确定核心架构原则：Skill 文件矩阵实现「专家坐席」路由，PostgreSQL 一套数据库搞定「记忆 + 知识 + 账本」，本地部署满足数据私有化要求。
  2. 分别设计三个 Skill 文件的内容和绑定工具，并说明它们之间的状态流转关系。
  3. 给出 PostgreSQL 的具体表结构设计（传统列 + JSONB + pgvector 的组合）。
  4. 选择轻量级本地部署方案（双卡 4090 D + Qwen 3.5-32B INT4），并规划分阶段上线里程碑。

▎详细方案

第一步：Skill 文件矩阵设计。 创建三个独立的 .skill 文件：

  • policy_expert.skill：System Prompt 设定为「严谨的客服专家，严格基于 RAG 知识库内容回答请假、公积金、退换货流程问题。如果知识库里没有，直接回答『抱歉，该问题超出了我的知识范围，正在为您转接人工』，严禁瞎编」。绑定工具：vector_knowledge_base_search。
  • order_handler.skill：System Prompt 设定为「拥有修改数据库订单和发起审批的权限。当用户要求修改地址或退款时，必须先引导用户提供必要的身份信息，校验通过后才能调用相关工具」。绑定工具：update_order_api、send_sms_verify_code。
  • empathy_complaint.skill：System Prompt 设定为「高级客诉专家，无论用户说什么，第一步必须先情绪认同，然后给出具体的补偿安抚方案，禁止用生硬的机器话术」。绑定工具：crm_vip_gift_api。

第二步：PostgreSQL 统一存储底座设计。 三张核心表：

  • chat_sessions 表：存储会话元数据（session_id、employee_id、start_time、end_time、channel），使用传统 SQL 列。
  • chat_messages 表：存储每轮对话。role、content、created_at 用传统列；dynamic_context 用 JSONB 类型，存储用户画像标签（如「意向：高」「渠道：抖音」）、临时变量、槽位填充状态等半结构化数据。在 JSONB 字段上建 GIN 索引，支持用 @> 操作符快速查询「这个员工之前是否通过抖音渠道投递过」。
  • knowledge_embeddings 表：存储 RAG 知识库的向量。使用 pgvector 插件的 vector(1024) 字段，建 HNSW 索引，用余弦相似度操作符 <=> 做语义检索。同时保留 metadata JSONB 列，存储「部门」「适用地区」「生效日期」等硬性过滤条件，实现混合检索。

第三步：本地部署硬件选型。 2000 名员工的 HR 客服，日常并发约 20-30 人，峰值可能到 50 人。选择 1 台双卡 RTX 4090 D（48GB 总显存）服务器，部署 Qwen 3.5-32B INT4 量化版（模型权重约 20GB），使用 vLLM 框架提供推理服务。PostgreSQL 部署在同一台服务器上（或独立的一台 8 核 32GB 虚拟机），通过内网通信。知识库向量规模预计在 50-100 万条，单机 PostgreSQL + pgvector 完全能够承载。硬件总投入约 6-10 万元，满足数据私有化要求。

第四步：里程碑规划。 分为三个阶段：

▎关键细节 & 踩坑点

  • 数据私有化的技术保障：本地部署的模型推理不经过任何外部 API，所有数据只在公司内网流转。但要注意：如果使用了 HuggingFace 下载模型权重，下载完成后必须断网运行，并清除模型文件中的远程凭证检查逻辑。
  • pgvector 的 HNSW 索引构建时间：100 万条向量的 HNSW 索引构建可能需要数小时，建议在业务低峰期（如周末）执行，或使用增量索引策略。
  • 语音客服的额外链路：如果系统需要支持语音输入（而非纯文本），需要在 LLM 之前增加 ASR（语音识别）模块，在 LLM 之后增加 TTS（语音合成）模块。这两个模块可以选用本地化的开源模型（如 Whisper、ChatTTS），避免数据外流。
  • 人工兜底机制：当 policy_expert.skill 判断知识库无答案或 empathy_complaint.skill 检测到用户情绪持续恶化时，必须能够无缝转接人工客服，并在转接时携带完整的对话上下文，避免用户重复描述问题。

▎可扩展优化
