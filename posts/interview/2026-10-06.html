📌 概念题 · Q1

考点标签

LangGraph 循环控制 · 难度：⭐⭐⭐

📝 题目

在 LangGraph 构建的反思型 Agent 中，经常会出现“复读机”死循环问题（反复调用同一工具、重复输出相同错误答案），请说明工业级 Agent 通常采用哪三层机制从根本上打破循环，而不是单纯靠 Prompt 约束？

💡 参考答案

▎一句话结论

打破 Agent 死循环不能仅靠语义提示，必须结合“硬计数器兜底+动态语义引导+节点级精准回滚”三层确定性工程机制，从代码层面强制约束循环边界。

▎核心原理

  • 第一层：显式计数器硬上限，在全局 State 中维护 loop_count 变量，每次进入重试/反思节点自动加1，达到阈值（通常3-5次）强制走降级路由
  • 第二层：动态 Prompt 语义注入，随重试次数递增，将前几次失败的具体原因、错误路径注入下一轮 Prompt，引导模型切换解题思路
  • 第三层：节点级时间旅行回滚，基于 Checkpointer 持久化的状态快照，定位到故障发生前的正确检查点，定向重定向执行路径做增量重试

▎深入解释

很多初级开发者做 Agent 时，只会在 System Prompt 里写一句“不要重复自己，如果失败请换思路”，这本质上是把控制权完全交给了非确定性的大模型，一旦模型陷入语义陷阱，就会无限刷 Token 直到把账户余额耗光。三层机制的设计逻辑是从“硬兜底到软引导”分层设防：最底层的计数器是不可逾越的代码红线，哪怕模型完全失控，也最多重试5次就会触发兜底回复（比如“当前问题暂时无法处理，已转人工”）；中间层的动态注入是从语义层面帮模型“跳出来”，相当于人做题卡住时旁人提醒“你前两次都在算错钢筋配比，换个定额标准试试”；最上层的回滚机制是精细化故障恢复，不需要把整个流程从头跑一遍，只需要回到出错的节点分叉重试，比如配图生成失败不需要重写整篇文章，只需要回到写作完成的 checkpoint 重新调配图接口即可，大幅降低重试成本。

▎面试加分点

  • 可以结合实际场景给出阈值经验：普通工具调用重试3次，复杂多步推理重试最多5次，阈值过高会导致Token浪费，过低会导致偶发网络错误被误拦截
  • 提到降级路由的设计：触发硬上限后不是直接报错，而是根据场景返回预设兜底话术、转人工队列、或者触发告警通知开发人员

▎常见误区

  • 误区：认为把 max_tokens 设小一点就能防止死循环——实际上死循环的核心是反复调用工具刷输入Token，输出Token限制根本拦不住
  • 误区：认为只要给模型加“你已经重试N次了”的提示就够了——没有代码层面的硬截断，模型完全可能无视提示继续循环

📌 概念题 · Q2

考点标签

长周期Agent设计 · 难度：⭐⭐⭐⭐

📝 题目

普通对话 Agent 都是一问一答常驻内存，但员工入职、跨部门审批等长周期业务往往需要跨越数天等待人工介入，无法让进程一直挂在内存里，请说明这类 Long-running Agent 的核心设计原则是什么，技术上如何实现休眠与唤醒？

💡 参考答案

▎一句话结论

长周期 Agent 的核心设计原则是“状态不驻留内存、执行可中断、唤醒可续跑”，基于“状态序列化持久化+中断信号挂起+Webhook异步唤醒”三段式机制实现跨天级流程执行。

▎核心原理

  • 状态序列化：每执行完一个节点，借助 PostgreSQL Checkpointer 将当前完整状态机、上下文、局部变量序列化为JSON存入数据库，随即释放计算资源
  • 两阶段中断：当执行到需要人工/外部系统介入的步骤时，调用外部工具生成唯一任务ID，同时向状态机抛出Interrupt信号强制挂起会话，进程退出不占资源
  • 异步唤醒：外部系统完成操作（如审批通过）后通过Webhook回调携带任务ID，服务端从数据库反序列化对应状态，将外部结果作为事件输入注入，唤醒Agent继续执行后续节点

▎深入解释

很多开发者做长流程业务时，会错误地采用“会话常驻内存+WebSocket长连接”的方案，这种方案在开发测试时没问题，但到生产环境会遇到致命问题：Pod重启、服务发布、网络波动都会导致内存里的状态全部丢失，用户填了一半的入职表单直接消失；而且如果一个流程要等3天总监审批，总不能让一个连接 hold 3天，资源成本根本扛不住。正确的设计本质上是把Agent当成“可暂停可恢复的分布式状态机”，而不是一个常驻的聊天进程：每走一步就把状态存到数据库，相当于游戏的“存档”功能，不管中间服务器怎么重启、过了多少天，只要拿到存档就能从上次暂停的地方继续玩。Interrupt信号相当于游戏里的“暂停键”，触发后进程直接退出，不需要占着CPU和内存；Webhook唤醒相当于用户点了“继续游戏”，系统读档接着跑。比如入职流程中，Agent验证完身份证就存档退出，等HR系统回调说总监审批通过了，再唤醒Agent生成劳动合同，整个过程不需要任何进程常驻。

▎面试加分点

  • 提到状态序列化的兼容性设计：状态结构变更时要做版本号管理，避免旧版本存档反序列化失败导致流程卡死
  • 提到唤醒时的幂等性设计：同一个Task_ID的重复Webhook回调要做去重，避免重复生成合同、重复发通知

▎常见误区

  • 误区：用Redis做长周期状态存储——Redis的内存成本高，而且如果配置了过期时间很容易丢状态，长周期状态必须存在持久化的关系型数据库里
  • 误区：让前端轮询接口来判断审批是否完成——轮询延迟高、浪费资源，Webhook才是工业级异步通知的标准方案

📌 概念题 · Q3

考点标签

大模型性能优化 · 难度：⭐⭐⭐

📝 题目

随着对话轮数增加，Agent 的上下文越来越长，会导致Token成本飙升、首字延迟（TTFT）越来越高，很多人采取的方案是“无脑截断历史对话”，但这会丢失关键用户信息，请说明工业级分层内存+前缀缓存的优化方案是如何兼顾效果、成本与速度的？

💡 参考答案

▎一句话结论

长上下文优化不能靠简单截断，必须通过“分层记忆管理压缩上下文长度+Prefix Cache 固定前缀命中KV缓存”双管齐下，在不丢失关键信息的前提下将TTFT和Token成本降低70%以上。

▎核心原理

  • 分层记忆管理：不把所有历史对话全量塞给模型，近期记忆（最近N轮）保留原始精确对话存在PostgreSQL，远期记忆通过后台异步摘要Agent压缩为结构化用户画像/事实标签（如偏好、预算、已确认信息）
  • Prefix Cache 深度触发：通过固定RAG片段排序、合并System Prompt、固定Few-Shot示例顺序等手段，保证所有请求的开头部分（System Prompt、固定Few-Shot、用户长期画像）在Token级别完全一致，命中推理框架的KV缓存和前缀缓存机制

▎深入解释

很多初级开发者做对话记忆时走两个极端：要么把所有历史记录全塞给模型，导致聊了20轮之后上下文到了32K，TTFT从1秒涨到15秒，Token成本翻好几倍；要么粗暴保留最近5轮，结果用户10轮前提到的“我对乳胶过敏”“预算2000以内”这些关键信息全丢了，Agent答非所问。分层记忆的逻辑和人类记忆机制完全一致：你不需要记住昨天和朋友聊天的每一句话，但你会记住朋友对芒果过敏、最近要搬家这些关键事实，这些事实被压缩成长期记忆，每次对话都带着；而最近几轮的对话精确保留，保证上下文连贯。前缀缓存的优化很多人忽略，其实大模型推理是自回归的，前面的Token计算完KV之后可以缓存复用，如果每个请求的前1000个Token都是固定的System Prompt和用户画像，那这1000个Token根本不需要重复计算，直接读缓存就行，TTFT会从十几秒直接降到2秒以内。比如FA-HR项目中，通过固定RAG检索结果的排序规则，避免了相同问题因为片段顺序不同导致前缀不命中缓存的问题，TTFT优化效果非常明显。

▎面试加分点

  • 提到摘要Agent的触发时机：不要同步做摘要阻塞主流程，要在对话空闲时异步后台执行，避免增加用户等待时间
  • 提到前缀缓存的注意事项：哪怕多一个空格、换个顺序，都会导致前缀不命中，所以必须严格控制Prompt模板的固定部分，动态参数全部放在请求末尾

▎常见误区

  • 误区：认为KV缓存是云厂商自动开的不需要管——实际上如果你的Prompt开头每次都不一样，哪怕开了缓存也完全命中不了，优化效果为0
  • 误区：认为长期记忆摘要越详细越好——摘要太长会挤占有效上下文空间，长期记忆应该是高度结构化的键值对事实，而不是大段文本

📌 概念题 · Q4

考点标签

流式输出全栈实现 · 难度：⭐⭐⭐⭐

📝 题目

高并发场景下的流式输出（Streaming）是提升用户感知体验的核心手段，很多人以为流式输出就是“后端开个SSE、前端接一下就行”，但实际落地会遇到数据不一致、Token统计不准、延迟高等问题，请从前后端全链路角度说明工业级流式输出的完整落地方案？

💡 参考答案

▎一句话结论

工业级流式输出必须实现“后端端到端Token流透传+前端异步流式解析+结构化输出与计费兼容”三层设计，才能在保证数据一致性的前提下将用户感知TTFT降低60%以上。

▎核心原理

  • 后端端到端流：基于FastAPI集成LangGraph的astream_events，监听on_chat_model_stream事件捕获Token级实时流，保证流式模式和非流式模式下Checkpointer存储的最终状态结构完全一致
  • 前端流式解析：前端通过fetch API获取response.body的ReadableStream reader，异步逐块解析增量Token直接渲染，不需要等整个响应返回再一次性渲染
  • 结构化与计费兼容：开启大模型原生JSON Mode，通过Pydantic Schema做强约束输出，同时手动解析/聚合流中的usage字段，解决云厂商流式返回不返回Token统计的问题

▎深入解释

很多团队做流式输出的常见坑是：后端自己攒一段内容再每隔几百毫秒发一块，这不是真流式，用户还是要等很久才看到第一个字；或者流式输出的时候只把内容发给前端，没把最终完整结果存到状态库，导致后续对话拿不到之前的回复上下文；还有就是开了结构化输出之后，云厂商的流式接口不返回usage字段，没法做Token计量和成本统计。正确的全链路设计应该是：从大模型吐出第一个Token开始，就通过事件流直接透传到前端，中间不做任何攒批等待，这样第一个Token到达用户的时间就是模型推理的首字时间，延迟最低。前端用浏览器原生的ReadableStream API逐块读取，收到一个字就渲染一个字，比传统的SSE库兼容性更好、延迟更低。针对结构化输出和计费的问题，不能因为要流式就放弃强约束和计量，而是要在流结束后，把所有Token拼接起来做Pydantic校验，同时在流的过程中累计prompt_tokens和completion_tokens，最终落库统计，这样既享受了流式的低延迟，又不丢结构化能力和成本数据。

▎面试加分点

  • 提到流式输出的错误处理：流传输过程中如果大模型报错、网络中断，要在前端正确展示错误提示，同时在后端补存中断的状态，避免状态不一致
  • 提到Markdown渲染优化：前端收到增量Token时要做增量Markdown解析，不要每次全量重新渲染，避免大段内容时的页面卡顿

▎常见误区

  • 误区：用WebSocket实现流式输出——SSE是单向下行传输，比WebSocket更轻量、更适合大模型流式响应场景，不需要双向通信时没必要用WebSocket
  • 误区：认为流式输出会降低大模型推理速度——实际上流式输出不会增加模型推理时间，只是把生成的内容逐块返回，用户感知更快而已

📌 概念题 · Q5

考点标签

多Agent架构设计 · 难度：⭐⭐⭐⭐

📝 题目

很多人做复杂业务时要么用一个全能Single Agent塞几十个工具，要么拆成一堆Agent互相调用导致链路混乱，请说明工业级Router-Worker多Agent架构的核心设计原则是什么，如何做路由分发才能兼顾准确率、成本和扩展性？

💡 参考答案

▎一句话结论

复杂业务场景下Single Agent必然出现注意力遗忘问题，工业级方案采用“路由中枢+专职Worker+子图拆分+多模型动态路由”的Router-Worker模式，每个Worker仅持有2-3个核心工具，在保证准确率的同时降低40%以上推理成本。

▎核心原理

  • 子图单元拆分：按业务领域拆分为独立SubGraph子图（如选题、写作、配图、客服），每个Worker Agent仅挂载自身领域的2-3个核心工具，避免工具过多导致模型注意力分散
  • 多模型动态调度：网关层做路由，简单任务（如分类、格式转换）分发给轻量高速Flash模型，复杂任务（如核心文案生成、逻辑纠错）路由到旗舰大模型，多模态任务单独调度视觉模型
  • 仓库与部署解耦：不同Worker Agent独立代码仓、独立部署、暴露HTTP接口，调度中心仅做路由转发，不侵入业务代码，新增功能只需加节点和路由规则

▎深入解释

Single Agent的核心问题是“注意力稀释”：大模型的上下文窗口是有限的，如果你给它挂20个工具，每次推理它都要从20个工具里选，很容易选错工具、漏参数，准确率会断崖式下跌，就像让一个人同时干客服、写文案、做设计、算数据，肯定每件事都干不好。Router-Worker模式本质上是公司的组织架构设计：路由Agent就是前台，只负责判断用户要办什么事，不干活；每个Worker就是专职部门，客服部只管接咨询，内容部只管写文案，每个部门只有自己干活需要的几个工具，准确率自然高。多模型动态路由是成本优化的核心：比如意图分类这种简单任务，用1.8B的Flash模型几毫秒就返回，成本是旗舰模型的几十分之一，没必要所有请求都打最贵的大模型。部署层面的解耦非常重要，不要把所有Agent代码都塞到一个仓库里，不然改一个客服Agent的逻辑要重新发布整个集群，出问题互相影响；每个Worker独立部署，调度中心通过HTTP调用，新增一个数据分析Agent只需要写个独立服务，在路由里加一条规则就行，扩展性极强。

▎面试加分点

  • 提到路由层的降级机制：如果轻量模型意图识别置信度低于阈值（如0.7），自动升级到旗舰大模型做二次判断，避免路由错误
  • 提到共享状态设计：所有Worker共用全局State对象，不需要在Agent之间反复传上下文，保证对话连贯性

▎常见误区

  • 误区：Agent拆得越细越好——过度拆分（比如把查天气、查温度、查湿度拆成三个Agent）会导致路由复杂度飙升，链路延迟增加，每个Worker应该是一个完整业务域的闭环
  • 误区：所有Agent都要用最好的大模型——80%的简单任务用小模型就能搞定，全用大模型成本会高到无法接受

📌 概念题 · Q6

考点标签

微调与RAG边界 · 难度：⭐⭐⭐⭐

📝 题目

工业界大模型落地经常提到“微调管风格、RAG管知识”的职责分离架构，请说明两者的核心边界是什么？为什么不能用微调注入动态知识，也不能用RAG让模型学习固定话术风格？Pipeline调优的关键手段是什么？

💡 参考答案

▎一句话结论

微调负责注入稳定的风格、格式、SOP遵循能力（改变模型行为模式），RAG负责注入动态、更新频繁的事实类知识（不改变模型权重），两者职责不可替代，配合“两阶段微调+三阶段RAG”Pipeline可以同时实现风格一致性和知识准确率。

▎核心原理

  • 两阶段微调管风格：SFT阶段让模型学会领域话术和流程（从“不会说”到“会说”），DPO阶段通过chosen/rejected偏好对做对齐，解决“说不好”的问题，让输出风格符合企业要求
  • 三阶段RAG管知识：构建Embedding向量粗召回（top20）+ Cross-Encoder重排序（top5）的Pipeline，解决双编码器向量检索区分度不足的问题，保证知识命中率
  • 边界划分原则：凡是半年内不会变、需要模型内化的行为模式（如客服语气、回复格式、SOP步骤）用微调；凡是经常更新、需要精确溯源的事实（如最新规章制度、产品价格、审批流程）用RAG

▎深入解释

很多团队落地时会走两个极端：要么什么都往微调里塞，把公司规章制度、产品价格全训到模型里，结果下个月产品调价，模型还在说旧价格，重新微调成本极高，而且微调无法解决知识溯源问题，模型会胡说八道编造不存在的条款；要么什么都靠RAG，把所有话术、格式要求全放到Prompt里，结果Prompt越来越长，模型经常不按要求的语气回复，格式错漏百出。两者的本质区别是：微调是改变模型的权重，相当于让一个人形成肌肉记忆，说话的语气、做事的流程不需要想就能做对，但你没法让他记住每周都变的值班表；RAG是给人一本随时更新的手册，他遇到问题就翻手册，能保证说的事实都是最新的，但你没法靠翻手册让一个人瞬间学会专业的客服语气。Pipeline调优的关键是RAG阶段必须加重排序：纯向量检索是双编码器，Query和Document单独编码，语义相近但重点不同的内容很难区分，比如“员工入职要带什么”和“员工离职要带什么”向量很像，但内容完全不同，加Cross-Encoder重排序之后，会把Query和Document拼起来一起做相关性打分，准确率能从70%提升到90%左右。

▎面试加分点

  • 提到微调数据的构造原则：SFT数据要覆盖各种边缘场景的对话，DPO的偏好对要明确区分“好回答”和“坏回答”的具体差异，不能随便凑数
  • 提到RAG的溯源能力：RAG返回结果时必须携带引用的文档片段和来源，方便用户核对，也方便排查知识错误

▎常见误区

  • 误区：微调之后模型就“懂”了企业知识——微调只是让模型学会说话风格，事实类知识如果不通过RAG注入，模型会产生幻觉编造内容
  • 误区：RAG召回的文档越多越好——召回太多无关文档会稀释模型注意力，top3-top5的精准召回远好于top20的粗召回，重排序是必选项不是可选项

📌 概念题 · Q7

考点标签

MCP中台架构 · 难度：⭐⭐⭐⭐

📝 题目

企业内部业务线众多，如果每个业务团队都自己做一套大模型调用、RAG、记忆管理，会造成大量重复建设，而且多租户场景下数据隔离困难，请说明基于MCP协议的共享Agent服务集群如何实现低耦合扩展和多租户安全隔离？

💡 参考答案

▎一句话结论

基于MCP的中台化架构通过“公共能力抽离为独立MCP Server+网关中间件链+知识库物理隔离”，实现提示词工程与业务逻辑解耦，新业务接入仅需编写无状态编排层，同时保证多租户数据互不干扰。

▎核心原理

  • 能力解耦中台化：将大模型调用、RAG检索、会话记忆、Prompt管理四类通用能力抽离为独立的MCP Server，上层业务通过HTTP网关统一接入，不需要重复造轮子
  • 多租户物理隔离：共享RAG服务底层基于向量数据库的project_id字段划分独立Collection，不同租户的知识库物理隔离，通过ingest_document Tool实现自助接入
  • 四层网关中间件链：在网关层统一实现身份认证、操作日志记录、Token配额控制、路由转发四个核心能力，统一管控API Key和调用额度，避免噪声邻居问题

▎深入解释

很多企业刚开始做大模型应用时，客服团队做一套RAG，HR团队做一套大模型封装，运营团队再做一套记忆模块，不仅重复开发浪费资源，而且每个团队的安全标准不一样，很容易出现数据泄露、Token超支没人管的问题。MCP（Model Context Protocol）的核心价值是定义了大模型能力调用的标准协议，就像微服务架构里的服务注册中心，把通用能力抽成标准服务，业务方不需要关心底层是用的OpenAI还是豆包、向量库是Milvus还是pgvector，只需要调用标准接口就行。多租户隔离的关键是不要共享同一个Collection，靠元数据字段过滤虽然逻辑上能隔离，但一旦代码出bug就可能串数据，物理Collection隔离才是生产级的安全方案。网关中间件是成本和安全的核心管控点：所有请求都过网关，谁在调用、调用了多少次、花了多少Token，全链路可追溯，某个租户调用量超了直接限流，不会把整个集群的资源拖垮，也不会出现一个业务线把大模型额度用完导致其他业务不可用的“噪声邻居”问题。

▎面试加分点

  • 提到MCP服务的无状态设计：所有MCP Server都做成无状态服务，可以水平扩展支撑高并发，状态统一存在Checkpointer和数据库里
  • 提到配额管控的精细化：可以按租户、按接口、按模型类型设置不同的配额阈值，比如测试环境租户每天限额100元，生产环境按需调整

▎常见误区

  • 误区：多租户隔离靠逻辑过滤就行——逻辑过滤依赖代码正确性，一旦出现SQL注入、过滤条件遗漏就会导致全量数据泄露，物理隔离是大厂合规的硬性要求
  • 误区：中台化会导致业务灵活性下降——中台只提供通用原子能力，业务编排逻辑完全由上层业务团队控制，反而因为不用写底层通用代码，业务迭代更快

📌 概念题 · Q8

考点标签

Agent安全风控 · 难度：⭐⭐⭐⭐⭐

📝 题目

Agent 系统经常需要对接内部数据库、外部平台API，具备写数据、发消息、调用支付等高危能力，很容易成为攻击目标，请从数据安全、下游保护、执行风控三个层面说明工业级Agent的安全防护体系如何设计？

💡 参考答案

▎一句话结论

Agent安全必须构建“两层数据脱敏合规+工程限流熔断+Human-in-the-Loop高危操作审批”的三层纵深防御体系，从输入、执行、输出全链路设防，避免数据泄露、Token刷爆、高危操作误执行等生产事故。

▎核心原理

  • 数据安全层：输入输出两端做敏感信息脱敏，结合正则表达式和NER命名实体识别识别手机号、身份证、薪酬等敏感字段，采用AES-256加密存储敏感数据，所有操作留痕审计
  • 服务保护层：基于SlowAPI做接口级强限流，引入熔断器模式保护下游大模型和内部API，连续失败、触发429报错超过阈值时自动切断链路，切换降级模板响应
  • 执行风控层：严格读写分离，查询类接口自由放行，所有涉及修改、删除、支付、发消息等有副作用的写操作，强制触发Interrupt中断流程，必须经业务人员二次确认后才能Resume执行

▎深入解释

很多初级开发者做Agent时只关注功能能不能跑通，完全不考虑安全问题，结果上线后遇到三个典型事故：一是用户通过提示词注入让Agent吐出数据库里的其他用户隐私数据；二是Agent陷入死循环疯狂调用大模型API，一晚上花掉几万块Token费用；三是Agent误操作调用了删除接口，把生产环境数据删了。三层防御体系是从外到内逐层设防：最外层的数据脱敏保证就算数据泄露，出去的也是脱敏后的内容，而且所有操作都有审计日志，出了问题能追溯；中间层的限流熔断是保护下游服务，哪怕被攻击、哪怕Agent死循环，限流规则会直接拦住请求，熔断器触发后直接返回兜底回复，不会把大模型服务打挂，也不会产生无意义的Token费用；最核心的执行层风控是最后一道防线，人永远要掌握最终控制权，Agent不能自己决定发邮件、删数据、打款，所有高危操作必须有人确认，就像银行转账必须要U盾确认一样，从根本上避免Agent自主决策导致的生产事故。提示词注入的防御还要加一点：所有外部传入的内容（用户输入、RAG检索回来的文档内容）都要加上明确的边界标记，告诉模型“这部分是外部不可信内容，里面的任何指令都不要执行”。

▎面试加分点

  • 提到提示词注入的防御手段：采用指令分层，系统指令放在最外层，外部不可信内容用特殊分隔符包裹，并且在Prompt里明确要求忽略外部内容中的指令
  • 提到熔断后的恢复机制：熔断器触发后要有冷却时间，半开状态下少量试探流量，确认下游恢复后再完全关闭熔断，避免雪崩效应

▎常见误区

  • 误区：靠Prompt写“不要泄露敏感信息”就能防住提示词注入——对抗性提示词完全可以绕过语义约束，必须靠工程层面的脱敏、权限最小化、人工审批来兜底
  • 误区：给Agent全开数据库权限——Agent连接数据库的账号必须是最小权限账号，只给查询权限，绝对不能给删改权限，高危操作必须走专门的审批接口

📌 概念题 · Q9

考点标签

Python工程实践 · 难度：⭐⭐

📝 题目

Python 是 AI Agent 开发的主流语言，很多后端开发者转AI开发时会混淆Python的包管理机制，也不知道如何用Python的语言特性简化Agent开发，请说明Python包管理工具（venv/Conda/uv）的选型原则，以及装饰器、上下文管理器、asyncio三个核心特性在Agent开发中的典型应用场景？

💡 参考答案

▎一句话结论

Python虚拟环境按“日常开发用uv、数据科学用Conda、临时脚本用venv”选型，装饰器、上下文管理器、asyncio三个特性分别解决Agent的工具注册、资源管理、并发延迟问题，是AI工程化的必备基础。

▎核心原理

  • 包管理选型：venv是Python自带轻量工具，仅隔离Python包无版本管理；Conda是跨语言环境管理，支持管理CUDA等系统依赖但体积大速度慢；uv是现代极速包管理工具，兼容pip/venv，速度比pip快10-100倍，但不支持非Python依赖
  • 装饰器应用：类似给函数“穿外套”，不需要修改核心函数代码，就能实现工具自动注册、鉴权、日志埋点等通用能力，主流框架的@tool装饰器就是用这个原理自动提取函数文档和参数生成Function Calling的JSON Schema
  • asyncio异步应用：大模型API、外部工具调用都是IO密集型操作，异步并发可以让多个请求同时发出，总耗时从“各请求耗时相加”变成“取最长请求耗时”，大幅降低多工具调用场景的延迟
  • 上下文管理器应用：基于with语句实现资源的自动获取与释放，保证数据库连接、文件句柄、锁资源哪怕发生异常也会被正确关闭，避免内存泄漏和资源占用

▎深入解释

很多刚从Java/JS转Python的开发者最容易踩的坑就是包环境污染，全局装一堆包，结果不同项目依赖版本冲突，所以虚拟环境是Python开发的基础。三个工具的定位完全不同：uv是新一代的工具，用Rust写的，安装依赖速度极快，普通Agent开发没有复杂系统依赖的话，uv是最优选择；如果做深度学习训练，需要管理CUDA、cuDNN这些系统级依赖，Conda是唯一选择；如果在服务器上跑个简单脚本，不想装额外工具，用自带的venv就行。三个语言特性在Agent开发里几乎天天用到：装饰器是实现插件化工具注册的核心，你要加一个新工具，只需要写个函数加@tool装饰器，框架就会自动把它注册成Agent可用的工具，不需要改Agent核心代码，完美符合开闭原则；asyncio是性能优化的关键，比如Agent要同时调用查天气、查股票、查新闻三个接口，同步写要等3次，异步写只要等最慢的那个返回就行，延迟能降三分之二；上下文管理器是稳定性的基础，比如你连数据库，查完数据如果代码抛异常了，不用上下文管理器的话连接就不会释放，久而久之连接池就满了，用with语句的话不管出什么错，连接都会自动还给连接池。

▎面试加分点

  • 提到Pydantic的应用：用Pydantic做Agent的状态定义、工具参数校验、结构化输出约束，比原生__getattr__更可靠，是现代Python Agent开发的标配
  • 提到uv的额外优势：uv支持一键管理Python版本、锁定依赖版本，比pip+venv的组合体验好很多，已经成为FastAPI等主流框架官方推荐的包管理工具

▎常见误区

  • 误区：Conda比pip好，所有场景都用Conda——Conda的源在国内速度慢，而且包数量不如PyPI全，普通Web/Agent开发用uv/pip就够了，没必要用Conda
  • 误区：异步比同步快——异步只有在IO密集型场景下才会提升吞吐量、降低总等待时间，CPU密集型场景用异步反而会增加复杂度，没有收益

📌 概念题 · Q10

考点标签

大模型微调落地 · 难度：⭐⭐⭐

📝 题目

很多开发者做领域大模型微调时，第一反应是要买高端本地显卡、下载几十GB的模型到本地，导致微调门槛极高、成本居高不下，请说明工业界落地领域微调的三种主流方案分别是什么？为什么说普通企业做微调完全不需要本地部署大模型和高端显卡？

💡 参考答案

▎一句话结论

大模型微调不需要本地存模型、不需要高端本地显卡，工业界三种主流方案（云GPU训练、在线平台训练、本地显卡训练）中，云GPU方案是99%企业的首选，1元/小时的24G显卡就能完成绝大多数垂直领域微调任务，成本极低、开机即用。

▎核心原理

  • 方案1：AutoDL/阿里云等云GPU平台（最推荐）：平台预装Qwen、Llama3等主流大模型和LLaMA Factory训练框架，24G显存显卡仅1-2元/小时，上传数据集打开网页就能训练，训完直接关机释放资源，不需要本地存模型、不需要本地有显卡
  • 方案2：ModelScope魔搭等在线训练平台：浏览器打开就能用，零本地部署，支持主流开源模型一键训练，适合快速验证小数据集效果，缺点是功能不如LLaMA Factory灵活
  • 方案3：本地显卡训练：适合有RTX 3090/4090以上显卡、需要长期做训练实验的开发者，需要自己下载模型、配置环境，前期搭建成本高

▎深入解释

很多人对微调的印象还停留在“要买几万块的显卡、下载几十GB的模型、搭几天环境才能开始训”，这是完全过时的认知。现在云GPU服务已经非常成熟，就像你不用自己建发电厂，用电的时候插插座按度数付钱就行。比如你要做HR客服话术的微调，根本不需要自己买3090显卡，也不需要在本地下载14B的Qwen模型，打开AutoDL，选一个带LLaMA Factory的镜像，1分钟就能开机，把你整理好的几千条HR对话数据集传上去，点开始训练，几个小时就训完了，花费可能才十几块钱，训完把LoRA权重导出来直接用，然后关机就不再产生费用。整个过程本地电脑只要有浏览器就行，不需要任何高端硬件。很多团队一开始就买几万块的显卡，结果大部分时间显卡都是闲置的，算下来成本比用云GPU高几十倍。而且云GPU平台的镜像都预装好了CUDA、PyTorch、LLaMA Factory这些环境，不需要自己踩环境配置的坑，新手也能1分钟启动训练。

▎面试加分点

  • 提到微调的硬件选型：7B模型LoRA微调只需要16G显存，14B模型只需要24G显存，根本不需要A100、H100这种高端卡，消费级显卡或者云GPU的24G卡完全够用
  • 提到微调产物的部署：LoRA微调产出的adapter权重只有几十MB，不需要重新部署完整大模型，配合vLLM等推理框架可以动态加载，非常适合SaaS多租户场景

▎常见误区

  • 误区：微调必须用A100/H100这种高端计算卡——LoRA微调的显存占用非常低，24G显存就能跑14B模型的微调，云GPU上1-2元/小时的卡完全够用
  • 误区：本地训练更安全——正规云GPU平台都支持数据加密，而且训练完可以彻底删除数据，对于绝大多数企业来说，云平台的安全合规性比本地机房还高，成本还低

场景标签

长周期业务Agent 休眠唤醒 状态持久化

📝 题目

某制造企业要搭建采购审批 Agent 系统，核心流程为：员工提交采购申请 → Agent 自动校验预算、核对库存 → 触发部门经理审批 → 经理审批通过后触发总监审批 → 所有审批完成后自动调用 ERP 生成采购单。整个流程可能跨越 3-7 天，期间会多次等待人工操作，且需要支持审批驳回后回退到申请修改环节。请你设计这套长周期 Agent 的核心架构，说明如何实现跨天的流程等待、状态恢复和异常回滚。

💡 参考答案

▎解题思路

  1. 第一步：首先明确长周期 Agent 与普通问答 Agent 的核心差异：不能常驻内存等待人工操作，必须实现状态持久化与中断唤醒机制，避免资源浪费和进程崩溃导致流程丢失。
  2. 第二步：基于状态机思想拆分流程节点，区分自动执行节点和人工等待节点，为每个节点设计明确的状态流转规则和回滚路径。
  3. 第三步：设计状态持久化方案、中断触发机制、异步唤醒链路，同时加入异常兜底和人工干预入口。
  4. 第四步：验证方案的可恢复性、幂等性，确保网络波动、服务重启、审批驳回等场景下流程不会错乱。

▎详细方案

整体采用 LangGraph 作为状态编排框架，搭配 PostgreSQL Checkpointer 实现全链路状态持久化，核心架构分为四层：
1. 状态定义层：全局 State 中包含采购申请单核心字段（申请人、金额、物料清单）、流程节点标识（当前走到哪个审批环节）、审批结果链（每个节点的审批人、时间、意见）、异常标记、loop_count 重试计数器。每个节点执行完成后，Checkpointer 自动将全量 State 序列化为 JSON 存入 PostgreSQL，同时释放当前 Pod 的计算资源，Agent 进入休眠状态，不占用常驻内存。
2. 节点执行层：将整个流程拆分为6个独立节点：①申请校验节点（自动校验预算、库存）、②经理审批触发节点（调用OA接口创建审批单）、③经理审批等待节点（中断点）、④总监审批触发节点、⑤总监审批等待节点（中断点）、⑥ERP采购单生成节点。其中自动节点执行完成后直接流转到下一个节点，等待节点执行时主动抛出 Interrupt 信号，将流程挂起。
3. 中断唤醒层：当审批人在OA系统点击同意/驳回时，OA系统通过 Webhook 回调 FastAPI 服务，携带审批单 Task_ID 和审批结果。服务端根据 Task_ID 从 PostgreSQL 中查询对应的 checkpoint_id，反序列化历史 State，将审批结果作为新的事件输入更新到 State 中，调用 graph.stream(None, config={"configurable": {"thread_id": task_id}}) 唤醒 Agent 继续执行后续流程。如果是驳回操作，则通过 graph.update_state() 将状态回滚到申请校验节点，同时把驳回意见注入 State，通知申请人修改后重新提交。
4. 异常兜底层：为每个外部接口调用（OA、ERP）配置3次重试机制，重试时动态注入失败原因到 Prompt 中调整调用策略；如果重试超过上限，自动触发降级路由，发送飞书通知给运维人员介入，同时保留所有历史状态支持人工恢复。

▎关键细节 & 踩坑点

  • 必须为每个流程实例生成全局唯一的 thread_id（通常用审批单 Task_ID 映射），避免不同采购单的状态串扰；唤醒时必须严格校验 Webhook 请求的签名，防止恶意请求伪造审批结果唤醒流程。
  • 状态持久化时不能只存对话上下文，必须把外部系统的交互凭证（如审批单ID、ERP临时token）、局部变量（如校验后的预算剩余额度）一起序列化，否则唤醒后会出现上下文丢失导致重复创建审批单的问题。
  • 所有写操作（如生成采购单、扣减预算）必须实现幂等性，通过业务唯一键（采购申请单号）做防重判断，避免唤醒时重复执行导致数据重复。
  • Interrupt 抛出前必须确保外部审批单已经创建成功，否则会出现 Agent 挂起但没有对应审批入口的死锁场景。

▎可扩展优化

  • 可以加入超时检测机制：通过定时任务扫描数据库中处于等待状态超过72小时的流程，自动发送催办通知给审批人，超过7天自动驳回流程。
  • 支持流程轨迹可视化：将每个 checkpoint 的状态变更同步到审计日志表，前端可以展示完整的审批流转时间线，方便问题追溯。
  • 扩展多分支路由：支持金额超过10万时自动增加财务总监审批节点，无需修改核心流程代码，只需在状态流转时动态插入节点即可。

题型

场景分析题

场景标签

多Agent协作 模型路由 成本优化

📝 题目

某电商公司要搭建智能客服系统，需要同时处理三类场景：①售后咨询（查物流、退换货规则，占比70%，问题简单、答案标准化）；②订单纠纷处理（退款协商、投诉安抚，占比25%，需要多轮沟通、调用订单/物流接口）；③复杂投诉升级（涉及赔偿、工商投诉，占比5%，需要严格遵循合规话术、转人工前生成完整案情摘要）。团队一开始想把所有工具和话术都塞给一个旗舰大模型做Single Agent，但测试发现不仅Token成本是预期的3倍，还经常出现简单问题调用复杂工具、纠纷场景话术不符合规范的问题。请你分析问题原因，并给出合理的Multi-Agent拆分和路由方案。

▎解题思路

  1. 第一步：先定位Single Agent方案的核心问题：工具过多导致模型注意力分散，所有请求都走旗舰模型造成成本浪费，不同场景的Prompt策略互相干扰导致输出不稳定。
  2. 第二步：按照“单一职责、工具最小集”的原则拆分Worker Agent，每个Agent只负责一类场景，只绑定对应场景需要的工具和Prompt。
  3. 第三步：设计分层路由机制，先做轻量意图分类，再根据场景复杂度路由到对应能力等级的模型，平衡成本和效果。
  4. 第四步：设计Agent之间的流转规则，特别是复杂场景升级时的上下文传递机制，避免用户重复描述问题。

▎详细方案

问题根因分析：Single Agent模式下，系统需要把物流查询、订单查询、退款计算、合规话术、案情摘要生成等十几个工具的Schema全部塞给大模型，同时System Prompt要同时覆盖三类场景的规则，会导致两个核心问题：一是模型的注意力被稀释，简单的查物流问题可能误调用退款工具，准确率下降；二是所有请求不管难易都走旗舰模型，70%的简单问题占用了大量算力，成本居高不下。

具体拆分和路由方案如下：
1. Agent拆分采用Router-Worker模式，共拆分4个角色：
- 路由Agent（Router）：只做意图识别和场景分类，不执行业务逻辑，绑定0个业务工具，只接收用户当前query和最近3轮对话历史，判断用户属于三类场景中的哪一类。
- 售后咨询Agent：只绑定物流查询、常见问题知识库2个工具，System Prompt只包含退换货规则、物流查询话术，不涉及任何纠纷处理逻辑。
- 订单纠纷Agent：绑定订单查询、物流轨迹查询、退款金额计算3个工具，System Prompt包含纠纷安抚话术、退款协商SOP，支持多轮沟通。
- 复杂投诉Agent：绑定用户历史订单查询、聊天记录摘要、合规话术库3个工具，System Prompt严格约束合规红线，负责生成案情摘要后触发转人工流程。
2. 模型动态路由策略：
- 路由Agent和售后咨询Agent全部调用轻量Flash模型（如豆包seed-1.8-flash），这两类场景占总请求的70%，单Token成本仅为旗舰模型的1/10，响应速度提升2倍。
- 订单纠纷Agent调用旗舰模型（如豆包seed-1.8），保证多轮沟通的逻辑连贯性和话术准确性。
- 复杂投诉Agent调用旗舰模型+合规规则前置校验，确保输出100%符合合规要求。
3. 流转机制：当售后咨询Agent识别到用户问题属于纠纷场景（如用户提到“要投诉”“赔偿”），自动将当前对话历史、已查询到的订单信息打包传递给路由Agent，重新路由到对应Agent，无需用户重复描述；复杂投诉Agent处理完成后，自动生成结构化的案情摘要（包含用户诉求、沟通记录、订单信息、初步处理建议），再推送给人工客服。

▎关键细节 & 踩坑点

  • 路由Agent不能只根据当前query分类，必须结合最近3轮对话历史，否则用户在售后咨询中突然提到“我要投诉”时会出现路由错误；路由Prompt要加入few-shot示例，覆盖场景切换的边界case。
  • 每个Worker Agent的工具集必须严格控制在2-3个，绝对不能把其他场景的工具暴露给当前Agent，从根源上避免误调用。
  • 跨Agent传递上下文时不能传递全量对话历史，只传递当前场景已经确认的结构化信息（如订单号、物流状态、用户核心诉求），避免上下文冗余导致成本上升。
  • 要设置路由兜底机制：如果路由Agent连续2次分类置信度低于0.8，直接路由到订单纠纷Agent，避免出现分类死循环。

▎可扩展优化

  • 可以在网关层加入缓存机制：对于高频的标准化问题（如“退换货规则是什么”），直接从缓存返回答案，不需要调用大模型，进一步降低成本。
  • 加入效果反馈闭环：每个会话结束后让用户评价满意度，对于路由错误、回答错误的case自动存入测试集，定期优化路由Agent的Prompt和分类阈值。
  • 支持多模态扩展：如果后续需要处理用户上传的商品破损照片，只需给复杂投诉Agent增加视觉模型调用工具，不影响其他两个Agent的逻辑。

🛠 应用题 · Q3 · 工程实现题

题型

工程实现题

场景标签

流式输出 SSE TTFT优化 结构化输出

📝 题目

你负责开发自媒体文案生成Agent的前端交互模块，产品要求：用户输入主题后，前端要实时展示Agent的思考过程（如“正在检索热点素材”“正在生成标题”“正在生成正文”）和正文的逐字输出效果，用户感知的首字延迟不能超过2s，同时要准确统计每次请求消耗的Token数量用于成本核算。但你发现很多云厂商的大模型流式接口在开启结构化输出时，无法在流的末尾返回标准的usage字段，而且如果直接把大模型的流返回给前端，会出现首字延迟高、节点状态不同步的问题。请你给出前后端的具体实现方案，包含核心代码逻辑。

💡 参考答案

▎解题思路

  1. 第一步：前后端职责拆分：后端负责对接大模型流、统一事件格式、处理Token统计，前端负责异步解析流、分块渲染不同类型的内容，避免前端直接对接大模型原生流导致的兼容性问题。
  2. 第二步：后端基于LangGraph的astream_events统一捕获节点状态变化和Token流，封装成标准SSE事件格式，保证流式和非流式模式下状态结构一致。
  3. 第三步：前端通过fetch API的ReadableStream实现异步解析，区分“节点状态事件”和“内容Token事件”分别渲染，进一步降低用户感知延迟。
  4. 第四步：解决结构化输出场景下的Token统计问题，通过前后端配合的手动计数+原生JSON Mode方案，兼容云厂商接口不返回usage的问题。

▎详细方案

整体采用后端统一流封装+前端分层解析的架构，核心实现逻辑如下：
1. 后端实现（FastAPI + LangGraph）：
- 首先定义SSE事件的统一格式，分为三类事件：①node事件：返回当前执行的节点名称、状态（开始/结束），用于前端展示思考过程；②token事件：返回大模型生成的正文内容片段；③end事件：返回完整的生成结果、Token统计信息、请求ID。
- 监听LangGraph的astream_events流，过滤出on_chat_model_stream事件捕获Token片段，过滤出on_chain_start/on_chain_end事件捕获节点状态变化，将这些事件按照统一格式序列化为SSE数据块返回。
- Token统计方案：开启大模型原生JSON Mode，使用Pydantic定义结构化输出Schema（包含标题、正文、标签三个字段），后端在接收流的过程中手动累计输入Token数（通过tiktoken库对输入Prompt编码计算）和输出Token数（对每个返回的Token片段编码累计），不需要依赖云厂商返回的usage字段。
核心后端伪代码：
```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import tiktoken
enc = tiktoken.get_encoding("cl100k_base")

@app.post("/api/generate")
async def generate(req: GenerateReq):
async def event_stream():
input_tokens = len(enc.encode(req.prompt + str(req.history)))
output_tokens = 0
async for event in graph.astream_events(
{"topic": req.topic},
config={"configurable": {"thread_id": req.thread_id}},
version="v2"
):
if event["event"] == "on_chain_start" and event["name"] in ["retrieve_node", "title_node", "content_node"]:
yield f"data: {json.dumps({'type': 'node', 'node': event['name'], 'status': 'start'})}\n\n"
if event["event"] == "on_chat_model_stream":

if chunk:
output_tokens += len(enc.encode(chunk))
yield f"data: {json.dumps({'type': 'token', 'content': chunk})}\n\n"
yield f"data: {json.dumps({'type': 'end', 'usage': {'input_tokens': input_tokens, 'output_tokens': output_tokens}})}\n\n"
return StreamingResponse(event_stream(), media_type="text/event-stream")
2. 前端实现（浏览器原生API，无第三方依赖）： - 使用fetch API获取响应流，通过response.body.getReader()获取读取器，用TextDecoder逐块解码SSE数据，按照`\n\n`分割事件块，解析每个事件的类型。 - 收到node事件时，实时更新页面上的“思考过程”区域，比如显示“✅ 已检索到12条热点素材”“正在生成正文...”；收到token事件时，直接将内容追加到正文区域，实现逐字输出效果；收到end事件时，展示完整结果和Token消耗统计，停止加载状态。 核心前端伪代码：javascript
async function generateContent(topic) {
const response = await fetch('/api/generate', {
method: 'POST',
body: JSON.stringify({topic, thread_id: Date.now()}),
headers: {'Content-Type': 'application/json'}
});
const reader = response.body.getReader();
const decoder = new TextDecoder();
let buffer = '';
while (true) {
const {done, value} = await reader.read();
if (done) break;
buffer += decoder.decode(value, {stream: true});
const events = buffer.split('\n\n');
buffer = events.pop(); // 保留未完成的块
for (const eventStr of events) {
if (!eventStr.startsWith('data: ')) continue;
const event = JSON.parse(eventStr.slice(6));
if (event.type === 'node') updateStatus(event.node, event.status);
if (event.type === 'token') appendContent(event.content);
if (event.type === 'end') showUsage(event.usage);
}
}
}
```

▎关键细节 & 踩坑点

  • 后端返回SSE时必须设置响应头Cache-Control: no-cache、Connection: keep-alive，同时关闭Nginx的缓冲（proxy_buffering off），否则会出现Nginx攒够一定数据才返回给前端，导致首字延迟升高的问题。
  • 手动计算Token数时要注意和大模型使用的Tokenizer保持一致（如OpenAI用cl100k_base，开源模型用对应的分词器），误差控制在1%以内完全可以满足成本核算需求，不需要依赖云厂商的usage字段。
  • 前端解析流时必须处理半包问题：因为TCP分片可能导致一个SSE事件被拆成多个块返回，所以要用buffer暂存未解析完成的数据，不能每次拿到chunk就直接解析，否则会出现JSON解析错误。
  • 结构化输出必须用大模型原生JSON Mode + Pydantic校验，不要自己用正则提取JSON，否则流式输出过程中会出现JSON不完整导致解析失败的问题。

▎可扩展优化

  • 可以在后端加入流压缩：对SSE事件进行gzip压缩，减少网络传输体积，进一步降低弱网环境下的延迟。
  • 加入断流重连机制：前端在流异常断开时，根据最后收到的节点状态请求后端继续生成，避免用户需要重新输入主题。
  • 支持中断功能：前端提供“停止生成”按钮，后端收到中断请求后调用graph.interrupt()终止大模型调用，避免浪费Token。

🛠 应用题 · Q4 · 排障优化题

题型

排障优化题

场景标签

上下文膨胀 Token成本 TTFT优化 前缀缓存

📝 题目

你负责的HR智能客服系统上线1个月后，监控数据显示：随着用户对话轮数增加，平均TTFT（首字延迟）从最初的2s上升到8s，单轮Token成本从0.01元上涨到0.08元，而且大模型经常出现“遗忘”之前用户说过的关键信息（如用户已经说过自己是新入职员工，模型后续还反复询问入职时间）。排查发现开发人员为了实现多轮对话，直接把所有历史聊天记录全部拼接到每一轮的Prompt中，没有做任何处理。请你定位问题根因，并给出具体的优化方案，要求优化后TTFT降到2s以内，Token成本降低70%以上，同时解决上下文遗忘问题。

💡 参考答案

▎解题思路

  1. 第一步：定位核心问题根因：全量历史消息拼接导致上下文长度线性增长，不仅Token成本飙升，还会因为上下文过长超出模型注意力窗口导致“中间遗忘”效应，同时过长的Prompt无法触发KV Cache前缀缓存，导致TTFT升高。
  2. 第二步：设计分层记忆架构，将对话历史分为近期记忆和长期记忆，避免全量拼接历史消息。
  3. 第三步：通过固定Prompt结构、排序RAG结果等手段深度触发前缀缓存，大幅降低TTFT。
  4. 第四步：加入记忆更新和校验机制，确保关键用户信息不会丢失，解决遗忘问题。

▎详细方案

问题根因拆解：
1. 成本问题：每轮请求都拼接N轮历史消息，输入Token数随轮数线性增长，10轮对话后输入Token可能达到4k+，单轮成本是短上下文的8倍。
2. 延迟问题：一方面长Prompt的Prefill阶段耗时随Token数线性增加；另一方面因为每轮对话的历史消息都在变化，请求前缀（System Prompt+历史消息）每轮都不一样，无法命中模型的Prefix Cache（前缀缓存）和KV Cache，导致每次请求都要重新计算所有Token的KV值，TTFT大幅升高。
3. 遗忘问题：当上下文长度超过模型的有效注意力窗口（如7B模型通常有效窗口在4k-8k），模型会出现“Lost in the Middle”现象，对中间位置的信息注意力极低，导致关键信息被遗忘。

具体优化方案分为三层：
1. 分层记忆管理，从根源减少输入Token数：
- 近期记忆（Short-term Memory）：仅保留最近5轮的原始对话记录，存入PostgreSQL，每轮请求时直接拼接到Prompt中，保证最近的对话上下文完整。
- 长期记忆（Long-term Memory）：对于更早的对话，通过后台异步运行的摘要Agent，每新增3轮对话就自动将历史消息压缩为结构化的用户画像和关键事实（如“用户：张三，2024年10月8日入职，技术部，咨询过社保转移问题”），存入用户画像表。每轮请求时只把结构化的用户画像摘要拼接到System Prompt中，不需要拼接全部历史消息。
优化后，无论对话进行多少轮，输入Token数都稳定在1k-2k之间，不会随轮数增长，Token成本直接降低70%以上。
2. 深度触发Prefix Cache，压缩TTFT：
- 固定Prompt结构：将System Prompt、用户画像摘要、RAG检索结果的顺序固定，System Prompt内容完全不变，用户画像和RAG结果放在Prompt的后半部分，确保请求的前N个Token（System Prompt部分，约500Token）在所有用户请求中完全一致。
- RAG结果固定排序：检索到的知识库片段按照文档ID排序，不要按照相关性分数动态排序，避免相同的检索结果因为顺序不同导致前缀不一致。
通过以上优化，请求的前缀部分可以100%命中云厂商的KV Cache，Prefill阶段不需要重新计算这部分Token的KV值，TTFT可以从8s降到1.5s-2s之间。
3. 关键信息防遗忘机制：
- 在每轮大模型调用前，增加一个轻量的信息提取步骤（用Flash模型），判断当前轮用户是否提供了新的关键信息（如入职时间、部门、具体诉求），如果有则自动更新到用户画像的结构化字段中，不会因为摘要压缩丢失信息。
- System Prompt中明确要求模型：回答前先参考用户画像中的关键信息，如果信息不全再询问用户，避免重复提问。

▎关键细节 & 踩坑点

  • 摘要Agent不能做通用文本摘要，必须输出结构化的JSON格式（如用户基本信息、核心诉求、待办事项三个字段），避免摘要过程中丢失关键信息。
  • 触发前缀缓存的前提是Token序列完全一致，不仅是文本内容一致，还要注意消息角色（System/User/Assistant）的顺序、空格、换行符都必须完全一致，否则无法命中缓存。比如不要在System Prompt中动态插入当前时间，否则每轮请求的前缀都会变化。
  • 近期记忆保留的轮数不要超过5-7轮，否则还是会出现上下文膨胀的问题；对于需要跨多轮参考的信息，必须提取到长期记忆的结构化字段中。
  • 不要用滑动窗口直接截断历史消息，否则会导致关键信息被直接丢弃，结构化摘要比滑动窗口的信息保留率高40%以上。

▎可扩展优化

  • 可以将长期记忆存入向量数据库，当用户问题和历史记忆相关时再检索对应的记忆片段，而不是把所有用户画像都拼接到Prompt中，进一步减少输入Token数。
  • 加入缓存命中率监控：通过云厂商的API返回的cache_hit_rate指标监控前缀缓存的命中情况，当命中率低于90%时自动告警，排查Prompt结构是否被修改。
  • 对于高频重复问题（如“社保怎么交”），直接在网关层缓存答案，不需要调用大模型，进一步降低成本和延迟。

Agent测试 Harness CI/CD 上线交付

📝 题目

你带领3人小团队开发建材报价Agent，核心能力是接收用户上传的CAD施工图纸，自动识别图纸中的建材用量，结合实时建材价格数据库生成Excel格式的报价单。目前团队已经完成了Demo版本开发，能够在本地跑通简单的测试图纸，但经常出现算量误差超过10%、遇到复杂图纸时陷入死循环疯狂消耗Token、价格数据库接口超时后Agent直接崩溃的问题。老板要求2周内上线第一个可用版本，要求算量误差控制在3%以内，不能出现死循环刷Token的问题，接口可用性达到99.5%。请你给出从当前Demo到生产可用版本的完整交付方案，包含测试体系、稳定性保障、上线流程。

💡 参考答案

▎解题思路

  1. 第一步：先搭建最基础的Agent Harness测试沙箱，把Demo版本的核心问题（算量不准、死循环、异常崩溃）先通过自动化测试复现出来，避免盲目改代码。
  2. 第二步：针对测试发现的问题，逐个加入稳定性防护机制（循环硬上限、超时熔断、异常降级），把非确定性的Agent行为用确定性的工程代码包裹起来。
  3. 第三步：基于测试集持续迭代Prompt和工具逻辑，直到算量准确率达到上线标准。
  4. 第四步：接入CI/CD流程，建立上线前的自动化测试门禁，同时配置线上监控和告警体系，确保上线后问题可发现、可回滚。

▎详细方案

整个交付过程分为四个阶段，2周内可完成：
第一阶段（第1-2天）：搭建极简Agent Harness测试体系，量化当前问题。
不需要一开始就搭建复杂的沙箱系统，直接用pytest写一个最简单的测试马具，核心功能包括：
- 测试集构建：收集50张覆盖不同场景的历史图纸（简单户型、复杂复式、工装项目），以及对应的人工审核过的标准报价单作为Ground Truth，按照7:3分为训练集和测试集。
- 测试脚本核心逻辑：批量遍历测试集，为每个Agent实例注入max_loops=10（最多循环10次）、timeout=120s（单轮执行超时2分钟）的熔断限制，运行Agent生成报价单后，自动对比算量结果和标准答案的误差率，统计三个核心指标：平均算量误差率、死循环发生率、接口异常崩溃率。
- 沙箱隔离：所有测试运行在Docker容器中，限制容器的CPU、内存、网络访问权限，避免Agent执行错误代码影响本地环境。
运行完第一版测试后，你会得到量化的基线数据（比如当前平均误差12%、死循环率15%、崩溃率20%），所有优化都基于这个基线做对比。

第二阶段（第3-8天）：稳定性加固和准确率优化，达到上线指标。
针对测试发现的三类核心问题逐个解决：
1. 死循环和Token刷爆问题：
- 在全局State中加入loop_count计数器，每次进入“重新算量”节点时计数器加1，达到5次硬上限时强制退出循环，返回“当前图纸过于复杂，请人工审核”的降级响应，从代码层面切断死循环。
- 动态Prompt注入：每次重试时，把上一次的算量结果和误差原因注入到Prompt中（如“这是你第2次算量，上次钢筋用量比标准值低8%，请重点检查梁结构的钢筋标注”），从语义层面避免无意义的重试。
2. 异常崩溃问题：
- 为所有外部工具调用（价格数据库查询、CAD解析接口）加入3次重试机制，重试间隔采用指数退避；如果重试失败，触发熔断器，直接返回降级结果，不要让异常向上抛出导致整个流程崩溃。
- 节点级回滚：如果CAD解析失败或者价格接口超时，通过Time-travel机制回滚到图纸上传节点，提示用户重新上传清晰的图纸，不需要重新走整个流程。
3. 算量准确率优化：
- 基于测试集的错误case，逐个优化System Prompt，加入算量规则的Few-Shot示例，针对误差大的建材类型（如钢筋、混凝土）单独增加校验步骤，要求Agent算完后自动核对用量和面积的匹配关系。
- 每修改一次Prompt或工具逻辑，就跑一遍全量测试集，直到测试集上的平均误差率≤3%、死循环率=0、崩溃率=0，才允许进入下一阶段。

第三阶段（第9-11天）：接入CI/CD门禁和预发布验证。
- 将Harness测试脚本接入代码仓库的CI流程，每次提交代码时自动运行核心测试集（20张高频图纸），如果误差率超过3%或者出现死循环、崩溃问题，直接阻断代码合并，避免劣化代码进入生产。
- 预发布环境搭建：用和生产一致的数据库、接口配置，连续24小时运行压力测试，模拟100并发上传图纸，验证接口可用性、Token消耗、响应时间是否符合要求，确保不会出现高并发下的服务雪崩。
- 加入灰度机制：上线初期只开放给10%的用户使用，所有生成的报价单都先经过人工审核，收集bad case持续迭代模型和Prompt。

第四阶段（第12-14天）：上线和监控体系搭建。
- 线上监控配置三个核心告警：①单请求Token消耗超过10k告警（可能出现死循环）；②算量误差率超过5%告警；③接口成功率低于99.5%告警。
- 所有Agent的执行轨迹（Tool调用、思考过程、算量中间结果）都存入日志系统，出现问题时可以快速回溯定位原因。
- 上线后第一周安排专人值班，每天收集错误case更新测试集，持续优化准确率。

▎关键细节 & 踩坑点

  • 第一版Harness不要追求完美，1天之内必须写出来跑通，核心是能批量跑测试用例、能做熔断限制、能自动计算误差率，不要一开始就想做可视化、LLM-as-a-judge等复杂功能，先解决有无问题。
  • 硬上限的阈值设置要合理：max_loops不要设置太大（如超过10次），正常情况下Agent3次重试以内就能得到正确结果，超过5次基本就是陷入死循环了，及时退出比无意义重试更重要。
  • 测试集必须覆盖边界case：比如图纸标注模糊、特殊建材、价格接口返回异常数据等场景，不能只用简单的标准图纸测试，否则上线后遇到复杂场景一定会出问题。
  • 熔断器的降级响应必须友好，不要直接返回“系统错误”，要给用户明确的指引（如“当前图纸识别难度较高，已转人工处理，预计2小时内给您回复”），避免影响用户体验。

▎可扩展优化

  • 当测试集扩大到1000张以上时，可以接入LangSmith或者Promptflow作为Harness平台，实现测试用例管理、轨迹可视化、LLM自动判分，提升测试效率。
  • 可以加入人工反馈闭环：用户或人工审核修正报价单后，自动把修正后的结果加入测试集，定期运行回归测试，让系统准确率随着数据积累持续提升。
  • 后续可以引入多模型路由：简单图纸用Flash模型算量，复杂图纸用旗舰模型算量，在保证准确率的前提下进一步降低算量成本。
