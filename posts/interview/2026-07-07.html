📌 概念题 · Q1

考点标签

Agentic RAG · 动态路由 · 难度：⭐⭐⭐

📝 题目
动态意图路由在Agentic RAG中的核心作用是什么？其实现的关键步骤有哪些？

💡 参考答案

▎一句话结论
动态意图路由是Agentic RAG实现任务分流与资源优化的核心机制，通过LLM自主决策将用户请求路由到最合适的检索工具或数据源，避免无效检索并提升响应效率。

▎核心原理
- LLM驱动的意图识别：利用大模型理解用户问题的意图类型（如事实查询、结构化数据检索、外部API调用）；
- 工具映射：将意图与预定义的检索工具（向量库、SQL数据库、第三方API等）建立关联；
- 自主选择：LLM根据工具描述（如适用场景、响应速度）自主选择最优工具；
- 结果整合：将工具返回的结果整合到Prompt中，供LLM生成最终回答。

▎深入解释
传统RAG是固定流程（Query→检索→生成），而动态路由让LLM像人类一样“思考”：用户问“去年Q3的销售数据”，路由到SQL数据库；问“公司文化手册内容”，路由到向量库；问“今天北京天气”，调用天气API。这种机制避免了对所有问题都进行向量检索的低效行为，同时支持复杂多工具组合（如同时查询SQL和向量库）。例如，用户问“去年Q3销售数据是否符合公司战略目标”，路由会先调用SQL查数据，再调用向量库查战略文档，最后整合结果生成回答。

▎面试加分点
- 提到结合工具元数据（如工具的成本、延迟、权限）让LLM更智能地选择工具；
- 举例说明动态路由的可扩展性：新增工具只需添加工具描述，无需修改核心流程；
- 提及路由的容错机制（如工具调用失败时自动切换备用工具）。

▎常见误区
- 误认为动态路由只是简单的规则匹配，忽略了LLM的自主决策能力；
- 未考虑工具调用的成本（如API费用）或权限（如敏感数据访问限制），导致路由决策不合理。

📌 概念题 · Q2

考点标签

pgvector · 索引选择 · 难度：⭐⭐⭐

📝 题目
在企业级RAG场景中，pgvector的HNSW和IVFFlat索引应该如何选择？各自的适用场景是什么？

💡 参考答案

▎一句话结论
HNSW适用于对检索速度和召回率要求高的场景，IVFFlat适用于数据量小、索引构建快的场景，两者的选择需平衡检索性能、内存开销和构建成本。

▎核心原理
- HNSW（Hierarchical Navigable Small Worlds）：基于图结构的索引，通过多层导航节点快速定位相似向量，召回率高（>95%），检索速度快，但索引构建慢、内存开销大；
- IVFFlat（Inverted File Flat）：基于聚类的索引，将向量分成多个簇，检索时先找目标簇再比较，索引构建快、内存开销小，但召回率随数据量增长下降明显。

▎深入解释
企业级RAG中，若知识库文档量达百万级以上，且要求低延迟（<100ms）和高召回率（如客服场景需准确匹配用户问题），优先选HNSW。例如，电商客服的产品问答场景，HNSW能快速从百万级商品描述中找到最相关的内容。若数据量较小（如十万级），或需要频繁更新索引（如每日新增少量文档），则选IVFFlat，因为它构建索引快且内存占用低。需注意：HNSW的索引需全量加载到内存，若服务器内存不足，可能导致性能下降。

▎面试加分点
- 提到HNSW的参数调优（如ef_construction控制索引质量，ef_search控制检索速度）；
- 举例说明混合使用场景：对热点数据用HNSW，冷数据用IVFFlat；
- 提及pgvector的最新优化（如HNSW的并行构建支持）。

▎常见误区
- 盲目选择HNSW，忽略内存限制导致服务崩溃；
- 认为IVFFlat的召回率足够高，未测试数据量增长后的性能下降。

📌 概念题 · Q3

考点标签

Redis · Stream · 多Agent协同 · 难度：⭐⭐⭐

📝 题目
Redis Stream为什么适合作为多Agent协同的任务队列？相比List和Pub/Sub有什么优势？

💡 参考答案

▎一句话结论
Redis Stream是多Agent协同的理想任务队列，因为它支持可靠的消息投递、消费确认和历史消息回溯，解决了List和Pub/Sub的局限性。

▎核心原理
- 可靠投递：Stream通过消息ID和ACK机制确保消息不丢失；
- 消费组：支持多个Agent组成消费组，实现任务分片和负载均衡；
- 历史回溯：保留所有消息，允许Agent重新消费历史任务；
- 阻塞读取：支持阻塞式读取，减少轮询开销。

▎深入解释
List作为任务队列时，若Agent崩溃，未处理的消息会丢失（除非手动备份）；Pub/Sub是广播模式，消息无持久化，Agent离线则错过消息。而Stream解决了这些问题：例如，在多Agent的订单处理场景，Stream将订单任务存入队列，消费组中的Agent各自处理不同的任务，处理完成后发送ACK，确保任务不重复执行。若Agent崩溃，未ACK的消息会被重新分配给其他Agent。此外，Stream支持按时间范围查询历史消息，方便Agent回溯处理失败的任务。

▎面试加分点
- 提到Stream的PENDING列表（记录未ACK的消息）和CLAIM命令（重新分配未处理的消息）；
- 举例说明消费组的使用：将任务按用户ID分片，确保同一用户的任务由同一Agent处理；
- 对比Kafka：Stream更轻量，适合中小规模的Agent协同场景。

▎常见误区
- 认为Stream和List功能相同，忽略ACK机制和消费组的优势；
- 未设置消息过期时间，导致Stream无限增长占用内存。

📌 概念题 · Q4

考点标签

大模型 · 结构化输出 · 约束解码 · 难度：⭐⭐⭐

📝 题目
什么是约束解码？在大模型输出JSON时，约束解码相比纯Prompt方法有什么优势？常用的工具和实现方式有哪些？

💡 参考答案

▎一句话结论
约束解码是在大模型生成过程中实时过滤非法Token，强制输出符合指定格式（如JSON）的内容，相比纯Prompt方法更稳定、更可靠。

▎核心原理
- Token过滤：在生成每个Token时，仅保留符合目标格式的候选Token（如JSON的{、"、:等）；
- 语法校验：实时检查生成的内容是否符合语法规则（如括号匹配、引号闭合）；
- Schema约束：支持基于JSON Schema的字段级约束（如类型、枚举值）。

▎深入解释
纯Prompt方法依赖模型的“自觉性”，容易出现格式错误（如缺少括号、使用单引号）。约束解码从生成过程入手，杜绝非法Token。例如，使用Outlines工具时，定义JSON Schema后，模型只能生成符合Schema的Token，即使模型想输出非JSON内容也会被过滤。常用工具包括Outlines（Python库）、Guidance（微软开源）、Llama.cpp的--json参数等。这些工具通过修改模型的Token生成逻辑，确保输出格式正确。例如，在金融Agent生成交易报告时，约束解码能保证输出的JSON包含必填字段（如交易金额、时间）且格式合法。

▎面试加分点
- 提到约束解码与模型原生JSON输出（如OpenAI的response_format）的结合；
- 举例说明复杂Schema的约束（如嵌套JSON、枚举值限制）；
- 对比后处理方案：约束解码比后处理更高效，避免重复调用模型。

▎常见误区
- 认为约束解码会降低模型的生成质量，实际上它仅限制格式，不影响内容的相关性；
- 忽略约束解码的性能开销，对低延迟场景需权衡使用。

📌 概念题 · Q5

考点标签

Agentic RAG · 纠错反思 · 难度：⭐⭐⭐⭐

📝 题目
CRAG（Corrective RAG）或Self-RAG的核心原理是什么？它如何解决传统RAG的幻觉和检索噪声问题？

💡 参考答案

▎一句话结论
CRAG/Self-RAG是Agentic RAG的纠错机制，通过LLM自主评估检索结果和生成内容，迭代优化检索策略，解决传统RAG的幻觉和噪声问题。

▎核心原理
- 文档打分：LLM评估检索到的文档是否与问题相关，剔除噪声；
- 幻觉检测：检查生成的回答是否有检索内容支撑，避免无中生有；
- 回答完备性验证：判断回答是否完全解决用户问题，若不足则重写Query重新检索；
- 迭代优化：基于评估结果调整检索策略（如扩大检索范围、更换工具）。

▎深入解释
传统RAG的检索结果可能包含无关文档，导致模型生成幻觉。CRAG/Self-RAG引入“质检循环”：例如，用户问“公司2023年的营收增长情况”，传统RAG可能检索到2022年的文档，模型生成错误回答。而CRAG会先评估检索到的文档是否符合时间范围，若不符合则重新检索2023年的文档。此外，CRAG会检查生成的回答是否有文档支撑，若发现幻觉则重新生成。这种机制大幅提升了回答的准确性和可靠性，尤其适合对幻觉敏感的场景（如医疗、法律）。

▎面试加分点
- 提到CRAG的实现框架（如LangGraph的循环节点）；
- 举例说明多轮纠错：第一次检索结果不足，重写Query后再次检索；
- 对比传统RAG：CRAG的召回率和准确率提升30%以上（根据相关论文数据）。

▎常见误区
- 认为CRAG会增加延迟，忽略其对回答质量的提升价值；
- 未设置迭代次数上限，导致无限循环。

📌 概念题 · Q6

考点标签

Agent · 记忆系统 · 异步处理 · 难度：⭐⭐⭐

📝 题目
企业级Agent记忆系统中，异步刷新（Buffer-to-Storage）机制的核心作用是什么？记忆压缩与冲突合并的常见策略有哪些？

💡 参考答案

▎一句话结论
异步刷新机制解决了实时写入长期记忆的性能问题，记忆压缩与冲突合并则保证了长期记忆的有效性和一致性。

▎核心原理
- 异步刷新：将用户对话从主线程解耦，通过消息队列（如Kafka）由后台Worker异步提取结构化记忆并写入长期存储；
- 记忆压缩：对历史对话进行摘要或合并，减少存储占用；
- 冲突合并：处理用户前后不一致的信息（如“喜欢Python”→“主攻AI Agent”），通过冷热标签或时间戳更新记忆。

▎深入解释
实时写入长期记忆会增加用户对话的延迟，异步刷新通过消息队列将写入操作转移到后台，不影响用户体验。例如，用户与Agent的每轮对话先存入Redis短期记忆，后台Worker定期从Redis读取对话，提取用户偏好（如“喜欢咖啡”）并写入向量库。记忆压缩策略包括：对长对话进行摘要（保留关键信息）、合并重复内容（如用户多次提到同一偏好）。冲突合并策略包括：用最新信息覆盖旧信息（如用户更新偏好）、添加时间戳区分版本、设置冷热标签（最新信息标记为热，旧信息标记为冷）。

▎面试加分点
- 提到消息队列的重试机制（如Kafka的重试策略）确保记忆不丢失；
- 举例说明记忆压缩的工具（如轻量级模型生成摘要）；
- 提及冲突合并的规则引擎（如基于时间戳的优先级）。

▎常见误区
- 认为异步刷新会导致数据延迟，忽略其对性能的提升；
- 未处理记忆冲突，导致Agent使用过时信息。

📌 概念题 · Q7

考点标签

RAG · 混合检索 · 重排 · 难度：⭐⭐⭐

📝 题目
混合检索中，BM25稀疏检索、向量稠密检索和Rerank重排三者的组合逻辑是什么？各自的角色是什么？

💡 参考答案

▎一句话结论
混合检索通过BM25保证关键词匹配、向量检索保证语义相关性、Rerank重排优化结果顺序，三者结合提升检索的准确性和召回率。

▎核心原理
- BM25：基于关键词的稀疏检索，匹配用户Query中的精确词（如订单号、产品型号）；
- 向量检索：基于语义的稠密检索，匹配与Query语义相似的文档；
- Rerank：用重排模型（如BGE-Rerank）对前两者的结果进行重新排序，优先展示最相关的文档。

▎深入解释
纯向量检索可能无法匹配精确关键词（如用户问“订单号12345的状态”），纯BM25无法理解语义（如用户问“如何解决登录问题”与“登录失败怎么办”）。混合检索结合两者优势：首先用BM25和向量检索分别获取结果，然后合并结果，最后用Rerank模型根据语义相关性重新排序。例如，用户问“订单12345的物流状态”，BM25会找到包含“订单12345”的文档，向量检索会找到包含“物流状态”的文档，Rerank会将同时包含两者的文档排在前面。这种组合大幅提升了检索的召回率和精确率。

▎面试加分点
- 提到混合检索的权重调整（如αBM25 + (1-α)向量得分）；
- 举例说明Rerank模型的选择（如BGE-Rerank适合中文场景）；
- 对比纯向量检索：混合检索的召回率提升20%以上。

▎常见误区
- 忽略BM25的作用，认为向量检索足够；
- 未使用Rerank，导致结果顺序不合理。

📌 概念题 · Q8

考点标签

pgvector · 混合查询 · 难度：⭐⭐⭐

📝 题目
为什么pgvector的混合查询（业务字段过滤+向量相似度检索）在企业级RAG中具有优势？相比独立向量库+关系库的方案有什么好处？

💡 参考答案

▎一句话结论
pgvector的混合查询将关系型过滤和向量检索整合在同一SQL中，解决了跨库同步和分布式事务问题，提升了查询效率和数据一致性。

▎核心原理
- 单库整合：将业务数据（如文档权限、时间戳）和向量数据存储在同一PostgreSQL数据库中；
- SQL混合查询：用一条SQL同时进行业务字段过滤（如WHERE user_id=1）和向量相似度检索（如<->操作符）；
- ACID保证：数据更新时遵循ACID事务，确保业务数据和向量数据的一致性。

▎深入解释
独立向量库+关系库的方案需要跨库查询，存在数据同步延迟和分布式事务问题（如更新文档权限时，向量库和关系库可能不一致）。pgvector将两者整合在PostgreSQL中，例如，用户查询“我有权限查看的产品文档”，可以用一条SQL：SELECT * FROM docs WHERE user_id=1 AND vector <-> 'query_vector' < 0.5 ORDER BY vector <-> 'query_vector' LIMIT 10。这种方式避免了跨库调用，提升了查询速度，同时保证了数据一致性。此外，pgvector支持索引优化（如HNSW），进一步提升检索性能。

▎面试加分点
- 提到pgvector的索引与业务索引的结合（如联合索引）；
- 举例说明多租户场景：用tenant_id过滤向量数据，确保数据隔离；
- 对比独立向量库：pgvector减少了运维成本（无需维护两个数据库）。

▎常见误区
- 认为pgvector的向量检索性能不如专用向量库，忽略其混合查询的优势；
- 未优化SQL查询，导致混合查询速度慢。

📌 概念题 · Q9

考点标签

Redis · Pub/Sub · 多Agent · 难度：⭐⭐⭐

📝 题目
Redis Pub/Sub在多Agent系统中的核心应用场景是什么？它与Stream的区别是什么？适用哪些场景？

💡 参考答案

▎一句话结论
Redis Pub/Sub适合多Agent的实时消息通知场景，与Stream的区别在于是否持久化消息，Pub/Sub适用于无需历史消息的广播场景。

▎核心原理
- 广播模式：Pub/Sub允许Agent订阅主题，发布者发送消息后，所有订阅者都会收到；
- 无持久化：消息不存储，Agent离线则错过消息；
- 低延迟：消息实时传递，适合实时通知。

▎深入解释
多Agent系统中，Pub/Sub常用于实时状态通知（如Agent完成任务后通知其他Agent）、事件广播（如系统配置更新）。例如，当客服Agent处理完用户问题后，用Pub/Sub发布“任务完成”消息，监控Agent订阅该主题后实时更新统计数据。与Stream相比，Pub/Sub更轻量、延迟更低，但不支持消息持久化和消费确认。因此，Pub/Sub适用于不需要历史消息的场景（如实时通知），而Stream适用于需要可靠投递的任务队列场景。

▎面试加分点
- 提到Pub/Sub的频道模式（Channel）和模式订阅（Pattern）；
- 举例说明Pub/Sub的限流机制（如控制消息发送频率）；
- 对比Kafka：Pub/Sub更适合小规模、低延迟的通知场景。

▎常见误区
- 用Pub/Sub实现任务队列，忽略其无持久化的缺点；
- 未考虑Pub/Sub的消息丢失问题，导致Agent错过关键通知。

📌 概念题 · Q10

考点标签

大模型 · KV Cache · PagedAttention · 难度：⭐⭐⭐⭐

📝 题目
PagedAttention技术的核心原理是什么？它如何解决KV Cache的内存碎片化问题？相比传统KV Cache管理有什么优势？

💡 参考答案

▎一句话结论
PagedAttention是vLLM框架的核心优化技术，通过虚拟内存管理将KV Cache切分为固定大小的页，解决内存碎片化问题，提升显存利用率和并发吞吐量。

▎核心原理
- 页式管理：将连续的KV Cache切分为固定大小的页（如4KB），不连续存储在显存中；
- 虚拟地址映射：用虚拟地址映射物理页，避免内存碎片化；
- 按需加载：只加载当前需要的页，减少显存占用；
- 高效回收：当页不再使用时，及时回收显存空间。

▎深入解释
传统KV Cache管理中，每个请求的KV Cache是连续的，导致显存碎片化（如多个请求的KV Cache之间存在空闲空间）。PagedAttention模仿操作系统的虚拟内存机制，将KV Cache切分为页，每个请求的KV Cache由多个不连续的页组成。例如，当处理100个并发请求时，传统管理可能浪费50%的显存，而PagedAttention将显存利用率提升到96%以上。此外，PagedAttention支持动态扩展页，适应不同长度的上下文，大幅提升了大模型的并发吞吐量。

▎面试加分点
- 提到PagedAttention与MQA/GQA的结合（进一步减少KV Cache占用）；
- 举例说明vLLM的性能提升：相比传统框架，吞吐量提升10倍以上；
- 对比其他KV优化技术：PagedAttention在内存利用率和并发性能上优于KV量化和Context Cache。

▎常见误区
- 认为PagedAttention仅适用于vLLM，忽略其可移植到其他推理框架；
- 未考虑页大小的选择，导致性能下降（如页太小会增加管理开销）。

架构设计

场景标签

多租户客服Agent

📝 题目
请设计一个支持多租户的企业级客服Agent混合存储架构，要求满足以下核心需求：
1. 实时保存用户会话状态（高频读写、结构动态变化）；
2. 高效检索企业产品知识库（静态海量、语义相似度查询）；
3. 异步处理Agent任务（如工单派发、后续跟进）；
4. 实时推送Agent状态变更给前端（如任务完成通知）；
5. 严格的多租户数据隔离。
请说明技术选型理由及各模块的交互逻辑。

💡 参考答案

▎解题思路
1. 拆分需求类型：将动态高频的会话状态、任务队列与静态海量的知识检索分离；
2. 选择适配工具：用PostgreSQL处理事务性需求（会话、任务、通知），专用向量库处理知识检索；
3. 设计多租户隔离层：通过元数据标签实现数据隔离；
4. 定义数据流闭环：用户输入→会话加载→知识检索→LLM生成→状态持久化→任务分发→实时通知。

▎详细方案
- 会话状态存储：用PostgreSQL的JSONB类型存储Agent会话状态（如当前槽位、对话历史），配合GIN索引实现嵌套字段快速查询，通过tenant_id字段隔离租户数据；
- 长期知识检索：用Milvus存储企业产品手册的向量数据，每个向量附带tenant_id元数据，确保跨租户数据隔离；
- 任务队列：用PostgreSQL的SELECT ... FOR UPDATE SKIP LOCKED实现高并发任务队列，支持Agent异步处理工单、跟进等任务；
- 实时通知：利用PostgreSQL的LISTEN/NOTIFY机制，当Agent状态变更时（如任务完成），触发通知推送给前端；
- 数据流交互：用户输入→PG读取会话历史→Milvus检索相关知识→LLM生成回答→PG写入新会话→任务队列提交后续任务→实时通知前端更新。

▎关键细节 & 踩坑点
- PG的JSONB需创建GIN索引（如CREATE INDEX idx_session_state ON sessions USING GIN (state jsonb)），否则嵌套字段查询性能极差；
- Milvus的租户隔离必须在向量插入时就附带tenant_id元数据，避免检索时跨租户泄漏；
- SKIP LOCKED必须配合事务使用，否则会导致任务重复消费；
- LISTEN/NOTIFY需注意连接池的复用问题，避免连接断开后丢失通知。

▎可扩展优化
- 引入Redis作为会话缓存层，减轻PG的高频读压力；
- Milvus采用分片集群模式，支持海量知识的水平扩展；
- 任务队列增加优先级字段，实现紧急任务优先处理；
- 增加数据同步机制，定期将PG中的历史会话摘要同步到Milvus，支持长期会话的语义检索。

题型

场景分析

场景标签

客服Agent存储选型

📝 题目
某企业客服Agent需要处理两类核心数据：
1. 用户实时会话（动态变化、高频读写、结构不固定）；
2. 企业产品知识库（静态海量、需语义相似度检索）。
请对比“PostgreSQL+Milvus混合架构”与“单一专用向量库”两种方案的优缺点，并给出选型建议。

💡 参考答案

▎解题思路
1. 分析两类数据的特性：会话数据是动态事务型，知识数据是静态检索型；
2. 对比两种方案在性能、功能、运维成本上的差异；
3. 根据企业规模和业务需求给出选型建议。

▎详细方案
- 混合架构（PG+Milvus）：
优点：
- 各司其职：PG处理会话的事务性读写（JSONB支持动态结构），Milvus处理知识的高效向量检索；
- 强一致性：会话与任务数据在PG中保持ACID，避免跨库同步问题；
- 功能丰富：PG支持任务队列（SKIP LOCKED）、实时通知（LISTEN/NOTIFY）等企业级功能；
缺点：
- 运维成本高：需维护两个数据库系统；
- 跨库交互：需处理PG与Milvus之间的数据关联（如会话ID与知识ID的映射）。

  • 单一专用向量库：
    优点：
  • 部署简单：仅需维护一个向量库系统；
  • 统一检索：可同时处理会话和知识的向量检索；
    缺点：
  • 性能瓶颈：会话的高频动态更新会导致向量库的写入性能下降；
  • 功能缺失：缺乏事务支持、任务队列、实时通知等企业级功能；
  • 数据冗余：会话数据无需向量化存储，浪费资源。

▎关键细节 & 踩坑点
- 单一向量库方案中，会话数据的频繁更新会触发向量库的索引重构，导致检索性能骤降；
- 混合架构中，需确保PG与Milvus的tenant_id元数据一致，避免数据泄漏；
- 向量库的事务支持较弱，不适合存储需要强一致性的会话状态。

▎可扩展优化
- 小型企业（知识量<100万条、会话并发<100QPS）可选择单一向量库方案，降低运维成本；
- 中型以上企业（知识量>100万条、会话并发>100QPS）必须选择混合架构，保证性能和功能完整性；
- 混合架构可引入ETL工具（如Airflow）实现PG与Milvus的数据同步，减少跨库交互复杂度。

工程实现

场景标签

PostgreSQL任务队列

📝 题目
请用PostgreSQL的SELECT ... FOR UPDATE SKIP LOCKED实现一个高并发的Agent任务队列，要求支持：
1. 任务提交；
2. 多Worker并发消费；
3. 任务状态流转（待处理→处理中→完成/失败）；
4. 异常重试机制。
请写出表结构设计和核心伪代码，并说明关键实现细节。

💡 参考答案

▎解题思路
1. 设计任务表结构，包含状态、优先级、重试次数等字段；
2. 实现任务提交逻辑（INSERT）；
3. 实现Worker消费逻辑（SELECT ... FOR UPDATE SKIP LOCKED）；
4. 实现任务状态更新和异常重试逻辑。

▎详细方案
- 表结构设计：
sql CREATE TABLE agent_tasks ( id SERIAL PRIMARY KEY, tenant_id VARCHAR(64) NOT NULL, task_type VARCHAR(32) NOT NULL, -- 如"ticket_create" status VARCHAR(16) NOT NULL DEFAULT 'pending', -- pending/processing/completed/failed payload JSONB NOT NULL, -- 任务参数（如用户ID、工单内容） priority INT NOT NULL DEFAULT 0, -- 0=低，1=中，2=高 retry_count INT NOT NULL DEFAULT 0, max_retries INT NOT NULL DEFAULT 3, created_at TIMESTAMP NOT NULL DEFAULT NOW(), updated_at TIMESTAMP NOT NULL DEFAULT NOW() ); -- 索引优化 CREATE INDEX idx_agent_tasks_status_priority ON agent_tasks(status, priority DESC); CREATE INDEX idx_agent_tasks_tenant_id ON agent_tasks(tenant_id);

  • 任务提交伪代码：
    python def submit_task(tenant_id: str, task_type: str, payload: dict, priority: int = 0): with pg_conn.cursor() as cur: cur.execute(""" INSERT INTO agent_tasks (tenant_id, task_type, payload, priority) VALUES (%s, %s, %s, %s) RETURNING id; """, (tenant_id, task_type, payload, priority)) task_id = cur.fetchone()[0] pg_conn.commit() return task_id

  • Worker消费伪代码：
    python def worker_loop(): while True: with pg_conn.cursor() as cur: # 锁定待处理的高优先级任务 cur.execute(""" SELECT id, payload FROM agent_tasks WHERE status = 'pending' ORDER BY priority DESC, created_at ASC LIMIT 1 FOR UPDATE SKIP LOCKED; """) task = cur.fetchone() if not task: time.sleep(1) continue task_id, payload = task # 更新状态为处理中 cur.execute(""" UPDATE agent_tasks SET status = 'processing', updated_at = NOW() WHERE id = %s; """, (task_id,)) pg_conn.commit() try: # 执行任务逻辑 execute_task(payload) # 任务完成 with pg_conn.cursor() as cur: cur.execute(""" UPDATE agent_tasks SET status = 'completed', updated_at = NOW() WHERE id = %s; """, (task_id,)) pg_conn.commit() except Exception as e: # 异常重试 with pg_conn.cursor() as cur: cur.execute(""" UPDATE agent_tasks SET status = CASE WHEN retry_count < max_retries THEN 'pending' ELSE 'failed' END, retry_count = retry_count + 1, updated_at = NOW() WHERE id = %s; """, (task_id,)) pg_conn.commit() time.sleep(0.1)

▎关键细节 & 踩坑点
- FOR UPDATE SKIP LOCKED必须配合事务使用，否则锁会立即释放；
- 任务状态流转必须原子化，避免出现中间状态；
- 重试次数需限制，防止死循环；
- 索引设计需覆盖查询条件（status、priority、created_at），否则消费性能会下降。

▎可扩展优化
- 增加任务超时机制：定期扫描处理中超过阈值的任务，重置为待处理；
- 支持任务优先级调整：允许动态修改任务优先级；
- 引入死信队列：将失败超过最大重试次数的任务转移到死信队列，人工处理；
- 批量消费：一次锁定多个任务，提高Worker效率。

题型

排障优化

场景标签

Redis会话丢失

📝 题目
某企业客服Agent使用Redis存储用户会话历史（List结构），近期用户反馈“刚聊几句就被清空会话”，请分析可能的原因并给出优化方案。

💡 参考答案

▎解题思路
1. 检查Redis的过期策略设置；
2. 检查内存淘汰机制；
3. 检查并发写冲突；
4. 检查会话存储逻辑是否正确。

▎详细方案
- 可能原因分析：
1. 过期时间过短：会话List的EXPIRE设置过短（如5分钟），用户未及时交互导致会话被删除；
2. 内存淘汰机制触发：Redis内存达到maxmemory，采用了volatile-lru或allkeys-lru策略，会话List被优先淘汰；
3. 并发写冲突：多个进程同时修改会话List，导致数据丢失；
4. 存储逻辑错误：会话更新时未正确延续过期时间（如每次追加会话后未重新设置EXPIRE）。

  • 优化方案：
    1. 调整过期时间：将会话过期时间设置为合理值（如30分钟），并在每次用户交互时重新设置EXPIRE；
    2. 优化内存淘汰策略：采用volatile-ttl策略，优先淘汰即将过期的会话；或增加Redis内存容量；
    3. 原子化操作：使用Redis的原子命令（如LPUSH+EXPIRE的组合，或Lua脚本）确保会话更新和过期时间设置的原子性；
    4. 会话备份：定期将Redis中的会话同步到PostgreSQL，避免数据丢失。

▎关键细节 & 踩坑点
- Redis的EXPIRE命令是针对Key的，List结构的每个元素不会单独过期，需确保整个Key的过期时间正确；
- 并发场景下，使用Lua脚本执行多个命令（如LPUSH+EXPIRE），避免中间状态；
- 内存淘汰机制需根据业务需求选择，noeviction策略会导致写失败，不适合生产环境；
- 会话备份需采用异步方式（如Kafka+Worker），避免影响主业务性能。

▎可扩展优化
- 引入多级缓存：本地内存缓存+Redis+PG，提高会话读取性能并降低Redis压力；
- 会话分片：根据用户ID哈希分片到不同的Redis节点，避免单节点内存瓶颈；
- 实时监控：使用Prometheus+Grafana监控Redis的内存使用、过期Key数量，及时发现问题；
- 会话压缩：对会话内容进行Gzip压缩，减少Redis内存占用。
