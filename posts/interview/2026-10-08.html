📌 概念题 · Q1

考点标签

Skill 模块化 · 难度：⭐⭐⭐

📝 题目

知识库中提到工业级 Agent 落地时要把不同能力拆分为独立的 .skills 配置文件，而不是把所有 Prompt、工具都堆到主 Agent 里。请解释：Skill 和 Tool 的核心区别是什么？为什么说 Skill 拆分是 Agent 从 Demo 走向商用的必经之路？

💡 参考答案

▎一句话结论

Tool 是无灵魂的原子代码函数，Skill 是封装了专属 Prompt、行为边界、绑定工具集的独立能力单元，Skill 模块化是解决大模型上下文污染、实现系统解耦的核心工程手段。

▎核心原理

  • Tool 本质是可被调用的函数接口（如查数据库、发验证码），只负责执行具体动作，不包含任何业务逻辑和人设设定
  • Skill 是一个完整的能力包，包含三要素：专属局部 System Prompt、绑定的可用工具列表、明确的输入输出契约
  • 主 Agent 只负责做路由分发，不承载具体业务逻辑，激活对应 Skill 时才动态拼接 Prompt 和挂载工具

▎深入解释

很多开发者做 Demo 时习惯把所有规则、人设、工具全写在一个几千字的主 Prompt 里，比如做智能客服时，同时把“查公积金规则”“处理退款”“安抚投诉用户”的要求全塞进去，结果大模型经常出现指令冲突：用户明明来投诉，它却生硬地念政策条款。而 Skill 机制就像公司的“专家坐席矩阵”：前台（主 Agent）只负责判断用户需求，然后把电话转接给对应专家——处理投诉的专家自带“先情绪安抚”的 SOP，手里只有送积分、查客诉记录的工具，根本看不到退款接口，从物理层面避免了越权和逻辑混乱。这种模式下，哪个环节效果不好，直接修改对应 Skill 的 Prompt 即可，不用动整个系统的核心逻辑。

▎面试加分点

  • 能提到 Skill 的动态加载机制：运行时才把 Skill 的 Prompt 和工具注入上下文，平时不占用主 Agent 的 Context Window，大幅节省 Token 成本
  • 能结合场景举例：比如自媒体系统拆分热点分析、脚本生成、合规发布三个 Skill，客服系统拆分政策解答、订单操作、客诉安抚三个 Skill，实现流水线式协作

▎常见误区

  • 误区：认为 Skill 就是 Prompt 模板的拆分。实际上 Skill 是包含权限边界（绑定工具）、输入输出校验、行为SOP的完整运行单元，比单纯的 Prompt 拆分粒度更粗、隔离性更强。

📌 概念题 · Q2

考点标签

Agent与Workflow边界 · 难度：⭐⭐

📝 题目

知识库中提到“Workflow 框定下限，Agent 提升上限”，当前工业界主流落地形态是 Agentic Workflow（智能体工作流），而不是完全自主的纯 Agent。请解释 Workflow 和纯 Agent 的核心差异是什么？为什么企业落地很少用完全自动驾驶的纯 Agent？

💡 参考答案

▎一句话结论

Workflow 是固定路径的确定性执行流，纯 Agent 是完全自主决策的动态执行流，Agentic Workflow 是“固定流程骨架 + 节点内大模型自主决策”的折中方案，是当前企业级落地的最优解。

▎核心原理

  • Workflow（传统工作流）：所有执行路径、分支条件都是预先硬编码的，就像流水线，输入确定则输出100%确定，没有任何自主决策空间
  • 纯 Agent：基于 ReAct 思想，完全由大模型自己观察、思考、调用工具、决定下一步走向，没有预先设定的固定路径，理论上可以处理任意开放场景
  • Agentic Workflow：核心流程节点和流转规则由图结构（如LangGraph状态机）固定，每个节点内部可以用 Agent 的自主能力处理非结构化输入，既保证流程可控，又保留大模型的灵活性。

▎深入解释

很多刚接触 Agent 的开发者会陷入两个极端：要么觉得“大模型足够聪明，让它自己干就行”，结果上线后发现 Agent 经常在工具调用里死循环，或者跳过必要的合规校验直接给用户退款，完全不可控；要么觉得“大模型不可靠，所有路径都写死”，结果变成了传统的规则引擎，稍微超出规则的问题就无法处理，完全体现不出 AI 的价值。Agentic Workflow 就像“带导航的自动驾驶”：整体路线（必须先校验身份、再查订单、最后退款）是系统预先定死的，绝对不会跑偏，但在具体路段（怎么理解用户的方言表述、怎么把退款规则用自然语言讲清楚）交给大模型灵活处理。这种模式下，系统的最差结果是被流程卡住转人工，不会出现越权操作、死循环烧 Token 等恶性故障，把大模型的不确定性锁死在单个节点内。

▎面试加分点

  • 能给出具体场景的边界划分：比如智能客服中“身份校验→问题分类→结果生成→人工审核”是固定Workflow，而“结果生成”节点内部用Agent理解用户情绪、组织回答话术
  • 能提到成本差异：纯Agent因为需要反复思考、调用工具，单次请求Token成本是固定Workflow的3-10倍，且延迟不可控，完全无法支撑高并发场景。

▎常见误区

  • 误区：认为Agentic Workflow是技术上的妥协，是“不够智能”的表现。实际上这是工业界的主动选择——企业系统首先要求可控、可审计、成本可预估，纯Agent的“自主性”在生产环境中恰恰是最大的风险源。

📌 概念题 · Q3

考点标签

PTQ与QAT量化路径 · 难度：⭐⭐⭐

📝 题目

大模型量化分为 PTQ（训练后量化）和 QAT（量化感知训练）两大核心路径，知识库中提到普通开源模型部署优先选社区现成的 AWQ/GPTQ 量化包，只有特殊场景才考虑QAT。请解释这两种量化路径的核心原理差异，以及各自的适用场景？

💡 参考答案

▎一句话结论

PTQ是模型训练完成后用少量校准集直接计算量化参数，成本极低、精度损失可控，是企业部署的首选；QAT是在训练过程中模拟量化误差，精度最高但训练成本极高，仅适用于对精度要求极致的极低比特量化场景。

▎核心原理

  • PTQ核心逻辑：不需要修改模型训练过程，拿少量有代表性的样本（校准集）跑一遍前向传播，统计权重和激活值的分布，计算出最优的缩放因子S和零点Z，把浮点数映射到低比特整数
  • 现代PTQ（AWQ/GPTQ）的优化点：识别出权重中1%左右的关键离群值，对这部分权重保留浮点精度，剩下99%的普通权重量化到INT4/INT8，把精度损失控制在1%~2%以内
  • QAT核心逻辑：在训练图中插入伪量化节点，前向传播时模拟低比特的截断误差，反向传播时仍然用浮点数更新梯度，让模型在训练过程中主动适应量化带来的精度损失，最终量化后的精度最接近原模型。

▎深入解释

很多人会觉得“QAT精度更高，所以应该优先用QAT”，这是完全脱离工程实际的想法。对于大部分企业来说，用开源模型做部署，根本没有足够的算力和高质量数据集去做QAT——70B模型做一次QAT需要几十张A100跑几天，成本几十万，而直接下载社区做好的AWQ量化包，只需要几分钟，精度损失几乎感知不到。AWQ/GPTQ这类现代PTQ算法已经把INT4量化的精度损失做到了普通人完全无法区分的程度，完全能满足95%以上的企业场景需求。QAT只有在两种场景下才值得投入：一是做端侧部署的INT2甚至更低比特量化，PTQ已经无法hold住精度损失；二是对推理精度要求极高的场景（如金融计算、医疗诊断），愿意付出极高的训练成本换那1%~2%的精度提升。

▎面试加分点

  • 能解释为什么离群点是量化的核心难点：如果为了覆盖极少数极高/极低的离群值把缩放范围拉大，会导致占99%的中间密集区域的量化步长变大，大量微小细节被抹平，这也是早期PTQ在INT4下精度崩塌的核心原因
  • 能提到量化的收益不仅是省显存：INT8/INT4的整数运算吞吐量是FP32的4~8倍，且内存带宽需求大幅降低，能同时缓解大模型推理的Compute Bound和Memory Bound两大瓶颈。

▎常见误区

  • 误区：认为量化一定会严重损失模型效果。实际上对于7B以上的大模型，INT8量化几乎没有可感知的效果损失，INT4 AWQ/GPTQ量化的效果损失也在绝大多数场景的可接受范围内，远小于换一个更小参数模型的损失。

📌 概念题 · Q4

考点标签

智能销售系统架构 · 难度：⭐⭐⭐⭐

📝 题目

知识库中提到智能销售客服的核心架构是“多轮意图深挖+脱敏案例查询+数据飞轮中台”，而不是简单的RAG问答机器人。请解释这套架构的四层核心逻辑是什么？为什么说单纯的问答机器人做不了高转化的销售？

💡 参考答案

▎一句话结论

高转化智能销售不是“用户问什么答什么”的问答机器人，而是以状态机驱动多轮信息收集、以真实脱敏案例做信任背书、以数据中台实现持续迭代的完整业务系统，最终目标是引导成交而不是回答问题。

▎核心原理

  • 第一层：显式状态机做意图深挖，通过Slot Filling（槽位填充）机制，必须收集齐预算、痛点、团队规模、期望上线时间四个核心信息，才会进入方案推荐环节，不会用户一上来问价格就直接报价
  • 第二层：工具调用对接企业真实业务数据库，根据客户的行业、规模标签匹配同类型成功案例，通过数据脱敏网关隐去敏感信息后，再交给大模型润色成有说服力的话术，杜绝大模型编造案例
  • 第三层：数据中台做飞轮迭代，自动清洗全量对话语料，标注成成功/失败案例，一方面更新RAG知识库，另一方面生成模型微调的黄金数据集
  • 第四层：数据价值外延，基于沉淀的对话数据衍生销售培训AI教练、竞品分析BI、流失客户精准再营销等周边业务，实现数据价值最大化。

▎深入解释

很多团队做的智能销售客服本质是“知识库问答机器人”：把产品文档灌进向量库，用户问什么就搜什么回答，这种系统转化率极低——因为真实销售场景中，客户第一次说的需求往往是伪需求，比如上来就问“你们系统多少钱”，实际上他可能连自己要解决什么问题都没想清楚，直接报价大概率会把客户吓跑。真正的销售是一个引导过程：先通过多轮对话把客户的真实痛点挖出来，然后拿出同行业的真实案例建立信任，最后才给出针对性的方案。而数据中台的存在让整个系统越用越聪明：上个月销冠怎么搞定同类客户的，下个月所有AI销售都能学会这个话术；客户普遍因为什么原因流失，产品部门可以针对性迭代功能，这是单纯的问答机器人完全不具备的能力。

▎面试加分点

  • 能提到脱敏层的必要性：绝对不能让大模型直接读取数据库里的原始客户数据，必须经过脱敏网关把真实公司名、联系人、金额替换成模糊表述，否则会引发严重的数据合规风险
  • 能算清商业账：这套系统的价值不只是替代人工客服，沉淀的对话数据是企业的核心资产，衍生的销售培训、BI分析等业务带来的价值甚至超过智能客服本身。

▎常见误区

  • 误区：认为销售客服的核心是大模型“会说话”。实际上高转化的核心是真实的案例数据和流程设计，大模型只是把结构化的数据用自然人性的方式表达出来，没有底层真实数据支撑，再会说的话术都是空的。

📌 概念题 · Q5

考点标签

LightRAG架构设计 · 难度：⭐⭐⭐

📝 题目

知识库中提到原生Graph RAG存在构建成本高、关系错误无修复机会等缺陷，因此衍生出了LightRAG框架。请解释原生Graph RAG的核心缺陷是什么？LightRAG相比原生方案做了哪些核心改进？

💡 参考答案

▎一句话结论

原生Graph RAG依赖全局社区发现和摘要，构建成本极高且错误传导不可逆，LightRAG通过双层查询、原图溯源、去重融合的设计，在保留图结构关联能力的同时，把构建成本和幻觉风险降到了可落地的水平。

▎核心原理

  • 原生Graph RAG的核心流程：先从全量文档中抽取实体和关系构建有向图，再用Leiden算法做社区发现，让LLM为每个社区生成全局摘要，查询时本地问题查实体关联、全局问题直接用社区摘要回答
  • 原生方案三大缺陷：一是社区摘要生成极其消耗Token，构建成本是普通RAG的几十倍；二是实体关系抽取如果出错，后续社区摘要会基于错误关系生成，错误层层传导没有修复机会；三是社区摘要本身是LLM生成的，存在二次幻觉风险
  • LightRAG的核心改进：一是不再提前做全局社区摘要，只做实体和关系的向量化，构建成本大幅降低；二是查询时同时生成high-level（抽象主题）和low-level（核心关键词）两路检索，既覆盖局部实体关联，又覆盖全局主题关系；三是检索到实体和关系后，直接通过ID关联回原始文本块，把原文内容喂给LLM生成答案，而不是依赖提前生成的摘要。

▎深入解释

原生Graph RAG刚出来的时候很多团队跟风尝试，结果发现处理1000份文档就要花掉几百块钱的Token成本，而且只要一开始实体抽错了（比如把“刘备”和“刘秀”当成兄弟），后面整个社区的摘要全错，根本没法用在生产环境。LightRAG的思路其实非常务实：它没有追求数学上完美的图社区划分，而是把图结构当成一个高级的“索引层”——图里的实体和关系只是用来做关联跳转，最终回答问题的依据还是原始文档，这就从根源上避免了摘要带来的二次幻觉。而且它在查询时同时做关键词精确匹配、主题语义匹配、原文兜底匹配，三路结果去重后再生成答案，既保留了Graph RAG擅长处理实体关联、全局问题的优势，又把构建成本降到了和普通RAG差不多的水平。

▎面试加分点

  • 能对比适用场景：原生Graph RAG适合对全局推理要求极高、文档量不大的场景（如小说人物关系分析、复杂案件卷宗梳理），LightRAG适合企业级大规模知识库场景，在成本、效果、速度上做到了更好的平衡
  • 能提到LightRAG的native查询通道：当图检索没有命中相关内容时，直接降级为传统的向量检索原文，不会出现Graph RAG常见的“图里没连到就回答不知道”的问题。

▎常见误区

  • 误区：认为LightRAG是比原生Graph RAG“更高级”的方案。实际上两者是不同场景下的设计取舍，LightRAG牺牲了一部分全局社区推理的精度，换来了构建成本的大幅降低和幻觉风险的可控，是面向工程落地的优化版本。

📌 概念题 · Q6

考点标签

显存容量规划 · 难度：⭐⭐⭐

📝 题目

很多企业采购GPU服务器时只看模型文件大小选显存，结果上线后频繁出现OOM（显存溢出）。知识库中提到“大模型运行时显存占用 ≥ 模型包体积 + KV Cache消耗”。请解释：为什么不能只按模型大小算显存？企业做显存规划时的核心原则是什么？

💡 参考答案

▎一句话结论

模型加载进显存只是基础开销，真正决定并发上限的是KV Cache占用，显存规划必须预留至少1/3~1/2的空间给KV Cache和运行时开销，否则即使能加载模型，也无法支撑多用户并发访问。

▎核心原理

  • 模型包体积是固定开销：不管多少用户访问，模型权重加载到显存后是常驻的，这部分占用和量化精度直接相关——INT4下1B参数约占0.5G，FP16下1B参数约占2G
  • KV Cache是动态开销：每个用户请求在生成Token的过程中，都会缓存前面所有Token的Key和Value矩阵，上下文越长、并发数越高，KV Cache占用的显存就越大，这部分是弹性的
  • 其他运行时开销：包括CUDA上下文、中间激活值、显存碎片等，通常会额外占用1~2G显存。

▎深入解释

举个最典型的反例：很多人觉得“14B INT4模型只有9G，我买张12G的4070显卡就能跑”，结果加载完模型确实能启动，但是只要有2~3个用户同时访问，或者用户的上下文长度超过4K，立刻就OOM崩溃——因为剩下的3G显存根本不够放KV Cache。这也是为什么知识库推荐单张24G显卡跑14B INT4模型：9G模型加载完后，剩下15G显存全部留给KV Cache，足够支撑10~20个用户同时用8K上下文访问，服务非常稳定。对于70B模型也是一样：INT4量化后约40G，两张24G4090加起来48G显存，剩下8G给KV Cache，足够支撑小团队内部使用；但如果要支撑高并发长上下文，就必须用显存更大的H200等专业卡。很多团队踩坑就是因为只算模型大小，完全没给KV Cache留空间，结果上线后单用户能跑，多用户就崩。

▎面试加分点

  • 能给出具体的估算公式：KV Cache显存占用 ≈ 2 * 层数 * 隐层维度 * 序列长度 * 批大小 * 精度字节数，比如7B模型8K上下文下，单用户KV Cache约占0.5G，10个并发就占5G
  • 能提到vLLM的PagedAttention技术就是为了解决KV Cache的显存浪费问题，通过类似操作系统虚拟内存的分页机制，把KV Cache的显存利用率从20%~40%提升到90%以上，同样的显存能支撑更高并发。

▎常见误区

  • 误区：认为“模型量化后推理速度变快，所以KV Cache占用也会变少”。实际上KV Cache的精度可以和模型权重精度不一样，很多部署框架为了保证效果，KV Cache仍然会用FP16存储，这部分开销不会因为权重量化而成比例减少。

考点标签

企业部署避坑指南 · 难度：⭐⭐⭐

📝 题目

知识库中反复强调企业本地部署大模型要“切忌算力焦虑”“重数据轻模型”“注意基础设施配套”三大避坑原则。请结合实际落地场景，解释这三个原则的具体含义，为什么很多企业花了大价钱买硬件却做不出效果？

💡 参考答案

▎一句话结论

企业大模型落地的核心瓶颈从来不是硬件不够好，而是业务场景没跑通、数据质量差、基础设施不配套，盲目堆硬件大概率会成为成本黑洞，必须从最小场景验证开始逐步迭代。

▎核心原理

  • 切忌算力焦虑：不要一上来就采购8卡B200这类顶级硬件，应该先用几万块钱的双卡4090跑通1~2个最高频的痛点业务（如HR文档检索、内部客服），验证ROI之后再根据业务需求升级硬件
  • 重数据轻模型：本地部署的核心优势是企业私有数据，把80%的精力花在清洗内部乱码文档、做好文本切片、构建高质量知识库上，带来的效果提升远比把模型从32B升级到70B要明显
  • 注意基础设施配套：顶级AI服务器的功耗、散热要求极高，8卡B200单机功耗接近15kW，很多企业机房的供电、空调根本带不动，买了服务器也没法开机运行。

▎深入解释

很多企业做AI建设的思路是“先买最贵的硬件，再想做什么场景”，结果花几百万买了服务器，最后发现内部的文档全是扫描件、乱码Excel，连高质量的训练/检索数据都没有，大模型跑起来回答问题全是错的，硬件利用率常年不到10%，变成了摆设。实际上大模型落地是一个渐进的过程：先用低成本硬件跑通最小场景，比如先给客服部门做一个知识库问答机器人，真的能帮客服减少30%的重复工作量，证明了价值，再逐步扩展到其他部门，再升级硬件。而且很多企业完全忽略机房配套：普通机柜的供电通常只有4~6kW，根本带不动15kW的AI服务器，还要额外投入几十万做电力扩容、液冷改造，这些隐形成本很多企业采购时根本没考虑到，最后设备到了装不上，白白浪费钱。

▎面试加分点

  • 能给出具体的ROI测算：双卡4090方案硬件成本仅5~8万，只要能替代2~3个客服的重复工作量，半年就能收回成本；而百万级的B200集群，除非有每天几亿Token的稳定调用需求，否则18个月的回本周期根本跑不通
  • 能提到数据清洗的具体价值：同样是32B模型，用清洗干净、切片合理的知识库，回答准确率能从60%提升到90%以上，而换70B模型如果数据还是垃圾，准确率可能只能提升到65%，性价比极低。

▎常见误区

  • 误区：认为“模型参数越大效果越好，所以一定要上最大的模型”。实际上企业内部场景大部分是知识检索、流程处理这类任务，14B/32B的量化模型完全能胜任，盲目上大模型只会带来更高的推理成本和更长的延迟，用户体验反而更差。

📌 概念题 · Q8

考点标签

LLM网关高并发设计 · 难度：⭐⭐⭐⭐

📝 题目

企业级大模型服务在几百人并发使用时，经常出现显存溢出、首字延迟过长的问题。知识库中提到要在LLM网关层部署语义缓存、开启动态批处理来提升并发能力。请解释这两个技术的核心原理，为什么它们比单纯堆GPU更有效？

💡 参考答案

▎一句话结论

语义缓存通过复用相似问题的结果跳过GPU计算，动态批处理通过Token级别的请求拼装提升GPU利用率，两者是低成本提升大模型服务并发能力的核心手段，效率提升远高于单纯堆硬件。

▎核心原理

  • 语义缓存核心原理：在网关层对用户请求做Embedding，和缓存库中的历史请求做向量相似度匹配，如果相似度超过阈值（如0.95），直接返回缓存的回答，不需要把请求发给GPU做推理，实现0Token成本、毫秒级响应
  • 动态批处理（Continuous Batching）核心原理：传统批处理是等一批请求凑齐了再一起推理，批次内先生成完的请求必须等最慢的那个请求完成才能返回，GPU利用率极低；动态批处理是在Token级别做调度，某个请求生成完一个Token，立刻把下一个等待的请求塞进去，不需要等整个批次完成，GPU利用率能从20%~30%提升到80%以上
  • 两者都是从“减少无效计算”“提升资源利用率”的角度优化，不需要额外增加硬件成本，就能把并发能力提升3~10倍。

▎深入解释

很多团队遇到并发问题的第一反应是“GPU不够，再买几张卡”，但实际上大模型推理的GPU利用率天然极低——企业内部场景中，至少30%~40%的问题是重复或高度相似的（比如“怎么请年假”“公积金怎么提取”这类高频问题），如果每个请求都跑一次GPU，完全是浪费算力。语义缓存就像公司的“常见问题手册”，同样的问题不用再去问专家，直接给标准答案就行，这部分请求根本不占GPU资源。而动态批处理解决的是大模型推理的“木桶效应”：传统批处理模式下，一个批次里如果有一个请求要生成1000个Token，其他请求只生成10个Token，那10个Token的请求也要等很久才能拿到结果，GPU大量时间在空等；动态批处理就像灵活的公交车，座位空了就立刻上客，不会等所有人都到终点再上下客，把GPU的算力吃满。这两个优化手段加上之后，同样的硬件能支撑的并发量能翻好几倍，比买新卡划算得多。

▎面试加分点

  • 能提到语义缓存的适用边界：对于事实性、答案固定的问题（如政策咨询、流程问答）缓存效果极好，对于需要实时数据、个性化回答的问题（如查个人订单、实时数据分析）不能缓存，需要做缓存Key的路由区分
  • 能对比动态批处理和静态批处理的指标差异：静态批处理的GPU利用率通常在30%以下，首字延迟（TTFT）随批次增大而飙升；动态批处理能在保持高GPU利用率的同时，把TTFT控制在几百毫秒的可接受范围内。

▎常见误区

  • 误区：认为语义缓存就是传统的Redis字符串匹配缓存。实际上语义缓存是基于向量相似度的模糊匹配，“2025年公积金怎么取”和“去年的公积金提取流程是什么”这两个表述完全不同的问题，也能命中同一个缓存，这是传统字符串缓存做不到的。

📌 概念题 · Q9

考点标签

Docker镜像打包策略 · 难度：⭐⭐⭐

📝 题目

在LangGraph多Agent系统的容器化部署中，知识库推荐使用多Dockerfile方案，为不同角色的Agent构建独立镜像，而不是把所有依赖打在一个大镜像里。请解释：为什么要做镜像拆分？什么场景下适合用单一镜像+变参启动的方案？

💡 参考答案

▎一句话结论

多Dockerfile方案通过依赖隔离实现镜像轻量化，大幅提升K8s弹性伸缩时的容器拉取速度，是异构Agent部署的首选；单一镜像方案仅适用于各Agent依赖差异极小的场景，维护成本更低但灵活性差。

▎核心原理

  • 多Dockerfile方案的核心逻辑：在同一个代码仓库下，为不同角色的Agent编写独立的Dockerfile——轻量级路由Agent用slim基础镜像，只装基础依赖，镜像大小可能只有几百MB；数据分析、本地推理的Agent用CUDA基础镜像，装torch、pandas等重型依赖，镜像大小几个G，互不影响
  • 多Dockerfile的核心优势：弹性伸缩时，轻量级路由Agent的镜像可以秒级拉取启动，不需要每次都拉取包含CUDA、PyTorch的几个G的大镜像，大幅提升扩容速度，减少冷启动时间
  • 单一镜像+变参启动的逻辑：所有Agent用同一个Dockerfile打包，部署时通过K8s的args参数覆盖启动命令，运行不同的服务入口，只需要维护一个镜像构建流程，适合所有Agent依赖基本一致的场景。

▎深入解释

很多开发者图省事，把所有Python依赖全装在一个镜像里，结果一个镜像动辄5~6G，在K8s弹性扩容的时候，拉取镜像就要花几分钟，突发流量过来的时候根本来不及扩容，服务直接雪崩。而且CPU节点根本不需要CUDA和PyTorch依赖，把这些装进去不仅浪费镜像仓库空间，还会增加潜在的安全漏洞。多Dockerfile方案就像“不同岗位的工服”：前台接待不需要穿重型防护服，一线工人不需要穿西装，各自带自己需要的装备就行，轻装上阵才能跑得快。当然，如果你的系统里所有Agent都是纯逻辑处理，没有重型GPU依赖，所有服务的依赖列表完全一样，那用单一镜像也没问题——只需要构建一次，部署时传不同的启动参数就行，维护成本更低。但只要有一个Agent需要装重型依赖，就必须做镜像拆分，否则整个系统的冷启动速度会被拖垮。

▎面试加分点

  • 能提到解耦的核心是服务化：不管用哪种镜像方案，最终都要把每个Agent节点通过FastAPI/gRPC封装成独立的网络服务，通过K8s Service通信，而不是在同一个进程内调用，这才是分布式多Agent架构的核心
  • 能给出具体的镜像大小对比：纯路由Agent的slim镜像通常只有300~500MB，而带CUDA和PyTorch的数据Agent镜像通常在3~5G，两者的拉取速度差10倍以上，在Serverless场景下冷启动体验差异极大。

▎常见误区

  • 误区：认为多Dockerfile需要维护多个代码仓库。实际上完全可以在同一个Monorepo仓库里管理多个Dockerfile，CI/CD流程中通过docker build -f参数指定不同的Dockerfile构建即可，代码还是一份，只是打包方式不同。

📌 概念题 · Q10

考点标签

RAG与微调选型 · 难度：⭐⭐⭐

📝 题目

知识库中提到企业知识接入要遵循“90%场景优先用RAG，10%场景才用LoRA微调”的原则。请解释：为什么RAG是企业知识接入的首选？什么场景下才值得投入成本做微调？

💡 参考答案

▎一句话结论

RAG具备知识实时更新、成本低、可溯源、无幻觉的优势，能满足绝大多数企业知识问答需求；微调仅适用于需要改变模型输出风格、格式习惯或固化行业黑话的场景，不能用来解决知识更新问题。

▎核心原理

  • RAG的核心优势：知识存储在外部向量数据库里，更新知识只需要增删数据库里的文档，秒级生效，不需要重新训练模型；回答时可以溯源到原始文档片段，方便审核校验，幻觉率极低；构建成本极低，普通工程师花几天就能搭起来
  • 微调的核心局限：知识是固化在模型权重里的，更新知识需要重新用数据集训练，一次训练成本几万到几十万，周期长达几天到几周；微调后的模型无法溯源回答依据，仍然可能出现幻觉，且知识更新不灵活
  • 微调的不可替代场景：一是需要模型稳定输出特定格式（如固定结构的JSON报告、符合企业规范的公文格式），Prompt约束无法100%保证格式稳定；二是需要模型学习独特的说话风格或行业黑话（如企业内部的专属术语、特定的客服话术风格）；三是需要模型掌握极其复杂的推理流程（如特定的合同审核逻辑、代码规范检查规则），靠RAG检索几个片段无法覆盖完整逻辑链。

▎深入解释

很多企业刚接触大模型的时候会陷入一个误区：“我要把公司所有文档喂给模型微调，让它变成我们公司的专属模型”，这是完全错误的做法——微调是教模型“怎么说话、怎么思考”，不是教模型“记住什么知识”。你把上个月的产品手册微调进模型，这个月产品更新了，你又要重新微调一次，成本极高而且永远滞后于业务变化。而RAG的思路是“开卷考试”：模型不需要记住所有知识，需要的时候去翻书（检索知识库）就行，书的内容随时可以更新，回答的时候还能标注页码（溯源），出了错可以直接定位到具体文档，这才是企业知识场景的正确思路。只有当你发现模型连“怎么翻书、怎么组织回答”都学不会的时候，比如不管怎么写Prompt，它输出的报告格式总是不对，或者总是听不懂公司内部的黑话，这时候才需要用少量高质量数据做一次LoRA微调，把这些行为习惯固化到模型里。

▎面试加分点

  • 能提到两者的组合使用：工业界最优实践是“RAG负责知识接入，微调负责能力对齐”——先通过微调让模型学会符合企业要求的输出格式和说话风格，再通过RAG接入实时更新的内部知识，两者结合效果最好
  • 能算清成本账：搭建一套RAG系统的成本通常在几千到几万元，当天就能上线；而一次7B模型的LoRA微调至少需要几张A100跑几天，成本几万起，周期一周以上，ROI差距极大。

▎常见误区

  • 误区：认为“微调后的模型知识更准确”。实际上微调不仅不能解决幻觉问题，反而可能因为训练数据的偏差让模型更自信地编造错误内容；而RAG因为有原始文档做依据，幻觉率比纯微调低一个数量级。

二、应用题（5 道 · 分类型）

🛠 应用题 · Q1 · 架构设计

题型

架构设计

场景标签

.skills技能体系 智能客服 模块化Agent

📝 题目

你所在的企业准备从零搭建一套全渠道智能客服Agent系统，覆盖售前咨询、订单操作、售后投诉、政策解答四类核心场景。团队之前踩过“把所有Prompt写在一个大System Prompt里导致模型经常角色混乱、违规操作订单”的坑。请你基于知识库中提到的.skills技能文件体系，设计一套可落地的模块化Agent架构，说明主Agent和各个Skill的职责边界、动态路由逻辑，以及Skill文件的核心结构规范。

💡 参考答案

▎解题思路

  1. 第一步：先做职责分层，彻底拆分“前台路由”和“后台专家”的边界，避免单个Prompt承载过多逻辑导致角色漂移。
  2. 第二步：按照客服的四类核心场景，定义独立的Skill文件，每个Skill只负责单一领域的SOP、专属Prompt、绑定工具，做到高内聚低耦合。
  3. 第三步：设计动态路由的触发规则，实现主Agent根据用户输入的意图、情绪、业务阶段自动加载对应Skill，切换模型的行为模式。
  4. 第四步：补充Skill的加载、卸载、上下文隔离机制，避免不同Skill的规则互相污染。

▎详细方案

整体架构采用“1个主路由Agent + N个独立Skill专家包”的模式：
1. 主Agent（前台接待）职责：只做意图分类和情绪识别，不直接回答业务问题、不直接调用业务工具。它的System Prompt极度精简，核心规则只有三条：① 识别用户当前的核心诉求和情绪强度；② 判断需要激活哪个Skill；③ 把用户的上下文完整传递给对应Skill，拿到结果后润色输出给用户。主Agent本身没有任何业务操作权限，从根源上避免误操作。
2. 四个核心Skill定义：
- policy_expert.skill（政策解答）：专属Prompt要求严格基于RAG知识库回答请假、退换货、公积金等规则问题，禁止编造，知识库无结果直接转人工；绑定工具仅开放向量库检索接口。
- order_handler.skill（订单操作）：专属Prompt要求用户完成身份校验（短信验证码）后才能操作退款、改地址；绑定工具开放订单查询、短信发送、订单更新接口。
- empathy_complaint.skill（客诉安抚）：专属Prompt要求第一步必须情绪认同，优先给出补偿方案，禁止生硬话术；绑定工具开放积分赠送、客诉工单创建接口。
- pre_sale.skill（售前咨询）：专属Prompt要求主动挖掘用户预算、需求、上线时间四个核心信息，匹配脱敏案例做推荐；绑定工具开放案例库检索接口。
3. 动态路由逻辑：主Agent每次收到用户输入后，先做两层判断：① 情绪分（如果负面情绪超过阈值，直接优先加载empathy_complaint.skill，先安抚再处理业务）；② 意图标签（匹配到订单操作类则加载order_handler.skill，匹配到规则类则加载policy_expert.skill）。路由完成后，引擎动态将主Prompt + Skill专属Prompt + Skill绑定工具拼接成最终的LLM请求，此时模型的行为完全受当前Skill的规则约束。
4. Skill文件标准结构：每个Skill是独立的YAML文件，包含四个必填字段：skill_id（唯一标识）、name（技能名称）、system_prompt（该场景下的专属SOP和行为准则）、bound_tools（该技能允许调用的工具白名单）、inputs/outputs（输入输出参数声明）。

▎关键细节 & 踩坑点

  • 绝对不能给主Agent开放业务工具调用权限，必须做到“权限最小化”：只有对应Skill加载时，才把该Skill允许的工具传给LLM，从根本上避免模型被Prompt注入后恶意调用删单、退款接口。
  • Skill切换时必须做上下文隔离：比如用户从投诉场景切换到查订单场景，要在Prompt里明确告知模型“当前已退出安抚模式，进入订单处理模式”，避免把之前的安抚语气带到业务流程里。
  • 不要让Skill之间直接互相调用，所有流转必须经过主Agent路由，否则会出现Skill递归调用、逻辑死循环的问题。

▎可扩展优化

  • 可以增加Skill的优先级配置，比如客诉Skill的优先级最高，只要检测到用户辱骂、投诉关键词，立刻中断当前其他Skill，优先加载安抚技能。
  • 可以做Skill的效果灰度：修改某个Skill的Prompt后，只对10%的流量生效，对比转化率、问题解决率指标，验证效果后再全量发布。
  • 可以给每个Skill增加独立的效果埋点，统计每个Skill的调用次数、转人工率、用户满意度，针对性优化薄弱环节。

题型

场景分析题

场景标签

智能销售客服 数据中台 业务落地

📝 题目

某ToB SaaS公司准备上线一套智能销售客服Agent，替代人工销售完成前期的线索跟进。产品经理提出三个需求：① 不能上来就给客户发报价，必须先挖透客户的预算、痛点、团队规模、上线时间四个核心信息；② 客户要看同行业案例时，不能让大模型瞎编，必须用公司真实的成交案例，但不能泄露客户的真实名称、联系人、合同金额等敏感信息；③ 系统不能越用越笨，要能自动从每天的对话里沉淀优质话术和失败原因，反过来优化销售能力。请你结合知识库中的智能销售落地思路，拆解这套系统的核心实现逻辑，说明每个环节的技术选型和业务价值。

💡 参考答案

▎解题思路

  1. 第一步：解决“多轮对话挖需求”的问题，不能靠大模型自由发挥，必须用显式状态机做信息完备度校验，确保四个核心信息收集齐了再进入下一步。
  2. 第二步：解决“真实案例查询+脱敏”的问题，不能把案例全塞到Prompt里，必须通过工具调用查企业的关系型数据库，经过脱敏网关处理后再交给大模型润色。
  3. 第三步：解决“数据自循环”的问题，搭建轻量级的数据清洗流水线，把每天的对话自动打标签、分类，沉淀成知识库和训练数据集，形成数据飞轮。
  4. 第四步：基于沉淀的数据做业务外延，把数据价值从“客服应答”延伸到销售培训、产品迭代、精准营销，给老板讲清楚ROI。

▎详细方案

整个系统分为四个核心模块，形成从对话到数据再到业务增值的闭环：
1. 多轮意图深挖模块（状态机驱动）：采用LangGraph搭建显式的对话状态机，每个状态对应一个信息收集节点（预算、痛点、团队规模、上线时间），每次大模型回复前先过“信息完备度检查点”：如果四个核心槽位（Slot）没有填满，就强制触发引导话术，比如客户说“我想了解下你们的系统多少钱”，系统不会直接报价，而是回复“方便问下您这边目前团队大概有多少人，主要想解决什么场景的问题吗？我给您匹配最合适的方案”。只有当四个槽位全部填充完成，状态机才会流转到“方案推荐”节点，触发报价逻辑。
2. 真实案例脱敏查询模块（工具调用+脱敏网关）：当大模型识别到用户有“看案例、看同行效果”的意图时，立刻触发工具调用，流程分为四步：① 大模型提取当前用户的标签（行业、规模、核心痛点）；② 调用公司MySQL/PostgreSQL里的成交案例库，检索标签匹配的真实案例；③ 所有返回的案例数据先经过数据脱敏网关，自动把真实甲方名称替换为“某XX行业头部客户”、联系人替换为“项目负责人”、具体合同金额替换为“数十万/数百万级别”；④ 把脱敏后的结构化数据塞到大模型上下文里，由模型润色成自然的销售话术输出，比如“巧了，我们上个月刚帮成都一家头部的社区团购平台做过库存系统升级，他们当时也遇到了和您一模一样的多门店库存不同步问题，上线后库存准确率提升了92%”。
3. 数据中台飞轮模块（自动清洗标注）：每天凌晨自动拉取当天所有的销售对话数据，用一个轻量级开源大模型（如Qwen2.5-7B）做自动化清洗：剔除无效对话、语气词，自动给每段对话打标签（比如“成功转化案例”、“客户嫌贵流失”、“竞品功能提及”），清洗后的数据一方面更新到RAG案例库，另一方面沉淀为黄金数据集，用于后续微调模型的销售话术。
4. 业务外延模块：基于沉淀的数据做三个增值场景：① AI销售教练：把销冠的高转化话术和失败案例做成“刁钻客户模拟器”，让新销售和AI对练；② BI分析：大模型自动分析每周客户拒绝的Top3原因、竞品提及率，输出产品迭代建议；③ 再营销：给流失客户打标签（比如“当时嫌贵”、“需要等下个月预算”），到促销节点自动触发个性化唤醒。

▎关键细节 & 踩坑点

  • 绝对不能让大模型直接输出数据库里的原始数据，脱敏网关必须是强制前置的，不能靠Prompt要求模型“不要泄露敏感信息”——大模型可能会被诱导绕过Prompt规则，直接把真实客户名说出来。
  • 状态机的槽位填充不要做成生硬的“查户口式提问”，要把引导话术融入自然对话里，比如不要连续问“你预算多少？你团队多少人？”，要结合用户的痛点顺势引导。
  • 数据清洗时一定要剔除无效的闲聊、测试对话，否则垃圾数据进了知识库或训练集，会导致模型越学越笨。

▎可扩展优化

  • 可以给每个销售线索打意向分，根据客户的回复积极度、痛点匹配度自动排序，高意向线索优先转人工销售跟进，提升转化率。
  • 可以增加话术A/B测试能力，同一个场景下自动测试两种不同的引导话术，统计哪种话术的槽位填充率更高，自动迭代最优话术。
  • 可以对接企业的CRM系统，把对话里提取的客户信息自动同步到CRM，不需要人工二次录入，降低销售的工作量。

🛠 应用题 · Q3 · 工程实现题

题型

工程实现题

场景标签

.skills引擎 动态Prompt拼接 Python实现

📝 题目

你需要用Python实现一个支持.skills技能体系的轻量级Agent引擎，核心要求是：① 支持从YAML文件加载Skill配置；② 调用对应Skill时，能自动把主Agent Prompt和Skill专属Prompt拼接，同时只把该Skill绑定的工具传给大模型；③ 支持Skill之间的切换，切换后自动清理上一个Skill的上下文污染。请写出核心类的实现逻辑（伪代码即可），并说明关键的实现细节。

💡 参考答案

▎解题思路

  1. 第一步：先定义核心类SkillAgentEngine的初始化逻辑，加载主Agent的基础配置，初始化Skill缓存字典和大模型客户端。
  2. 第二步：实现load_skill方法，读取YAML格式的Skill文件，做格式校验后存入内存缓存，避免每次调用都读磁盘。
  3. 第三步：实现核心的run_with_skill方法，做Prompt动态拼接、工具白名单过滤、上下文隔离，然后调用大模型接口。
  4. 第四步：实现clear_skill_context方法，在Skill切换时清空当前会话中属于上一个Skill的历史消息，避免上下文污染。

▎详细方案

核心代码的实现逻辑如下（可直接用于生产环境的轻量级引擎）：

import yaml
from typing import List, Dict, Optional
from openai import OpenAI # 兼容所有OpenAI格式的大模型接口

class SkillAgentEngine:
    def __init__(self, main_system_prompt: str, llm_client: OpenAI):
        # 1. 初始化主Agent配置：主Prompt只做路由，不包含业务逻辑
        self.main_system_prompt = main_system_prompt
        self.llm = llm_client
        # 2. Skill缓存：key是skill_id，value是解析后的Skill配置
        self.skills: Dict[str, Dict] = {}
        # 3. 会话上下文管理：每个会话独立存储历史消息
        self.session_context: Dict[str, List[Dict]] = {}
        # 4. 当前激活的Skill记录，用于切换时做清理
        self.current_active_skill: Dict[str, Optional[str]] = {}

    def load_skill(self, skill_yaml_path: str) -> None:
        """从YAML文件加载Skill配置到内存"""
        with open(skill_yaml_path, 'r', encoding='utf-8') as f:
            skill_config = yaml.safe_load(f)
        # 做必填字段校验，避免加载不合法的Skill
        required_fields = ['skill_id', 'name', 'system_prompt', 'bound_tools']
        for field in required_fields:
            if field not in skill_config:
                raise ValueError(f"Skill文件缺失必填字段: {field}")
        self.skills[skill_config['skill_id']] = skill_config

    def _switch_skill(self, session_id: str, target_skill_id: str) -> None:
        """切换Skill时的上下文清理逻辑"""
        # 如果当前已经有激活的Skill，先清理上一个Skill的上下文痕迹
        if session_id in self.current_active_skill and self.current_active_skill[session_id] is not None:
            old_skill = self.skills[self.current_active_skill[session_id]]
            # 在上下文中添加明确的模式切换提示，告诉模型已经退出上一个模式
            self.session_context[session_id].append({
                "role": "system",
                "content": f"【系统提示】已退出【{old_skill['name']}】模式，所有该模式下的规则不再生效。"
            })
        # 更新当前激活的Skill记录
        self.current_active_skill[session_id] = target_skill_id
        target_skill = self.skills[target_skill_id]
        # 注入新Skill的专属系统提示
        self.session_context[session_id].append({
            "role": "system",
            "content": f"【系统提示】当前已进入【{target_skill['name']}】模式，必须严格遵守以下规则：\n{target_skill['system_prompt']}"
        })

    def run_with_skill(self, session_id: str, skill_id: str, user_input: str, 
                       available_tool_map: Dict) -> str:
        """
        调用指定Skill处理用户输入
        :param available_tool_map: 所有工具的实现映射，key是工具名，value是工具函数/JSON Schema
        """
        # 1. 校验Skill是否存在
        if skill_id not in self.skills:
            raise ValueError(f"Skill {skill_id} 未加载")
        target_skill = self.skills[skill_id]

        # 2. 初始化会话上下文（如果是新会话）
        if session_id not in self.session_context:
            self.session_context[session_id] = [
                {"role": "system", "content": self.main_system_prompt}
            ]

        # 3. 如果当前激活的Skill不是目标Skill，执行切换逻辑
        if self.current_active_skill.get(session_id) != skill_id:
            self._switch_skill(session_id, skill_id)

        # 4. 把用户输入加入上下文
        self.session_context[session_id].append({
            "role": "user", "content": user_input
        })

        # 5. 核心：只把当前Skill绑定的工具传给大模型，做权限最小化控制
        allowed_tools = []
        for tool_name in target_skill['bound_tools']:
            if tool_name in available_tool_map:
                allowed_tools.append(available_tool_map[tool_name])

        # 6. 调用大模型
        response = self.llm.chat.completions.create(
            model="qwen2.5-72b",
            messages=self.session_context[session_id],
            tools=allowed_tools if allowed_tools else None,
            temperature=0.3
        )

        # 7. 把模型回复加入上下文，返回结果
        assistant_msg = response.choices[0].message
        self.session_context[session_id].append(assistant_msg)
        return assistant_msg.content

▎关键细节 & 踩坑点

  • 工具权限控制是核心安全线：绝对不能把所有工具都传给大模型，必须严格按照Skill配置里的bound_tools做白名单过滤，比如政策解答Skill绝对不能拿到订单修改、退款的工具权限，否则一旦出现Prompt注入就会造成资损。
  • Skill切换时不能直接删掉历史消息，否则会丢失之前的对话上下文，导致模型“失忆”；正确的做法是通过显式的系统提示告诉模型“上一个模式的规则已经失效”，既保留对话历史，又避免规则冲突。
  • 加载Skill时必须做必填字段校验，否则线上如果某个YAML文件写错了字段（比如漏写了system_prompt），会导致调用时直接报错，影响用户体验。
  • 会话上下文不要存在全局变量里，生产环境要把session_context存到Redis里，支持多实例部署时的会话共享。

▎可扩展优化

  • 可以增加工具调用的自动执行逻辑：如果大模型返回了tool_calls，引擎自动校验工具是否在当前Skill的白名单里，校验通过后执行工具，把结果返回给大模型继续生成，实现完整的ReAct循环。
  • 可以增加Skill的超时自动退出机制：比如用户30分钟没有说话，自动把当前激活的Skill重置为路由模式，避免下次用户进来时还停留在之前的客诉安抚模式。
  • 可以增加Skill的调用审计日志：记录每次Skill切换、工具调用的时间、用户输入、返回结果，方便线上排查问题和做效果分析。

🛠 应用题 · Q4 · 排障优化题

题型

排障优化题

场景标签

模型量化 显存不足 部署优化

📝 题目

某创业公司买了2张RTX 4090D（每张24GB显存，共48GB），部署Qwen2.5-32B模型给内部50人团队做知识库助手。运维同学为了“追求最高精度”，直接部署了FP16版本的模型，结果上线后频繁出现OOM（显存溢出）报错，稍微多几个人并发就崩溃，而且响应速度很慢。已知FP16版本的32B模型理论大小是64GB，INT8版本是32GB，INT4 AWQ版本是18GB。请你分析这个故障的根本原因，给出具体的优化方案，计算优化后的显存余量，说明为什么量化后精度损失几乎可以忽略，以及还要做哪些配置能支撑更高的并发。

💡 参考答案

▎解题思路

  1. 第一步：先算清楚显存的总账，找到OOM的根本原因——大模型推理的显存占用不等于模型本身大小，还要算KV Cache的开销，FP16的32B模型本身就64G，两张4090总共才48G显存，根本装不下，必然OOM。
  2. 第二步：选择合适的量化精度，在精度、显存、速度之间做折中，选择INT4 AWQ量化版本，把模型本身的显存占用降到18G，留出足够的空间给KV Cache。
  3. 第三步：解释清楚为什么AWQ量化的精度损失可以忽略，打消团队“量化会变笨”的顾虑。
  4. 第四步：补充推理框架的优化配置，进一步提升并发能力，避免出现显存够了但并发还是上不去的问题。

▎详细方案

  1. 故障根因分析：运维同学的核心错误是只算了模型本身的理论大小，忽略了大模型推理的显存公式：总显存占用 = 模型权重大小 + KV Cache大小 + 运行时临时开销。FP16精度的32B模型权重本身就需要64GB显存，而两张4090D总共只有48GB显存，哪怕一点KV Cache都不分配，模型本身都装不下，必然会出现OOM；即使通过模型并行勉强把模型拆到两张卡上，剩下的显存几乎为0，只要有1-2个用户并发，KV Cache就会把显存占满，直接崩溃，而且跨卡传输权重的延迟会导致响应速度极慢。
  2. 量化方案选型：直接选择社区预训练好的Qwen2.5-32B INT4 AWQ量化版本，模型权重大小仅18GB左右。两张4090D共48GB显存，加载完模型后还剩30GB的空闲显存，按照vLLM的PagedAttention机制，128K上下文长度下，每个并发用户的KV Cache大约占用1-2GB显存，30GB的空闲空间可以轻松支撑15-20个并发用户，完全满足50人内部团队的使用需求（内部系统的同时在线并发率通常在10%-20%，50人团队峰值并发也就5-10人）。
  3. 精度损失的合理性解释：AWQ是目前训练后量化（PTQ）里精度保持最好的算法之一，它的核心原理是“保护权重里1%的核心离群点权重不量化，只对剩下99%的普通权重做INT4量化”，在MMLU、GSM8K等主流基准测试上，INT4 AWQ量化的模型和FP16原生模型的精度差距通常在1%以内，人几乎感知不到差异，完全能满足内部知识库问答的场景需求。而且量化后不仅显存占用降低了75%，INT4的整数运算吞吐量是FP16的2-4倍，推理速度反而会比FP16模型快2-3倍。
  4. 并发优化配置：量化完成后，还要做三个配置优化：① 用vLLM作为推理框架，开启PagedAttention和Continuous Batching（动态批处理），把不同用户的请求在Token级别做批处理，GPU利用率可以从30%提升到80%以上；② 在LLM网关层开启语义缓存，相似问题直接返回缓存结果，不占用GPU算力；③ 设置合理的max_model_len（比如设为32K，内部知识库场景不需要128K那么长的上下文），进一步减少KV Cache的显存占用。

▎关键细节 & 踩坑点

  • 不要自己从零做量化，直接用HuggingFace上社区已经验证过的、带-AWQ后缀的预量化模型，自己做量化如果校准集选不好，很容易出现精度崩塌，尤其是代码、数学类的能力会掉很多。
  • 不要为了“省显存”把量化精度压到INT3或者更低，低于4bit的量化精度损失会非常明显，而且目前主流推理框架对INT3的优化并不成熟，速度反而不一定快。
  • 部署时要开启vLLM的--gpu-memory-utilization参数，设置为0.9（即最多用90%的显存），留10%的显存给运行时临时开销，不要把显存占满，否则还是会出现偶发OOM。

▎可扩展优化

  • 如果后续团队规模扩大到200人，可以在网关层增加请求排队机制，当并发数超过GPU承载能力时，让用户排队等待，而不是直接把服务打崩。
  • 可以开启vLLM的前缀缓存功能，内部知识库的系统Prompt和RAG召回的公共前缀是重复的，缓存这部分KV Cache可以进一步减少显存占用，提升响应速度。
  • 可以针对高频的知识库问题做微调，用LoRA训练一个专属的小适配器，进一步提升回答准确率，不需要升级更大的模型。

综合落地题

场景标签

企业本地部署 从0到1落地 ROI核算

📝 题目

某100人规模的律师事务所，所有业务数据（诉讼文书、客户合同、案件记录）绝对不能外流，要求完全内网部署一套AI助手，核心需求是：① 支持上传PDF/Word卷宗，自动提炼案件大纲、检索相似历史案例；② 支持律师写文书时的逻辑校对、法条引用检查；③ 初期并发不高（峰值10个律师同时用），但要求响应速度快，总预算控制在10万元以内，后期可以按需扩容。请你给出一套从硬件选型、模型选择、核心功能搭建到落地避坑的完整落地方案，说明为什么这么选，以及如何在3个月内验证ROI。

💡 参考答案

▎解题思路

  1. 第一步：先做硬件选型，严格控制预算，选择性价比最高的消费级显卡方案，不要上来就买昂贵的企业级GPU，避免算力焦虑。
  2. 第二步：模型选择上，优先选中文能力强、法律场景表现好的开源模型，用AWQ量化控制显存占用，在有限的硬件上跑出最好的效果。
  3. 第三步：核心功能搭建上，80%的场景用RAG解决（文书检索、案例匹配），20%的定制化需求用轻量Prompt工程解决（大纲提炼、逻辑校对），不要上来就做微调，降低落地复杂度。
  4. 第四步：制定分阶段落地计划，先跑通核心场景验证ROI，再逐步扩容，避免一次性投入过大。

▎详细方案

整套方案总硬件成本控制在6万元左右，完全在10万预算内，普通后端工程师1个月就能搭完，3个月就能看到明确的效率提升：
1. 硬件选型（总成本约5.5万）：选择1台工作站服务器，配置为2张NVIDIA RTX 4090D（24GB显存，每张约1.3万，共2.6万）+ 128G内存 + 2T NVMe SSD + 16核CPU，整机成本约5.5万。不选择昂贵的A10、H200等企业级显卡，因为4090D的FP16推理性能和A10相当，价格只有A10的1/3，完全能满足10人并发的需求；而且不需要做机房改造，普通办公室的220V电源就能带动，不需要液冷，运维成本极低。
2. 模型与推理框架选型：模型选择Qwen2.5-32B-Instruct的INT4 AWQ量化版本（约18GB显存），这个模型的中文理解、长文本处理能力在同参数量级里是第一梯队，法律场景的表现远好于同尺寸的Llama模型；推理框架用vLLM，开启PagedAttention和动态批处理，加载完模型后还剩30GB显存，足够支撑10-15个并发用户，生成速度可以达到80 tokens/s以上，律师输入一个问题3-5秒就能出结果，完全满足响应速度要求。
3. 核心功能搭建（分三个模块，2周就能搭完）：
- 卷宗处理与检索模块：用Unstructured库做PDF/Word文档解析，把历史诉讼文书、合同、法条按512Token切片，存入本地部署的Qdrant向量库（不需要买专门的向量数据库服务，直接跑在服务器上就行），用BGE-M3做Embedding模型，检索时加BGE-Reranker做重排，保证相似案例检索的准确率。律师上传一份50页的卷宗后，系统自动提取案件的原告、被告、核心诉求、证据链，生成大纲，同时检索相似的历史判例，提供参考。
- 文书校对模块：写一个独立的Skill文件，专属Prompt要求模型作为资深律师助理，检查文书里的逻辑矛盾、法条引用错误、诉讼时效遗漏，不改变律师的原文风格，只给出修改建议；绑定法条检索工具，当模型识别到文书里引用了法条时，自动去本地的法条知识库校验引用是否正确。
- 安全模块：在入口部署本地的PII（敏感信息）过滤器，自动识别文档里的客户身份证号、银行卡号等敏感信息，做掩码处理；整个系统完全物理断网，不连接任何外部API，所有数据都存在本地服务器上，满足律所的数据合规要求。
4. 分阶段落地与ROI验证：
- 第一阶段（第1个月）：搭完基础环境，先导入近1年的1000份历史文书，跑通卷宗大纲提炼、相似案例检索两个核心功能，找5个资深律师做内测，收集反馈优化检索准确率。
- 第二阶段（第2个月）：全所推广使用，统计两个核心指标：① 律师提炼卷宗大纲的时间从平均2小时/份降到10分钟/份；② 检索相似案例的时间从平均1小时/份降到1分钟/份。按每个律师每小时收费500元计算，100个律师每月节省的时间成本就超过10万元，2个月就能收回硬件成本。
- 第三阶段（第3个月）：上线文书校对功能，同时把历史的所有文书（约10万份）导入向量库，逐步扩展功能。

▎关键细节 & 踩坑点

  • 绝对不要一开始就买8卡服务器或者70B模型，10人并发的场景下32B INT4模型完全够用，把80%的精力花在数据清洗上——把历史PDF里的乱码、扫描件OCR错误、页眉页脚等垃圾内容清理干净，检索准确率的提升比把模型从32B换成70B要大得多。
  • 不要上来就做微调，法律场景的核心需求是“检索准确、不编造”，RAG完全能满足90%的需求，微调不仅需要大量标注数据，还会导致模型知识过时，更新法条时还要重新微调，成本极高。
  • 一定要做权限控制，不同律师只能看到自己负责的案件文档，不能访问其他律师的客户数据，避免内部数据泄露。
  • 4090D显卡要选涡轮散热版本的服务器专用卡，不要选消费级的风冷卡，服务器机箱里多块显卡间距小，风冷卡散热不好会导致降频，速度变慢。

▎可扩展优化

  • 当后期全所100个律师都用起来，并发上来后，可以再增加2张4090D显卡，用vLLM做张量并行，把模型升级到Qwen2.5-72B INT4版本，进一步提升推理能力，硬件成本只需要再加2.6万，不需要换整个服务器。
  • 可以增加合同审查的专属Skill，自动识别合同里的风险条款（比如违约责任不对等、管辖地约定不合理），给出风险提示，进一步扩展使用场景。
  • 可以搭建本地的语义缓存，把律师常问的法条问题、文书模板问题缓存起来，进一步提升响应速度，降低GPU负载。
  • 后期可以用所里的历史胜诉判决书做LoRA微调，让模型学习律所的文书风格，生成的文书更符合所里的要求，但这一步一定要等RAG跑顺、数据积累足够了再做，不要一开始就搞。
