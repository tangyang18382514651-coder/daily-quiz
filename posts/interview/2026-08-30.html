📌 概念题 · Q1

考点标签

优雅关闭 · Lifespan · SIGTERM · 难度：⭐⭐⭐

📝 题目

在 FastAPI 中，为什么不能用简单的 try...finally 或进程级信号处理来实现 Agent 任务的优雅关闭？lifespan 异步上下文管理器相比传统的 @app.on_event("startup/shutdown") 有什么本质优势？请结合长耗时 Agent 任务（如生图、流式文案生成）说明其核心原理。

💡 参考答案

▎一句话结论

lifespan 是 FastAPI 官方推荐的、基于 asyncio 上下文管理器协议的生命周期钩子，它解决了传统 on_event 无法优雅等待在途异步任务完成的问题，是生产级 Agent 服务实现“零中断发布”的关键基础设施。

▎核心原理

  • lifespan 使用 @asynccontextmanager 装饰，将启动逻辑写在 yield 之前，关闭逻辑写在 yield 之后，天然支持异步等待
  • 与 on_event("shutdown") 不同，lifespan 中的代码运行在同一个事件循环上下文中，可以 await asyncio.sleep() 来轮询在途任务
  • 通过全局计数器（active_tasks）跟踪正在执行的 Agent 任务数，在收到 SIGTERM 后不立即退出，而是等待计数器归零

▎深入解释

传统 @app.on_event("shutdown") 的问题在于：它是同步回调，无法在其中执行 await 等待异步任务完成。当你用 Uvicorn 托管 FastAPI 时，收到 SIGTERM 信号后，服务器会立即停止接收新请求，但如果直接终止进程，那些正在执行 LangGraph 编排（比如正在生成一张配图，耗时 30 秒）的请求就会被硬生生切断——用户看到的是 502 错误，而 Agent 的 Checkpointer 可能还没来得及把中间状态落库，导致任务丢失或状态不一致。

lifespan 的优雅之处在于：它在 yield 之后可以写任意异步代码。当平台层（如 K8s、自研 Serverless 平台）发送 SIGTERM 后，Uvicorn 会触发 lifespan 的关闭分支，此时你的代码可以先停止接收新请求（通过反向代理或网关层配合），然后进入一个 while active_tasks > 0 的轮询循环，每隔 1 秒检查一次是否还有在途任务。只有当所有任务都通过 Checkpointer 持久化落库后，进程才真正退出。这本质上是把“进程生命周期管理”和“业务任务生命周期管理”解耦了。

▎面试加分点

  • 结合 K8s 的 terminationGracePeriodSeconds 配置：如果优雅关闭时间超过该值，K8s 会强制 kill 进程，所以需要合理设置超时上限
  • 提到“先摘流量再关闭”：在 lifespan 关闭分支中先调用网关的摘流 API，再等待任务完成
  • 强调 active_tasks 计数器的线程安全性：在异步环境中用 asyncio.Lock 或直接依赖单线程事件循环的原子性

▎常见误区

  • 以为 on_event("shutdown") 可以替代 lifespan 完成异步等待——实际上它是同步函数，无法 await
  • 只在 finally 块中做清理，但 finally 只保证单请求内的资源释放，无法阻止进程被 SIGTERM 直接杀死
  • 忽略了“停止接收新请求”这一步，导致关闭期间仍有新请求进来，计数器永远无法归零

📌 概念题 · Q2

考点标签

Docker Compose · healthcheck · depends_on · 难度：⭐⭐⭐

📝 题目

在 Docker Compose 编排多服务 Agent 集群时，depends_on 的默认行为和 condition: service_healthy 有什么区别？为什么说“只写 depends_on 不配 healthcheck 等于没写”？请结合 MCP Server 依赖场景说明。

💡 参考答案

▎一句话结论

depends_on 默认只保证容器“已启动”（进程存在），而 condition: service_healthy 保证服务“已就绪”（健康检查通过），后者才是生产级多服务编排的正确姿势。

▎核心原理

  • Docker Compose 的 depends_on 默认行为是：只要被依赖的容器进入了 “running” 状态，就认为依赖满足，开始启动下一个容器
  • “running” 状态只代表容器内的主进程（PID 1）已经起来，不代表服务真正可用——比如 MCP Server 可能还在加载模型、建立数据库连接、预热索引
  • healthcheck 定义了服务的健康探测逻辑（如 curl -f http://localhost:8001/health），condition: service_healthy 会持续轮询直到健康检查通过才启动下游服务

▎深入解释

举个具体场景：你的 api-gateway 依赖 mcp-rag-server。如果只用默认的 depends_on，Compose 可能在 RAG 服务还在加载向量索引（耗时 30 秒）时就启动了网关。此时网关开始接收流量，但 RAG 服务还没就绪，导致第一批请求全部失败，甚至触发熔断器误判。

healthcheck 的配置有几个关键参数：interval（探测间隔）、retries（连续失败多少次才判定为不健康）、start_period（容器启动后的宽限期，给服务预留初始化时间）。通过 condition: service_healthy，Compose 会阻塞上游服务的启动，直到下游服务的健康检查连续成功。

更进一步，在 K8s 中对应的概念是 readinessProbe 和 livenessProbe。readinessProbe 决定“是否把流量打到这个 Pod”，livenessProbe 决定“是否重启这个 Pod”。Docker Compose 的 healthcheck 更接近 readinessProbe 的语义。

▎面试加分点

  • 提到在 healthcheck 中应该探测的是“业务就绪”而非“进程存活”：比如 /health 端点不仅要返回 200，还要内部检查数据库连接、MCP Client 初始化状态
  • 结合“分层发布拓扑”：底层 MCP 服务 → 网关 → 上层业务 Agent，每一层都用 service_healthy 保证物理顺序
  • 提到 start_period 的重要性：大模型服务启动慢，如果不设置宽限期，容器可能被误判为不健康而反复重启

▎常见误区

  • 以为 depends_on 会等待服务完全就绪——它只等待容器启动
  • 健康检查端点只返回 {"status": "ok"} 但内部没有真正检查依赖组件，导致“假健康”
  • 在 healthcheck 中使用过重的探测逻辑（比如触发一次完整的 RAG 检索），导致每次探测都消耗大量资源

📌 概念题 · Q3

考点标签

多仓库部署 · 微服务 · Agent集群 · 难度：⭐⭐⭐

📝 题目

在 AI Agent 集群架构中，为什么推荐“底层 MCP 共享服务”和“上层业务 Agent”分仓库独立部署，而不是把所有 Agent 塞进同一个 Monorepo？这种拆分与“总 Agent 路由分发”模式有什么本质区别？

💡 参考答案

▎一句话结论

多仓库独立部署的核心逻辑是“基础设施与业务逻辑解耦”：底层 MCP 服务作为稳定底座单独发布，上层业务 Agent 各自独立迭代，互不阻塞；而“总 Agent 路由”是反模式，因为它把流量分发和业务逻辑耦合在一个脆弱的非确定性组件中。

▎核心原理

  • 底层 MCP 服务（LLM 调用、RAG 检索、会话记忆、Prompt 管理）变更频率低，追求极致稳定性，适合独立仓库、独立发布节奏
  • 上层业务 Agent（HR 客服、自媒体运营）变更频率高，业务逻辑差异大，需要快速迭代，独立仓库可以做到“发布 A 不影响 B”
  • 通过 HTTP 网关统一接入，新业务只需要写自己的 LangGraph 编排层，通过 API 调用底层 MCP 服务，无需修改公共代码

▎深入解释

想象一下如果所有 Agent 都在一个 Monorepo 里：自媒体团队改了 Prompt 模板，需要重新构建整个镜像，结果 HR 客服的 CI/CD 流水线也被触发了，甚至因为一个无关的改动导致整个系统回滚。这就是“耦合的代价”。

拆分成多仓库后，底层 MCP 服务就像公司的“水电煤”——稳定、通用、不轻易变。上层业务 Agent 就像各个部门——各自有独立的代码库、独立的发布窗口、独立的回滚策略。当 HR 客服需要调用自媒体能力时，它不通过“总 Agent”去中转，而是直接通过网关发起 HTTP 请求（平级调用），或者通过共享的 PostgreSQL 用户画像层实现数据互通。

“总 Agent 路由分发”的问题在于：大模型做意图分类的准确率不是 100%，一旦分类错误，请求就被发到了错误的业务 Agent；而且总 Agent 挂掉会导致全公司所有 Agent 瘫痪，是典型的单点故障。

▎面试加分点

  • 提到“团队开发隔离”：不同团队只负责自己的仓库，代码评审、权限管理、发布审批都独立
  • 强调“网关是确定性的，Agent 是非确定性的”：路由分发用纯代码（FastAPI/Nginx）做，不用大模型做
  • 结合“共享记忆层”实现跨 Agent 数据同步：用户画像存在统一的 PostgreSQL，各 Agent 通过 user_id 读取

▎常见误区

  • 以为多仓库就是“微服务”，忽略了服务间通信的成本（网络延迟、序列化开销、分布式事务）
  • 在 Agent 之间做同步的 RPC 调用链路过长，导致一个请求要经过 5 个 Agent 才能返回
  • 把“总 Agent 路由”和“网关路由”混为一谈：前者是业务层的非确定性分发，后者是基础设施层的确定性转发

📌 概念题 · Q4

考点标签

LangGraph · Checkpointer · Time-travel · 难度：⭐⭐⭐⭐

📝 题目

在 LangGraph 中，Checkpointer 的 get_state_history() 和 update_state() 被称为“时间旅行”（Time-travel）能力。请说明这种能力在 Agent 死循环熔断和节点级失败重试中的核心价值，以及为什么它比传统的“整个任务重跑”更高效？

💡 参考答案

▎一句话结论

Checkpointer 的时间旅行能力让 Agent 可以从任意历史节点“分叉重试”，而不是从头再来，这是实现节点级故障恢复和精准熔断降级的核心技术手段。

▎核心原理

  • Checkpointer 在每次节点执行完毕后自动将图的完整状态（State）序列化到持久层（如 PostgreSQL），每个状态对应一个唯一的 checkpoint_id
  • get_state_history(config) 可以回溯所有历史 checkpoint，找到“故障发生前”的最近一个健康状态
  • update_state(config, values, as_node=...) 可以修改历史状态并创建新的分叉，让图从这个点重新开始执行

▎深入解释

假设你的自媒体 Agent 工作流是：选题 → 写作 → 配图 → 发布。配图节点并行生成 4 张图，其中第 3 张因为 API 超时失败了。如果不用时间旅行，你只有两个选择：要么整个任务重跑（浪费前面选题和写作的 Token 和时间），要么手动写复杂的重试逻辑。

有了 Checkpointer 的时间旅行，你可以这样做：通过 get_state_history() 找到“写作节点刚结束、配图节点未开始”的那个 checkpoint，然后调用 update_state() 把状态重置到那个点，只重新执行配图节点。这就像游戏里的“存档/读档”——你不需要从第一关重新打，只需要从最近的存档点继续。

更进一步，在死循环熔断场景中，你可以在计数器达到硬上限时，通过时间旅行回退到“进入反思循环之前”的状态，然后走降级路由（比如直接返回模板话术），而不是让 Agent 继续在循环里消耗 Token。

▎面试加分点

  • 提到“增量重试”的成本优势：只重试失败节点，不重试整个图，Token 消耗降低 70% 以上
  • 强调 as_node 参数的作用：指定从哪个节点开始恢复，而不是从图的入口开始
  • 结合 PostgreSQL 的 ACID 特性：Checkpointer 的持久化是事务性的，不会出现“存了一半”的脏状态

▎常见误区

  • 以为 update_state() 会修改历史记录——它实际上创建了一个新的分叉，历史 checkpoint 仍然保留
  • 在内存中使用 Checkpointer（如 MemorySaver），服务重启后所有状态丢失，无法实现真正的持久化
  • 忽略了 Checkpointer 的序列化开销：每个节点都存一次状态，在高并发场景下可能成为性能瓶颈

📌 概念题 · Q5

考点标签

长周期Agent · Interrupt · Webhook · 难度：⭐⭐⭐⭐

📝 题目

在处理员工入职、跨部门审批等长周期（Long-running）业务时，Agent 不能常驻内存等待人工介入。请说明 LangGraph 的 Interrupt 机制如何实现“Agent 休眠与唤醒”，以及它与传统消息队列（如 Celery + Redis）方案的异同。

💡 参考答案

▎一句话结论

LangGraph 的 Interrupt 机制让 Agent 在需要人工审批时主动挂起并持久化状态，释放计算资源；当外部系统通过 Webhook 回调时，Agent 从持久层反序列化状态并继续执行，实现了“无状态服务 + 有状态流程”的完美结合。

▎核心原理

  • Agent 执行到审批节点时，触发 Tool 调用在 OA/HR 系统中创建审批单，并向 LangGraph 状态机抛出 Interrupt 信号
  • Interrupt 信号导致图执行暂停，当前完整状态（包括上下文、局部变量、执行轨迹）被序列化到 Checkpointer
  • 外部审批完成后，HR 系统后端向 FastAPI 发送 Webhook 回调，接收端根据 Task_ID 从数据库读取状态，反序列化后作为外部事件输入唤醒 Agent

▎深入解释

传统方案（Celery + Redis）的思路是：把长任务拆成多个小任务，每个任务执行完就释放 Worker，下一个任务通过消息队列触发。但这种方式的问题是：任务的“上下文”需要手动管理——你要自己把中间结果存到 Redis，自己定义任务的依赖关系，自己处理失败重试。

LangGraph 的 Interrupt 机制把这个过程“内建”到了图执行引擎中。Agent 不需要关心“我的状态存在哪里”、“我该怎么恢复”——这些问题由 Checkpointer 和 LangGraph Runtime 自动处理。开发者只需要在图中标记“这里需要人工介入”，然后等待外部事件。

一个关键设计是：Interrupt 不是异常，而是正常的控制流。它告诉图引擎：“我现在不能继续了，但不要销毁我的状态，等我被唤醒。” 这比抛异常然后重试要优雅得多，因为它保留了完整的执行上下文。

▎面试加分点

  • 提到“两阶段提交”：审批单创建和 Agent 状态持久化要在同一个事务中，避免“审批单创建了但状态没存”的不一致
  • 强调“幂等性”：Webhook 回调可能重复发送，接收端要根据 Task_ID 做幂等处理
  • 结合 Serverless 架构：Agent 休眠期间 Pod 可以缩容到 0，唤醒时再冷启动，成本极低

▎常见误区

  • 以为 Interrupt 会丢失状态——实际上状态已经被 Checkpointer 持久化了
  • 用轮询代替 Webhook：让 Agent 每隔 5 秒查一次审批状态，浪费资源且延迟高
  • 忽略了超时机制：如果审批人一直不处理，Agent 需要有过期降级策略

📌 概念题 · Q6

考点标签

Prefix Caching · KV Cache · TTFT · 难度：⭐⭐⭐⭐

📝 题目

在大模型推理中，Prefix Caching（前缀缓存）和 KV Cache（键值缓存）有什么区别？为什么说“固定 System Prompt 的 Token 级一致性”是触发 Prefix Caching 的关键前提？请结合 RAG 场景说明如何设计 Prompt 结构来最大化缓存命中率。

💡 参考答案

▎一句话结论

KV Cache 是单次推理内部的注意力缓存，而 Prefix Caching 是跨请求的缓存复用机制——通过保证请求开头的 Token 序列完全一致，让不同请求共享同一个前缀的 KV 计算结果，从而大幅降低首字延迟（TTFT）和推理成本。

▎核心原理

  • KV Cache 是 Transformer 推理时缓存每个 Token 的 Key 和 Value 矩阵，避免在生成后续 Token 时重复计算前面所有 Token 的注意力
  • Prefix Caching 是推理引擎（如 vLLM、SGLang）在 KV Cache 基础上的跨请求优化：如果两个请求的前缀 Token 完全相同，则直接复用第一个请求已经计算好的 KV 缓存
  • 触发条件：前缀必须在 Token 级别完全一致，任何微小的差异（如时间戳、用户 ID、随机数）都会导致缓存失效

▎深入解释

RAG 场景的典型 Prompt 结构是：System Prompt（角色设定 + 安全规则）→ Few-Shot 示例 → 检索到的文档片段 → 用户问题。如果每次请求都把检索结果拼在最前面，那么每个请求的前缀都不同，Prefix Caching 完全无法命中。

正确的做法是：把最稳定的部分（System Prompt、Few-Shot、RAG 检索片段的排序规则）放在最前面，并且保证这些内容在 Token 级别完全一致。比如，你可以把检索结果按照固定规则排序（如按相关度分数降序、按文档 ID 排序），然后拼接成固定格式的字符串。这样，只要 System Prompt 和 Few-Shot 不变，所有请求的前缀就是相同的，推理引擎可以直接复用缓存的 KV。

更进一步，在 LangGraph 的节点设计中，如果多个节点共享同一个 System Prompt 前缀，可以把这个前缀抽离为常量，避免在代码中动态拼接时引入细微差异。

▎面试加分点

  • 提到“缓存命中率”的量化：通过监控推理引擎的缓存命中指标，可以评估 Prompt 设计的优劣
  • 结合“Token 级一致性”的陷阱：看似相同的文本，如果编码方式不同（如全角/半角、空格差异），Token 序列也会不同
  • 强调 RAG 场景下“先排序后拼接”的策略：检索结果按固定规则排序后再拼入 Prompt，保证前缀稳定

▎常见误区

  • 以为 Prefix Caching 是模型层面的能力——它实际上是推理引擎（vLLM 等）的优化
  • 在 Prompt 中插入动态时间戳或用户 ID，导致前缀永远无法命中缓存
  • 把 RAG 检索结果放在 System Prompt 前面，导致每个请求的前缀都不同

📌 概念题 · Q7

考点标签

GraphRAG · Contextual Retrieval · 确定性解析 · 难度：⭐⭐⭐⭐

📝 题目

企业级 RAG 正在从“纯向量 RAG”转向“GraphRAG + 确定性解析 + Contextual Retrieval”的组合架构。请说明这三种技术分别解决了传统 RAG 的什么痛点，以及为什么它们在企业垂直领域（如财务报表、ERP 数据）中成为标配？

💡 参考答案

▎一句话结论

GraphRAG 解决“多跳推理和全局总结”能力不足的问题，确定性解析解决“粗暴切块破坏文档结构”的问题，Contextual Retrieval 解决“切块后信息碎片化、上下文丢失”的问题——三者组合构成了企业级 RAG 的“检索质量铁三角”。

▎核心原理

  • GraphRAG：通过提取实体及其关联构建知识图谱，结合向量检索形成“语义相似度 + 拓扑关联”的双轨检索，擅长处理跨文档、跨章节的宏观问题
  • 确定性解析：使用 Docling-Studio 等技术进行多模态物理布局解析，严格保护表格、段落标题、页脚的完整性，替代按字符数固定切块的粗暴做法
  • Contextual Retrieval：在入库前通过小模型为每个 Chunk 自动生成一段包含母文档核心信息的“前缀补全”，解决切块后丢失上下文的问题

▎深入解释

传统 RAG 的三个致命伤在企业场景中被无限放大：

第一，向量检索只能找“相似的”，不能找“相关的”。比如问“公司 Q3 的净利润同比变化是多少”，向量检索可能找到一堆包含“净利润”的片段，但无法理解“Q3”和“同比”之间的逻辑关系。GraphRAG 通过知识图谱的拓扑结构，可以直接定位到“Q3 财务报告”这个实体，再沿着“同比”关系找到去年 Q3 的数据。

第二，固定字符数切块会切断表格和段落。财务报表中的表格如果被从中间切开，LLM 看到的是一堆无意义的数字碎片。确定性解析通过识别文档的物理布局（标题层级、表格边界、段落结构），保证每个 Chunk 都是语义完整的单元。

第三，切块后的片段像“断章取义”。一个 Chunk 说“该政策适用于以下情况”，但没说是哪个政策。Contextual Retrieval 让一个小模型在入库前为每个 Chunk 生成一段上下文前缀（如“本文档是《2025 年员工考勤管理办法》，以下内容属于第三章请假流程”），这样即使 Chunk 被单独检索出来，LLM 也能理解它的背景。

▎面试加分点

  • 提到 GraphRAG 的“双轨检索”策略：简单查询走向量检索（快），复杂查询走图谱检索（准），由 Router 决定
  • 强调确定性解析的“物理布局感知”：不是用正则表达式猜结构，而是用专门的解析引擎理解文档的视觉层级
  • 结合“小模型生成前缀”的成本优势：用 Flash 模型做 Contextual Retrieval 的前缀生成，成本极低

▎常见误区

  • 以为 GraphRAG 可以完全替代向量检索——实际上两者是互补关系，各有擅长场景
  • 在文档结构简单的场景也强行上确定性解析，增加了不必要的复杂度和延迟
  • 忽略了 Contextual Retrieval 的“入库时一次性成本”：虽然检索时更快，但入库时多了一次小模型调用

📌 概念题 · Q8

考点标签

Multi-Agent · Router-Worker · SubGraph · 难度：⭐⭐⭐

📝 题目

在复杂业务场景中，为什么“Single Agent + 大量工具”是灾难性的？请说明 Router-Worker Pattern（路由-工人模式）和 SubGraph Pattern（子图模式）的核心区别，以及各自适用的业务场景。

💡 参考答案

▎一句话结论

Single Agent 的灾难源于“注意力稀释”：工具越多，模型越容易选错工具、忽略关键参数；Router-Worker 通过专职路由 Agent 分发任务到专职 Worker Agent，SubGraph 通过将复杂流程拆分为独立编排单元，两者都是“分而治之”思想在 Agent 架构中的体现。

▎核心原理

  • Single Agent 的“注意力遗忘”：当工具定义超过 5-10 个时，LLM 在 Function Calling 时的准确率显著下降，容易选错工具或遗漏必填参数
  • Router-Worker Pattern：一个 Router Agent 只做意图分类和任务分发，不执行业务逻辑；每个 Worker Agent 只负责一个垂直领域，持有 2-3 个核心工具
  • SubGraph Pattern：将一个复杂的 LangGraph 图拆分为多个子图（如选题子图、写作子图、配图子图），每个子图有自己的状态和节点，主图只负责编排子图的调用顺序

▎深入解释

Router-Worker 的核心思想是“意图识别与业务执行分离”。Router Agent 的 Prompt 极其简单：“判断用户意图是 A、B 还是 C”，它不需要知道 A 业务的具体工具怎么用。当 Router 判断出意图后，把请求分发给对应的 Worker Agent。Worker Agent 的工具集很小（2-3 个），所以选错的概率极低。

SubGraph 的核心思想是“复杂流程的模块化”。比如自媒体 Agent 的完整流程是“选题 → 写作 → 配图”，如果全部写在一个图里，状态定义会非常庞大，任何一个节点的修改都可能影响其他节点。拆分为子图后，每个子图可以独立开发、独立测试、独立复用。比如“配图子图”可以同时被自媒体 Agent 和 HR 客服 Agent 复用。

两者的区别在于：Router-Worker 是“横向拆分”（按业务领域），SubGraph 是“纵向拆分”（按流程阶段）。在实际项目中，两者经常组合使用：Router 分发到不同的业务 Worker，每个 Worker 内部又用 SubGraph 拆分为多个阶段。

▎面试加分点

  • 提到“工具数量的黄金法则”：每个 Worker Agent 的工具不超过 3 个，超过就考虑拆分
  • 强调 SubGraph 的“独立状态管理”：子图有自己的 State Schema，可以独立持久化，故障恢复粒度更细
  • 结合“多模型路由”：Router 用 Flash 模型（快、便宜），Worker 根据任务复杂度选择 Flash 或旗舰模型

▎常见误区

  • 以为 Router Agent 需要很复杂的 Prompt——实际上 Router 的 Prompt 越简单越好，复杂逻辑放在 Worker 里
  • 在 Worker 之间做同步调用链路过长，导致一个请求要经过 5 个 Worker 才能返回
  • 把 SubGraph 拆得太细，导致子图之间的通信开销超过了拆分带来的收益

📌 概念题 · Q9

考点标签

SFT · DPO · RAG · 职责分离 · 难度：⭐⭐⭐⭐

📝 题目

“微调管风格、RAG 管知识”被称为企业级 Agent 的职责分离架构。请说明 SFT 和 DPO 在“管风格”中的各自职责，以及为什么说“通过微调让模型记住知识是错误的方向”？RAG 和微调在知识更新成本上有什么本质区别？

💡 参考答案

▎一句话结论

SFT 让模型“从不会到会说”（学习风格和话术策略），DPO 让模型“从会说到说好”（偏好精排）；知识更新走 RAG 是因为知识库修改的成本是秒级的，而微调更新知识的成本是天级的。

▎核心原理

  • SFT（Supervised Fine-Tuning）：用标注好的“输入-理想输出”对训练模型，让模型学习特定领域的表达风格、话术策略和输出格式
  • DPO（Direct Preference Optimization）：用 chosen/rejected 偏好对训练，不需要显式的奖励模型，让模型学会“在多个合理回答中选择更好的那个”
  • RAG 管知识：知识存储在向量数据库/知识库中，更新知识只需要修改知识库，模型权重不变

▎深入解释

为什么“微调管知识”是错误方向？因为知识是高频变化的——公司的考勤政策下个月可能就改了，产品价格每天都在变。如果每次知识更新都要微调模型，你需要重新准备训练数据、启动 GPU 训练、评估效果、部署上线，整个流程至少需要几天时间。而 RAG 的知识更新只需要把新文档写入向量数据库，秒级生效。

微调的唯一目的是“改变模型的行为范式”，而不是“注入事实”。比如 HR 客服场景，SFT 让模型学会“用温和、专业、结构化的方式回答员工问题”，DPO 让模型学会“在多个合理回答中，优先选择那些包含具体操作步骤、引用政策条款的回答”。这些“行为范式”是相对稳定的，不需要频繁更新。

一个经典的比喻：微调是教模型“怎么说话”（口吻、风格、格式），RAG 是给模型“说什么内容”（事实、数据、政策）。你不能通过微调让模型记住所有政策条款——模型的参数容量有限，而且知识会过时；你也不应该用 RAG 来改变模型的表达风格——RAG 只会把检索到的文本拼给模型，不会改变模型生成文本的方式。

▎面试加分点

  • 提到 DPO 相比 RLHF 的优势：不需要训练奖励模型，训练更稳定，成本更低
  • 强调“知识更新 SLA”：RAG 的知识更新是秒级到分钟级，微调是天级到周级
  • 结合“SFT + DPO 两阶段”的工程实践：SFT 阶段用大量风格数据打基础，DPO 阶段用少量高质量偏好对做精调

▎常见误区

  • 以为微调可以替代 RAG——微调后模型仍然会“幻觉”，因为知识不在参数里
  • 在 SFT 数据中混入了大量知识性问答，导致模型“记住”了训练数据中的知识，但这些知识很快过时
  • 忽略了 DPO 的偏好对质量：chosen/rejected 的标注质量直接影响 DPO 效果，标注不一致会引入噪声

📌 概念题 · Q10

考点标签

MCP · 多租户隔离 · 物理隔离 · 难度：⭐⭐⭐⭐

📝 题目

在多租户 SaaS 场景中，MCP Server 作为共享服务，如何实现租户间的知识库“物理隔离”而非“逻辑隔离”？为什么说“物理隔离”是安全合规的底线要求？请结合向量数据库的 Collection 划分说明。

💡 参考答案

▎一句话结论

物理隔离意味着不同租户的数据存储在不同的 Collection（集合）中，通过 project_id 等租户标识进行硬性隔离，而不是在同一个 Collection 中用 tenant_id 字段过滤——后者只是逻辑隔离，存在数据泄露和检索污染的风险。

▎核心原理

  • 逻辑隔离：所有租户的数据存在同一个 Collection 中，通过 tenant_id 字段在查询时过滤，但底层存储是共享的
  • 物理隔离：每个租户拥有独立的 Collection，租户 A 的数据和租户 B 的数据在存储层完全分离，查询时通过 Collection 名称路由
  • MCP Server 的 ingest_document Tool 接收 project_id 参数，根据租户标识将文档写入对应的 Collection

▎深入解释

逻辑隔离的最大风险是“检索污染”：如果向量检索的 top-K 召回在过滤 tenant_id 之前就执行了，那么租户 A 的查询可能会召回租户 B 的文档片段。即使你在查询时做了过滤，如果过滤条件写错了（比如拼错了字段名），数据就会泄露。

物理隔离的另一个优势是“性能隔离”：不同租户的 Collection 可以独立配置索引参数（如 HNSW 的 M 和 efConstruction），独立扩缩容。一个租户的向量数据量暴增不会影响其他租户的检索性能。

在 MCP Server 的设计中，物理隔离的实现方式是：ingest_document Tool 接收 project_id 参数，内部根据 project_id 动态路由到对应的 Collection。新租户接入时，只需要创建一个新的 Collection，不需要修改任何代码。这体现了“自助式接入”的设计理念。

▎面试加分点

  • 提到“Collection 级别的权限控制”：在网关层做 API Key 到 Collection 的映射，确保租户 A 的 API Key 无法访问租户 B 的 Collection
  • 强调“数据加密”：即使物理隔离了，敏感数据（如手机号、身份证号）在写入向量库前仍需要 AES-256 加密
  • 结合“合规审计”：物理隔离使得审计日志可以精确到“哪个租户在什么时间写入了哪些文档”

▎常见误区

  • 以为在同一个 Collection 中用 tenant_id 过滤就是“隔离”——这只是逻辑隔离，底层数据仍然共享
  • 忽略了向量检索的“过滤时机”：如果过滤在召回之后执行，可能已经泄露了其他租户的数据
  • 在 MCP Server 中硬编码 Collection 名称，导致新租户接入需要修改代码——应该用 project_id 动态路由

🛠 应用题 · Q1 · 架构设计

题型

架构设计

场景标签

优雅关闭 SIGTERM 在途任务 Checkpointer 分层发布

📝 题目

你负责一个自媒体内容生成 Agent 系统的部署架构。该系统有一个痛点：单次图文生成任务耗时较长（涉及 LangGraph 多节点编排：选题 → 写作 → 配图，平均耗时 3~5 分钟）。每次发布新版本时，直接 kill 进程会导致正在生成的任务中断，用户看到"生成失败"。同时，底层依赖一个 MCP RAG 检索服务，如果 RAG 服务还没就绪就启动业务服务，会导致启动初期大量 500 错误。

请设计一套完整的无损发布方案，覆盖以下三个层面：
1. 应用层：如何在收到终止信号时，让进程"体面地"等待在途任务完成后再退出？
2. 编排层：如何保证底层依赖服务健康检查通过后，上层业务才启动？
3. 状态层：在途任务中断后，如何保证任务状态不丢失、可恢复？

💡 参考答案

▎解题思路

  1. 应用层：利用 FastAPI 的 lifespan 异步上下文管理器捕获 SIGTERM 信号，通过全局计数器追踪在途任务数，在退出前轮询等待计数器归零。
  2. 编排层：在 Docker Compose 中使用 depends_on + condition: service_healthy，配合健康检查端点，实现自底向上的拓扑分层发布。
  3. 状态层：在 LangGraph 中使用 PostgreSQL Checkpointer 做状态持久化，每个节点执行完自动落库；进程被强杀后，下次可通过 checkpoint_id 恢复执行。

▎详细方案

第一层：应用层优雅关闭（FastAPI lifespan）

from contextlib import asynccontextmanager
from fastapi import FastAPI

active_tasks = 0

@asynccontextmanager
async def lifespan(app: FastAPI):
    # 启动逻辑：初始化 MCP 连接池
    await init_mcp_clients()
    yield
    # 终止逻辑：收到 SIGTERM 后执行
    print("收到终止信号，开始优雅终止...")
    while active_tasks > 0:
        print(f"当前还有 {active_tasks} 个任务进行中，等待 1 秒...")
        await asyncio.sleep(1)
    # 关闭底层连接
    await close_mcp_clients()
    print("所有在途任务已安全落库，服务器可以安全关闭。")

app = FastAPI(lifespan=lifespan)

@app.post("/generate/media")
async def generate_media():
    global active_tasks
    active_tasks += 1
    try:
        result = await media_agent.run()  # LangGraph 编排
        return result
    finally:
        active_tasks -= 1

核心要点：finally 块确保无论任务成功还是异常，计数器都会递减，避免计数泄漏导致进程永远无法退出。

第二层：编排层分层发布（Docker Compose）

version: '3.8'
services:
  mcp-rag-server:
    image: mcp-rag:latest
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8001/health"]
      interval: 5s
      timeout: 3s
      retries: 5
      start_period: 10s

  api-gateway:
    image: my-gateway:latest
    depends_on:
      mcp-rag-server:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/health"]

      retries: 3

  media-agent-app:
    image: media-agent:latest
    depends_on:
      api-gateway:
        condition: service_healthy

第三层：状态持久化与恢复（LangGraph Checkpointer）

from langgraph.checkpoint.postgres import PostgresSaver

checkpointer = PostgresSaver.from_conn_string(DATABASE_URL)
graph = builder.compile(checkpointer=checkpointer)

# 恢复中断的任务
async def resume_task(thread_id: str):
    config = {"configurable": {"thread_id": thread_id}}
    state_history = graph.get_state_history(config)
    # 找到最后一个成功节点之后的 checkpoint
    latest_checkpoint = state_history[0]
    # 从该 checkpoint 继续执行
    async for event in graph.astream(None, config=latest_checkpoint.config):
        yield event

▎关键细节 & 踩坑点

  • 计数器必须用 finally 递减：如果任务抛出未捕获异常而计数器不减，优雅关闭会永远等待。建议在 finally 中递减，并且加一个兜底超时（如 120 秒强制退出）。
  • start_period 不能省略：健康检查如果从容器启动第 0 秒就开始，应用还没起来就会连续失败，导致容器被反复重启。start_period: 10s 给应用预留启动时间。
  • SIGTERM 与 SIGKILL 的区别：Docker 默认先发 SIGTERM，等待 10 秒（可配置 stop_grace_period）后发 SIGKILL。如果优雅关闭逻辑超过这个窗口，任务仍会被强杀。需要根据最长任务耗时调大 stop_grace_period。
  • 多副本场景下的计数器问题：如果部署了多个 Pod，每个 Pod 有自己的 active_tasks 计数器，K8s 滚动更新时是逐个 Pod 终止的，每个 Pod 只需管好自己的在途任务即可。但如果使用集中式任务队列，需要在队列层面做"摘流量"操作（先停止消费新任务，再等待在途任务完成）。

▎可扩展优化

  • 摘流量优先：在收到 SIGTERM 后，先调用注册中心（如 Consul/Nacos）将当前实例标记为"下线"，停止接收新请求，再等待在途任务完成。这样比单纯靠计数器更可靠。
  • 任务级幂等 + 断点续跑：对每个 LangGraph 节点做幂等设计，即使节点重复执行也不会产生副作用（如重复生成配图时先检查是否已存在）。
  • K8s preStop Hook：在 Kubernetes 环境中，可以用 preStop 钩子执行一个脚本，先 sleep 几秒让 Service 摘流量，再触发优雅关闭逻辑。
  • 可观测性集成：在优雅关闭的等待循环中，定期上报当前在途任务数到 Prometheus，便于运维团队观察发布时的任务排空进度。

场景标签

多仓库部署 网关路由 平级协作 共享记忆层

📝 题目

你所在的公司同时运行着两个独立的 AI Agent 业务系统：
- FA-HR 智能客服：处理员工入职咨询、语音交互（ASR/TTS）、表单提交引导
- FA-自媒体运营：自动选题、写文案、生成配图

现在有一个业务需求：候选人在 HR 智能客服中聊到"想要一份针对我的岗位宣传文案"，客服 Agent 需要调用自媒体 Agent 的能力来生成文案，然后再转成语音返回给用户。

同时，CTO 提出了一个架构约束：不允许设计一个"总 Agent"来做统一路由分发，理由是担心单点故障和路由准确率问题。

请设计一套满足以下要求的架构方案：
1. 两个业务系统如何独立部署、独立发布？
2. 没有"总 Agent"，外部请求如何被正确路由到对应的业务系统？
3. HR 客服需要调用自媒体能力时，Agent 之间如何协作？
4. 用户在两个系统中的偏好数据如何共享？

💡 参考答案

▎解题思路

  1. 多仓库独立部署：底层 MCP 公共服务（RAG、记忆、LLM 调用）单独一个仓库，HR 客服和自媒体运营各一个业务仓库。
  2. 网关路由替代总 Agent：用 FastAPI 网关的 URL 路径规则做确定性路由，不依赖大模型"思考"。
  3. 平级接口调用：HR 客服的 LangGraph 工作流中，某个节点直接通过 HTTP 调用自媒体 Agent 的接口。
  4. 共享记忆层：两个 Agent 都读写同一个 PostgreSQL 用户画像表，通过 user_id 实现数据互通。

▎关键细节 & 踩坑点

  • 网关不要做重业务逻辑：网关只做认证、限流、路由转发。如果网关里写了大量业务判断逻辑，网关本身就会变成新的"总 Agent"。
  • Agent 间调用要设置超时和降级：如果自媒体 Agent 生成文案耗时 3 分钟，HR 客服的 HTTP 调用不能无限等待。建议设置 30~60 秒超时，超时后返回降级话术（如"文案生成中，稍后推送给您"）。
  • 共享记忆层的写入冲突：两个 Agent 同时写同一个 user_id 的画像时，要用 UPSERT（ON CONFLICT DO UPDATE）避免覆盖丢失。
  • API Key 的粒度：网关层的 API Key 应该按"业务线 + 调用方"来区分，而不是一个全局 Key 打天下。这样 HR 客服调用自媒体 Agent 时，可以用独立的 Key 做审计和限流。

▎可扩展优化

  • 引入 A2A 协议：当 Agent 间协作越来越复杂时，可以考虑引入 A2A（Agent-to-Agent）协议，标准化 Agent 间的能力发现和调用方式。
  • 异步任务队列：如果 HR 客服调用自媒体 Agent 的耗时超过用户可等待阈值，可以改为异步模式：HR 客服创建一个任务，拿到 task_id 后立即返回"生成中"，自媒体 Agent 完成后通过 Webhook 回调 HR 客服。
  • 共享记忆层升级为 MCP Memory Server：将共享记忆抽象为 MCP Server，提供统一的 read_profile / write_profile / extract_facts 工具，两个 Agent 通过 MCP 协议调用，避免直接操作数据库。

场景标签

死循环防护 状态机 节点级回滚 Checkpointer

📝 题目

你在开发一个基于 LangGraph 的自媒体内容生成 Agent，工作流包含三个节点：选题 → 写作 → 配图。其中"配图"节点调用了外部图片生成 API，该 API 经常因为 Prompt 不合规或服务过载返回失败。你的 Agent 设计了 Self-Correction（自我反思）机制：配图失败时，Agent 会反思失败原因并重试。

但上线后你发现了两个严重问题：
1. 死循环：当图片生成 API 持续返回同一种错误时，Agent 陷入"失败 → 反思 → 重试 → 再失败"的无限循环，Token 消耗暴涨。
2. 全流程重跑：配图节点失败后，整个工作流从头开始重跑，导致已经成功的"选题"和"写作"节点被重复执行，浪费了大量 Token 和时间。

请设计一套工程方案，解决这两个问题。要求：
1. 如何用显式计数器防止死循环？
2. 如何实现"只重试失败的节点，不重跑已成功的节点"？
3. 如何利用 Checkpointer 实现节点级精准回滚？

💡 参考答案

▎解题思路

  1. 死循环防护：在 LangGraph 的 State 中维护 loop_count 变量，每次进入反思/重试节点时加 1，达到硬上限（如 3 次）后强制跳出循环，走降级路由。
  2. 节点级重试：利用 LangGraph 的 Checkpointer 记录每个节点执行后的状态快照，失败时通过 get_state_history 找到"写作节点刚完成、配图节点未开始"的 checkpoint，从该点恢复执行。
  3. 动态 Prompt 注入：在重试时把前几次的失败原因注入 Prompt，引导模型换一种策略，避免"复读机效应"。

▎详细方案

第一步：State 设计

class MediaState(TypedDict):
    topic: Optional[str]           # 选题结果
    article: Optional[str]         # 写作结果
    images: Optional[list]         # 配图结果
    loop_count: int                # 重试计数器
    error_history: list            # 失败原因记录
    status: str                    # 当前状态

第二步：带计数器的反思节点

MAX_RETRY = 3

async def image_generation_node(state: MediaState) -> MediaState:
    """配图节点：调用图片生成 API"""
    try:
        images = await call_image_api(state["article"])
        state["images"] = images
        state["status"] = "completed"
    except ImageAPIError as e:
        state["error_history"].append(str(e))
        state["status"] = "failed"
    return state

async def reflection_node(state: MediaState) -> MediaState:
    """反思节点：分析失败原因，决定是否重试"""
    state["loop_count"] += 1

    if state["loop_count"] >= MAX_RETRY:
        # 达到硬上限，强制降级
        state["status"] = "degraded"
        return state

    # 动态注入失败历史到 Prompt
    error_context = "\n".join(state["error_history"])
    reflection_prompt = f"""
    你第 {state['loop_count']} 次尝试配图。
    前几次失败原因：
    {error_context}
    请换一种配图策略，避免重复之前的错误。
    """
    # 将 reflection_prompt 注入到下一轮配图节点的上下文中
    state["reflection_hint"] = reflection_prompt
    state["status"] = "retry"
    return state

第四步：节点级精准回滚（Checkpointer）

from langgraph.checkpoint.postgres import PostgresSaver

checkpointer = PostgresSaver.from_conn_string(DATABASE_URL)
graph = builder.compile(checkpointer=checkpointer)

async def resume_from_writing_node(thread_id: str):
    """从写作节点完成后、配图节点开始前的 checkpoint 恢复"""
    config = {"configurable": {"thread_id": thread_id}}

    # 获取状态历史
    state_history = graph.get_state_history(config)

    # 找到写作节点刚完成的 checkpoint
    target_checkpoint = None
    for checkpoint in state_history:
        snapshot = checkpoint.values
        if snapshot.get("article") and not snapshot.get("images"):
            target_checkpoint = checkpoint
            break

    if target_checkpoint:
        # 从该 checkpoint 恢复执行（只重跑配图节点）
        resume_config = target_checkpoint.config
        async for event in graph.astream(None, config=resume_config):
            yield event

▎关键细节 & 踩坑点

  • 计数器必须放在 State 中而非全局变量：LangGraph 的 State 是每个线程（thread_id）独立的，如果放在全局变量中，多个并发任务会互相干扰。
  • loop_count 的初始化：在图的入口节点（如 topic 节点）中必须初始化 loop_count = 0，否则多个任务复用同一个 State 结构时可能残留上次的值。
  • 降级节点的必要性：达到重试上限后，不能直接 return state 就结束，必须路由到一个降级节点，返回一个"部分成功"的响应（如"文案已生成，配图失败，请稍后手动重试"），否则用户会看到空白结果。
  • Checkpointer 的 checkpoint 粒度：默认情况下，LangGraph 在每个 super-step 后保存 checkpoint。如果配图节点内部有多个 API 调用，需要明确每个 API 调用后是否要保存 checkpoint，避免恢复时重复调用同一个 API。
  • get_state_history 的性能：如果线程历史很长，遍历所有 checkpoint 会变慢。建议在生产环境中定期清理旧的 checkpoint，或者使用 limit 参数限制返回数量。

▎可扩展优化

  • 指数退避重试：在反思节点中加入指数退避逻辑（如第 1 次重试等 2 秒，第 2 次等 4 秒，第 3 次等 8 秒），避免对下游 API 造成瞬时压力。
  • 熔断器模式：如果图片生成 API 连续失败超过阈值（如 5 次），直接触发熔断，跳过配图节点，返回降级结果。熔断器冷却期结束后再恢复调用。
  • 异步并行生成：如果一篇文章需要多张配图，可以将配图节点拆分为多个并行子任务，每个子任务独立重试，互不影响。
  • Token 消耗监控：在 loop_count 增加时，同步上报 Token 消耗到监控系统，当某个线程的 Token 消耗超过阈值时，主动中断该线程，防止成本失控。

📝 题目

你的团队负责一个 FA-HR 智能客服 Agent 系统，上线后用户反馈"回复太慢"。监控数据显示：
- 平均首字延迟（TTFT）为 15 秒，用户等待体验极差
- 随着对话轮数增加，延迟和 Token 消耗呈线性增长
- 高峰期大模型 API 调用频繁触发 429 限流

请从以下三个维度分析问题根因并给出优化方案：
1. 上下文管理：对话轮数增加后，Prompt 越来越长，如何处理？
2. 缓存机制：如何利用前缀缓存（Prefix Caching）降低 TTFT？
3. 成本控制：如何通过分层记忆和模型路由降低 Token 消耗？

💡 参考答案

▎解题思路

  1. 上下文管理：采用分层记忆架构，近期记忆保留最近 N 轮精确对话，长期记忆用异步摘要 Agent 压缩历史对话，避免全量塞入 Prompt。
  2. 前缀缓存：固定 System Prompt 和 Few-Shot 示例的 Token 序列，确保请求开头完全一致，触发模型侧的 KV Cache 复用，将 TTFT 从 15 秒压缩到 2 秒以内。
  3. 成本控制：简单意图（如"请假流程是什么"）路由到轻量 Flash 模型，复杂意图（如"帮我计算这个月的加班工资"）路由到旗舰模型，通过动态路由降低 40% 推理成本。

class LayeredMemory:
    def __init__(self, short_term_limit=5):
        self.short_term_limit = short_term_limit  # 最近 5 轮

    def build_context(self, user_id: str, current_query: str) -> str:

                                        -self.short_term_limit, -1)

        # 2. 从 PostgreSQL 获取长期摘要（异步生成的压缩画像）
        long_term_summary = pg.query(
            "SELECT summary FROM user_memory WHERE user_id = %s",
            (user_id,)
        )

        # 3. 拼接上下文
        context = f"""
        [用户长期画像]
        {long_term_summary}

        [近期对话]
        {recent_messages}

        [当前问题]
        {current_query}
        """
        return context

async def summarize_old_conversations(user_id: str):
    old_messages = redis.lrange(f"chat:{user_id}:recent", 0, -6)  # 超过 5 轮的部分
    if not old_messages:
        return

    summary = await llm.generate(
        f"将以下对话压缩为 100 字以内的用户画像摘要：{old_messages}"
    )

    # UPSERT 到 PostgreSQL
    pg.execute(
        """INSERT INTO user_memory (user_id, summary, updated_at) 
           VALUES (%s, %s, NOW()) 
           ON CONFLICT (user_id) DO UPDATE SET summary = %s, updated_at = NOW()""",
        (user_id, summary, summary)
    )

    # 从 Redis 中删除已摘要的旧消息

# prompt_builder.py
class PromptBuilder:
    def __init__(self):
        # 固定 System Prompt（Token 序列完全一致）
        self.system_prompt = """你是 FA-HR 智能客服助手。你的职责是回答员工关于考勤、请假、薪酬、社保等 HR 相关问题。
回答要求：
1. 基于提供的知识库内容回答，不要编造
2. 如果知识库中没有相关信息，明确告知用户
3. 回答简洁、专业、友好
"""
        # 固定 Few-Shot 示例（顺序和内容都不变）
        self.few_shot_examples = [
            {"q": "年假怎么算？", "a": "根据公司规定，工作满 1 年不满 10 年的员工，年休假 5 天..."},
            {"q": "病假需要什么证明？", "a": "病假需要提供二级以上医院的诊断证明..."},
        ]

    def build(self, rag_context: str, user_query: str) -> str:
        # 关键：RAG 检索片段的排序必须固定
        sorted_rag_chunks = self.sort_chunks(rag_context)

        prompt = f"""
{self.system_prompt}

[示例]
{self.few_shot_examples}

[知识库内容]
{sorted_rag_chunks}

[用户问题]
{user_query}
"""
        return prompt

    def sort_chunks(self, rag_context: str) -> str:
        """固定 RAG 检索片段的排序规则，确保相同查询的 Prompt 前缀一致"""
        chunks = rag_context.split("\n---\n")
        # 按 chunk 的 hash 排序，保证确定性
        chunks.sort(key=lambda x: hash(x))
        return "\n---\n".join(chunks)

class ModelRouter:

▎关键细节 & 踩坑点

  • 前缀缓存的前提是 Token 级完全一致：任何微小的改动（如多一个空格、换行符变化、RAG 检索结果顺序变化）都会导致前缀缓存失效。必须确保 System Prompt、Few-Shot 示例、RAG 片段排序都是确定性的。
  • RAG 片段排序的确定性：如果 RAG 检索返回的片段顺序每次不同（取决于向量相似度分数的微小波动），前缀缓存就会失效。需要在 Prompt 构建层做一次确定性排序。
  • 分层记忆的摘要时机：摘要 Agent 不能阻塞主流程。建议用 Celery/APScheduler 定时任务或消息队列异步触发，避免用户等待摘要生成。
  • Redis 和 PostgreSQL 的数据一致性：近期对话在 Redis 中，长期摘要在 PostgreSQL 中，如果 Redis 宕机导致近期对话丢失，用户会感觉 Agent "失忆"。建议 Redis 开启持久化（RDB + AOF），或者定期将近期对话同步到 PostgreSQL 做备份。
  • Flash 模型的降级策略：如果 Flash 模型回答质量不够（用户反馈"答非所问"），需要有一个自动升级机制：检测到用户连续两次追问同一问题时，自动切换到旗舰模型。

▎可扩展优化

  • 语义缓存（Semantic Caching）：对高频相似问题（如"年假怎么算"和"年假如何计算"），用向量相似度匹配缓存的历史回答，直接返回缓存结果，完全绕过 LLM 调用。
  • KV Cache 的跨请求复用：某些推理框架（如 vLLM）支持跨请求的 Prefix Caching，可以将公共前缀的 KV Cache 保存在 GPU 显存中，新请求只计算增量部分。
  • 流式输出的 TTFT 优化：通过 SSE 流式输出，在第一个 Token 生成后就立即推送给前端，用户感知的延迟从"等待完整回答"变为"看到第一个字的时间"，配合前端 ReadableStream 解析，可进一步降低 60% 的感知延迟。
  • Token 预算动态分配：根据对话轮数和用户等级，动态调整每次请求的 max_tokens 上限。VIP 用户分配更多 Token，普通用户限制在合理范围内，控制整体成本。
