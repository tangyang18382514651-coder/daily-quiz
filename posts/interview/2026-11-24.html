📌 概念题 · Q1

考点标签

Skill文件设计 · 难度：⭐⭐

📝 题目

在可商用的 Agent 工程落地中，通常不会把所有业务逻辑、Prompt 和工具权限都塞进主 Agent 的系统提示词里，而是拆分为独立的 .skill 配置文件。请解释 Skill 文件的核心结构是什么？它和普通的 Tool（工具函数）有什么本质区别？

💡 参考答案

▎一句话结论

Skill 是封装了专属 Prompt、行为准则、绑定工具和输入输出契约的独立能力包，是给 Agent 切换“专家身份”的模块化单元；而 Tool 只是无灵魂的原子代码函数，二者是“大脑能力”和“手脚工具”的关系。

▎核心原理

  • Skill 文件的标准三要素：专属局部 System Prompt、绑定的原子工具列表、明确的输入/输出 Schema
  • Tool 是无状态的函数实现，只负责执行具体动作（如查数据库、调API），不包含任何角色设定和决策逻辑
  • 主 Agent 仅负责路由调度，运行时动态加载对应 Skill，将主Prompt、Skill局部Prompt、用户输入拼接后发给大模型

▎深入解释

很多初级开发者做 Agent 时，会把“写小红书文案、查订单、安抚投诉用户”所有规则都堆在一个几千字的主 Prompt 里，最后导致大模型上下文混乱、角色串台、工具乱调。而 Skill 设计的本质是“关注点分离”：把每个垂直场景的能力做成独立的“锦囊”，就像医院的前台导诊（主Agent）只负责判断病人挂什么科，真正看病的是各个科室的专家（Skill）。
比如用户情绪激动来投诉，主Agent检测到负面情绪后，动态加载empathy_complaint.skill，此时大模型立刻切换成“客诉安抚专家”身份，严格遵循该Skill里的“先共情、再给补偿、禁止生硬话术”规则，同时仅开放赠送积分、查订单的工具权限，完全不会出现跳转到写文案、查政策的逻辑混乱。

▎面试加分点

  • 能提到Skill的权限隔离价值：不同Skill绑定不同工具，避免大模型拿到不必要的高危工具权限（比如客诉Skill不能调用删库工具）
  • 能提到Skill的可维护性：业务迭代时只需要修改对应Skill的Prompt文件，不需要动主流程代码，非技术的运营人员也能编辑调整
  • 能类比微服务架构：Skill 相当于 Agent 系统里的“微服务单元”，主Agent相当于API网关做路由转发

▎常见误区

  • 误区：认为Skill就是把Prompt拆成多个文件，本质没区别。实际上Skill不仅拆分Prompt，还绑定了专属工具集、输入输出校验、SOP流程规则，是完整的能力封装。
  • 误区：认为Skill数量越多越好。实际上过度拆分Skill会导致路由复杂度飙升，通常按业务场景边界（如政策解答、订单操作、客诉安抚）拆分即可。

📌 概念题 · Q2

考点标签

智能销售客服架构 · 难度：⭐⭐⭐

📝 题目

工业级智能销售客服系统和普通“问答式客服机器人”的核心差异是什么？一套能真正产生商业转化的智能销售系统，必须具备哪四层核心架构？

💡 参考答案

▎一句话结论

普通问答客服是“用户问什么答什么”的被动响应系统，而能转化的智能销售客服是“主动引导、拿真实案例做信任背书、靠数据飞轮持续迭代”的主动进攻系统，核心是显式状态机+数据库工具调用+数据中台的三层闭环。

▎核心原理

  • 第一层：多轮意图深挖层，基于显式状态机做槽位填充，没收集全预算、痛点、规模、上线时间四个核心信息前绝不报价
  • 第二层：真实案例背书层，通过工具调用查询企业沉淀的成交数据库，经过动态脱敏后喂给大模型生成说服力话术
  • 第三层：数据飞轮层，自动清洗所有对话语料，打标签后反哺RAG知识库和微调数据集
  • 第四层：业务外延层，基于沉淀的对话数据衍生销售培训、BI分析、精准再营销等增值业务

▎深入解释

很多公司做的智能客服之所以没用，本质是把它做成了“带搜索框的知识库”：用户问“你们系统多少钱”，机器人直接把价目表甩出去，转化率极低。因为销售的本质不是一次性问答，客户一开始说的往往是伪需求，而且大模型瞎编的案例根本没有说服力。
真正能打的销售客服，会像顶级销冠一样沟通：用户说“我想了解下你们的系统”，机器人不会直接报价，而是一步步引导“方便问下您团队目前多少人呀？现在遇到的最大痛点是效率低还是数据不准呀？”，等信息收集全了，再调用数据库找同行业的成交案例，把敏感信息脱敏成“上个月刚帮成都某头部团购平台做过类似升级，他们当时也遇到了库存同步不准的问题”，这种真实案例的说服力是大模型瞎编内容的100倍。更重要的是，所有对话数据不会浪费，清洗后既可以做销冠话术库培训新员工，还能分析客户流失的Top原因反哺产品迭代。

▎面试加分点

  • 能提到动态脱敏层的设计：案例查询不能直接返回原始数据库字段，必须经过脱敏网关替换真实公司名、联系人、财务数据，避免泄露商业机密
  • 能提到数据飞轮的ROI：系统用得越久，沉淀的案例和对话数据越多，转化效果越好，形成正向循环，而不是上线后效果一成不变
  • 能点出和普通RAG客服的差异：普通RAG只查产品说明书，销售客服要查成交案例库、客户标签库，核心目标是转化不是答疑

▎常见误区

  • 误区：认为销售客服只要Prompt写得好、会说漂亮话就行。实际上没有真实客户案例做背书，再华丽的辞藻客户也不会信，核心弹药必须来自企业自己的数据库。
  • 误区：认为槽位填充是死板的表单提问。实际上是大模型用自然的对话方式引导，不会让客户感觉到在填问卷。

📌 概念题 · Q3

考点标签

大模型量化原理 · 难度：⭐⭐⭐

📝 题目

大模型量化的核心是“牺牲精度换取效率”，请解释量化过程中缩放因子S和零点Z的作用是什么？为什么传统PTQ量化在INT4极低比特下会出现精度崩塌，而AWQ、GPTQ等算法能做到几乎不掉点？

💡 参考答案

▎一句话结论

S和Z是浮点数到整数空间映射的两个核心参数，S决定量化步长、Z保证0值精确映射；传统PTQ精度崩塌的根源是离群点拉大了缩放范围导致密集区域精度丢失，AWQ/GPTQ的核心思路是只保护1%的关键离群权重保持浮点，剩下99%普通权重量化，实现精度和体积的平衡。

▎核心原理

  • 量化映射公式：整数 = round(浮点数 / S + Z)，反量化时可以近似还原原始浮点数
  • 离群点问题：权重矩阵中存在极少数极高/极低的离群值，如果为了覆盖离群点把S调大，会导致占绝大多数的中间密集值被压缩到极小的整数区间，丢失大量细节
  • AWQ/GPTQ的核心创新：不追求所有权重量化，通过校准集识别出对激活值影响最大的1%关键权重（通常是离群通道）保留FP16精度，其余99%权重正常量化到INT4

▎深入解释

很多人以为量化就是简单把浮点数转成整数，其实是一门“找冗余”的艺术。Transformer模型本身有极强的鲁棒性，绝大多数权重的微小变化根本不会影响输出结果，但极少数关键通道的权重如果量化误差大了，整个模型的输出就会跑偏。
举个通俗的类比：你要把一张100平米的房子（浮点数范围）画到1米宽的画布（INT4整数范围，只有16个刻度）上，如果房子里有一根100米高的天线（离群点），你为了把天线画进去，就必须把比例尺调到1:100，最后房子里的家具、墙壁全都挤成一团看不清。传统PTQ就犯了这个错，为了照顾离群点牺牲了绝大多数区域的精度。而AWQ/GPTQ的思路很简单：那根天线单独用高精度画（保留浮点），剩下的房子正常用1:10的比例尺画，最后整体画面既装下了所有内容，细节也足够清晰。

▎面试加分点

  • 能说清量化带来的两个性能提升：一是显存/内存占用降低，缓解Memory Bound（内存带宽瓶颈），相同时间能读4倍参数；二是整数运算吞吐量是FP32的数倍，缓解Compute Bound（计算瓶颈），能耗更低
  • 能区分PTQ和QAT的适用场景：PTQ不需要重新训练，几分钟就能完成，适合绝大多数企业部署场景；QAT需要在训练时加伪量化节点，精度最高但成本极高，只有基础模型厂商才会用
  • 能给出实际部署的选型建议：企业本地部署直接下载社区带-AWQ/-GPTQ后缀的量化模型即可，不需要自己做量化，省时省力

▎常见误区

  • 误区：认为INT4量化精度损失很大，不能用在生产环境。实际上经过AWQ/GPTQ优化的INT4模型，精度损失通常在1%~2%以内，人几乎感知不到，但显存占用直接砍到原来的1/4，是企业部署的首选。
  • 误区：认为量化就是为了缩小模型体积。实际上更大的收益是提升推理吞吐量、降低延迟，因为整数运算单元比浮点单元快得多、功耗低得多。

📌 概念题 · Q4

考点标签

Workflow与Agent差异 · 难度：⭐⭐

📝 题目

行业里常说“Workflow框定下限，Agent提升上限”，请解释传统工作流（Workflow）、纯Agent、Agentic Workflow（智能体工作流）三者的核心差异是什么？为什么现在工业界落地的主流是Agentic Workflow而不是纯Agent？

💡 参考答案

▎一句话结论

传统Workflow是固定路径的“铁轨”，确定性100%但毫无灵活性；纯Agent是完全自主的“自动驾驶”，灵活性最高但容易跑偏不可控；Agentic Workflow是“固定轨道+自主变道”的混合架构，用Workflow保证核心流程不翻车，用Agent处理需要灵活决策的节点，是目前工业落地的最优解。

▎核心原理

  • 传统Workflow：所有执行路径、分支条件都是提前硬编码的，输入确定则输出100%确定，不会出错也不会处理意外情况
  • 纯Agent：完全靠大模型自主思考、自主选工具、自主决定下一步做什么，没有固定流程，理论上能处理任何情况，但容易出现死循环、工具调用错误、跑题
  • Agentic Workflow：把核心业务流程的骨架用Workflow（如LangGraph状态机）固定下来，在需要理解、判断、生成的节点插入Agent能力，既保证核心流程可控，又具备灵活处理异常的能力

▎深入解释

很多刚接触Agent的开发者会走两个极端：要么觉得大模型无所不能，所有逻辑都让Agent自己决定，结果上线后经常出现用户问了个无关问题，Agent就开始无限循环调用工具，或者直接给用户返回错误结果；要么觉得大模型不可靠，所有流程都硬编码成if-else，最后做出来的东西和十年前的规则机器人没区别，用户稍微问点超出规则的问题就答不上来。
举个报销流程的例子：纯Workflow的做法是硬编码“提交申请→主管审批→财务打款”，如果用户上传的发票模糊，系统直接打回，不会告诉用户哪里模糊、怎么重新拍；纯Agent的做法是让大模型全程处理报销，可能出现大模型觉得金额太大直接跳过主管审批给财务打款的严重事故；而Agentic Workflow的做法是把“提交→主管审批→财务打款”的核心流程固定死，在发票审核节点用Agent识别发票内容、判断清晰度、用自然语言告诉用户怎么修改，既不会出现越权审批的事故，又比硬编码规则灵活得多。

▎面试加分点

  • 能点出纯Agent落地的核心痛点：大模型的输出是概率性的，没有100%的确定性，对于涉及资金、权限、合规的核心流程，绝对不能让Agent自主决定流转方向
  • 能结合LangGraph的设计理念：LangGraph本质就是Agentic Workflow框架，用状态机固定流程边，节点内部用Agent做灵活处理，不是纯Agent框架
  • 能给出场景选型原则：越靠近核心交易、合规要求越高的流程，Workflow占比越高；越靠近用户交互、需要自然语言理解的环节，Agent占比越高

▎常见误区

  • 误区：认为Agentic Workflow就是Agent加了个工作流外壳，本质还是Agent。实际上核心控制权在Workflow手里，Agent只是流程里的一个执行节点，没有决定流程走向的最高权限。
  • 误区：认为纯Agent是更先进的架构。实际上工业界从来不会把核心系统的控制权交给概率性的大模型，可控性永远是生产环境的第一要求。

📌 概念题 · Q5

考点标签

Native Graph RAG缺陷 · 难度：⭐⭐⭐⭐

📝 题目

原生Graph RAG（基于社区发现的图检索增强生成）在处理复杂知识关联问题上比传统向量RAG效果好，但在实际生产落地中存在三个致命缺陷。请解释这三个缺陷是什么？为什么LightRAG的设计能部分解决这些问题？

💡 参考答案

▎一句话结论

原生Graph RAG的三个致命缺陷是社区构建Token成本极高、实体关系抽取错误没有修正机会导致满盘皆输、全局查询必须喂所有社区摘要成本不可控；LightRAG通过去掉预构建全局社区、实体和关系双粒度向量化、高低阶查询分离+原文溯源的设计，在保留图关联能力的同时大幅降低成本、提升准确率。

▎核心原理

  • 缺陷1：社区构建成本极高。原生Graph RAG需要用Leiden算法做全图社区发现，再让LLM给每个社区生成摘要，文档量大的时候Token成本是普通RAG的几十倍
  • 缺陷2：错误传播无修正。如果第一步实体关系抽取出现幻觉（比如把“刘备和关羽是君臣”抽成“刘备和关羽是仇人”），后续图结构、社区摘要全都是错的，检索出来的内容必然错误，没有兜底机制
  • 缺陷3：全局查询成本不可控。回答全局问题时必须把所有社区摘要都喂给LLM，文档量到百万级时根本放不下上下文
  • LightRAG优化点：不提前做全局社区摘要，而是把实体和关系都做向量化，查询时先做关键词匹配召回相关子图，直接关联原文Chunk做回答，同时支持低阶（具体实体）、高阶（抽象主题）、原生（原文检索）三路查询融合

▎深入解释

很多人刚接触Graph RAG时觉得它能解决传统RAG“找不到关联知识”的问题，比如问“三国时期刘备集团的核心人物有哪些”，传统向量RAG可能只能召回和刘备最相关的几个片段，而Graph RAG能沿着刘备的关系边找到关羽、张飞、诸葛亮等所有关联人物。但原生Graph RAG的工程成本极高，光构建阶段的Token成本就很多企业承受不起，而且实体抽取是整个流程的单点故障，只要LLM抽错一个关系，整个图的结构就歪了，最后生成的答案比传统RAG还离谱。
LightRAG的思路更务实：不追求做完美的全局图结构，而是把实体和关系都当成可检索的向量单元，查询的时候动态召回相关的子图，不需要提前构建全量社区，而且最后一定会关联到原始文本Chunk，相当于给图检索加了一层原文兜底，即使关系抽错了，也能通过原文内容修正错误，不会出现完全胡编的情况。

▎面试加分点

  • 能说清Graph RAG和传统向量RAG的适用场景差异：Graph RAG适合需要多跳关联、全局总结的场景（如分析人物关系、事件脉络），传统向量RAG适合单点事实查询的场景（如查某个政策的具体条款），二者不是替代关系是互补关系
  • 能提到Graph RAG落地的核心前提：实体关系抽取的准确率必须足够高，通常需要做抽取结果的Gleaning（二次校验），不能让LLM抽完直接用
  • 能点出成本问题：原生Graph RAG的构建成本是O(n²)级别，文档量超过10万篇时构建时间和Token成本会指数级上升，根本不适合大规模知识库场景

▎常见误区

  • 误区：认为Graph RAG比传统向量RAG更先进，应该全量替换。实际上90%的企业知识库场景都是单点查询，传统向量RAG+重排的效果已经足够好，成本只有Graph RAG的1/10，没必要为了10%的多跳场景上复杂的Graph RAG。
  • 误区：认为图结构是语义理解。实际上知识图谱是纯数学的关联结构，本身不理解语义，关联关系错了就完全没用。

📌 概念题 · Q6

考点标签

多Agent通信机制 · 难度：⭐⭐⭐

📝 题目

现代多Agent系统（如LangGraph实现）已经不再采用Agent之间直接发消息的点对点通信模式，而是基于共享全局State（状态）做通信。请解释这种共享状态通信模式的核心机制是什么？它是如何实现串行、循环、并行三种流程控制的？

💡 参考答案

▎一句话结论

基于共享State的多Agent通信本质是“全局账本机制”：所有Agent不直接对话，只负责从全局State读数据、加工后写回State，流程流转完全由图的边（Edges）控制，相比点对点通信具备更好的可观测性、可追溯性和流程可控性。

▎核心原理

  • 串行/循环控制：通过路由边定义节点流转规则，前一个Agent写完State后自动触发下一个Agent；如果审核Agent发现State里的内容不合格，路由边指向回退到上一个节点，形成循环直到满足条件
  • 并行控制：通过Fan-out（分流）边让一个节点同时触发多个并行Agent，每个Agent把结果写到State的列表字段里，后续汇聚节点进入阻塞等待，直到所有并行Agent都完成写入才被唤醒执行（Fan-in汇聚）
  • 高并发场景扩展：如果并发量极高，不适合在内存里维护State，就把State放到数据库/Redis里，Agent通过网关接口读写State，实现分布式部署

▎深入解释

早期的多Agent设计很多是模仿人类微信群的模式：Agent之间互相发消息，你一句我一句沟通，最后出结果。这种模式看起来很智能，但工程上问题极大：首先是消息传递的路径不可控，很容易出现两个Agent无限循环聊天的死锁；其次是状态散落在各个Agent的对话历史里，出了问题根本没法排查到底哪一步错了；最后是并行实现非常复杂，要自己写同步逻辑等待所有Agent返回。
而共享State模式就像工厂的流水线传送带：全局State就是传送带上的工件，每个Agent就是工位上的工人，工人只需要从传送带上拿工件加工，做完放回去，传送带（图路由）自动把工件送到下一个工位。要做串行就把工位排成一条线，要做打回重改就加一条反向传送带，要做并行就把传送带分成好几条同时送到多个工位，最后再汇总到一条传送带上。整个流程完全可视化，每一步谁改了什么数据都存在State里，排查问题极其方便。

▎面试加分点

  • 能点出共享State模式的可观测性优势：每一步的State变化都可以持久化到Checkpointer，支持断点续传、人工介入（Human-in-the-loop），比如审核节点可以暂停流程，等人工修改完State里的内容再继续执行
  • 能对比点对点通信的缺陷：点对点通信没有全局状态视角，容易出现消息风暴、死锁、状态不一致，调试难度极大，只适合极小规模的多Agent原型
  • 能提到高并发场景的State存储选型：低并发场景可以用内存State，高并发生产环境必须用Redis/PostgreSQL做持久化State存储，避免服务重启状态丢失

▎常见误区

  • 误区：认为共享State就是所有Agent都能随便改State里的任何字段。实际上每个Agent应该只拥有修改自己负责字段的权限，避免多个Agent同时改同一个字段导致写入冲突。
  • 误区：认为并行执行需要写复杂的多线程代码。实际上LangGraph这类框架已经把Fan-out/Fan-in的并行、等待、汇总逻辑封装好了，只需要画好节点之间的连线，框架自动处理多线程调度。

📌 概念题 · Q7

考点标签

Harness与Runtime架构 · 难度：⭐⭐⭐

📝 题目

工业级Agent系统通常会拆分为Harness（控制面）和Runtime（执行面）两层架构，业界常用“缰绳和马车”来形容二者的关系。请解释这两层的核心职责边界是什么？两层分别出故障时会有什么不同的故障表现？

💡 参考答案

▎一句话结论

Harness是Agent的“大脑和缰绳”，负责所有业务逻辑、流程编排、Prompt组装、LLM调用和输出解析，决定Agent“怎么想、怎么走”；Runtime是Agent的“马车和跑道”，负责提供沙箱执行环境、持久化存储、外部API调用等基础设施，决定Agent“在哪跑、拿啥干”，二者必须严格解耦。

▎核心原理

  • Harness核心职责：动态组装Prompt、驱动LLM思考、维护状态机路由、解析LLM输出的JSON和工具调用指令，所有和业务逻辑相关的代码都在这一层
  • Runtime核心职责：提供安全的Docker/WASM代码执行沙盒、管理数据库持久化连接（Checkpointer）、实际执行外部API/工具调用，完全不关心业务逻辑
  • 故障表现差异：Harness出故障会导致逻辑死循环、Prompt注入、理解错误、路由走错，属于“脑子坏了”；Runtime出故障会导致权限不足、沙箱超时、数据库连接失败、工具调用报错，属于“手脚坏了”

▎深入解释

很多小团队做Agent时会把所有逻辑混在一起：流程编排代码里直接写死数据库连接，沙箱里塞了一堆业务Prompt，最后改个Prompt要重启整个执行环境，沙箱出问题把整个业务流程带崩。分层架构的核心思路是让专业的层做专业的事：Harness层是纯业务逻辑，通常是轻量级的CPU服务，可以快速迭代、频繁发布，改个Prompt只需要重启Harness服务，完全不影响正在运行的沙箱任务；Runtime层是重基础设施，稳定优先，不会因为业务逻辑调整而频繁变更，比如沙箱镜像可能几个月才更新一次，数据库连接池是提前初始化好的。
举个通俗的类比：Harness就是坐在马车上的车夫，负责看路、拉缰绳、决定往哪走；Runtime就是拉车的马和脚下的路，负责提供动力、承载重量。车夫脑子糊涂走错路（Harness故障），车会往错误的方向跑但还能动；如果马腿断了或者路塌了（Runtime故障），车直接动不了，但车夫的脑子是清醒的。

▎面试加分点

  • 能提到分层架构的部署优势：Harness通常部署在普通CPU容器上，启动快、弹性伸缩快；Runtime中需要GPU/重依赖的沙箱、模型服务可以独立部署，不需要和Harness绑在一起扩缩容，资源利用率更高
  • 能提到安全边界：Runtime层是安全防线，即使Harness被Prompt注入攻击发出恶意指令，Runtime层的沙箱权限控制、API鉴权也能阻止高危操作，不会让攻击穿透到底层基础设施
  • 能结合之前的Docker打包最佳实践：多Dockerfile方案本质就是把Harness（路由Agent，轻量镜像）和Runtime（数据Agent、沙箱，重量级GPU镜像）分开打包，独立部署

▎常见误区

  • 误区：认为Runtime就是大模型运行时。实际上Runtime不仅包含大模型推理环境，还包含代码沙箱、数据库、API网关等所有执行相关的基础设施，大模型只是Runtime里的一个组件。
  • 误区：认为Harness必须和Runtime部署在同一个服务里。实际上生产环境通常是分离部署的，Harness通过RPC调用Runtime的接口执行任务，完全可以独立扩缩容。

📌 概念题 · Q8

考点标签

大模型显存估算 · 难度：⭐⭐

📝 题目

企业本地部署大模型时，经常出现“模型包刚好能放进显存，但一跑并发就OOM（显存溢出）”的问题。请解释大模型运行时的显存占用由哪两部分组成？为什么单张24G显存的RTX4090推荐部署14B INT4量化模型（约9G），而不是7B INT4模型（约4.5G）？

💡 参考答案

▎一句话结论

大模型运行时总显存占用 = 模型权重体积 + KV Cache（上下文缓存）占用，只算模型体积不算KV Cache是显存规划最常见的错误；24G显卡部署14B INT4模型剩下的15G显存足够容纳多用户并发的KV Cache，资源利用率最高，而部署7B模型会浪费大量显存。

▎核心原理

  • 模型权重显存：加载模型参数本身占用的显存，和参数量、量化精度正相关，INT4精度下1B参数约占0.5G，是固定开销
  • KV Cache显存：推理时存储每个用户上下文的Key/Value缓存占用的显存，和并发用户数、上下文长度正相关，是动态开销，用户越多、对话越长，占用越大
  • 显存规划原则：必须给KV Cache预留至少50%以上的显存空间，否则并发上来后KV Cache没地方放，就会出现OOM，或者服务自动把上下文截断，导致长对话失忆

▎深入解释

很多新手部署大模型时，会算“7B INT4模型才4.5G，我24G显存肯定能跑，还能剩好多”，结果上线后只要有3~5个用户同时用，服务直接崩了。核心原因就是忘了算KV Cache的开销：大模型生成每个Token的时候，都要用到之前所有上下文的Key和Value，如果每次都重新计算，速度会慢到无法接受，所以必须把这些KV值存在显存里，这部分开销是动态增长的。
比如14B INT4模型权重占9G，剩下15G显存给KV Cache，大概能支撑10~20个用户同时用10K左右的上下文对话，刚好是单部门使用的并发量，资源利用率能到90%以上。如果部署7B INT4模型，权重只占4.5G，剩下近20G显存给KV Cache，确实能支持更高的并发，但7B模型的逻辑能力比14B差很多，相当于花同样的硬件钱，买了个能力更差的模型，剩下的显存其实大部分时间都用不上，纯粹浪费。

▎面试加分点

  • 能提到vLLM的PagedAttention技术：像操作系统管理内存一样管理KV Cache显存，减少显存碎片，比原生HuggingFace推理的KV Cache利用率高2~4倍，同样的显存能支持更高的并发
  • 能给出不同场景的显存规划经验：单卡24G最优是14B INT4，单卡48G（RTX6000 Ada/A10）最优是32B INT4/72B INT4，4卡H200最优是72B BF16原生精度
  • 能提到长上下文场景的额外开销：如果要支持128K长上下文，KV Cache的开销会比短上下文场景大好几倍，需要预留更多显存，不能按短对话的标准规划

▎常见误区

  • 误区：认为模型越小，推理速度越快。实际上在显存足够的情况下，大batch并发时，GPU算力利用率越高，速度反而越快，小模型占显存少，GPU算力喂不满，速度不一定比大模型快多少，能力还差很多。
  • 误区：认为KV Cache可以存在内存里。实际上KV Cache存在内存里会导致推理速度慢10倍以上，必须放在显存里才能达到最优性能。

📌 概念题 · Q9

考点标签

企业部署方案选型 · 难度：⭐⭐⭐

📝 题目

企业本地部署大模型通常有三个梯度的方案：轻量级单机方案、中量级私有云方案、集团级AI工厂方案。请解释这三个方案分别适合什么阶段的企业？为什么行业反复强调“不要一开始就上顶配B200集群，要先从轻量方案跑通ROI再升级”？

💡 参考答案

▎一句话结论

轻量方案（2张4090，成本4-8万）适合微型企业/单部门验证场景，中量方案（4卡H200，成本40-60万）适合中型企业核心业务落地，集团级方案（8卡B200集群，成本百万级）适合大型企业全场景覆盖；一开始就上顶配的核心问题是ROI极低，业务没跑通前硬件投入很容易浪费，而且数据没准备好的话再好的模型也没用。

▎核心原理

  • 轻量方案优势：成本极低，普通后端工程师就能维护，能跑32B INT4模型，足够支撑知识库、代码助手等单部门场景，1~2周就能上线验证业务价值
  • 中量方案优势：能跑70B/72B BF16原生精度模型，不需要重度量化，逻辑能力强，能支撑多Agent编排、金融计算等复杂核心业务，支持几千员工并发使用
  • 集团级方案优势：能跑671B级别的MoE大模型（如DeepSeek-R1），支持上万并发的深度推理场景，但需要专门的MLOps团队、液冷机房改造、电力扩容，隐性成本极高
  • 落地优先级原则：大模型项目的核心瓶颈永远是数据不是算力，80%的效果提升来自高质量的私有数据清洗，不是模型参数变大，先跑通业务验证价值再升级硬件，风险最低

▎深入解释

很多企业刚接触大模型时容易陷入“算力焦虑”，觉得必须买最好的卡、跑最大的模型才叫AI转型，结果花几百万买了B200集群，最后发现内部数据全是乱码PDF、过期的Wiki文档，RAG做出来答非所问，Agent流程没理顺，最后集群只能用来跑个聊天机器人，ROI极低，项目直接烂尾。
正确的落地路径应该是小步快跑：先花几万块买两张4090，找一个最高频、最痛的小场景（比如HR政策问答、客服知识库），把内部数据清洗干净，跑通流程，算出来“这个系统每年能帮公司省多少人力成本”，验证了ROI之后，再根据业务需求升级硬件。如果连小场景都跑不出价值，买再贵的硬件也是浪费。就像开餐馆，先租个小门面把菜的味道做好、验证有回头客了，再扩店面开分店，而不是一开始就租个几千平的豪华酒楼，最后菜不好吃没人来，房租都付不起。

▎面试加分点

  • 能提到隐性成本：顶配B200集群单机功耗15kW，相当于普通家庭10台空调同时开的功率，很多企业机房的供电、散热根本达不到要求，还要额外花几十万做电力扩容和液冷改造，这些成本经常被忽略
  • 能提到MoE模型的优势：DeepSeek-R1这类MoE模型虽然总参数671B，但每次推理只激活37B左右的参数，在B200的FP4精度加持下，推理速度和成本甚至比70B稠密模型还优，但只有并发量足够高的时候才能体现出成本优势
  • 能给出ROI测算逻辑：大模型部署的回本周期通常是12~18个月，如果按每天调用的Token量算，自建集群的成本低于调用公有云API成本时，再升级硬件才是划算的

▎常见误区

  • 误区：认为模型越大效果越好。实际上如果企业私有数据清洗得差，70B模型的效果还不如用干净数据微调的7B模型，数据质量的影响远大于模型大小。
  • 误区：认为本地部署一定比调用公有云API便宜。如果并发量很低，每天只有几十次调用，调用公有云API比自己买服务器便宜得多，本地部署只有达到一定并发量之后才有成本优势。

📌 概念题 · Q10

考点标签

LangGraph容器化部署 · 难度：⭐⭐⭐

📝 题目

在K8s上部署LangGraph多Agent系统时，同一个代码仓库下的不同Agent节点，推荐采用多Dockerfile方案分别打包镜像，而不是打一个通用镜像通过启动参数区分角色。请解释为什么多Dockerfile方案是生产环境首选？这种方案的核心架构原则是什么？

💡 参考答案

▎一句话结论

多Dockerfile方案的核心优势是实现镜像的轻量化和解耦，避免把重依赖（如CUDA、PyTorch）打包到不需要GPU的轻量节点镜像里，导致K8s弹性伸缩时镜像拉取慢、资源浪费；其核心原则是每个节点的镜像只包含自己需要的最小依赖，通过网络接口做服务间通信。

▎核心原理

  • 依赖差异问题：LangGraph里不同节点的依赖差异极大，路由节点只需要FastAPI、LangChain核心库，镜像只有几百M；数据分析、代码执行节点需要PyTorch、Pandas、CUDA驱动，镜像有几个G甚至十几G
  • 弹性伸缩效率问题：K8s弹性扩容时需要先拉取镜像，如果路由节点的镜像里打包了CUDA等重依赖，镜像体积会达到几个G，扩容时拉取镜像需要几分钟，根本应对不了突发流量
  • 解耦架构原则：每个Agent节点通过FastAPI/gRPC封装成独立的网络服务，节点之间通过K8s Service做网络通信，不需要共享代码内存，完全解耦，可以独立发布、独立扩缩容、独立分配资源

▎深入解释

很多开发者图省事，把整个项目所有依赖都写到一个requirements.txt里，打一个通用镜像，部署的时候通过启动参数决定跑哪个节点。这种方案在开发阶段没问题，到了生产环境会遇到大麻烦：比如大促的时候路由节点需要扩容10个副本，每个副本都要拉取10G的镜像，等镜像拉完流量高峰都过去了；而且路由节点是纯CPU服务，根本不需要CUDA，把CUDA打包进去不仅浪费镜像仓库带宽，还会增加容器启动时间、攻击面。
多Dockerfile方案就像寄快递：路由节点是文件，只需要用文件袋（轻量基础镜像）装，快递员骑着电动车就能送，速度快成本低；数据节点是重家电，需要用木箱（CUDA基础镜像）打包，用货车送。如果不管什么东西都用大木箱装，送文件的成本和送家电一样高，效率极低。而且每个服务独立打包之后，改了路由节点的代码只需要重新构建路由镜像，数据节点完全不受影响，发布风险也更小。

▎面试加分点

  • 能提到资源调度优势：K8s可以根据节点的资源需求调度到不同的节点池，轻量CPU节点调度到普通CPU服务器，GPU节点调度到GPU服务器，不会出现GPU服务器上跑一堆不需要GPU的轻量容器浪费算力的情况
  • 能对比两种方案的适用场景：单镜像变参启动方案只适合所有节点依赖几乎一致的小型项目，生产环境多节点、依赖差异大的场景必须用多Dockerfile方案
  • 能提到Monorepo的最佳实践：不需要把代码拆成多个仓库，同一个仓库下通过不同Dockerfile管理不同镜像，CI/CD流程里通过-f参数指定Dockerfile构建即可，兼顾代码复用和镜像轻量化

▎常见误区

  • 误区：认为多Dockerfile会导致代码重复、维护麻烦。实际上公共代码可以放在同一个目录下，Dockerfile构建时只需要把公共代码复制进去，依赖分开写即可，维护成本并没有增加多少，但带来的性能提升是巨大的。
  • 误区：认为节点之间通信必须用LangGraph的内置状态流转。实际上生产环境中把每个节点封装成独立的HTTP/gRPC服务之后，即使不用LangGraph，也可以通过API调用串联流程，架构灵活性更高。

场景标签

.skills技能体系 模块化Agent 智能客服系统

📝 题目

某中型零售企业计划搭建全渠道智能客服系统，需要覆盖政策咨询、订单操作、客诉安抚三类核心场景。团队最初尝试把所有规则、Prompt、工具都写在一个主Agent里，上线后出现三个严重问题：① 客诉场景下Agent经常用生硬的政策话术回复情绪激动的用户，导致投诉升级；② 订单退款场景下Agent偶尔跳过身份校验直接调用退款接口，存在资损风险；③ 每次修改某一类场景的话术，都要重新测试整个系统，迭代效率极低。请结合.skill文件的设计思想，设计一套模块化的客服Agent架构，解决上述问题，并说明模块边界、路由逻辑和运行机制。

💡 参考答案

▎解题思路

  1. 第一步：先拆解根因——单块Prompt的核心问题是“角色冲突”，同一个系统Prompt里同时要求“严谨遵守规则”“温柔安抚情绪”“高效处理订单”，大模型会在不同目标之间摇摆，必然出现行为漂移。
  2. 第二步：按照“单一职责”原则拆分独立Skill单元，每个Skill只负责一类场景的专属人设、SOP流程、绑定工具，从根源上避免角色混淆。
  3. 第三步：设计前置路由层，不把路由判断交给业务Skill，而是用轻量级分类器做意图+情绪的双层识别，精准激活对应Skill。
  4. 第四步：设计动态加载机制，运行时只把当前激活Skill的Prompt和工具注入上下文，避免无关规则干扰大模型判断。

▎详细方案

整体架构分为三层：
1. 接入与路由层（前台接待）：只做两件事，一是做用户意图分类（政策咨询/订单操作/客诉安抚），二是做情绪识别（平静/不满/暴怒）。这一层用小参数模型（如Qwen3-7B）或者微调后的BERT分类器即可，不需要调用大模型，响应速度快、成本低。
- 路由规则优先级：情绪识别优先级 > 意图识别。如果检测到用户暴怒，无论用户说的是订单问题还是政策问题，先激活客诉安抚Skill，等情绪平稳后再路由到对应业务Skill。
2. Skill能力层（专家坐席）：拆分为三个独立的.skill配置文件，每个文件完全独立：
- policy_expert.skill：System Prompt明确要求“严格基于RAG知识库回答，无答案直接转人工，禁止编造”，绑定工具仅为向量知识库查询工具，无任何写操作权限。
- order_handler.skill：System Prompt明确写入SOP流程“第一步必须校验用户手机号+验证码，校验通过后才能查询/修改订单，禁止跳过校验步骤”，绑定工具为短信发送接口、订单查询/修改接口，严格限制工具调用的前置条件。
- empathy_complaint.skill：System Prompt明确要求“第一句必须情绪认同，禁止讲规则、禁止甩锅，先给出积分补偿方案”，绑定工具为CRM积分赠送接口，无订单修改权限。
3. 运行时引擎层：参考Python动态加载逻辑，路由层确定要激活的Skill后，引擎读取对应YAML配置，将主Prompt（通用客服礼貌规范）+ Skill专属System Prompt + Skill绑定的工具列表，动态拼接成最终的LLM请求，其他Skill的规则和工具完全不注入上下文。
- 流程示例：用户输入“老子昨天申请退款到现在没动静！”，路由层检测到“暴怒”情绪，优先加载empathy_complaint.skill，此时大模型只能看到安抚话术要求和积分赠送工具，看不到退款接口，自然不会直接操作订单；等用户情绪平稳、表示接受补偿后，路由层再切换到order_handler.skill，走身份校验+退款查询流程。

▎关键细节 & 踩坑点

  • 绝对不能让Skill自己决定是否调用其他Skill，路由权必须收归中央路由层，否则会出现Skill之间互相跳转、流程死循环的问题。
  • 每个Skill绑定的工具必须做最小权限原则：政策Skill绝对不能给订单修改权限，客诉Skill绝对不能直接操作退款，从工具层堵住资损风险，不能仅靠Prompt约束。
  • Skill的Prompt里必须把SOP流程写成“硬约束步骤”，比如订单Skill的第一步必须是身份校验，要明确写“如果未完成校验，禁止调用任何订单相关工具”，不能只写“请注意校验用户身份”这种软提示。
  • 不要在主Prompt里写任何具体场景的规则，主Prompt只保留通用礼貌规范，所有场景逻辑全部下沉到Skill文件，否则还是会出现角色干扰。

▎可扩展优化

  • 后续新增场景（如发票开具、物流查询）只需要新增对应的.skill文件，不需要修改原有逻辑，做到“开-闭原则”，迭代时只需要测试新Skill即可，不需要全量回归。
  • 可以给Skill增加“激活置信度”阈值，如果路由层对意图判断的置信度低于0.8，不要强行激活Skill，而是先反问用户澄清需求，避免路由错误导致答非所问。
  • 可以增加Skill执行后的结果校验环节，比如订单Skill调用退款接口前，引擎层做二次校验：检查是否已经完成身份验证，从代码层绕过LLM的不确定性，彻底堵住资损漏洞。

场景分析题

场景标签

智能销售客服 数据飞轮 商业价值落地

📝 题目

某ToB企业服务公司计划上线AI智能销售客服，替代部分人工销售做初步线索筛选。产品团队最初的方案是：对接公司产品知识库做RAG，用户问什么就答什么，能留资就转人工。但业务负责人认为这个方案价值太低，只是个“高级问答机器人”，无法真正提升销售转化，也无法给公司沉淀长期资产。请结合智能销售系统的商业底层逻辑，分析“纯RAG问答客服”和“工业级智能销售系统”的核心差距是什么？并设计一套能形成数据飞轮的完整落地方案，说明如何从“一次性问答工具”升级为“能持续产生商业价值的业务系统”。

💡 参考答案

▎解题思路

  1. 第一步：先定位纯RAG问答的本质缺陷——它是“被动响应”的，用户问什么答什么，既不会主动挖掘需求，也不会用真实案例建立信任，更不会沉淀数据，ROI极低。
  2. 第二步：按照销售转化的漏斗逻辑分层设计能力：从最上层的意图深挖，到中间层的信任建立，再到底层的数据沉淀，最后延伸到数据的二次商业变现。
  3. 第三步：设计数据闭环流程，让每一次对话都能反过来优化系统本身，形成飞轮效应，而不是对话结束就数据丢失。
  4. 第四步：跳出“客服”本身的边界，设计基于对话数据的衍生业务场景，让系统的价值从“降本”延伸到“增收”。

▎详细方案

纯RAG问答客服和工业级智能销售系统的核心差距体现在三个维度：
| 维度 | 纯RAG问答客服 | 工业级智能销售系统 |
|------|--------------|--------------------|
| 交互逻辑 | 被动响应，有问必答，用户问完就走 | 主动引导，通过多轮对话挖透需求，推动转化 |
| 信任建立 | 只会讲通用产品介绍，内容空泛 | 动态匹配同行业脱敏成功案例，用真实战绩建立信任 |
| 长期价值 | 对话数据无沉淀，系统永远不会进化 | 形成数据飞轮，数据反哺模型、反哺业务，衍生更多价值 |

完整落地方案分为四层：
1. 第一层：多轮意图深挖层（解决“伪需求”问题）
不要用户说“我想了解一下产品”就直接发产品介绍，而是基于显式状态机做槽位填充（Slot Filling），必须收集到四个核心信息才进入方案推荐环节：客户所属行业、团队规模、核心痛点、预算范围、期望上线时间。如果信息不全，Agent会主动引导提问，比如“方便问下您这边目前团队大概多少人吗？我可以给您匹配最合适的版本”，而不是被动等用户提问。
2. 第二层：动态案例匹配层（解决“信任不足”问题）
不要让大模型瞎编案例，而是打通公司历史成交客户数据库。当Agent识别到用户属于某个行业、提到某个痛点时，自动触发工具调用：第一步根据用户标签（行业=制造业、规模=500人、痛点=库存不准）检索匹配的成功案例；第二步经过数据脱敏网关，把真实客户名、合同金额、联系人信息替换为“某长三角头部制造企业”“数百万元级合作”；第三步把脱敏后的案例传给大模型润色成自然话术，比如“巧了，我们上个月刚帮苏州一家500人规模的制造企业解决过一模一样的库存不准问题，他们之前每个月盘点要花一周时间，上线后准确率提到了99.8%”，说服力远强于通用产品介绍。
3. 第三层：数据中台清洗层（搭建飞轮底座）
所有对话语料、录音转写结果全部进入数据中台，用轻量级开源大模型做自动化清洗：剔除无效对话、无意义语气词，自动给对话打标签（如“高意向客户”“因价格流失”“竞品对比提及”“异议未解决”）。清洗后的数据一方面沉淀为新的RAG知识库（比如用户最近常问的新问题、新的竞品对比点），另一方面作为后续模型微调的黄金数据集，让Agent越来越懂销售话术。
4. 第四层：业务外延层（放大商业价值）
数据中台建好后，不止服务于客服本身：① 做AI销售培训：用高转化对话和流失案例生成“刁钻客户模拟器”，让新销售和AI对练，缩短培训周期；② 做BI分析：自动统计客户拒绝的Top3原因、竞品提及率变化，反哺产品迭代；③ 做精准再营销：给半年前因价格流失的客户打上标签，公司做促销活动时由Agent自动发起个性化二次触达。

▎关键细节 & 踩坑点

  • 槽位填充不能硬来，不要像查户口一样连续问用户五个问题，要在对话中自然引导，比如用户问“你们多少钱”，不要直接报价，而是说“不同版本价格不一样，方便问下您这边主要想解决什么问题吗？我给您算下最划算的方案”。
  • 案例脱敏必须做网关层硬处理，不能靠大模型自己脱敏，否则大模型出现幻觉会把真实客户名、合同金额说出去，造成严重的客户信息泄露事故。
  • 数据标注不要一开始就找人工标注，先用7B级别的小模型做自动化标注，人工只需要抽检10%的结果修正，成本能降低90%。
  • 不要一开始就想着做微调，前3个月优先用RAG更新知识库，等积累了至少1万条高质量标注对话后，再考虑用LoRA做轻量微调，否则数据量不够反而会把模型调坏。

▎可扩展优化

  • 可以对接CRM系统，把Agent识别到的高意向客户标签、核心痛点自动同步给人工销售，人工销售跟进时可以直接看到之前的对话记录和客户需求，不需要重复提问，大幅提升转化效率。
  • 可以增加对话质量实时评分功能，当Agent和用户对话时，实时检测是否出现了“话术生硬”“答非所问”“未收集到关键信息”等问题，及时触发人工介入，避免流失高价值客户。
  • 可以基于历史转化数据训练“意向度预测模型”，根据用户的提问内容、回复速度、情绪变化，实时预测客户成交概率，高概率客户优先转人工接待，把人力用在刀刃上。

2. 在线查询阶段（Query流程）
核心思路是查询时动态生成高低层级检索词，三路并行召回，不需要提前构建全局摘要：
python def query_lightrag(question: str, graph, entity_embs, relation_embs, chunk_map): # 步骤1：让LLM把问题拆解为两类检索关键词 # low_level：具体实体、事件关键词，用于回答局部细节问题（如“刘备”“关羽”“温酒斩华雄”） # high_level：抽象主题、概念关键词，用于回答全局问题（如“蜀汉权力结构”“三国鼎立战役”） low_keywords, high_keywords = llm_extract_keywords(question) # 步骤2：三路并行检索 # 2.1 Low-level检索：用具体关键词匹配实体/关系向量，召回命中的节点、一阶邻居、关联边，以及对应的原文Chunk low_entities = vector_search(low_keywords, entity_embs, top_k=10) low_subgraph = extract_subgraph(graph, low_entities, hop=1) low_chunks = get_related_chunks(low_subgraph, chunk_map) # 2.2 High-level检索：用抽象关键词匹配实体/关系向量，召回更大范围的子图，覆盖全局关联信息 high_entities = vector_search(high_keywords, entity_embs, top_k=20) high_subgraph = extract_subgraph(graph, high_entities, hop=2) high_chunks = get_related_chunks(high_subgraph, chunk_map) # 2.3 Native原文检索：和传统RAG一样，直接用问题向量匹配原文Chunk，兜底召回未被图覆盖的细节 native_chunks = vector_search_raw_text(question, chunk_map, top_k=3) # 步骤3：结果去重融合，把三类来源的Chunk、子图结构信息合并，去掉重复内容 all_context = merge_and_deduplicate(low_chunks, high_chunks, native_chunks, low_subgraph, high_subgraph) # 步骤4：把融合后的上下文传给LLM生成回答，同时附带来源ChunkID方便溯源 answer = llm_generate(question, all_context) return answer

和原生GraphRAG相比，LightRAG的核心优势：
1. 构建成本极低：不需要全量跑Leiden社区发现、不需要给每个社区生成摘要，Token消耗只有原生GraphRAG的10%不到，构建时间从几小时缩短到几分钟。
2. 错误影响范围小：原生GraphRAG如果某条关系抽取错误，会导致社区划分错误、全局摘要错误，最终回答满盘皆输；LightRAG是查询时动态召回子图，单个关系错误只会影响局部检索结果，不会污染全局摘要。
3. 增量更新友好：新增文档时只需要抽取新Chunk的实体关系、追加到图里即可，不需要重新计算全量社区、重新生成所有摘要，适合知识持续更新的场景。

▎关键细节 & 踩坑点

  • 实体关系抽取时必须增加gleaning（二次校验）环节，第一次抽取完后，让LLM再检查一遍“当前Chunk里是否还有未抽取的重要实体/关系”，能减少30%以上的抽取遗漏错误。
  • 子图召回时hop数不要设太大，low-level检索设1跳邻居足够，high-level检索最多设2跳，否则会召回大量无关节点，反而干扰大模型判断，还会增加Context长度。
  • 必须保留native原文检索作为兜底，因为实体抽取不可能做到100%准确，有些细节信息可能没有被抽成实体/关系，直接查原文能避免漏召回。
  • 向量库要分开存实体向量和关系向量，不要混在一起，因为实体是节点、关系是边，检索时的权重和匹配逻辑不一样，分开存召回准确率更高。

▎可扩展优化

  • 可以给图中的边增加权重，根据两个实体在同一个Chunk里共现的次数、共现的距离计算权重，检索时优先召回权重高的关系，减少无关边的干扰。
  • 对于高频的全局类问题，可以在查询后缓存对应的子图和摘要，下次问类似问题时直接返回缓存结果，不需要每次都重新遍历子图，进一步降低查询延迟和Token成本。
  • 可以增加实体消歧环节，比如《三国演义》里有两个“马忠”（东吴的擒关羽的马忠、蜀汉的将领马忠），抽取实体时结合上下文给实体加唯一ID，避免检索时把两个不同的人混淆。

🛠 应用题 · Q4 · 排障优化题

题型

排障优化题

场景标签

大模型量化部署 显存优化 成本优化

📝 题目

某创业公司初期为了快速验证业务，采购了2张消费级RTX 4090D（单卡24GB显存，共48GB），用vLLM部署了Qwen2.5-14B的FP16原生模型，服务内部知识库问答业务，上线初期并发量低（同时在线5-10人），运行稳定。随着业务推广，并发量涨到同时在线30人以上，服务频繁出现两个问题：① 高峰期经常出现CUDA OOM（显存溢出）错误，服务崩溃重启；② 正常请求的TTFT（首字延迟）从原来的300ms涨到3s以上，用户体验极差。运维同学一开始以为是显存不够，申请预算买新卡，但CTO要求先做工程优化，在不增加硬件成本的前提下解决问题。请分析故障根因，给出完整的优化方案，量化说明每个优化手段能带来的显存节省和性能提升，最终目标是在现有48GB显存上稳定支撑50人并发，TTFT降到1s以内。

💡 参考答案

▎解题思路

  1. 第一步：先算清楚显存账，定位OOM和高延迟的根因：FP16精度的14B模型本身权重占28GB显存，两张卡张量并行拆分后每张卡放14GB权重，剩下10GB/卡的显存要存KV Cache，10人并发时KV Cache占用约8GB还能撑住，30人并发时KV Cache需求涨到24GB以上，直接把显存占满导致OOM；同时因为显存不够，vLLM无法做高效的动态批处理，请求排队导致TTFT飙升。
  2. 第二步：按照“权重显存优化→KV Cache显存优化→调度层优化→缓存层优化”的优先级依次做优化，每一步都量化显存收益，先解决OOM问题，再优化延迟。
  3. 第三步：优化完成后做压力测试，验证并发数和延迟指标，最后设置合理的限流阈值，避免流量超过承载能力导致服务崩溃。

▎详细方案

根因定位明确：FP16模型权重占用过高，留给KV Cache的显存空间不足，并发上涨时KV Cache挤爆显存，同时动态批处理效率下降导致请求排队。优化方案按优先级从高到低落地：
1. 第一优先级：模型权重量化，释放基础显存（收益最大，改动最小）
把原来的FP16模型替换为社区预训练好的Qwen2.5-14B-AWQ INT4量化版，根据之前的体积换算，INT4量化后14B模型的权重体积仅为9GB左右，两张卡张量并行拆分后每张卡仅需放4.5GB权重。
- 显存收益：原来权重占28GB，现在仅占9GB，直接释放19GB显存，全部留给KV Cache使用。
- 精度损失：AWQ量化通过保护离群点权重，在14B模型上INT4精度损失不到1%，对于知识库问答场景完全无感知。
- 性能提升：INT4量化后，内存带宽需求降低75%，权重读取速度变快，单请求推理速度提升30%以上。
- 落地注意：不要自己做量化，直接下载社区后缀带-AWQ的模型包，用vLLM直接加载即可，不需要改代码。
2. 第二优先级：开启KV Cache量化，提升并发承载能力
vLLM默认用FP16存储KV Cache，每个Token的KV Cache占用空间约为2 * 层数 * 隐层维度 * 精度字节数，14B模型FP16下每个用户128K上下文的KV Cache要占几百MB。开启vLLM的KV Cache INT8量化功能，把KV Cache从FP16压缩到INT8。
- 显存收益：KV Cache占用直接减少50%，原来10GB显存能存10人并发的KV Cache，现在能存20人以上。
- 精度损失：KV Cache量化对输出质量的影响极小，因为KV Cache里存的是注意力的中间值，神经网络对这部分的精度损失鲁棒性极强，实测在问答场景下几乎没有效果下降。
- 性能提升：KV Cache体积变小后，显存带宽压力进一步降低，动态批处理能同时装下更多请求，吞吐量提升近一倍。
3. 第三优先级：开启vLLM的PagedAttention和动态批处理最优配置
很多同学部署vLLM时用默认参数，没有开启最优调度配置：
- 开启--enable-prefix-caching（前缀缓存）：企业知识库问答场景下，很多用户的System Prompt、检索到的知识库前缀是完全一样的，开启前缀缓存后，相同的前缀KV Cache可以在不同用户之间共享，不需要重复计算，能再省30%左右的KV Cache空间，同时TTFT直接降低50%以上。
- 设置合理的--max-num-seqs（最大并发序列数）：根据剩下的显存计算，量化后两张卡共有48GB显存，权重占9GB，剩下39GB给KV Cache，INT8 KV Cache下可以支撑至少60个并发序列，设置为50留一定冗余，避免OOM。
- 开启--gpu-memory-utilization 0.9：默认vLLM只给KV Cache留90%的显存，原来因为显存紧张不敢开高，现在显存充足可以开到0.95，进一步提升KV Cache可用空间。
4. 第四优先级：网关层增加语义缓存，减少重复请求打到GPU
在vLLM前面部署一层GPTCache语义缓存，对于相似度超过0.95的问题（比如“年假怎么休”和“公司年假政策是什么”），直接返回缓存结果，不需要走GPU推理。
- 性能收益：企业内部知识库场景下，重复问题占比通常在30%~50%，这部分请求可以做到毫秒级响应，0 Token成本，整体TTFT平均再降30%，GPU负载降低一半。

优化后效果测算：
- 权重占用9GB + KV Cache（50并发INT8+前缀缓存）约占32GB，总显存占用约41GB，剩余7GB显存作为冗余，彻底解决OOM问题。
- 吞吐量比优化前提升4~5倍，原来只能撑10并发，现在稳定撑50并发，平均TTFT降到500ms以内，远低于1s的目标。
- 全程不需要增加任何硬件成本，只需要换模型、改启动参数、加一层缓存。

▎关键细节 & 踩坑点

  • 不要用GPTQ量化做部署，AWQ量化在vLLM上的推理速度比GPTQ快20%以上，且精度损失更小，是目前生产环境INT4量化的首选。
  • KV Cache量化不要用INT4，INT4 KV Cache在长上下文场景下会有可感知的精度损失，INT8是精度和性能的最佳平衡点。
  • 前缀缓存一定要配合Chunked Prefill（分块预填充）开启，否则长上下文请求的Prefill阶段会阻塞其他请求，反而导致TTFT升高。
  • 语义缓存的相似度阈值不要设太低，建议设0.95以上，否则会出现“问题相似但答案不同”的错误，比如“北京的公积金政策”和“上海的公积金政策”相似度很高，但答案完全不同，阈值太低会返回错误结果。
  • 一定要设置--max-model-len参数，不要用模型默认的128K上下文，企业知识库问答场景下8K上下文足够，限制最大上下文长度能避免单个用户传超长文本把KV Cache占满。

▎可扩展优化

  • 后续如果并发继续上涨，可以开启vLLM的Speculative Decoding（投机采样），用一个小的7B模型做草稿，大模型做验证，能再把推理速度提升2~3倍，同样不需要增加硬件。
  • 可以做请求分级，把内部员工的普通问答请求优先级设为低，把高优先级的管理岗请求设为高，调度时优先处理高优先级请求，保障核心用户体验。
  • 监控KV Cache利用率，当KV Cache利用率长期超过90%时，再考虑申请预算加卡，不要一开始就盲目采购硬件，90%的场景下通过量化和缓存优化就能把硬件利用率提升3~5倍。
