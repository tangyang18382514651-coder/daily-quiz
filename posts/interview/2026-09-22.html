📌 概念题 · Q1

考点标签

向量数据库运维 · 难度：⭐⭐⭐

📝 题目

你在 Windows 本地用 Docker Desktop 挂载 Windows 目录部署 Qdrant 做开发测试，发现存储目录占用高达 400 多 MB，但同样的数据部署到线上 Linux 服务器后用 du -h 查看只占几 MB。有同事说这是数据损坏或者配置错误导致的，你认同这个说法吗？如果想让本地开发环境的磁盘占用表现和线上一致，应该怎么调整？

💡 参考答案

▎一句话结论

这既不是数据损坏也不是配置错误，本质是 Linux 与 Windows/NTFS 文件系统对稀疏文件（空洞文件）的预分配落盘机制不同导致的统计差异，数据内容本身完全一致。

▎核心原理

  • Linux 支持稀疏文件（Sparse File）机制：逻辑大小 32MB 的预分配页文件、WAL 文件，未写入的空白部分不会实际占用磁盘块，du -h 统计的是实际占用块大小，因此只有几 MB。
  • Windows NTFS + Docker Desktop bind mount 场景下，容器创建的预分配文件会按完整逻辑大小占用磁盘空间，不会识别稀疏空洞，因此相同数据会显示几百 MB 占用。
  • 额外占用来自向量库的固定开销：Collection 的 Segment 固定页文件、WAL 预写日志、Payload 索引预分配文件，Segment 数量过多会进一步放大占用差异。

▎深入解释

我们可以把稀疏文件理解成“提前占了座位号但没真的坐人”的电影院：Qdrant 启动时会提前创建固定大小的页文件（比如 32MB 的 page_0.dat、chunk_0.mmap），预留好后续写入的空间。在 Linux 上，这些预留的空位只要没真的写入数据，文件系统就不会给它分配实际的磁盘块，相当于电影院只给真正到场的观众安排座位；而在 Windows 的 bind mount 模式下，系统会直接把所有预留的座位全部占满，不管有没有人坐，所以显示的占用会大很多。
如果在 Linux 上用 du -h --apparent-size 查看文件的逻辑大小，你会发现它和 Windows 上显示的大小基本一致，这就证明了数据本身没有任何差异，只是统计口径不同。之前本地出现 2.5GB 的超大占用，本质是 Segment 数量过多导致预分配文件堆积，合并 Segment 后降到 432MB 属于正常范围。

▎面试加分点

  • 能准确区分 du -h（实际磁盘块占用）和 du -h --apparent-size（文件逻辑大小）的区别，说明你有实际的 Linux 运维排错经验。
  • 能指出 Qdrant 磁盘占用的三个固定组成部分：Segment 页文件、WAL 日志、Payload 预分配索引，而不是笼统归为“数据大”。

▎常见误区

  • 误区1：认为 Windows 占用大是因为 Qdrant 存了多余的缓存或临时文件，盲目删除存储目录导致数据丢失。
  • 误区2：为了节省磁盘强行关闭 Qdrant 的预分配机制，导致写入性能下降、Segment 碎片化严重。
  • 误区3：想让本地和线上一致，直接把存储目录放在 Windows 盘符下改配置，正确做法是把 Qdrant 存储放到 WSL2 的 Linux 文件系统或者 Docker named volume 中，而不是 Windows 目录 bind mount。

📌 概念题 · Q2

考点标签

Agent工具生态 · 难度：⭐⭐

📝 题目

很多开发者把 SkillsLLM 当成 Codex/Claude Skills 的一键安装市场，搜到项目就直接复制到 skills 目录，结果发现很多“Skill”根本无法调用。请说明 SkillsLLM 的本质定位是什么？如何判断上面的资源应该安装到哪个目录？

💡 参考答案

▎一句话结论

SkillsLLM 不是专门的 Codex Skill 官方应用市场，而是一个覆盖 Skills、MCP Server、CLI 工具、IDE 插件、普通开源项目的 AI Agent 生态聚合搜索站，只适合做资源发现，不能直接无脑一键安装。

▎核心原理

  • SkillsLLM 上的资源分为 6 大类：带 SKILL.md 的标准 Skill、MCP 服务、CLI 命令行工具、自定义 Agent、Codex/Claude 插件、普通 GitHub 项目，不同类型的资源安装路径和配置方式完全不同。
  • 标准 Codex Skill 的唯一判断依据是目录下存在合法的 SKILL.md 文件，且文件头部包含 name、description 等必填元信息，这类资源才能放到 skills 目录通过 $skill-name 调用。
  • Codex 的三类扩展是完全隔离的：Skills 放在 ~/.codex/skills 或项目级 .agents/skills，自定义 Agents 放在 ~/.codex/agents，Plugins 放在 ~/.codex/plugins，三者不会互相识别。

▎深入解释

我们可以把 SkillsLLM 理解成 AI 工具界的“hao123 导航页”，而不是“苹果 App Store”：它帮你把全网散落的 AI 开发相关资源聚合到一起方便搜索，但不会帮你做应用审核和适配，你点进去的链接可能是手机 App、可能是电脑软件、可能是网页游戏，不能全部都按手机 App 的方式安装。
比如你在上面搜到一个 MCP Server，它的正确安装方式是在 MCP 配置文件里添加服务地址，而不是复制到 skills 目录；搜到一个 CLI 工具，正确方式是用 pip/npm 安装到系统路径，而不是放到 Codex 目录；搜到一个自定义 Agent，要放到 ~/.codex/agents 目录，通过点名调用或者 orchestrator 调度，它不会出现在 Skills 面板里，这是正常现象不是安装失败。

▎面试加分点

  • 能清晰区分个人全局安装和项目级安装的路径差异：个人常用的通用 Skill 放到用户目录下的 .codex/skills 全局复用，团队共享的项目专用 Skill 放到项目根目录的 .agents/skills 随代码仓库提交，不要把项目专用 Skill 放到个人全局目录导致团队成员无法复用。
  • 能指出标准 SKILL.md 的必填结构：必须包含 YAML 格式的 name 和 description 字段，说明 Skill 的触发场景，否则 Codex 无法识别什么时候调用该 Skill。

▎常见误区

  • 误区1：把普通 GitHub 仓库复制到 skills 目录，发现无法调用就认为 Codex 出问题了，实际上没有 SKILL.md 的项目根本不是标准 Skill。
  • 误区2：把自定义 Agent 放到 skills 目录，抱怨为什么在 Skills 面板看不到，实际上 Agent 本来就不会出现在 Skills 列表，属于不同的扩展类型。
  • 误区3：把项目专用的 Skill 放到个人全局 .codex/skills 目录，导致其他团队成员拉取代码后缺少对应能力，破坏项目的可复现性。

📌 概念题 · Q3

考点标签

Agent安全 · 难度：⭐⭐⭐⭐

📝 题目

传统软件系统中，OAuth 2.0 和 API Key 已经是非常成熟的鉴权方案，但知识库提到当 AI Agent 获得自主调用工具、修改数据的权限后，传统鉴权机制不再适用，需要引入 Agentic Auth（智能体鉴权）体系。请说明传统鉴权方案在 Agent 场景下的核心缺陷是什么？Agentic Auth 的三层落地架构分别解决什么问题？

💡 参考答案

▎一句话结论

传统鉴权是为“人类操作固定权限的程序”设计的静态凭证体系，无法应对 Agent 的自主决策、动态工具调用、跨节点信任链流转带来的越权风险，Agentic Auth 是从网关、沙箱、人工审核三个层级构建的全链路动态权限控制体系。

▎核心原理

  • 网关层鉴权：为每个 Agent 节点分发统一身份标识，严禁硬编码 API Key，在向量检索等操作前强制注入租户/部门维度的标量预过滤，从入口层堵死多租户越权。
  • 安全沙箱隔离：Agent 执行代码的环境必须是用完即毁的轻量级安全容器（gVisor/Kata Containers/E2B），绝对不能直接给宿主机权限，防止代码执行类风险扩散。
  • 人肉安全闸（HITL）：严格区分查询类接口和副作用类接口，涉及修改、删除、财务操作的高危请求必须中断流程持久化状态，等待人类二次确认后才能恢复执行。

▎深入解释

传统的 API Key 鉴权就像给员工配了一把万能钥匙：只要你拿着这把钥匙，就能开对应权限的所有门，系统默认拿钥匙的人是可信的、知道自己在做什么。但 Agent 本质是一个“会自己做决定的实习生”，你给了它万能钥匙，它可能会被普通员工诱导去开高管办公室的门查涉密数据（人机越权），可能会不小心反复按消防按钮导致整个系统瘫痪（工具滥用死循环），也可能拿着钥匙去帮别的没有权限的人开门（A2A 通信的信任链流转问题），这些都是静态凭证无法解决的。
Agentic Auth 的三层架构相当于给这个实习生配了三重保险：进门的时候刷工牌确认身份和所属部门，不该进的楼层直接在闸机挡住（网关层）；干活的时候给它一个独立的一次性工作台，干完就销毁，就算弄坏了东西也影响不到外面（沙箱层）；遇到签合同、转钱这种大事，必须停下来找真实的人类领导签字确认才能继续（HITL 层）。

▎面试加分点

  • 能结合 RAG 场景说明网关层预过滤的重要性：很多团队做 RAG 多租户时只是在代码层面拿到结果后过滤，这会导致 Top-K 结果被过滤后数量不足，正确做法是在向量检索前就把 tenant_id 作为强制 WHERE 条件做 Pre-filtering，从物理层面隔离数据。
  • 能结合 LangGraph 说明 HITL 的工程实现：利用 interrupt_before 机制在高危节点前中断，把 thread_id 和图状态持久化到数据库，释放线程资源，等用户确认后再携带原状态 Resume 流程，不需要 Agent 常驻内存等待。

▎常见误区

  • 误区1：认为 Agentic Auth 就是给 Agent 加个 API Key 就行，忽略了 Agent 行为的自主性和不可预测性，没有做细粒度的权限边界控制。
  • 误区2：认为沙箱就是 Docker 容器，普通 Docker 容器和宿主机共享内核，存在逃逸风险，生产环境必须用 gVisor 这类用户态内核的安全容器或者专门的 Serverless 沙箱服务。
  • 误区3：所有操作都加人工确认，导致 Agent 的自动化优势完全丧失，正确做法是查询类接口自由放行，只有高危副作用接口才触发 HITL。

📌 概念题 · Q4

考点标签

知识管理 · 难度：⭐⭐⭐

📝 题目

Obsidian 被很多开发者称为构建“第二大脑”的终极工具，和 Notion、印象笔记等云笔记软件相比，它的核心理念是本地优先（Local-first）。请说明本地优先架构给 Obsidian 带来了哪些核心优势？为什么说新手刚开始用 Obsidian 不应该一上来就折腾大量插件？

💡 参考答案

▎一句话结论

Obsidian 的本地优先核心理念是让用户完全掌控自己的知识数据，所有笔记以纯 Markdown 格式存储在本地磁盘，不依赖厂商服务，带来了数据主权、极速离线、高可定制性三大核心优势，新手过度折腾插件反而会陷入配置焦虑，忽略知识积累本身。

▎核心原理

  • 绝对数据主权：所有笔记都是标准 Markdown 纯文本文件，即使 Obsidian 厂商倒闭、软件停止维护，用户依然可以用任何文本编辑器打开、编辑自己的笔记，不存在数据绑架问题。
  • 极速离线体验：数据全部存在本地磁盘，不需要联网加载，启动和全文搜索速度远高于云笔记，没有网络的环境下也可以完全正常使用。
  • 高度可定制的插件生态：上千个社区插件可以把 Obsidian 改造成看板、思维导图、任务管理系统、个人仪表盘，适配不同用户的工作流。

▎深入解释

我们可以把云笔记类比成租房子：你把家具和行李放在房东的房子里，房东涨房租、赶你走、或者房子塌了，你的东西可能就拿不回来了，每次进出还要经过房东的检查，网速慢的时候连门都进不去；而 Obsidian 相当于你自己买的房子，房子里的所有东西都是你的，你想怎么装修就怎么装修，断水断电断网也不影响你在家待着，就算以后换了更好的房子，你的家具（Markdown 文件）也可以原封不动搬过去。
但很多新手刚用 Obsidian 时会陷入“插件收集癖”：今天装个看板插件、明天装个思维导图插件、后天换个花里胡哨的主题，花了几十个小时配置工作流，结果没写几篇笔记。这就像你买了房子之后天天装修、买家具，却从来不在里面看书学习，完全违背了知识管理的初衷。正确的入门方式是先把它当成普通记事本，用 [[双向链接]] 慢慢积累笔记，等遇到具体的痛点（比如需要管理待办、需要画思维导图）时，再去找对应的插件解决问题。

▎面试加分点

  • 能关联到 LLM Wiki 生态：Obsidian 现在已经有 Karpathy LLM Wiki 插件，可以自动给本地笔记生成概念实体和双向链接，把本地知识库和大模型能力结合起来，实现离线环境下的个人知识管理增强。
  • 能说明双向链接和传统文件夹分类的本质区别：传统文件夹是树状的、非此即彼的分类，双向链接是网状的，可以自然表达知识之间的交叉关联，更符合人类大脑的联想记忆模式。

▎常见误区

  • 误区1：认为 Obsidian 必须付费才能用，实际上个人使用的基础功能和绝大多数社区插件都是完全免费的，只有官方的同步、发布服务需要付费，用户完全可以用免费的 Git 或者网盘实现多端同步。
  • 误区2：把 Obsidian 当成云笔记用，把仓库放在网盘同步目录里，多端同时编辑时容易出现文件冲突，正确做法是用 Git 做版本管理，或者用官方同步服务。
  • 误区3：一开始就追求完美的笔记分类和标签体系，导致记笔记的成本极高，慢慢就放弃了，正确做法是先记录，再通过双向链接慢慢梳理关联。

📌 概念题 · Q5

考点标签

RAG落地 · 难度：⭐⭐⭐

📝 题目

你的团队准备基于阿里云百炼平台搭建企业文档 RAG 系统，团队里有人说“现在多模态是趋势，我们直接上多模态 Embedding 模型，一步到位支持所有文档类型”。结合知识库中百炼模型搭配的最佳实践，你认为这个方案合理吗？纯文本和多模态场景下的模型选型应该遵循什么路线？

💡 参考答案

▎一句话结论

一上来就全量切多模态 Embedding 是典型的过度设计，会带来成本上升、速度下降的问题，正确的选型路线是“先纯文本链路跑通核心场景，确有真实图片检索需求后再叠加跨模态能力”的分阶段落地策略。

▎核心原理

  • 纯文本场景（包括 OCR 后的图片文字、表格、普通文档）首选 text-embedding-v4 + qwen3-rerank 的组合，速度更快、成本更低、向量维度选择更灵活，重排精度完全满足企业需求。
  • 只有当存在真实的图片语义检索需求（比如需要根据文字描述搜文档里的架构图、流程图，而不是搜图片里的文字）时，才需要引入 qwen3-vl-embedding + qwen3-vl-rerank 的多模态组合。
  • 纯文搜图、图搜图的跨模态搜索场景，才需要用到 tongyi-embedding-vision-plus 这类专门的跨模态模型，普通文档场景完全不需要。

▎深入解释

很多团队做 RAG 时容易陷入“技术追新”的误区：觉得多模态是最新的技术，就应该一步到位上最好的模型，但忽略了企业落地最核心的 ROI 问题。实际上企业里 90% 以上的文档内容都是可以 OCR 成文字的：合同里的章、表格里的数字、流程图里的文字，这些内容通过 OCR 提取后走纯文本链路，检索精度更高、速度更快、成本只有多模态的几分之一。
如果盲目全量上多模态 Embedding，首先是 Embedding 成本会上升数倍，其次多模态向量的维度更高，检索速度会变慢，最后很多图片里的冗余信息（比如文档里的装饰性图片、页眉页脚的 logo）还会引入检索噪音，导致召回准确率下降。这就像你本来只是要去楼下买个菜，没必要开个重型卡车去，开个私家车甚至走路就够了，只有当你需要拉货的时候才需要用卡车。

▎面试加分点

  • 能说明分阶段落地的优势：第一阶段用纯文本链路可以快速上线 MVP，验证业务价值，积累用户真实的查询日志，等发现确实有大量“搜图片”的需求时，再投入资源做多模态，避免前期投入浪费。
  • 能指出“文档里有图片”不等于“需要多模态检索”：如果用户的问题是“第三章的架构图里画了几个模块”，OCR 提取图片里的文字和图注后走纯文本链路完全可以回答，不需要真的去理解图片的视觉内容。

▎常见误区

  • 误区1：认为多模态 Embedding 精度一定比纯文本高，实际上对于纯文字内容，专门的文本 Embedding 模型的召回精度是高于多模态模型的，因为多模态模型需要同时兼顾文本和视觉，文本语义的表征能力会被稀释。
  • 误区2：重排模型可以随便选，纯文本场景用多模态重排模型只会增加成本和延迟，不会带来精度提升，必须和 Embedding 模型配套选择。
  • 误区3：为了“一步到位”前期投入大量资源做多模态，结果上线后发现 99% 的用户查询都是纯文本问题，投入产出比极低。

📌 概念题 · Q6

考点标签

知识工程 · 难度：⭐⭐⭐⭐

📝 题目

Andrej Karpathy 提出的 LLM Wiki 模式被认为是下一代知识管理架构，和传统 RAG 相比，它提出了“录入即思考”的核心理念。请说明 LLM Wiki 和传统 RAG 在知识处理流程上的本质区别？它的三层核心架构分别承担什么职责？

💡 参考答案

▎一句话结论

传统 RAG 是“查询时临时抱佛脚”，用户提问时才临时切片检索，难以建立跨文档的实体关联；LLM Wiki 是“录入时主动思考”，文档入库时就由 LLM 提炼成结构化、双向链接的维基页面，从根本上解决传统 RAG 回答肤浅、割裂的问题。

▎核心原理

  • Immutable Sources（不变量源码层）：只读存储原始 PDF、研报、笔记等源文件，大模型绝对不允许修改这一层，作为所有知识的最终事实依据，避免幻觉。
  • The Wiki（维基层）：由 LLM 动态维护的 Markdown 文件目录，包含源文档摘要、核心概念页、观点交锋页，所有页面通过 [[双括号]] 建立双向链接，形成知识网络。
  • The Schema（约束规范层）：通过 CLAUDE.md/AGENTS.md 提示词文件，严格规定 LLM 维护 Wiki 的模板规范、链接规则、自我纠错机制，保证输出格式的一致性。

▎深入解释

传统 RAG 的工作模式就像学生考试前临时抱佛脚：考试的时候（用户提问）才把书（原始文档）拿出来，随便翻几页（切片检索），然后把翻到的内容拼凑成答案交上去。这种方式的问题是，如果你要考的知识点散落在书的不同章节，你翻的时候可能漏了，或者把不同章节的内容拼错了，给出的答案自然是割裂、肤浅的。
而 LLM Wiki 的模式就像学霸做读书笔记：每学完一章（文档入库），就主动整理笔记，把核心概念提炼出来，把不同章节里提到同一个概念的地方互相标注引用，慢慢形成一本属于自己的结构化参考书。等考试的时候，直接看自己整理的参考书就行，不需要再去翻厚厚的原始教材，不仅速度快，而且能建立跨文档的知识关联，回答的深度和准确性会高很多。

▎面试加分点

  • 能对比三种知识管理模式的差异：传统笔记靠人类手动打标签建链接，传统 RAG 靠查询时临时抽取，LLM Wiki 靠 LLM 异步增量自动维护知识网络，是人和 AI 协作的新范式。
  • 能说明 LLM Wiki 为什么适合终端/轻量 IDE 交互：因为它的知识是结构化的 Markdown 文件，可以直接在 Cursor、Claude Code 这类工具中被读取和引用，不需要额外的检索服务，实现代码级的知识插拔。

▎常见误区

  • 误区1：认为 LLM Wiki 会取代传统 RAG，实际上两者是互补关系：LLM Wiki 负责沉淀核心的、跨文档的结构化知识，传统 RAG 负责处理最新的、临时的、不需要长期沉淀的文档，两者结合效果最好。
  • 误区2：认为 LLM Wiki 会修改原始文档，实际上架构明确规定源文件层是只读的，所有 LLM 生成的内容都在独立的 Wiki 目录，不会破坏原始数据，出现幻觉时可以回溯源文件校验。
  • 误区3：认为 LLM Wiki 必须用复杂的专用系统，实际上用 Obsidian 加对应的插件，配合 CLAUDE.md 规则文件，就可以搭建出个人版的 LLM Wiki。

📌 概念题 · Q7

考点标签

Prompt工程 · 难度：⭐⭐

📝 题目

Few-Shot（少样本提示）是大模型应用开发中最常用的提示工程技术之一，很多人说“Few-Shot 就是给大模型举几个例子”，但在工业界落地时，很多人写的 Few-Shot 并没有效果。请说明 Few-Shot 的核心作用是什么？它和模型微调（Fine-Tuning）的本质区别是什么？分别适用于什么项目阶段？

💡 参考答案

▎一句话结论

Few-Shot 的核心作用是通过 2~5 个高质量示例，给大模型锁死输出格式、语言风格、判断边界三个核心要素，本质是不改变模型权重的提示词引导技术，和改变模型权重的微调相比成本极低，适合项目早期 MVP 阶段快速验证业务逻辑。

▎核心原理

  • Few-Shot 是“推理时引导”：在每次请求的提示词中加入示例，模型参数完全没有变化，通过上下文学习（In-Context Learning）让模型“照猫画虎”按照示例的规律输出。
  • 微调是“训练时改变”：通过成千上万条数据重新训练模型，改变模型本身的权重参数，让模型从“根本上”学会某种风格或能力，训练完成后调用不需要再带示例。
  • Few-Shot 的核心价值是零成本快速迭代：不需要算力、不需要清洗大量数据，修改提示词里的示例就可以立即调整模型的输出行为，试错成本极低。

▎深入解释

大模型本质上是一个“见过海量文本的实习生”，如果你只给它一个抽象的指令，比如“帮我做客服意图识别，返回 JSON”，它可能会自由发挥，给你加一堆客套话，或者返回格式不对的结果。但如果你给它看 2~5 个标准的输入输出示例，它就会立刻明白：“哦，原来这个任务是要我严格按照这个格式输出，不能加多余的话，判断标准是这样的”，输出的稳定性会提升一个量级。
这就像你带新实习生，你跟他说“你按规范写报告”，他可能写出来的东西五花八门；但你给他看 3 份之前写好的优秀报告样例，告诉他“就照着这个格式、这个风格写”，他立刻就能写出八九不离十的内容。这就是 Few-Shot 的本质。而微调相当于你花几个月时间专门培训这个实习生，让他从骨子里掌握某种技能，培训完之后他不需要看样例就能直接写出符合要求的内容，但培训的成本要高很多。

▎面试加分点

  • 能说出工业界的落地共识：“先用大模型 + Few-Shot 快速跑通和验证业务边界，等积累了足够多的真实负样本和高质量数据后，再考虑进行 SFT 或 DPO 微调”，避免一开始就投入大量资源做微调。
  • 能指出 Few-Shot 示例的选择原则：示例要覆盖典型的正例、容易混淆的边界 case、错误的反例，示例数量控制在 2~5 个，太多会浪费 Token 甚至干扰模型判断。

▎常见误区

  • 误区1：认为示例越多越好，实际上 Few-Shot 的示例超过 5 个之后边际收益会快速下降，还会占用大量上下文 Token，增加调用成本和延迟。
  • 误区2：项目刚启动就着急做微调，结果没有足够的高质量标注数据，微调出来的模型效果还不如 Few-Shot，浪费了大量算力和人力。
  • 误区3：示例里的输出格式不统一，比如有的示例返回 JSON、有的返回纯文本，模型会无所适从，输出格式混乱。

📌 概念题 · Q8

考点标签

开源大模型 · 难度：⭐⭐⭐

📝 题目

Hermes 3 系列模型被很多开发者称为“开源 Agent 专用大脑”，在函数调用、结构化输出场景下表现非常突出。请说明 Hermes 模型的本质是什么？和 Llama、Qwen 等官方底座模型相比，它在 Agent 开发场景下有哪些独特优势？

💡 参考答案

▎一句话结论

Hermes 不是新的大模型框架，而是 Nous Research 基于 Llama 等优秀开源底座专门为 Agent 场景深度微调的开源大语言模型，核心优势是极强的函数调用稳定性、未过度对齐的高听话度、优秀的长上下文注意力能力，是开源社区落地多智能体系统的主流选择之一。

▎核心原理

  • 极致的结构化输出与函数调用能力：微调时专门针对 JSON/XML 格式输出、Function Calling 参数格式做了深度优化，能够稳定理解多工具组合调用逻辑，准确判断何时该调用工具、何时直接回复，大幅降低 LangGraph/AutoGen 等框架的工具调用报错率。
  • Agentic 对齐（未过度对齐）：去除了官方底座模型常见的过度道德说教和随意拒绝回答的问题，保持中立客观的态度，严格服从开发者的 System Prompt 指令，不会随意打断业务逻辑。
  • 长上下文优化：基于 RoPE 扩展到 128K+ 上下文后专门做了注意力机制微调，“大海捞针”测试表现优异，长对话、长文档 RAG 场景下不容易漏掉中间的关键信息。

▎深入解释

官方的通用底座模型就像一个受过通用高等教育的毕业生，什么都懂，但你让它专门做某个岗位的工作时，它可能会有很多“自己的想法”：比如你让它调用工具查数据，它可能会跟你说“这个操作有风险我不能做”，或者输出的 JSON 格式少个括号导致程序报错，或者看长文档的时候看到中间就忘了前面的要求。
而 Hermes 就像这个毕业生经过了专门的岗前培训：培训的内容就是怎么当一个合格的 Agent 打工人——老板让干什么就干什么，不要说多余的话，输出格式要严格符合程序要求，看长文档的时候不要漏关键信息，需要调用工具的时候准确填对参数。而且它提供了不同尺寸的模型：8B 小模型量化后可以本地部署跑高频简单任务，成本几乎为零；70B/405B 大模型可以当主管 Agent 负责任务规划和反思，适配不同的场景需求。

▎面试加分点

  • 能说出 Hermes 的 Prompt 最佳实践：完美适配 ChatML 格式，System Prompt 要直白明确不要客套，让模型在输出 JSON 之前先用 <thinking> 标签做思维链推理，可以进一步提升函数调用的准确率。
  • 能说明 Hermes 适合的落地场景：个人开发者本地部署、企业内部不需要对外公开的业务流程自动化、对工具调用稳定性要求高但不想用闭源模型的场景，因为它的未过度对齐特性可以避免很多不必要的拒绝回答问题。

▎常见误区

  • 误区1：认为 Hermes 是新的开发框架，实际上它就是微调后的 LLM 权重，和 LangGraph、AutoGen 等框架是互补关系，框架负责编排，Hermes 负责推理。
  • 误区2：认为未过度对齐就是“无审查”，实际上它是去除了不必要的过度对齐和说教，依然可以通过 System Prompt 设定安全边界，不是完全没有安全限制。
  • 误区3：不管什么场景都用最大尺寸的 Hermes 模型，实际上高频简单的子任务用 8B 量化版本就能满足需求，响应速度更快、成本更低，只有顶层规划节点需要用大尺寸模型。

📌 概念题 · Q9

考点标签

大模型基础设施 · 难度：⭐⭐⭐⭐

📝 题目

FlashAttention 是现在大模型训练和推理的标配加速技术，很多人只知道它“速度快、省显存”，但说不清楚它为什么快。请从 GPU 硬件特性的角度，解释 FlashAttention 的核心设计思想，为什么它能同时实现速度提升和显存占用下降？

💡 参考答案

▎一句话结论

FlashAttention 的核心设计思想是“不拼算力拼物流”——它发现大模型注意力计算的瓶颈不是 GPU 算力不够，而是显存和计算核心之间的数据搬运太慢，因此通过“分块计算+重计算中间结果”的策略，大幅减少数据搬运次数，实现了速度和显存占用的双重优化。

▎核心原理

  • 传统注意力机制的瓶颈：需要在显存中存储完整的 N×N 注意力矩阵，序列长度变长时显存占用呈平方级增长，而且需要反复在 HBM（高带宽显存）和 SRAM（计算核心附近的高速缓存）之间搬运数据，IO 开销极大。
  • 分块（Tiling）策略：把完整的注意力矩阵拆成多个可以放进 SRAM 的小块，每次只加载一小块数据到高速缓存中计算，不需要把整个矩阵存进 HBM，显存占用从 O(N²) 降到 O(N)。
  • 重计算（Recomputation）策略：反向传播时不保存中间的注意力权重矩阵，需要用到的时候用前向传播的输入重新计算，用廉价的算力换昂贵的显存带宽，进一步减少数据存储和搬运开销。

▎深入解释

我们可以把 GPU 想象成一个超级工厂：计算核心（SM）是车间，加工速度极快；SRAM 是车间旁边的临时货架，存取速度极快但空间很小；HBM 显存是离车间很远的大仓库，空间大但搬运速度很慢。传统的注意力计算方式是：把所有原材料都从大仓库搬到车间，加工完的中间半成品全部放回大仓库，需要用的时候再搬过来——结果车间的工人大部分时间都在等原材料运过来，真正加工的时间很少，而且大仓库很快就被半成品堆满了。
FlashAttention 的思路完全反过来：每次只从大仓库搬一小批原材料到车间旁边的小货架，在车间里加工完直接出最终结果，中间的半成品不运回大仓库，下次需要的时候就在车间里重新算一遍。因为车间的加工速度实在太快了，重新算一遍的时间比从大仓库搬过来的时间还短，所以整体速度反而更快，而且大仓库里不用堆大量半成品，显存占用自然就降下来了——这就是“宁可多算几次，也绝不浪费时间搬运数据”的核心逻辑。

▎面试加分点

  • 能准确说出 IO 瓶颈是现代 GPU 计算的核心矛盾：GPU 的算力增长速度远快于显存带宽的增长速度，属于“算力过剩、带宽稀缺”，所以优化访存比优化计算量带来的收益大得多。
  • 能说明 FlashAttention 为什么不影响精度：虽然用了重计算，但所有计算都是精确的，没有做近似或者量化，所以计算结果和传统注意力完全一致，不存在精度损失，这也是它能快速成为标配的重要原因。

▎常见误区

  • 误区1：认为 FlashAttention 是通过近似计算或者减少计算量来加速的，实际上它的计算量比传统注意力还略高一点，只是大幅减少了数据搬运的开销，总耗时更短。
  • 误区2：认为 FlashAttention 只有训练的时候有用，实际上推理阶段尤其是长上下文推理，FlashAttention 同样能大幅降低显存占用、提升速度，现在 vLLM 等主流推理框架都默认开启 FlashAttention。
  • 误区3：认为开了 FlashAttention 就可以无限延长上下文长度，实际上它只是把显存复杂度从平方级降到线性级，上下文长度还是会受到 KV Cache 显存占用的限制。

📌 概念题 · Q10

考点标签

大模型SaaS架构 · 难度：⭐⭐⭐⭐

📝 题目

在多租户大模型 SaaS 场景中，很多团队的个性化方案是“为每个租户微调一个专属模型，独立部署”，但知识库中提到生产环境的主流方案是“1 个通用大底座 + N 个租户 LoRA 小补丁”。请说明为什么“每个租户一个独立模型”的方案不可行？vLLM 这类推理框架是如何支持 LoRA 动态加载的？

💡 参考答案

▎一句话结论

每个租户部署一个独立模型会带来极高的显存成本、运维成本和更新成本，完全无法支撑 SaaS 场景下的大规模租户需求，“共享底座+动态 LoRA 加载”方案通过把个性化差异抽离成小体积的适配器补丁，在不复制整个模型的前提下实现租户级个性化，是目前工业界的标准落地架构。

▎核心原理

  • 成本问题：一个 7B 模型量化后也要占 10GB 左右显存，70B 模型更是需要上百 GB 显存，如果为每个租户部署一个独立模型，租户数量上来后显存成本会呈线性增长，没有任何商业可行性。
  • LoRA 补丁的本质：微调后的 LoRA 权重只有几 MB 到几百 MB，相当于给通用底座打的“个性化补丁”，不需要修改底座模型的参数，只需要在推理时把补丁的参数和底座参数合并计算即可。
  • 推理框架的动态加载能力：vLLM 等主流框架内置了 LoRA 适配器管理能力，请求到来时根据租户 ID 动态加载对应的 LoRA 权重，不需要为每个 LoRA 启动独立的模型实例，多个租户可以共享同一个底座模型的显存。

▎深入解释

我们可以把通用大模型底座想象成一个通用的操作系统，比如 Windows：所有用户共享同一个 Windows 内核，如果你需要个性化，只需要安装对应的软件、改对应的主题配置就行，不需要为每个用户单独开发、安装一个独立的操作系统。如果真的为每个用户做一个定制版 Windows，首先是硬盘根本装不下，其次是微软每次更新系统的时候，要给成千上万个定制版分别打补丁，运维成本是不可想象的。
LoRA 补丁就相当于用户安装的软件和主题配置，体积很小，个性化的内容都在补丁里，底层的系统内核是共享的。vLLM 这类推理框架就像一个多用户的操作系统，它把底座模型加载到显存里常驻，当 A 租户的请求过来时，就临时把 A 的 LoRA 补丁加载进来计算，算完之后可以把不常用的 LoRA 换出显存，B 租户过来时再加载 B 的补丁，几十个甚至上百个租户可以共享同一个底座模型的显存资源，成本直接下降一到两个数量级。

▎面试加分点

  • 能准确说出 LoRA 补丁的核心文件结构：adapter_config.json 是补丁的超参数配置（比如秩、挂载的层位置），adapter_model.safetensors 是真正的权重数据，也就是补丁的“肉身”，部署时只需要把这些文件存到 OSS 或者配置中心，不需要存储整个模型。
  • 能说明这种架构的运维优势：当底座模型需要升级（比如从 Qwen2.5-7B 升级到更新的版本）时，只需要替换一次底座，所有租户的 LoRA 补丁只要和新底座兼容就可以直接使用，不需要为每个租户重新训练、部署模型。

▎常见误区

  • 误区1：认为动态加载 LoRA 会让推理延迟大幅上升，实际上 LoRA 权重体积很小，加载开销极低，而且框架会做 LoRA 权重缓存，热门租户的 LoRA 会常驻显存，几乎没有额外延迟。
  • 误区2：认为 LoRA 的效果不如全参数微调，实际上对于 SaaS 场景下的风格个性化、话术定制这类需求，LoRA 的效果完全可以媲美全参数微调，成本却只有几十分之一。
  • 误区3：所有租户的 LoRA 都要常驻显存，实际上框架会做 LRU 缓存，把不常用的 LoRA 换出到内存甚至磁盘，只有活跃租户的 LoRA 占用显存，支持的租户数量远大于显存能容纳的模型副本数量。

二、应用题（5 道 · 分类型）

🛠 应用题 · Q1 · 架构设计

题型

架构设计

场景标签

LLM Wiki 知识管理 个人知识库

📝 题目

你是一位 AI 应用架构师，一位资深技术博主希望搭建个人的 LLM Wiki 知识库，用来管理他 5 年积累的 2000+ 篇技术博客草稿、300+ 份 PDF 技术研报、数万条碎片化笔记和聊天记录。他不满足于传统 RAG "提问时临时检索"的肤浅回答，希望实现 Karpathy 提出的 LLM Wiki 模式：录入即思考、自动生成双向链接、跨文档概念关联。请你为他设计一套完整的 LLM Wiki 架构，并说明如何与他现有的 Obsidian 工作流无缝打通。

💡 参考答案

▎解题思路

  1. 第一步：严格遵循 LLM Wiki 的三层架构原则，划分不可变源码层、AI 维护的维基层、约束规范层，确保原始数据永不丢失。
  2. 第二步：设计增量录入管道，新文档进入时触发 LLM 异步处理，而非查询时临时计算。
  3. 第三步：打通 Obsidian 生态，利用双向链接和 Graph View 实现可视化知识网络。
  4. 第四步：设计对话交互层，支持基于 Wiki 网络的深度问答，而非传统切片检索。

▎详细方案

整体架构分为四层，从下到上依次是：

第一层：Immutable Sources 不变量源码层。这一层是绝对只读的，所有原始文件（PDF 研报、Markdown 草稿、聊天记录导出文件）原封不动存放在 ~/wiki/raw/ 目录下，按来源和日期分目录存储，大模型永远不会修改这一层的任何文件。每次新增文件时计算 SHA256 哈希，存入 SQLite 元数据库，避免重复处理。

第二层：Ingestion Pipeline 增量录入管道。这是 LLM Wiki 区别于传统 RAG 的核心。当新文件进入 raw 目录，文件监听器（watchdog）触发异步处理流：
- 第一步用 Unstructured 或 PyMuPDF 解析文档，提取纯文本和结构。
- 第二步让 LLM 生成 Source Note：提取文档的核心 Claim（论点）、关键数据、直接引述及对应页码，存入 ~/wiki/wiki/sources/[文档名].md。
- 第三步让 LLM 做实体和概念抽取：识别文档中出现的技术概念、人物、工具、方法论，与已有 Concept Pages 做匹配——已存在的概念页追加新内容并更新双向链接，不存在的则新建 Concept Page 存入 ~/wiki/wiki/concepts/。
- 第四步自动生成 [[双括号链接]]，在 Source Note 和 Concept Page 之间建立引用关系。

第三层：The Wiki 维基层。完全由 LLM 维护的 Markdown 目录结构，包含三类文件：Source Notes（单文档摘要）、Concept Pages（跨文档概念聚合页）、Debate Pages（不同文献观点对比页）。每个文件头部都有 YAML Frontmatter，记录创建时间、关联来源、标签、最后更新时间等元数据。这一层就是 Obsidian 直接打开的 Vault 目录。

第四层：The Schema 约束规范层。通过根目录的 CLAUDE.md（或 AGENTS.md）严格规定 LLM 的行为：强制使用 [[双括号]] 建立链接、Concept Page 的固定模板（定义/核心原理/相关技术/引用来源/延伸阅读）、自我纠错机制（每次更新后检查是否有断链、是否遗漏关键论点）。

交互层上，一方面直接用 Obsidian 打开 wiki 目录作为 Vault，享受原生双向链接、Graph View、全文搜索；另一方面提供一个轻量聊天接口（基于 Claude Code 插件或 Cursor），提问时不是做向量切片检索，而是先定位相关 Concept Page，再顺着双向链接遍历关联的 Source Notes 和 Debate Pages，把整个知识子图喂给 LLM 生成深度回答。

▎关键细节 & 踩坑点

  • 绝对不要让 LLM 修改 raw 层的原始文件，所有 AI 生成内容都必须放在 wiki 层，否则一旦 LLM 产生幻觉篡改原始资料，将造成不可逆的知识损失。
  • 不要一开始就追求全自动概念抽取，初期建议加入 HITL 环节：LLM 新建 Concept Page 时给用户发通知，用户确认后再正式写入，避免概念碎片化（比如同一个技术生成了三个相近但不互通的概念页）。
  • 双向链接不要滥用，LLM 容易给每个词都加链接导致图谱变成毛线团，Schema 里必须明确规定：只有核心技术概念、关键人物、重要方法论才加链接，普通动词和通用名词不加。
  • 处理 PDF 时不要只提取纯文本，必须保留页码信息，Source Note 里的每个引述都要标注页码，方便溯源验证。

▎可扩展优化

  • 引入图算法（如 Louvain 社区发现）定期分析 Wiki 的双向链接网络，自动发现知识聚类和知识盲区——比如两个高度相关的概念之间居然没有链接，提醒用户或 LLM 补全关联。
  • 增加增量更新机制：当同一主题有新文档录入时，LLM 不仅追加内容，还要主动对比新老文献的观点差异，自动生成或更新 Debate Page。
  • 对接向量数据库做混合检索：Concept Page 和 Source Note 除了双向链接，同时生成 Embedding 存入 Qdrant，当用户提问涉及非常冷门的概念时，先用向量检索找到入口节点，再顺着图谱遍历，兼顾广度和深度。
  • 增加版本控制：整个 wiki 目录用 Git 管理，每次 LLM 更新都自动提交，方便回滚到任意历史版本，避免 LLM 某次更新把之前写好的概念页改坏。

🛠 应用题 · Q2 · 场景分析题

题型

场景分析题

场景标签

阿里云百炼 RAG落地 模型选型

📝 题目

某传统制造企业要搭建内部 RAG 知识库系统，第一期需要处理的文档包括：2000 份设备操作手册（Word/PDF，大部分是文字+表格，少量设备照片带参数标注）、500 份安全生产规范（纯文本）、300 份历史故障维修记录（含现场照片和故障部位截图）。技术团队在选型时产生分歧：有人说直接上多模态 Embedding 一步到位，有人说纯文本链路成本低效果稳。请你结合阿里云百炼的模型矩阵，给出分阶段的选型方案和成本对比分析，并说明为什么不建议第一期就全量上多模态。

💡 参考答案

▎解题思路

  1. 第一步：先对文档类型做拆解，区分哪些信息可以通过 OCR 转化为文本，哪些信息必须依赖多模态理解。
  2. 第二步：对照阿里云百炼的官方模型推荐矩阵，为不同类型的内容匹配最合适的 Embedding 和 Rerank 模型。
  3. 第三步：做两阶段规划，第一期先跑通纯文本链路验证业务价值，第二期再根据真实需求叠加多模态能力，避免过度设计。
  4. 第四步：从成本、速度、准确率三个维度做量化对比，给出决策依据。

▎详细方案

第一阶段（0-3个月，MVP 验证期）：纯文本链路为主，OCR 提取图片文字。

模型选型严格遵循百炼官方推荐：Embedding 用 text-embedding-v4，Rerank 用 qwen3-rerank。

针对文档中的图片做差异化处理：
- 设备操作手册里的设备照片：大部分照片是设备外观图，真正有用的信息是照片旁边的文字说明、参数表格，这部分直接用 PDF 解析提取文字即可，不需要多模态。
- 照片上的参数标注（比如仪表盘读数、开关位置标注）：用 OCR 工具（如 PaddleOCR 或百炼内置的文档解析接口）把图片上的文字提取出来，作为图片说明文字追加到对应段落的后面，一起走纯文本 Embedding 链路。
- 安全生产规范：100% 纯文本，直接切片走标准流程。
- 故障维修记录里的现场照片：先用多模态大模型（如 qwen-vl-max）做一次离线打标，生成一段描述性文字（如"图片显示3号电机轴承部位有明显漏油痕迹，周围有金属碎屑"），把这段文字作为图片的 Caption 存入元数据，和正文一起走纯文本检索。

这个阶段的核心逻辑是：只要信息能转化为文字，就绝不走多模态链路。

第二阶段（3-6个月，体验优化期）：按需叠加多模态能力。

只有当第一期上线后，确实出现了"必须看图片才能回答"的真实用户需求（比如维修师傅问"这个零件长什么样，在设备哪个位置"，文字描述怎么都说不清楚），才引入 qwen3-vl-embedding 和 qwen3-vl-rerank，而且不是全量切换，只针对故障维修记录里的关键部位照片、设备操作手册里的装配示意图这两类图片做多模态 Embedding，其他文档仍然走纯文本链路。

成本对比分析：
- 纯文本链路：text-embedding-v4 的成本大约是 0.7 元/百万 Token，qwen3-rerank 约 4 元/百万 Token，处理 1000 万 Token 的文档总成本不到 50 元，且检索速度快（毫秒级），维度可选（支持 256/512/1024/2048 维，低维向量更省存储）。
- 多模态链路：qwen3-vl-embedding 的成本是纯文本的 5-10 倍，且图片需要先做分块和预处理，检索延迟高 2-3 倍，向量维度更高，存储成本也相应增加。如果第一期全量上多模态，2500 份文档的处理成本可能要上千元，且 80% 的图片其实没有多模态检索的必要，纯属浪费。

▎关键细节 & 踩坑点

  • 不要迷信"多模态就是更先进"，工业场景下 90% 以上的知识都在文字和表格里，图片大多是辅助说明，OCR + 离线打标生成 Caption 的方式，效果往往比直接做多模态检索更可控，因为你可以审核和修正 Caption 内容，而多模态 Embedding 是黑盒，你不知道它到底提取了图片里的什么特征。
  • 用多模态模型给图片打 Caption 时，Prompt 必须明确要求输出结构化的信息，比如"请描述这张故障图片中的：1.故障部位 2.故障现象 3.可能的原因"，而不是泛泛地"描述这张图片"，否则生成的 Caption 信息密度不够，检索效果差。
  • 表格处理是很多 RAG 系统的重灾区，不要把表格拆成一行一行的文本切片，应该用 Markdown 格式保留表格结构，或者用专门的表格解析工具提取行列关系，再生成 Embedding，否则检索时会把完整的表格拆得七零八落。
  • 第一期上线一定要做 Bad Case 收集，每周统计用户提问中"搜不到答案"的 Case，分析其中有多少是因为图片信息没被检索到，如果这个比例低于 10%，根本没必要上多模态。

▎可扩展优化

  • 建立图片类型分类器：自动识别文档中的图片是"装饰性配图"、"参数表格截图"、"设备实物图"、"故障部位特写"，只有后两类才进入多模态处理流程，进一步降低成本。
  • 引入混合检索路由：用户提问时先做意图识别，如果问题是问参数、规范、流程，走纯文本检索；如果问题包含"长什么样"、"哪个位置"、"截图里的"等关键词，自动路由到多模态检索链路，实现成本和效果的动态平衡。
  • 对历史维修记录做知识图谱增强：把故障现象、故障原因、维修方法、涉及零件抽成实体和关系，当用户问某个故障怎么修时，不仅返回文档片段，还能顺着图谱给出完整的故障排查链路，比纯向量检索准确率高很多。

🛠 应用题 · Q3 · 工程实现题

题型

工程实现题

场景标签

Codex Skills 开发工具链 工程规范

📝 题目

你所在的团队有 10 个开发人员，共同维护一个基于 Python 的 AI Agent 后端项目。团队希望统一使用 Codex CLI 作为 AI 辅助开发工具，并且沉淀一套团队共享的 Skills（比如代码规范检查、数据库迁移脚本生成、Dockerfile 编写规范、API 接口文档自动生成）。同时每个开发者自己也有一些个人常用的 Skills（比如个人快捷键配置、常用代码片段）。请你设计一套完整的 Codex Skills 目录结构方案，并写出关键的配置步骤和验证方法，确保团队共享 Skills 可以随项目代码一起版本控制，个人 Skills 不污染项目仓库。

💡 参考答案

▎解题思路

  1. 第一步：严格区分全局 Skills、项目级 Skills、全局 Agents、全局 Plugins 的存放路径，避免混淆。
  2. 第二步：设计项目内的标准目录结构，把团队共享 Skills 纳入 Git 版本控制，随项目一起分发。
  3. 第三步：编写安装脚本和验证流程，新同事入职可以一键配置环境，不需要手动复制文件。
  4. 第四步：给出标准 Skill 的编写模板和示例，确保团队成员写的 Skill 符合规范。

▎详细方案

第一部分：目录结构的严格划分

首先必须明确 Codex 三类扩展的存放位置，绝对不能混放：

个人全局目录（不纳入 Git，每个开发者自己维护）：
- 全局 Skills：C:\Users\[用户名]\.codex\skills\（Windows）或 ~/.codex/skills/（Mac/Linux），存放个人常用的、和具体项目无关的 Skill，比如个人代码片段、常用命令别名。
- 全局 Agents：C:\Users\[用户名]\.codex\agents\，存放个人自定义的子 Agent，比如个人专用的代码审查 Agent。
- 全局配置：C:\Users\[用户名]\.codex\config.toml，个人的 Codex 配置，比如默认模型、快捷键。
- 全局 Plugins：C:\Users\[用户名]\.codex\plugins\，从官方市场安装的插件。

项目级目录（纳入 Git 版本控制，团队共享）：
项目根目录下的结构必须是：

your-agent-project/
├── AGENTS.md               # 项目级全局提示词，规定整个项目的编码规范、技术栈
├── .agents/
│   └── skills/             # 团队共享的项目级 Skills，提交到 Git
│       ├── code-style/     # 代码规范检查 Skill
│       │   └── SKILL.md
│       ├── db-migration/   # 数据库迁移脚本生成 Skill
│       │   ├── SKILL.md
│       │   └── references/ # 存放数据库表结构文档，作为 Skill 的参考资料
│       │       └── schema.md
│       ├── docker-writer/  # Dockerfile 编写规范 Skill
│       │   └── SKILL.md
│       └── api-doc/        # API 接口文档生成 Skill
│           └── SKILL.md
├── .gitignore              # 必须把 .codex/ 目录加入 .gitignore
└── 其他项目文件...

这里最关键的一点：项目级 Skills 必须放在 .agents/skills/ 下，绝对不能放在 .codex/skills/ 下，因为 .codex/ 目录是 Codex 运行时生成的缓存、日志、临时配置目录，不同人的环境下内容不一样，如果把 .codex/ 提交到 Git 会造成大量冲突，而且不符合官方规范。

第二部分：标准 Skill 的编写规范

每个 Skill 目录下必须至少有一个 SKILL.md 文件，文件头部必须有 YAML Frontmatter 声明名称和使用场景，例如 code-style/SKILL.md 的内容：

---
name: code-style
description: 当需要编写新的 Python 代码、或者审查现有代码是否符合规范时使用这个 Skill
---

你是这个项目的代码规范审查专家，必须严格遵循以下规则：
1. 所有 Python 代码必须符合 PEP8 规范，使用 4 空格缩进，行宽不超过 120 字符
2. 所有函数必须有类型注解和 Google 风格的 docstring
3. 数据库操作必须使用 SQLAlchemy 2.0 语法，禁止写裸 SQL
4. 所有外部 API 调用必须加超时和重试机制
5. 异常捕获禁止使用裸 except，必须指定具体的异常类型

当用户让你写代码或审查代码时，先对照以上规则检查，再输出结果。

第三部分：新同事入职的一键配置脚本

在项目根目录写一个 setup-codex.ps1（Windows）或 setup-codex.sh（Mac/Linux）脚本，自动完成配置：

# 1. 检查 Codex CLI 是否安装
if (-not (Get-Command codex -ErrorAction SilentlyContinue)) {
    Write-Error "请先安装 Codex CLI"
    exit 1
}

# 2. 把项目根目录的 AGENTS.md 和 .agents/skills 链接到 Codex 能识别的位置
$projectRoot = Get-Location
$codexProjectConfig = Join-Path $HOME ".codex\projects\$($projectRoot.Name)"
New-Item -ItemType Directory -Path $codexProjectConfig -Force | Out-Null

# 3. 提醒用户重启 Codex 或执行 Force Reload Skills
Write-Host "配置完成！请重启 Codex 或执行 /reload skills 命令加载团队共享 Skills"
Write-Host "可用的团队 Skills：$code-style, $db-migration, $docker-writer, $api-doc"

第四部分：验证方法

配置完成后，每个开发者执行以下步骤验证：
1. 重启 Codex CLI，输入 $code-style 检查当前目录下的 main.py 文件，看 Codex 是否能正确调用代码规范 Skill。
2. 输入 /skills 命令，查看列出的 Skills 中是否包含团队共享的四个 Skill。
3. 测试个人全局 Skill：在 ~/.codex/skills/ 下放一个个人测试 Skill，确认可以调用，且不会出现在 Git 变更列表中。

▎关键细节 & 踩坑点

  • 必须把 .codex/ 目录加入项目的 .gitignore，否则每个开发者运行 Codex 生成的缓存文件都会被提交到 Git，造成大量无意义的冲突。
  • 不要把个人常用的 Skill 放到项目的 .agents/skills/ 目录下，否则会被提交到 Git 影响其他同事，个人 Skill 一律放全局目录。
  • Skill 的 description 非常重要，Codex 是根据 description 来判断什么时候调用这个 Skill 的，如果 description 写得太模糊，Codex 会在不该调用的时候乱调用，或者该调用的时候想不起来。
  • Skill 目录下的 references 文件夹可以放参考文档，比如数据库表结构、API 规范，Codex 调用 Skill 时会自动读取这些文件作为上下文，不需要每次都把这些内容写到 SKILL.md 里，避免 SKILL.md 过于臃肿。
  • 很多人安装完 Agent 后发现 Skills 列表里看不到，这是正常的——Agents 是放在 ~/.codex/agents/ 下的，不会出现在 Skills 列表里，必须通过点名调用或者让 agents-orchestrator 来调度，不要因为看不到就以为安装失败了。

▎可扩展优化

  • 编写团队 Skill 的 CI 检查：在 Git 提交时自动检查 .agents/skills/ 下的每个 Skill 是否有合法的 SKILL.md，Frontmatter 是否完整，避免有人提交不符合规范的 Skill。
  • 增加 Skill 版本管理：每个 Skill 的 SKILL.md 里加 version 字段，当团队更新 Skill 时，Codex 启动时自动检查版本，提醒开发者更新本地缓存。
  • 开发一个团队内部的 Skill 生成器：用一个小工具引导团队成员按照模板写新的 Skill，自动生成目录结构和 Frontmatter，降低 Skill 编写门槛。
  • 对接 SkillsLLM 作为发现源：团队成员可以在 SkillsLLM 上搜索开源的好用 Skill，经过安全审核后再引入到项目的 .agents/skills/ 目录下，注意不要直接把 SkillsLLM 当成一键安装源，安装前必须检查代码是否安全，有没有恶意操作。

题型

场景标签

Qdrant 磁盘占用 Windows/WSL2 向量数据库运维

📝 题目

你负责维护团队的 Qdrant 向量数据库，开发环境是 Windows 11 + Docker Desktop，生产环境是阿里云 Linux 服务器（Ubuntu 22.04）。最近开发同事反馈：他的本地 Qdrant storage 目录占用了 2.5GB 磁盘空间，但生产环境同样的 Collection、同样的数据量只显示几 MB，他以为是本地数据损坏了，直接删了 storage 目录重建，结果本地开发数据全丢了。请你排查这个磁盘占用差异的根本原因，给出本地开发环境的优化方案，把本地磁盘占用降到合理范围，同时设计一套 Qdrant 的备份恢复机制，避免以后再出现误删数据的事故。

💡 参考答案

▎解题思路

  1. 第一步：先安抚同事，明确这不是数据损坏，而是 Linux 和 Windows 文件系统对稀疏文件（Sparse File）的处理机制差异导致的。
  2. 第二步：拆解 Qdrant 的文件组成，区分哪些是预分配的空洞文件，哪些是真正写入了数据的文件，哪些是多余的 Segment 碎片。
  3. 第三步：给出本地开发环境的存储配置优化方案，从根源上解决 Windows 下磁盘占用过高的问题。
  4. 第四步：设计完善的备份恢复流程，避免误删数据。

▎详细方案

第一步：定位根本原因——文件系统的稀疏文件机制差异

首先明确：数据没有损坏，两边的逻辑数据量是完全一样的，差异出在文件系统对预分配文件的落盘处理上。

Qdrant 运行时会创建几类固定大小的文件：
- 每个 Segment 的 page_0.dat、chunk_0.mmap 等页文件，逻辑大小通常是 32MB。
- WAL（Write-Ahead Log）预写日志文件，固定大小预分配。
- Payload 索引的预分配文件。

在生产环境的 Linux 文件系统（ext4/xfs）上，这些文件是稀疏文件（Sparse File）：文件逻辑上看起来有 32MB，但如果文件里的空白部分从来没有被写入过数据，操作系统不会给这些空白部分分配实际的磁盘块。所以用 ls -l 看文件大小是 32MB，但用 du -h（统计实际占用磁盘块）看只有几 KB，这就是为什么生产环境只显示几 MB。如果用 du -h --apparent-size 看逻辑大小，会和本地一样是几百 MB。

但在本地开发环境，同事用的是 Docker Desktop + Windows 目录 bind mount（./storage:/qdrant/storage，把 Windows 的 D:\xxx\storage 挂载到容器里的 /qdrant/storage）。在 Windows 的 NTFS 文件系统 + Docker Desktop bind mount 的场景下，这些预分配的文件不会被识别为稀疏文件，而是直接按照逻辑大小全额分配磁盘空间——逻辑上 32MB 的文件，就真的占 32MB 磁盘。再加上同事之前做过大量的写入和删除操作，Qdrant 产生了很多零散的 Segment 没有合并，每个 Segment 都有自己的一套预分配文件，所以最终占用达到了 2.5GB。

第二步：本地磁盘占用过高的直接优化

首先处理已经产生的 2.5GB 占用：
1. 调用 Qdrant 的 Segment 优化接口：对每个 Collection 执行 POST /collections/{collection_name}/service/optimize，触发强制段合并，把零散的小 Segment 合并成大 Segment，删除已经标记为删除的数据，减少 Segment 数量——这一步通常能把 2.5GB 降到 400-500MB 左右，因为合并后很多空的预分配文件会被回收。
2. 清理过期的 WAL 文件：Qdrant 默认会保留最近几个 WAL 文件，确认数据已经全部刷盘后，可以安全删除旧的 WAL 文件（不要直接删文件，通过 Qdrant 的 API 触发 WAL 清理）。

第三步：从根源解决本地磁盘占用问题——不要用 Windows 目录 bind mount

这是最核心的优化：把 Qdrant 的存储从 Windows 项目目录的 bind mount，改成以下两种方案之一：
- 方案一（推荐）：用 Docker Named Volume。把 docker-compose.yml 里的 volumes 配置从 ./storage:/qdrant/storage 改成 qdrant_storage:/qdrant/storage，Docker 会把数据存在 WSL2 的 Linux 文件系统里，这时候稀疏文件机制就生效了，同样的数据量磁盘占用会降到和生产环境差不多的水平（几 MB 到几十 MB）。
- 方案二：把 storage 目录放到 WSL2 的文件系统里。比如在 WSL2 里创建 ~/qdrant-storage 目录，挂载到容器里，因为 WSL2 是 Linux 文件系统，同样支持稀疏文件，磁盘占用会大幅降低。

优化后本地磁盘占用应该稳定在 50-100MB 左右（取决于实际写入的数据量），和生产环境的差异缩小到正常范围。

第四步：建立完善的备份恢复机制，避免误删

  1. 定时快照机制：写一个定时脚本，每天凌晨调用 Qdrant 的快照 API（POST /collections/{collection_name}/snapshots），生成 Collection 级别的快照，把快照文件备份到 OSS 或者其他独立的存储位置，不要和 Qdrant 的 storage 目录放在同一个磁盘上。
  2. 本地开发环境的数据备份：本地开发的 Qdrant 虽然是开发环境，但里面存了测试用的数据集，重建很麻烦，所以也要配置定期快照，快照存在项目的 .backup/qdrant/ 目录下，加入 .gitignore 不提交，但会留在本地磁盘。
  3. 危险操作保护：写一个 qdrant-cli 工具，封装常用的操作，比如"清理数据"必须输入 Collection 名称二次确认，禁止直接执行 rm -rf storage 这种危险操作。
  4. 恢复流程文档化：写清楚从快照恢复的步骤：先创建空 Collection，再调用 POST /collections/{collection_name}/snapshots/upload 上传快照文件，Qdrant 会自动恢复数据，不需要手动复制 storage 目录。

▎关键细节 & 踩坑点

  • 不要看到本地磁盘占用比线上大就以为数据损坏，先在 Linux 环境下用 du -h 和 du -h --apparent-size 对比实际占用和逻辑大小，再在 Windows 下看文件大小，确认是稀疏文件的问题。
  • 不要直接删除 storage 目录下的文件！Qdrant 的存储文件是有内部结构的，手动删文件几乎一定会导致数据库损坏，所有操作都要通过 Qdrant 的官方 API 来执行。
  • Docker Named Volume 的数据存在 WSL2 的虚拟磁盘里，如果 WSL2 虚拟磁盘占用过大，可以执行 wsl --shutdown 后用 diskpart 压缩虚拟磁盘，释放未使用的空间。
  • Segment 数量过多不仅占磁盘，还会影响检索性能，生产环境要配置合理的 Segment 优化阈值，不要让 Segment 数量无限增长。
  • Windows 下的 Docker Desktop bind mount 不仅有磁盘占用问题，IO 性能也比 WSL2 文件系统差很多，做开发的时候尽量把需要频繁读写的容器存储放在 Named Volume 或者 WSL2 文件系统里。

▎可扩展优化

  • 配置 Qdrant 的监控：用 Prometheus + Grafana 监控 Qdrant 的磁盘占用、Segment 数量、WAL 大小、检索延迟，当 Segment 数量超过阈值或者磁盘占用增长异常时自动报警。
  • 本地开发环境可以开启 Qdrant 的内存存储模式（如果数据量不大），不需要持久化到磁盘，重启后数据清空，适合单元测试和集成测试场景，完全不占磁盘空间。
  • 生产环境配置自动备份策略：每天全量快照，每小时增量 WAL 备份，备份数据保留 30 天，定期做恢复演练，确保备份是可用的。
  • 如果团队有多个开发人员，可以搭一个共享的开发环境 Qdrant 实例，大家共用一套测试数据集，不需要每个人本地都存一份，进一步节省磁盘空间，也保证测试数据的一致性。

第一阶段：模型选型与分层部署架构

Hermes 3 是 Nous Research 基于 Llama 3 等底座专门为 Agent 场景微调的模型，核心优势是 Function Calling 稳定、结构化输出靠谱、没有过度对齐的道德说教、完全服从 System Prompt，非常适合企业内部 Agent 场景。

根据 2 台 8卡 A10（40GB）的硬件资源，做分层模型部署，不要所有任务都跑大模型：
- 主管模型层（Supervisor）：部署 Hermes 3 70B 版本，用 4 张 A10 卡做张量并行，开启 Int8 量化，单卡显存占用约 20GB，4 卡刚好放下。这个模型负责复杂任务：任务规划、多工具调度、复杂代码生成、CR 评论、跨文档知识库问答、长会议纪要整理。它扮演多 Agent 系统里的"主管"角色，负责把复杂任务拆解成子任务，分发给下面的小模型执行。
- 工作模型层（Worker）：部署 2 个 Hermes 3 8B 版本的实例，每个实例用 1 张 A10 卡，开启 FP16 精度，不需要量化。这两个实例负责高频简单任务：单测生成、简单代码补全、周报草稿生成、常规知识库问答、意图识别、参数提取。8B 模型响应速度极快，Token 生成速度可以达到 100+ tokens/s，适合高并发的简单任务。
- Embedding 和 Rerank 层：用剩下的 2 张 A10 卡部署 bge-m3 向量模型和 bge-reranker-v2-m3 重排模型，支撑内部 RAG 知识库的检索需求。
