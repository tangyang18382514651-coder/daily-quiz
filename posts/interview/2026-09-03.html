📌 概念题 · Q1

考点标签

Linux 进程管理 · 难度：⭐⭐⭐

📝 题目

知识库中反复强调：Agent 服务不能因为 SSH 终端断开就挂掉，并推荐了 Tmux 和 Systemd 两种方案。请问：Tmux 和 Systemd 在 Agent 部署中的本质区别是什么？为什么开发调试期和生产部署期要选用不同的方案？

💡 参考答案

▎一句话结论

Tmux 是"交互式会话保持器"，面向人在回路；Systemd 是"系统级进程守护者"，面向无人值守。

▎核心原理

  • Tmux 创建的是虚拟终端会话，SSH 断开后进程仍在该会话中运行，但进程本身不受系统托管
  • Systemd 将 Agent 注册为系统服务（Unit），由 init 进程直接托管，具备开机自启、崩溃自动拉起、日志收集等能力
  • 两者核心差异在于：谁来负责进程的"存活保障"——Tmux 靠用户手动管理，Systemd 靠操作系统自动管理

▎深入解释

可以把 Tmux 理解为"给服务器开了一个永不关闭的远程桌面窗口"。你在这个窗口里跑 Agent，断网了窗口还在，重新连上就能"恢复现场"看到输出。但它有一个致命缺陷：如果 Agent 进程自己崩溃了，Tmux 不会帮你重启，你只能手动再跑一次。Systemd 则完全不同——你把 Agent 写成一个 .service 文件交给 Systemd 后，它就像"雇了一个 7×24 小时的保安"，进程挂了立刻拉起，服务器重启后自动恢复服务。类比：Tmux 是你自己搭的帐篷，Systemd 是物业公司。

▎面试加分点

  • 主动提出"混合模式"：开发期用 Tmux 快速迭代调试，上线前把启动命令封装成 Systemd Unit，通过 systemctl restart agent 实现灰度发布
  • 能补充说明 Systemd 的 Restart=always + LimitNOFILE + EnvironmentFile=.env 等关键配置项，体现真正写过生产配置

▎常见误区

  • 以为 Tmux 能防崩溃——它只防"断连"，不防"崩进程"
  • 以为 Systemd 只能跑二进制——它同样能托管 Python 脚本，只需在 ExecStart 里写 python3 /path/to/agent.py

📌 概念题 · Q2

考点标签

Linux 安全沙盒 · 难度：⭐⭐⭐⭐

📝 题目

知识库中给出了一个强警告："如果 Agent 拥有 Computer Use 或 Code Execution 能力，千万不要在 Linux 宿主机上直接给它 root 权限！一定要把它丢进 Docker 容器或虚拟机隔离"。请问：Docker 容器隔离在 Agent 安全场景下具体能防住什么？它和虚拟机隔离的本质区别是什么？为什么说"幻觉执行 rm -rf /"在 Docker 里也并非绝对安全？

💡 参考答案

▎一句话结论

Docker 提供的是进程级、文件系统级、网络级的"软隔离"，能防住绝大多数"幻觉误操作"，但防不住"内核逃逸"和"资源耗尽"；虚拟机才是真正的"硬隔离"。

▎核心原理

  • Docker 通过 Namespace 隔离进程/网络/挂载点，通过 Cgroup 限制 CPU/内存/磁盘 IO，Agent 在容器内 rm -rf / 只会删掉容器自己的文件系统层
  • Docker 容器共享宿主机的 Linux 内核，一旦存在内核漏洞或用户挂载了宿主机目录（-v /:/host），隔离就可能被穿透
  • 虚拟机拥有独立的 Guest OS 内核，即使 Agent 执行了恶意代码，攻击面也被限制在虚拟机内部

▎深入解释

把 Docker 比作"大楼里的隔间办公室"——墙是有的，但整栋楼的地基（内核）是共享的。Agent 在隔间里乱砸东西，最多砸烂自己的办公桌，不会影响隔壁。但如果它发现了"大楼结构图"（内核漏洞），理论上可能砸穿墙壁。虚拟机则像"独立的小楼"，地基完全分开，安全性更高但资源开销也更大。对于 Agent 场景，Docker 的性价比极高：用 --memory=4g --cpus=2 --read-only 限制资源，用 --user=nobody 降权运行，用 --network=none 断网，就能防住 99% 的"死循环写满磁盘"和"幻觉删库"事故。

▎面试加分点

  • 能说出 Docker 安全三件套：非 root 用户运行（--user）+ 资源限额（--memory/--cpus）+ 只读文件系统（--read-only）
  • 主动提出"双层沙盒"策略：外层 Docker 做资源隔离，内层再叠加 Python 的 seccomp 或 nsjail 做系统调用过滤
  • 能举出真实案例：某 Agent 幻觉执行了 while True: os.fork()，因为 Docker 限制了 PID 数量（--pids-limit 100）才没把宿主机搞挂

▎常见误区

  • 以为 Docker 等于绝对安全——它只是"减小攻击面"，不是"消除攻击面"
  • 以为只有 Code Execution 才需要沙盒——Computer Use（GUI 操作）的风险同样大，比如 Agent 误点"格式化磁盘"按钮

📌 概念题 · Q3

考点标签

CUDA 多卡调度 · 难度：⭐⭐⭐

📝 题目

知识库中提到，在多卡服务器上通过 export CUDA_VISIBLE_DEVICES=0 或 =1,2 来实现不同 Agent 项目的显卡物理隔离。请问：这个环境变量的底层作用机制是什么？为什么说"代码层零改动"是它的核心优势？它和 PyTorch 里的 .to('cuda:0') 是什么关系？

💡 参考答案

▎一句话结论

CUDA_VISIBLE_DEVICES 是在 CUDA 驱动层做"设备号重映射"，让进程根本"看不见"被屏蔽的 GPU，因此上层的 PyTorch/TensorFlow 代码无需任何修改即可实现物理隔离。

▎核心原理

  • 该环境变量由 CUDA 驱动在初始化时读取，驱动只会向进程暴露"可见列表"中的 GPU 设备
  • 重映射规则：CUDA_VISIBLE_DEVICES=1,2 时，进程内部看到的 cuda:0 实际对应物理 1 号卡，cuda:1 对应物理 2 号卡
  • 隔离发生在驱动层，比在框架层（如 PyTorch 里手动指定 cuda:1）更彻底——被屏蔽的 GPU 对进程完全不可见，连显存查询都查不到

▎深入解释

想象一个公寓楼有 8 个房间（8 张 GPU），每个租户（Agent 进程）手里有一份"可用房间清单"。CUDA_VISIBLE_DEVICES 就是这张清单——物业（CUDA 驱动）只把清单上的房间号告诉租户，租户从头到尾都不知道其他房间的存在。更妙的是"房号重映射"：物业告诉租户"你的 1 号房"其实是整栋楼的 3 号房，租户完全不需要知道真相。这就是为什么代码里写的 cuda:0 不用改，只要启动脚本里换一下环境变量，同一个代码就能无缝切换到不同物理卡上。这在多团队共享一台 8 卡 A100 服务器时极其高效：A 团队 export CUDA_VISIBLE_DEVICES=0,1,2,3，B 团队 =4,5,6,7，互不干扰。

▎面试加分点

  • 能补充说明：除了物理隔离，还可以用 NVIDIA MIG（Multi-Instance GPU） 把一张大卡切成多个独立实例，实现更细粒度的算力切分
  • 能指出一个常见坑：如果代码里硬编码了 torch.cuda.set_device(3)，而 CUDA_VISIBLE_DEVICES=0,1 只暴露了 2 张卡，会直接报错——所以最佳实践是永远用 cuda:0 配合环境变量，而不是硬编码物理卡号
  • 能提到 nvidia-smi 查看时要注意：容器或环境变量屏蔽后，nvidia-smi 默认仍显示物理编号，需要加 -L 查看逻辑映射

▎常见误区

  • 以为设置 CUDA_VISIBLE_DEVICES 后显存会被自动回收——它只影响新启动的进程，对已在跑的进程无效
  • 以为所有深度学习框架都遵守这个变量——绝大多数遵守，但某些推理引擎（如 TensorRT）需要额外配置

📌 概念题 · Q4

考点标签

多智能体架构 · 难度：⭐⭐⭐⭐

📝 题目

知识库在描述「全功能 HR Agent 协同网络」时，给出了一个关键架构决策："千万不要在一个巨大的 Prompt 里让大模型同时做所有的事，那样大模型会彻底过载。目前的最佳实践是利用 LangGraph 或 Multi-Agent 框架，把它们写成独立的节点（Nodes）。" 请问：为什么"一个巨大 Prompt 做所有事"会导致模型过载？把任务拆成多个独立 Agent 节点后，系统的"智能"从单点转移到了哪里？

💡 参考答案

▎一句话结论

单体巨型 Prompt 的过载本质是"注意力稀释"——模型有限的上下文窗口和推理能力被大量无关指令瓜分；拆分为多 Agent 节点后，系统的智能从"单次推理的深度"转移到了"状态机编排的精度"。

▎核心原理

  • 大模型的注意力机制决定了：Prompt 越长，每个 Token 分到的注意力权重越稀疏，关键指令容易被"淹没"在噪声中
  • 单体 Prompt 无法实现"条件分支"——比如"如果是医疗报销就走 RAG，如果是开证明就走审批流"，所有分支逻辑都要靠模型自己判断，极易混淆
  • 多 Agent 架构将"做什么"（意图路由）、"怎么做"（工具执行）、"怎么验证"（安全合规）拆成独立节点，每个节点只处理单一职责，Prompt 短而精准

▎深入解释

用一个比喻：单体 Prompt 相当于"把整个公司的所有部门员工叫到一个会议室里，同时下达 20 条不同的工作指令"。每个人都在听，但没人知道自己到底该干什么，最终产出混乱。多 Agent 架构则像"流水线"——前台（路由 Agent）只负责判断访客来意，然后转给对应的专业窗口（RAG Agent / 填单 Agent / 安全 Agent），每个窗口的人只精通一件事。系统的"智能"不再依赖某一次超长的推理，而是体现在状态机如何在不同节点间传递上下文、挂起等待、恢复执行。在 LangGraph 中，这种智能被具象化为图结构：节点（Node）是执行单元，边（Edge）是流转规则，State 是共享记忆。

▎面试加分点

  • 能说出单体 Prompt 的量化劣化：当指令超过 2000 Token 时，模型对"中间部分"指令的遵循度会显著下降（Lost in the Middle 现象）
  • 能提出"分层路由"的工程实践：第一层用规则/向量做粗筛（省钱），第二层用 LLM 做精细意图判断（保准），第三层用独立 Agent 做领域执行（提效）
  • 能补充说明：拆分后每个节点可以独立调试、独立评测、独立升级模型版本，这是单体 Prompt 无法做到的工程优势

▎常见误区

  • 以为拆得越细越好——节点过多会导致编排复杂度爆炸，状态传递开销增大，一般 3-7 个核心节点最合适
  • 以为拆分后就不需要大模型了——每个节点内部仍然是 LLM 在驱动，只是每个节点的 Prompt 更聚焦

📌 概念题 · Q5

考点标签

意图识别架构 · 难度：⭐⭐⭐⭐

📝 题目

知识库提出了意图识别的「三级分流模式」：一快（规则硬编码）、二省（向量相似度）、三准（大模型推理）。请问：这种三级分流的本质是在平衡什么？为什么不能"一刀切"全部走大模型？在什么情况下，向量相似度层会失效，必须降级到大模型？

💡 参考答案

▎一句话结论

三级分流的本质是在"响应时延、Token 成本、识别准确率"三者之间做帕累托最优——用规则兜底高频确定性场景，用向量覆盖中频模糊场景，用 LLM 攻克长尾复杂场景。

▎核心原理

  • 规则层（关键词/正则）：零成本、零延迟，但覆盖面极窄，只能处理"转人工"、"投诉"等强诉求
  • 向量层（Embedding 相似度）：毫秒级响应、成本极低，但依赖"用户输入与预设种子句的语义距离"，对未见过的表达方式会失效
  • LLM 层（Function Calling/JSON）：准确率最高、能处理多意图和上下文指代，但延迟高（秒级）、成本高（Token 消耗）

▎深入解释

用一个客服系统的真实数据来说明：假设每天有 10 万次用户请求，其中 30% 是"转人工"、"查余额"这类高频固定表达（规则层直接命中），40% 是"我的钱怎么少了"这类变体表达但语义清晰（向量层可以以 0.85 置信度命中），剩下 30% 是"我上个月在你们这儿买了个东西，然后我朋友说他也想要，但是他的地址和我不同..."这类复杂长尾表达（必须 LLM 深度推理）。如果全部走 LLM，每天 10 万次调用的 Token 成本和延迟将不可接受；如果全部走规则/向量，30% 的长尾用户会被错误分流，体验极差。三级分流让每一类请求都走"刚好够用"的路径。向量层失效的典型场景：用户使用了代词（"那个东西"）、多重意图混合（"我要退款顺便问下物流"）、或者领域外的表达方式（训练种子句里从未出现过的新说法）。

▎面试加分点

  • 能说出"置信度阈值"的动态调节策略：高峰期（双十一）把向量层阈值从 0.85 降到 0.75，让更多请求被快速消化，牺牲少量准确率换取吞吐量
  • 能提出"冷启动到精细化"的演进路径：先 LLM + Few-shot 快速上线 → 积累真实数据后训练专属 Embedding 模型 → 最终微调小参数模型作为专属 Router
  • 能补充说明：向量层需要定期更新种子句库，把 LLM 层新发现的"高频长尾表达"沉淀为新的种子句，形成闭环

▎常见误区

  • 以为向量相似度可以替代规则——向量对"精确匹配"（如订单号、工号）反而不如正则可靠
  • 以为三级分流是"串行"的——实际工程中通常是"并行探测"，规则先跑，同时向量和 LLM 也在评估，谁先高置信命中就用谁

📌 概念题 · Q6

考点标签

槽位填充 / 会话状态机 · 难度：⭐⭐⭐⭐

📝 题目

知识库在讨论 HR 场景的"追问用户"机制时，给出了一个关键工程细节："当大模型识别到工具 apply_employment_certificate 但必填参数 cert_type 为空时，SDK 不会返回 Tool Call，而是直接在 Content 里生成一句反问。工程上需要有一个会话状态机（State），把当前'准备开证明'的意图挂起（Pending），等员工回答后再拼接到上下文里。" 请问：这个"挂起（Pending）"状态在系统设计中解决的核心问题是什么？如果没有这个状态机，直接用"把反问和回答都塞进下一轮 Prompt"的方式，会出现什么致命缺陷？

💡 参考答案

▎一句话结论

Pending 状态解决的核心问题是"跨轮次的意图保持"——让系统记住"上一轮在等什么参数"，从而把用户的新回答精准拼接到原意图上，而不是把每轮对话当作独立的新请求。

▎核心原理

  • 无状态机时，每轮对话都是"从零开始"：用户说"在职证明"后，LLM 不知道这是在回答上一轮的反问，还是发起了一个全新的意图
  • Pending 状态将对话建模为"有限状态机"：当前状态 = 等待 cert_type 参数，用户输入 = 参数值，状态转移 = 补齐参数后触发工具调用
  • 状态机还支持"超时回滚"和"中途改意图"：如果用户 5 分钟不回复，Pending 自动过期；如果用户突然说"算了不开了"，状态机需要能重置

▎深入解释

用餐厅点餐来类比：服务员问"您要几分熟的牛排？"，顾客说"七分熟"。如果服务员没有"记性"（状态机），他会把"七分熟"当成一句全新的话来理解——"什么叫七分熟？是要点七份熟食吗？" 这就是无状态系统的致命缺陷。在 HR 场景中，这个缺陷更加严重：用户第一轮说"帮我开个证明"，系统反问"在职证明还是收入证明？"，用户回复"在职的"。如果没有 Pending 状态，LLM 看到"在职的"这三个字时，可能理解成"查询在职状态"或"在职培训报名"，导致工具调用完全错误。状态机的价值在于把"对话的时序性"转化为"显式的状态变量"，让每一轮推理都在正确的上下文锚点上进行。

▎面试加分点

  • 能说出 LangGraph 中实现 Pending 的标准做法：用 interrupt() 挂起图执行，用户回复后通过 Command(resume=...) 恢复，状态自动持久化到 Checkpointer
  • 能补充"多槽位并行填充"的进阶设计：一次反问可以同时问多个缺失参数（"请问您的入司时间和证明类型分别是？"），状态机维护一个 missing_slots 列表
  • 能提到"槽位冲突检测"：如果用户在 Pending 状态下又发起了新意图（"算了，帮我查下年假"），状态机需要判断是"覆盖旧意图"还是"并行处理"

▎常见误区

  • 以为"把反问和回答都塞进 Prompt"就能解决——短对话可能碰巧能用，但超过 3 轮后上下文污染严重，且无法区分"回答问题"和"发起新意图"
  • 以为 Pending 状态只能有一个——复杂场景下可能需要"嵌套 Pending"（等参数 A 时又问了一个子问题）

📌 概念题 · Q7

考点标签

工具设计 / 强管控 vs 纯 RAG · 难度：⭐⭐⭐

📝 题目

知识库提出了一个关键的工具设计原则：在 HR 场景中，"开证明"、"查年假"这类需要走接口、调系统的叫"强管控工具"；而"婚假有几天？"、"怎么点外卖报销？"这类政策咨询，不要给每个政策都写一个单独的工具描述，而是只定义一个 hr_knowledge_rag 总工具。 请问：这种"强管控工具 vs 纯 RAG 文本"的二分法，其背后的架构逻辑是什么？如果违反这个原则，给每个政策都写一个工具，会发生什么？

💡 参考答案

▎一句话结论

强管控工具和纯 RAG 的二分法本质是"确定性执行"和"概率性检索"的分离——需要精确调用系统 API 的场景必须有明确的工具边界和参数 Schema；纯知识查询场景则统一收敛到一个 RAG 入口，避免工具列表爆炸导致模型路由精度崩溃。

▎核心原理

  • 强管控工具的特征：有明确的副作用（写数据库、触发审批流）、需要精确参数（工号、证明类型）、需要审计日志
  • 纯 RAG 的特征：只读操作、答案在文档中、参数灵活（自然语言即可）、对"查不到"有兜底策略
  • 工具列表的长度直接影响 LLM 的 Function Calling 准确率：当工具超过 10-15 个时，模型"选错工具"的概率显著上升

▎深入解释

想象你是一个前台接待员，手里有一本"服务目录"。如果目录里有 300 个条目——"婚假政策咨询"、"产假政策咨询"、"年假政策咨询"、"病假政策咨询"...——你光是翻目录就要花 5 分钟，还经常翻错。但如果目录只有 10 个条目，其中一条是"人事政策咨询（涵盖所有假期、报销、福利政策）"，你看到"婚假有几天"就直接选这一条，然后去后面的资料柜里翻具体文件。这就是 hr_knowledge_rag 总工具的设计智慧：把"路由决策"和"内容检索"解耦。路由层只需要判断"这是不是政策咨询"，不需要知道具体是哪条政策；内容检索层（RAG）负责从向量库里找到最相关的文档片段。如果违反这个原则，给每条政策都写工具，模型在路由时就会被 300 个相似的工具描述搞晕——"婚假政策"和"产假政策"的 Tool Description 在语义上高度相似，模型很难精准区分。

▎面试加分点

  • 能提出"工具描述工程"的具体实践：强管控工具的 Description 要写清楚"什么时候用、什么时候不用、需要什么参数、有什么副作用"，RAG 工具的 Description 要写"适用于所有知识类、政策类、文档类查询"
  • 能补充"工具数量治理"的量化指标：当 Function Calling 的准确率低于 90% 时，优先考虑合并相似工具，而不是优化 Prompt
  • 能说出"强管控工具"的额外要求：幂等性设计（重复调用不会重复扣款/重复审批）、超时熔断、人工确认节点（高风险操作需要 Human-in-the-loop）

▎常见误区

  • 以为"工具越精细越好"——精细意味着更多路由决策负担，反而降低整体准确率
  • 以为 RAG 工具不需要参数——至少需要 query 参数（用户的具体问题），有时还需要 filters（如部门、时间范围）来做元数据过滤

📌 概念题 · Q8

考点标签

Agent 记忆系统 · 难度：⭐⭐⭐⭐

📝 题目

知识库在讨论企业级 Agent 记忆系统时，提出了一个关键架构原则："长期记忆不能'只进不出'，否则会导致向量空间污染和检索噪点"，并给出了"异步刷新（Buffer-to-Storage）"和"记忆压缩与冲突合并"两个解决方案。请问：为什么长期记忆"只进不出"会导致向量空间污染？"异步刷新"解决的核心矛盾是什么？"冲突合并"在用户偏好记忆场景下具体怎么做？

💡 参考答案

▎一句话结论

"只进不出"的记忆系统会导致向量空间中堆积大量过时、矛盾、低质量的信息，使得检索时"噪声淹没有效信号"；异步刷新解决的是"主链路低延迟"与"记忆高质量沉淀"之间的矛盾；冲突合并的核心是"新信息覆盖旧信息"的版本管理机制。

▎核心原理

  • 向量空间污染：每一条写入的向量都会参与相似度计算，如果旧的偏好（"我喜欢 Python"）和新的偏好（"我现在主攻 AI Agent"）同时存在，检索时可能同时返回矛盾信息，LLM 被误导
  • 异步刷新：用户对话的主线程只负责"读记忆"（低延迟），"写记忆"由后台 Worker 通过消息队列（Kafka/RabbitMQ）异步完成，避免阻塞对话响应
  • 冲突合并：通过"实体识别 + 时间戳 + 冷热标签"来判断新旧信息的关系——覆盖（用户改了偏好）、叠加（用户新增了偏好）、降权（用户很久没提这个偏好了）

▎深入解释

把长期记忆比作一个"个人档案柜"。如果只往里塞文件、从不清理，三年后这个柜子会变成什么样？里面有用户三年前说"我喜欢用 Java"的纸条，也有上周说"我现在只用 Go"的新纸条。当 Agent 需要判断"该给用户推荐 Java 还是 Go 的教程"时，它在柜子里翻出了两张矛盾的纸条，彻底懵了。这就是向量空间污染的真实危害——不是"查不到"，而是"查到太多互相矛盾的东西"。异步刷新的价值在于：对话主链路（用户等回复的那 2 秒内）只做"快速读取相关记忆"，不做"慢速写入新记忆"。写入动作被丢到 Kafka 队列里，由后台 Worker 慢慢做"提取-清洗-合并-写入"的完整流程。冲突合并的一个具体做法是：当识别到用户表达了一个与历史记忆冲突的新偏好时，不直接删除旧记忆，而是给旧记忆打上"已被覆盖"的标记并在检索时过滤掉，同时保留审计追溯能力。

▎面试加分点

  • 能提出"记忆 TTL 分层"策略：用户画像类记忆（如姓名、职位）长期有效；偏好类记忆（如技术栈）设置 90 天衰减期；事件类记忆（如某次任务的成功经验）永久保留但需要定期去重
  • 能补充"记忆质量评分"机制：每条记忆在写入时根据"来源可靠性、提及频率、时间新鲜度"计算一个质量分，检索时按质量分加权排序
  • 能说出"定期记忆体检"的运维实践：每周跑一个离线任务，统计向量库中各主题的条目数量、时间分布、矛盾对数量，发现异常及时告警

▎常见误区

  • 以为"只进不出"只是占存储空间——真正的危害是检索精度下降，且这种下降是"温水煮青蛙"式的，初期很难察觉
  • 以为异步刷新就是"延迟写入"——异步的核心不是"延迟"，而是"解耦"，让写入流程可以做得更重（如调用 LLM 做记忆提取）而不影响主链路

📌 概念题 · Q9

考点标签

多租户安全隔离 · 难度：⭐⭐⭐⭐

📝 题目

知识库在讨论企业级记忆系统时，特别强调了多租户隔离的硬性要求："A 部门的 Agent 绝对不能检索到 B 部门的敏感财务记忆"，并给出了实现方式："在向量数据库或 Redis 中，必须带有 tenant_id 或 user_id 的元数据标签（Metadata Filtering），在检索阶段从底层直接过滤。" 请问：为什么必须"从底层直接过滤"，而不是"检索出来之后再过滤"？这两种方案在安全性和性能上有什么本质区别？

💡 参考答案

▎一句话结论

"底层过滤"是在向量索引扫描阶段就排除无权数据，"检索后过滤"是先查出结果再剔除无权数据——前者是安全边界，后者是安全补丁；前者的性能开销可忽略，后者在高维向量场景下可能浪费 90% 以上的计算资源。

▎核心原理

  • 向量检索的本质是"在全量向量空间中找 Top-K 最近邻"，如果不在索引层做过滤，无权数据也会参与相似度计算，消耗算力
  • 底层过滤通过"预过滤（Pre-filtering）"或"过滤向量（Filtered Vector）"技术实现：先根据 tenant_id 缩小候选集，再做 ANN 搜索
  • 检索后过滤存在"K 值失真"问题：如果 Top-100 中有 80 条是其他租户的数据，过滤后只剩下 20 条，但用户期望的是 50 条，导致召回不足

▎深入解释

用图书馆借书来类比：底层过滤相当于"你只能进入自己学院的分馆，里面的书架上全是你们学院的书"——你在这个分馆里找书，又快又准。检索后过滤相当于"你在总馆里找书，找到 100 本相关的，然后管理员说'哦对不起，其中 80 本是你没有权限看的'，最后只给你 20 本"。你花了 100 本书的查找时间，只得到了 20 本书的结果，而且可能因为你想要 50 本而实际只拿到 20 本，信息严重不足。在向量数据库中，这个问题的技术实现是：Milvus 支持在 Collection 中为 tenant_id 字段建立标量索引，查询时通过 expr="tenant_id == 'dept_A'" 在 ANN 搜索前先做标量过滤。PGVector 则可以通过 WHERE tenant_id = 'dept_A' ORDER BY embedding <=> query_vector LIMIT 50 实现类似的预过滤。安全性的核心逻辑是：过滤条件必须在查询计划的最底层执行，而不是在应用层做"事后补救"——因为应用层过滤意味着数据已经离开了数据库，进入了应用内存，一旦代码有漏洞（比如忘记过滤），数据就泄露了。

▎面试加分点

  • 能说出"分区隔离"的进阶方案：为每个大租户创建独立的 Collection（或独立的向量索引），彻底物理隔离，适合租户数量少但数据量大的场景
  • 能补充"行级安全（Row-Level Security）"在 PostgreSQL 中的应用：通过 CREATE POLICY 让数据库自动在 SQL 查询中注入 tenant_id 过滤条件，即使应用层代码忘记写 WHERE 子句也不会泄露
  • 能提到"元数据过滤 + 向量相似度"的混合打分：Score = α × Dense_Score + (1-α) × BM25_Score，且租户过滤是前置的硬条件，不参与打分

▎常见误区

  • 以为"检索后过滤"只是性能问题——它首先是安全问题，因为数据已经进入了无权访问者的应用上下文
  • 以为加个 tenant_id 字段就够了——如果向量索引没有为 tenant_id 建立标量索引，过滤仍然需要全表扫描，性能极差

📌 概念题 · Q10

考点标签

Dify 二开 / 企业级平台选型 · 难度：⭐⭐⭐

📝 题目

知识库在讨论基于 Dify 的二次开发时，给出了一个企业落地优先级排序：P0 是"账号体系与精细化权限打通（Auth & RBAC）"和"彻底的私有化与本地模型集成（Data Privacy）"，P1 是"自定义企业内网工具与节点"，P2 才是"视觉换肤与品牌定制"。请问：为什么"账号体系打通"会被列为 P0 中的第一位，甚至排在"数据私有化"之前？如果一个企业跳过 P0 直接做 P1（接入内网工具），会发生什么？

💡 参考答案

▎一句话结论

账号体系是平台能否"上线"的生死线——没有 SSO 和 RBAC，业务部门根本无法合规使用（无法审计、无法管控权限）；数据私有化是"红线"但可以先用 Docker 内网部署快速满足；而跳过 P0 直接做 P1 会导致"功能很强大但没人敢用"的尴尬局面。

▎核心原理

  • 企业级平台的第一道门槛不是"功能强不强"，而是"能不能用"——没有 SSO，员工需要单独注册账号，IT 部门无法统一管理密码策略、离职回收、审计日志
  • RBAC 决定了"谁能看到什么、谁能调用什么"：财务部的知识库和 Agent 如果技术部也能访问，就是合规事故
  • P0 优先级的逻辑：先解决"能不能上线"（Auth），再解决"上线了会不会出事"（Privacy），最后才解决"上线后好不好用"（P1/P2）

▎深入解释

想象你要在一个 5000 人的公司里推广一个内部 AI 平台。如果平台没有接入公司的飞书/钉钉 SSO，员工需要单独注册账号，那么：① IT 部门无法统一管理账号生命周期（入职开通、离职禁用）；② 安全部门无法审计谁在什么时候调用了什么 Agent；③ 业务部门领导无法控制自己团队的数据不被其他部门看到。结果就是——平台功能再强大，也没有部门敢把自己的业务数据放上去。这就是为什么 Auth & RBAC 是 P0 中的第一位。而如果跳过 P0 直接做 P1（比如接入 CRM 系统的 API），你会发现一个尴尬的场景：Agent 可以查询 CRM 数据了，但你无法控制"哪个用户有权让 Agent 查哪些 CRM 数据"——因为权限体系还没建好。这相当于"给一个没有门锁的房子装了智能家居"，功能很炫但安全性为零。

▎面试加分点

  • 能说出具体的技术实现路径：修改 Dify 的 api/controllers/auth.py 接入 OAuth2/OIDC，通过 JWT 中的 department 字段映射到 Dify 的 Workspace 权限体系
  • 能提出"权限模型"的设计要点：至少需要三层——用户（User）、角色（Role）、资源（Resource/Agent/Knowledge Base），且支持"部门继承"（部门 A 的子部门默认继承 A 的权限）
  • 能补充"审计日志"的合规要求：企业级平台必须记录"谁在什么时间调用了什么 Agent、传入了什么参数、返回了什么结果"，且日志保留期限通常不少于 180 天

▎常见误区

  • 以为"数据私有化"应该排第一——私有化部署可以用 Docker 在一天内完成，但账号体系打通需要和企业的 IT/安全/HR 多个部门协调，周期长得多，所以必须提前启动
  • 以为"视觉换肤"只是锦上添花——对于内部平台确实优先级低，但如果是 SaaS 产品对外售卖，White-Labeling 就是 P0（客户不能看到你的品牌）

二、应用题（5 道 · 分类型）

🛠 应用题 · Q1 · 架构设计

题型

架构设计

场景标签

Linux 运维 Agent 常驻服务 GPU 资源调度 安全沙盒

📝 题目

你负责将公司内部的 HR 智能客服 Agent（基于 LangGraph 构建，包含意图路由、RAG 检索、填单追问、安全合规四个节点）部署到一台 4 卡 A100 的 Linux 服务器上。这台服务器同时还要跑另一个数据分析 Agent 项目。要求：两个项目互不干扰、HR Agent 必须 7×24 小时常驻、且 HR Agent 拥有 Code Interpreter 能力（允许 LLM 生成并执行 Python 代码来处理员工上传的 Excel 考勤表）。请给出完整的部署架构设计，包括：进程管理方案、GPU 隔离策略、安全沙盒设计、以及环境变量与密钥管理。

💡 参考答案

▎解题思路

  1. 先明确三个核心约束：常驻不中断（SSH 断开后服务不能挂）、GPU 物理隔离（两个项目各用各的卡）、代码执行安全（LLM 生成的代码绝不能直接跑在宿主机上）。
  2. 进程管理采用「开发调试用 Tmux，生产托管用 Systemd」的双轨策略，Systemd 保证开机自启和崩溃自动重启。
  3. GPU 隔离用 CUDA_VISIBLE_DEVICES 环境变量在 Systemd 服务单元文件中写死，从系统层物理屏蔽。
  4. Code Interpreter 必须放进 Docker 容器执行，容器内限制非 root 用户、内存上限（如 2GB）、CPU 核数（如 1 核）、禁用网络（防止代码外传数据），并设置超时强杀机制。
  5. 敏感信息统一走 .env 文件 + Systemd 的 EnvironmentFile 指令注入，代码内只用 os.environ.get() 读取。

▎详细方案

进程管理：
- HR Agent 的 Systemd 单元文件示例：

# /etc/systemd/system/hr-agent.service
[Unit]
Description=HR Intelligent Agent Service
After=network.target docker.service

[Service]
Type=simple
User=agent_user
WorkingDirectory=/opt/hr-agent
EnvironmentFile=/opt/hr-agent/.env
Environment=CUDA_VISIBLE_DEVICES=0
ExecStart=/opt/miniconda3/envs/hr_agent/bin/python -m uvicorn main:app --host 0.0.0.0 --port 8001
Restart=always
RestartSec=5
LimitNOFILE=65535

[Install]
WantedBy=multi-user.target
  • 数据分析 Agent 的 Systemd 单元文件里设置 Environment=CUDA_VISIBLE_DEVICES=1,2，两者互不干扰。
  • 开发调试阶段用 tmux new -s hr_dev 快速迭代，上线后切换到 Systemd。

安全沙盒（Code Interpreter）：
- 在宿主机上不直接执行 LLM 生成的代码，而是通过 Docker SDK 动态创建一次性容器：

import docker
import tempfile

def execute_code_sandbox(code: str, timeout: int = 10) -> dict:
    client = docker.from_env()
    container = client.containers.run(
        image="python:3.11-slim",
        command=["python", "-c", code],
        user="nobody",                    # 非 root 用户
        mem_limit="512m",                 # 内存上限
        nano_cpus=1_000_000_000,          # 限制 1 核 CPU
        network_disabled=True,            # 禁用网络
        read_only=True,                   # 只读文件系统
        working_dir="/sandbox",
        detach=True,
    )
    try:
        result = container.wait(timeout=timeout)
        logs = container.logs().decode("utf-8")
        return {"exit_code": result["StatusCode"], "output": logs}
    except Exception as e:
        container.kill()
        return {"exit_code": -1, "output": f"Timeout/Error: {e}"}
    finally:
        container.remove(force=True)
  • 如果代码需要处理用户上传的 Excel，先将文件挂载为只读卷到容器内，不允许容器写回宿主机。

环境变量与密钥管理：
- .env 文件权限设为 600，仅 agent_user 可读。
- Systemd 通过 EnvironmentFile 加载，代码内通过 os.environ.get('OPENAI_API_KEY') 读取，绝不硬编码。
- 不同环境（dev/staging/prod）使用不同的 .env 文件，通过部署脚本自动切换。

▎关键细节 & 踩坑点

  • Systemd 与 Conda 的坑：ExecStart 必须写绝对路径到 Conda 环境内的 Python 解释器，不能依赖 shell 的 source activate，否则 Systemd 找不到虚拟环境。
  • Docker 容器资源限制：光设 mem_limit 不够，必须同时设 nano_cpus，否则 LLM 生成一个死循环代码就能把整台服务器的 CPU 打满。
  • kill -9 与显存释放：如果 Agent 进程僵死，kill -9 后显存不一定会立即释放，需要检查 nvidia-smi 确认显存回收，必要时用 fuser -v /dev/nvidia* 找到残留进程。
  • CUDA_VISIBLE_DEVICES 的生效时机：必须在 Python 进程启动前设置，在代码里 os.environ['CUDA_VISIBLE_DEVICES']='0' 是无效的，因为 CUDA 上下文在 import torch 时就已经初始化。
  • Docker 容器的一次性设计：每次执行代码都新建容器并销毁，虽然开销大（约 1-2 秒），但能保证隔离的绝对性。如果追求性能，可以用预热容器池（Container Pool），但复杂度显著上升。

▎可扩展优化

  • 容器池预热：预先启动 3-5 个空闲容器，执行完代码后不销毁而是重置环境，将代码执行延迟从 2 秒降到 200ms。
  • gVisor / Kata Containers：如果安全等级要求更高（如金融行业），可以替换 Docker 默认的 runc 运行时，用 gVisor 提供内核级隔离。
  • GPU 动态调度：当 HR Agent 空闲时，通过脚本动态修改 Systemd 环境变量并重启服务，把空闲 GPU 临时让给数据分析 Agent，实现算力共享。
  • 日志集中管理：将 Agent 日志接入 Loki + Grafana，实现多服务日志的统一检索和告警。

import redis
import json
from datetime import timedelta

r = redis.Redis(host='localhost', port=6379, db=0)

class ShortTermMemory:
    def __init__(self, session_id: str, ttl_minutes: int = 30):
        self.session_id = session_id
        self.ttl = timedelta(minutes=ttl_minutes)

    def add_conversation(self, role: str, content: str):
        """追加一轮对话到滑动窗口（保留最近 10 轮）"""
        key = f"session:{self.session_id}:history"
        r.rpush(key, json.dumps({"role": role, "content": content}))
        r.ltrim(key, -10, -1)  # 只保留最近 10 轮
        r.expire(key, self.ttl)

    def set_slot(self, slot_name: str, value: str):
        """动态槽位：锁定关键业务参数"""
        key = f"session:{self.session_id}:slots"
        r.hset(key, slot_name, value)
        r.expire(key, self.ttl)

    def get_slot(self, slot_name: str) -> str | None:
        key = f"session:{self.session_id}:slots"
        val = r.hget(key, slot_name)
        return val.decode() if val else None

    def get_context_for_prompt(self) -> str:
        """组装注入 Prompt 的上下文：最近对话 + 槽位 + 摘要"""
        history_key = f"session:{self.session_id}:history"
        slots_key = f"session:{self.session_id}:slots"
        summary_key = f"session:{self.session_id}:summary"

        history = [json.loads(x) for x in r.lrange(history_key, 0, -1)]
        slots = {k.decode(): v.decode() for k, v in r.hgetall(slots_key).items()}
        summary = r.get(summary_key)

        context = f"## 会话摘要\n{summary.decode() if summary else '无'}\n\n"
        context += f"## 已锁定参数\n{json.dumps(slots, ensure_ascii=False)}\n\n"
        context += "## 最近对话\n" + "\n".join(
            f"{h['role']}: {h['content'][:200]}" for h in history
        )
        return context

class EpisodicMemory:
    def __init__(self, conn_string: str):
        self.conn = psycopg2.connect(conn_string)
        register_vector(self.conn)

    def store_case(self, error_signature: str, solution: str, embedding: list[float], success: bool):
        """存储一个成功/失败的案例"""
        with self.conn.cursor() as cur:
            cur.execute("""
                INSERT INTO episodic_cases (error_signature, solution, embedding, success, created_at)
                VALUES (%s, %s, %s, %s, NOW())
            """, (error_signature, solution, embedding, success))
        self.conn.commit()

    def retrieve_similar_cases(self, query_embedding: list[float], top_k: int = 3, success_only: bool = True) -> list[dict]:
        """检索最相似的历史案例"""
        with self.conn.cursor() as cur:
            cur.execute("""
                SELECT error_signature, solution, success, 
                       1 - (embedding <=> %s::vector) AS similarity
                FROM episodic_cases
                WHERE (success = %s OR %s = FALSE)
                ORDER BY embedding <=> %s::vector
                LIMIT %s
            """, (query_embedding, success_only, success_only, query_embedding, top_k))
            rows = cur.fetchall()
        return [
            {"signature": r[0], "solution": r[1], "success": r[2], "similarity": r[3]}
            for r in rows
        ]

class ProfileMemory:
    def __init__(self, conn):
        self.conn = conn

    def update_profile(self, user_id: str, field: str, new_value: str, source: str = "explicit"):
        """更新用户画像，处理冲突"""
        with self.conn.cursor() as cur:
            # 查当前值
            cur.execute("""
                SELECT value, source, updated_at 
                FROM user_profiles 
                WHERE user_id = %s AND field = %s
            """, (user_id, field))
            row = cur.fetchone()

            if row is None:
                # 新字段，直接插入
                cur.execute("""
                    INSERT INTO user_profiles (user_id, field, value, source, updated_at)
                    VALUES (%s, %s, %s, %s, NOW())
                """, (user_id, field, new_value, source))
            else:
                old_value, old_source, old_time = row
                # 冲突合并策略：
                # 1. 显式陈述 > 隐式推断
                # 2. 新时间 > 旧时间（覆盖）
                if source == "explicit" or old_source == "implicit":
                    cur.execute("""
                        UPDATE user_profiles 
                        SET value = %s, source = %s, updated_at = NOW()
                        WHERE user_id = %s AND field = %s
                    """, (new_value, source, user_id, field))
                # 3. 如果是同一来源，保留旧值但记录冲突日志
                else:
                    cur.execute("""
                        INSERT INTO profile_conflict_log 
                        (user_id, field, old_value, new_value, created_at)
                        VALUES (%s, %s, %s, %s, NOW())
                    """, (user_id, field, old_value, new_value))
        self.conn.commit()

▎关键细节 & 踩坑点

  • 循环上限必须硬编码：不能依赖 LLM 自己判断“是否应该继续循环”。LLM 的评估标准会漂移，有时候会过于严格（认为所有文档都不相关），有时候会过于宽松（认为所有文档都相关）。硬性上限 MAX_ITER=2 是最可靠的兜底。
  • 重写无效检测：如果重写后的 Query 和原 Query 的向量相似度 > 0.95，说明重写几乎没有改变语义，继续循环没有意义，应该直接用当前结果兜底。
  • Token 消耗的隐性来源：LangGraph 的 State 在每次节点跳转时都会携带完整的对话历史和中间结果。如果 State 中堆积了大量无关数据，每个节点的 Input Token 会指数级增长。需要在节点间传递时裁剪 State，只保留必要字段。
  • 评估模型的 Prompt 要极简：用 0.5B 小模型做评估时，Prompt 不能太长（不超过 500 tokens），否则小模型处理不了长上下文，延迟反而更高。
  • 流式输出：回答生成节点使用流式输出（Streaming），用户感知延迟可以从 2s 降到 500ms（首 Token 延迟），即使总延迟不变，用户体验也大幅提升。

▎可扩展优化

  • 异步评估：将「文档质量评估」和「回答生成」并行执行——评估在后台跑，回答先生成，如果评估发现文档不相关，再触发重试。这样正常请求的延迟不受评估影响。
  • Speculative Retrieval：在用户输入的同时，用规则快速预估可能需要的检索范围，提前发起检索请求，等意图识别完成时检索结果已经就绪。
  • 自适应循环策略：根据历史数据动态调整 MAX_ITER——对于简单查询（单跳），MAX_ITER=1；对于复杂查询（多跳），MAX_ITER=3。通过分类器判断查询复杂度。
  • 成本监控告警：在 LangGraph 的 Callback 中实时统计 Token 消耗，当单次对话 Token 超过阈值（如 8000）时触发告警，人工介入分析。
