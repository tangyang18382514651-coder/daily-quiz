📌 概念题 · Q1

考点标签

Agent 身份认证 · 难度：⭐⭐⭐

📝 题目

知识库中提到了三种 Agent 调用后台系统的身份认证方案：OAuth 授权码模式、服务账号模式（AppKey/AppSecret + HMAC 签名）和 API 网关统一拦截。请解释：为什么在「定时自动化后台任务」场景下，服务账号模式（Service Account）比 OAuth 授权码模式更合适？HMAC-SHA256 动态签名机制的核心安全价值是什么？

💡 参考答案

▎一句话结论

服务账号模式解决的是"没有人在场时的机器身份证明"问题，而 HMAC-SHA256 动态签名解决的是"证明请求确实来自持有密钥的那台机器，且请求内容在传输中未被篡改"的问题。

▎核心原理

  • OAuth 授权码模式的核心假设是"有一个真实人类在场，能够跳转浏览器完成授权点击"，但定时任务（如凌晨 3 点自动盘点）没有人类在场
  • 服务账号模式通过 AppKey（身份标识）+ AppSecret（共享密钥）建立长期稳定的机器身份，密钥存储在 Vault 等凭据中心而非代码仓库
  • HMAC-SHA256 签名将「时间戳 + 随机数 + 请求体」与 AppSecret 混合哈希，后台用同一把密钥重新计算并比对，实现身份验证 + 防重放攻击 + 防篡改三重保障

▎深入解释

OAuth 授权码模式本质上是"人类委托授权"的协议。它的流程中有一个不可跳过的环节：用户被重定向到授权服务器，在浏览器里点击"同意授权"。这保证了"人类意志"在授权链中的核心地位。但对于凌晨自动跑的库存盘点 Agent，没有人类能爬起来点按钮。如果强行用 OAuth，只能使用 Refresh Token 长期续期，但 Refresh Token 的首次获取仍然需要人类完成一次授权流程，且 Token 过期后如果无人值守就会导致任务静默失败。

服务账号模式则完全不同。管理员在后台创建一个名为 agent_replenish_service 的"机器员工"，系统生成一对 AppKey/AppSecret。Agent 的工程代码（不是大模型）从 Vault 中取出密钥，每次请求时用 HMAC-SHA256 算法计算签名。这个签名的精妙之处在于：它将 timestamp（时间戳）和 nonce（随机数）纳入计算，所以即使攻击者截获了请求报文，也无法在 5 秒后重放同一个请求——因为时间戳过期了。同时，如果攻击者篡改了请求体中的任何一个字符，签名就会完全对不上。

▎面试加分点

  • 强调"最小权限原则"：只给 Agent 勾选"库存只读"权限，不给写权限或超管权限，这是 PE 维度的安全意识
  • 提到密钥存储方案：环境变量 → HashiCorp Vault → KMS 加密的分层演进
  • 能画出完整的请求链路：Agent 代码 → Vault 取密钥 → 计算签名 → 网关验签 → 转发后台

▎常见误区

  • 误以为"服务账号就是写死一个用户名密码"，实际上服务账号的核心是动态签名而非静态密码
  • 误以为"HMAC 签名可以防止密钥泄露"，实际上签名只能防止传输篡改和重放，密钥本身必须靠 Vault 保护

📌 概念题 · Q2

考点标签

Agent 通信架构 · 难度：⭐⭐⭐⭐

📝 题目

知识库中反复强调一个核心观点："Agent 通信 = 代码跑腿 + 模型思考"，并指出"大模型（LLM）不负责网络传输，工程框架（如 Python、MQ、HTTP）负责"。请解释：为什么在 Multi-Agent 系统中，Agent 之间的通信不能直接让大模型"对话"？基于消息队列（MQ）的异步解耦设计相比同步 HTTP 调用，在哪些场景下有不可替代的优势？

💡 参考答案

▎一句话结论

大模型只是一个"思考器官"，它没有网络传输能力，Agent 之间的通信本质上是工程代码将模型的输出序列化后通过 MQ/HTTP 传输，再由对方代码反序列化后喂给另一个模型——MQ 的核心价值在于将"发送"和"处理"在时间维度上解耦。

▎核心原理

  • 大模型的输入输出是纯文本/Token，它无法直接"喊话"给另一台服务器上的 Agent，必须由工程代码完成网络 I/O
  • 同步 HTTP 调用要求接收方 Agent 实时在线且立即响应，一旦接收方正在处理高并发任务，发送方就会被阻塞
  • MQ（如 RabbitMQ、Kafka）允许发送方把消息"丢进队列"后立即返回，接收方空闲时再从队列中"捞出"处理，实现了时间维度的完全解耦

▎深入解释

很多人第一次接触 Multi-Agent 时会有一种浪漫的误解：以为 Agent A 和 Agent B 就像两个人在微信上聊天，你一言我一语。但工程现实是：Agent A 的"大脑"（大模型）输出了一段文本，比如 {"action": "purchase", "quantity": 50}，这段文本本身不会自己跑到 Agent B 那里。Agent A 的工程代码（Python/Go）必须把这段文本打包成 JSON，通过 HTTP POST 或 MQ 消息发送出去。Agent B 的工程代码收到后，把这段 JSON 拼接到自己的 Prompt 上下文中，再调用自己的大模型进行推理。

同步 HTTP 的致命问题在于"耦合"：如果采购 Agent 正在处理 100 个补货请求，库存 Agent 的第 101 个请求就必须排队等待。如果采购 Agent 恰好崩溃了，库存 Agent 的 HTTP 调用会直接报 Connection Refused，消息丢失。而 MQ 模式下，库存 Agent 只需把消息丢进队列就完成了自己的任务，采购 Agent 什么时候有空什么时候取。即使采购 Agent 宕机了，消息仍然安全地躺在队列里，等它重启后继续处理。

▎面试加分点

  • 能举例说明"财务 Agent 高并发排队处理报销时，采购 Agent 依然能发出消息"的场景
  • 提到消息确认机制（ACK）：消费者处理成功后才从队列中删除消息，失败则重新入队
  • 能区分 MQ 的两种模式：点对点（Queue）和发布订阅（Topic），并说明 Agent 场景下各自适用的情况

▎常见误区

  • 误以为"Agent 之间的通信就是让两个大模型互相发文字"，忽略了工程代码的桥梁作用
  • 误以为"MQ 一定比 HTTP 好"，实际上对于需要立即返回结果的同步场景（如客服 Agent 调用内容生成 Agent），HTTP 更简单直接

📌 概念题 · Q3

考点标签

分布式集群状态管理 · 难度：⭐⭐⭐⭐⭐

📝 题目

知识库中提出了分布式 Agent 集群的两大核心痛点："状态丢了"和"算力浪费（KV Cache 不能跨服务器复用）"，并给出了对应的解决方案：状态下沉到 Redis + 网关会话粘滞（Sticky Sessions）。请解释：为什么在弹性扩容场景下，PostgreSQL 作为 Checkpointer 会出现严重的 I/O 瓶颈？会话粘滞（一致性哈希路由）与无状态架构之间是否存在矛盾？

💡 参考答案

▎一句话结论

PostgreSQL 的强一致性和磁盘 I/O 特性决定了它不适合作为高并发集群的"热状态"存储，而会话粘滞与无状态架构并不矛盾——"无状态"指的是服务器节点本身不持有状态，而不是"状态不存在"，粘滞路由只是为了让同一个用户的请求尽量落在已经缓存了 KV Cache 的服务器上，即使落到了新服务器，状态仍然可以从 Redis 中恢复。

▎核心原理

  • PostgreSQL 是磁盘型数据库，每次 Checkpointer 读写都要经过磁盘 I/O，在长文本会话记忆的高频读写场景下，磁盘 I/O 成为瓶颈
  • Redis 是内存级存储，读写延迟在微秒级，天然适合作为"热状态"的中央仓库
  • 会话粘滞（Sticky Sessions）通过 hash $arg_session_id consistent 将同一用户的请求固定到同一台服务器，目的是命中 GPU 上的 KV Cache 前缀缓存，而非保存状态本身

▎深入解释

LangGraph 官方默认的 PostgresCheckpointer 在单机或低并发场景下运行良好，因为它提供了 ACID 事务保证和持久化能力。但一旦进入集群高并发场景，问题就暴露了：假设有 100 台服务器同时运行 Agent，每台服务器每完成一个推理步骤就要向 PostgreSQL 写入一次完整的状态快照（可能包含几万字的长文本对话历史）。PostgreSQL 的磁盘 I/O 能力是有限的，当写入请求超过磁盘吞吐量时，所有服务器都会被阻塞在数据库连接上，形成"雪崩"。

Redis 的解决方案是：把所有状态放在内存中，读写延迟从毫秒级降到微秒级。但纯 Redis 方案也有代价——内存贵、数据可能丢失。所以工业界的标准做法是"Redis 做热状态 + PostgreSQL 做冷持久化"：运行时读写 Redis，定期异步快照到 PostgreSQL。

会话粘滞与无状态的关系是面试中最容易被追问的点。正确理解是：服务器节点本身不存储任何用户状态（无状态），所以任何一台服务器挂了，用户的请求可以被网关重新分配到另一台服务器，新服务器从 Redis 中读出状态继续服务。但粘滞路由的存在是为了"性能优化"——如果用户的前 10 轮对话已经在服务器 001 的 GPU 上缓存了 KV Cache，那么第 11 轮请求继续发到服务器 001 就能直接复用缓存，首字延迟从 15 秒降到 2 秒。如果服务器 001 挂了，网关会把用户切到服务器 002，服务器 002 从 Redis 恢复状态，只是需要重新计算 KV Cache，延迟会短暂上升。

▎面试加分点

  • 能说出"无状态是正确性保障，粘滞是性能优化"这句话
  • 提到一致性哈希（Consistent Hashing）与普通取模哈希的区别：服务器增减时，一致性哈希只影响少部分用户，不会导致所有会话重新映射
  • 能提到"Prefix Caching 的触发条件是 Token 级别的前缀完全一致"，所以粘滞路由必须配合固定的 System Prompt 和 RAG 检索排序

▎常见误区

  • 误以为"用了 Redis 就不需要 PostgreSQL 了"，实际上两者是互补关系
  • 误以为"粘滞路由会导致服务器负载不均"，实际上一致性哈希 + 虚拟节点可以在粘滞和均衡之间取得平衡

📌 概念题 · Q4

考点标签

优雅终止与分层发布 · 难度：⭐⭐⭐⭐

📝 题目

知识库中详细描述了 FastAPI 的 Lifespan 异步生命周期管理器和 Docker Compose 的 depends_on + service_healthy 分层发布机制。请解释：什么是"优雅终止（Graceful Shutdown）"？为什么在 AI Agent 系统中，优雅终止比传统 Web 服务更加关键？分层发布的"拓扑顺序"为什么必须是 MCP Server → 网关 → 业务应用？

💡 参考答案

▎一句话结论

优雅终止是让服务器在收到停机信号后"先不接新活，把手里的活在途任务安全存盘后再关闭"的机制，而分层发布的拓扑顺序由依赖方向决定——上层业务依赖网关，网关依赖底层 MCP Server，所以必须自底向上发布。

▎核心原理

  • 传统 Web 服务的请求处理周期极短（毫秒级），即使暴力断电也只丢失极少量请求；但 AI Agent 的生成任务可能持续数十秒甚至数分钟（如生图、长文本流式生成）
  • FastAPI 的 Lifespan 钩子在应用启动时执行 yield 之前的逻辑，在应用关闭时执行 yield 之后的逻辑，通过 active_tasks 计数器阻塞进程退出
  • Docker Compose 的 depends_on 配合 condition: service_healthy 确保底层服务的健康检查端点（/health）返回 200 后，上层服务才启动

▎深入解释

在自媒体 Agent 系统中，一个典型的"生成小红书文案 + 配图"任务可能需要 30 秒到 2 分钟。如果发布新版本时直接 kill -9 杀掉进程，所有正在生成的任务都会中断，用户看到的就是"生成到一半卡住了"。更糟糕的是，如果 Checkpointer 还没来得及把中间状态写入数据库，这些任务的进度就永远丢失了。

Lifespan 的优雅终止流程是这样的：当发布平台（如 Kubernetes）向 Pod 发送 SIGTERM 信号时，FastAPI 的 Lifespan 钩子开始执行 yield 之后的代码。它首先通知网关"我准备下班了，别再给我分新任务"（通过就绪探针失败实现），然后进入一个 while active_tasks > 0 的循环，每秒检查一次是否还有在途任务。只有当所有在途任务都执行完毕、状态通过 Checkpointer 持久化落库后，进程才真正退出。

分层发布的拓扑顺序则是另一个维度的保障。假设系统拆分为：底层的 4 个 MCP Server（LLM 调用、RAG 检索、会话记忆、Prompt 管理）→ 中间层的 API 网关 → 上层的业务应用（智能客服、自媒体）。如果发布顺序搞反了，比如先发布了业务应用，而底层的 RAG MCP Server 还在旧版本，就会导致新版本的业务代码调用旧版本的接口，可能出现参数不匹配、协议不兼容等问题。depends_on 配合 service_healthy 保证了：只有当 RAG 服务的 /health 端点返回 200 且连续 3 次探测通过后，网关才会启动；只有当网关健康后，业务应用才会启动。

▎面试加分点

  • 能说出"优雅终止的核心是计数器 + 循环等待 + 状态持久化"三件套
  • 提到 Kubernetes 的 terminationGracePeriodSeconds 与 Lifespan 的配合关系
  • 能解释为什么健康检查端点不能只返回 200，还要检查依赖服务的实际连通性

▎常见误区

  • 误以为"优雅终止就是加一个 try-finally"，实际上需要配合网关的就绪探针、负载均衡器的摘流机制
  • 误以为"分层发布只需要按顺序执行 docker compose up"，实际上还需要考虑数据库迁移、配置中心更新等前置步骤

📌 概念题 · Q5

考点标签

多仓库架构与网关路由 · 难度：⭐⭐⭐

📝 题目

知识库中明确反对设计一个"总 Agent"来负责接入所有项目，主张采用"网关接入 + 平级协作"的模式。请解释：为什么"总 Agent"架构在企业级 Multi-Agent 系统中是反模式？基于 URL 路径路由的 FastAPI 网关相比"总 Agent 意图识别"在性能、可靠性和可维护性上有哪些优势？

💡 参考答案

▎一句话结论

"总 Agent"架构将大模型的非确定性引入了流量分发层，既是大模型能力的浪费，也是单点故障的温床；而基于 URL 路径的网关路由是确定性的、O(1) 时间复杂度的代码逻辑，不依赖任何模型推理。

▎核心原理

  • 大模型处理业务路由的准确率不是 100%，让模型去做流量分发意味着每次请求都有概率被分错
  • "总 Agent"是所有请求的必经之路，一旦它宕机或触发限流，全公司的所有 Agent 全部瘫痪
  • 网关路由是纯代码逻辑：看一眼 URL 路径（如 /api/v1/hr-customer），直接转发到对应的服务，延迟在微秒级

▎深入解释

"总 Agent"的想法在直觉上很吸引人：一个超级智能体，听懂用户说什么，然后决定派哪个小弟去干活。但工程现实是残酷的。首先，大模型推理是有延迟的（至少几百毫秒），如果每个请求都要先经过一次模型推理才能决定路由，那么整个系统的 P99 延迟会显著上升。其次，大模型有幻觉风险——用户说"帮我写个文案"，模型可能误判为"客服咨询"，把请求发给了客服 Agent。最后，也是最致命的，"总 Agent"是单点故障源。它挂了，所有业务全挂；它被限流了，所有业务全被限流。

网关路由则完全不同。FastAPI 网关的中间件链（认证 → 日志 → 配额 → 路由）全部是确定性代码，不涉及任何模型推理。URL 路径 /api/v1/hr-customer 永远只会转发到智能客服仓库部署的服务器，/api/v1/media-ops 永远只会转发到自媒体仓库。这种确定性意味着：性能可预测（微秒级转发）、可靠性可保障（网关本身可以水平扩展）、维护成本低（新增业务只需加一条路由规则）。

当 Agent 之间需要协作时，它们是"平级的邻居关系"，直接通过 HTTP 互相调用。比如智能客服在执行工作流时，某个节点直接调用自媒体 Agent 的接口："帮我生成一份针对这个候选人的小红书文案"。这种协作不需要一个"总老大"来指挥，而是通过共享的 MCP 服务层和统一的用户画像数据库实现数据互通。

▎面试加分点

  • 能说出"网关是确定性的，Agent 是非确定性的，确定性层应该包裹非确定性层"
  • 提到四层中间件链的设计：认证身份 → 记录日志 → 控制配额 → 路由转发
  • 能举例说明"平级协作"的具体场景：客服 Agent 调用内容 Agent 生成文案，两个 Agent 共享同一个 PostgreSQL 用户画像

▎常见误区

  • 误以为"网关路由就是简单的 Nginx 反代"，实际上企业级网关还需要处理 API Key 校验、Token 配额计量、多租户隔离
  • 误以为"平级协作就是 Agent 之间随意互相调用"，实际上需要统一的协议（如 MCP/A2A）和治理规范

考点标签

GraphRAG 与确定性解析 · 难度：⭐⭐⭐⭐

📝 题目

知识库中指出，企业垂直领域的知识库技术正在从"纯向量 RAG"转向"GraphRAG 与确定性解析"。请解释：为什么传统的"文档 → 切块 → 向量化 → 向量数据库"流程在处理财务报表、ERP 数据、复杂组织关系时频频翻车？Contextual Retrieval（上下文前缀拼接）是如何解决"切块后信息碎片化"问题的？

💡 参考答案

▎一句话结论

纯向量 RAG 的翻车根源在于"暴力切块"破坏了文档的语义完整性和实体间的拓扑关联，而 Contextual Retrieval 通过为每个 Chunk 自动生成包含母文档核心信息的"前缀补全"，在保留向量检索效率的同时恢复了上下文信息。

▎核心原理

  • 固定字符数切块（如每 500 字切一块）会粗暴地切断表格、段落标题、跨页脚注之间的逻辑关联，导致检索到的 Chunk 缺乏上下文
  • 财务报表中的"净利润"可能依赖于前文 10 页的"营收"和"成本"数据，单独检索到"净利润：5000 万"这个 Chunk 无法回答"为什么净利润下降了"
  • Contextual Retrieval 在入库前通过小模型为每个 Chunk 生成一段包含文档标题、章节主题、核心结论的"前缀"，使每个 Chunk 即使脱离原文也能被理解

▎深入解释

纯向量 RAG 的假设是"每个 Chunk 是一个自包含的信息单元"。这个假设在处理维基百科式的独立词条时成立，但在处理企业文档时完全崩塌。考虑一份 50 页的年度财务报告，其中"资产负债率 65%"出现在第 30 页。如果按 500 字切块，这个数据所在的 Chunk 可能只包含"资产负债率 65%，较去年同期上升 3 个百分点"这一句话。当用户问"公司的财务风险如何？"时，向量检索可能找到了这个 Chunk，但大模型无法从这个孤立的片段中理解：这个 65% 是高于行业平均还是低于？上升 3 个百分点是恶化还是改善？因为答案需要跨文档的多跳推理。

GraphRAG 的解法是：预先提取文档中的实体（公司、指标、时间、事件）及其关联（"资产负债率" → "属于" → "财务风险指标"），构建知识图谱。查询时，先通过向量检索找到语义相似的 Chunk，再通过图谱遍历找到与这些 Chunk 关联的其他实体和文档片段，形成"语义相似度 + 拓扑关联"的双轨检索。这种方案在处理"多跳推理"问题时，准确率比纯向量 RAG 提升了 35% 以上。

Contextual Retrieval 则是一个更轻量的补充方案。它不构建知识图谱，而是在切块后、向量化前，用一个小模型（如 GPT-4o-mini）为每个 Chunk 生成一段"上下文前缀"。例如，对于"资产负债率 65%"这个 Chunk，小模型会生成："本文档是 XX 公司 2025 年度财务报告，第 30 页讨论财务风险指标，前文分析了营收和成本数据，本段给出了资产负债率的具体数值。"这段前缀会和原始 Chunk 拼接后一起向量化。这样，即使检索时只命中了这个 Chunk，大模型也能从前缀中获得足够的上下文来正确解读数据。

▎面试加分点

  • 能区分 GraphRAG 和 Contextual Retrieval 的适用场景：前者适合多跳推理和全局总结，后者适合模糊查询的召回率提升
  • 提到 Docling-Studio 等多模态物理布局解析工具，强调"确定性 ingestion"对表格、页脚的保护
  • 能说出"向量检索解决的是相似度问题，图谱检索解决的是关联性问题，两者互补"

▎常见误区

  • 误以为"GraphRAG 就是比向量 RAG 更好"，实际上 GraphRAG 的构建成本高、维护复杂，适合对准确率要求极高的场景
  • 误以为"Contextual Retrieval 的前缀可以用大模型实时生成"，实际上是在入库时离线生成，避免查询时的额外延迟和成本

📌 概念题 · Q7

考点标签

Agent Harness 与状态机 · 难度：⭐⭐⭐⭐

📝 题目

知识库中提到，企业级 Agent 开发正在从"重框架（LangChain）"转向"轻量状态机（Graph/Harness）"，核心理念是"框架做减法，状态机做加法"。请解释：什么是 Agent Harness？为什么确定性状态机（Finite State Machine）比"让大模型自由决定下一步"更可靠？这种转变背后的工程哲学是什么？

💡 参考答案

▎一句话结论

Agent Harness 是一套"控制性框架"，它用确定性的状态机严格限制 Agent 的跳转路由——下一步能干什么由代码定义，而不是由大模型盲猜，从而将非确定性系统的风险控制在一个可预测的边界内。

▎核心原理

  • 传统 LangChain 的 AgentExecutor 允许大模型在任意时刻选择任意工具，这种"自由度过高"的设计在生产环境中极易因为幻觉调用错 API
  • 状态机（FSM）将 Agent 的执行流程建模为有限的状态集合和确定性的转移条件，每个状态只能跳转到预定义的下一状态
  • Agent Harness 不仅包含状态机，还包含沙盒环境、任务控制器、工具桥接器和自动评估器，是一套完整的"测试 + 运行 + 评估"框架

▎深入解释

LangChain 早期的 AgentExecutor 模式本质上是"让大模型在一个 while 循环里自由发挥"：每轮推理，模型决定调用哪个工具，工具返回结果，模型再决定下一步。这种设计在 Demo 中看起来非常智能，但在企业核心业务（如 HR 入职自动化、供应链审批）中是一个定时炸弹。模型可能在"查询库存"和"修改价格"之间自由切换，可能因为一个 Prompt 注入攻击而执行了未授权的操作，也可能在一个循环里反复调用同一个工具直到 Token 耗尽。

状态机的解法是"剥夺模型的自由"。以 HR 入职流程为例，状态机定义了严格的状态序列：验证身份 → 填写表单 → 提交审批 → 等待审批 → 生成合同 → 完成。模型在"验证身份"状态下只能调用身份证验证工具，不能调用"修改薪资"工具。即使模型产生了幻觉，认为"我应该调用修改薪资工具"，状态机也会在代码层拦截这个请求，因为"验证身份"状态没有到"修改薪资"的转移边。

这种转变背后的工程哲学是：把大模型看作一个"不确定性的 CPU"，用确定性的软件工程代码去驯服它。 模型擅长的是自然语言理解、文本生成、语义推理，而不是流程控制。流程控制应该由代码来做，因为代码是确定性的、可测试的、可审计的。Agent Harness 就是这种哲学的落地：它把模型的能力限制在"每个状态节点内的推理"，而把"状态之间的跳转"交给代码。

▎面试加分点

  • 能说出"状态机不是限制模型的能力，而是让模型在正确的边界内发挥能力"
  • 提到 LangGraph 的 add_conditional_edges 与状态机的关系：条件边由代码函数决定，而非模型自由选择
  • 能举例说明"Reviewer Agent"在状态机中的角色：作为合规检查节点，它的输出决定是否允许进入下一状态

▎常见误区

  • 误以为"状态机就是写死 if-else"，实际上状态机 + 模型推理是"代码控制路由，模型控制节点内的智能"
  • 误以为"Agent Harness 只是测试工具"，实际上它同时是运行时的控制框架和评估框架

📌 概念题 · Q8

考点标签

LLM-as-a-Judge 与自动化评估 · 难度：⭐⭐⭐⭐

📝 题目

知识库中指出，企业级大模型系统最难的是"如何证明你改完代码后，系统变聪明了还是变笨了"，并引入了 LLM-as-a-Judge 自动化评估。请解释：为什么传统的人工盲测无法支撑企业级 Agent 的持续迭代？LLM-as-a-Judge 中的 Groundedness（基于事实）、Context Adherence（上下文遵从度）和 Faithfulness（忠实度）分别衡量什么？它们之间有什么区别？

💡 参考答案

▎一句话结论

人工盲测的瓶颈在于"慢且不可复现"，无法支撑每次代码提交都跑几百个测试用例的 CI/CD 节奏；而 LLM-as-a-Judge 用大模型作为"裁判"，围绕事实性、上下文遵从度和忠实度三个维度进行自动化打分，实现了评估的规模化、标准化和可复现。

▎核心原理

  • 人工盲测的评估周期以天为单位，而企业级 Agent 的迭代节奏是每天多次提交，人工评估完全跟不上
  • Groundedness（基于事实）衡量的是：Agent 的输出是否基于检索到的文档内容，而不是模型编造的幻觉
  • Context Adherence（上下文遵从度）衡量的是：Agent 是否严格遵循了 System Prompt 中的指令和约束
  • Faithfulness（忠实度）衡量的是：Agent 的输出是否忠实于用户的实际意图，没有添油加醋或答非所问

▎深入解释

传统的人工盲测流程是：改完代码 → 部署到测试环境 → 找几个测试人员手动问几十个问题 → 人工判断回答质量 → 记录分数。这个流程的致命问题在于：第一，慢。一轮盲测至少需要半天到一天，无法跟上每天多次代码提交的迭代节奏。第二，不可复现。不同测试人员对"好回答"的标准不一致，同一个回答可能得到完全不同的分数。第三，覆盖度低。几十个测试用例无法覆盖企业知识库中成千上万种可能的查询场景。

LLM-as-a-Judge 的解法是：用一个大模型（通常是 GPT-4 级别）作为"裁判"，按照预定义的评分标准（Rubric）对 Agent 的输出进行打分。每次代码提交后，CI/CD 流水线自动运行几百个基准测试用例，每个用例包含：用户问题、检索到的上下文、Agent 的输出、以及裁判模型的评分。整个过程在几分钟内完成，评分标准完全一致，结果可复现。

三个评估维度的区别需要仔细区分。Groundedness 关注的是"输出是否有据可查"——如果 Agent 说"公司 2025 年营收 100 亿"，但检索到的文档中根本没有这个数据，那么 Groundedness 分数就很低。Context Adherence 关注的是"输出是否遵守了指令"——如果 System Prompt 要求"回答不超过 100 字"，但 Agent 输出了 500 字，那么 Context Adherence 分数就低。Faithfulness 关注的是"输出是否忠实于用户意图"——用户问"如何请假"，Agent 却回答"如何报销"，即使回答内容本身是正确的，Faithfulness 分数也低。

▎面试加分点

  • 能说出"Ragas 和 DeepEval 是当前主流的 LLM-as-a-Judge 框架"
  • 提到"裁判模型本身也需要校准"：定期用人工标注的黄金数据集来验证裁判模型的评分准确性
  • 能举例说明"评估指标的选择取决于业务场景"：客服场景更看重 Faithfulness，知识库问答更看重 Groundedness

▎常见误区

  • 误以为"LLM-as-a-Judge 就是让大模型随便打分"，实际上需要精心设计评分标准和 Few-Shot 示例
  • 误以为"三个指标是独立的"，实际上它们经常相互影响：一个输出可能同时违反多个指标

📌 概念题 · Q9

考点标签

Human-in-the-Loop 与读写分离 · 难度：⭐⭐⭐⭐

📝 题目

知识库中提出了一个关键的安全原则："坚决执行读写分离。对于高危的'写操作'工具，在网关层设置中断审批流，必须由业务人员在后台系统二次确认后才真正下发 API 动作。"请解释：为什么查询类操作可以全自动执行，而"修改价格"、"删除数据"、"同意审批"等写操作必须设置 Human-in-the-Loop？在工程实现上，如何做到"大模型只输出结构化 JSON，工程代码去底层安全地捞出 Token"？

💡 参考答案

▎一句话结论

读写分离的本质是风险不对称：查询操作的错误只影响用户体验，写操作的错误可能造成不可逆的业务损失；而"大模型只输出 JSON，工程代码捞 Token"的设计是为了让大模型永远接触不到敏感凭证，从根源上杜绝 Prompt 注入导致的凭证泄露。

▎核心原理

  • 查询类操作的错误是可恢复的——用户看到错误答案后可以重新问，系统不会因此产生实际损失
  • 写操作的错误是不可逆的——价格改错了、数据删掉了、审批通过了，可能造成直接的经济损失或合规风险
  • 大模型极易受到 Prompt 注入攻击：攻击者可以在用户输入中嵌入恶意指令，诱导模型泄露密钥或执行未授权操作

▎深入解释

在 Agent 系统中，读写分离不是技术上的限制，而是风险管理上的必然选择。查询操作（如"查一下 iPhone 的库存"）即使出错，最坏的结果是用户得到了错误信息，用户可以重新问，或者系统可以自动重试。但写操作（如"把 iPhone 的价格改为 1 元"）一旦执行，可能瞬间被大量用户以错误价格下单，造成不可挽回的损失。更危险的是"同意审批"类操作——如果 Agent 因为幻觉而错误地批准了一笔大额采购，后果可能是灾难性的。

Human-in-the-Loop 的工程实现通常是在网关层或工具层设置"中断点"。当 Agent 的工作流执行到"修改价格"节点时，代码不会直接调用后台系统的写接口，而是先在 OA/HR 系统中创建一张审批单，包含操作内容、操作理由、影响范围等信息，然后向 LangGraph 状态机抛出 Interrupt 信号，将会话挂起。当真实人类员工在后台点击"确认"后，系统通过 Webhook 回调唤醒 Agent，注入审批结果，Agent 才继续执行后续步骤。

"大模型只输出 JSON，工程代码捞 Token"的设计则是为了应对 Prompt 注入攻击。如果开发者把 API 密钥写在 Prompt 里（如"你现在用账号 admin 密码 123456 去调用接口"），攻击者可以通过构造恶意的用户输入，诱导模型把密钥吐出来。正确的做法是：大模型只负责输出结构化的意图（如 {"action": "get_inventory", "sku": "123"}），工程代码解析这个 JSON 后，从 Vault 或环境变量中安全地取出 Token，拼接成 HTTP 请求发出。这样，大模型从头到尾都接触不到任何敏感凭证。

▎面试加分点

  • 能说出"读写分离的粒度应该细化到工具级别，而非 Agent 级别"
  • 提到"审批流的 Task_ID 关联机制"：通过唯一 Task_ID 将审批单与挂起的 Agent 会话绑定
  • 能举例说明"查询操作也需要限流和熔断，只是不需要人肉审批"

▎常见误区

  • 误以为"Human-in-the-Loop 就是让用户确认每一步"，实际上只在写操作时中断，查询操作全自动
  • 误以为"把密钥放在环境变量里就绝对安全"，实际上还需要防止 Prompt 注入诱导模型调用读取环境变量的工具

📌 概念题 · Q10

考点标签

大小模型协同与 PEFT · 难度：⭐⭐⭐⭐

📝 题目

知识库中提出了企业垂直领域的模型选用策略："大小模型协同（SLM + LLM）"，并指出"企业生产环境中，高达 70% 的路由分类、实体提取、文本摘要等意图，已经全面下放到更便宜、高并发的小参数模型"。请解释：为什么不能所有任务都用最贵的闭源大模型？"微调的唯一目的是改变模型的行为范式，而不是让模型记住知识"这句话如何理解？QLoRA 在企业场景下的核心优势是什么？

💡 参考答案

▎一句话结论

大小模型协同的本质是"按任务的认知复杂度分配算力"——简单任务用便宜的小模型，复杂任务用昂贵的大模型，从而在保证质量的同时将推理成本压缩 40% 以上；而微调的目标是改变模型的"行为习惯"（如输出格式、专业术语口吻），而非让它记忆知识（那是 RAG 的工作）。

▎核心原理

  • 路由分类、实体提取、文本摘要等任务的认知复杂度较低，小参数模型（如 Gemini Flash、Qwen 低参数版本）已经能达到 95% 以上的准确率，而推理成本只有大模型的 1/10
  • 微调的本质是"改变模型的条件概率分布"：通过训练让模型学会"看到这种输入就应该输出这种格式"，而不是"记住某个具体的知识点"
  • QLoRA（Quantized LoRA）通过 4-bit 量化基础模型 + 低秩适配器，将显存需求从全参数微调的数百 GB 降低到单张消费级 GPU 可承载的水平

▎深入解释

"所有任务都用最贵的闭源大模型"在企业生产环境中是不可持续的。假设一个 HR 智能客服每天处理 10 万次请求，其中 70% 是简单的意图分类（如"我想请假" → 分类为"请假申请"）。如果用 GPT-4 级别的大模型处理这些请求，每天的成本可能是数千美元。但如果用 Gemini Flash 级别的小模型处理，成本可能只有数百美元，而分类准确率几乎相同。这就是"端云协同"的核心逻辑：小模型负责高并发的简单任务，大模型负责低频的复杂推理任务。

"微调改变行为范式，RAG 管知识"是一个重要的架构原则。很多企业犯的错误是：试图通过微调让模型"记住"公司的产品手册、规章制度。这种做法有两个问题：第一，知识会过期，每次知识更新都需要重新微调；第二，微调后的模型可能"记住"了知识但无法准确引用来源，产生幻觉。正确的做法是：微调只用于训练模型的"行为"——比如让模型学会用 HR 领域的专业术语口吻说话、学会输出严格的 JSON 格式、学会写特定风格的 SQL 查询。知识则通过 RAG 在推理时动态检索注入。

QLoRA 的技术优势在于：它通过 4-bit 量化将基础模型的内存占用降低到原来的 1/4，然后只训练一个极小的低秩适配器（通常只有基础模型参数的 0.1%~1%）。这使得企业可以用单张 RTX 4090 完成 70B 参数模型的微调，而全参数微调需要数十张 A100。更重要的是，QLoRA 的适配器可以独立保存和加载，同一个基础模型可以挂载多个不同的适配器，实现"一个底座、多种行为"。

▎面试加分点

  • 能说出"路由分类用小模型，核心文案生成用大模型"的具体调度策略
  • 提到"微调数据的质量比数量更重要"：几百条高质量的结构化数据比几万条噪声数据更有效
  • 能区分 SFT（监督微调）和 DPO（直接偏好优化）在"改变行为范式"中的不同作用

▎常见误区

  • 误以为"小模型就是能力差"，实际上在特定任务上，经过微调的小模型可以超越未微调的大模型
  • 误以为"微调可以让模型学会新知识"，实际上微调改变的是行为模式，知识更新应该走 RAG 路线
  • 误以为"QLoRA 的量化会导致精度大幅下降"，实际上 4-bit 量化 + LoRA 的组合在大多数任务上的精度损失可以忽略不计

🛠 应用题 · Q1 · 架构设计

题型

架构设计

场景标签

服务账号 API网关 M2M鉴权 最小权限

📝 题目

你正在为一家大型零售企业设计「凌晨自动盘点 Agent」。该 Agent 每天凌晨 2 点自动运行，调用后台 ERP 系统的库存接口，执行以下操作：① 读取前一日库存快照；② 对比销售流水，计算差异；③ 对差异超阈值的 SKU 自动生成盘点工单并写入 ERP。

该场景中没有真实人类在操作，且 Agent 需要同时具备「读库存」和「写盘点工单」两类权限。但安全团队提出：绝不能让 Agent 持有 ERP 系统的管理员账号密码，且必须保证「即使 Agent 被 Prompt 注入攻击，攻击者也无法获得真实凭证」。

请设计一套完整的 Agent 身份认证与权限管控方案，涵盖：身份凭证管理、请求签名机制、权限边界控制、以及人类审批的介入点。

💡 参考答案

▎解题思路

  1. 明确场景本质：这是一个典型的 Machine-to-Machine（M2M）后台自动化任务，没有人类用户参与交互式登录，因此不能使用 OAuth 授权码模式，而应该采用服务账号 + AppKey/AppSecret 签名方案。
  2. 凭证与模型隔离：大模型（LLM）只负责输出结构化指令（如 {"action": "create_stocktake_order", "sku": "SKU-123"}），绝不接触任何真实凭证。凭证由包裹 LLM 的工程代码（Tool/Plugin 层）从环境变量或 Vault 中安全读取。
  3. 权限分级与人工闸门：将「读库存」和「写盘点工单」拆分为两个独立的服务账号（或一个账号两种独立权限），其中「写操作」必须经过 Human-in-the-Loop 审批流。
  4. 网关统一拦截：所有 Agent 请求经过 API 网关，由网关完成验签、限流、权限校验，后端 ERP 系统完全不对外暴露。

▎详细方案

第一层：服务账号创建与凭证管理

在 ERP 后台管理系统中，由管理员创建两个专用服务账号：

账号名 权限范围 用途
agent_inventory_reader 库存只读（inventory:read） 凌晨拉取库存快照、销售流水
agent_stocktake_writer 盘点工单写入（stocktake:create） 生成盘点工单

每个账号由系统生成一对 AppKey（标识身份）和 AppSecret（签名密钥）。AppSecret 通过 HashiCorp Vault 或云厂商 KMS 加密存储，并以环境变量形式注入 Agent 运行时，绝不写入代码仓库或 Prompt。

第二层：请求签名机制（HMAC-SHA256）

Agent 每次调用 ERP 接口时，由工程代码执行以下签名流程：

签名串 = HTTP_METHOD + "\n" + PATH + "\n" + TIMESTAMP + "\n" + NONCE + "\n" + BODY_SHA256
Signature = Base64(HMAC-SHA256(AppSecret, 签名串))

请求头携带：X-AppKey、X-Timestamp（Unix 毫秒时间戳）、X-Nonce（随机数）、X-Signature。

网关收到请求后：
1. 校验 X-Timestamp 与服务器时间差不超过 300 秒（防重放攻击）；
2. 校验 X-Nonce 在 Redis 中不存在（防重放，写入后设置 300 秒 TTL）；
3. 根据 X-AppKey 从 Vault 中取出对应 AppSecret，用相同算法计算签名并比对。

第三层：API 网关统一拦截与权限校验

在 Kong/APISIX 网关上配置两条路由：

  • POST /api/v1/inventory/read → 仅允许 agent_inventory_reader 账号访问
  • POST /api/v1/stocktake/create → 仅允许 agent_stocktake_writer 账号访问，且必须携带人工审批通过的 approval_token

网关层同时配置：
- IP 白名单：只允许 Agent 服务器所在网段的请求进入；
- 限流：每账号每分钟最多 60 次请求，防止 Agent 逻辑失控刷爆 ERP。

第四层：Human-in-the-Loop 人工审批闸门

盘点工单的「写操作」不是全自动的。Agent 生成盘点工单草稿后，系统将工单内容推送给值班主管的企业微信/钉钉，主管点击「确认」后，后端才生成一个 一次性 approval_token（有效期 10 分钟），Agent 携带该 Token 才能通过网关的写操作校验。

▎关键细节 & 踩坑点

  • ⚠️ 绝对不要把 AppSecret 放进 Prompt：曾有团队为了让 LLM 自主调用 API，把凭证直接写在 System Prompt 里，结果被用户通过 Prompt Injection 直接套出。正确做法是：LLM 只输出结构化 JSON，由 Tool 层代码负责签名和发请求。
  • ⚠️ 签名中的 Nonce 必须全局唯一：如果只用时间戳防重放，攻击者在同一秒内重放请求即可绕过。必须引入随机 Nonce 并在 Redis 中记录。
  • ⚠️ 最小权限原则落地：读账号和写账号必须分离。如果 Agent 只需要查库存，就只给它 inventory:read，绝不给 inventory:write 或超管权限。一旦 Agent 被攻破，攻击者也只能读数据，不能篡改。
  • ⚠️ 审批 Token 的一次性：approval_token 必须用完即焚，防止 Agent 缓存后重复使用。

▎可扩展优化

  • 引入短期证书（如 SPIFFE/SPIRE）：在大规模集群中，可以用短期 X.509 证书替代静态 AppSecret，证书每 1 小时自动轮换，泄露后的攻击窗口极小。
  • 审计日志全链路追踪：每次 Agent 调用 ERP 时，网关记录完整的 AppKey、时间戳、请求体摘要、审批 Token ID，便于事后审计和异常定位。
  • 异常行为检测：如果 agent_inventory_reader 账号突然开始尝试调用写接口，网关应触发告警并自动封禁该账号 10 分钟。

场景标签

多Agent通信 消息队列 异步解耦 供应商协同

📝 题目

你所在的公司运营一个电商平台，需要构建一套「自动补货多 Agent 系统」，涉及三个独立 Agent：

  • 库存 Agent：实时监控库存水位，发现某 SKU 低于安全线时触发补货流程；
  • 采购 Agent：根据历史销量、季节性因素计算补货数量，并向外部供应商下单；
  • 财务 Agent：收到供应商的接单回执后，自动完成预付款扣除。

这三个 Agent 分别部署在不同的服务器上，由不同团队维护。库存 Agent 的高峰触发频率极高（大促期间每秒可能产生数百条补货请求），而财务 Agent 处理能力有限（受制于银行接口每秒只能处理 10 笔扣款）。

请分析：这三个 Agent 之间应该采用同步 HTTP 调用还是消息队列异步通信？请给出具体的通信架构设计，并重点说明如何防止财务 Agent 被高并发压垮。

💡 参考答案

▎解题思路

  1. 识别系统瓶颈：库存 Agent 的触发频率（每秒数百条）与财务 Agent 的处理能力（每秒 10 笔）之间存在 两个数量级的差距。如果采用同步 HTTP 调用，库存 Agent 会直接阻塞等待财务响应，导致请求堆积、超时、雪崩。
  2. 选择异步解耦模式：引入消息队列（如 RabbitMQ / Kafka / RocketMQ）作为 Agent 之间的「缓冲层」，将同步调用改为异步消息传递。上游 Agent 发完消息即可返回，下游 Agent 按自己的节奏消费。
  3. 设计消息协议：定义结构化的 JSON 消息格式，包含任务 ID、SKU、数量、时间戳、来源 Agent 标识等字段，确保消息可追踪、可重试。
  4. 为财务 Agent 增加流量整形：通过队列的消费者并发数控制和死信队列机制，保证财务 Agent 不会被瞬时流量冲垮。

▎详细方案

第一层：消息队列选型与拓扑设计

库存 Agent ──→ [Topic: replenish.request] ──→ 采购 Agent
                                                    │
                                     [Topic: order.confirmed]
                                                    ↓
                                              财务 Agent
  • 使用 Kafka 作为主消息总线：replenish.request 主题接收库存 Agent 的补货请求，分区数设为 32 以支撑高吞吐；order.confirmed 主题接收供应商回执。
  • 采购 Agent 作为消费者组 purchase-group 订阅 replenish.request，处理完成后将结果写入 order.confirmed。
  • 财务 Agent 作为消费者组 finance-group 订阅 order.confirmed，消费者实例数限制为 2 个（每个实例并发处理 5 笔/秒，合计 10 笔/秒，与银行接口能力匹配）。

第二层：消息结构设计

  "type": "replenish_request",
  "source_agent": "inventory-agent",
  "timestamp": "2026-01-15T02:00:00Z",

    "sku": "IPHONE-15-PRO-256",
    "current_stock": 5,

第三层：财务 Agent 的流量整形与保护

财务 Agent 消费端配置：

  • 并发消费者数：2 个消费者实例，每个实例内部串行处理；
  • 批量拉取：每次从队列拉取最多 5 条消息，批量调用银行接口（如果银行支持批量扣款），减少网络开销；
  • 失败重试与死信队列：扣款失败的消息重试 3 次（指数退避：1s、5s、30s），仍失败则进入死信队列 finance.dlq，由人工介入处理；
  • 熔断保护：如果银行接口连续 5 次返回 5xx 或超时，财务 Agent 自动停止消费 30 秒，避免无效重试堆积。

第四层：消息可靠性保障

  • At-Least-Once 语义：消费者处理完消息后手动提交 Offset，确保消息不丢失；
  • 幂等设计：财务 Agent 在扣款前，先根据 message_id 查询 Redis，若已处理过则直接跳过，防止重复扣款。

▎关键细节 & 踩坑点

  • ⚠️ 不要用同步 HTTP 串联 Agent 链：如果库存 Agent 同步调用采购 Agent，采购 Agent 再同步调用财务 Agent，任何一个环节慢下来，整条链路都会阻塞，最终导致库存 Agent 线程池耗尽。
  • ⚠️ 消息队列不是银弹：引入 MQ 后，系统变成了最终一致性模型。库存 Agent 发出补货请求后，不能立即知道采购结果。需要在业务层设计「状态回查」或「回调通知」机制。
  • ⚠️ 财务 Agent 的消费速率必须可配置：银行接口的吞吐能力可能随业务调整，消费者并发数应通过配置中心动态调整，而不是硬编码。
  • ⚠️ 死信队列必须有人监控：进入 DLQ 的消息意味着「钱没扣成」或「单没下成」，必须配置告警，否则会导致库存补货中断而无人知晓。

▎可扩展优化

  • 引入事件溯源（Event Sourcing）：将每个 Agent 的状态变更作为事件写入 Kafka，任何 Agent 都可以通过重放事件来重建状态，便于故障恢复和审计。
  • 升级为 Agent-to-Agent（A2A）协议：当 Agent 数量增多、跨团队协作频繁时，可以在消息队列之上引入标准化的 A2A 协议层，统一消息格式和会话管理。
  • 动态弹性伸缩：在大促期间，通过监控队列积压深度（Lag），自动扩容采购 Agent 的消费者实例数；财务 Agent 由于受外部银行接口限制，不扩容实例数，而是通过优化批量扣款逻辑提升吞吐。

场景标签

优雅终止 SIGTERM Lifespan Checkpointer持久化

📝 题目

你负责的「自媒体内容生成 Agent」系统部署在自研 Serverless 平台上，每个请求会触发一个 LangGraph 工作流，包含「选题 → 写作 → 配图」三个节点。其中配图节点调用扩散模型生成图片，单张图片生成耗时约 8~15 秒。

现在运维团队要求：每次发布新版本时，不能有任何一个正在进行的生成任务被中断丢失。但平台在发布时会直接向容器发送 SIGTERM 信号，并在 30 秒后强制 Kill 容器。

请设计一套完整的优雅终止方案，包括：如何监听 SIGTERM 信号、如何阻断新请求、如何等待在途任务完成、以及如何在超时强制 Kill 前做最后的持久化兜底。请给出关键代码逻辑（伪代码即可）。

💡 参考答案

▎解题思路

  1. 理解 SIGTERM 与强制 Kill 的时间窗口：平台发送 SIGTERM 后，容器有 30 秒的「黄金窗口」来完成收尾工作。超过 30 秒，平台会发送 SIGKILL，进程无法做任何清理。
  2. 利用 FastAPI 的 Lifespan 异步上下文管理器：在 lifespan 中监听 asyncio 事件循环的终止信号，实现「先阻断新请求 → 等待在途任务完成 → 持久化状态 → 退出」的流程。
  3. 设计任务计数器与状态持久化：维护一个全局的 active_tasks 计数器，每个任务开始时加 1、结束时减 1。当收到 SIGTERM 时，循环检查计数器，直到归零或超时。
  4. 超时兜底策略：由于配图任务最长可能 15 秒，30 秒窗口理论上足够。但为了防止极端情况（如扩散模型卡死），必须设置一个硬超时（如 25 秒），超时后强制将未完成的任务状态写入 Checkpointer，然后退出。

▎详细方案

第一层：FastAPI Lifespan 优雅终止实现

import asyncio
import signal
from contextlib import asynccontextmanager
from fastapi import FastAPI

# 全局在途任务计数器
active_tasks = 0
# 全局标志：是否正在优雅终止
is_shutting_down = False
# 硬超时时间（秒），必须小于平台强制 Kill 的 30 秒
GRACEFUL_TIMEOUT = 25

@asynccontextmanager
async def lifespan(app: FastAPI):
    # 启动逻辑：初始化 MCP 连接、加载模型等
    await init_mcp_connections()

    # 注册 SIGTERM 信号处理器
    loop = asyncio.get_running_loop()
    stop_event = asyncio.Event()

    def handle_sigterm():
        print("收到 SIGTERM 信号，开始优雅终止...")
        stop_event.set()

    loop.add_signal_handler(signal.SIGTERM, handle_sigterm)

    yield  # 应用运行中

    # 收到 SIGTERM 后的优雅终止逻辑
    global is_shutting_down
    is_shutting_down = True
    print("阻断新请求，等待在途任务完成...")

    # 等待在途任务完成，但不超过硬超时
    try:
        await asyncio.wait_for(
            _wait_for_tasks_drain(stop_event),
            timeout=GRACEFUL_TIMEOUT
        )
    except asyncio.TimeoutError:
        print(f"超过 {GRACEFUL_TIMEOUT} 秒硬超时，强制持久化未完成任务...")
        await _force_persist_all_tasks()

    # 关闭 MCP 连接、释放资源
    await close_mcp_connections()
    print("优雅终止完成，进程安全退出。")

async def _wait_for_tasks_drain(stop_event: asyncio.Event):
    """等待所有在途任务完成"""
    while active_tasks > 0:
        print(f"当前还有 {active_tasks} 个任务在进行，等待 1 秒...")
        await asyncio.sleep(1)

app = FastAPI(lifespan=lifespan)

第三层：Checkpointer 持久化兜底

LangGraph 的 Checkpointer 会在每个节点执行完成后自动保存状态。但如果在配图节点执行到一半时被强制 Kill，该节点的中间状态可能丢失。因此需要：

async def _force_persist_all_tasks():
    """强制持久化所有未完成的任务状态"""
    # 获取所有正在执行的任务的 config
    for task_config in running_task_configs:
        try:
            # 强制将当前状态写入 Checkpointer
            await media_agent.graph.aget_state(task_config)
            # 标记该任务为「中断未完成」，启动时可恢复
            await redis_client.set(
                f"interrupted_task:{task_config['configurable']['thread_id']}",
                "pending_resume",
                ex=3600  # 1 小时过期
            )
        except Exception as e:
            print(f"持久化任务 {task_config} 失败: {e}")

第四层：启动时的中断恢复

async def init_mcp_connections():
    """启动时检查是否有上次被中断的任务需要恢复"""
    interrupted_keys = await redis_client.keys("interrupted_task:*")
    for key in interrupted_keys:
        thread_id = key.decode().split(":")[-1]
        # 从 Checkpointer 恢复状态并继续执行
        config = {"configurable": {"thread_id": thread_id}}
        await media_agent.graph.aresume(config)
        await redis_client.delete(key)

▎关键细节 & 踩坑点

  • ⚠️ 硬超时必须小于平台 Kill 时间：如果平台 30 秒后强制 Kill，你的优雅终止逻辑必须在 25 秒内完成。否则进程被 SIGKILL 杀死，所有未持久化的状态都会丢失。
  • ⚠️ 信号处理器必须在主事件循环中注册：loop.add_signal_handler 只能在主线程的事件循环中调用，不能在子线程或 Worker 进程中注册。
  • ⚠️ 计数器必须用 finally 保证递减：如果任务执行中抛出异常，finally 块确保 active_tasks 正确递减，否则优雅终止逻辑会永远等待。
  • ⚠️ 配图任务的中间状态：扩散模型生成图片的过程中，如果被 SIGKILL 杀死，GPU 上的中间张量无法持久化。因此最好的策略是：在配图节点开始前，先将「写作节点」的输出完整持久化，这样即使配图失败，恢复时也只需重新生成图片，而不需要从头开始。
  • ⚠️ 多进程部署时的信号处理：如果使用 Uvicorn 多 Worker 模式，每个 Worker 进程都需要独立处理 SIGTERM。建议使用单进程 + 多协程模式，或者使用 Gunicorn 的 --graceful-timeout 参数统一管理。

▎可扩展优化

  • 引入 Kubernetes PreStop Hook：在 K8s 环境中，可以在 Pod 的 preStop 钩子中先调用一个 /drain 端点，将 Pod 从 Service 的 Endpoints 中摘除，然后再发送 SIGTERM，实现更平滑的流量切换。
  • 任务级 Checkpoint：对于超过 30 秒的长任务（如视频生成），可以在任务内部设置多个检查点，每隔 N 秒主动持久化一次中间状态，这样即使被强制 Kill，恢复时也从最近检查点继续，而不是从头开始。
  • 优雅终止的监控告警：记录每次优雅终止的耗时、强制持久化的任务数，如果频繁出现「硬超时强制持久化」的情况，说明任务执行时间过长，需要优化或拆分任务。

🛠 应用题 · Q4 · 排障优化

题型

排障优化

场景标签

KV Cache 会话粘滞 一致性哈希 无状态集群

📝 题目

你负责的「FA-HR 多模态智能客服」系统上线后，运维团队在高峰期进行了服务器弹性扩容（从 3 台扩展到 10 台）。扩容后用户投诉骤增，主要问题有两个：

  1. 用户对话记忆丢失：用户和客服 Agent 聊到第 5 轮时，突然被分流到一台新服务器，之前的对话历史全部丢失，Agent 开始「失忆」，用户需要从头解释自己的问题。
  2. 首字延迟（TTFT）从 2 秒飙升至 15 秒：排查发现，扩容前用户请求通过 Nginx 默认轮询分发，但扩容后同一个用户的连续请求被分发到不同服务器，导致大模型的 Prefix Caching（前缀缓存）完全失效，每次请求都需要重新计算全部上下文的 KV Cache。

请分析这两个问题的根本原因，并给出完整的架构修复方案，包括：状态下沉策略、网关路由改造、以及如何验证修复效果。

💡 参考答案

▎解题思路

  1. 识别核心矛盾：扩容前，用户请求可能碰巧被同一台服务器处理（因为只有 3 台，概率较高），对话历史存在该服务器内存中，KV Cache 也在该服务器 GPU 上。扩容到 10 台后，同一用户的连续请求被 Nginx 轮询分发到不同服务器的概率大幅上升，导致「记忆丢失」和「缓存失效」同时爆发。
  2. 状态下沉：将对话历史从服务器本地内存迁移到外部共享存储（Redis Cluster），使任何服务器都能读取用户的完整对话上下文。
  3. 网关会话粘滞：在 Nginx/Ingress 层配置基于 session_id 的一致性哈希路由，确保同一用户的请求始终打到同一台服务器，从而命中该服务器 GPU 上的 KV Cache。
  4. 验证方案：通过压测工具模拟多用户并发请求，对比修复前后的 TTFT 分布和缓存命中率。

▎详细方案

第一层：状态下沉——Redis 共享记忆

将对话历史从服务器本地内存迁移到 Redis Cluster：

import redis
import json
from langgraph.checkpoint.base import BaseCheckpointSaver

class DistributedRedisCheckpointer(BaseCheckpointSaver):
    def __init__(self, redis_url: str):
        super().__init__()
        self.client = redis.from_url(redis_url)

    def put(self, config: dict, checkpoint: dict, metadata: dict) -> dict:
        thread_id = config["configurable"]["thread_id"]
        # 将状态序列化写入 Redis，所有服务器共享
        self.client.set(
            f"agent_state:{thread_id}",
            json.dumps(checkpoint),
            ex=86400  # 24 小时过期
        )
        return config

    def get_tuple(self, config: dict):
        thread_id = config["configurable"]["thread_id"]
        data = self.client.get(f"agent_state:{thread_id}")
        if data:
            return json.loads(data)
        return None

# 初始化 LangGraph 时使用分布式 Checkpointer
memory = DistributedRedisCheckpointer(redis_url="redis://redis-cluster:6379")
graph = workflow.compile(checkpointer=memory)

第二层：网关会话粘滞——Nginx 一致性哈希

修改 Nginx 配置，使用 hash 指令基于 session_id 做一致性哈希：

upstream agent_servers {
    # 关键：根据请求参数中的 session_id 进行哈希
    # 确保同一用户的请求始终打到同一台服务器
    hash $arg_session_id consistent;

    server 192.168.1.10:8000;  # 服务器 A
    server 192.168.1.11:8000;  # 服务器 B
    server 192.168.1.12:8000;  # 服务器 C
    # ... 共 10 台
}

server {
    listen 80;
    location /v1/chat/audio {
        proxy_pass http://agent_servers;
        # 设置合理的超时时间
        proxy_read_timeout 60s;
        proxy_send_timeout 60s;
    }
}

第四层：验证方案

  1. 压测模拟：使用 Locust 或 JMeter 模拟 1000 个并发用户，每个用户发送 10 轮连续对话请求。
  2. TTFT 对比：修复前，同一用户的 10 轮请求可能被分发到 10 台不同服务器，每轮 TTFT 都在 10~15 秒；修复后，同一用户始终打到同一台服务器，第 1 轮 TTFT 约 2 秒，第 2~10 轮 TTFT 应降至 1 秒以内（命中 Prefix Cache）。
  3. 缓存命中率监控：在 Agent 代码中记录每次请求的 cache_hit 字段（通过大模型 API 返回的 usage.prompt_tokens_details.cached_tokens 判断），修复后缓存命中率应显著提升。

▎关键细节 & 踩坑点

  • ⚠️ 一致性哈希的「雪崩」问题：当一台服务器宕机时，一致性哈希会将原本路由到该服务器的用户重新分配到其他服务器，导致这些用户的 KV Cache 全部失效。解决方案：使用 Ketama 一致性哈希算法（Nginx 的 consistent 参数已实现），尽量减少重新分配的用户数量。
  • ⚠️ 会话粘滞的「热点」问题：如果某个用户的对话特别长（如 HR 面试场景，聊了 50 轮），该用户会一直占用同一台服务器的 GPU 显存。需要设置 KV Cache 的 TTL 或 LRU 淘汰策略，避免显存被少数长会话占满。
  • ⚠️ Redis 的 I/O 瓶颈：将状态下沉到 Redis 后，每次请求都需要读写 Redis。如果 Redis 是单节点，高并发下会成为新瓶颈。必须使用 Redis Cluster 或至少 主从 + Sentinel 架构。
  • ⚠️ 服务器发布时的会话粘滞失效：当需要发布新版本时，旧服务器会陆续下线，原本粘滞在这些服务器上的用户会被重新分配到新服务器，导致 KV Cache 失效。解决方案：优雅终止 + 分层发布，让旧服务器在处理完在途请求后再下线，并提前将用户会话状态持久化到 Redis。

▎可扩展优化

  • 引入 Prefix Caching 的跨服务器共享：某些推理框架（如 vLLM）支持将 KV Cache 存储到分布式共享内存（如 NVLink 互联的 GPU 集群），这样即使请求被分发到不同服务器，也能命中缓存。
  • 动态路由策略：在网关层引入更智能的路由逻辑，不仅基于 session_id，还考虑每台服务器的当前负载和 GPU 显存占用，实现「粘滞 + 负载均衡」的平衡。
  • 预热机制：在发布新版本时，提前将高频用户的会话状态和 Prefix Cache 预热到新服务器上，减少切换时的延迟抖动。
