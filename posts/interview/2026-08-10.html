📌 概念题 · Q1

考点标签

LoRA文件结构 · 难度：⭐⭐

📝 题目

在一个典型的 LoRA 微调产物目录中，除了训练脚本和日志外，最核心的是 adapter_config.json 和 adapter_model.safetensors 两个文件。请分别解释这两个文件在 LoRA 推理过程中扮演的角色，并说明为什么 adapter_model.safetensors 不能用普通的文本编辑器打开查看？

💡 参考答案

▎一句话结论

adapter_config.json 是 LoRA 的“说明书”，定义了补丁如何挂载到基座模型；adapter_model.safetensors 是“肉身”，存储了低秩矩阵的实际权重，因其采用高效的二进制序列化格式，故无法用文本编辑器直接查看。

▎核心原理

  • 配置与权重分离：adapter_config.json 以纯文本 JSON 存储超参数（如秩 r、缩放系数 alpha、目标模块 target_modules），而 adapter_model.safetensors 以二进制格式存储密集的浮点数张量。
  • 安全与高效：safetensors 格式专为深度学习设计，避免了 Python pickle 的反序列化安全风险，并支持零拷贝内存映射，加载速度极快。
  • 推理引擎的依赖性：vLLM 或 Hugging Face PEFT 等推理框架必须先读取 adapter_config.json 明确 LoRA 的结构，才能正确地将 adapter_model.safetensors 中的低秩矩阵注入到基座模型的指定层。

▎深入解释

可以把基座模型想象成一个巨大的乐高城市，LoRA 微调就是要在这个城市的特定位置加装一些小型装饰（补丁）。adapter_config.json 就是施工图纸，它精确标明了要在哪些建筑（target_modules，如 q_proj, v_proj）的哪个位置加装，以及装饰的尺寸（秩 r）和风格强度（lora_alpha）。adapter_model.safetensors 则是装着这些装饰零件的箱子，里面是实实在在的零件（多维矩阵）。箱子是用高效的工业封装方式打包的，你不能用肉眼（文本编辑器）看透箱子里的零件细节，必须用专门的扫描仪（safetensors 库）来读取。这种设计让模型分发和加载变得极其安全高效，因为推理引擎拿到图纸和零件箱后，就能快速、无误地完成组装。safetensors 内部是一个字典，键是像 layers.0.self_attn.q_proj.lora_A.weight 这样的路径，值是一个 PyTorch 张量，直接映射到乐高城市的具体坐标。

▎面试加分点

  • 提及 safetensors 相比 .bin (pickle) 的安全优势：能防止因加载恶意文件导致的任意代码执行，是 Hugging Face 等社区的主流标准。
  • 理解 target_modules 的作用：明确指出 LoRA 通常只作用于 Transformer 的注意力层（Q, K, V, O），这是经验驱动的高效选择。
  • 关联推理框架：能说出 vLLM 的 LoRA 热插拔就是通过动态读取和替换这些文件对应的显存矩阵实现的。

▎常见误区

  • 误区：认为 adapter_config.json 可有可无，只要有权重文件就能跑。
  • 纠正：没有配置文件，推理引擎完全不知道这是一个 LoRA 补丁，也不知道它的秩、目标模块等关键信息，根本无法正确加载。

📌 概念题 · Q2

考点标签

SaaS多租户架构 · 难度：⭐⭐⭐

📝 题目

在 SaaS 平台为多个企业客户提供个性化大模型服务的场景中，为什么“1个共享大底座 + N个租户小补丁（LoRA）”的架构，在成本和工程维护上远优于“为每个客户独立部署一套完整的大模型”？请从显存占用、服务部署和模型迭代三个维度进行分析。

💡 参考答案

▎一句话结论

“共享底座 + 租户补丁”架构通过复用基座模型的算力和显存，将多租户服务的边际成本从“模型级别”降低到“文件级别”，实现了极致的资源利用率和运维效率。

▎核心原理

  • 显存占用的乘法与加法：独立部署是“乘法”逻辑（基座模型大小 × 租户数量），而共享底座是“加法”逻辑（基座模型大小 + LoRA 大小 × 租户数量）。例如，一个 14B 模型（~30GB）服务 100 个客户，独立部署需要 3TB 显存，而共享底座仅需约 35GB 显存（30GB + 100 × 50MB）。
  • 服务部署的原子化：共享底座架构只需维护一个推理服务集群。新租户上线或旧租户模型更新，只需在对象存储上新增或替换一个几十MB的 LoRA 文件，并通过推理引擎动态加载，无需启动新容器或重启服务，实现零停机。
  • 模型迭代的一键同步：当基座模型从 Qwen2.5 升级到 Qwen3.0 时，独立部署需要为所有客户重训、重部署。共享底座只需升级一个基座模型实例，所有租户的 LoRA 补丁在多数情况下可直接适配或仅需少量重训，极大降低了维护成本。

▎深入解释

这个架构的本质是计算与存储的分离。基座模型是“计算引擎”，常驻昂贵的 GPU 显存，提供通用智能。LoRA 补丁是“业务配置”，存储在廉价的磁盘或对象存储中，提供个性化风格。当请求到达时，推理引擎（如 vLLM）就像一个精密的转接头，在计算过程中临时将对应租户的 LoRA 矩阵“插入”到基座模型的计算流中。计算完成，插入即移除，不留下任何痕迹。这就像所有租户共享一个超级大脑，但每个人都可以在大脑皮层上临时贴上一个专属的思维导图（LoRA），用完即撕下，大脑本身不受任何永久性改变。这种架构让 SaaS 平台的 AI 服务边际成本趋近于零，是商业上可行的唯一路径。

▎面试加分点

  • 明确显存计算：能给出具体的数字对比，如“14B模型+100租户，共享方案节省约98%显存”。
  • 提及 S-LoRA 或 Punica 等专门优化多 LoRA 并发推理的框架，它们能进一步管理 LoRA 的显存缓存和批量调度。
  • 结合 RAG 定位：指出 RAG 负责解决动态知识库问题，LoRA 负责解决静态风格/流程问题，两者是黄金组合。

▎常见误区

  • 误区：认为 LoRA 补丁之间完全隔离，不会相互影响。
  • 纠正：虽然逻辑上隔离，但在显存中并发执行时，如果推理框架的调度或显存管理不当，仍可能出现资源争抢或 OOM 问题，需要成熟的框架支持。

📌 概念题 · Q3

考点标签

Agent架构设计 · 难度：⭐⭐⭐

📝 题目

在构建复杂的 AI Agent 系统时，架构师常将系统拆分为 Harness（控制面）和 Runtime（执行面）。请解释这两个概念的本质区别，并说明为什么这种分离对构建“高安全、可观测”的工业级 Agent 系统至关重要？

💡 参考答案

▎一句话结论

Harness 是 Agent 的“逻辑大脑”，负责思考、规划和决策；Runtime 是 Agent 的“物理身体与环境”，负责安全、高效地执行具体动作。二者的分离是实现安全隔离、错误追踪和技术栈解耦的基石。

▎核心原理

  • 职责分离：Harness（缰绳）处理纯逻辑：LLM 调用、Prompt 拼接、状态机流转、输出解析。Runtime（沙盒）处理物理执行：代码执行、API 调用、数据库读写。前者不关心代码怎么跑，后者不关心业务逻辑。
  • 安全边界：Harness 生成的代码或指令是不可信的。Runtime 提供 Docker/WASM 等隔离沙箱，确保即使 LLM 生成了恶意或错误的代码，也无法突破环境限制，损害宿主机或访问未授权资源。
  • 可观测性：Harness 产生的错误是逻辑错误（如死循环、意图理解错误），Runtime 产生的错误是执行错误（如超时、权限不足、资源耗尽）。分离后，可以在各自的边界内精确捕获、记录和告警，实现细粒度的调试。

▎深入解释

想象一个自动驾驶系统。Harness 是驾驶决策软件，它观察地图和传感器，决定“下一个路口右转，驶入辅路”。Runtime 是汽车的转向系统、刹车和油门。决策软件只发出“右转30度”的指令，它不需要知道转向助力泵如何工作。如果决策软件崩溃，车会失去方向（Harness 错误）；如果转向系统卡死，车无法转弯（Runtime 错误）。在 Agent 系统中，当 LLM 决定调用一个 Python 函数来查询数据库时，Harness 负责生成函数名和参数，Runtime 负责在一个独立的容器里启动这个 Python 进程，注入参数，并等待结果。如果函数执行超时，Runtime 会直接终止它并返回一个超时错误给 Harness，Harness 再决定是重试还是告诉用户“操作超时”。这种分层设计让系统既强大又可控。

▎面试加分点

  • 提及具体的 Runtime 技术：如 Docker 容器、WASM 沙箱、Firecracker microVM。
  • 关联可观测性三大支柱：日志（Logs）、指标（Metrics）、追踪（Traces），并指出它们在 Harness 和 Runtime 层是如何分别采集的。
  • 强调 LangGraph 的角色：LangGraph 本质上是一个强大的 Harness 框架，它需要配合合适的 Runtime 才能用于生产。

▎常见误区

  • 误区：认为 Harness 和 Runtime 只是代码上的模块划分，意义不大。
  • 纠正：它们是架构层面的物理或进程级隔离，是实现“安全第一”原则的根本保障，而不仅仅是代码组织方式。

📌 概念题 · Q4

考点标签

模型量化 · 难度：⭐⭐⭐

📝 题目

在大模型部署中，我们常说“量化是用精度换效率”。请从计算机体系结构的角度，深入解释为什么将模型权重从 FP16 量化到 INT4 后，推理速度会显著提升？除了模型体积变小，还有哪些更深层次的性能收益？

💡 参考答案

▎一句话结论

量化带来的推理加速，不仅源于模型体积缩小减少了内存带宽压力（Memory Bound 缓解），更在于整数计算单元（INT8/INT4 Tensor Core）相比浮点计算单元（FP16/FP32 CUDA Core）拥有更高的计算吞吐量和更低的能耗。

▎核心原理

  • 打破内存带宽瓶颈：LLM 推理通常是 Memory Bound，即计算单元大部分时间在等待数据从显存搬运过来。FP16 到 INT4，数据量减至 1/4，意味着在相同时间内，内存带宽可以搬运 4 倍的参数，计算单元不再“挨饿”，利用率飙升。
  • 利用专用计算单元：现代 GPU（如 Nvidia 的 Hopper、Blackwell 架构）集成了专用的 Tensor Core，它们在执行 INT8 或 INT4 矩阵乘法时，吞吐量（FLOPS）是 FP16 计算的好几倍。量化后，计算任务可以从较慢的通用 CUDA Core 转移到更快的专用 Tensor Core 上。
  • 提升计算密度与能效：整数运算单元在芯片上占用的面积和功耗远小于浮点单元。这意味着在同样的芯片面积和功耗预算下，可以塞入更多的整数计算单元，从而实现更高的并行度和更好的能效比（TOPS/W）。

▎深入解释

可以把推理过程想象成一个工厂流水线。模型权重是原料，计算单元是加工机器。FP16 模型就像用大卡车（高带宽需求）运来一大堆原料，但加工机器（FP16 CUDA Core）处理速度一般，原料经常在仓库（显存）门口排长队（Memory Bound）。量化成 INT4 后，不仅把大卡车换成了小货车（体积缩小），更重要的是，工厂把原来的通用加工机器换成了专门处理小零件的超高速机器（Tensor Core），这些小机器处理速度极快，而且非常省电。虽然原料在运输过程中有些许损耗（精度损失），但整个工厂的产出效率（吞吐量）和运营成本（功耗）都得到了巨大优化。Blackwell 架构引入的原生 FP4 支持更是将这个逻辑推向了极致。

▎面试加分点

  • 区分 Memory Bound 和 Compute Bound：明确指出 LLM 推理的瓶颈是前者，量化首要解决的是这个问题。
  • 提到硬件级别优化：说出 Tensor Core、CUDA Core，以及 Blackwell 的 FP4 支持。
  • 关联具体量化算法：说明 AWQ 和 GPTQ 等算法正是为了在利用这些硬件优势的同时，最大程度地减少精度损失。

▎常见误区

  • 误区：认为模型越小就跑得越快，所以性能提升完全是因为体积变小。
  • 纠正：速度提升是“内存带宽缓解 + 计算单元升级”双重作用的结果。即使模型体积不变，若能将其计算映射到更快的计算单元上，速度也会提升。

📌 概念题 · Q5

考点标签

Agent 多轮对话 · 难度：⭐⭐⭐

📝 题目

在智能销售 Agent 的设计中，为了防止 Agent 过早报价或进行无效推荐，我们引入了基于“信息完备度检查点”的 Slot Filling（槽位填充）机制。请详细阐述这个机制是如何与 LLM 的主动引导能力结合，实现从“被动问答”到“主动深挖”的转变？

💡 参考答案

▎一句话结论

Slot Filling 机制通过定义一个必须填满的“信息槽位”集合，将 LLM 的生成过程约束在一个目标驱动的状态机内，迫使 Agent 在收集到所有关键信息前，持续主动提问，从而深度挖掘客户真实意图。

▎核心原理

  • 定义关键槽位：业务专家预先定义一组核心信息槽位（如预算、痛点、团队规模、上线时间），这些是判断销售线索质量和制定方案的必备要素。
  • 状态感知与决策：每轮对话后，系统会调用一个“槽位解析器”（可以是一个轻量级分类模型或一个专门设计的 LLM Prompt），从对话历史中提取并填充已获取的槽位信息。
  • 生成策略路由：根据槽位填充状态，LLM 被路由到不同的 Prompt 策略。如果关键槽位未满，LLM 加载“追问模式”的 System Prompt，其核心指令是“通过自然、关怀的对话，引导用户提供缺失的槽位信息”。只有当所有必要槽位被填满后，LLM 才被允许切换到“方案/报价生成模式”。

▎深入解释

这相当于给 Agent 安装了一个“任务进度条”。传统的聊天机器人是“乒乓模式”：用户问，它答。Slot Filling 模式是“寻宝模式”：Agent 手里拿着一张藏宝图（槽位列表），图上有几个关键点必须被点亮。Agent 的每一轮对话都不是为了结束对话，而是为了点亮下一个点。例如，客户说“我想了解一下你们的产品”，Agent 识别到“痛点”、“预算”等槽位为空，于是它会生成一个像“为了给您更精准的建议，可以聊聊您目前在XX方面遇到的最大挑战是什么吗？”这样的回复。这个回复不是对问题的直接回答，而是一个由“痛点”槽位缺失状态触发的主动引导。LLM 的角色从“问答生成器”变成了“目标驱动的对话策略执行器”。这保证了销售流程的专业性和一致性，避免了 AI 的随意发挥。

▎面试加分点

  • 将 Slot Filling 与状态机（State Machine）或 LangGraph 的状态图联系起来，说明其工程实现方式。
  • 强调“槽位解析器”的准确性是关键，可以讨论用正则、BERT 分类模型或 LLM Function Calling 来实现的优缺点。
  • 提出“软填充”与“硬填充”：有些槽位可以从上下文推断（软），有些必须用户明确确认（硬），增加了设计的灵活性。

▎常见误区

  • 误区：认为 Slot Filling 就是简单的关键词匹配，比如用户说了“5万”，就填充“预算”槽位。
  • 纠正：真正的 Slot Filling 需要语义理解，例如用户说“我们小公司，预算有限”，也需要能提取出“预算”槽位值为“低”或“有限”，并触发后续追问具体数字的动作。

📌 概念题 · Q6

考点标签

Agent 数据安全 · 难度：⭐⭐⭐

📝 题目

在智能销售客服场景中，需要向客户展示过往成功案例以建立信任，但又必须保护案例中甲方公司的真实隐私信息。请设计一套基于“数据脱敏网关”的自动化案例展示流程，并解释它如何与 LLM 的 Tool-use 能力结合，实现动态脱敏和自然语言润色？

💡 参考答案

▎一句话结论

该流程通过在数据库查询和 LLM 生成之间插入一个“数据脱敏网关”，利用 Tool-use 机制，让 LLM 先获取结构化脱敏数据，再进行自然语言润色，从而实现既安全又生动的案例展示。

▎核心原理

  • 基于意图的工具调用：当 LLM 识别到客户需要看案例的意图时，它发起一个 Function Call，参数是客户的关键特征标签（如行业、规模）。
  • 脱敏网关的中间件作用：这个 Function Call 的后端不是一个普通的数据库 API，而是一个“数据脱敏网关”。网关执行原始 SQL 查询后，在返回数据前，会应用一系列规则（如正则替换、命名实体识别 NER 模型）将敏感信息（如“XX科技公司”、“王总”、“2000万”）替换为泛化标签（如“某头部电商平台”、“张总”、“数千万”）。
  • 结构化数据注入与润色：LLM 的 Function Call 返回的是一个安全的、结构化的 JSON 对象。LLM 最后根据这个 JSON 和当前对话上下文，生成流畅、有说服力的文案：“巧了，我们上个月刚帮一家和您同行业的头部电商平台解决了类似问题，他们的负责人反馈说……”

▎深入解释

这个流程的精妙之处在于“关注点分离”。数据库管理员只关心数据怎么存，脱敏网关只关心哪些是敏感信息以及如何脱敏，而 LLM 只关心如何讲故事。三者通过 API 契约和 Tool-use 机制完美解耦。脱敏网关像是一个“隐私过滤器”，它确保任何从数据库流向 LLM 的数据都是经过清洗的。LLM 永远接触不到原始的真实数据，从根本上杜绝了隐私泄露的风险。同时，因为 LLM 拿到的是结构化的关键信息（如“行业：电商”、“效果：提升30%”），而不是被脱敏弄得支离破碎的病句，所以它依然能发挥其强大的语言生成能力，将冰冷的标签组合成有温度、有说服力的销售话术。这个架构比“先让 LLM 生成案例再人工审核”要高效和安全得多。

▎面试加分点

  • 提出使用 NER 模型进行智能脱敏，比正则规则更灵活，能识别未预定义的实体。
  • 强调脱敏策略的可配置性：不同租户或不同安全级别可以配置不同的脱敏规则。
  • 关联数据中台：指出这套脱敏后的案例数据可以反哺到 RAG 知识库或用于未来的模型微调，形成数据飞轮。

▎常见误区

  • 误区：认为可以在 Prompt 里直接告诉 LLM “不要泄露隐私信息”，让它自己看着办。
  • 纠正：把安全寄托在 LLM 的“自觉性”上是极其危险的，必须通过工程手段在数据离开数据库的那一刻就进行物理拦截和替换。

📌 概念题 · Q7

考点标签

Agent 通信 · 难度：⭐⭐⭐⭐

📝 题目

在现代多 Agent 系统（如基于 LangGraph 构建的工作流）中，Agent 之间不再直接点对点发消息，而是通过读写一个全局的 State 对象来协同工作。请解释这种基于共享状态的通信模式，在处理“打回重改”这类循环依赖场景时，相比传统的消息队列模式有何优势？

💡 参考答案

▎一句话结论

基于共享 State 的通信模式将工作流的上下文和中间结果统一存储，使得任何 Agent 在任何步骤都能访问完整的“任务记忆”，从而天然支持循环、重试和分支，避免了消息队列模式下复杂的消息回退和数据拼接问题。

▎核心原理

  • 全局上下文透明性：在“打回重改”场景中，ReviewerAgent 需要将修改意见连同原始草稿一起返回给 WriterAgent。在 State 模式下，ReviewerAgent 只需将“审核意见”字段写入 State，并将流程指针指回 WriterAgent。WriterAgent 再次启动时，从同一个 State 对象中就能读到自己的上一版草稿和最新的修改意见，无需任何额外的数据传递。
  • 状态驱动的流程控制：循环依赖不再是复杂的消息路由，而是一个简单的“条件边”。图引擎检查 State 中的“审核结果”字段，如果为“不通过”，边就指向 WriterAgent，形成一个闭环。这比在消息队列中实现“消费消息、处理失败、重新发送到原始队列”的逻辑要直观和可靠得多。
  • 无状态 Agent 设计：每个 Agent 本身可以设计为无状态的，它们只负责“读取 State -> 处理 -> 写回 State”。这使得 Agent 可以独立开发、测试和扩展，因为它们不依赖任何外部的会话上下文或消息顺序。

▎深入解释

可以把消息队列模式想象成流水线上的工人，每个人完成自己的工序后，把半成品和一张“工序单”装进箱子，传给下一个人。如果质检员发现不合格，他需要找到原始的箱子，附上一张“返工单”，再把箱子重新搬回第一个工人的入口。这个过程涉及箱子的物理移动、单据的查找和附加，很容易出错。而 State 模式则像一块所有工人共享的“智能白板”。撰稿人把文章初稿写在白板上，质检员看了之后，直接在“审核意见”区域写下修改建议，并把撰稿人的任务状态改为“待重写”。撰稿人看到自己任务状态更新后，直接从白板上读文章和意见进行修改，所有信息都在白板上，一目了然，没有搬箱子的过程。这种模式让复杂的协同变得像操作一个共享文档一样简单，极大降低了编排的复杂度。

▎面试加分点

  • 明确 State 的不可变性与版本控制：每次写回 State 实际上是创建一个新版本，这为调试和回溯提供了天然支持。
  • 关联 LangGraph 的 Checkpointer：指出通过 Checkpointer，State 可以被持久化，系统即使在循环中崩溃，也能从断点恢复，这是消息队列难以实现的。
  • 对比 Actor 模型：可以简单提及，State 模式与 Actor 模型各有优劣，但在需要复杂上下文共享的 LLM 工作流中，State 模式更优。

▎常见误区

  • 误区：认为共享 State 是万能的，所有多 Agent 系统都该用它。
  • 纠正：当 Agent 之间是完全异步、解耦、且不需要共享复杂上下文的独立服务时，事件驱动或消息队列模式可能更合适。选择取决于耦合度和上下文共享需求。

📌 概念题 · Q8

考点标签

Graph RAG · 难度：⭐⭐⭐⭐

📝 题目

Graph RAG 的构建流程中，在从文本中抽取实体和关系并构建成知识图谱后，会执行一个“社区发现”步骤。请解释为什么在 Graph RAG 中需要执行社区发现，以及 Leiden 算法在此场景下相比 Louvain 算法有何关键优势？

💡 参考答案

▎一句话结论

社区发现是为了在庞大的知识图谱中识别出语义内聚的“话题簇”，从而为 LLM 提供高质量、模块化的全局摘要。Leiden 算法相比 Louvain，通过确保生成的社区内部完全连通，解决了后者可能产生“断连社区”的缺陷，提升了在 Graph RAG 中摘要的连贯性和质量。

▎核心原理

  • 化整为零，模块化总结：一个企业级知识图谱可能包含数十万个节点和边。直接让 LLM 对整个图做总结是不可能的。社区发现算法能将图自动分割成多个规模适中、内部联系紧密的子图（社区），每个社区代表一个相对独立的话题或概念群。
  • 生成全局摘要：对每个社区，可以提取其包含的实体和关系，作为 LLM 的上下文，生成该社区的摘要。这些社区摘要共同构成了对整个知识库的宏观理解，用于回答高层、概括性问题。
  • Leiden 算法的“连通性”保障：Louvain 算法在优化模块度的过程中，可能会将一个社区内部割裂成多个不连通的部分，这违反了“社区”的基本直觉。Leiden 算法在每次迭代后增加了一个“细化”阶段，它可以将一个社区内部不连通的部分分裂出去，从而保证最终生成的每个社区都是完全连通的。对于 LLM 摘要来说，一个内部逻辑连贯、实体紧密关联的社区信息，远比一个松散、割裂的集合更容易理解和总结。

▎深入解释

可以把知识图谱想象成一张巨大的城市交通图。社区发现就是在划分“街区”。一个好的街区划分应该是内部街道纵横交错，但街区之间只有少数主干道相连。Louvain 算法有时会划分出一个“名义上的街区”，但这个街区内可能被一条大河分成两半，彼此没有桥连接，这显然不合理。Leiden 算法能识别出这条大河，并将这个名义上的街区一分为二，确保每个街区内都是四通八达的。在 Graph RAG 中，如果 LLM 拿到一个“断连社区”的实体列表，它可能会困惑于为什么这些看似无关的实体会被归为一类，从而生成逻辑混乱或错误的摘要。Leiden 算法保证了输入给 LLM 的上下文本身就是高质量的、内聚的信息单元，这是生成可靠全局摘要的基础。

▎面试加分点

  • 明确指出 Leiden 算法的复杂度与 Louvain 相近，但质量更高，是 Graph RAG 的首选。
  • 解释“模块度”：简单说明社区发现是在优化模块度，即最大化社区内连接与社区间连接的比值。
  • 关联 Light RAG：指出 Light RAG 等框架正是利用了社区发现和摘要来构建其高效的混合检索机制。

▎常见误区

  • 误区：认为社区发现只是图算法的一个炫技步骤，对最终效果影响不大。
  • 纠正：社区发现是 Graph RAG 实现“全局理解”的关键。没有它，Graph RAG 就退化为只能回答局部问题的增强版 RAG。

📌 概念题 · Q9

考点标签

Light RAG · 难度：⭐⭐⭐⭐

📝 题目

Light RAG 提出了一种融合 low-level（关键词）、high-level（主题）和 native（原文）的混合检索架构。请详细解释这三种检索路径各自解决什么问题，以及它们是如何协同工作，最终提升 RAG 系统在复杂问题上的回答质量的？

💡 参考答案

▎一句话结论

Light RAG 通过 low-level 检索精确匹配实体，high-level 检索理解宏观主题，native 检索补充细节原文，三者协同工作，使得系统既能回答“关羽的武器是什么”这样的具体问题，也能回答“蜀汉兴衰的历程”这样的概括性问题，实现了对知识库的“点、线、面”全方位覆盖。

▎核心原理

  • Low-Level 检索（精确匹配）：将用户查询中的关键词和实体进行向量化，在图的实体向量库中检索最相关的节点。它解决的是“点”的问题，能快速定位到具体的人物、事件、物品等实体，并获取其周边关系和属性。适用于事实型、细节型问题。
  • High-Level 检索（主题理解）：将用户查询的整体语义进行向量化，与预先计算好的社区摘要向量库进行匹配，召回最相关的社区摘要。它解决的是“面”的问题，能理解查询的宏观主题和抽象概念，获取跨实体的总结性知识。适用于全局性、总结性问题。
  • Native 检索（原文溯源）：直接将用户查询与原始文本块进行向量匹配。它解决的是“线”的问题，能找回包含相关细节的原始上下文，作为对图和摘要的补充。适用于需要精确原文引用的场景。

▎深入解释

这就像在图书馆里找资料。你要研究“赤壁之战”，low-level 检索就像直接去人物传记区找到“周瑜”、“曹操”的档案卡，上面有他们的生平简介和关系网。high-level 检索就像去阅览室找到一本《三国演义》的摘要集，里面有一篇“赤壁之战始末”的专题总结，让你快速了解全局。native 检索就像去书架上一排排翻原版书，找到描写“火烧赤壁”那几个章节的原文，获取最生动的细节。Light RAG 的巧妙之处在于，它会同时执行这三种查找，然后把档案卡、专题总结和原文片段都交给 LLM，并告诉它：“这是关于你问题的关键人物信息，这是宏观背景，这是原文细节，请你综合回答。”这种多维度信息的聚合，让 LLM 的回答既有宏观视野，又有微观事实支撑，避免了单一检索方式带来的片面性。

▎面试加分点

  • 强调检索结果的去重与融合：Light RAG 需要将三种路径得到的、可能重复的信息进行合并，再喂给 LLM，避免上下文窗口浪费。
  • 关联 Graph RAG 的缺陷：指出 Light RAG 的混合检索是对原生 Graph RAG 的一种改进，解决了后者构建成本高、关系一旦错误无法修复等问题。
  • 提及查询意图分类：可以讨论在检索前，先用一个轻量级模型对查询意图进行分类，再动态调整三种检索路径的权重，效果会更好。

▎常见误区

  • 误区：认为 Light RAG 是三种 RAG 的简单叠加。
  • 纠正：它是一种有机融合。其核心创新在于利用图结构同时支持了低层和高层两种语义粒度的检索，而非常规 RAG 仅支持中等粒度的文本块检索。

📌 概念题 · Q10

考点标签

企业本地部署 · 难度：⭐⭐⭐

📝 题目

某金融企业出于数据合规要求，必须将所有 AI 服务部署在物理隔离的内网环境。在选型硬件时，架构师提出了一个“轻量起步，逐步扩展”的方案：先用 2 张 RTX 4090 D（共 48GB 显存）验证业务，未来再平滑升级到 4 卡 H200 服务器。请从显存数学和推理框架的角度，分析这个升级路径的可行性，以及在初期方案中运行 Qwen 3.5-32B（INT4 量化版）时需要注意的关键限制。

💡 参考答案

▎一句话结论

该升级路径在技术上是平滑可行的，因为 vLLM 等框架支持张量并行（Tensor Parallelism），可在不同规格的 GPU 集群间无缝迁移模型。但在初期方案中，48GB 显存运行 32B INT4 模型（约 18GB）时，必须为 KV Cache 预留足够空间，并严格限制输入/输出长度和并发数。

▎核心原理

  • 显存数学：32B 参数的 INT4 量化模型，其权重文件大小约为 32 × 0.5 = 16GB。加上推理框架开销，总显存占用约 18-20GB。2 张 4090 D 共 48GB 显存，剩余约 28GB 可用于 KV Cache。KV Cache 的显存占用与 批次大小 * 序列长度 * 隐藏层维度 * 层数 成正比，是并发和长文本处理的主要消耗者。
  • 张量并行：vLLM 支持将模型的层或张量切分到多张 GPU 上并行计算。初期在 2 张 4090 上运行，需要开启张量并行，将模型切分。未来升级到 4 卡 H200 时，只需调整张量并行度参数，模型本身无需任何改变，即可利用更多显存和算力。
  • 关键限制：消费级显卡的显存带宽和卡间通信带宽远低于企业级显卡。4090 D 的显存带宽约为 1TB/s，而 H200 高达 4.8TB/s。卡间通信上，4090 通常通过 PCIe 连接，速度远低于 H200 的 NVLink。这会导致在 4090 上，长文本输入或高并发时，推理延迟会显著增加，甚至因 KV Cache 不足而 OOM。

▎深入解释

这个方案就像先用一辆双引擎的家用 SUV（2x 4090）在小区里试跑物流，验证路线和流程。它能拉货，但载重和速度有限。验证成功后，直接换一辆四引擎的重型卡车（4x H200），货物（模型）还是那个货物，但运输能力天差地别。在 SUV 阶段，你必须非常小心地控制每次拉货的重量（输入长度）和同时出发的车队数量（并发）。如果一次拉的货太多（输入 32K tokens），或者同时出发的车太多（并发 10 个请求），KV Cache 这个“临时堆放区”就会爆满，导致系统崩溃。而重型卡车不仅“货仓”（显存）巨大，而且“卸货通道”（显存带宽）极宽，“车队协同”（NVLink）效率极高，可以轻松应对。

▎面试加分点

  • 给出具体的 KV Cache 估算公式：2 * 批次大小 * 序列长度 * 隐藏层维度 * 层数 * 2字节，展示量化分析能力。
  • 提及 vLLM 的 PagedAttention：它能优化 KV Cache 的显存使用，减少碎片，是应对该限制的关键技术。
  • 强调 PCIe 带宽限制：明确指出消费级显卡做多卡并行时，卡间通信是最大瓶颈。

▎常见误区

  • 误区：认为只要模型权重能装进总显存，就能跑任何长度的文本和高并发。
  • 纠正：KV Cache 的显存消耗常常超过模型权重本身。部署前必须根据业务场景的序列长度和并发量，精确计算所需显存。

🛠 应用题 · Q1 · 架构设计

题型

架构设计

场景标签

SaaS多租户 LoRA vLLM 模型量化

📝 题目

你正在为一家 SaaS 公司设计一个“AI 文案风格定制平台”。平台需要为每个企业租户提供专属的文案生成模型，要求推理服务能根据请求中的 tenant_id 动态加载对应的模型风格，且服务不能重启。公司预算有限，初期仅采购了一台搭载 2 张 NVIDIA RTX 4090 D（共 48GB 显存）的服务器。请设计一套完整的模型服务架构方案，涵盖从模型选型、量化策略、多租户动态加载到 HTTP 服务暴露的全过程，并论述其可行性。

💡 参考答案

▎解题思路

  1. 需求拆解与约束分析：核心约束是硬件资源（48GB显存）有限，需求是“零停机动态切换”和“多租户隔离”。这直接排除了为每个租户部署独立模型实例的方案。
  2. 技术选型：采用“一个共享基座模型 + N 个轻量级 LoRA 适配器”的架构。基座模型常驻显存，租户的个性化风格以 LoRA 权重文件形式存储在磁盘，推理时动态挂载。
  3. 可行性验证：进行显存数学计算。基座模型选型与量化是关键，必须确保加载基座模型后，剩余显存足够支撑推理时的 KV Cache 和 LoRA 权重缓存。

▎详细方案

  1. 基座模型选型与量化：
    • 选择 Qwen2.5-14B 作为基座模型，其中文能力强，参数量适中。
    • 采用 INT4 量化（AWQ/GPTQ） 压缩模型。根据公式 模型大小(GB) ≈ 参数量(B) × 比特数(Bit) / 8，14B 模型 INT4 量化后体积约 9GB。加载进显存后，剩余 39GB 空间，为多租户并发推理的 KV Cache 和 LoRA 加载提供了充足余量，完全可行。
  2. 推理服务框架：
    • 使用 vLLM 作为推理引擎。它原生支持 LoRA 热插拔，并具备 PagedAttention 机制高效管理显存。
  3. 服务部署与动态路由：
    • 以 OpenAI 兼容服务器模式启动 vLLM，在启动命令中通过 --enable-lora 和 --lora-modules 参数预注册所有租户的 LoRA 适配器路径。
      bash vllm serve /path/to/qwen2.5-14b-int4 \ --enable-lora \ --lora-modules tenant_A=/models/adapters/style_A tenant_B=/models/adapters/style_B
    • 上游 API 网关或业务服务在接收到用户请求后，只需在转发给 vLLM 的请求体中填入 model 参数（如 ”tenant_A”），vLLM 内部的路由层就会自动将对应的 LoRA 权重与基座模型结合进行推理，对业务层完全透明。

▎关键细节 & 踩坑点

  • LoRA 权重体积：单个 LoRA 权重文件通常只有几十 MB，因此即使有数十个租户，磁盘和显存缓存压力也极小。
  • 显存缓冲区：在 vLLM 启动时需通过 --gpu-memory-utilization 预留一定比例显存（如 0.85），不要拉满，防止加载 LoRA 或 KV Cache 增长时导致 OOM（显存溢出）。
  • LoRA 模块管理：vLLM 会维护一个 LoRA 缓存池，当请求到来时，若其 LoRA 不在显存中，会自动触发加载（热插拔），并淘汰不常用的 LoRA 以腾出空间。

▎可扩展优化

  • 自动化微调流水线：当租户上传新数据并触发微调时，后台训练集群（可利用空闲时段或独立 GPU）完成训练后，将新的 adapter_model.safetensors 文件推送到约定路径，并调用 vLLM 的 API 动态刷新 LoRA 模块列表，实现全自动化闭环。
  • 多基座模型支持：未来若业务扩展，可部署多套不同规格的基座模型（如一个通用模型，一个法律专用模型），通过网关层根据租户属性路由到不同的 vLLM 实例。

题型

场景分析

场景标签

智能客服 Skill文件 动态路由 情绪识别

📝 题目

你负责一个智能客服系统的“专家坐席”模块设计。系统需要处理三类完全不同的用户请求：A. 标准业务流程咨询（如“如何退货”），B. 敏感业务操作（如“修改订单地址”），C. 高情绪化投诉（如“你们是骗子，我要投诉！”）。如果将所有处理逻辑都塞进一个巨大的 Prompt 中，会导致 Agent 行为混乱、幻觉风险高。请基于 Skill 配置文件 的思想，设计一套动态路由与加载方案，让 Agent 能根据用户意图和情绪，自动切换到对应的“专家技能”模式来处理问题。

💡 参考答案

▎解题思路

  1. 问题拆解：核心是将“路由决策”与“技能执行”解耦。我们需要一个“前台接待员”负责分类，然后由不同领域的“专家”来处理具体问题。
  2. 方案设计：将三类请求的处理逻辑抽象为三个独立的 Skill 配置文件（.skill），每个文件封装了该场景专属的 System Prompt 和可调用的 Tool 集合。主 Agent 作为路由器，根据对用户输入的初步分析，动态加载并激活对应的 Skill。
  3. 核心价值：这种模块化设计使得每个 Skill 的 Prompt 高度专注，不受其他场景干扰，极大降低了幻觉，并且易于独立维护和升级。

▎详细方案

  1. Skill 文件定义：
    • policy_expert.skill: system_prompt 设定为“你是一个严谨的客服，请严格基于知识库回答流程问题...”，bound_tools 包含 vector_search。
    • order_handler.skill: system_prompt 设定为“你拥有订单操作权限，必须先引导用户完成身份验证...”，bound_tools 包含 send_sms， update_order_api。
    • empathy_complaint.skill: system_prompt 设定为“你是一个高级客诉专家，首要任务是安抚用户情绪，严禁使用机械话术...”，bound_tools 包含 crm_vip_gift_api。
  2. 主 Agent 路由逻辑：
    • 意图与情绪识别层：主 Agent 的 System Prompt 被设定为一个“分诊台护士”。它首先接收用户输入，并调用一个轻量级的分类函数或直接利用 LLM 进行初判，输出一个 JSON：{“intent”: “complaint”, “emotion”: “angry”}。
    • Skill 加载与执行：业务代码根据分类结果，从文件系统中读取对应的 .skill 配置。
      python if intent == “complaint” and emotion == “angry”: skill = load_skill(“empathy_complaint.skill”) elif intent == “order_operation”: skill = load_skill(“order_handler.skill”) # ...
    • 上下文融合：将主 Agent 的基础设定（如“你是一个乐于助人的助手”）与 Skill 的 system_prompt 拼接成最终的 System Prompt，同时将该 Skill 的 bound_tools 列表传给 LLM，发起最终的推理请求。

▎关键细节 & 踩坑点

  • 路由准确性：情绪识别是关键。如果用户辱骂但意图是“退款”，却路由到了“标准流程” Skill，会激化矛盾。可以设置规则：只要情绪为“愤怒”，无论何种意图，都优先路由到 empathy_complaint.skill 进行安抚。
  • Skill 切换的平滑性：在多轮对话中，一个会话可能从“投诉”开始，安抚后转为“订单处理”。对话管理系统需要支持在一个 Session 内动态切换激活的 Skill，并继承之前的上下文。

▎可扩展优化

  • 基于向量相似度的路由：当 Skill 数量激增时，可以将每个 Skill 的 description 进行 Embedding。路由时，将用户问题的 Embedding 与所有 Skill 描述进行相似度匹配，实现更灵活、更自动化的路由。
  • Skill 链式调用：复杂的业务流程可以由多个 Skill 串行或并行完成。例如，一个“售后处理”总 Skill 可以内部编排调用 empathy_complaint.skill 和 order_handler.skill。

🛠 应用题 · Q3 · 工程实现题

题型

工程实现

场景标签

LoRA权重 safetensors adapter_config 模型文件结构

📝 题目

你完成了一个医疗领域的 LoRA 微调任务，产出了一个名为 qwen2.5-7b-lora-medical 的目录，里面包含 adapter_config.json 和 adapter_model.safetensors 两个核心文件。现在，你需要编写一个 Python 脚本来对这个补丁包进行“健康检查”，以验证其完整性与兼容性。请设计这个脚本的核心逻辑，包括：1. 如何读取并校验配置文件；2. 如何加载权重文件并验证其内部矩阵形状是否与配置匹配；3. 如何判断这个补丁是否能安全地挂载到目标基座模型上。

💡 参考答案

▎解题思路

  1. 分步校验：健康检查应遵循“先文本，后数据，再逻辑”的顺序。先解析 JSON 配置，确认其语法正确且字段完整；再读取二进制权重文件，确认其可加载且数据结构正确；最后将两者信息结合，进行逻辑一致性校验。
  2. 核心逻辑：关键校验点是 adapter_config.json 中的 r（秩）和 target_modules（目标模块），必须与 adapter_model.safetensors 文件内矩阵的维度完全一致。例如，配置中 r=16，那么所有 lora_A 矩阵的第一维必须是 16。
  3. 兼容性判断：通过比对配置中的 base_model_name_or_path 与预期值，确保这个补丁是为正确的基座模型训练的。

▎详细方案

import json
import os
from safetensors.torch import load_file

def health_check_lora(adapter_path, expected_base_model):
    # 1. 校验配置文件
    config_path = os.path.join(adapter_path, “adapter_config.json”)
    try:
        with open(config_path, ‘r’) as f:
            config = json.load(f)
    except FileNotFoundError:
        return False, “错误: 找不到 adapter_config.json”
    except json.JSONDecodeError:
        return False, “错误: adapter_config.json 格式非法”

    # 检查必要字段
    required_fields = [“r”, “lora_alpha”, “target_modules”, “base_model_name_or_path”]
    for field in required_fields:
        if field not in config:
            return False, f“错误: adapter_config.json 中缺少必要字段 ‘{field}’”

    # 2. 校验基座模型兼容性
    if config[“base_model_name_or_path”] != expected_base_model:
        return False, f“错误: 补丁是为 ‘{config[‘base_model_name_or_path’]}’ 训练，但预期基座模型为 ‘{expected_base_model}’”

    # 3. 加载并校验权重文件
    weights_path = os.path.join(adapter_path, “adapter_model.safetensors”)
    try:
        weights = load_file(weights_path)
    except FileNotFoundError:
        return False, “错误: 找不到 adapter_model.safetensors”
    except Exception as e:
        return False, f“错误: 无法加载 safetensors 文件: {e}”

    # 核心：检查矩阵形状与配置的一致性
    r = config[“r”]
    target_modules = config[“target_modules”]

    for key, tensor in weights.items():
        # 检查 lora_A 的维度: shape[0] 应等于 r
        if “lora_A” in key:
            if tensor.shape[0] != r:
                return False, f“错误: 矩阵 ‘{key}’ 的形状为 {tensor.shape}，其第一维应为 r={r}”
        # 检查 lora_B 的维度: shape[1] 应等于 r
        elif “lora_B” in key:
            if tensor.shape[1] != r:
                return False, f“错误: 矩阵 ‘{key}’ 的形状为 {tensor.shape}，其第二维应为 r={r}”

        # 检查是否所有 target_module 都有对应的权重
        module_found = False
        for module in target_modules:
            if module in key:
                module_found = True
                break
        if not module_found:
            return False, f“错误: 权重 ‘{key}’ 不属于配置中声明的 target_modules {target_modules}”

    return True, “健康检查通过！LoRA 补丁完整且兼容。”

▎关键细节 & 踩坑点

  • 矩阵对应关系：必须清楚 lora_A 权重形状是 (r, input_dim)，lora_B 权重形状是 (output_dim, r)。校验逻辑必须严格对应。
  • 非量化参数：adapter_model.safetensors 中可能包含一些非 LoRA 矩阵（如 embed_tokens 或 norm 层的权重），如果微调时设置了不对它们应用 LoRA。脚本需要能处理这些“额外”的键，不能报错。
  • r 和 lora_alpha 不是一回事：r 决定矩阵结构，lora_alpha 是缩放因子，不影响形状，不要混淆校验。

▎可扩展优化

  • 值范围校验：可以增加对权重值的统计检查，如检查是否存在大量 NaN 或 Inf 值，初步判断训练是否崩溃。
  • 与推理引擎联动：将此脚本集成到 vLLM 的 LoRA 加载流程中，在服务启动或动态加载时自动执行，实现上线前的自动卡点。

🛠 应用题 · Q4 · 排障优化题

题型

排障优化

场景标签

Graph RAG Light RAG 成本优化 性能分析

📝 题目

你的团队基于传统的 Graph RAG 构建了一个企业知识库问答系统。流程是：文档 -> 实体关系抽取 -> 构建图 -> Leiden 社区发现 -> LLM 为每个社区生成摘要 -> 查询时路由（局部/全局搜索）。上线后发现两个严重问题：1. 构建成本极高，处理一万字的文档，LLM 生成社区摘要的 Token 消耗就高达数百万，且耗时超过 10 分钟；2. 错误不可修复，一旦 LLM 在实体关系抽取或摘要阶段产生幻觉，整个知识图谱的质量就会下降，且没有自动纠错机制。请分析问题根源，并提出一个基于 Light RAG 思想 的优化方案，重点说明如何解决上述两个问题。

💡 参考答案

▎解题思路

  1. 问题根源分析：
    • 成本高：传统 Graph RAG 的“社区发现 + 摘要”是 Token 杀手。Leiden 算法将图划分为多个社区后，需要为每一个社区调用一次 LLM 生成摘要。对于大文档，社区数量可能成百上千，导致 LLM 调用次数和 Token 消耗爆炸式增长。
    • 错误不可修复：传统流程是“一次性”的。实体关系抽取和摘要生成是独立的离线步骤，一旦完成，错误就被固化在图和摘要中。查询阶段只是从这些可能出错的数据中检索，缺乏对原始文本的二次验证机制。
  2. 优化思想：引入 Light RAG 的核心理念，将昂贵的“全局摘要”从构建阶段移除，转为查询时按需生成；同时，在检索流程中增加对原始文本的“原生查询”通道，作为事实依据的最终保障。

▎详细方案

  1. 构建阶段优化（解决成本问题）：
    • 保留轻量级图构建：仍然进行实体关系抽取和图的构建，但完全取消“社区发现”和“LLM 生成社区摘要”这两个最耗时的步骤。此时的图是一个纯粹的、无摘要的数学结构。
    • 向量化双索引：将图中的实体和关系分别进行 Embedding，建立向量索引。这是 Light RAG 的核心，为后续的高效检索打下基础，成本远低于生成摘要。
  2. 查询阶段优化（解决错误不可修复问题）：
    • 混合检索模式：当用户查询“刘备和关羽是什么关系？”时，系统并行执行三种检索：
      • Low-level（关键词检索）：从问题中提取关键词（“刘备”，“关羽”），用实体向量索引找到对应节点，再获取其周边子图的结构化信息。
      • High-level（主题检索）：将整个问题 Embedding，去匹配关系向量索引，找到最相关的抽象关系。
      • Native（原生文本检索）：将问题直接去原始文本的切片（Chunks）中进行相似度检索，找回最相关的原始段落。
    • 去重、融合与生成：将三路检索的结果进行去重和排序。此时，LLM 拿到的上下文既有从图结构中推导出的关系（Low/High-level），也有未经任何加工的原始文本（Native）。LLM 可以交叉验证，如果图结构信息与原文冲突，LLM 有能力和机会依据原文来纠正或忽略图中的错误信息。

▎关键细节 & 踩坑点

  • Gleaning（补充校验）：在 Light RAG 的构建阶段，实体关系抽取后有一个 gleaning 步骤，即让 LLM 进行二次自查，补充可能遗漏的实体，这能在源头提高图的质量。
  • 检索效率：并行执行三路检索对底层检索引擎的并发能力有要求。需要确保向量数据库能高效处理并发查询，并将各路召回结果快速合并。

▎可扩展优化

  • 动态成本控制：可以根据查询的复杂度，动态决定是否开启 High-level 检索。对于简单的事实性问题，仅靠 Low-level 和 Native 检索就能回答，进一步节省 Token。
  • 图结构的持续更新：当原始文档更新时，只需对新增或修改的 Chunk 重新进行实体关系抽取，并增量更新图结构和向量索引，无需重建整个图谱，实现准实时的知识更新。

题型

综合落地

场景标签

智能销售 数据中台 RAG 数据飞轮 从0到1

📝 题目

你被任命为一家企业服务公司的 AI 团队负责人，要求你在三个月内，从零开始交付一个“智能销售助理”系统的 MVP（最小可行产品）。CEO 的期望是：这个系统不仅能回答产品问题，还能在多轮对话中挖掘客户意图，并且能引用脱敏后的历史成功案例来促进成交。更重要的是，系统的数据能够形成闭环，反哺未来的销售策略和培训。请给出你的完整交付计划，包括技术选型、模块划分、实施路径和数据飞轮的设计。

💡 参考答案

▎解题思路

  1. 目标对齐与范围界定：MVP 的核心不是“大而全”，而是跑通“意图挖掘 -> 案例展示 -> 数据回收”这个最小闭环。我们必须用最成熟、成本最低的技术组合来快速验证价值。

  3. 分阶段实施：三个月划分为三个阶段，每月一个里程碑，步步为营。

▎详细方案

第一阶段：数据中台雏形与基座能力（第 1 个月）
* 目标：完成历史数据的清洗与结构化，并让 Agent 具备基础的 RAG 问答能力。
* 实施路径：
1. 数据清洗工场：从 CRM 和销售手中收集历史对话记录、成功案例文档。编写脚本进行数据清洗：去除无效字符、统一格式，并利用轻量级 LLM（如 Qwen2.5-7B）自动打标签（如：“成功案例”，“价格异议”，“竞品对比”）。
2. 搭建 RAG 知识库：将清洗后的产品文档、FAQ 切片并存入向量数据库（如 Milvus）。
3. 搭建基础 Agent：基于 LangGraph 构建一个简单的 ReAct Agent，可以调用向量数据库检索产品知识，实现单轮问答。
* 交付物：一个能回答“你们产品有什么功能？”的对话机器人 Demo。

第二阶段：意图挖掘与案例展示引擎（第 2 个月）
* 目标：实现多轮对话的槽位填充（Slot Filling）和动态脱敏案例展示。
* 实施路径：
1. 设计状态机：在 LangGraph 中定义销售对话的状态（如 greeting, needs_discovery, case_showing, closing）。needs_discovery 状态内部实现 Slot Filling 逻辑：Agent 必须收集到“预算、痛点、团队规模、上线时间”四个槽位，否则状态机不允许进入 case_showing 状态。
2. 实现 Tool-use：
* 开发一个 query_crm_cases 工具，当 Agent 进入 case_showing 状态时，调用此工具，传入当前客户标签（如行业=“电商”），从传统数据库（PostgreSQL）中查询匹配的成功案例。
* 在工具函数内部实现数据脱敏网关：用正则或 NER 模型自动将公司名、人名、电话等敏感信息替换为“某头部电商平台”、“张总”等占位符。
3. 整合 Prompt：将脱敏后的案例数据注入到 LLM 的 Prompt 中，生成具有说服力的自然语言话术。
* 交付物：一个能主动询问需求，并在合适时机展示“我们曾帮某同行解决过类似问题...”的销售助理 MVP。

第三阶段：数据飞轮与业务外延（第 3 个月）
* 目标：实现数据闭环，让 MVP 产生的数据能自我进化，并探索衍生价值。
* 实施路径：
