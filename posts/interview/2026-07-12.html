📌 概念题 · Q1

考点标签

Agentic Auth · 难度：⭐⭐⭐⭐

📝 题目

请解释企业级 Agent 开发中 Agentic Auth（智能体鉴权体系）的核心定位是什么？它包含哪几个物理层级的安全设计？为什么说它是 AI 时代的"OAuth 标准"？

💡 参考答案

▎一句话结论

Agentic Auth 是一套覆盖网关鉴权、数据隔离、沙箱执行和人肉安全闸的多层级安全架构，解决的是"Agent 代表人类执行操作时如何证明授权合法性"这一信任链流转问题。

▎核心原理

  • 网关层鉴权：所有子 Agent 调用外部工具时必须携带统一身份标识（如 X-Agent-ID），禁止单独硬编码 API Key，通过统一 LLM Gateway 集中管控
  • 多租户数据隔离：在 RAG 检索向量库时，网关或代码层必须注入硬性标量预过滤（Pre-filtering），将 tenant_id、company_id 作为强制 WHERE 条件绑定在向量相似度检索之前
  • 安全沙箱隔离：Agent 需要现场编写并执行代码时，必须在 K8s 中利用 gVisor、Kata Containers 或 E2B/Modal 创建秒级创建、用完即毁的隔离运行环境
  • 人肉安全闸（HITL）：对破坏性接口（删除、修改、退款等），利用 interrupt_before 机制将状态持久化后释放线程，等待真实人类确认后再 Resume

▎深入解释

传统 SaaS 鉴权解决的是"用户→系统"的信任问题，而 Agentic Auth 解决的是"用户→Agent→工具→数据"这条多跳信任链。当 Agent A 通过网络调用 Agent B，或者 Agent 代表用户通过 MCP 协议连接企业内网时，每一跳都需要证明"这个行为得到了真实人类的授权"。

核心矛盾在于：模型计算在公有云，而核心资产、私有工具留在企业内网。Agentic Auth 通过 MCP 协议的标准化暴露机制，优雅地解决了这一矛盾——类似于 AI 界的 OAuth 或 USB-C 标准，让跨组织、跨生态的 Agent 协作有了统一的安全基座。

▎面试加分点

  • 能区分"查询接口"（可自动化执行）与"功能接口"（必须 HITL 拦截）的工程判断力
  • 提到 interrupt_before + thread_id 持久化到 PostgreSQL/Redis 的具体落地机制
  • 指出预过滤必须发生在向量相似度检索"之前"，而非事后用代码过滤（否则 Top-K 会残缺）

▎常见误区

  • 认为给每个子 Agent 发一个 API Key 就够了——实际上这无法追溯授权链路，且一旦泄露无法收敛
  • 把多租户隔离做在"检索后过滤"层——这会导致向量检索返回的 Top-K 结果被过滤后数量不足，检索质量严重下降

📌 概念题 · Q2

考点标签

Obsidian · 难度：⭐⭐

📝 题目

请说明 Obsidian 作为"第二大脑"知识管理工具的核心定位是什么？它的四大核心优势分别解决了什么痛点？与 Notion 等云端笔记软件的本质区别在哪里？

💡 参考答案

▎一句话结论

Obsidian 是一款本地优先的 Markdown 知识管理工具，通过双向链接和关系图谱把碎片化笔记编织成知识网络，核心优势在于数据绝对掌控、极速离线、恐怖的插件生态和完全免费。

▎核心原理

  • 本地优先：所有笔记以 .md 纯文本格式保存在本地硬盘，即使 Obsidian 公司倒闭，数据仍可用任何文本编辑器打开
  • 双向链接：用 [[另一篇笔记]] 语法建立引用，系统自动生成关系图谱，帮助发现知识间隐藏联系
  • 卡片盒笔记法：适合记录碎片化灵感，通过标签和链接逐步聚沙成塔
  • 插件生态：上千个社区插件，可从记事本扩展为看板、思维导图、个人仪表盘

▎深入解释

Obsidian 与 Notion、印象笔记等云端笔记软件的本质区别在于数据主权。云端软件的数据存储在厂商服务器上，用户面临限速、丢数据、频繁改版、甚至厂商停服的风险。Obsidian 选择本地优先策略，数据完全掌握在用户手中，启动和搜索速度极快，且在无网络环境下无缝使用。

对于程序员和技术人员来说，Obsidian 的 Markdown 原生支持、代码高亮、文档树结构非常适合记录技术文档、排查日志和积累代码片段。结合 LLM Wiki 插件（如 Karpathy 提出的模式），AI 可以自动在 Graph View 上生成概念实体和双向引用链接，进一步放大"第二大脑"的效能。

▎面试加分点

  • 提到 Obsidian 与 LLM Wiki 模式的结合点——AI 自动维护双向链接和概念图谱
  • 指出本地纯文本格式是"抗厂商锁定"的终极保险
  • 对新手建议"先当记事本用，等笔记量大起来再根据痛点找插件"，体现工程务实思维

▎常见误区

  • 上手就盲目折腾各种复杂插件和皮肤——应该先用 [[ ]] 建立几篇笔记链接，等笔记量大了再按需引入插件
  • 认为"本地优先"等于"不能同步"——实际上可通过插件实现多端同步

📌 概念题 · Q3

考点标签

LLM Wiki · 难度：⭐⭐⭐⭐

📝 题目

请解释 Andrej Karpathy 提出的 LLM Wiki 模式的核心内涵是什么？它的三层架构如何设计？与传统 RAG 系统"临时抱佛脚"的检索方式相比，解决了哪些根本性痛点？

💡 参考答案

▎一句话结论

LLM Wiki 是让 LLM 充当全职图书管理员，在文档录入阶段就主动提取实体、概念和论点，自动构建并维护一个结构化、高度互联的 Markdown 知识库，实现"录入即思考"的知识管理范式转变。

▎核心原理

  • Immutable Sources（不变量源码层）：只读的原始 PDF、研报、笔记，大模型绝不修改，作为最后的事实依据
  • The Wiki（维基层）：由 LLM 完全拥有并动态维护的 Markdown 文件目录，包含 Source Notes（源文档摘要）、Concept Pages（核心概念页）、Author/Debate Pages（观点交锋大纲）
  • The Schema（约束规范层）：通过 CLAUDE.md 或 AGENTS.md 提示词配置文件，严格规定模型维护 Wiki 的行为准则、模板规范（YAML Frontmatter、[[双括号]] 双向链接）及自我纠错（Lint）机制

▎深入解释

传统 RAG 的工作流是"临时抱佛脚"：用户提问时，系统才临时把问题转向量，在原始文档中"盲捞"切片，再塞给大模型组合答案。这种模式每次检索都从零开始，如果知识散落在不同文档中，极易因语义截断、无法建立跨文档实体关联而给出肤浅、割裂的回答。

LLM Wiki 的颠覆性在于将"思考时机"从查询时提前到录入时。当新文档喂给系统时，LLM 像人类学者做研究一样，主动提取实体、概念、论点，并写入持久化的维基百科。后续查询时，用户直接站在已经融会贯通的知识体系上对话，而非每次重新检索。

在交互界面上，LLM Wiki 更适合终端或轻量 IDE（如 Claude Code / Cursor），实现代码级插拔，而非传统 RAG 的单一无状态 Chatbox。

▎面试加分点

  • 能清晰对比三个维度的差异：知识沉淀由谁完成（人类手工 vs AI 临时抽取 vs LLM 全自动维护）、思考时机（查问时 vs 录入时）、交互界面（GUI vs Chatbox vs IDE）
  • 提到社区已有 Obsidian 插件和桌面端独立应用（利用 Louvain 算法发现知识聚类和知识盲区）
  • 指出 Schema 层的自我纠错机制是保证 Wiki 质量不退化的关键

▎常见误区

  • 认为 LLM Wiki 就是"用 AI 生成笔记"——实际上它是一个持久化、增量维护、相互引用的知识网络，不是一次性生成
  • 忽略 Schema 层的重要性——没有严格的行为准则和 Lint 机制，LLM 维护的 Wiki 会逐渐退化成无结构的垃圾堆

📌 概念题 · Q4

考点标签

Few-Shot · 难度：⭐⭐⭐

📝 题目

请解释 Few-Shot（少样本提示）的核心概念是什么？Zero-Shot、One-Shot、Few-Shot 三者有何区别？在企业实际落地中，Few-Shot 与模型微调（Fine-Tuning）的本质差异和选型逻辑是什么？

💡 参考答案

▎一句话结论

Few-Shot 是在提示词中提供 2~5 个"问题与答案示例"来引导大模型按预期格式、逻辑和风格生成结果的技术，本质是"不改变模型参数的上下文引导"，与微调"改变模型权重肉身"有根本性差异。

▎核心原理

  • Zero-Shot：不给任何例子，直接下达指令（如"请翻译这句话"）
  • One-Shot：给 1 个例子，让模型摸索规律
  • Few-Shot：给 2~5 个例子，锁死输出格式、语言风格和判断边界
  • 与 Fine-Tuning 的本质差异：Few-Shot 只是在提示词里塞例子，模型参数完全没变；Fine-Tuning 把成千上万条数据喂给模型重新训练，改变了模型权重

▎深入解释

大模型虽然知识渊博，但不给范例时经常出现格式不固定（你想要 JSON 它返回废话）、理解不了潜台词（复杂业务逻辑产生幻觉）等问题。Few-Shot 通过几个高质量样本，让 AI 瞬间锁死三个核心要素：输出格式、语言风格、判断边界。

在工程落地中，Few-Shot 与 Fine-Tuning 的选型逻辑是：Few-Shot 成本几乎为零，适合项目早期 MVP 验证和规则较简单的场景，但每次调用都消耗额外 Token；Fine-Tuning 成本较高（需要算力、数据清洗、研发时间），但训练好后单次调用更省 Token，适合业务成熟期追求极致高并发和超低延迟的场景。

工业界主流共识是："先用大模型 + Few-Shot 快速跑通验证业务边界，等积累了足够多的真实负样本和高质量数据后，再考虑 SFT 或 DPO。"

▎面试加分点

  • 能举出智能客服意图识别的具体 Few-Shot 应用场景（给 2~3 个意图分类示例，锁死 JSON 输出格式）
  • 指出 Few-Shot 的核心价值是"树立行为模范"，而非教模型新知识
  • 提到"先用 Few-Shot 验证边界，再 SFT/DPO 固化能力"的渐进式工程路径

▎常见误区

  • 认为 Few-Shot 例子越多越好——实际上 2~5 个高质量样本就足够，过多会浪费 Token 且可能引入噪声
  • 把 Few-Shot 当作微调的替代品——两者解决的是不同阶段的问题，Few-Shot 是验证期的工具，Fine-Tuning 是规模化期的工具

📌 概念题 · Q5

考点标签

Qdrant · 难度：⭐⭐⭐⭐

📝 题目

请说明 Qdrant 作为专用向量数据库的三大"杀手锏"优势是什么？在什么场景下应该选择 Qdrant 而非 Milvus 或 PostgreSQL(pgvector)？

💡 参考答案

▎一句话结论

Qdrant 的三大杀手锏是：极致的硬件白嫖能力（量化+On-disk 存储）、原生标量过滤不丢 Top-K 的 Payload 索引、以及单体架构带来的极低 DevOps 心智负担，适合百万到数亿级向量、追求单机极致性价比的独立 AI 业务。

▎核心原理

  • 量化+On-disk 存储：支持 Int8 标量量化和 On-disk 索引，做 HNSW 计算时才动态映射到内存，用极低服务器预算抗住海量数据
  • Payload 标量过滤不丢 Top-K：底层原生支持标量与向量的单阶段混合检索，多租户、细粒度权限隔离极为优雅，不会出现"先检索后过滤"导致 Top-K 残缺的问题
  • 单体架构零依赖：只有一个二进制文件/一个 Docker 镜像，无外部基础设施依赖（不像 Milvus 捆绑 etcd/MinIO），Helm Chart 或 Docker 挂卷即可进生产

▎深入解释

在选型矩阵中，三种方案各有定位：PostgreSQL(pgvector) 适合千万级向量以内、重度依赖关系表联合查询的场景，运维复杂度极低；Qdrant 适合百万到数亿级向量、追求单机极致性价比的纯非结构化检索，运维复杂度中低；Milvus 适合亿级以上海量多模态数据、追求极致超高并发 QPS，但运维复杂度中高（单机也捆绑 MinIO、etcd 等组件）。

选择 Qdrant 的典型时机是：项目属于独立 AI 业务，数据体量已明显超越 pgvector 的承载范围（如千万级多模态切片、大量半结构化文档），但还不需要 Milvus 分布式集群的规模，且团队希望单台服务器稳稳抗住、运维不掉头发。

工程落地最优解是在云服务器（如 4核16G/8核32G ECS）上拉 Qdrant Docker 镜像，开启 Int8 量化和 Payload 倒排索引，上层直接对接 LangGraph 或 FastAPI 后端，速度达毫秒级，ROI 极高。

▎面试加分点

  • 能解释"先向量检索再代码过滤"导致 Top-K 残缺的技术原理，以及 Qdrant 单阶段混合检索如何解决
  • 指出 Milvus 的 etcd 对磁盘性能敏感，官方建议用本地 NVMe/SSD，慢盘影响稳定性
  • 提到 Qdrant 的 Rust 底层语言带来的内存安全性和性能优势

▎常见误区

  • 认为 Qdrant 不适合生产环境——实际上它的单体架构恰恰是生产环境的优势，减少了分布式组件的故障点
  • 把 Qdrant 和 Milvus Distributed 做同维度对比——Qdrant 的定位是单机高性能，Milvus Distributed 是多机高可用，不在一个量级

📌 概念题 · Q6

考点标签

Hermes 3 · 难度：⭐⭐⭐

📝 题目

请说明 Hermes 3 系列模型的核心定位是什么？它在 Agent 开发场景中有哪些致命吸引力？与官方 Llama 3 或 GPT-4 相比，它的"未过度对齐"特质解决了什么工程痛点？

💡 参考答案

▎一句话结论

Hermes 3 是由 Nous Research 基于 Llama 底座深度微调的开源大语言模型，专门为"当好智能体大脑"而优化，在函数调用稳定性、结构化输出和长文本注意力方面极致强化，同时去除了大厂模型的过度对齐，完全服从开发者指令。

▎核心原理

  • 极强的 Function Calling：对 XML/JSON 标签包裹和函数调用做了深度优化，能稳定理解多工具组合流，准确判断何时调用工具、何时直接回复
  • 未过度对齐：去除了大厂模型常见的多余道德说教和过度对齐，保持中立、客观、极度听话的特质，不轻易拒绝复杂指令
  • 长文本注意力：基于 RoPE 扩展到 128K+ 上下文后做了专门的注意力机制微调，Needle In A Haystack 测试几乎全绿
  • 多尺寸选择：8B 适合本地量化部署跑高频子 Agent，70B/405B 适合作为多智能体系统的 Supervisor

▎深入解释

在 Agent 开发中，最让人头疼的是模型不听话——无法稳定输出 JSON、调用工具时参数格式报错。官方 Llama 3、GPT-4 或 Claude 在对齐上做得极其严格，有时甚至"死板"，动不动拒绝回答或用政治正确的套话敷衍，这在长文本生成或复杂业务逻辑推演中严重影响体验。

Hermes 3 的核心价值在于"Agentic Alignment"——它像一个真正的"冷酷工具人"，完全顺着开发者的 System Prompt 和业务逻辑深度思考，不会因为"安全护栏"而偏离业务目标。这对于处理复杂的企业级业务逻辑和高自由度角色扮演至关重要。

在开发实践中，Hermes 完美适配 ChatML 格式（<|im_start|>system...<|im_end|>），写 System Prompt 时直接用最直白的逻辑约束即可。让模型在输出 JSON 前先在 <thinking> 标签里进行思维链推理，Function Calling 准确率会再次飙升。

▎面试加分点

  • 能区分"对齐"与"过度对齐"的边界——对齐是防止有害输出，过度对齐是牺牲业务效率
  • 提到 CoT（思维链）+ XML 标签的 Prompt 工程技巧来进一步提升 Hermes 的工具调用准确率
  • 指出多尺寸选择策略：小模型跑子 Agent 省成本，大模型做 Supervisor 保质量

▎常见误区

  • 认为"Uncensored"等于"不安全"——实际上 Hermes 是去除了多余道德说教，而非移除所有安全机制
  • 把 Hermes 当作通用聊天模型——它的核心定位是 Agent 引擎，在闲聊场景未必优于通用模型

📌 概念题 · Q7

考点标签

vLLM · 难度：⭐⭐⭐

📝 题目

请说明 vLLM 作为高性能推理框架的核心定位是什么？它在生产环境中如何实现 LoRA 补丁的动态热插拔加载？这种机制对 SaaS 多租户架构有什么关键意义？

💡 参考答案

▎一句话结论

vLLM 是当前工业界最主流的高性能大模型推理框架，通过内置 LoRA 动态加载机制，在显存中常驻一个共享基座模型，同时为不同租户秒级热插拔各自的 LoRA 补丁，实现了"1个底座 + N个补丁"的多租户个性化服务架构。

▎核心原理

  • 共享底座常驻显存：在显存中只加载一套未微调的官方基座模型（如 Qwen2.5-7B-Instruct），所有租户共用底层算力
  • LoRA 热插拔：通过 --enable-lora 参数启动，在显存中开辟 Cache 区域，请求进来时微秒级将对应租户的 LoRA 矩阵与 Base 模型动态结合计算
  • OpenAI 兼容接口：前端或网关只需在标准 HTTP 请求体的 model 参数中指定 LoRA 名称，对业务层完全透明
  • 显存管理：通过 max_loras 和 max_lora_rank 控制显存中同时缓存的补丁数量和最大秩

▎深入解释

传统做法是为每个微调后的模型部署独立服务，服务器成本会瞬间拖垮 SaaS 公司。vLLM 的动态加载机制彻底改变了这一局面：LoRA 补丁通常只有几十 MB（大小取决于秩 r，r=16 大概几十 MB），而基座模型可能有十几 GB。多个租户共享同一个基座的显存开销，各自只额外占用几十 MB 的补丁空间，极大提升了显存利用率。

在实际生产中，启动命令 vllm serve Qwen/Qwen2.5-7B-Instruct --enable-lora --lora-modules tenant_A=/path/to/a tenant_B=/path/to/b 即可。当 A 租户请求进来，vLLM 自动检查该 LoRA 是否在显存中，不在则自动"热插拔"加载，无需重启服务。整个过程对调用方完全透明，业务代码无需任何修改。

这种机制使得"RAG 解决私有数据和动态知识 + LoRA 解决话术风格和 SOP 遵循"的黄金组合成为可能，是成本、性能与效果三者平衡的最佳实践。

▎面试加分点

  • 能解释 LoRA 补丁的物理结构：adapter_config.json（说明书）+ adapter_model.safetensors（权重肉身）+ 可选 README
  • 指出 vLLM 的显存缓存区管理策略——通过 max_loras 控制 LRU 淘汰，避免显存溢出
  • 提到 S-LoRA / LoRAX 作为更专业的多租户 LoRA 推理引擎，支持更大规模的租户路由

▎常见误区

  • 认为每个租户需要独立的 GPU 实例——实际上 vLLM 的动态加载让多个租户共享同一 GPU
  • 混淆 LoRA 训练和推理——vLLM 是推理框架，不负责训练，训练用 LLaMA-Factory / Unsloth

📌 概念题 · Q8

考点标签

Catastrophic Forgetting · 难度：⭐⭐⭐

📝 题目

请解释大模型微调中的"灾难性遗忘（Catastrophic Forgetting）"现象是什么？它为什么是全参数微调的核心劣势？LoRA/QLoRA 如何从机制上缓解这一问题？

💡 参考答案

▎一句话结论

灾难性遗忘是指大模型在学习新任务或新知识时，由于更新了全部参数权重，导致原本预训练阶段习得的通用能力和旧知识被严重覆盖和遗忘的现象，这是全参数微调相比 LoRA 最致命的工程劣势。

▎核心原理

  • 全参数微调的根源：更新模型所有参数，新数据的梯度会直接修改预训练权重，破坏原有知识分布
  • LoRA 的缓解机制：冻结大模型原本的权重，在旁边挂一个"低秩矩阵"（低维补丁插件），原模型参数完全不变，新知识只存在于补丁中
  • QLoRA 的进一步优化：将原模型量化为 4-bit 来压榨显存，同时保持冻结策略，补丁以更高精度训练
  • 不可完全避免：即使是 LoRA，如果补丁训练数据与原模型分布差异过大，仍可能出现一定程度的遗忘

▎深入解释

可以把大模型想象成一个经验丰富的通才。全参数微调就像强迫这个通才"重新洗脑"——用新数据覆盖他大脑里所有的神经连接，结果是他学会了新技能，但可能忘了怎么写代码、怎么做数学。这在企业场景中极其危险：你微调了一个医疗风格模型，结果发现它的通用推理能力下降了，或者它不再能正确调用 Function Calling 了。

LoRA 的巧妙之处在于"不碰原脑，外挂记忆模块"。原模型的几百亿参数完全冻结，新知识只写入一个几十 MB 的低秩矩阵。推理时，原模型权重与 LoRA 补丁做矩阵加法即可。这意味着如果你发现微调后模型能力退化，可以直接拔掉 LoRA 补丁回到原始状态，零风险回滚。

这也是为什么工业界共识是"能用 PEFT（高效参数微调）就绝不用全参数微调"——除非你需要彻底改变模型的底层认知或特定风格（如法律/医疗垂直大模型），否则 LoRA/QLoRA 是更安全、更经济、更可控的选择。

▎面试加分点

  • 能从矩阵分解角度解释 LoRA 为什么能缓解遗忘——低秩约束限制了补丁能修改的"方向"，不会大范围覆盖原权重
  • 提到回滚能力是 LoRA 相比全参数微调的隐藏优势——拔掉补丁即可恢复原模型
  • 指出 DPO/ORPO 等偏好对齐方法也可能引发遗忘，需要控制训练数据比例

▎常见误区

  • 认为 LoRA 完全不会遗忘——实际上如果补丁训练数据与原分布差异过大，仍可能出现局部遗忘
  • 把灾难性遗忘等同于"过拟合"——遗忘是旧知识被覆盖，过拟合是新数据上 memorize 而非 generalize

考点标签

LLaMA-Factory · 难度：⭐⭐⭐

📝 题目

请说明 LLaMA-Factory 在大模型微调工具链中的核心定位是什么？它与 Unsloth、DeepSpeed 的分工关系是怎样的？在企业级 SaaS 自动化微调流水线中扮演什么角色？

💡 参考答案

▎一句话结论

LLaMA-Factory 是当前工业界大模型微调工具链的事实标准，提供了从数据预处理到 LoRA/DPO/全参数微调的一站式 Web UI 和 CLI 能力，在 SaaS 自动化流水线中作为"微调 Worker"的核心执行引擎，配合 Unsloth 加速训练、DeepSpeed 实现多卡分布式。

▎核心原理

  • 统一工具链：支持 LoRA/QLoRA、全参数微调、DPO/ORPO 等多种微调范式，无需切换框架
  • 与 Unsloth 的分工：Unsloth 是底层加速库，将 LoRA 训练速度翻倍且省显存，LLaMA-Factory 可集成 Unsloth 作为后端
  • 与 DeepSpeed 的分工：DeepSpeed ZeRO-3 负责多卡并行（4~8卡 A100/H100 高速互联集群），LLaMA-Factory 负责上层训练流程编排
  • SaaS 流水线角色：用户触发微调后，任务进入消息队列（RabbitMQ/Kafka），后台 Worker 集群调用 LLaMA-Factory 脚本异步执行

▎深入解释

在企业的 SaaS 多租户微调架构中，微调往往是自动化的。用户在前端点击"开始训练"后，系统会将任务丢入消息队列。后台专门的"微调 Worker 集群"（配有高配显卡）异步拉取用户的私有数据，调用 LLaMA-Factory 脚本进行微调。训练完成后，将 .safetensors 适配器文件推送到对象存储（如阿里云 OSS / MinIO），并刷新推理引擎（如 vLLM）的路由表，实现零停机上线下发。

工具链的选型逻辑是：小规模尝试/垂直领域（1张 RTX 4090/5090）用 Unsloth + LLaMA-Factory，LoRA 速度翻倍且省显存；大模型中英双语、复杂逻辑微调（4~8卡 A100/H100）用 DeepSpeed ZeRO-3 + LLaMA-Factory，实现多卡数据并行。

LLaMA-Factory 的核心价值在于"统一入口"——无论你用哪种微调范式、哪种底层加速库，上层 API 和配置流程保持一致，极大降低了团队的工程切换成本。

▎面试加分点

  • 能描述完整的 SaaS 自动化微调流水线：用户触发→消息队列→Worker 异步拉取→LLaMA-Factory 训练→OSS 存储→路由表刷新→vLLM 热加载
  • 指出 Unsloth 和 DeepSpeed 不是竞争关系，而是 LLaMA-Factory 的可插拔后端
  • 提到训练沙箱的数据隔离——用户私有数据必须在独立的数据库/命名空间中

▎常见误区

  • 认为 LLaMA-Factory 只是"训练脚本"——实际上它是一个完整的微调生命周期管理工具，包含数据预处理、训练监控、模型评估
  • 把 LLaMA-Factory 和 vLLM 混为一谈——前者负责训练，后者负责推理，分工明确

📌 概念题 · Q10

考点标签

Lost in the Middle · 难度：⭐⭐⭐⭐

📝 题目

请解释大模型长上下文处理中的"Lost in the Middle（中间迷失）"现象是什么？它对 RAG 和 Agent 开发有什么实际影响？Hermes 3 等模型通过什么技术手段来缓解这一问题？

💡 参考答案

▎一句话结论

"Lost in the Middle"是指大模型在处理长上下文时，倾向于记住开头和结尾的信息，而忽略中间部分内容的现象，这直接导致 RAG 检索的中间切片被"视而不见"、Agent 长对话历史中的关键约束条件被遗漏，是长上下文场景下的核心工程瓶颈。

▎核心原理

  • 注意力分布不均：模型的自注意力机制在长序列中对首尾位置的 token 赋予更高权重，中间位置注意力衰减
  • 位置编码衰减：传统的绝对位置编码在距离较远时，位置信号区分度下降
  • RoPE（旋转位置编码）扩展：通过旋转矩阵的外推性，将上下文窗口从原生长度扩展到 128K 甚至更高，且保持相对位置感知
  • 注意力机制微调：在扩展上下文后进行专门的注意力微调，使模型在长序列中均匀关注各位置

▎深入解释

在实际的 RAG 场景中，"中间迷失"的影响非常具体：当你把检索到的 10 个文档切片塞给大模型时，排在第 4~7 位的切片被"看到"但没被"理解"的概率显著高于首尾切片。这意味着即使你的向量检索准确召回了相关内容，如果它恰好排在中间位置，模型也可能忽略它而给出错误回答。

在 Agent 开发中，问题更严重：长对话历史中，用户在第 5 轮说的关键约束条件（如"预算不超过 500 元"），到了第 15 轮可能被模型遗忘，导致 Agent 推荐了超出预算的方案。

Hermes 3 等模型通过两个手段缓解这一问题：一是基于 RoPE 将上下文扩展到 128K+，利用旋转位置编码的外推性保持长距离位置感知；二是在扩展后进行专门的注意力机制微调，使模型在长序列中能均匀关注各位置。其 Needle In A Haystack（大海捞针）测试几乎全绿，意味着在挂载知识库、调用大篇幅 API 文档或处理长对话历史时，不容易漏掉关键约束条件。

▎面试加分点

  • 能指出 RAG 中文档排序策略的重要性——将最相关的切片放在首尾位置，而非中间
  • 提到 Needle In A Haystack 测试是评估长上下文模型的标准 benchmark
  • 指出 FlashAttention 的分块计算策略从工程层面也帮助缓解了中间迷失——分块处理使每个 token 都能获得充分的注意力计算

▎常见误区

  • 认为"上下文窗口够长就行"——实际上窗口长度和注意力质量是两个维度，128K 窗口不等于 128K 全程有效关注
  • 把"中间迷失"等同于"记忆容量不足"——这不是容量问题，而是注意力分配不均的问题，即使总 token 数远未达到上限也可能发生

二、应用题（5 道 · 分类型）

🛠 应用题 · Q1 · 架构设计

题型

架构设计

场景标签

Agentic Auth LLM Gateway 安全沙箱 HITL 多租户隔离

📝 题目

你的公司正在构建一套企业级多 Agent 系统，包含三个核心智能体：Data Agent（需要现场编写 Python 脚本分析内部数据）、CRM Agent（需要调用企业内网 API 修改客户信息、触发退款）和 Knowledge Agent（需要检索多租户向量数据库）。系统将通过 MCP 协议连接企业内网的多个私有工具服务。请设计完整的 Agentic Auth 安全架构，涵盖网关层鉴权、安全沙箱隔离、人肉安全闸（HITL）三个核心层级，并说明各层如何协同工作以防止越权操作。

💡 参考答案

▎解题思路

  1. 梳理攻击面：首先明确三个 Agent 各自的风险边界——Data Agent 有代码执行风险（可能逃逸宿主机）、CRM Agent 有副作用操作风险（修改真实业务数据）、Knowledge Agent 有数据越权风险（跨租户读取）。同时，Agent 之间通过 MCP 协议互调时存在信任链断裂风险。
  2. 分层防御设计：按照「网关层 → 沙箱层 → HITL 层」由外到内构建三道防线，每一层解决不同维度的安全问题，形成纵深防御体系。
  3. 定义信任链流转协议：从真实用户发起请求到最终工具执行，设计一条不可伪造的授权凭证链路，确保每一步操作都可审计、可追溯。
  4. 区分查询与功能接口：对每个 Agent 调用的工具按「只读查询」和「有副作用操作」分类，分别走自动化和人工审批两条链路。

▎详细方案

第一层：基于身份标识与审计的网关层鉴权

在所有 Agent 与外部世界（大模型 API、MCP Server、第三方 SaaS）之间，部署一个统一的 LLM Gateway 作为唯一出入口：

用户请求 → API Gateway（JWT 验证）
              ↓
         LLM Gateway（统一鉴权 + 审计）
              ↓
    ┌─────────┼──────────┐
    ↓         ↓          ↓
 Data Agent  CRM Agent  Knowledge Agent
    ↓         ↓          ↓
  [沙箱]   [HITL拦截]  [Pre-filter注入]

核心规则：
- 禁止子 Agent 硬编码 API Key：所有密钥由 Gateway 统一托管，Agent 只能通过 Gateway 代理访问外部服务。
- Agent 身份证机制：每个上线的 Agent 节点在发起任何外部调用时，必须携带统一的身份标识头（如 X-Agent-ID: data-agent-001 和 X-MCP-Token: <动态签发>）。Gateway 校验该 Token 的合法性、有效期和权限范围。
- 信任链传递：当 Agent A 通过 MCP 协议调用 Agent B 时，A 必须在请求头中携带原始用户的授权上下文（X-User-ID、X-Tenant-ID、X-Auth-Scope），B 收到后必须验证该上下文是否在允许范围内，防止 Agent 被劫持后横向越权。
- 多租户数据隔离（Knowledge Agent 专属）：在 RAG 检索向量数据库时，Gateway 或业务代码层必须注入硬性标量预过滤。例如，将当前请求的 tenant_id、company_id 作为强制 WHERE 条件绑定在向量相似度检索之前：

# ❌ 危险写法：先向量检索再过滤，可能捞到其他租户的数据
results = qdrant.search(query_vector=emb, limit=10)
filtered = [r for r in results if r.payload["tenant_id"] == current_tenant_id]

# ✅ 安全写法：标量预过滤 + 向量检索，物理层面卡死越权空间
results = qdrant.search(
    query_vector=emb,
    query_filter=Filter(
        must=[
            FieldCondition(
                key="tenant_id",
                match=MatchValue(value=current_tenant_id)
            ),
            FieldCondition(
                key="department_id",
                match=MatchValue(value=current_dept_id)
            )
        ]
    ),
    limit=10
)

这样即使 Agent 被注入恶意 Prompt，也无法绕过 Gateway 注入的标量过滤条件去捞取其他租户的向量数据。

第二层：颗粒度极细的安全沙箱隔离（Data Agent 专属）

Data Agent 需要「现场编写 Python 脚本并执行」，这是整个系统最危险的入口。绝对不能直接给它宿主机权限，必须在 K8s 中利用轻量级安全容器技术，为每一次代码执行任务秒级创建绝对隔离、用完即毁的运行环境：

# K8s Pod 安全策略示例
apiVersion: v1
kind: Pod
metadata:
  name: agent-sandbox-<task-id>
  labels:
    app: agent-code-sandbox
spec:
  runtimeClassName: gvisor  # 使用 gVisor 提供内核级隔离
  containers:
  - name: python-executor
    image: e2b/code-sandbox:latest  # 或自建沙箱镜像
    resources:
      limits:
        cpu: "2"
        memory: "4Gi"
        ephemeral-storage: "10Gi"
      requests:
        cpu: "1"
        memory: "2Gi"
    securityContext:
      runAsNonRoot: true
      readOnlyRootFilesystem: true
      allowPrivilegeEscalation: false
      capabilities:
        drop: ["ALL"]
  ttlSecondsAfterFinished: 300  # 5分钟后自动清理
  networkPolicy:
    # 限制网络访问：只允许访问内网数据源，禁止外网

技术选型建议：
- gVisor：Google 开源的用户态内核，拦截系统调用，适合通用 Python 脚本执行场景。
- Kata Containers：基于轻量级 VM 的容器运行时，隔离更强但启动稍慢，适合需要更高安全级别的场景。
- E2B / Modal：专门的 Serverless 沙箱服务，秒级启动、免运维，适合团队没有 K8s 深度运维能力的场景。

每次 Data Agent 执行代码的流程：Gateway 接收代码 → K8s API 创建沙箱 Pod → 在沙箱内执行 → 采集 stdout/stderr → 销毁 Pod。整个过程对 Agent 透明，Agent 只看到一个「执行代码并返回结果」的 Tool 接口。

第三层：决定生死线的人肉安全闸（CRM Agent 专属）

CRM Agent 需要调用「修改客户信息」「触发真实退款」等带有副作用的操作。系统必须在代码层强行拦截，利用类似 LangGraph 的 interrupt_before 机制：

from langgraph.graph import StateGraph

# 定义工作流图
workflow = StateGraph(AgentState)

# 添加节点
workflow.add_node("retrieve_customer_info", retrieve_customer_info)
workflow.add_node("analyze_request", analyze_request)
workflow.add_node("execute_crm_action", execute_crm_action)  # 危险操作节点
workflow.add_node("generate_response", generate_response)

# 添加边
workflow.add_edge("retrieve_customer_info", "analyze_request")
workflow.add_edge("analyze_request", "execute_crm_action")
workflow.add_edge("execute_crm_action", "generate_response")

# ⚠️ 核心：在执行 CRM 操作前强制中断
workflow.add_conditional_edges(
    "analyze_request",
    lambda state: "interrupt" if state["requires_approval"] else "auto_execute",
    {
        "interrupt": "execute_crm_action",  # 会触发 interrupt_before
        "auto_execute": "execute_crm_action",
    }
)

# 编译时指定中断点
graph = workflow.compile(
    interrupt_before=["execute_crm_action"]  # 在此节点前暂停
)

中断后的处理流程：
1. LangGraph 将当前图的拓扑状态、会话 ID（thread_id）、待执行的操作详情打包，持久化到 PostgreSQL / Redis。
2. 释放线程资源（不占用 Worker），避免长时间挂起导致资源耗尽。
3. 前端界面弹窗展示操作详情（修改什么字段、退款金额多少），让真实人类员工点击「确认」或「拒绝」。
4. 用户确认后，携带原 thread_id 唤醒流程（Resume），LangGraph 从断点继续执行 execute_crm_action 节点。
5. 如果用户拒绝，流程终止并记录审计日志。

接口分类标准：

接口类型 示例 处理方式
只读查询 查天气、检索公开制度、查物流状态 允许自动化执行
敏感操作 修改价格、删除数据、同意审批、触发退款 强制 HITL 拦截

▎关键细节 & 踩坑点

  • Token 时效性：X-MCP-Token 必须设置短时效（如 5 分钟），防止 Token 泄露后被长期利用。Gateway 应实现 Token 的自动轮换机制。
  • 沙箱网络隔离：gVisor 默认不限制网络访问，必须配合 K8s NetworkPolicy 一起使用，否则恶意代码仍可通过网络外传数据。
  • HITL 超时处理：人工审批不能无限等待。必须设置超时时间（如 24 小时），超时后自动拒绝并通知发起人，避免持久化数据无限堆积。
  • 审计日志完整性：每一层都必须记录操作日志（谁、什么时间、通过哪个 Agent、调用了什么工具、参数是什么、结果是什么），日志写入不可篡改的存储（如阿里云 SLS + OSS 归档）。
  • Gateway 单点故障：LLM Gateway 是整个系统的咽喉，必须做高可用部署（至少 3 节点 + 负载均衡），否则 Gateway 宕机会导致所有 Agent 瘫痪。

▎可扩展优化

  • 引入 OPA（Open Policy Agent）：将权限策略从代码中抽离，用 Rego 语言声明式管理，实现策略热更新无需重启服务。
  • 基于风险评分的动态拦截：不是所有 CRM 操作都走 HITL，可以引入风险评分模型——修改一个收货地址（低风险）自动放行，触发 10 万元退款（高风险）强制拦截，减少人工审批负担。
  • MCP Server 注册中心：随着 MCP Server 数量增长，建立动态注册与发现机制，Agent 不再硬编码 MCP Server 地址，而是通过注册中心按需发现并建立连接，同时支持 Server 健康检查和自动故障转移。

LLM Wiki 传统RAG缺陷 知识管理 Karpathy Obsidian

📝 题目

你的企业研究院拥有数千份行业研报、技术白皮书和内部会议记录，当前使用传统 RAG 系统供研究员检索。但用户反馈三大痛点：① 跨文档的概念关联回答不上来（如「A 报告提到的技术趋势与 B 报告的市场预测之间有什么联系」）；② 回答肤浅割裂，缺乏深度提炼；③ 每次检索都像「临时抱佛脚」，没有知识沉淀。团队正在评估引入 Karpathy 提出的 LLM Wiki 模式。请对比两种方案的核心差异，并给出从传统 RAG 迁移到 LLM Wiki 的完整策略和分阶段落地路径。

💡 参考答案

▎解题思路

  1. 诊断根因：用户反馈的三个痛点本质上是传统 RAG 的架构缺陷——它是「查询时检索」模式，每次从零开始线性检索文档切片，无法在录入阶段建立跨文档的实体关联和概念网络。
  2. 对比方案差异：从知识沉淀时机、思考深度、交互界面三个维度对比传统 RAG 与 LLM Wiki，明确 LLM Wiki 的核心优势在于「录入即思考」。
  3. 设计迁移策略：不能一刀切替换，需要设计「双轨并行 → 逐步迁移 → 最终替代」的分阶段路径，确保业务连续性。
  4. 规划落地架构：基于 LLM Wiki 的三层核心架构（Immutable Sources / Wiki / Schema），设计具体的技术实现方案。

▎详细方案

一、核心差异对比分析

对比维度 传统 RAG 系统 LLM Wiki 模式
知识沉淀时机 查询时临时检索，不改变原始数据 录入时即由 LLM 主动提取实体、概念、论点并写入持久化 Wiki
跨文档关联 靠向量相似度「盲捞」切片，语义截断严重 LLM 在录入时即完成跨文献的结构化与概念级融会贯通
知识网络 无，每次检索都是独立的线性过程 自动生成双向链接 [[]]，形成知识图谱
模型负担 查询时模型负担重（要同时理解问题 + 拼接切片 + 生成答案） 录入时异步处理，查询时直接检索已结构化的 Wiki 页面
交互界面 Web 端无状态 Chatbox 终端或轻量 IDE（Claude Code / Cursor），代码级插拔
知识盲区发现 无此能力 可通过图算法（如 Louvain 算法）自动发现知识聚类和盲区

传统 RAG 的核心缺陷可以用一个比喻说明：它像一个「每次考试前才翻书的学生」，不记笔记、不做总结，每次提问都从原始文档里临时捞几页，遇到需要综合多份资料的问题时自然力不从心。

LLM Wiki 的核心解法是「录入即思考」：当你把新研报喂给系统时，LLM 像一个永不疲倦的学者，主动提取其中的核心实体（公司名、技术术语）、关键概念（行业趋势、技术原理）、论点交锋（不同报告对同一话题的不同看法），并把它们写入一个持久化的、用 Markdown 双向链接相互引用的「维基百科」。

二、LLM Wiki 三层核心架构设计

┌─────────────────────────────────────────────┐
│         The Schema（约束规范层）               │
│   CLAUDE.md / AGENTS.md                      │
│   - 行为准则：LLM 维护 Wiki 的规则             │
│   - 模板规范：YAML Frontmatter + [[]] 双链    │
│   - 自我纠错：Lint 机制检查格式一致性           │
└──────────────────┬──────────────────────────┘
                   │ 约束
┌──────────────────▼──────────────────────────┐
│         The Wiki（维基层）                    │
│   - Source Notes：源文档摘要、Claim、页码      │
│   - Concept Pages：核心概念页面               │
│   - Author/Debate Pages：观点交锋大纲          │
│   （LLM 完全拥有并动态维护的 Markdown 目录）    │
└──────────────────┬──────────────────────────┘
                   │ 引用
┌──────────────────▼──────────────────────────┐
│     Immutable Sources（不变量源码层）          │
│   原始 PDF、研报、会议记录（只读，不可修改）     │
└─────────────────────────────────────────────┘

第一层：Immutable Sources（不变量源码层）

所有原始文档（PDF 研报、Word 会议记录、Slack 聊天记录等）存入只读存储（如 MinIO / OSS），LLM 绝不修改这一层，作为最后的事实依据。当 Wiki 中的概念页面与原始文档产生矛盾时，以源文档为准。

第二层：The Wiki（维基层）

这是 LLM 完全拥有并动态维护的 Markdown 文件目录，包含三类页面：

  • Source Notes：针对每一份源文档自动生成的摘要页面，包含关键 Claim、直接引述、页码引用。例如 [[2026-Q1-新能源研报-摘要]]。
  • Concept Pages：提取的核心概念页面，如 [[固态电池技术]]、[[碳交易市场]]。这些页面会自动聚合所有提及该概念的源文档片段，形成跨文献的知识汇总。
  • Author/Debate Pages：提取的核心人物页面或观点交锋大纲，如 [[宁德时代-vs-比亚迪-技术路线之争]]，自动汇总不同报告中对同一话题的不同论点。

所有页面强制使用 [[双括号]] 建立双向链接，形成知识网络。

第三层：The Schema（约束规范层）

通过一个名为 CLAUDE.md 的核心提示词配置文件，严格规定 LLM 维护 Wiki 的行为准则：

# CLAUDE.md - LLM Wiki 维护规范

## 行为准则
1. 每次录入新文档时，必须生成 Source Note，并提取至少 3 个 Concept Pages
2. 所有概念页面必须使用 [[双括号]] 引用相关概念
3. 每条 Claim 必须标注来源文档名和页码
4. 发现与已有 Wiki 内容矛盾时，不得删除旧内容，必须在 Debate Page 中记录交锋

## 模板规范
- 每个页面必须包含 YAML Frontmatter（元数据）
- 必须包含 `tags`、`source`、`created`、`last_updated` 字段
- 概念页面必须包含「定义」「核心论点」「关联概念」三个章节

## 自我纠错（Lint 机制）
- 检查所有 [[]] 链接是否有对应的目标页面，无则创建 Stub
- 检查是否有孤立页面（无任何反向链接），标记为「待补充」
- 检查 Frontmatter 格式是否合规

三、分阶段迁移路径

阶段一：双轨并行（第 1-2 个月）

保留现有 RAG 系统不变，同时在旁路搭建 LLM Wiki 基础设施：
- 部署 LLM Wiki 引擎（可基于开源的 llm_wiki 仓库或 Obsidian + Karpathy LLM Wiki 插件）。
- 将历史文档批量灌入，让 LLM 异步生成 Source Notes 和 Concept Pages。
- 研究员可以同时使用两套系统，对比检索效果。

阶段二：增量录入（第 3-4 个月）

新文档进入时，同时走两条链路：
- 传统 RAG：切片 → 向量化 → 存入 Qdrant（保持现有检索能力）。
- LLM Wiki：LLM 录入时提取实体和概念 → 写入 Wiki Markdown 目录 → 建立双向链接。
- 在传统 RAG 的检索结果中，增加一个「Wiki 关联推荐」模块，将 LLM Wiki 中相关的 Concept Pages 一并展示，让用户逐步习惯 Wiki 的知识结构。

阶段三：查询层切换（第 5-6 个月）

当 LLM Wiki 积累了足够多的 Concept Pages 后，将查询入口从「向量检索原始文档」切换为「检索 Wiki 概念页面」：
- 用户提问 → 先在 Wiki 中检索最相关的 Concept Page → 如果 Concept Page 已包含答案，直接返回；如果需要更细节的信息，再通过 Concept Page 中的 Source 引用回溯到原始文档。
- 利用图算法（如 Louvain 算法）自动发现知识聚类和知识盲区，主动提示研究员「哪些领域还缺少文档覆盖」。

▎关键细节 & 踩坑点

  • LLM 录入质量：LLM Wiki 的效果完全取决于录入阶段 LLM 的提取质量。建议使用 Claude 3.5 Sonnet 或 GPT-4o 等强模型做录入处理，不要用小模型，否则提取的概念会不准确、双向链接会混乱。
  • 增量维护一致性：当新文档与已有 Wiki 内容矛盾时，LLM 容易直接覆盖旧内容。必须在 CLAUDE.md 中强制规定「不得删除旧内容，必须记录交锋」，否则会丢失历史观点。
  • 成本控制：每份文档录入时 LLM 要做多轮提取（Source Note → Concept Pages → 双向链接维护），Token 消耗远高于传统 RAG 的切片。建议对文档做优先级分级，核心研报走全量 LLM Wiki 流程，普通文档只做 Source Note。
  • Obsidian 集成：如果团队已经在用 Obsidian，可以直接使用 Karpathy LLM Wiki 插件，AI 会自动在 Graph View 上长出概念实体和双向链接，无需额外搭建前端。

▎可扩展优化

  • 知识盲区可视化：利用 sigma.js 渲染知识拓扑图，用不同颜色标注「知识密集区」「知识稀疏区」「完全空白区」，帮助研究院领导做选题决策。
  • 与 Agent 系统打通：将 LLM Wiki 作为 Agent 的长期记忆层——Agent 在回答用户问题时，优先检索 Wiki 中已结构化的 Concept Pages，而非每次都从原始文档检索，大幅提升回答深度和一致性。
  • 多语言 Wiki 同步：对于跨国企业，可以维护多语言版本的 Concept Pages，LLM 在录入时自动生成对应语言的翻译版本并保持双向链接同步。

你需要基于阿里云百炼平台，为一家法律科技公司搭建文档检索 RAG 系统。系统需要处理两类文档：① 纯文本法律法规和 OCR 后的合同文本（占总数据量 85%）；② 包含流程图、架构图的图文混合文档（占 15%）。请给出完整的模型选型依据、两阶段检索链路的代码实现（Embedding + Rerank），以及从纯文本阶段演进到多模态阶段的分阶段上线方案。

▎解题思路

  1. 分析数据分布：85% 是纯文本，15% 是图文混合。按照「先用文本链路跑通大部分场景，再逐步扩展多模态」的策略，避免一开始就全部切到多模态带来的成本和复杂度暴增。
  2. 模型选型：根据阿里云百炼官方文档的推荐，纯文本场景用 text-embedding-v4 + qwen3-rerank，图文混合场景用 qwen3-vl-embedding + qwen3-vl-rerank，跨模态搜索用 tongyi-embedding-vision-plus。
  3. 设计两阶段链路：第一阶段（Embedding 召回）用向量模型从海量文档中召回 Top-50 候选；第二阶段用 Rerank 模型对候选精排取 Top-5。
  4. 分阶段上线：先上纯文本链路验证业务价值，再增量加入多模态检索能力。

▎详细方案

一、模型选型依据

场景 Embedding 模型 Rerank 模型 选型理由
纯文本/表格/OCR 后文档 text-embedding-v4 qwen3-rerank 速度更快、成本更低、维度选择更多
图文混合检索（文档中图片也要被搜到） qwen3-vl-embedding qwen3-vl-rerank 支持图片+文本联合向量化
文搜图/图搜图跨模态搜索 tongyi-embedding-vision-plus qwen3-vl-rerank 专门优化跨模态匹配

核心原则：图片只是「文档里存在」不等于必须多模态。如果图片里的信息能 OCR 成文字，先走文本链路通常更划算。 只有当图片本身承载了不可替代的语义信息（如流程图中的节点关系、架构图中的系统拓扑），才需要走多模态链路。

二、第一阶段：纯文本 RAG 链路实现

import dashscope
from dashscope import TextEmbedding, TextReRank
import uuid

# ============ 配置 ============
EMBEDDING_MODEL = "text-embedding-v4"
RERANK_MODEL = "qwen3-rerank"
COLLECTION_NAME = "legal_docs_text"

# ============ 1. 文档入库：Embedding 生成 ============
def embed_documents(documents: list[dict]) -> list[dict]:
    """
    将法律文档列表向量化并存入向量库
    documents: [{"id": "doc_001", "text": "合同法第十三条...", "metadata": {...}}]
    """
    points = []
    for doc in documents:
        # 调用百炼 text-embedding-v4 生成向量
        resp = TextEmbedding.call(
            model=EMBEDDING_MODEL,
            input=doc["text"],
            dimension=1024,  # v4 支持多种维度选择，1024 是性价比最优选
            output_type="dense"  # 输出稠密向量
        )

        if resp.status_code != 200:
            raise Exception(f"Embedding 失败: {resp.message}")

        vector = resp.output["embeddings"][0]["embedding"]

        points.append({
            "id": doc["id"],
            "vector": vector,
            "payload": {
                "text": doc["text"],
                "title": doc.get("title", ""),
                "doc_type": doc.get("doc_type", ""),  # 法律法规/合同/判决书
                "tenant_id": doc.get("tenant_id", ""),
                "page_num": doc.get("page_num", 0),
                "source_file": doc.get("source_file", "")
            }
        })

    # 批量写入 Qdrant 向量库
    qdrant_client.upsert(
        collection_name=COLLECTION_NAME,
        points=points
    )
    return points


# ============ 2. 检索链路：Embedding 召回 + Rerank 精排 ============
def retrieve_legal_docs(
    query: str,
    tenant_id: str,
    top_k_recall: int = 50,
    top_k_final: int = 5
) -> list[dict]:
    """
    两阶段检索：向量召回 Top-50 → Rerank 精排 Top-5
    """
    # ---- 第一阶段：Embedding 向量召回 ----
    query_resp = TextEmbedding.call(
        model=EMBEDDING_MODEL,
        input=query,
        dimension=1024,
        output_type="dense"
    )
    query_vector = query_resp.output["embeddings"][0]["embedding"]

    # 在 Qdrant 中做标量预过滤 + 向量检索（多租户隔离）
    search_results = qdrant_client.search(
        collection_name=COLLECTION_NAME,
        query_vector=query_vector,
        query_filter=Filter(
            must=[
                FieldCondition(
                    key="tenant_id",
                    match=MatchValue(value=tenant_id)  # 硬性租户隔离
                )
            ]
        ),
        limit=top_k_recall  # 召回 50 条
    )

    candidates = [
        {
            "id": hit.id,
            "text": hit.payload["text"],
            "title": hit.payload["title"],
            "score": hit.score,
            "source_file": hit.payload["source_file"]
        }
        for hit in search_results
    ]

    if not candidates:
        return []

    # ---- 第二阶段：qwen3-rerank 精排 ----
    rerank_resp = TextReRank.call(
        model=RERANK_MODEL,
        query=query,
        documents=[c["text"] for c in candidates],
        top_n=top_k_final,  # 只取最相关的 5 条
        return_documents=False  # 只返回分数和索引，不重复返回文本
    )

    # 将 Rerank 结果与原始候选映射
    final_results = []
    for item in rerank_resp.output["results"]:
        idx = item["index"]
        final_results.append({
            **candidates[idx],
            "rerank_score": item["relevance_score"],
            "original_score": candidates[idx]["score"]
        })

    return final_results


# ============ 3. 调用示例 ============
results = retrieve_legal_docs(
    query="劳动合同解除后竞业限制条款的效力如何认定？",
    tenant_id="law_firm_001",
    top_k_recall=50,
    top_k_final=5
)

for r in results:
    print(f"[{r['rerank_score']:.4f}] {r['title']} | 来源: {r['source_file']}")
    print(f"  内容: {r['text'][:100]}...")

from dashscope import MultiModalEmbedding

# ============ 多模态文档入库 ============
def embed_multimodal_documents(documents: list[dict]) -> list[dict]:
    """
    对包含图片的文档生成多模态向量
    documents: [{"id": "doc_001", "text": "系统架构说明...", "image_url": "oss://..."}]

    points = []
    for doc in documents:

    )

# ============ 多模态检索 ============
def retrieve_multimodal_docs(query: str, tenant_id: str, top_k: int = 5):
    """文搜图文：用文本 query 检索图文混合文档"""
    # 文本转向量（用多模态 Embedding 模型）
    resp = MultiModalEmbedding.call(
        model="qwen3-vl-embedding",
        input={"contents": [{"text": query}]},
        dimension=1024
    )
    query_vector = resp.output["embeddings"][0]["embedding"]

    # 检索多模态 Collection
    results = qdrant_client.search(
        collection_name="legal_docs_multimodal",
        query_vector=query_vector,
        query_filter=Filter(must=[
            FieldCondition(key="tenant_id", match=MatchValue(value=tenant_id))
        ]),
        limit=20
    )

    # 多模态 Rerank
    rerank_resp = TextReRank.call(
        model="qwen3-vl-rerank",
        query=query,
        documents=[r.payload["text"] for r in results],
        top_n=top_k
    )

    return rerank_resp.output["results"]

▎关键细节 & 踩坑点

  • 不要一开始就全部切到多模态：图片只是「文档里存在」不等于必须多模态。如果图片里的信息能 OCR 成文字（如合同扫描件），先走文本链路通常更划算——速度更快、成本更低、维度选择更多。
  • 维度选择：text-embedding-v4 支持多种维度输出（如 512/1024/2048），1024 是性价比最优选择。维度越高检索精度越好但存储和计算成本也越高，需要根据实际数据量做 A/B 测试。
  • Rerank 的输入长度限制：qwen3-rerank 对单条文档的输入长度有上限（通常 512 Token），超长的文档切片需要在 Rerank 前截断，否则会报错或效果下降。
  • 多模态 Collection 分离：纯文本和多模态向量应该存在不同的 Collection 中，因为它们的向量空间不同（一个是纯文本 Embedding，一个是图文联合 Embedding），混在一起检索会导致相似度计算不准确。
  • OSS 图片访问权限：多模态 Embedding 需要传入图片 URL，确保该 URL 是百炼服务可访问的（如果用私有 OSS，需要生成临时签名 URL）。

▎可扩展优化

  • 混合检索（Hybrid Search）：在向量召回阶段，同时做 BM25 关键词检索和向量检索，用 RRF（Reciprocal Rank Fusion）融合两路结果后再送入 Rerank，对法律术语等精确匹配场景效果更好。
  • 缓存 Rerank 结果：对于高频查询，可以将 Rerank 后的 Top-5 结果缓存到 Redis（key 为 query 的 hash），TTL 设为 1 小时，大幅降低 Rerank API 调用成本。
  • 文档切片策略优化：法律文档有严格的条款结构（第X条第X款），建议按条款粒度切片而非固定长度切片，并在 payload 中保存条款编号，便于 Rerank 后的法律引用溯源。
