AI Agent 面试知识库 · 概念型面试题 10 连击

考点标签

Agentic RAG · 难度：⭐⭐⭐

📝 题目

知识库中强调 Agentic RAG 的核心是“把硬编码的死板检索，变成给大模型一个工具箱”。但在实际工程中，很多团队发现：给 Agent 注册了 20 个工具后，模型开始频繁“选错工具”或“反复调用同一个工具却不终止”。请从架构设计的角度分析：为什么工具数量增多会导致 Agent 决策质量下降？在设计工具注册（Tool Registration）时，应该遵循哪些工程原则来缓解这个问题？

💡 参考答案

▎一句话结论

工具注册的本质是“压缩决策空间”——工具越多，模型在每个推理步骤中需要消化的 Description 和 Schema 信息量就越大，决策精度必然下降；工程上必须通过“工具收敛、描述精炼、分层路由”来主动压缩这个空间。

▎核心原理

  • 注意力稀释效应：所有工具描述都会进入 System Prompt 或上下文，工具数量从 5 个涨到 20 个时，模型对单个工具描述的“注意力权重”被摊薄，容易混淆语义相近的工具（如 search_knowledge_base 和 query_vector_db）。
  • 决策链长度爆炸：Agentic RAG 本身就有“思考→选工具→执行→反思”的循环，每多一个工具，模型在每个循环节点的“可行动作集合”就扩大一次，错误路径的组合数呈指数级增长。
  • Description 的模糊地带：当两个工具的 Description 存在语义重叠（比如“检索文档”和“搜索知识库”），模型无法稳定区分适用边界，会随机选择或反复横跳。
  • 终止条件不明确：模型不知道“什么情况下不需要调用工具”，导致它倾向于“先调一个看看”，即使问题本身可以直接回答。

▎深入解释

可以类比一个人类新员工入职的场景。如果你给新员工一本包含 20 个内部系统的操作手册，却不告诉他“什么场景用哪个系统”，他遇到每个任务都会翻手册、试系统，效率极低。但如果给他 3 个核心系统，并且明确告诉他：“查规章制度用 A 系统，查实时数据用 B 系统，查历史报表用 C 系统，其他情况直接回答”，他的决策速度和准确率会大幅提升。

在 Agentic RAG 中，工具 Description 就是“操作手册”。工程上有一个重要原则：每个工具的 Description 必须包含“何时用”和“何时不用”。比如：

“当且仅当用户询问企业内部规章制度、操作流程、HR 政策时使用此工具。如果用户询问实时天气、股票行情或通用知识，请勿使用此工具。”

这种“反例引导”比只写“用于检索企业内部知识”有效得多。

另一个关键工程手段是 工具分组 + 动态路由。不要把所有 20 个工具一次性全部暴露给模型，而是在第一层用一个“意图分类器”（可以是轻量级 LLM 调用或规则引擎）把用户请求路由到某个工具子集，再让 Agent 在子集内做精细决策。比如：查询类请求只暴露 3 个检索工具，操作类请求只暴露 2 个执行工具。这样每个决策节点的候选工具数从 20 降到 3-5，决策精度显著提升。

▎面试加分点

  • 能提到“工具 Description 需要包含正例和反例”，展现对 Prompt 工程在工具调用场景的深度理解。
  • 能提出“分层工具路由”或“工具分组 + 子 Agent”的架构方案，体现系统化思维。
  • 能指出“工具数量与模型上下文窗口的隐性竞争关系”——工具描述占用的 Token 越多，留给历史对话和检索结果的 Token 就越少。

▎常见误区

  • 认为“工具越多，Agent 能力越强”。实际上工具数量超过模型处理阈值后，能力不升反降。
  • 认为“只要 Description 写清楚就行”。实际上语义重叠的 Description 即使各自清晰，模型仍会混淆。
  • 认为“模型选错工具是模型能力问题”。实际上往往是工具设计问题——Description 缺乏边界条件、工具粒度不一致（一个工具做太多事，另一个工具做太少事）。

考点标签

结构化输出 · 难度：⭐⭐⭐

📝 题目

知识库中给出了大模型稳定输出 JSON 的“四层防御体系”：Prompt 软约束 → API 原生约束 → 约束解码 → 后处理兜底。但在 Agent 工作流中，一个节点可能生成 JSON 后被下游节点直接消费，如果 JSON 解析失败，整个工作流就会中断。请问：在 Agent 架构中，应该在哪一层做 JSON 校验最合理？为什么不能把校验全部放在“后处理兜底层”？

💡 参考答案

▎一句话结论

在 Agent 工作流中，JSON 校验必须“前置到节点内部”而不是“后置在工作流末尾”——每个产生结构化输出的节点都应该自带 Schema 校验 + 自动重试闭环，否则一个节点的失败会通过 DAG 依赖关系级联放大，导致整个工作流不可恢复。

▎核心原理

  • 失败成本随节点深度递增：在 DAG 编排中，如果节点 A 的输出 JSON 格式错误，节点 B、C 都依赖 A 的输出，那么 A 的失败会导致 B、C 全部失败，且这些失败发生在工作流执行的中途，已经消耗了大量 Token 和时间。
  • 重试的局部性原理：在节点内部做校验，重试只发生在“出错的节点”，其他已完成的节点不需要重新执行。如果等到工作流末尾再校验，重试需要从出错节点开始重跑整个下游链路。
  • Schema 即契约：Agent 节点之间的数据传递本质上是“契约式编程”。节点 A 的输出 Schema 就是节点 B 的输入契约，契约校验必须发生在“交货时”（节点 A 完成时），而不是“收货后”（节点 B 使用时）。
  • Self-Correction 的闭环设计：节点内部校验失败后，可以把错误信息（Pydantic ValidationError）作为上下文回传给 LLM，让它“看到自己的错误并修正”，这比在工作流层面重新调度要高效得多。

▎深入解释

可以类比工厂流水线。假设流水线有 5 个工位，工位 1 生产零件，工位 2 组装，工位 3 喷漆，工位 4 质检，工位 5 包装。如果你把质检全部放在工位 4，那么工位 1 生产的次品会一路流到工位 4 才被发现，此时工位 2 和 3 已经在次品上浪费了工时。更糟糕的是，如果次品在工位 2 导致了设备故障，整个流水线都要停。

正确的做法是“每个工位自检”：工位 1 完成后立刻检查零件是否合格，不合格当场返工。这就是 Agent 节点内部 JSON 校验的逻辑。

在 LangGraph 中，这个模式通常实现为：

Node A: call_llm() → extract_json() → validate_with_pydantic()
         ↓ 失败
         retry: call_llm(error_message) → extract_json() → validate()
         ↓ 成功
         输出结构化对象给 Node B

关键点在于：重试循环是节点内部的局部逻辑，不涉及 Checkpoint 回滚或工作流重新调度。这比在工作流层面捕获异常、回滚状态、重新执行要简单得多。

▎面试加分点

  • 能提出“每个节点自带 Pydantic 校验 + 自动重试（最多 2-3 次）”的设计模式，展现工程化思维。
  • 能指出“节点间传递的是 Pydantic 对象而不是原始 JSON 字符串”，从类型系统层面保证下游安全。
  • 能区分“格式校验”（JSON 是否合法）和“语义校验”（字段值是否符合业务规则），并说明两者应该在不同层做。

▎常见误区

  • 认为“后处理兜底层”能解决所有 JSON 问题。实际上兜底层只能保证“不崩溃”，无法保证“下游节点能正确消费”。
  • 认为“只要用了 response_format 就不需要校验”。API 原生约束只能保证 JSON 合法，不能保证字段类型、枚举值、必填项完全符合业务 Schema。
  • 认为“校验失败就重试，重试次数越多越好”。实际上重试会消耗大量 Token，应该设置上限（通常 2-3 次），超过后走降级路径（如返回默认值或抛人工介入信号）。

考点标签

KV Cache · 难度：⭐⭐⭐

📝 题目

知识库中提到 KV Cache 的本质是“用空间换时间”，并指出在长文本对话中，KV Cache 占用的显存甚至可能超过模型权重本身。请问：为什么 KV Cache 的显存占用会随着“并发量（Batch Size）”线性增长？在多用户同时请求一个 Agent 服务时，这种增长对 GPU 资源调度意味着什么？为什么说“Context Cache（上下文缓存）”在 Agent 多轮对话场景下比在单轮问答场景下更有价值？

💡 参考答案

▎一句话结论

KV Cache 的显存占用与 Batch Size 成正比，因为每个请求序列都有独立的一套 K/V 矩阵；在 Agent 多轮对话中，Context Cache 的价值被放大，是因为 Agent 的 System Prompt + 工具描述 + 历史对话形成了大量“可复用的公共前缀”，缓存命中率远高于单轮问答。

▎核心原理

  • KV Cache 的独立性：每个请求序列（Sequence）在推理时都会生成自己的 K 和 V 矩阵。Batch Size = 8 意味着 GPU 上同时有 8 个序列在推理，每个序列都需要独立的 KV Cache 空间。显存占用 = 单序列 KV Cache × Batch Size。
  • Agent 场景的上下文膨胀：Agent 的每次 LLM 调用都包含 System Prompt（角色设定 + 工具描述 + 输出格式要求）+ 历史对话 + 工具执行结果。这些内容在多次调用中高度重复，形成了大量“公共前缀”。
  • Context Cache 的命中机制：当多个请求共享相同的公共前缀（比如同一个 Agent 的 System Prompt），推理框架可以只计算一次该前缀的 KV Cache，后续请求直接复用。在 Agent 场景中，同一个用户的多轮对话、甚至不同用户使用同一个 Agent 模板时，前缀命中率极高。
  • 成本的三重节省：缓存命中后，① 不需要重新计算前缀的注意力（速度提升）；② 不需要重新存储前缀的 KV Cache（显存节省）；③ API 服务商可以对命中缓存的前缀 Token 少收费（成本降低）。

▎深入解释

可以类比餐厅点餐。单轮问答就像每个顾客进来点一道完全不同的菜，厨师每次都要从零开始准备食材。Agent 多轮对话则像同一个顾客分多次点餐，每次都点“套餐 A + 额外加一份 X”。如果餐厅把套餐 A 的食材提前备好（缓存），每次只需要准备“额外加的那份 X”，出餐速度大幅提升。

在技术层面，Agent 的 System Prompt 通常非常长（包含角色设定、工具列表、工具 Description、输出格式要求、Few-Shot 示例等），可能占 2000-5000 Token。在多轮对话中，这部分内容在每一轮 LLM 调用中都是完全相同的。如果不做 Context Cache，每轮调用都要重新计算这 5000 Token 的注意力，浪费大量 GPU 算力。有了 Context Cache，这 5000 Token 的 KV Cache 只计算一次，后续轮次直接复用。

更关键的是，在 多用户并发场景 下，如果所有用户都使用同一个 Agent 模板（比如同一个 HR 智能客服），那么 System Prompt 对所有用户都是相同的。这意味着 Context Cache 可以在用户之间共享，命中率从“单用户多轮”扩展到“跨用户共享”，价值进一步放大。

▎面试加分点

  • 能指出 Agent 场景下 Context Cache 的“跨用户共享”特性，比单纯说“多轮对话命中缓存”更有深度。
  • 能提到“工具描述和 Few-Shot 示例是公共前缀的重要组成部分”，展现对 Agent Prompt 结构的理解。
  • 能区分“Prompt Cache”（API 服务商层面）和“PagedAttention”（推理框架层面）的不同层次。

▎常见误区

  • 认为“Context Cache 只对同一个用户的多轮对话有效”。实际上跨用户共享同一 Agent 模板时，缓存价值更大。
  • 认为“KV Cache 的显存增长只与上下文长度有关”。实际上 Batch Size 是另一个独立的线性增长维度。
  • 认为“缓存命中后就不需要显存了”。实际上缓存本身也需要占用显存，只是在“重复计算”和“重复存储”之间做了权衡。

考点标签

PostgreSQL · 难度：⭐⭐⭐

📝 题目

知识库中强调 PostgreSQL 在 Agent 架构中可以同时扮演“向量数据库 + 状态机 + 记忆中心”的复合角色，并特别提到 JSONB 配合 GIN 索引可以对 JSON 内部嵌套字段进行毫秒级筛选。请问：在 Agent 状态持久化场景中，为什么选择 JSONB 而不是 JSON 或传统的关系型列（如 state_step、state_value 分开建列）？JSONB 的 GIN 索引在什么情况下会失效或性能下降？

💡 参考答案

▎一句话结论

JSONB 在 Agent 状态存储中的核心优势是“结构灵活性 + 查询高性能”的平衡——它允许状态 Schema 随 Agent 迭代快速演进，同时通过二进制存储和 GIN 索引保持对嵌套字段的高效检索；但 GIN 索引并非万能，在“高频更新”和“低选择性过滤”场景下会显著退化。

▎核心原理

  • JSON vs JSONB 的本质区别：JSON 是纯文本存储，每次读取都要完整解析，不支持索引；JSONB 是解析后的二进制格式，读取时无需重新解析，支持 GIN 索引。写入时 JSONB 有少量解析开销，但在 Agent 场景中“读多写少”的特征下，这个权衡是划算的。
  • JSONB vs 传统关系型列：Agent 状态结构多变（不同 Agent 有不同的 State 字段，同一个 Agent 在不同版本也可能增减字段），传统关系型列需要 ALTER TABLE 来适应变化，JSONB 则天然支持动态 Schema。但 JSONB 牺牲了关系型数据库的类型强约束和列级统计信息。
  • GIN 索引的工作原理：GIN（Generalized Inverted Index）为 JSONB 中的每个键和值建立倒排索引。当查询 WHERE state->>'current_step' = 'retrieval' 时，GIN 索引可以直接定位包含该键值对的文档，而不需要全表扫描。
  • GIN 索引的退化场景：① 高频 UPDATE——每次更新 JSONB 字段都会触发 GIN 索引的重建，写入放大严重；② 低选择性过滤——如果某个键值对出现在 80% 的行中，GIN 索引的过滤效果很差，不如全表扫描；③ 深度嵌套查询——GIN 索引对深层嵌套路径（如 state->'nested'->'deep'->>'value'）的支持不如浅层键值对高效。

▎深入解释

可以类比图书馆的索引卡片。JSON 就像把所有书的内容原样堆在一起，每次找一本书都要从头翻到尾。JSONB 就像给每本书做了分类标签和索引卡片，找书时先查卡片，再定位到书架位置。传统关系型列就像把每本书的内容拆成固定的几个字段（书名、作者、分类），每个字段单独建索引——查询很快，但如果有一天要增加“ISBN 号”这个字段，所有书都要重新整理。

Agent 状态存储的痛点在于：状态结构是“半结构化”的。LangGraph 的 State 可能包含 messages（对话历史列表）、current_step（当前步骤）、retrieved_docs（检索到的文档列表）、tool_results（工具执行结果）等字段。这些字段在不同 Agent 之间差异很大，在同一个 Agent 的不同版本之间也可能增减。如果用传统关系型列，每次迭代都要做数据库迁移；如果用 JSON 纯文本，每次读取都要完整解析，性能不可接受。JSONB 恰好提供了“动态 Schema + 高效查询”的平衡点。

关于 GIN 索引的退化，一个常见的工程陷阱是：在 LangGraph 的 Checkpoint 表中，如果每次节点执行都更新同一个 JSONB 字段（比如 state 字段），GIN 索引会频繁重建，导致写入延迟显著上升。解决方案是：对于高频更新的状态字段，不建 GIN 索引，只在需要精确查询的字段（如 user_id、session_id）上建 B-Tree 索引；对于需要 JSONB 内部字段查询的场景，考虑使用“部分索引”或“表达式索引”来缩小索引范围。

▎面试加分点

  • 能指出“JSONB 写入开销”和“GIN 索引写入放大”的区别——前者是 JSONB 本身的解析开销，后者是索引维护的开销。
  • 能提出“对高频更新的 JSONB 字段不建 GIN 索引，对低频查询字段建部分索引”的精细化策略。
  • 能结合 LangGraph Checkpointer 的实际场景，说明 JSONB 在状态持久化中的具体应用。

▎常见误区

  • 认为“JSONB 一定比 JSON 好”。在“只写不查”或“写入极高频”的场景下，JSON 的写入性能更好。
  • 认为“GIN 索引建了就一定生效”。如果查询条件的选择性太低（比如过滤出 90% 的行），查询优化器可能选择全表扫描。
  • 认为“JSONB 可以完全替代关系型列”。对于有强类型约束、外键关系、频繁 JOIN 的数据，关系型列仍然是更好的选择。

考点标签

RAG 架构 · 难度：⭐⭐⭐⭐

📝 题目

知识库中描述了一个企业级 RAG 系统的“自定义标识符”设计：id = 外包公司ID # 文档ID # chunk_序号，并强调这个 ID 可以用于“上下文无损拼接”——当用户问到某张流程图时，代码可以凭主键直接干捞出 chunk_2（图表前的文字）和 chunk_4（图表后的注意事项），拼在一起喂给大模型。请问：这种基于“确定性 ID 顺序”的上下文拼接方案，相比“向量检索获取上下文”有什么本质优势？在什么情况下这种方案会失效？

💡 参考答案

▎一句话结论

确定性 ID 顺序拼接的本质是“用结构化元数据替代语义搜索”——它避免了向量检索的相似度不确定性，保证上下文拼接的精确性和完整性；但当文档结构被打乱、切片经过重排、或用户的问题跨越多个文档时，这种方案就会失效。

▎核心原理

  • 向量检索的“相似度不确定”问题：向量检索返回的是“语义最相似”的 Top K 切片，但“语义相似”不等于“上下文连续”。如果用户问的是某张流程图的内容，向量检索可能返回流程图本身的切片，但漏掉了流程图前后的文字说明，导致 LLM 缺乏上下文而理解错误。
  • 确定性 ID 的“主键定位”优势：chunk_3 的 ID 中包含了“它在原始文档中的物理位置”。一旦定位到 chunk_3，代码可以通过 chunk_2 和 chunk_4 的 ID 直接精确获取相邻切片，不需要做任何相似度计算。这保证了“上下文拼接”的完整性和确定性。
  • 适用场景的边界：这种方案最适合“文档结构清晰、切片顺序与阅读顺序一致”的场景（如规章制度、操作手册、流程图说明）。当文档是多级标题结构时，切片顺序天然对应阅读顺序，确定性拼接非常有效。
  • 失效场景：① 文档经过重排（Rerank）后，物理顺序与逻辑顺序不再一致；② 用户的问题跨越多个文档（比如“对比 A 公司的入职流程和 B 公司的入职流程”），需要跨文档拼接；③ 切片被去重或合并后，ID 的连续性被破坏。

▎深入解释

可以类比一本书的阅读体验。如果你读到第 50 页的某个流程图，但发现流程图前后各缺了一页，你可能会看不懂。向量检索就像“根据关键词搜索书中的相关页面”，它可能返回第 50 页（流程图本身），但漏掉了第 49 页（流程图的文字说明）和第 51 页（流程图的注意事项）。确定性 ID 拼接就像“直接翻到第 50 页，然后往前翻一页、往后翻一页”，保证你看到完整的上下文。

在工程实现中，这种方案的关键在于：切片时必须保持“物理顺序”和“逻辑顺序”的一致性。如果使用 MarkdownHeaderTextSplitter，它会按照标题层级切分，切片顺序天然对应文档的阅读顺序。但如果使用了“语义切片”（根据语义相似度聚类切分），切片顺序可能被打乱，确定性拼接就会失效。

另一个关键点是：ID 的连续性必须在“同一文档内”保证，跨文档不保证。chunk_2 和 chunk_4 只有在同一个 doc_id 下才有“相邻”的含义。如果 chunk_3 是文档 A 的最后一个切片，chunk_4 是文档 B 的第一个切片，它们虽然在 ID 上相邻，但在语义上毫无关系。

▎面试加分点

  • 能提出“混合策略”：先用向量检索定位核心切片，再用确定性 ID 拼接相邻切片，两者结合。
  • 能指出“确定性拼接的上下文窗口是有限的”——如果 chunk_2 和 chunk_4 加起来超过了 LLM 的上下文窗口，需要做截断或摘要。
  • 能结合“多租户隔离”场景，说明 ID 中嵌入 tenant_id 的价值：既防止越权，又支持精确删除。

▎常见误区

  • 认为“向量检索一定能返回完整上下文”。实际上向量检索的 Top K 是基于相似度排序的，不一定包含所有必要的上下文。
  • 认为“确定性 ID 拼接可以替代向量检索”。实际上它只能作为向量检索的补充，用于“定位后的上下文扩展”。
  • 认为“ID 连续就代表语义连续”。实际上如果切片时没有保持逻辑顺序，ID 连续只是物理连续，不代表语义连续。

Agent 架构 · 难度：⭐⭐⭐⭐

📝 题目

知识库中提出了“动静分离”的混合存储架构：企业内部知识库（静态、海量、重检索）使用专用向量数据库（如 Milvus），用户会话历史和 Agent 状态（动态、高频、重事务）使用 PostgreSQL。但在实际落地中，很多团队发现：用户会话历史中其实也包含大量“值得向量化”的语义信息（比如用户之前问过“社保公积金比例”，现在问“那医保呢？”——这里的“那”指代了之前的上下文）。请问：在这种“指代消解”需求下，是否应该把会话历史也向量化存入向量库？如果不应该，Agent 如何解决这种跨轮次的语义指代问题？

💡 参考答案

▎一句话结论

会话历史不应该全量向量化存入向量库，因为会话历史的查询模式是“精确的 Session ID 点查”而非“语义相似度搜索”；跨轮次指代消解的正确做法是把“压缩后的会话摘要”或“关键实体”作为上下文注入 LLM，而不是让向量库去做它不擅长的事情。

▎核心原理

  • 查询模式的本质区别：知识库查询是“语义搜索”——用户问“社保比例怎么算”，系统需要在海量文档中找到“语义最相似”的切片。会话历史查询是“精确点查”——系统知道用户是 user_id=123、session_id=456，直接按主键查出最近 N 轮对话即可。两者的查询模式完全不同，不应该用同一种存储引擎。
  • 向量化的收益与成本：将会话历史向量化，收益是“可以按语义搜索历史对话”，但成本是：① 每轮对话都要调用 Embedding 模型（额外延迟和成本）；② 向量检索返回的是“语义相似”的历史消息，但跨轮次对话需要的是“时间顺序上相邻”的消息；③ 向量库的写入和更新成本远高于 PostgreSQL 的行追加。
  • 指代消解的正确解法：跨轮次指代（如“那医保呢？”中的“那”指代上文的“社保”）本质上是一个“上下文补全”问题，不是“语义搜索”问题。正确做法是在组装 Prompt 时，把最近 N 轮对话历史（或对话摘要）直接注入 LLM 的上下文，让 LLM 自己理解“那”指代什么。
  • 长对话的压缩策略：当会话历史超过 LLM 上下文窗口时，不是去向量库搜索“最相关的历史消息”，而是使用“滑动窗口 + 摘要压缩”——保留最近 K 轮完整对话，更早的对话用 LLM 生成摘要，把摘要作为上下文注入。

▎深入解释

可以类比微信聊天记录。你想找“上周三和朋友讨论的餐厅名字”，有两种方式：① 在聊天记录里输入关键词“餐厅”搜索（类似向量检索）；② 直接翻到上周三的聊天记录（类似精确点查）。对于“和朋友继续聊餐厅话题”这个场景，你不需要搜索，你只需要把最近的聊天记录往上翻一翻，就能理解上下文。

Agent 的跨轮次对话也是同样的逻辑。用户问“社保公积金比例”，系统回答了。用户接着问“那医保呢？”——这里的“那”不需要做语义搜索，只需要把上一轮的问答作为上下文注入 LLM，LLM 自然能理解“那”指代“社保公积金比例”。

但在长对话场景下（比如用户和 Agent 聊了 50 轮），把所有历史都注入 LLM 是不现实的。这时候需要做对话摘要：用 LLM 把前 40 轮对话压缩成一段摘要（比如“用户在咨询入职流程，已经问过社保、公积金、体检，当前正在问医保”），然后把摘要 + 最近 10 轮完整对话注入 LLM。这个摘要可以存在 PostgreSQL 的 JSONB 字段中，随会话状态一起管理。

▎面试加分点

  • 能区分“语义搜索”和“上下文补全”两种不同的信息需求，并指出它们应该用不同的技术方案。
  • 能提出“对话摘要 + 滑动窗口”的混合策略，展现对长对话场景的工程化思考。
  • 能指出“如果未来确实需要对历史会话做语义搜索（比如用户问‘我上周问过什么来着’），可以异步地把会话摘要向量化，而不是把原始对话向量化”。

▎常见误区

  • 认为“会话历史向量化后就能解决指代消解”。实际上指代消解需要的是“时间顺序相邻”的上下文，不是“语义相似”的历史消息。
  • 认为“PostgreSQL 存会话历史就是不做语义理解”。实际上语义理解发生在 LLM 层，不是存储层。
  • 认为“对话摘要会丢失信息”。实际上对于跨轮次指代消解，摘要保留“关键实体和话题”就足够了，不需要保留完整对话。

Redis · 难度：⭐⭐⭐

📝 题目

知识库中提到 Redis 在 Agent 架构中扮演“短时记忆库”的角色，并给出了使用 List 存储最近 N 轮对话、使用 EXPIRE 自动清理的示例。但在多 Agent 协同场景中，一个 Agent 可能需要“读取另一个 Agent 的对话历史”来做出决策。请问：使用 Redis List 存储对话历史时，如何实现“多个 Agent 安全地读取和追加同一个会话的对话记录”？List 的 LPUSH + LTRIM 组合在这个场景下有什么局限性？

💡 参考答案

▎一句话结论

Redis List 存储对话历史的核心优势是“时间有序 + O(1) 追加 + 自动裁剪”，但它本质上是“无锁的追加日志”，不支持“多 Agent 并发修改同一段历史”；在多 Agent 协同场景中，需要引入“会话锁”或改用 Redis Stream 来保证写入的原子性和消费的有序性。

▎核心原理

  • List 的时间有序性：LPUSH 把新消息插入列表头部，LRANGE 0 N-1 按时间倒序读取最近 N 条消息。这种结构天然适合“对话历史”的存储——最新的消息在最前面，读取最近 N 轮只需要一次 LRANGE 操作。
  • LTRIM 的裁剪机制：LPUSH 后紧跟 LTRIM 0 N-1，可以保证 List 中只保留最近 N 条消息，超过 N 条的最老消息被自动删除。这解决了“对话历史无限增长”的问题。
  • 多 Agent 并发的原子性问题：LPUSH 本身是原子的，但“LPUSH + LTRIM”是两个独立的命令，中间可能被其他 Agent 的写入打断。更关键的是，如果 Agent A 想“读取最近 5 条消息，然后基于这些消息追加一条回复”，这个“读-思考-写”的过程不是原子的，Agent B 可能在同一时间也追加了一条消息，导致 Agent A 的回复“插队”或“基于过时的上下文”。
  • List 的局限性：① 不支持“消费确认”——消息被读取后不会自动标记为已读，多个 Agent 可能重复读取同一条消息；② 不支持“按消费者分组”——无法区分哪些消息是给 Agent A 的，哪些是给 Agent B 的；③ 不支持“阻塞等待”——如果 Agent A 想等待 Agent B 的回复，需要轮询，不如 BRPOP 或 Stream 的 XREAD BLOCK 高效。

▎深入解释

可以类比一个共享的聊天群。如果多个人同时在群里发消息，每个人发消息时都是“原子”的（一条消息不会被打断），但如果你想说“我基于上面 3 条消息回复”，你需要先读上面 3 条，再发你的回复。在你“读”和“发”之间，别人可能又发了一条新消息，导致你的回复“插队”了。

在 Redis 中，LPUSH 就是“发消息”，LRANGE 就是“读消息”。这两个操作单独都是原子的，但“读 + 思考 + 写”的组合不是原子的。在多 Agent 协同场景中，如果 Agent A 和 Agent B 同时处理同一个会话，就可能出现“A 基于旧上下文回复，B 也基于旧上下文回复，两人的回复都插入了 List，但彼此不知道对方的存在”。

解决方案有两种：

  1. 会话级锁（悲观锁）：在 Agent 读取和写入对话历史期间，使用 Redis 分布式锁（SET session_lock NX PX）锁定该会话，防止其他 Agent 同时写入。缺点是锁的粒度和持有时间需要精细控制，否则会阻塞其他 Agent。

  2. 改用 Redis Stream（推荐）：Stream 支持 XADD（追加消息）、XREAD BLOCK（阻塞读取新消息）、XACK（消费确认）、XGROUP（消费者分组）。多个 Agent 可以作为同一个 Consumer Group 的消费者，每条消息只被一个 Agent 消费，消费后需要 ACK，未 ACK 的消息可以被重新投递。这天然适合“多 Agent 协同处理同一个会话”的场景。

▎面试加分点

  • 能指出“List 适合单 Agent 的对话历史存储，Stream 适合多 Agent 的消息协同”，并说明两者的适用边界。
  • 能提出“用 WATCH + MULTI 事务或 Lua 脚本实现读-写原子性”的方案，展现对 Redis 原子性的理解。
  • 能结合“Agent 状态恢复”场景，说明 List 中的对话历史如何与 Checkpoint 机制配合。

▎常见误区

  • 认为“LPUSH + LTRIM 是原子的”。实际上它们是两个独立命令，中间可能被打断。
  • 认为“List 可以替代 Stream 做消息队列”。List 的 BRPOP 可以做简单的阻塞队列，但不支持消费确认和消费者分组，无法满足多 Agent 协同的可靠性要求。
  • 认为“对话历史必须存在 Redis 中”。实际上对于需要长期保存的对话历史，应该定期持久化到 PostgreSQL，Redis 只作为“热数据”缓存。

Agentic RAG · 难度：⭐⭐⭐⭐

📝 题目

知识库中对比了传统 RAG 和 Agentic RAG，指出 Agentic RAG 引入了“自我反思（Self-Reflection）”机制，包括文档打分（Document Grading）、幻觉检测（Hallucination Critique）和回答完备性验证。但在实际工程中，很多团队发现：引入自我反思后，系统的 Token 消耗呈阶梯式上升，但答案质量并没有同比例提升。请问：在什么情况下，自我反思机制是“必要的开销”？在什么情况下，它是“过度设计”？如何在工程上做一个“适度反思”的折中设计？

💡 参考答案

▎一句话结论

自我反思机制的价值与“问题的复杂度”和“错误的代价”成正比——对于简单的单跳事实查询，反思是过度设计；对于多跳推理、跨文档比对、或对幻觉极度敏感的场景，反思是必要的质量保障；工程上应该采用“分级反思”策略，让简单问题走快路径，复杂问题走慢路径。

▎核心原理

  • 反思的成本结构：每次反思都意味着一次额外的 LLM 调用。文档打分需要 LLM 判断“检索结果是否相关”，幻觉检测需要 LLM 判断“草稿是否被上下文支撑”，完备性验证需要 LLM 判断“是否真正回答了问题”。三次反思 = 三次额外的 LLM 调用，Token 消耗是“无反思”的 3-4 倍。
  • 反思的收益递减规律：对于简单问题（如“公司年假有几天”），单次检索 + 生成就能得到正确答案，反思只是在“确认一个已经正确的答案”。对于复杂问题（如“对比 A 公司和 B 公司的入职流程差异”），单次检索可能遗漏关键信息，反思能捕捉到这种遗漏并触发补充检索。
  • 分级反思的设计原则：在 Agent 的“意图路由”阶段，先对问题复杂度做一个快速判断。简单查询（单跳、事实型、有明确答案）走“无反思快路径”；复杂查询（多跳、对比型、推理型）走“带反思慢路径”。这个判断本身可以是一个轻量级的分类器，不需要完整的反思循环。
  • 反思的触发条件：不是所有步骤都需要反思。一个更精细的设计是“条件反射”——只有当某些指标触发时（如检索结果的相似度分数低于阈值、生成草稿的置信度低于阈值、用户明确表示不满意），才启动反思循环。

▎深入解释

可以类比考试答题。对于一道简单的选择题（如“1+1=？”），你不需要检查三遍再交卷——直接写答案就行。对于一道复杂的数学证明题，你需要检查推理过程是否正确、是否有遗漏的边界条件、结论是否完整。这就是“分级反思”的直觉。

在 Agentic RAG 中，一个常见的工程陷阱是：对所有请求都启用完整的反思循环。这导致简单问题也要经过“检索→打分→生成→幻觉检测→完备性验证”的完整流程，Token 消耗翻了好几倍，但答案质量并没有提升——因为简单问题本来就不会出错。

一个更聪明的设计是：

if query_complexity == "simple":
    result = retrieve_and_generate(query)  # 无反思
elif query_complexity == "medium":
    result = retrieve() → grade_documents() → generate()  # 只做文档打分
elif query_complexity == "complex":
    result = retrieve() → grade() → generate() → critique() → verify()  # 完整反思

这个“分级”逻辑可以基于规则（如问题长度、是否包含“对比/分析/为什么”等关键词），也可以基于一个小型的分类模型。

▎面试加分点

  • 能提出“分级反思”或“条件反射”的架构设计，展现对成本-收益权衡的工程化思考。
  • 能指出“反思的触发条件应该基于可观测指标（如相似度分数、置信度），而不是盲目地对所有请求反思”。
  • 能结合“幻觉敏感场景”（如医疗、法律、金融）说明为什么在这些场景下反思是必要的，即使成本高。

▎常见误区

  • 认为“反思越多，答案越好”。实际上反思的收益有上限，超过一定轮次后，反思只是在重复确认已知信息。
  • 认为“Agentic RAG 一定比传统 RAG 好”。对于简单查询，传统 RAG 的“单次检索 + 生成”更快、更便宜、质量一样。
  • 认为“反思机制可以完全避免幻觉”。反思只能降低幻觉概率，不能完全消除。

💡 参考答案

▎一句话结论

“物理剥离”和“语义理解”分离的本质是“解耦 IO 密集型操作与计算密集型操作”——第一步的 OCR/版面分析是确定性的、可缓存的结构化操作，第二步的图片语义理解是昂贵的、依赖 Prompt 的 LLM 调用；分离后可以独立优化、独立重试、独立升级，避免“改 Prompt 就要重新跑整个流水线”的灾难。

▎核心原理

  • 成本与频率的不对称：OCR/版面分析只需要做一次，结果（图片 URL + 占位符）可以永久缓存。图片语义理解可能需要多次——如果三个月后你想调整图片描述的 Prompt（比如希望描述更简短、更聚焦于文字内容），只需要重新跑第二步，不需要重新做 OCR。
  • 失败域隔离：如果第一步就调用多模态 LLM，那么 LLM 调用失败（超时、限流、格式错误）会导致整个解析流水线中断。分离后，第一步的失败（OCR 失败）和第二步的失败（LLM 失败）可以独立重试，互不影响。
  • Prompt 的可迭代性：图片描述的 Prompt 是业务逻辑的一部分，会随着用户反馈和业务需求不断调整。如果 Prompt 嵌入在第一步中，每次调整都要重新解析原始 PDF，成本极高。分离后，调整 Prompt 只需要对已剥离的图片重新调用 LLM。
  • 计算资源的差异化调度：OCR/版面分析可以用 CPU 或轻量级 GPU 跑，图片语义理解需要多模态 LLM（通常是昂贵的 GPU 资源）。分离后，两类任务可以放在不同的队列中，用不同的资源池调度。

▎深入解释

可以类比“拍照”和“修图”的关系。拍照（OCR/版面分析）是确定性的——你拍一张照片，照片的内容是固定的。修图（图片语义理解）是主观的——你可以今天用“明亮滤镜”，明天用“复古滤镜”，同一个原始照片可以反复修。如果你把修图嵌入到拍照过程中，每次想换滤镜都要重新拍一张照片，这显然是荒谬的。

在 Agent 架构中，“延迟理解”的设计模式还有几个类似的应用：

  1. Embedding 生成与 Rerank 的分离：Embedding 是确定性的向量化操作，Rerank 是昂贵的精排模型调用。两者分离后，可以独立调整 Rerank 模型而不需要重新生成 Embedding。

  2. 数据采集与数据清洗的分离：Agent 的工具调用结果（原始数据）先原样存储，后续再根据业务需求做清洗和转换。如果清洗逻辑变了，不需要重新调用工具。

  3. 日志记录与日志分析的分离：Agent 的执行日志先原样记录，后续再根据分析需求做聚合和挖掘。如果分析维度变了，不需要重新执行 Agent。

▎面试加分点

  • 能提出“中间态缓存”的概念：第一步的输出（图片 URL + 占位符）是稳定的中间产物，可以缓存和复用。
  • 能指出“Prompt 迭代成本”是分离的核心动机——在 AI 系统中，Prompt 是变化最频繁的组件，应该与确定性的数据管道解耦。
  • 能举出“延迟理解”在 Agent 架构中的其他应用（如日志分析、数据清洗），展现模式迁移能力。

▎常见误区

  • 认为“分离会增加系统复杂度，不如一步到位”。实际上分离后的系统更容易维护，因为每个阶段可以独立测试、独立部署。
  • 认为“OCR 和图片理解可以合并成一个多模态 LLM 调用”。实际上 OCR 是确定性的结构化提取，图片理解是主观的语义描述，两者的优化目标不同。
  • 认为“中间态缓存会占用额外的存储空间”。实际上存储成本远低于重复计算成本，尤其是当 Prompt 频繁调整时。

考点标签

Agent 架构 · 难度：⭐⭐⭐⭐

📝 题目

知识库中对比了三种执行模式：传统同步（A→B→C）、简单异步并发（asyncio.gather）、异步 DAG 编排（A→分流→B 和 C 并发）。并指出“如果是复杂的、带循环纠错（Human-in-the-loop）的 Agent 集群，手写 asyncio 会很痛苦，强烈建议直接上 LangGraph”。请问：为什么“循环纠错”和“Human-in-the-loop”这两个特性，会让手写 asyncio 的复杂度急剧上升？LangGraph 在解决这两个问题时，提供了哪些手写异步代码难以实现的核心能力？

💡 参考答案

▎一句话结论

“循环纠错”和“Human-in-the-loop”本质上打破了 DAG 的“有向无环”假设——它们引入了“环”和“挂起等待”，而手写 asyncio 需要程序员手动管理环的退出条件、挂起状态的持久化和恢复、以及并发任务的取消与补偿；LangGraph 通过 Checkpoint 机制和状态机抽象，把这些复杂度下沉到框架层。

▎核心原理

  • 循环纠错的“环”问题：DAG 是“有向无环图”，任务从起点流向终点，不会回头。但循环纠错意味着“如果节点 C 的输出不合格，回到节点 B 重新执行”。这个“环”在手写 asyncio 中需要手动管理：什么时候退出循环？最多循环几次？循环中哪些任务需要重新执行，哪些可以复用结果？
  • Human-in-the-loop 的“挂起”问题：当工作流执行到“等待人工审核”节点时，整个工作流需要“挂起”——释放计算资源，把状态持久化，等待外部事件（人工点击“通过”或“拒绝”）。手写 asyncio 中，这个“挂起”意味着协程不能简单地 await，因为 await 会阻塞事件循环。你需要把状态序列化到数据库，然后通过另一个入口（如 FastAPI 的 webhook）来恢复执行。
  • 状态持久化的复杂性：循环纠错和人工审核都需要“记住当前执行到哪里了”。手写 asyncio 中，这个状态存在内存变量里，进程重启就丢了。LangGraph 的 Checkpoint 机制自动把每个节点的执行状态持久化到数据库，进程重启后可以从 Checkpoint 恢复。
  • 并发任务的取消与补偿：如果节点 B 和 C 并发执行，B 完成了但 C 失败了，需要决定“是否取消 B 的结果”或“补偿 B 的副作用”。手写 asyncio.gather 中，return_exceptions=True 只能捕获异常，无法做精细的补偿逻辑。

▎深入解释

可以类比“项目管理”和“流水线”的区别。流水线是线性的，每个工位做完就传给下一个，不会回头。项目管理是动态的——如果测试阶段发现需求理解错了，需要回到设计阶段重新做；如果某个关键决策需要老板审批，项目就“挂起”等待老板回复。

手写 asyncio 就像用代码模拟项目管理：你需要手动记录“项目当前在哪个阶段”、“哪些任务已经完成”、“哪些任务需要重做”、“老板的审批结果是什么”。当项目越来越复杂（多个循环、多个审批点、多个并发分支），这些手动管理的代码会变得极其复杂且容易出错。

LangGraph 的核心价值在于：它把“状态机”和“Checkpoint”作为一等公民。每个节点的执行都会自动保存 Checkpoint（包括当前状态、输入输出、执行时间戳），当需要“回到某个节点重新执行”或“从挂起点恢复”时，框架自动处理状态的加载和恢复。程序员只需要定义“节点是什么”和“边怎么连”，不需要手动管理状态持久化。

▎面试加分点

  • 能指出“循环纠错打破了 DAG 的无环假设”，这是理解 LangGraph 价值的关键洞察。
  • 能提出“Human-in-the-loop 的本质是‘长时挂起 + 外部事件驱动恢复’”，并说明为什么这与 asyncio 的短时并发模型不匹配。
  • 能结合“进程重启后从 Checkpoint 恢复”的场景，说明状态持久化在生产环境中的重要性。

▎常见误区

  • 认为“asyncio.gather 能解决所有并发问题”。实际上它只能处理“无依赖的并发”，无法处理“有条件的循环”和“挂起等待”。
  • 认为“LangGraph 只是封装了 asyncio”。实际上 LangGraph 的核心价值是状态机抽象和 Checkpoint 机制，不是异步调度。
  • 认为“循环纠错就是简单的 while 循环”。实际上循环纠错涉及“循环条件判断、最大迭代次数、部分重试、结果复用”等多个维度，比简单的 while 循环复杂得多。

场景标签

Agentic RAG 意图路由 多跳推理 PostgreSQL Redis

📝 题目

你正在为一家大型跨国制造企业设计「全球供应链智能问答 Agent」。该系统的用户包括采购、物流、财务三个部门的员工，他们的提问场景差异极大：

  • 采购问：“上个月华东区螺丝钉供应商的交付准时率是多少？”（需要查结构化数据库）
  • 物流问：“如果台风导致宁波港封港，我们的应急预案是什么？”（需要检索内部 PDF 制度文档）
  • 财务问：“对比一下 Q2 和 Q3 的运输成本构成变化，并解释原因。”（需要跨多份文档做多跳推理）

同时，系统每天要承载 5 万次以上的用户请求，P95 延迟必须控制在 2 秒以内。请设计一套完整的 Agentic RAG 架构，重点回答：

  1. 如何设计「动态意图路由」层，让三种类型的提问分别走向最优的检索路径？
  2. 如何平衡「Agentic RAG 的智能性」与「高并发下的延迟与成本约束」？
  3. PostgreSQL 和 Redis 在这个架构中分别承担什么角色？为什么不能只用其中一个？

💡 参考答案

▎解题思路

  1. 第一步：识别三类提问的本质差异——结构化查询（SQL）、单跳语义检索（向量）、多跳推理（需要迭代检索与反思），据此设计路由层。
  2. 第二步：采用「轻量分类器 + 规则兜底」的混合路由策略，避免每一次请求都进入完整的 Agentic 循环。
  3. 第三步：利用 PostgreSQL 的 pgvector 实现「业务过滤 + 向量检索」的融合查询，Redis 承担热点缓存与限流，形成「快路径」与「慢路径」分流的架构。

▎详细方案

路由层设计：

用户问题 → 轻量分类器（小模型或规则引擎）
  ├── 类型A：结构化数据查询（含时间/指标/聚合词） → 走 Text-to-SQL 管道
  ├── 类型B：单跳事实型（“XX 是什么/在哪里”） → 直接走传统 RAG（单次检索 + 生成）
  └── 类型C：复杂推理型（“对比/分析/为什么”） → 进入完整 Agentic RAG 循环

类型 A 走 Text-to-SQL 管道：
- LLM 根据 Schema 描述生成 SQL → 在 PostgreSQL 只读副本上执行 → 结果表格化后交给 LLM 生成自然语言回答。
- 关键优化：使用 response_format 强制 LLM 输出结构化 SQL，配合 Pydantic 校验，失败则重试一次。

类型 B 走传统 RAG 快路径：
- 单次 Embedding → pgvector 的 HNSW 索引检索 Top 10 → Rerank 模型重排 Top 3 → 生成回答。
- 端到端延迟控制在 800ms 以内。

类型 C 进入 Agentic RAG 慢路径：
- 基于 LangGraph 构建状态图：拆解子问题 → 动态路由检索 → 上下文质量评估 → 条件循环（重写 Query 或生成答案）。
- 设置最大迭代次数为 3，防止无限循环。
- 使用 Redis 缓存中间检索结果，相同子查询直接命中。

PostgreSQL 与 Redis 的角色分工：

PostgreSQL：
- 存储所有文档切片的向量（pgvector），同时存储 tenant_id、department、doc_type 等标量字段。
- 单条 SQL 同时完成权限过滤 + 向量相似度检索，避免跨库事务。
- 持久化 Agent 状态（JSONB），支持 LangGraph Checkpointer。

Redis：
- 缓存高频问题的最终答案（Key 为问题 Embedding 的哈希，Value 为答案），命中率预估 30%+。
- 对 LLM API 调用做滑动窗口限流（ZSet），防止突发流量击穿成本上限。
- 缓存热点文档切片的 Embedding 向量，减少重复计算。

▎关键细节 & 踩坑点

  • 路由误判是最大风险：一个需要多跳推理的问题被误判为单跳，会导致答案质量断崖式下降。建议在分类器中加入「置信度阈值」，低于阈值时降级到 Agentic 路径。
  • Text-to-SQL 的安全问题：必须使用只读数据库账号，并在 SQL 前加 LIMIT 和超时控制，防止 LLM 生成全表扫描或笛卡尔积查询。
  • Agentic 路径的循环失控：必须设置最大迭代次数和 Token 预算，否则一次请求可能消耗数万 Token，成本爆炸。
  • pgvector 的 HNSW 索引内存占用：当向量数据超过 500 万条时，HNSW 索引可能占用数十 GB 内存，需要评估是否将「冷文档」迁移到专用向量库。

▎可扩展优化

  • 引入「影子路由」机制：让 5% 的流量同时走快路径和慢路径，对比答案质量，动态调整路由规则。
  • 在 Agentic 路径中引入「工具缓存」：将常用的检索工具结果缓存到 Redis，相同子问题直接复用。
  • 对于超高频问题（如“年假政策”），可以预生成答案并推送到 CDN 边缘节点。

场景标签

KV Cache GQA 上下文缓存 成本优化

📝 题目

你负责一个面向 C 端用户的「AI 法律咨询助手」产品，日活用户 50 万。每个用户进入产品后，系统会注入一段 2000 Token 的固定法律声明与免责条款 作为 System Prompt，然后用户开始提问。当前架构直接调用某大模型 API，按 Token 计费。

运营数据显示：
- 用户平均每轮对话 8 轮，每轮平均输入 3000 Token（含历史对话）
- 高峰期 QPS 达到 300
- 月度 LLM API 成本已超过 120 万元，其中 约 40% 的 Token 消耗来自重复传输 System Prompt 和历史对话
- 用户投诉「回复越来越慢」，P90 首字延迟从 1.2 秒恶化到 3.5 秒

请分析：

  1. 从 KV Cache 的角度，解释为什么「重复传输 System Prompt 和历史对话」会造成如此巨大的成本和延迟问题？
  2. 如果你们决定自建推理服务（而非继续用 API），你会优先采用哪些 KV Cache 优化技术来降低成本和延迟？请给出优先级排序和理由。
  3. 如果暂时无法自建，继续使用 API 服务，你能通过哪些工程手段来缓解这个问题？

💡 参考答案

▎解题思路

  1. 第一步：理解 KV Cache 的计费逻辑——在自回归生成中，每生成一个新 Token，都需要把「所有历史 Token 的 K/V 矩阵」重新参与注意力计算，API 服务商按「输入 Token 数」计费，重复传输历史上下文等于为同样的计算反复付费。
  2. 第二步：区分「API 模式」和「自建模式」下可用的优化手段。
  3. 第三步：设计一个「前缀缓存 + 会话截断 + 摘要压缩」的三层降本方案。

▎详细方案

为什么重复传输 System Prompt 和历史对话如此昂贵？

在 Transformer 的自回归推理中，每生成一个 Token，模型都要对「当前 Token 的 Q」与「所有历史 Token 的 K/V」做注意力计算。这意味着：
- 如果对话有 8 轮，第 8 轮生成时，前 7 轮的所有 Token 的 K/V 矩阵都要重新计算并参与注意力。
- 但前 7 轮的 K/V 在第 7 轮时已经算过了，第 8 轮重新计算完全是在做重复功。
- API 服务商虽然内部有 Context Cache 优化，但计费上仍然按「输入 Token 数」收费，用户实际上在为重复计算买单。

自建推理服务的优化优先级：

优先级 技术 理由
1 Context Cache（前缀缓存） 2000 Token 的 System Prompt 是固定不变的，命中率接近 100%，收益最直接
2 GQA（Grouped Query Attention） 从模型架构层面将 KV Cache 占用砍掉 4-8 倍，是长期降本的关键
3 PagedAttention（vLLM） 提升显存利用率到 96%+，直接提升并发吞吐量，减少需要的 GPU 数量
4 KV 量化（INT8/INT4） 在长对话场景下进一步压缩显存，但会带来轻微的精度损失

继续使用 API 的工程缓解方案：

方案一：会话状态摘要化。当对话超过 6 轮时，调用一个便宜的模型（如 GPT-4o mini）将前 6 轮对话压缩为 200 Token 的摘要，后续轮次只携带摘要 + 最近 2 轮原文。可将输入 Token 减少 60% 以上。

方案二：System Prompt 瘦身。将 2000 Token 的法律声明拆分为「核心必读」（200 Token，每轮携带）和「按需查阅」（1800 Token，仅在用户询问相关问题时通过工具调用注入）。

方案三：客户端缓存 + 会话恢复。对于同一用户的多次独立咨询，在客户端本地缓存历史摘要，新会话开始时只发送摘要而非完整历史。

▎关键细节 & 踩坑点

  • 摘要压缩的语义损失：法律场景对精确性要求极高，摘要可能丢失关键的法律条款引用。建议在摘要中保留「条款编号」和「关键词」，并在需要时通过工具调用回查原文。
  • Context Cache 的命中条件：API 服务商的 Context Cache 通常要求「前缀完全一致」，哪怕只改动一个字符，整个缓存都会失效。因此 System Prompt 必须严格模板化，禁止动态拼接用户昵称等个性化内容。
  • GQA 的模型选型：如果自建推理，选模型时必须确认其是否采用 GQA 架构（如 Llama 3、Mistral），否则 KV Cache 占用会高 4-8 倍。

▎可扩展优化

  • 引入「分层缓存」：L1 为 API 服务商的 Context Cache，L2 为自建 Redis 缓存高频问答对，L3 为 CDN 边缘缓存静态法律条文。
  • 对于超高频的法律问题（如“劳动仲裁时效是多久”），预生成标准答案，直接走缓存不调用 LLM。

📝 题目

你正在开发一个「合同条款自动提取 Agent」，核心流程是：用户上传一份合同 PDF，系统需要从中提取出结构化的条款信息，包括：

{
  "parties": [{"name": "甲方公司名", "role": "甲方"}, {"name": "乙方公司名", "role": "乙方"}],
  "payment_terms": {"amount": 1000000, "currency": "CNY", "due_days": 30},
  "effective_date": "2025-01-01",
  "termination_clauses": ["违约解除", "协商解除"],
  "is_auto_renew": true
}

你使用的开源模型（如 Qwen2.5-72B）部署在私有化环境中，不支持 response_format 参数。实际测试中发现模型输出的 JSON 经常出现以下问题：

  • 约 15% 的输出被包裹在 ```json ... ``` 代码块中
  • 约 8% 的输出存在字段名未加双引号（如 {name: "张三"}）
  • 约 5% 的输出存在尾逗号（如 "tags": ["a", "b",]）
  • 约 3% 的输出存在中文引号（如 {"name"："张三"}）
  • 约 2% 的输出直接截断（Token 达到 max_tokens 上限）

  1. 给出 Prompt 层的设计要点（包括 Few-Shot 示例和 Schema 声明）
  2. 给出后处理层的完整代码逻辑（伪代码即可），覆盖清洗、修复、校验、重试

💡 参考答案

▎解题思路

  1. 第一步：将问题分层——Prompt 层解决「引导正确」，后处理层解决「兜底纠错」，重试层解决「最终兜底」。
  2. 第二步：针对每一种错误类型设计对应的修复策略，形成「正则清洗 → JSON 修复库 → Schema 校验 → 带错误信息重试」的管道。
  3. 第三步：设置最大重试次数和降级策略，确保系统在任何情况下都能返回一个可用的结果。

▎详细方案

Prompt 层设计：

你是合同条款提取器。仅输出符合 RFC 8259 标准的纯 JSON 对象。

禁止输出：
- Markdown 代码块（```json 或 ```）
- 任何解释性文字、注释
- 尾逗号、单引号、中文引号
- JSON 之外的任何字符

必须输出以下 Schema：
{
  "parties": [{"name": "string", "role": "甲方|乙方"}],
  "payment_terms": {"amount": "integer", "currency": "CNY|USD", "due_days": "integer"},
  "effective_date": "YYYY-MM-DD",
  "termination_clauses": ["string"],
  "is_auto_renew": "boolean"
}

正确示例：
{"parties":[{"name":"华为技术有限公司","role":"甲方"},{"name":"中软国际","role":"乙方"}],"payment_terms":{"amount":1000000,"currency":"CNY","due_days":30},"effective_date":"2025-01-01","termination_clauses":["违约解除"],"is_auto_renew":true}

错误示例（禁止模仿）：
{name: "张三", "tags": ["a", "b",]}

后处理层伪代码：

import re
import json
from json_repair import repair_json
from pydantic import BaseModel, ValidationError
from typing import Optional

class ContractInfo(BaseModel):
    parties: list[dict]
    payment_terms: dict
    effective_date: str
    termination_clauses: list[str]
    is_auto_renew: bool

def extract_json_from_text(text: str) -> str:
    """第 1 步：剥离 Markdown 代码块和多余文本"""
    # 匹配 ```json ... ``` 或 ``` ... ```
    code_block = re.search(r"```(?:json)?\s*([\s\S]*?)\s*```", text)
    if code_block:
        return code_block.group(1)
    # 匹配第一个 { 到最后一个 }
    brace_match = re.search(r"\{[\s\S]*\}", text)
    if brace_match:
        return brace_match.group(0)
    return text

def clean_json_text(text: str) -> str:
    """第 2 步：基础清洗"""
    # 替换中文引号为英文引号
    text = text.replace('"', '"').replace('"', '"')
    text = text.replace(''', "'").replace(''', "'")
    # 移除尾逗号
    text = re.sub(r",\s*([}\]])", r"\1", text)
    return text

def parse_with_retry(llm_output: str, max_retries: int = 3) -> dict:
    """第 3 步：解析 + 修复 + 校验 + 重试"""
    raw_text = extract_json_from_text(llm_output)
    cleaned_text = clean_json_text(raw_text)

    for attempt in range(max_retries):
        try:
            # 尝试直接解析
            data = json.loads(cleaned_text)
        except json.JSONDecodeError:
            try:
                # 使用 json_repair 库修复
                repaired = repair_json(cleaned_text)
                data = json.loads(repaired)
            except Exception:
                # 修复失败，携带错误信息重试 LLM
                error_msg = f"JSON 解析失败，尝试 {attempt + 1}/{max_retries}。请严格按 Schema 输出纯 JSON，不要用代码块包裹，不要有尾逗号。"
                llm_output = call_llm_with_error_feedback(error_msg)
                raw_text = extract_json_from_text(llm_output)
                cleaned_text = clean_json_text(raw_text)
                continue

        # Schema 校验
        try:
            validated = ContractInfo.model_validate(data)
            return validated.model_dump()
        except ValidationError as e:
            error_msg = f"Schema 校验失败：{e.errors()}。请修正字段类型和必填项后重新输出。"
            llm_output = call_llm_with_error_feedback(error_msg)
            raw_text = extract_json_from_text(llm_output)
            cleaned_text = clean_json_text(raw_text)
            continue

    # 最终降级：返回部分字段或空结构
    return {"parties": [], "payment_terms": {}, "effective_date": "", 
            "termination_clauses": [], "is_auto_renew": False, "parse_error": True}

▎关键细节 & 踩坑点

  • 重试时必须携带具体错误信息：不要只说“解析失败”，要把 Pydantic 的 e.errors() 返回的字段级错误（如“payment_terms.amount 应为 integer，实际为 string”）反馈给 LLM，这样它才能精准修正。
  • max_tokens 截断问题：如果输出被截断，extract_json_from_text 可能提取到不完整的 JSON。此时应检测最后一个字符是否为 }，如果不是，在重试 Prompt 中要求模型「减少输出长度」或「分步输出」。
  • json_repair 不是万能的：它能修复尾逗号、中文引号等问题，但无法修复「字段名完全错误」或「结构完全不对」的情况，所以 Schema 校验和重试仍然是必须的。
  • 成本控制：每次重试都会消耗 Token，建议在重试时使用更短的 Prompt（只包含错误信息和原始需求，不重复发送完整合同文本），或者将合同文本缓存起来，只发送错误反馈 + 原始输出的截断部分。

▎可扩展优化

  • 如果错误率持续高于 10%，考虑对模型进行 SFT 微调，用标注好的 JSON 数据集训练模型学习输出格式。
  • 引入「约束解码」工具（如 Outlines、Guidance），从 Token 生成层面强制 JSON 语法合规，从根源上消除格式错误。
  • 对于超长合同，先做「条款定位」再「逐段提取」，避免一次性输出过长导致截断。

排障优化

场景标签

Agentic RAG 延迟 Token 消耗 状态持久化 性能优化

📝 题目

你负责的一个企业级 Agentic RAG 系统（基于 LangGraph 构建）在双十一大促期间出现了严重的性能问题。该系统负责为电商客服提供「智能工单处理建议」，工作流包含以下节点：

用户问题 → 意图识别 → 子问题拆解 → 并行检索（向量库 + SQL + 外部 API）→ 上下文质量评估 
→ 条件循环（重写 Query 或生成答案）→ 答案生成 → 人工审核 → 最终输出

故障现象：
- P95 端到端延迟从平日的 2.5 秒飙升到 12 秒
- LLM API 的 Token 消耗量是平日的 4.5 倍
- 有 3 个节点频繁出现「状态丢失」告警，用户投诉「问着问着就从头开始了」
- 监控显示「上下文质量评估」节点的重试率从 5% 飙升至 40%

请分析：

  1. 为什么 Agentic RAG 在高峰期会出现「延迟和 Token 消耗同时暴涨」的现象？其背后的机制是什么？
  2. 针对「状态丢失」问题，你会如何排查和修复？
  3. 请给出至少 4 条具体的优化措施，并说明每条措施能解决什么问题、可能带来什么副作用。

💡 参考答案

▎解题思路

  1. 第一步：从 Agentic RAG 的三个固有缺陷（长延迟、Token 消耗、状态持久化）出发，逐一分析高峰期的放大效应。
  2. 第二步：定位「状态丢失」的根因——LangGraph Checkpointer 的并发写入冲突或 Redis 内存淘汰。
  3. 第三步：设计「降级策略 + 缓存策略 + 状态持久化加固」的组合优化方案。

▎详细方案

为什么延迟和 Token 消耗会同时暴涨？

Agentic RAG 的核心特征是「循环迭代 + 自我反思」。在高峰期，以下因素形成恶性循环：

  1. 检索质量下降：向量库在并发压力下响应变慢，部分检索请求超时返回空结果或部分结果。
  2. 评估节点误判：检索结果不完整 → 「上下文质量评估」判定为不相关 → 触发「重写 Query 并重新检索」的循环。
  3. 循环放大效应：每次循环都会重新调用 LLM（评估 + 重写 + 生成），Token 消耗成倍增长。如果循环 3 次，单次请求的 Token 消耗是正常路径的 3-4 倍。
  4. 并发排队：大量请求同时进入循环，LLM API 的并发限制导致请求排队，延迟进一步恶化。

这解释了为什么「评估节点重试率从 5% 飙升至 40%」——不是评估逻辑变差了，而是上游检索质量下降导致评估节点频繁判负，触发了大量重试循环。

「状态丢失」的排查与修复：

排查步骤：
1. 检查 LangGraph Checkpointer 的持久化后端（PostgreSQL 或 Redis）的连接池是否耗尽。
2. 检查 Redis 的 maxmemory 配置和淘汰策略——如果使用 Redis 做 Checkpointer，高峰期大量状态写入可能导致 Redis 触发内存淘汰，把未过期的状态 Key 也淘汰掉了。
3. 检查是否有多个实例共享同一个 Checkpointer，但配置了不同的 thread_id 生成逻辑，导致状态写入冲突。

修复方案：
- 将 Checkpointer 从 Redis 迁移到 PostgreSQL（或使用 Redis 的 noeviction 策略 + 持久化 AOF）。
- 为 Checkpointer 配置独立的连接池，避免与业务查询争抢连接。
- 引入「状态版本号」机制，每次写入时检查版本号，防止并发覆盖。

具体优化措施：

措施 解决的问题 副作用
1. 设置最大循环次数为 2（从 3 降为 2） 减少 Token 消耗和延迟 可能降低答案质量
2. 对「评估节点」引入降级策略：连续 2 次判负后，不再重试，直接使用已有上下文生成答案并标注「置信度低」 阻断恶性循环 可能输出不完整答案
3. 对高频子问题（如“退款流程”）的检索结果做 Redis 缓存，TTL 设为 10 分钟 减少向量库压力 缓存可能过期导致答案不准确
4. 在网关层做限流和排队，而非让所有请求直接打到 Agent 工作流 保护后端不被压垮 用户等待时间可能变长
5. 将「意图识别」和「子问题拆解」合并为一个 LLM 调用（原来分开调用两次） 减少一次 LLM 往返 单次 Prompt 变长，可能影响拆解质量

▎关键细节 & 踩坑点

  • 不要在高流量时盲目增加循环次数：Agentic RAG 的「智能」是有代价的，高峰期应该优先保证「可用性」，而不是「最优答案」。
  • 降级策略必须显式告知用户：当系统因降级而给出低置信度答案时，应该在回复中标注「该建议仅供参考，请人工确认」，避免误导。
  • Checkpointer 的写入频率：LangGraph 的每个节点执行后都会触发一次 Checkpoint 写入，高峰期可能达到每秒数千次写入。必须使用批量写入或异步写入来降低数据库压力。

▎可扩展优化

  • 引入「弹性降级」机制：根据系统负载动态调整 Agentic 循环的深度。负载低时允许 3 次循环，负载高时降为 1 次。
  • 对「上下文质量评估」节点使用更小的模型（如 7B 级别），降低评估环节的 Token 消耗和延迟。
  • 将「向量检索」和「SQL 检索」的结果做交叉验证，减少因单一检索源失败导致的评估误判。

2. 重新解析新文件并插入新切片
3. 更新文档元数据表的版本号和更新时间
