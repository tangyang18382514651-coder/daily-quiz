📌 概念题 · Q1

考点标签

Agent架构 · JSONB · 数据库设计 · 难度：⭐⭐⭐

📝 题目

在构建 AI Agent 的记忆系统时，为什么推荐使用 PostgreSQL 的 JSONB 字段来存储对话中的动态上下文和临时标签，而不是为每一种新信息频繁地修改数据库表结构（增加列）？这种“传统列存骨架，JSONB 存变动”的设计哲学，其底层原理和性能优势是什么？

💡 参考答案

▎一句话结论

这种设计利用了 JSONB 二进制存储、可索引的特点，实现了数据结构的“静态骨架”与“动态血肉”分离，在保证核心查询性能的同时，获得了应对 AI 对话中不可预测的动态属性的极致灵活性。

▎核心原理

  • 结构灵活性： JSONB 允许在同一列中存储不同结构的半结构化数据，无需预先定义 Schema。当 Agent 需要记录用户意向、临时变量等“对话零碎”时，直接塞入 JSONB 字段即可，避免了频繁的 ALTER TABLE 操作。
  • 高性能查询： 与纯文本 JSON 不同，JSONB 以二进制格式存储，数据在写入时已解析排序，查询时无需重复解析。配合 GIN 索引，可以高效检索 JSON 内部的任意键值对。
  • 存储效率： 二进制格式比文本格式更节省空间，且支持压缩。

▎深入解释

我们可以把 Agent 的一次对话记录看作一份档案。档案的固定表头，如“发送人、时间、会话ID”，永远不会变，适合用传统的 SQL 列（如 sender VARCHAR, created_at TIMESTAMP）来存储，这样能利用 B-Tree 索引实现最高效的范围查询和精确匹配。然而，AI 在对话中产生的上下文是动态且不可预测的：上一轮可能是“用户意向：高”，这一轮可能变成了“提取的日期：2024年5月20日”。如果为每一个新属性都去 ALTER TABLE ADD COLUMN，在数据量大时，这会是一个昂贵的锁表操作，并且会使表结构迅速膨胀、难以维护。JSONB 字段就像一个灵活的“附件袋”，所有非标准的动态属性都往里放。当需要查询“所有意向为高的对话”时，通过 jsonb_column @> '{"intent": "high"}' 配合 GIN 索引，查询速度可以与普通列索引媲美。

▎面试加分点

  • 可以提到，这种设计在“HR智能客服”场景中，能轻松应对从对话中抽取的各类标签，如“候选人意向”、“离职倾向”、“技术栈”等，无需重新设计数据库。
  • 这种架构思维体现了“一套数据库解决多种需求”的哲学，减少了引入额外 NoSQL 数据库（如 MongoDB）带来的数据同步延迟和运维成本。

▎常见误区

  • 误区：认为 JSONB 万能，所有字段都存进去。 实际上，对于需要频繁作为 WHERE 条件进行范围查询（如时间）或高基数的精确匹配（如用户ID）的字段，仍应保留为传统列，以利用最成熟的 B-Tree 索引性能。
  • 误区：混淆 JSON 与 JSONB。 直接用 JSON 类型存储文本，每次查询都需要解析，性能极差，且无法有效建立索引。

📌 概念题 · Q2

考点标签

输出模式 · Structured Output · 工具调用 · 难度：⭐⭐⭐⭐

📝 题目

在大模型的五种核心输出模式中，“结构化输出（JSON Mode）”和“工具调用（Function Calling）”都涉及返回结构化的 JSON 数据。请问它们在设计哲学、核心用途和对 AI Agent 的意义上有什么本质区别？为什么说工具调用是 Agent 从“能说”到“能做”的关键一步？

💡 参考答案

▎一句话结论

结构化输出旨在“约束模型的嘴”，确保其回答格式可控；而工具调用旨在“赋予模型手”，让它能主动选择并驱动外部系统执行动作，是 AI Agent 行动能力的核心。

▎核心原理

  • 目的不同： 结构化输出的目标是信息本身，它要求模型把思考结果填入一个预定义的 JSON 模板中，方便程序解析（如提取文章中的姓名、日期）。工具调用（Function Calling）的目标是触发一个外部函数，它返回的不是最终答案，而是一个“指令”，告诉系统应该调用哪个工具以及用什么参数。
  • 交互模式不同： 结构化输出是单轮交互的终点，模型生成 JSON 后，任务通常就结束了。工具调用是多轮交互的起点，系统拿到“指令”后执行函数，再将结果返回给模型，由模型整合后生成最终回复。
  • 对 Agent 的意义不同： 结构化输出让 Agent 能更好地“理解”和“格式化”信息。而工具调用让 Agent 拥有了与外部世界交互的“行动力”，可以查询天气、搜索数据库、发送邮件，这是 Agent 从聊天机器人进化为智能助手的核心标志。

▎深入解释

可以这样类比：你让一个助手帮你整理一份报告。结构化输出就像是告诉他：“请把报告的标题、作者、摘要分别填进这个表格里。”助手做完表格，任务就完成了。工具调用则像是你给了他一个工具腰带，上面有“计算器”、“搜索引擎”、“电话”等工具，然后问他：“帮我查一下公司去年的总利润。”助手自己不会知道这个数字，但他会主动从腰带上拿出“搜索引擎”工具，输入“公司去年财报”进行查询，拿到结果后，再告诉你答案。这个过程里，助手不仅输出了内容，更关键的是他自主完成了“选择工具”和“使用工具”的决策与动作。

▎面试加分点

  • 可以结合 LangGraph 等框架说明，工具调用是构建多 Agent 协同网络的基础。一个 Agent 的输出（工具调用指令）可以作为另一个 Agent 的输入，实现复杂的任务编排。
  • 提及国内 Dify、Coze 等低代码平台将 Function Calling 的复杂性封装起来，让开发者通过拖拽配置即可实现，大大降低了 Agent 开发门槛。

▎常见误区

  • 误区：认为两者是替代关系。 实际上，它们是互补的。一个复杂的 Agent 流程可能先用工具调用获取数据，然后将数据用结构化输出整理成标准格式，传递给下一个环节。
  • 误区：认为工具调用就是简单的 API 调用。 其核心价值在于大模型对用户意图的理解和工具的自主选择，而非执行调用本身。

📌 概念题 · Q3

考点标签

Agent安全 · 数据库操作 · 沙箱 · 难度：⭐⭐⭐⭐

📝 题目

在设计能直接操作 SQL 数据库的 AI Agent 时，为什么要严格区分“读操作”和“写操作（增删改）”？并解释为什么即使允许写操作，也必须引入“人类反馈确认”和“SQL 环境沙箱隔离”这两道安全防线？

💡 参考答案

▎一句话结论

对数据库操作进行读写分离，并对写操作施加“人类确认”与“沙箱隔离”，是为了在利用 AI 提升效率与防范其“幻觉”可能带来的灾难性数据风险之间建立核心安全防线。

▎核心原理

  • 风险等级分离： 读操作（SELECT）是安全的，最多消耗资源或泄露数据（需配合权限控制），但不会破坏数据完整性。写操作（INSERT, UPDATE, DELETE）是破坏性的，一个错误的 UPDATE 或 DELETE 可能导致业务数据永久丢失。
  • 人类反馈（Human-in-the-Loop）： 大模型存在“幻觉”，可能生成语法正确但逻辑荒谬的 SQL。在执行任何写操作前，必须将生成的 SQL 语句和影响范围（如“将更新 150 行数据”）展示给人类审核，点击确认后才能执行。这是防止 AI “胡作非为”的最后一道逻辑防线。
  • 环境沙箱隔离： 即使通过了人类确认，Agent 的执行环境也必须与生产数据库物理或逻辑隔离。例如，使用一个只读副本或一个受限的数据库账户。这能防止 Agent 因 prompt 注入攻击或被恶意利用而执行超出预期的操作，如 DROP TABLE。

▎深入解释

这就像一个公司里的实习生（Agent）和正式员工（人类）。实习生可以随意查阅公共资料库（读操作），这能帮他快速学习并产出报告。但如果允许他直接修改公司核心财务报表（写操作），风险就太大了。正确的做法是：实习生可以起草修改方案（生成 SQL），然后交给他的导师（人类）审核，导师检查无误后签字确认（人类反馈）。并且，即使导师签字了，实习生也只能在一个独立的测试环境（沙箱）里操作，由系统自动检查无误后，再由正式流程同步到生产环境。这种多层防御体系是工程实践中的最佳选择。

▎面试加分点

  • 可以提到，在 HR 系统中，Agent 可以“读取”简历库进行筛选，但“修改”候选人状态或“删除”记录则必须经过 HR 人工确认。
  • 可以补充说明，沙箱隔离不仅是安全需要，也是合规要求，确保所有数据变更都有据可查，符合审计标准。

▎常见误区

  • 误区：认为只要 Prompt 写得足够好，就能完全避免 SQL 风险。 Prompt 工程是概率性的，无法提供 100% 的确定性保障，必须依赖确定性的系统安全机制。
  • 误区：把“人类确认”当作唯一防线。 如果 Agent 的执行环境权限过高，一个被诱骗的确认操作（如用户误点击）同样可能造成破坏，因此沙箱隔离是必要的物理兜底。

📌 概念题 · Q4

考点标签

向量数据库 · Milvus · 索引选型 · 难度：⭐⭐⭐⭐

📝 题目

在 Milvus 向量数据库中，HNSW 和 IVFFlat 是两种主流索引。在构建对响应延迟要求极高的“HR 语音智能客服”时，为什么普遍推荐选择 HNSW 而非 IVFFlat？请从查询性能、召回率、内存占用和构建成本四个维度进行对比分析。

💡 参考答案

▎一句话结论

HNSW 通过构建“高速公路网”式的图索引结构，在查询时能牺牲少量内存和构建时间，换取比 IVFFlat 更优、更稳定的低延迟和高召回率，完美契合语音客服等对实时性要求严苛的场景。

▎核心原理

  • 查询性能： HNSW 基于图结构进行搜索，通过在图中快速“跳跃”，能以极低的时间复杂度找到最近邻。IVFFlat 则是先通过聚类进行粗粒度筛选，再在候选聚类中进行暴力搜索。在数据量和维度较高时，HNSW 的查询速度通常更快、更稳定。
  • 召回率： IVFFlat 的召回率高度依赖于其聚类数量（nlist）和搜索范围（nprobe）参数，参数调优不当会导致大量相关向量被遗漏。HNSW 的图结构能更全面地探索空间，通常在同等查询速度下能提供更高的召回率。
  • 内存占用： HNSW 需要在内存中维护完整的图结构，内存占用高于原始向量数据。而 IVFFlat 仅需存储聚类中心，内存占用相对更低。
  • 构建成本： HNSW 建索引的过程是逐点插入并构建图，比较耗时。IVFFlat 建索引主要是聚类训练，速度相对较快。

▎深入解释

我们可以把在高维向量空间中搜索比作在一个陌生的巨型城市里找朋友家。IVFFlat 的策略是先把城市分成几百个“区”（聚类），告诉你朋友家大概在哪个区，然后你到这个区里挨家挨户（暴力搜索）去找。如果你记错了区，或者朋友家正好在区边界上，你就可能找不到（低召回率）。HNSW 则是帮你在这个城市里修了一张复杂的“高速公路网”，并给了你一张地图。你可以从任意一个点出发，顺着高速公路快速跨越，迅速接近目标区域，然后在小路上找到精确地址。这条路虽然前期修起来费劲（构建慢），地图也比较占地方（内存占用高），但一旦建成，你每次去找朋友都又快又准。对于语音客服场景，用户说一句话，需要在毫秒内从百万级知识库中找到答案，HNSW 的“低延迟、高召回”是绝对的首选。

▎面试加分点

  • 明确指出在 HR 智能语音客服项目中，选择了 HNSW 索引，因为其查询延迟极低、准确率极高，能直接提升用户对话体验。
  • 可以补充说明，对于数据量极大（数十亿级）且内存资源受限的场景，可能会考虑 IVFFlat 或其改进版，但 HNSW 是目前 Agent 领域最主流的索引选择。

▎常见误区

  • 误区：认为 HNSW 在所有维度上都优于 IVFFlat。 如果硬件内存非常有限，且可以接受稍微降低召回率来换取更低的内存占用，IVFFlat 仍有其价值。
  • 误区：建完索引后就不再调整。 随着数据插入和删除，HNSW 索引的性能会下降，需要定期进行索引压缩和重建。

📌 概念题 · Q5

考点标签

Agent架构 · 意图识别 · 路由分发 · 难度：⭐⭐⭐

📝 题目

在设计一个多功能 AI Agent（如 HR 智能客服）时，为什么推荐采用“意图识别路由 + 工具集分发”的架构，而不是把所有能力都写进一个巨大的 Prompt 中？这种架构的核心工作流程是怎样的？

💡 参考答案

▎一句话结论

采用“意图路由”架构是为了通过分而治之的策略，将复杂任务拆解并分发到专业的子 Agent 或工具上，从而避免“超级 Prompt”带来的大模型认知过载、幻觉率升高和难以维护的问题，显著提升系统的准确性和可扩展性。

▎核心原理

  • 降低单点复杂度： 将所有功能（如报销查询、简历筛选、政策问答）的规则和例子塞入一个 Prompt，会让大模型难以区分不同任务的细微差别，极易产生混淆和幻觉。路由架构让每个子 Agent 或工具只聚焦于一个明确的、边界清晰的任务。
  • 提升准确率与效率： 一个专门做意图识别的轻量级 Agent 或模型，其判断准确率远高于一个“万能”模型。识别出意图后，将任务精准分发到最擅长的处理单元，能获得最优结果。同时，对于简单、高频的意图，可以直接用规则匹配，成本为0。
  • 易于扩展与维护： 当需要增加新功能（如“开具在职证明”）时，只需开发一个新的工具并注册到路由表中，无需修改其他功能的 Prompt，避免了“牵一发而动全身”的风险。

▎深入解释

这个架构就像一个公司的总机前台（意图路由 Agent）。客户打电话进来，不会直接找到能解决所有问题的老板，而是由前台判断：“您是咨询报销的？我给您转财务部（RAG 检索工具）。”“您是想请假？我给您转人事部（填单追问 Agent）。”“您是找人的？我给您转员工通讯录查询接口（API 工具）。”财务部、人事部各自有自己专业的知识和流程，处理起来高效且准确。如果让老板一个人接所有电话，他很快就会因为信息过载而出错。在这个流程中，“定义工具 -> 描述边界 -> 大模型路由 -> 后端分发 -> 执行返回”是关键路径。当识别出的工具缺少必要参数时，还会触发“槽位填充”（Slot Filling）机制，由追问 Agent 向用户获取信息后再继续。

▎面试加分点

  • 可以结合 HR 智能客服项目，阐述如何将“医疗报销”、“简历筛选”、“政策问答”等定义为不同的工具，并由一个路由 Agent 统一调度。
  • 可以提到“规则+模型并行”的混合策略：对“打卡”、“请假”等高频固定指令直接走规则，零成本毫秒级响应；对模糊、复杂的意图再交给大模型进行语义路由。

▎常见误区

  • 误区：认为意图路由就是简单的关键词匹配。 真正的路由是基于语义理解的，能处理“我身体不舒服，明天不想来了”和“请一天病假”是同一种意图的情况。
  • 误区：为每一个细微的功能都创建一个工具。 过度拆分会导致路由 Agent 难以选择。应将同类功能合并，例如所有政策查询类问题都路由到一个统一的 RAG 工具。

📌 概念题 · Q6

考点标签

部署架构 · 阿里云 · Serverless · 难度：⭐⭐⭐

📝 题目

在阿里云上部署一个复杂的 Multi-Agent 系统（如使用 LangGraph 编排），为什么推荐选择 ACK Serverless 而非 SAE 或 FC？请从编排能力、生态兼容性和资源弹性三个角度分析其核心优势。

💡 参考答案

▎一句话结论

ACK Serverless 是部署复杂 Multi-Agent 系统的最佳选择，因为它完美融合了 Kubernetes 强大的编排生态与 Serverless 的极致弹性，既能驾驭 LangGraph 等复杂调度，又能实现 GPU 资源的按需使用和缩容到 0，是兼顾生产级能力与成本效益的最优解。

▎核心原理

  • 编排能力： ACK Serverless 提供完整的 K8s API，原生支持复杂的容器编排。Multi-Agent 系统通常由多个独立服务（如路由、RAG、代码执行器等）组成，这些服务间的依赖、顺序、并行、错误重试等复杂拓扑，K8s 能以声明式的方式轻松管理，这是 SAE 和 FC 难以做到的。
  • 生态兼容性： 它无缝兼容 K8s 生态工具，如 Helm 一键部署、Kubectl 运维、Prometheus 监控等。你可以直接复用社区成熟的 LangGraph 部署方案、向量数据库（Milvus）集群部署方案，无需为适配平台而魔改代码。
  • 资源弹性与隔离： 它具备 Serverless 的核心优势——弹性伸缩，特别是能基于 GPU 负载进行扩缩容，甚至缩容到 0，极大节省成本。同时，其底层使用 ECI（弹性容器实例）提供安全沙箱，每个 Agent 的 Pod 都拥有独立的、隔离的运行环境，安全性远超共享宿主机内核的方案。

▎深入解释

我们可以把部署一个 Multi-Agent 系统比作组建一个交响乐团。FC（函数计算） 就像一位独奏音乐家，你让他吹一段小号（执行一个函数），他能完美完成，但无法指挥整个乐团。SAE（Serverless 应用引擎） 像一个现成的室内乐队，你把谱子（Docker 镜像）给它，它能演奏，但如果你想实现复杂的声部切换和动态配合，它的能力就受限了。ACK Serverless 则为你提供了一个顶级的、可按需付费的音乐厅和所有乐器，并配备了标准的指挥系统（K8s）。你可以用乐谱界的标准语言（Helm Chart）来指挥整个交响乐团（Multi-Agent），让弦乐（RAG Agent）、管乐（代码执行 Agent）、打击乐（路由 Agent）完美协作。演出结束后，乐手们离场，你只为演出时段付费。

▎面试加分点

  • 明确说出：“对于追求纯粹 K8s 生态但又不想养服务器的团队，ACK Serverless 是承载复杂 Multi-Agent 系统的最佳生产环境。”
  • 可以补充说明，FC 非常适合作为 Agent 的一个“工具端”，提供安全、用完即毁的代码执行沙箱，与主 Agent 服务配合使用。

▎常见误区

  • 误区：认为 Serverless 就是只能跑简单函数。 ACK Serverless 是“容器即服务”，能运行任何容器化应用，包括长期运行的、有状态的 Agent 服务。
  • 误区：为了省事，把整个 Multi-Agent 系统打包成一个巨大镜像部署在 SAE 上。 这完全失去了微服务和 Serverless 的优势，一个组件的故障或扩容需求会影响整个系统。

📌 概念题 · Q7

考点标签

Agent架构 · 并发控制 · 悲观锁 · 难度：⭐⭐⭐

📝 题目

在“社媒内容运营 Agent”这类多节点并发处理的场景中，当多个 AI 节点可能同时修改同一条数据（如热点选题的状态）时，为什么需要使用 SELECT ... FOR UPDATE 这样的悲观锁，而不是依赖乐观锁或应用层的逻辑判断？

💡 参考答案

▎一句话结论

在多 Agent 节点高并发争抢同一热点资源的场景下，使用悲观锁（FOR UPDATE）能通过数据库层面的强制串行化，以最简单、最可靠的方式避免数据被覆盖，保证状态流转的一致性和零冲突。

▎核心原理

  • 强制串行化： SELECT ... FOR UPDATE 会在事务中查询某行数据时，立即对该行加一个排他锁。其他任何尝试修改或加锁读取这行数据的事务都会被阻塞，直到当前事务提交或回滚。这相当于把并发的修改操作强行排成一队，一个一个执行。
  • 避免“检查后执行”的竞态条件： 乐观锁和应用层判断都存在一个时间窗口。例如，节点A读取状态为“待处理”，准备改为“处理中”；就在这一瞬间，节点B也读取了“待处理”状态，也准备修改。乐观锁通过版本号能发现冲突，但会导致其中一个节点失败重试；应用层判断则直接导致数据覆盖。悲观锁直接从根源上杜绝了这个时间窗口。
  • 逻辑简单可靠： 相比乐观锁需要设计版本号字段和重试机制，悲观锁的 SQL 逻辑非常直接。对于“热点选题”这种争抢激烈、冲突概率高的场景，悲观锁避免了大量失败重试带来的性能开销和逻辑复杂性。

▎深入解释

想象一下，一个爆款热点话题出现了，它就像一个限量版的打折商品。你的多个 Agent 节点就像一群抢购的顾客。乐观锁 就像让所有顾客先拿商品，最后结账时发现有人比你先拿到，你就得把商品放回去重新抢。这个过程混乱且体验差。应用层判断 就像让一个管理员在门口喊：“我数三二一，你们告诉我谁要买！”结果大家同时喊，管理员还是不知道卖给谁。悲观锁（FOR UPDATE） 就像给这个商品上了一把锁，只有第一个拿到钥匙的顾客（Agent节点）才能打开柜子取货。他取货的时候，其他所有人都必须在后面排队等待。虽然排队降低了并发度，但对于争抢激烈的稀缺资源，这是保证秩序和公平的唯一有效方法。在内容运营 Agent 中，保证选题不被重复生成、状态正确流转，远比追求极致的并发吞吐量更重要。

▎面试加分点

  • 可以结合 PostgreSQL 的事务机制来回答，展示你对数据库底层原理的理解。
  • 可以提到，在使用悲观锁时，事务要尽可能短小精悍，持有锁的时间越长，造成的阻塞就越严重。

▎常见误区

  • 误区：认为悲观锁会影响性能，所以一律不用。 在冲突频率低的场景下，乐观锁性能更好。但在冲突频率高的场景，悲观锁通过避免大量无效重试，反而能获得更稳定的整体吞吐量。
  • 误区：在 FOR UPDATE 的事务中执行耗时的外部 API 调用。 这会导致数据库锁长时间无法释放，引发严重的性能问题。所有外部调用应在加锁事务之前或之后完成。

📌 概念题 · Q8

考点标签

Agent架构 · 槽位填充 · 多轮对话 · 难度：⭐⭐⭐⭐

📝 题目

在 HR 智能客服的多轮对话中，当用户意图需要调用一个工具但缺少必填参数时（如“帮我开个证明”，但缺少证明类型），Agent 是如何通过“槽位填充”（Slot Filling）机制来补齐参数的？请描述其核心工作流程和状态管理方式。

💡 参考答案

▎一句话结论

槽位填充是一种将多轮对话目标转化为参数补齐任务的状态机机制，Agent 通过识别缺失的“槽位”（参数），主动生成追问来引导用户提供，并将参数暂存在会话状态中，直到所有必填参数齐全后才触发最终的工具调用。

▎核心原理

  • 槽位定义： 每个工具（Function）都被预先定义好了一组参数（Slots），如 apply_certificate 工具包含 cert_type（证明类型）和 employee_name（员工姓名）等槽位。
  • 状态追踪： 对话系统维护一个会话状态机（State Machine）。当意图识别为“开证明”时，状态进入 PENDING_CERTIFICATE，并初始化一个空的槽位字典，如 {"cert_type": null}。
  • 追问生成： 系统检查槽位字典，发现 cert_type 为空，则触发追问逻辑，由大模型或预设模板生成自然语言提问：“请问您需要开具的是‘在职证明’还是‘收入证明’呢？”
  • 参数提取与回填： 用户下一轮回答“在职证明”时，系统再次利用大模型进行信息抽取，将“在职证明”这个值填入槽位字典的 cert_type 中。然后再次检查，若所有必填槽位都已齐全，则触发最终的 apply_certificate 工具调用。

▎深入解释

这个过程就像你去医院挂号。你告诉分诊台护士（意图路由 Agent）：“我要挂号。”护士知道挂号这个业务（工具）需要两个关键信息：科室（department）和医生（doctor_name）。她发现你都没提供，于是先问：“您要看哪个科室？”你回答：“内科。”护士就在她的小本本（会话状态）上记下 department: "内科"。她发现还缺医生信息，于是继续问：“内科有张医生和李医生，您挂谁的号？”你说：“李医生。”她再记下 doctor_name: "李医生"。现在所有信息都齐了，护士才给你打印挂号单（执行工具调用）。这个“小本本”就是会话状态机，它跟踪了整个挂号流程的进度和已收集的信息，确保了多轮对话能够围绕一个明确的任务目标连贯地进行下去。

▎面试加分点

  • 可以结合 LangGraph 来说明，每个槽位填充步骤都可以定义为一个节点，状态流转通过边来控制，使得整个追问逻辑可视化、可编排。
  • 提到这种机制不仅用于收集参数，还可以用于处理用户中途改变意图或取消操作的复杂对话场景。

▎常见误区

  • 误区：认为追问是简单的“if-else”判断。 追问的内容和方式需要结合上下文，由大模型动态生成，才能保持对话的自然和流畅。
  • 误区：将槽位信息存储在客户端。 所有状态必须安全地保存在服务端会话中，以防止用户篡改，例如将“普通员工”身份篡改为“管理员”来查询敏感信息。

📌 概念题 · Q9

考点标签

部署架构 · 降级方案 · 高可用 · 难度：⭐⭐⭐

📝 题目

在为 3000 人规模的企业部署基于 Milvus 单机版的 RAG 系统时，为什么必须在应用层设计一个“逃生通道”（降级方案），比如在 Milvus 宕机时自动切换到 PostgreSQL 的全文检索？这个降级方案的核心价值是什么？

💡 参考答案

▎一句话结论

“逃生通道”是企业级 AI 应用高可用的最后一道防线，它通过在核心向量数据库不可用时，自动降级到备用检索方案，确保了基本业务的连续性，将“服务不可用”的灾难降级为“体验下降”的可接受状态。

▎核心原理

  • 单点故障风险： 单机版 Milvus 虽然性价比高，但存在单点故障风险。物理机宕机、Docker 进程崩溃、磁盘满等任何问题都可能导致服务完全中断。
  • 业务连续性保障： 对于 HR 系统，员工查询政策、报销流程是刚需。如果因为 Milvus 故障导致整个客服系统瘫痪，会严重影响公司运营。逃生通道能在此时提供最基本的搜索服务，确保业务不断线。
  • 体验与成本的权衡： 逃生通道提供的全文检索方案在语义理解上远不如向量检索，但成本极低（复用已有数据库）。这是一种在紧急情况下，用“体验降级”换取“服务可用”的务实策略，远比构建一套成本高昂的向量数据库双活集群更经济。

▎深入解释

这就像一栋大楼的消防通道。平时大家上下楼都坐高速电梯（Milvus 向量检索，又快又好）。但一旦发生火灾（Milvus 宕机），电梯必须停用。这时，消防通道（PostgreSQL 全文检索）就成了唯一的生命线。虽然走楼梯又慢又累（体验差），但它能让你安全撤离（业务不断线）。你不能因为平时有电梯，就不建消防通道。同样，你不能因为 Milvus 性能强大且稳定，就不设计降级方案。这个方案的核心价值在于，它将一个影响公司全员、可能导致业务停滞的 P0 级事故，降级为一个部分用户可能感知到“搜索结果不太准”的 P2 级体验问题，为运维团队争取了宝贵的修复时间。

▎面试加分点

  • 可以提到，在代码中通过一个简单的配置开关或异常捕获就能实现，当捕获到连接 Milvus 超时或报错异常时，自动执行降级逻辑。
  • 可以补充，除了 PostgreSQL，轻量级的本地 Faiss 内存检索或 DuckDB 也可以作为更轻量的逃生通道。

▎常见误区

  • 误区：认为系统足够稳定，不需要降级方案。 墨菲定律告诉我们，任何可能出错的事，最终都会出错。高可用的核心不是保证 100% 不出事，而是出了事之后有预案。
  • 误区：降级方案只是一个临时补丁，不需要测试。 逃生通道必须定期进行故障演练，确保在真实事故发生时，它能被成功触发并正常工作。

📌 概念题 · Q10

考点标签

大模型应用 · 多模态输出 · 交互演进 · 难度：⭐⭐⭐

📝 题目

相比传统的文本流式输出，以 GPT-4o 的端到端语音流和 Claude 的 Artifacts 代码画布为代表的多模态输出模式，为 AI Agent 的产品交互带来了哪些本质上的革新？为什么说这是从“信息交付”到“原生体验”的跨越？

💡 参考答案

▎一句话结论

多模态输出模式将 AI 的交互从单一的“文本交付”升级为“原生多媒体体验”，通过直接输出语音、图像、可交互代码等富媒体，消除了传统 TTS 和独立渲染的中间环节，实现了更低延迟、更丰富情感和更强表现力的端到端全新交互范式。

▎核心原理

  • 消除中间层，降低延迟： 传统语音助手是“文本->TTS->语音”的级联模式，延迟高且丢失情感信息。端到端语音流模型（如 GPT-4o）直接从音频输入到音频输出，能捕捉语气、停顿，甚至笑声和歌声，交互体验更接近真人对话。
  • 交互范式的升维： 文本流是线性的、一维的。Artifacts 模式则在文本流之外，开辟了一个独立的、可交互的“画布”空间。模型可以一边用文字解释代码逻辑，一边在画布上实时渲染出 HTML 页面、SVG 图表或 React 组件，用户可以即时看到、操作和迭代结果。
  • 从信息到行动： 这种输出不再是给用户一段需要二次加工的信息，而是直接交付一个可用的“成品”。比如，一个图表生成 Agent 输出的不是描述图表的文字，而就是图表本身，用户可以直接截图或嵌入报告。

▎深入解释

传统的 AI 交互就像你看一本菜谱，它用文字告诉你“放适量盐，翻炒至金黄”，你需要自己想象和执行。多模态输出 则像一个大厨直接在你面前做菜，你不仅能听到他讲解（语音流），还能亲眼看到菜在锅里变色的过程（实时画布），甚至能尝一口告诉他咸淡，他立刻调整。这种交互是沉浸式的、同步的、多感官的。对于 Agent 产品而言，这意味着它可以直接生成一个交互式数据看板给领导，而不是一份文字分析报告；可以直接用带有同情和安慰的语气回复一位焦虑的员工，而不是一段冷冰冰的文本。它让 AI 从一个“文案写手”变成了一个“全栈创作者”。

▎面试加分点

  • 可以对比国内外差异：国外在多模态输出上走得更前沿，而国内产品目前更擅长用流式文本和强大的中间件平台来优化现有体验。
  • 可以展望，未来的 Agent 可能会融合更多模态，如直接输出 3D 模型、触觉反馈等，创造更拟人化的交互体验。

▎常见误区

  • 误区：将多模态输出简单等同于“能生成图片”。 其核心是端到端的原生生成和实时交互能力，而非独立模块的简单拼接。
  • 误区：认为这种模式会完全取代文本流。 在很多信息密度高、需要仔细阅读和逻辑分析的场景，文本流依然是最高效的交互方式。两者将长期共存，各司其职。

🛠 应用题 · Q1 · 架构设计

题型

架构设计

场景标签

Multi-Agent HR 业务 协同网络

📝 题目

你正在设计一个全功能的 HR 智能客服系统，该系统需要处理员工上传的医疗发票图片并回答报销问题。系统内部需要集成多模态识别、意图路由、RAG 知识库检索、追问填单和安全合规检查等多个独立功能。请设计一套 Multi-Agent 协同架构来处理这个复杂流程，并详细说明你如何避免将所有逻辑塞进单一 Prompt 导致的“模型过载”问题。

💡 参考答案

▎解题思路

  1. 问题拆解（分而治之）： 将一个复杂的报销咨询流程拆解为一系列独立的、可复用的原子能力（Agent 节点），每个节点只负责一个特定任务。
  2. 编排与路由（Orchestration）： 引入一个中心化的“路由 Agent”或状态机作为总控，负责理解全局意图，并根据上下文状态将任务像“传球”一样在不同的 Agent 节点间流转。
  3. 状态管理（有状态流转）： 设计一个全局的会话状态对象，用于在多个 Agent 节点间传递上下文、中间结果和缺失的参数，实现多轮对话的槽位填充。

▎详细方案

采用基于图的 Agent 协同网络架构，例如使用 LangGraph 构建一个有状态、有环的图。具体流程如下：

  1. 入口节点 - 多模态 Agent： 接收用户上传的图片和文本。它的唯一职责是调用视觉模型，将图片内容转化为结构化文本（例如：“这是一张成都市某三甲医院的门诊收费票据，金额500元”）。输出纯文本，传递给下游。
  2. 总控节点 - 意图路由 Agent： 接收多模态 Agent 的结果和用户原始问题。它的职责是根据预定义的“工具集”进行意图分类。在此场景中，它会识别出意图为 medical_reimbursement_query，并将任务路由到 RAG 检索节点。
  3. 知识节点 - RAG 检索 Agent： 被触发后，它使用意图和提取的关键信息（如“成都”、“门诊”）去向量数据库（如 Milvus）中检索《公司补充医疗保险白皮书》等内部政策文档，并返回精准的政策条款（如“成都地区门诊报销比例为80%”）。
  4. 交互节点 - 填单追问 Agent： 接收 RAG 节点返回的政策。它会分析政策的执行是否缺少必要参数（例如，政策规定“司龄不同，比例不同”，但当前上下文没有司龄信息）。如果缺参数，它会生成一个反问，如：“请问您入司满一年了吗？”，并将此反问返回给用户，同时将图状态挂起，等待用户补充信息。
  5. 安全节点 - 安全合规 Agent： 在最终回复生成前，对所有输出内容进行审查。它检查回复中是否包含其他员工的隐私信息、是否使用了不当的绝对化承诺词语，确保输出符合公司合规要求。通过后，才将最终回复输出给用户。

▎关键细节 & 踩坑点

  • 状态对象的精妙设计： 会话状态对象（State）是核心。它需要在所有节点间共享，存储 messages（完整对话历史）、extracted_info（如金额、医院名）、intent、missing_slots（缺省参数列表）等。所有节点的读写都围绕这个对象进行。
  • 路由 Agent 的兜底策略： 必须为路由 Agent 定义一个“兜底工具”，例如 fallback_to_general_qa。当用户问了一个超出所有预定义工具范围的问题时（如“讲个笑话”），路由 Agent 能将其导向通用对话能力，而不是报错或产生幻觉。
  • 追问与重入： 当追问 Agent 反问用户后，用户的下一轮回复必须能够携带上一次的上下文，重新进入意图路由节点或直接进入填单追问节点，完成参数补齐的闭环。这是一个典型的“人机协同”循环。

▎可扩展优化

  • 引入评估节点： 在安全节点后，可以增加一个“质量评估 Agent”，使用另一个更强大的模型对最终回复的质量、准确性和共情能力进行打分，低于阈值的回复将被重写或转人工。
  • 工具集动态化： 将 Agent 的能力（如 RAG检索、填单追问）注册为一个动态的“工具库”。意图路由 Agent 可以基于工具的描述动态选择，当公司政策或业务流程变化时，只需增加或修改工具定义，无需改动主流程架构。

题型

场景分析

场景标签

数据库选型 混合检索 成本优化

📝 题目

你正在为一家公司从零搭建一个“社媒内容运营 Agent”，它需要存储和分析结构化数据（如任务状态、发布时间、发布渠道）、半结构化数据（如动态变化的文章标签、AI 生成的摘要、用户画像）以及非结构化的向量数据（用于爆款文案的语义检索）。团队规模小，运维资源有限。请分析并对比“PostgreSQL + pgvector”一体化方案与“MySQL + Redis + Milvus”组合方案的优劣，并给出你的最终选型和依据。

💡 参考答案

▎解题思路

  1. 需求拆解： 明确业务需要处理的数据类型：结构化（关系型）、半结构化（JSON 文档）、向量化（Embedding）。
  2. 方案对比： 从功能覆盖度、数据一致性、运维复杂度、总体拥有成本（TCO）四个维度，对两种方案进行对比分析。
  3. 决策权衡： 在“术业有专攻”和“一个打十个”之间，根据团队规模和业务阶段做出最务实的权衡。

▎详细方案

  • 方案一：MySQL + Redis + Milvus（组合方案）

    • 优势： 各个组件在其专业领域内性能极致。MySQL 处理关系型事务极强，Redis 提供亚毫秒级缓存，Milvus 专为十亿级向量检索设计，性能天花板极高。
    • 劣势：
      1. 运维噩梦： 需要独立部署、监控、备份和升级三个不同的有状态服务，对运维能力要求极高，与我们“小团队”的现状严重不符。
      2. 数据同步延迟： 结构化数据和向量数据存储在不同数据库，天然存在数据同步延迟和一致性问题。例如，一个文案的状态在 MySQL 中已更新为“已发布”，但 Milvus 中的对应向量可能因同步延迟而未被及时更新。
      3. 成本高昂： 需要为这三个服务预留额外的服务器资源和维护人力，TCO 显著增加。

  • 方案二：PostgreSQL + pgvector（一体化方案）

    • 优势：
      1. 功能三合一： 一套数据库实例即可通过传统 SQL 处理结构化业务，通过 JSONB 列高效处理半结构化的动态标签和元数据，通过 pgvector 插件原生支持向量存储和相似度检索。完美覆盖所有需求。
      2. 数据强一致性： 所有数据都在同一个数据库的事务管理之下。你可以轻松地用一条 SQL 语句实现“混合检索”：在 WHERE 子句中过滤出“成都本地、近30天内”的硬性条件，同时在 ORDER BY 子句中使用余弦相似度操作符 <=> 对向量字段进行排序。这一切都在一个原子事务内完成，无延迟，无一致性问题。
      3. 运维极简： 团队只需维护一套数据库系统，备份、恢复、高可用方案都只需做一次，极大地降低了运维成本和心智负担。
    • 劣势： 在向量规模达到数十亿级别时，其检索性能可能不及专门为此设计的 Milvus。但对于社媒内容运营场景下，百万到千万级的文案库，其性能绰绰有余。

▎关键细节 & 踩坑点

  • 混合检索的实现： 这是方案二的核心亮点。在面试中必须清晰地描述出 SELECT content FROM articles WHERE region='成都' AND publish_date > now()-interval '30 days' ORDER BY embedding <=> query_vector LIMIT 10; 这样的 SQL 语句，这体现了架构师思维。
  • JSONB 与 GIN 索引： 强调 JSONB 不是简单的文本存储，它支持 GIN 索引，能对 JSON 文档内部的 key-value 进行快速搜索，这是普通 JSON 或 TEXT 字段做不到的。

▎可扩展优化

  • 读写分离与缓存： 当业务量增长后，可以为 PostgreSQL 配置一主多从的读写分离集群。同时，可以在应用层引入 Redis 作为查询缓存，缓存高频的政策文档或热门向量检索结果，进一步降低数据库负载，但数据库本身依然是单一核心，运维复杂度可控。
  • 平滑迁移路径： 如果未来数据量真的膨胀到单机 PgSQL 无法承受的百亿级别，可以基于目前的架构，将 pgvector 部分平滑迁移到专门的 Milvus 集群，而业务和半结构化数据依然保留在 PgSQL 中。这是一种务实的、可演进的架构。

🛠 应用题 · Q3 · 工程实现

题型

工程实现

场景标签

Agent 安全 SQL 操作 沙箱隔离

📝 题目

你的“HR 智能招聘 Agent”需要具备一个新功能：能够根据用户（HR）的自然语言指令，自动查询公司的简历库数据库。例如，HR 说：“帮我找出过去一个月投递的、有3年以上 Java 经验的候选人”。但是，直接让大模型生成并执行 SQL 存在巨大的安全风险。请设计一个安全的、带有人类反馈环节的 Agent 操作数据库的工程实现方案，并说明如何构建执行沙箱。

💡 参考答案

▎解题思路

  1. 权限最小化： 绝对不给 Agent 直接连接生产数据库的、拥有增删改权限的账号。
  2. 读/写分离与管控： 对 Agent 的操作进行严格分级。读取操作可以半自动化，但任何增、删、改操作必须引入人类审批节点。
  3. 沙箱隔离： Agent 的所有代码执行（包括 SQL）必须在受限的沙箱环境中进行，防止其“幻觉”破坏系统。

▎详细方案

采用“Agent 生成草案 -> 人类确认 -> 沙箱执行”的三段式安全架构。

  1. SQL 生成与预检（Agent 侧）：

    • 意图解析： Agent 解析 HR 的自然语言，将其转化为 SQL 草案。
    • 安全预检（静态分析）： 在 Agent 生成 SQL 后、展示给 HR 前，后端代码必须对 SQL 字符串进行静态分析。使用正则或简单的 SQL Parser，检查 SQL 中是否包含 INSERT, UPDATE, DELETE, DROP, TRUNCATE 等危险关键字。
    • 只读拦截： 如果检测到任何写操作关键字，Agent 直接回复：“抱歉，我无法执行修改数据的操作。请手动处理。” 如果通过检查，则进入下一步。

  2. 人类反馈与确认（Human-in-the-loop）：

    • 草案展示： 将通过安全预检的 SQL 草案清晰地展示给 HR，并附带自然语言的解释。例如：“我将执行以下查询：SELECT * FROM candidates WHERE ... LIMIT 50，是否确认？”
    • 确认机制： 提供一个明确的“确认执行”按钮。只有 HR 点击确认后，后端才会真正发送 SQL 去执行。这是一个不可绕过的同步阻断点。

  3. 沙箱化执行（后端侧）：

    • 创建只读数据库账号： 专门为 Agent 服务创建一个数据库用户，该用户只被 GRANT SELECT 权限在指定的、脱敏过的视图或表上。Agent 服务全程使用这个只读账号连接数据库。
    • 构建执行沙箱（隔离环境）： 即使有了只读账号，也要防止 Agent 执行恶意查询（如 SELECT * FROM candidates 可能拖垮数据库）。因此，SQL 执行逻辑被封装在一个独立的 Docker 容器中。这个容器：
      • 网络隔离： 只有访问指定数据库（通过内网 DNS 和防火墙规则）的权限，无法访问外网或其他内部服务。
      • 资源限制： 启动时通过 Docker 参数严格限制 CPU 和内存使用量，防止 Agent 写出笛卡尔积查询导致服务器 OOM。
      • 查询超时： 在 SQL 执行层面设置严格的超时时间（如 statement_timeout），超过 5 秒的查询自动终止。

▎关键细节 & 踩坑点

  • SQL 注入防御： 绝对不能使用字符串拼接的方式来构建 SQL 查询！必须使用参数化查询。Agent 生成的是参数（如 city = 'Chengdu'），后端代码将参数安全地绑定到预编译的 SQL 模板中。
  • 数据脱敏： 即使查询成功，返回给 Agent 和 HR 的数据也应该经过脱敏处理。例如，候选人的手机号中间四位应显示为 ****。这可以在数据库视图层或应用层实现。
  • 审计日志： 所有 Agent 发起的查询（包括被HR拒绝的草案）都必须记录完整的审计日志，包括时间、HR 账号、原始指令、生成的 SQL 草案、最终执行的 SQL 和结果摘要，以备合规审查。

▎可扩展优化

  • 智能 SQL 优化： Agent 在生成 SQL 后，可以增加一个“优化节点”，由另一个专门微调过的模型或规则引擎，为 SQL 自动添加 LIMIT、优化索引提示等，防止慢查询。
  • 动态权限矩阵： 将数据权限与 HR 的角色绑定。例如，初级 HR 的 Agent 只能查询公开简历库，而高级 HR 的 Agent 可以查询公司内部人才库。这个权限矩阵在人类确认环节进行校验。

题型

排障优化

场景标签

高并发 状态防撞墙 PostgreSQL

📝 题目

你的“社媒内容运营 Agent”系统在生产环境中运行，该系统有多个并发的 Agent 节点同时在分析热点并生成文案。一天，运营人员反馈，系统经常出现“多个 Agent 节点同时抢到同一个热点话题并生成了重复文案”的现象，导致内容同质化严重。请分析这个问题的根本原因，并提出至少两种解决方案，重点说明如何利用数据库的特性来实现“状态防撞墙”。

💡 参考答案

▎解题思路

  1. 问题定性： 这是一个典型的分布式并发冲突问题。多个工作节点（Agent）在没有协调机制的情况下，同时对一个共享资源（热点话题）执行“检查-执行”操作，导致竞态条件。
  2. 解决路径： 核心思路是将“抢占话题”这个操作变成一个原子性操作。可以通过数据库层面的悲观锁、乐观锁或引入分布式锁中间件来实现。
  3. 方案对比： 在已有 PostgreSQL 的架构下，优先利用数据库自身能力解决，避免引入新的中间件，降低系统复杂度。

▎详细方案

  • 方案一：数据库悲观锁（SELECT ... FOR UPDATE）【推荐】

    • 原理： 利用数据库的行级锁，将“查询并锁定一个未处理的话题”变成一个不可分割的事务。
    • 实现：
      1. 每个 Agent 节点在领取任务时，开启一个数据库事务。
      2. 执行 SELECT * FROM hot_topics WHERE status = 'pending' ORDER BY heat_score DESC LIMIT 1 FOR UPDATE SKIP LOCKED;。
      3. FOR UPDATE 会对查询到的行加上排他锁，其他并发事务无法再对同一行加锁或修改。
      4. SKIP LOCKED 是关键！它告诉数据库，如果目标行已经被其他事务锁定，就跳过它，直接查找下一条符合条件的记录。这避免了其他节点被阻塞等待，实现了高效的任务分发。
      5. 成功获取到行锁的节点，立即将该行 status 更新为 processing，并记录自己的节点 ID。然后提交事务。
    • 优点： 强一致性，绝对不会出现多个节点抢到同一个任务的情况。逻辑简单可靠，完全由成熟稳定的数据库机制保证。

  • 方案二：数据库乐观锁（基于版本号）

    • 原理： 在“热点话题”表中增加一个 version 字段（整数类型）。更新时通过比对版本号来判断是否有人捷足先登。
    • 实现：
      1. 节点 A 查询出一个 status='pending' 且 id=100 的话题，此时 version=1。
      2. 节点 A 尝试更新：UPDATE hot_topics SET status='processing', version=2 WHERE id=100 AND version=1;。
      3. 如果更新影响行数为 1，说明抢占成功。如果影响行数为 0，说明在 A 查询后、更新前的瞬间，另一个节点 B 已经抢先更新了，导致 version 不再是 1。此时 A 需要重新查询下一个任务。
    • 优点： 没有锁等待开销，性能更高。
    • 缺点： 需要编写重试逻辑，在高并发冲突激烈的场景下，大量节点会反复重试，浪费资源。对于“抢占任务”这个场景，悲观锁的 SKIP LOCKED 模式效率更高。

▎关键细节 & 踩坑点

  • 事务范围： 悲观锁方案中，SELECT ... FOR UPDATE 和 UPDATE 必须在同一个数据库事务中完成，锁会在事务提交后释放。事务要尽可能小，避免长事务阻塞其他节点。
  • 索引的重要性： WHERE status = 'pending' 这个条件必须要有索引支持，否则数据库会扫描全表，性能极差。SKIP LOCKED 配合索引能实现毫秒级的任务分发。
  • 死锁预防： 如果 Agent 需要同时锁定多个资源（如话题和对应的素材库），必须保证所有节点都以相同的顺序访问资源，防止循环等待造成死锁。

▎可扩展优化

  • 任务状态机： 将 status 字段设计为一个完整的状态机：pending -> processing -> generating -> completed / failed。并增加 heartbeat_time 字段。如果一个任务长时间处于 processing 状态，说明该节点可能宕机了，可以有一个定时任务将这些“僵死”的任务状态重置回 pending，实现故障恢复。
  • 引入 Redis 分布式锁： 如果未来系统架构变得极其复杂，跨越了多个不同的数据源，可以引入 Redis 的 SETNX 命令来实现一个轻量级的分布式锁。但在当前场景下，数据库锁是最简单、最一致的选择。

🛠 应用题 · Q5 · 综合落地

题型

综合落地

场景标签

项目交付 HR 招聘 从0到1

📝 题目

你作为项目负责人，需要从 0 到 1 交付一个“HR 日常简历筛选与匹配 Agent”。该 Agent 的核心目标是替代 HR 80% 的重复性简历初筛工作。它需要能解析 PDF/Word 格式的简历，根据岗位 JD 进行匹配打分并生成推荐报告，还能结合公司过往招聘记录进行面试画像总结，最后将报告推送给业务领导审批。请给出你的完整项目交付思路，包括关键阶段、技术选型和风险预案。

💡 参考答案

▎解题思路

  1. 业务闭环设计： 不能只做一个“匹配打分”的功能，必须打通从“简历流入”到“报告推送”的完整业务流，形成闭环。
  2. MVP 优先，逐步迭代： 先跑通核心的“解析-匹配-报告”链路，再逐步引入“历史画像”、“人才库回溯”等高级功能。
  3. 人类角色前置： 明确这是一个“提效”工具而非“替代”工具，在关键决策点（推送领导前）必须设计 HR 的审核与介入环节。

▎详细方案

项目分为四个核心阶段：

阶段一：MVP 核心链路（解析-匹配-报告）
- 简历解析服务： 部署一个专门的解析微服务，内部集成 PyMuPDF、python-docx 等库，将各种格式的简历统一提取为结构化文本。对于复杂格式，引入一个轻量级的多模态模型进行辅助识别，确保关键信息（姓名、电话、工作经历、技能栈）的提取准确率。
- 智能匹配引擎： 这是 Agent 的大脑。
1. JD 结构化： 同样用大模型将非结构化的岗位 JD 解析为结构化的“技能标签”、“经验要求”、“学历要求”等。
2. 混合匹配策略：
- 硬性条件过滤： 使用规则引擎（或简单的 SQL 查询）过滤掉不满足学历、工作年限等硬性指标的候选人。
- 语义相似度匹配： 将简历和 JD 的关键信息（如技能、项目经验）通过 Embedding 模型向量化，存入 pgvector，计算余弦相似度，得出软性技能的匹配得分。
3. 报告生成： 将匹配得分、匹配上的关键点、简历摘要通过 Prompt 模板喂给大模型，生成一份包含“匹配度评分”、“核心优势”、“风险点”的结构化推荐报告。

阶段二：业务流与人工审核（推送-审批）
- 任务队列： 当 Agent 为一个岗位筛选出 Top N 候选人后，不直接推送。而是将这些候选人和报告放入一个“待审阅”队列，在 HR 的工作台上高亮显示。
- HR 审核工作台： HR 可以看到 Agent 的推荐理由，并在线查看简历原文。HR 可以执行“通过”、“驳回（并填写原因）”、“调整优先级”等操作。这个环节是数据飞轮的起点，HR 的反馈会被记录下来。
- 一键推送： HR 审核通过的候选人及其报告，通过调用内部 OA 或企业微信 API，一键推送给对应的业务领导。

阶段三：数据飞轮与高级功能
- 历史画像集成： 对接公司历史招聘数据库，Agent 可以分析“成功入职且绩效为A的候选人”的共同特征，生成“面试官画像”或“成功候选人模型”，用于优化匹配算法的权重。
- 人才库回溯： 当发布新岗位时，Agent 自动在“一个月内投递过但未通过的其他岗位简历库”中进行二次检索，盘活历史简历资源。

阶段四：监控、优化与安全
- 效果监控： 建立业务看板，监控“简历处理时长”、“HR 采纳率”、“推送后领导的面试邀约率”等核心指标。
- 数据安全： 所有简历数据在落盘时加密，数据库访问权限严格控制。定期自动清理超过一定周期的简历文件，遵循数据最小化原则。

▎关键细节 & 踩坑点

  • 简历解析是第一道鬼门关： PDF 的格式千奇百怪（双栏、表格、图片），解析准确率直接决定了后续所有环节的质量。必须投入足够精力做解析层的鲁棒性，甚至针对高频的简历模板做专门优化。
  • 匹配模型的可解释性： 不能只给出一个分数。必须通过 Prompt 工程，让大模型明确指出“因为候选人A有3年Java经验，符合JD要求，所以加分”，这样才能赢得 HR 的信任。
  • 冷启动问题： 初期没有“成功候选人”数据，如何画像？可以先基于 JD 本身和资深 HR 的经验，手动构建一个初始的“理想候选人画像”作为种子。
