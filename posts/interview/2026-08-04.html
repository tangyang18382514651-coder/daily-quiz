📌 概念题 · Q1

考点标签

Agent架构 · 难度：⭐⭐⭐

📝 题目

在 Agent 工程架构中，Harness（缰绳/控制面）和 Runtime（马车/执行面）的职责边界经常被混淆。请说明两者的核心区别，以及为什么说“Harness 挂了会导致 Agent 逻辑死循环，而 Runtime 挂了只会导致权限不足或环境超时”？

💡 参考答案

▎一句话结论

Harness 是 Agent 的“大脑中枢”，负责业务逻辑、流程编排与决策路由；Runtime 是“物理躯干”，负责安全隔离的执行环境与基础设施支撑。两者的本质区别在于：Harness 关心“怎么想、怎么走”，Runtime 关心“在哪跑、拿啥干”。

▎核心原理

  • Harness 承载状态机路由、动态 Prompt 组装、LLM 输出的 JSON/工具调用解析，是业务逻辑的绝对核心
  • Runtime 提供 Docker/WASM 代码执行沙盒、数据库持久化连接（Checkpointer）、外部 API 实际调用，是纯粹的执行层
  • Harness 满载业务逻辑，任何错误都会导致 Agent 理解错误或陷入死循环；Runtime 纯粹不关心业务，只负责“安全地执行”

▎深入解释

可以把 Harness 理解为一个自动驾驶系统的“决策规划模块”——它实时读取地图（State）、判断路况（用户输入）、决定变道还是刹车（工具调用）。如果这个模块挂了，车辆会做出错误决策，比如在高速上突然左转。而 Runtime 是“底层车辆控制系统”——它只负责执行“刹车力度 30%”这样的指令，不关心为什么要刹车。如果 Runtime 挂了，表现是刹车失灵或油门卡死（权限不足/超时），但不会主动做出错误决策。

在 LangGraph 等现代 Agent 框架中，Harness 通常体现为状态图定义（Graph）、节点逻辑（Node）、条件边（Conditional Edge）；Runtime 则体现为 Checkpointer 的数据库连接、工具执行时的容器隔离环境。这种分离设计使得业务逻辑可以独立迭代，而执行环境可以统一加固安全策略。

▎面试加分点

  • 能举出具体故障场景：Harness 故障 = Prompt 注入导致无限重试循环；Runtime 故障 = 沙箱超时导致工具调用失败
  • 理解这种分离是“关注点分离（Separation of Concerns）”在 Agent 架构中的核心实践
  • 能关联到 LangGraph 的 StateGraph（Harness）与 Checkpointer/ToolExecutor（Runtime）的具体对应关系

▎常见误区

  • 误以为 Runtime 只是“运行代码的地方”，忽略了它还包括数据库连接管理、外部 API 网关等基础设施
  • 把 Tool 调用逻辑（属于 Harness 的决策范畴）和 Tool 执行环境（属于 Runtime）混为一谈

📌 概念题 · Q2

考点标签

模型量化 · 难度：⭐⭐⭐

📝 题目

模型量化的核心公式中涉及 S（Scale，缩放因子）和 Z（Zero-point，零点）两个关键参数。请说明它们的物理含义，以及为什么“离群点（Outliers）”是量化过程中最大的精度杀手？

💡 参考答案

▎一句话结论

S（Scale）决定量化后的步长精度，Z（Zero-point）确保浮点 0 值在整数空间的精确映射；离群点之所以是精度杀手，是因为它们会迫使 S 扩大覆盖范围，导致中间密集区域的量化粒度变粗，大量微小细节被“抹平”。

▎核心原理

  • S = (max_float - min_float) / (max_int - min_int)，决定了每个整数值代表多大的浮点跨度
  • Z 的作用是保证浮点数中的 0 能被整数空间中的一个精确值表示，这对神经网络中大量的零值填充和 ReLU 激活至关重要
  • 离群点（如某个权重值高达 100，而 99% 的权重在 [-1, 1] 之间）会强制 max_float 拉大到 100，导致 S 变大，中间密集区域的精度被牺牲

▎深入解释

想象你有一把尺子，要测量从 0.01 毫米到 1 米的物体。如果尺子总共有 256 个刻度（INT8），正常情况下你可以精确到毫米级。但如果你必须同时测量一个 100 米高的建筑（离群点），这把尺子的刻度范围必须拉大到 0-100 米，此时每个刻度代表约 0.4 米——你再也无法区分 1 毫米和 2 毫米的差异了。

这就是离群点对量化的破坏机制。Transformer 架构中的某些激活值或权重通道确实存在这种极端分布，尤其是在 FFN 层的某些神经元上。现代量化算法（如 AWQ、GPTQ）的核心突破，就是识别出这些“关键离群通道”，对它们保留 FP16 精度或分配更高的量化范围，而对其余 99% 的普通权重进行激进的低比特量化。AWQ 通过分析激活值的分布自动发现这些通道，GPTQ 则通过逐层重建误差来补偿量化损失。

▎面试加分点

  • 能解释为什么 INT8 量化通常精度损失极小（<1%），而 INT4 需要 AWQ/GPTQ 等高级算法才能保持可用精度
  • 理解“量化不是纯数学问题，而是寻找冗余的艺术”——Transformer 的鲁棒性天然容忍一定精度损失
  • 能关联到实际部署：名字后缀带 -AWQ 或 -GPTQ 的模型包，直接下载就能用 vLLM 部署

▎常见误区

  • 以为量化就是简单的四舍五入，忽略了 S 和 Z 的动态计算过程
  • 认为所有层的量化敏感度相同——实际上 Embedding 层和最后输出层通常需要保留更高精度

📌 概念题 · Q3

考点标签

Graph RAG · 难度：⭐⭐⭐⭐

📝 题目

Graph RAG 的构建流程中有一个关键步骤叫“社区发现（Community Detection）”，通常使用 Leiden 算法。请说明为什么需要做社区发现，以及 Global 查询和 Local 查询在 Graph RAG 中的核心区别是什么？

💡 参考答案

▎一句话结论

社区发现是将大规模知识图谱中的实体和关系自动聚类成“语义阵营”的过程，目的是为 Global 查询提供宏观摘要；Local 查询依赖实体嵌入的向量相似度召回周边子图，回答具体事实问题；Global 查询则直接喂入全部社区摘要，回答全局关系、趋势类问题。

▎核心原理

  • 社区发现（Leiden 算法）是纯数学的图聚类过程，不依赖语义理解，仅基于图的拓扑结构将紧密连接的节点归为一个社区
  • 每个社区生成一个 LLM 摘要，描述该社区内实体的核心关系和主题，这些摘要是 Global 查询的“压缩知识单元”
  • Local 查询：问题 Embedding → 匹配实体 Embedding → 召回实体周边的图关系 → 将子图信息塞给 LLM 回答
  • Global 查询：直接喂入全部社区摘要给 LLM，让其从宏观视角综合回答

▎深入解释

以《三国演义》为例，Graph RAG 会先抽取实体（刘备、关羽、曹操、赤壁之战）和关系（结拜、敌对、参与）。Leiden 算法会发现：刘备、关羽、张飞、诸葛亮形成一个紧密连接的“蜀汉社区”；曹操、司马懿、许褚形成“曹魏社区”。然后 LLM 为每个社区生成摘要：“蜀汉社区以刘备为核心，核心成员包括关羽、张飞、诸葛亮，主要活动围绕建立蜀汉政权展开”。

当用户问“关羽和刘备是什么关系？”（Local 查询），系统通过 Embedding 匹配到关羽、刘备两个实体，提取他们周边的直接关系（结拜兄弟、君臣），精准回答。当用户问“三国鼎立的格局是如何形成的？”（Global 查询），系统直接把蜀汉、曹魏、东吴三个社区的摘要全部喂给 LLM，让它从宏观视角综合回答。

▎面试加分点

  • 理解 Leiden 算法相比 Louvain 的优势：保证社区内部连通性，避免产生“断连社区”
  • 能指出原生 Graph RAG 的缺陷：构建社区消耗 Token 极大、关系抽取错误会满盘皆输、LLM 幻觉无修复机会
  • 能对比 Light RAG 的改进：引入 Gleaning 补充校验、High/Low 双路检索、Native 检索兜底

▎常见误区

  • 以为社区发现需要 LLM 理解语义——它纯基于图拓扑的数学计算，效率极高
  • 混淆 Local 和 Global 查询的适用场景：具体人物/事件用 Local，宏观趋势/整体格局用 Global

📌 概念题 · Q4

考点标签

Agent通信 · 难度：⭐⭐⭐⭐

📝 题目

现代多 Agent 架构（如 LangGraph）不再让 Agent 之间直接“加好友发消息”，而是通过共享全局 State 对象进行通信。请说明这种“基于共享状态的通信模式”相比传统 Agent 点对点通信的核心优势，以及 Fan-out/Fan-in 模式如何实现并行任务分发与汇聚？

💡 参考答案

▎一句话结论

基于共享 State 的通信模式将多 Agent 协作变成“拼图游戏”——每个 Agent 只读写全局账本，不直接对话，实现了彻底的解耦和可观测性；Fan-out 将一个节点同时连向多个 Agent 实现并行分发，Fan-in 则阻塞等待所有并行节点完成后才唤醒汇总 Agent。

▎核心原理

  • 全局 State 是唯一的数据真相源（Single Source of Truth），所有 Agent 的输入输出都写入 State，避免信息孤岛
  • Agent 之间的流转由“图的边（Edges）”控制，而非硬编码的调用关系：串行靠条件边自动触发，循环靠反向边实现打回重改
  • Fan-out：一个节点同时连向多个 Agent（如小红书 Agent、抖音 Agent），LangGraph 自动开启多线程并行执行
  • Fan-in：汇总 Agent 进入阻塞等待，直到所有并行 Agent 把结果写回 State 列表后才被唤醒

▎深入解释

传统 Agent 点对点通信像“打电话”——Agent A 必须知道 Agent B 的地址、接口格式，一旦 B 挂了或接口变了，A 也跟着崩。基于共享 State 的模式像“公告板”——每个 Agent 只关心公告板上自己需要的信息，写完结果就贴回去，下一个 Agent 由图的连线自动唤醒。

以自媒体一键分发多平台为例：主 Agent 完成文案后触发 Fan-out，同时启动小红书 Agent、抖音 Agent、微博 Agent。这三个 Agent 并行执行，各自根据平台调性改写文案，把结果写入 State 的一个 list 字段中。汇总 Agent 在 Fan-in 节点等待，直到 list 中三个平台的结果都到齐，才被唤醒进行打包和发布。

这种模式的核心优势是：① 新增平台只需在图中加一个节点和连线，不影响现有 Agent；② 所有中间状态都记录在 State 中，任何环节出错都能精准定位；③ 天然支持 Human-in-the-loop，人工可以在任意节点介入修改 State。

▎面试加分点

  • 能指出高并发场景下，State 对象需要借助 Redis 或数据库实现跨进程共享，而非单机内存
  • 理解 Fan-out/In 的底层实现：LangGraph 使用 Python 的 asyncio 或 threading 实现并发
  • 能对比传统微服务编排（如 Temporal、Airflow）与 LangGraph 在 Agent 通信上的异同

▎常见误区

  • 以为 State 只是一个简单的 dict——它包含 Channel 机制，支持并发写入时的冲突合并策略
  • 忽略循环通信中的“无限循环风险”——必须设置最大重试次数或人工介入节点作为终止条件

📌 概念题 · Q5

考点标签

数据安全 · 难度：⭐⭐⭐

📝 题目

在智能销售/客服 Agent 调用内部数据库查询历史客户成交案例时，必须经过一个独立的“动态脱敏层（Data Masking Gateway）”。请说明这个脱敏层的核心处理流程，以及为什么不能把脱敏逻辑直接写死在 SQL 查询语句或 Agent 的 Prompt 里？

💡 参考答案

▎一句话结论

动态脱敏层的核心流程是：识别查询意图 → 提取客户标签 → 查询数据库 → 自动替换敏感字段 → 将脱敏结果塞回 LLM Context；独立成层的原因是脱敏规则需要统一管控、动态更新，且不能依赖 LLM 的“自觉性”来保护隐私。

▎核心原理

  • 步骤 A：Agent 提取当前客户的标签（行业、规模、痛点），作为查询条件
  • 步骤 B：调用传统数据库 API，检索匹配的成功案例原始数据
  • 步骤 C：脱敏层自动将敏感信息（公司名、负责人电话、财务数字）替换为泛化表述（“某成都头部团购平台”、“张总”、“数百万流水”）
  • 步骤 D：将脱敏后的结构化数据塞回 LLM Context，由模型润色输出

▎深入解释

为什么不能把脱敏逻辑写死在 SQL 里？因为脱敏规则是动态变化的——比如《个人信息保护法》更新后，某些字段的脱敏方式需要调整。如果脱敏逻辑散落在几十个 SQL 查询和 Prompt 模板中，改一个规则就要全量回归测试，这是运维噩梦。

为什么不能依赖 Prompt 让 LLM“自觉脱敏”？因为 LLM 不是安全组件，它可能因为 Prompt 注入攻击、上下文过长被截断、或模型幻觉而泄露敏感信息。安全策略必须由确定性的代码网关强制执行，不能交给概率性的模型“自觉”。

独立脱敏层的架构优势：① 统一管控：所有数据库查询结果必须经过脱敏层才能到达 LLM，形成一道不可绕过的安全闸门；② 审计可追溯：每次脱敏操作都有日志，合规审查时能证明数据未被泄露；③ 灵活配置：不同角色（客服、销售、管理）可以有不同的脱敏级别，客服看到“张先生”，管理者可以看到全名。

▎面试加分点

  • 能提出脱敏层的实现方案：基于正则表达式 + NER 命名实体识别 + 可配置规则引擎
  • 理解“脱敏不是删除”——需要保持数据的业务可用性（如“某头部平台”仍能传达“我们有大客户经验”的信息）
  • 能关联到实际法规：《个人信息保护法》要求的最小必要原则，脱敏层是实现合规的关键技术手段

▎常见误区

  • 以为脱敏就是简单的字符串替换——需要考虑上下文一致性（同一实体的多次出现要保持相同的替换名）
  • 忽略脱敏层本身的性能开销——在高并发场景下，脱敏层可能成为瓶颈，需要缓存和异步处理

📌 概念题 · Q6

考点标签

数据飞轮 · 难度：⭐⭐⭐⭐

📝 题目

智能销售/客服系统中常提到“数据飞轮（Data Flywheel）”效应，即数据驱动业务持续进化的闭环。请说明数据飞轮的核心闭环逻辑，以及为什么“没有数据飞轮的 AI 系统是一潭死水”？

💡 参考答案

▎一句话结论

数据飞轮的核心闭环是：业务产生数据 → 数据清洗标注 → 反哺模型微调/RAG知识库 → 模型能力提升 → 业务效果更好 → 产生更多高价值数据；没有这个闭环，AI 系统只能依赖初始训练数据，无法适应业务变化，能力会随时间衰减。

▎核心原理

  • 数据输入层：每天成千上万条“AI 销售 vs 真实客户”的聊天语料、录音转写，持续涌入
  • 中台清洗层：利用轻量级大模型做自动化清洗工场，剔除无效对话、无意义语气词，自动打标签（成功案例、流失案例、异议未解决案例）
  • 知识沉淀层：清洗后的高价值数据，一方面沉淀为 RAG 知识库的新增文档，另一方面作为模型微调的黄金数据集
  • 模型进化层：用新数据定期微调模型，让模型学习最新的业务话术、客户痛点、行业黑话

▎深入解释

为什么没有数据飞轮的 AI 系统是“一潭死水”？因为业务环境是动态变化的——新的竞品出现、政策法规更新、客户需求演变。一个只用半年前数据训练的模型，面对今天的客户提问时，可能完全不知道“最近出台的 XX 政策”是什么，或者还在推荐已经下架的产品。

数据飞轮的价值不仅在于“让模型更准”，更在于它衍生出的商业想象空间。以销售场景为例：① 用销冠的高转化对话数据训练“AI 教练”，让新员工与 AI 客户对练，加速上手；② 分析客户拒绝的 Top 3 原因，直接反哺产品迭代；③ 对未成交客户进行标签化追踪，促销活动时精准二次唤醒。

从技术角度看，数据飞轮需要三个基础设施：① 数据采集管道（日志、数据库 CDC、API 埋点）；② 自动化标注流水线（基于规则 + 小模型 + 人工抽检）；③ 模型持续训练/更新平台（MLOps Pipeline）。缺任何一个环节，飞轮都转不起来。

▎面试加分点

  • 能指出数据飞轮的“冷启动”问题：初期没有足够数据时，需要先用专家规则 + 人工标注启动飞轮
  • 理解“数据飞轮”和“模型漂移（Model Drift）”的关系：飞轮是主动进化，漂移是被动退化
  • 能关联到实际业务指标：飞轮运转后，客服首响准确率、销售转化率应该有可量化的持续提升

▎常见误区

  • 以为数据飞轮就是“多收集数据”——核心是“清洗和标注”，原始日志 90% 是噪音
  • 忽略数据飞轮的“毒性循环”风险：如果模型给出的错误回答被当作正确数据回流，会越训越偏

📌 概念题 · Q7

考点标签

模型部署 · 难度：⭐⭐⭐

📝 题目

企业在本地部署大模型时，经常会按模型文件大小估算显存需求，结果上线后频繁 OOM。请说明大模型推理时的显存主要由哪几部分构成，以及为什么“模型文件 15G，用 16G 显存的卡就能跑”是一个危险的误解？

💡 参考答案

▎一句话结论

大模型推理显存 = 模型权重 + KV Cache（上下文缓存）+ 框架开销 + 中间激活值；模型权重只占一部分，KV Cache 随上下文长度和并发用户数线性增长，是 OOM 的主要元凶。

▎核心原理

  • 模型权重：FP16 下 1B 参数 ≈ 2GB，INT4 下 1B ≈ 0.5GB，这是最容易被计算的固定开销
  • KV Cache：Transformer 自注意力机制需要缓存每个 Token 的 Key 和 Value 矩阵，显存占用 = 2 × 层数 × 隐藏维度 × 上下文长度 × 并发批次
  • 框架开销：推理框架（vLLM、TensorRT-LLM）本身的内存管理、CUDA 上下文、PagedAttention 的块表等，通常占用 1-3GB
  • 中间激活值：推理过程中的临时张量，虽然比训练时小很多，但长上下文下仍不可忽略

▎深入解释

以 Qwen2.5-7B INT4 量化版为例：模型文件约 4.5GB，加载进显存后权重占约 5GB。如果只服务 1 个用户、上下文 2048 Token，KV Cache 约 1-2GB，总显存约 7-8GB，12G 显卡轻松应对。但如果同时服务 10 个用户、每个上下文 8192 Token，KV Cache 可能膨胀到 10-15GB，加上权重 5GB，总共 15-20GB——12G 显卡直接 OOM。

这就是为什么 vLLM 的 PagedAttention 技术如此重要：它把 KV Cache 分成固定大小的“页”，像操作系统管理虚拟内存一样管理显存，不连续存储、按需分配，大幅减少碎片化浪费。但即便如此，KV Cache 的物理上限仍由显存总量决定。

正确的显存估算逻辑：先算权重占用，再根据目标并发用户数 × 平均上下文长度估算 KV Cache 峰值，最后预留 20% 缓冲。例如：7B INT4 模型权重 5GB + 50 并发 × 4096 上下文约 8GB KV Cache = 13GB，选择 16GB 以上显存的卡。

▎面试加分点

  • 能说出 KV Cache 的计算公式，并现场估算一个具体场景的显存需求
  • 理解 PagedAttention 的核心思想：将 KV Cache 分页管理，减少碎片，提升显存利用率
  • 能指出长上下文（128K）场景下，KV Cache 可能比模型权重本身还大

▎常见误区

  • 只看模型文件大小买显卡，忽略了生产环境的并发和长上下文需求
  • 以为量化能解决所有显存问题——量化主要压缩权重，KV Cache 仍然是 FP16 精度

容器化部署 · 难度：⭐⭐⭐

📝 题目

在 LangGraph 多智能体项目中，推荐使用“多 Dockerfile 方案”为不同 Agent 节点（如路由 Agent、数据分析 Agent）打包独立镜像，而不是“单镜像 + 启动参数分化”。请说明多 Dockerfile 方案的核心优势，以及为什么路由 Agent 的镜像应该尽量保持轻量？

💡 参考答案

▎一句话结论

多 Dockerfile 方案的核心优势是“按需加载依赖”——每个 Agent 只安装自己需要的库，避免路由 Agent 的镜像因包含 torch、CUDA 等重依赖而变得臃肿；路由 Agent 保持轻量是因为它通常只做意图分类和图调度，不需要 GPU 和机器学习库，小镜像能加速 K8s 弹性伸缩时的容器拉取速度。

▎核心原理

  • 依赖隔离：数据分析 Agent 需要 torch、pandas、numpy、CUDA 驱动（镜像可能 5-8GB），路由 Agent 只需要 FastAPI + langgraph（镜像可能 300MB）
  • 启动速度：K8s 在扩容时，轻量路由 Agent 镜像拉取只需几秒，重量数据 Agent 镜像拉取可能需要几分钟
  • 安全最小化：每个镜像只暴露必要的端口和依赖，减少攻击面
  • 独立迭代：修改数据分析逻辑只需要重新构建 data_agent 镜像，不影响路由 Agent

▎深入解释

如果采用“单镜像 + 启动参数分化”方案，所有 Agent 共用一个包含全部依赖的通用镜像。这意味着路由 Agent 也要带着 5GB 的 torch 和 CUDA 库——它根本用不到这些，但每次 K8s 扩容一个路由 Pod 时，都要从镜像仓库拉取这个 5GB 的巨无霸。

在高并发场景下，这种差异是致命的。假设流量突增，K8s 需要在 30 秒内扩容 10 个路由 Pod 来分担流量。轻量镜像（300MB）30 秒内拉取完成，服务快速恢复；重量镜像（5GB）可能需要 3-5 分钟才能拉完，这期间用户已经在报错了。

多 Dockerfile 方案的实现也很简单：在 Monorepo 项目根目录下创建 Dockerfile.router 和 Dockerfile.data_agent，CI/CD 时用 docker build -f 分别构建。路由 Agent 的基础镜像用 python:3.10-slim（约 50MB），数据 Agent 用 nvidia/cuda:12.1-runtime-ubuntu22.04（约 2GB），各自只安装自己的依赖。

▎面试加分点

  • 能关联到 K8s 的镜像拉取策略（IfNotPresent vs Always）对冷启动时间的影响
  • 理解“解耦的关键在于 server/ 入口”——每个 Agent 通过 FastAPI 或 gRPC 封装成独立服务，通过网络通信
  • 能提出更激进的优化：路由 Agent 甚至可以打成 Distroless 镜像或使用 Alpine Linux，进一步压缩体积

▎常见误区

  • 以为“镜像越大功能越全越好”——镜像臃肿会拖慢整个 CI/CD 流水线和弹性伸缩响应
  • 忽略镜像层缓存优化：Dockerfile 中 COPY 依赖文件应该在 COPY 源码之前，利用层缓存加速构建

考点标签

Light RAG · 难度：⭐⭐⭐⭐

📝 题目

Light RAG 在原生 Graph RAG 的基础上引入了“Gleaning 补充校验”和“High/Low 双路检索”两个关键改进。请说明这两个改进分别解决了原生 Graph RAG 的什么痛点，以及 High 查询和 Low 查询的核心区别是什么？

💡 参考答案

▎一句话结论

Gleaning 补充校验解决了原生 Graph RAG “关系抽取错误满盘皆输”的痛点，通过二次校验补充遗漏的实体和关系；High/Low 双路检索解决了“单一向量检索无法区分宏观主题和具体关键词”的痛点，High 查询匹配抽象主题，Low 查询匹配核心关键词，两者互补。

▎核心原理

  • Gleaning 机制：在初步实体关系抽取后，LLM 再次扫描原文，检查是否有遗漏的关键实体或关系，进行补充和修正，降低一次抽取失败导致的级联错误
  • High 查询（抽象主题）：LLM 先提取用户问题的抽象主题（如“三国鼎立格局”），用实体向量化匹配相关社区节点，获取宏观关系
  • Low 查询（核心关键词）：LLM 提取问题的核心关键词（如“刘备、关羽”），用关系向量化匹配具体节点，获取微观关系
  • 最终结果去重合并：将 High、Low、Native（传统 RAG 原文检索）三路结果去重后喂给 LLM 生成答案

▎深入解释

原生 Graph RAG 最大的风险是“一步错，步步错”。如果在实体关系抽取阶段，LLM 把“关羽”和“刘备”的关系错误标注为“敌人”而非“结拜兄弟”，后续所有基于这个关系的查询都会给出错误答案，且没有修复机会。Gleaning 机制相当于给抽取结果加了一道“校对工序”——LLM 带着初步结果重新审视原文，问自己“我有没有漏掉什么重要的人？有没有关系标错了？”

High/Low 双路检索的设计灵感来自人类检索信息的方式。当你问“三国鼎立的格局如何形成？”，你的大脑会先定位“三国时期”这个宏观主题（High），然后在这个主题下搜索“赤壁之战”、“夷陵之战”等具体事件（Low）。单一向量检索只能做一种粒度的匹配，要么偏向宏观摘要，要么偏向微观细节，很难两者兼顾。

Light RAG 还保留了 Native 检索（直接查原文）作为兜底，防止图结构没有覆盖到的信息被遗漏。三路结果去重后，LLM 获得了多粒度的上下文，回答质量显著提升。

▎面试加分点

  • 能对比 Light RAG 和 Graph RAG 的 Token 消耗差异：Light RAG 不需要为全图做社区摘要，只在查询时动态检索，大幅降低构建成本
  • 理解 Gleaning 不是简单的“再问一次”，而是带着初步结果的上下文进行定向补充，更精准
  • 能指出 Light RAG 仍存在的局限：Gleaning 本身也消耗 Token，且无法 100% 消除 LLM 幻觉

▎常见误区

  • 以为 Gleaning 就是多跑一次抽取——它的关键是“带着初步结果”去校验，不是重复劳动
  • 混淆 High 查询和 Global 查询：High 是 Light RAG 的检索策略（动态匹配），Global 是 Graph RAG 的查询模式（喂入全部社区摘要）

📝 题目

在企业本地部署大模型时，业内反复强调“切忌算力焦虑”和“重数据轻模型”两条落地原则。请说明这两条原则的核心逻辑，以及为什么“把 80% 的精力花在清洗企业内部数据上，效果提升远比把模型从 32B 升级到 70B 显著”？

💡 参考答案

▎一句话结论

“切忌算力焦虑”的核心逻辑是：先用最低成本跑通业务闭环验证 ROI，再逐步升级硬件，避免一次性投入百万买 8 卡 B200 却发现业务根本用不上；“重数据轻模型”的核心逻辑是：大模型的通用能力已经足够强，决定业务效果上限的是你喂给它的私有数据的质量和覆盖度，而非模型参数量的边际提升。

▎核心原理

  • 算力焦虑陷阱：企业容易被“不用最强模型就会落后”的焦虑驱使，采购远超当前需求的硬件，结果机房供电、散热、运维团队都跟不上
  • 数据质量杠杆：企业内部 PDF、Excel、Wiki 中充满乱码、重复内容、过时信息，这些垃圾数据直接喂给 RAG，再强的模型也输出垃圾
  • 模型能力的边际递减：从 7B 到 32B 效果提升显著，但从 32B 到 70B 在大多数垂直场景（客服、文档检索）中提升有限，而硬件成本翻 3-5 倍
  • 数据飞轮效应：高质量私有数据能持续迭代，而模型参数是固定的——你今天清洗好的数据，明天换更好的模型依然能用

▎深入解释

“重数据轻模型”不是说不重视模型，而是强调“数据质量是木桶的最短板”。一个典型的反面案例：某企业花 60 万买了 4 卡 H200 跑 70B 模型做内部知识库问答，但喂进去的 PDF 是扫描件 OCR 转的，充满识别错误；Wiki 页面是 5 年前的，产品信息早已过时。结果员工问“最新的请假流程是什么？”，模型基于过时文档给出了已被废除的旧流程，被 HR 部门投诉。问题不在模型不够大，而在数据没清洗。

正确的落地策略是：先用 2 张 RTX 4090D（约 4-6 万）跑 Qwen2.5-32B INT4 量化版，选择一个高频痛点场景（如客服话术辅助）跑通闭环，验证业务价值。同时投入精力清洗数据：去重、纠错、分块优化、元数据标注。等业务 ROI 验证通过、数据质量达到一定标准后，再根据实际并发量和延迟要求评估是否需要升级硬件。

▎面试加分点

  • 能举出数据清洗的具体步骤：去重 → 格式标准化 → 乱码清除 → 语义分块（Chunking）→ 元数据标注
  • 理解“数据飞轮”和“重数据轻模型”的关系：高质量数据是飞轮转起来的燃料
  • 能指出硬件升级前必须先评估的三件事：机房供电（B200 8 卡 15kW）、散热方式（风冷 vs 液冷）、运维团队能力

▎常见误区

  • 把“重数据”理解为“多收集数据”——核心是“清洗和标注”，原始日志 90% 是噪音
  • 以为模型越大效果一定越好——在垂直场景中，32B + 高质量私有数据的效果往往优于 70B + 垃圾数据

题型

架构设计

场景标签

智能体通信 解耦 状态管理

📝 题目

你正在设计一个包含三个子 Agent 的智能客服系统：意图识别 Agent、订单处理 Agent 和 客诉安抚 Agent。系统要求当用户输入“我刚买的手机还没发货，我要退款！”时，意图识别 Agent 能判断出“退款”和“负面情绪”，并自动将任务先路由给客诉安抚 Agent，待其安抚成功并生成安抚摘要后，再将控制权连同摘要和原始意图交给订单处理 Agent 执行退款查询。

请设计这套多 Agent 系统的通信与编排架构。要求：
1. 阐述你选择的通信模型（如基于共享状态、消息队列或直接调用），并说明理由。
2. 画出核心的编排流程（可用文字描述状态图），说明如何实现“安抚完成”这个条件触发后续的“订单处理”。
3. 对比你选择的方案与传统的链式调用（A->B->C）的优势。

💡 参考答案

▎解题思路

  1. 确定通信模型： 面对异构 Agent（意图、安抚、订单），需要解耦和灵活的路由。基于知识库中的“共享状态 (State)”和“路由边 (Edges)”思想，采用基于全局状态的图编排模型是最佳选择。
  2. 设计编排流程： 将每个 Agent 视为图中的一个节点，通过条件边实现动态路由。关键点在于“安抚完成”是一个状态变更，需要由安抚 Agent 写回 State，并由图引擎根据此状态决定下一步的路由。
  3. 对比分析： 传统链式调用是硬编码的，无法应对“必须先安抚再处理”这种条件分支。基于状态的图编排天然支持循环、条件分支和动态路由，更灵活健壮。

▎详细方案

  1. 通信模型：基于共享状态的图编排（LangGraph 模型）
    - 全局状态对象 (State)： 定义一个 dict 或 TypedDict 作为全局账本，包含 user_input, intent, sentiment, appeasement_summary, order_status 等字段。
    - Agent 节点化： 每个 Agent 都是一个独立的节点函数，其签名均为 (State) -> State。它只从输入的 State 中读取需要的信息，执行完毕后将结果写回一个新的 State 字典并返回。
    - 图编排引擎： 使用 LangGraph 的 StateGraph 来构建和编译工作流。这负责维护状态、在节点间传递状态，并根据条件边决定下一个要执行的节点。

  2. 编排流程设计（状态图描述）
    - 节点定义：

    • intent_analyzer: 分析 user_input，输出 intent (如 refund) 和 sentiment (如 angry)。
    • empathy_agent: 读取 sentiment，执行安抚逻辑，生成 appeasement_summary 并写回 State。
    • order_agent: 读取 intent 和 appeasement_summary，查询订单信息并输出结果。
    • 图结构（边与路由）：
    • 入口 -> intent_analyzer 节点。
    • intent_analyzer 节点之后，是一个条件边。它检查 State 中的 sentiment 字段：
    • 如果 sentiment == "angry"，路由到 empathy_agent 节点。
    • 否则，直接路由到 order_agent 节点。
    • empathy_agent 节点执行完毕后，无条件地连接到 order_agent 节点。这就实现了“安抚完成”后自动触发订单处理的逻辑。
    • 流程示例： 用户输入“我要退款！” -> intent_analyzer 设置 intent=refund, sentiment=angry -> 条件边命中 angry -> 进入 empathy_agent，它执行安抚并设置 appeasement_summary="用户已安抚，赠送积分" -> 自动进入 order_agent，它看到摘要后，以更友好的方式查询并返回退款进度。

  3. 方案优势对比
    - 解耦与灵活路由： 链式调用是 A -> B -> C，无法处理 if angry then B else C 的逻辑。我们的方案通过条件边，实现了基于上下文（State）的动态路由，Agent 之间完全解耦。
    - 状态持久化与可恢复性： 全局 State 可以轻松集成 LangGraph 的 Checkpointer，将状态持久化到数据库。如果安抚 Agent 执行到一半服务重启，可以从断点恢复，而链式调用通常难以做到这一点。
    - 可扩展性： 未来若需增加一个“欺诈检测 Agent”在订单处理之前执行，只需在图中增加一个节点和一条边，无需修改任何现有 Agent 的代码。

▎关键细节 & 踩坑点

  • State 的不可变性： 在每个节点函数中，必须返回一个新的 State 对象（如 {**state, "new_key": value}），而不是修改传入的原始对象。这确保了状态的变更历史可追踪，是实现 Checkpoint 和人机交互的基础。
  • 条件边的逻辑健壮性： 条件路由函数必须能处理所有可能的 sentiment 值，包括 null 或未定义的情况，否则图编排会在运行时抛出异常。
  • 节点间的数据传递： 必须明确定义 State 的 Schema（如使用 TypedDict），让所有节点开发人员都清楚哪些字段是可读、哪些是必写的，避免因 Key 不匹配导致运行时错误。

▎可扩展优化

  • 并行处理： 如果意图识别 Agent 同时识别出“退款”和“投诉商品质量”，可以利用图的并行能力（Fan-out），同时将任务分发给 order_agent 和 quality_complaint_agent，最后汇总结果。
  • 人机协同 (Human-in-the-loop)： 在 empathy_agent 和 order_agent 之间，可以增加一个 interrupt 断点。当生成安抚摘要后，暂停图执行，等待人工客服审核摘要内容，审核通过后再继续执行订单处理，实现关键节点的安全把控。

Graph RAG 知识图谱 业务选型

📝 题目

你所在的公司是一家法律科技初创企业，拥有超过 10 万份的历史判决文书。产品部门提出了两个核心功能需求：
1. 全局分析： 律师输入“近五年知识产权案件的赔偿金额趋势如何？”，系统能总结出宏观趋势。
2. 细节检索： 律师输入“在‘某某科技公司诉某某网络公司不正当竞争案’中，法院对电子证据的采纳标准是什么？”，系统能精确回答具体细节。

你的团队正在评估使用 Graph RAG 还是 Light RAG 来构建底层知识库系统。请从这两种技术的构建流程、核心优势与原生缺陷出发，分析并推荐最适合当前需求的方案，并阐述你的理由。

💡 参考答案

▎解题思路

  1. 需求与能力映射： 将业务需求映射到两种 RAG 的技术特点上。全局分析对应 Graph RAG 的“社区摘要”能力，细节检索对应 Light RAG 的高效“双路径检索”能力。
  2. 技术对比分析： 深入对比两者在构建、查询和缺陷上的差异。Graph RAG 构建重、查询全局强；Light RAG 构建轻、查询细节快。
  3. 综合决策： 法律场景对细节准确性要求极高，而全局分析也是刚需。因此，不能简单二选一，需要给出一个既能满足双重需求，又能规避单一技术缺陷的组合方案或演进路线。

▎详细方案

  1. 需求与技术映射分析
    - 需求 1（全局分析） 恰好是 Graph RAG 的核心优势。Graph RAG 通过 Leiden 算法进行社区发现，并用 LLM 为每个社区生成摘要。当用户提出宏观问题时，系统可以直接检索这些社区摘要来回答，非常擅长处理“总结”、“趋势”类问题。
    - 需求 2（细节检索） 是 Light RAG 的强项。Light RAG 设计了 Low-Level（具体实体）和 High-Level（抽象主题）双路检索，能够精确地定位到知识图谱中的特定实体和关系，并直接索引回原文片段，非常适合回答“具体案件中某标准是什么”这类事实性问题。

  2. 技术对比与选型困境
    - Graph RAG 的困境： 虽然它擅长全局分析，但其原生缺陷在此场景下是致命的。

    • 构建成本高： 对 10 万份法律文书进行实体关系抽取、图构建和社区摘要生成，Token 消耗巨大，成本极高。
    • 细节丢失与幻觉风险： 社区摘要是对信息的压缩，会丢失原文中的精确细节（如具体的法条编号、精确的赔偿金额）。且一旦 LLM 在生成摘要时产生幻觉，错误将被固化到社区摘要中，且几乎没有修复机会。
    • Light RAG 的优势： 更适合作为基础。
    • 构建效率高： 它对文档进行切片、抽取、建图并向量化，流程更轻量，成本更低。
    • 细节检索精准： 其 Low-Level 检索模式能通过向量匹配找到相关实体，再通过图关系找到周边实体和原始文本块，非常适合事实核查和精确引用。
    • 原生缺陷可被覆盖： Light RAG 的全局分析能力相对较弱，但这可以通过上层应用逻辑来弥补。

  3. 最终推荐方案：以 Light RAG 为底座，上层封装 Graph RAG 思想
    - 第一步：构建 Light RAG 索引。 将所有 10 万份判决文书通过 Light RAG 流程处理，建立起包含实体、关系、向量和原文索引的高效检索引擎。这能低成本、高质量地满足“细节检索”需求。
    - 第二步：按需触发“轻量级”社区摘要。 不进行全局的 Leiden 社区发现，而是当用户提出全局性问题时，动态触发一个上层逻辑：

    • 利用 Light RAG 的 High-Level 检索，召回与问题相关的关键实体和关系簇。
    • 将这些召回的局部子图数据（而非全量数据）和原文片段作为上下文，提交给一个更强大的 LLM（如 GPT-4 或 DeepSeek-R1）进行即时总结和趋势分析。
    • 这种方案的优势：
    • 成本可控： 避免了天量的离线 Token 消耗。
    • 准确性高： 细节回答直接来自未经压缩的原文，杜绝了摘要层的幻觉。
    • 灵活性好： 全局分析是“在线”生成的，可以根据问题动态调整分析的焦点和范围，而不是依赖一成不变的离线摘要。

▎关键细节 & 踩坑点

  • 实体关系定义的挑战： 法律文书中的实体关系（如“原告-起诉-被告”、“法院-引用-法条”）与三国演义完全不同。需要与法务专家合作，定义一套适合业务的实体关系 Schema，这是决定检索效果的基石。如果抽取出的关系错误，后续所有步骤都是徒劳。
  • Light RAG 的 Gleaning（补充校验）环节至关重要： 在初次实体关系抽取后，必须进行多轮 Gleaning，让 LLM 自我检查并补充遗漏的实体和关系，尤其是在复杂的法律长文本中，这一步能显著提升知识图谱的完整度。

▎可扩展优化

  • 混合检索策略： 对于细节检索，可以结合向量检索（语义相似）和关键词检索（BM25，精确匹配法条编号），在 Light RAG 的检索阶段就进行混合召回，进一步提升准确率。
  • 图谱版本管理： 随着新判决文书的不断加入，Light RAG 的图结构会持续演化。需要建立图谱版本管理机制，以便在检索效果变差时，可以回溯到之前的稳定版本。

🛠 应用题 · Q3 · 工程实现题

题型

工程实现

场景标签

模型量化 性能优化 GPU推理

📝 题目

某团队计划在单张 NVIDIA L40S（48GB 显存）上部署 Qwen2.5-32B 模型，以支持一个对响应延迟要求极高的内部代码助手 Agent。他们直接下载了官方 BF16 精度的模型，使用 vLLM 框架部署后，发现模型加载后显存占用高达 65GB，导致 OOM 无法启动。

请你作为架构师介入，设计一套工程方案，确保该模型能在单卡上流畅运行，并尽可能保证模型精度和推理速度。请详细说明你的方案，并解释每一步解决了什么问题。

💡 参考答案

▎解题思路

  1. 问题诊断： BF16 精度的 32B 模型，理论上需要 32B * 2 Bytes ≈ 64GB 显存，超出了 L40S 的 48GB 限制。核心问题是精度过高导致模型体积过大。
  2. 核心解决路径： 必须对模型进行量化压缩，将精度从 16-bit 降低到 8-bit 甚至 4-bit，以大幅减少显存占用。
  3. 方案设计： 选择成熟的量化算法（AWQ/GPTQ），将其量化到 INT4 精度。然后利用 vLLM 框架的高效推理能力进行部署，并针对显存进行精细化配置。

▎详细方案

  1. 模型量化：从 BF16 到 INT4 (AWQ)
    - 选择量化算法： 选用 AWQ (Activation-aware Weight Quantization)。相较于 GPTQ，AWQ 更注重保护对推理结果影响大的“显著权重”，在 INT4 精度下通常能保持更好的模型性能，特别适合代码生成这类对逻辑性要求高的场景。
    - 量化操作： 不使用官方 BF16 模型，而是去 Hugging Face 等社区直接下载已经量化好的 Qwen2.5-32B-AWQ 模型包。如果找不到，则使用 AutoAWQ 库，在自己的校准数据集（可以是项目中的少量代码片段）上花少量时间完成量化。
    - 解决的问题： 将模型精度从 16-bit 降至 4-bit，模型文件大小从约 64GB 骤降至约 32B * 0.5 Bytes = 16GB。这解决了模型本身无法装入 48GB 显存的核心矛盾。

  2. 推理框架配置与优化 (vLLM)
    - 使用 vLLM 加载模型： 使用 vLLM 直接加载 AWQ 量化后的模型。vLLM 原生支持 AWQ 格式，会自动识别并采用最优的推理内核。
    - 显存精细化管理：

    • 限制 KV Cache 显存占比： vLLM 默认会使用 90% 左右的剩余显存作为 KV Cache。在 48GB 总显存、模型占约 16GB 的情况下，剩余约 32GB。为给系统和波动留出余量，我们通过 --gpu-memory-utilization 0.90 参数，将 vLLM 可用的总显存池限制在 48GB * 0.9 ≈ 43.2GB。这样 KV Cache 可用空间为 43.2GB - 16GB = 27.2GB。
    • 设置最大模型长度： 代码助手通常不需要超长上下文。通过 --max-model-len 8192 或 16384 来限制最大序列长度，防止单个请求创建过大的 KV Cache 导致 OOM。
    • 解决的问题： 在模型能装入显存的基础上，精细控制显存分配，确保有足够且可控的空间用于推理时的动态计算（KV Cache），支撑多用户并发，避免运行时 OOM。

  3. 启动与验证
    - 启动命令示例：
    bash python -m vllm.entrypoints.openai.api_server \ --model /path/to/Qwen2.5-32B-AWQ \ --quantization awq \ --gpu-memory-utilization 0.90 \ --max-model-len 8192 \ --dtype auto
    - 解决的问题： 通过正确的启动参数，将上述所有优化策略落地，最终在单张 L40S 上成功启动推理服务。

▎关键细节 & 踩坑点

  • 量化模型的精度验证： 部署前，必须使用内部的代码补全、解释等测试集，对 INT4 量化模型进行精度评测（如 pass@k），确保其性能下降在可接受范围内（通常 AWQ 的损失在 1% 以内）。不能只关心显存，忽略了业务效果。
  • 校准数据集的选择： 如果自行量化，校准数据集必须与目标场景（代码）强相关。用新闻语料去校准代码模型，量化后的精度会大打折扣。
  • AWQ 与 GPTQ 的选择： 对于 L40S 这类较新架构的 GPU，vLLM 对 AWQ 的内核优化通常更好，推理速度更快。而 GPTQ 在一些老卡上兼容性更广。这是一个需要实测验证的点。

▎可扩展优化

  • 引入投机采样 (Speculative Decoding)： 用一个更小的草稿模型（如 Qwen2.5-0.5B）来辅助 32B 的量化模型。在代码生成这类模式化较强的任务中，小模型能快速预测出大部分简单 Token，再由大模型验证，可将吞吐量提升 2-3 倍，进一步降低用户感知延迟。
  • Prefix Caching： 开启 vLLM 的 --enable-prefix-caching。在代码助手场景，用户的多轮对话或不同请求间，系统提示词（System Prompt）是高度重复的。Prefix Caching 可以缓存这部分 Prompt 的 KV Cache，避免重复计算，显著降低 TTFT（首 Token 延迟）。

🛠 应用题 · Q4 · 排障优化题

题型

排障优化

场景标签

Agent编排 容器化 性能瓶颈

📝 题目

你们团队基于 LangGraph 开发了一个数据处理 Agent，它包含“路由”和“数据分析”两个节点。你们采用“单镜像+启动参数”的方案将其打包，并部署到 K8s 集群。上线后，出现两个严重问题：
1. 扩容缓慢： 每当需要扩容“路由”节点来应对流量高峰时，新 Pod 的启动时间长达 3-5 分钟，导致大量请求在就绪前被丢弃。
2. 资源浪费： “路由”节点是一个非常轻量级的服务，但 K8s 调度器却总是将其调度到带有昂贵 GPU 的节点上，造成 GPU 资源被“占着不用”的浪费。

请分析造成这两个问题的根本原因，并给出优化方案。

💡 参考答案

▎解题思路

  1. 问题归因： 两个问题的根源都指向了“单镜像+启动参数”这种打包策略。它将所有依赖（包括pandas, numpy, torch等重依赖）打包进了一个臃肿的镜像。
  2. 问题 1（扩容慢）分析： 镜像体积过大导致容器镜像拉取时间过长，拖慢了 Pod 启动速度。
  3. 问题 2（资源浪费）分析： 由于路由和数据节点使用同一镜像，K8s 无法从镜像层面区分它们的资源需求。为满足数据分析节点，镜像或 Pod 定义中可能声明了对 GPU 的请求，导致轻量的路由 Pod 也被强制调度到 GPU 节点。

▎详细方案

  1. 根本原因分析
    - 镜像臃肿： 为了能让“数据分析”节点运行 pandas, torch 等库，这个“全家桶”镜像的体积可能达到 5-8 GB。当“路由”节点需要快速扩容时，即使是在千兆网络下，拉取这么庞大的镜像也需要数分钟，这严重违反了云原生应用的快速启动原则。
    - 资源需求耦合： 在 K8s 的 Pod 定义中，为了确保“数据分析”节点能正常工作，很可能在 resources.limits 中声明了 nvidia.com/gpu: 1。当使用相同镜像启动“路由”节点时，尽管它的启动参数不同，但其 Pod 定义中的资源请求是相同的。K8s 调度器看到这个 Pod “需要” GPU，就会忠实地将其调度到有 GPU 的节点上，即使“路由”进程根本不会调用 CUDA。

  2. 优化方案：采用多 Dockerfile 策略进行解耦
    - 拆分 Dockerfile：

    • Dockerfile.router： 基于轻量级基础镜像（如 python:3.10-slim），只安装 langgraph, fastapi, httpx 等路由和网络通信所需的最小依赖。这个镜像体积可以控制在 300MB 以内。
    • Dockerfile.data_agent： 基于 CUDA 基础镜像（如 nvidia/cuda:12.1-runtime-ubuntu22.04），安装 torch, pandas, numpy 等所有重型数据分析依赖。
    • 编写独立的 K8s 部署清单：
    • 路由节点 Deployment： 使用 image: .../router-agent:v1。在 resources 中，只请求 CPU 和内存，不请求任何 GPU 资源。
      yaml resources: requests: cpu: "250m" memory: "512Mi"
    • 数据分析节点 Deployment： 使用 image: .../data-agent:v1。在 resources 中，明确请求 GPU 资源。
      yaml resources: limits: nvidia.com/gpu: 1

▎关键细节 & 踩坑点

  • 镜像拉取策略： 对于 router-agent 这种频繁变动的镜像，可在 Pod Spec 中设置 imagePullPolicy: IfNotPresent，并配合 :latest 标签使用。但更推荐在 CI/CD 中为每次构建打上唯一 Tag（如 Git Commit SHA），并使用 IfNotPresent，这样既能保证版本一致性，又能在节点已有该镜像时跳过拉取，实现秒级启动。
  • K8s 节点亲和性与污点/容忍： 为了更精细地控制调度，可以为 GPU 节点打上污点（Taint），如 nvidia.com/gpu=true:NoSchedule，这样只有声明了对应容忍（Toleration）的 Pod 才能被调度上去。数据分析节点的 Deployment 添加容忍，而路由节点的则不添加。这提供了双重保险。
  • CI/CD 流水线的调整： 需要修改 CI/CD 脚本，使其能根据 Dockerfile.router 和 Dockerfile.data_agent 分别构建并推送两个不同的镜像到镜像仓库。

▎可扩展优化

  • 引入 Distroless 镜像： 对于“路由”这类服务，可以进一步使用 Google 的 Distroless 镜像作为基础，它只包含应用程序及其运行时依赖，不包含 Shell、包管理器等，体积更小，安全攻击面也更少。
  • 使用 Init Container 进行前置检查： 在数据分析节点的 Pod 中，可以增加一个 Init Container，用于检查 GPU 驱动、CUDA 库是否可用，确保在主容器启动前环境是完备的，避免主容器因环境问题而 CrashLoopBackOff。

🛠 应用题 · Q5 · 综合落地题

题型

综合落地

场景标签

本地部署 数据飞轮 项目交付

📝 题目

你作为 AI 架构师，被一家传统制造企业聘为顾问，帮助他们从 0 到 1 落地一个“设备维修知识库智能助手”。现状是：企业有大量经验丰富但即将退休的老师傅，他们的维修经验都在脑子里；还有散落在各车间电脑里的 Word、Excel 格式的维修记录。老板希望用一个 AI 系统将这些知识沉淀下来，让新人也能快速解决设备故障，并要求所有数据绝对不能传出公司内网。

请你设计一个从 0 到 1 的完整交付方案，重点阐述你如何解决“数据沉淀”和“数据飞轮”这两个核心问题，并给出硬件选型建议。

💡 参考答案

▎解题思路

  1. 需求分析与目标拆解： 核心是“知识沉淀”和“数据飞轮”。这不仅仅是部署一个模型和向量库，而是要设计一个能持续吸收、清洗、反馈数据的闭环系统。
  2. 硬件与基座选型： 基于“数据不出内网”和“传统制造企业”的预算，推荐高性价比的本地化轻量级方案。模型选型优先考虑成本和实用性，而非一味追求大参数。
  3. 数据沉淀方案： 设计一套“冷启动”流程，将存量非结构化数据（Word/Excel）和隐性知识（老师傅经验）转化为结构化的 RAG 知识库。
  4. 数据飞轮设计： 在助手上线后，设计反馈、标注和自动化清洗机制，让系统效果随着使用不断自动提升，形成正向循环。

▎详细方案

  1. 硬件与基座模型选型（成本与合规优先）
    - 硬件方案： 推荐 方案 A：单机双卡 RTX 4090 D（48GB 显存）。这个方案成本约 5-8 万元，对于非高并发的内部维修场景完全足够，且能满足物理隔离要求。在机房条件允许下，这是验证 ROI 的最佳起点。
    - 基础模型： 选用 Qwen2.5-32B-AWQ (INT4 量化版)。模型大小约 16GB，两张 4090D 可以轻松加载，并留有充足显存处理多轮对话和知识库检索。Qwen 的中文理解和指令遵循能力也足够胜任。
    - 技术栈： vLLM (推理框架) + LangChain/LlamaIndex (RAG 编排) + BGE (Embedding 模型) + Milvus/Qdrant (向量数据库，可本地部署) + MongoDB/PostgreSQL (存储维修案例和对话历史)。

  2. 数据沉淀方案（解决“从0到1”的冷启动）
    - 第一步：存量数据清洗与导入。

    • 数据收集： 集中收集所有车间的维修记录 Word/Excel。
    • 数据清洗工程（投入 80% 精力）： 编写脚本或利用工具，进行格式统一、去除乱码、修正错误。最关键的是 Chunking（文本切片），需要根据维修记录的格式（如按“故障现象-原因分析-解决步骤”的结构）设计特定的切片策略，而不是简单的按字数切割。
    • 向量化与入库： 将清洗好的文本块通过 BGE 模型向量化，存入 Milvus 向量数据库。
    • 第二步：隐性知识显性化。
    • 访谈与实录： 组织与老师傅的故障排查访谈会，全程录音。
    • 语音转写与精炼： 使用本地部署的语音识别模型（如 Whisper）将录音转文字。然后，让老师傅或初级工程师一起，将口语化的、跳跃的对话精炼成结构化的、步骤清晰的维修指南（SOP）。这个精炼后的文档才是最有价值的资产。
    • 导入知识库： 将精炼后的 SOP 文档同样进行切片和向量化入库。

  3. 数据飞轮设计（解决“从1到N”的持续进化）
    - 反馈入口（AI 教练）： 在助手界面上，为每个答案提供“有用”、“无用”、“专家修正”等按钮。
    - 数据清洗工场（自动化闭环）：

    • 采集： 收集所有“无用”和“专家修正”的反馈，以及对应的对话上下文。
    • 自动化清洗与标注： 利用一个轻量级 LLM（如 Qwen2.5-7B）在后台对这些反馈数据进行自动化分析。例如，如果用户点了“无用”，小模型尝试总结原因：“答案未切中要点”或“知识库中缺少相关案例”。
    • 人工审核与回流： 每周，由一名初级工程师花少量时间，审核小模型的标注结果，将修正后的标准答案或新案例，更新到向量数据库或维修案例库中。
    • 模型微调（按需触发）： 当积累到数千条高质量、结构化的“问题-标准答案”数据对后，可以对 32B 模型进行一次 LoRA 微调，让它更适应企业内部的术语和回答风格，进一步提升效果。
