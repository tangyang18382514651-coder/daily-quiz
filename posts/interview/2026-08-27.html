一、概念题（10 道）

📌 概念题 · Q1

考点标签

意图识别 · 三级分流 · 成本优化 · 难度：⭐⭐⭐

📝 题目

在智能客服的意图识别架构中，知识库提出了「一快、二省、三准」的三级分流模式：规则硬编码 → 向量相似度 → 大模型推理。请从「Token 成本与响应时延的梯度分布」这一视角出发，解释为什么不能把所有意图识别全部交给大模型完成，以及这种三级架构在企业级高并发场景下的核心价值是什么？

💡 参考答案

▎一句话结论

三级分流模式的本质是把「确定性意图」用最廉价的工程手段拦截在流量入口，只将「不确定性意图」交给大模型，从而在高并发场景下实现成本与准确率的帕累托最优。

▎核心原理

  • 规则层（关键词/正则）的边际成本趋近于零，响应时延在毫秒级，适合处理「转人工」「投诉」等强诉求类意图
  • 向量相似度层（Embedding 比对）的成本仅为一次向量检索，远低于 LLM 推理，适合处理高置信度的标准问法
  • LLM 推理层虽然准确率最高，但单次调用 Token 消耗大、时延高（通常 1-3 秒），只应处理长尾、多意图、模糊表达

▎深入解释

设想一个日均 10 万次咨询的电商客服场景。如果全部走 LLM 意图识别，假设每次平均消耗 500 Token（含 System Prompt 和对话历史），按当前 API 价格计算，单日 Token 成本可能高达数千元，且用户平均等待时间将超过 2 秒。但如果 70% 的请求被规则层拦截（如用户直接输入「转人工」），20% 被向量层以 0.85 以上置信度命中，只有 10% 真正进入 LLM，则总成本骤降 80% 以上，且大部分用户体验到的是毫秒级响应。这种架构设计本质上是在「确定性」与「不确定性」之间建立了一道经济学意义上的分层过滤机制。

▎面试加分点

  • 强调「规则不是过时技术，而是成本控制的第一道防线」——这体现了对工程经济学的理解，而非盲目追求技术先进性
  • 可以补充：向量层的阈值（如 0.85）是可以动态调整的，根据业务对误判的容忍度做弹性配置
  • 还可以提到：三级分流天然适合做灰度发布和 A/B 测试，因为每一层的拦截率都可以独立监控和调优

▎常见误区

  • 认为「大模型无所不能，规则和向量是过渡方案」——实际上，即使在 GPT-5 时代，规则层依然存在，因为它解决的不是「能不能识别」而是「值不值得花这个成本去识别」
  • 把向量层阈值设得过高（如 0.95），导致大量请求穿透到 LLM 层，失去了分流的意义

📌 概念题 · Q2

考点标签

意图识别 · 上下文改写 · 多轮对话 · 难度：⭐⭐⭐

📝 题目

在意图识别的工程实践中，知识库提出了「上下文改写（Query Rewriting）」这一关键补丁：识别意图时必须携带 2-3 轮对话历史，防止用户使用代词（如「那个」「来两个」）导致识别失败。请解释：为什么简单的「把历史对话拼接进 Prompt」并不能真正解决代词消解问题，正确的 Query Rewriting 在工程上应该怎么做？

💡 参考答案

▎一句话结论

Query Rewriting 的核心不是「让 LLM 看到更多上下文」，而是「让 LLM 在进入意图识别之前，先把指代消解掉，生成一个语义自足的独立查询」。

▎核心原理

  • 直接把历史对话拼进 Prompt 会导致「上下文噪声」：LLM 需要同时理解多轮对话中的多个实体和话题切换，反而增加误判概率
  • 正确的做法是引入一个独立的「改写步骤」：让 LLM 将当前轮次的用户输入，结合历史对话，重写为一个不含代词的、语义完整的句子
  • 改写后的 Query 再送入意图识别模块（无论是向量层还是 LLM 层），此时它已经是一个「自包含」的输入

▎深入解释

用户说「那个帮我查一下」，如果直接拼上历史对话，LLM 看到的可能是：「用户：我要退货。客服：请问订单号？用户：那个帮我查一下」。此时 LLM 需要自行推断「那个」指代的是「退货订单」，这个推断过程不可控——它可能把「那个」理解为「上一个话题中的某个实体」，也可能理解为「用户想要查询某个商品」。而 Query Rewriting 的做法是：先让 LLM 输出一个改写结果，比如「帮我查询退货订单的物流状态」，然后再把这个改写结果作为意图识别的输入。这样做的本质是将「隐式指代消解」从意图识别的黑盒中剥离出来，变成一个独立、可验证、可调试的步骤。在企业级实现中，这一步通常用一个轻量级 Prompt 完成，甚至可以复用同一个 LLM 但用不同的 System Prompt。

▎面试加分点

  • 强调「改写步骤」可以单独做缓存和日志分析，当识别出错时，可以快速定位是「改写错了」还是「识别错了」
  • 可以提到：在 LangGraph 等框架中，Query Rewriting 通常被建模为一个独立节点，这样可以单独监控它的耗时和成功率
  • 加分表达：「把隐式语义问题显式化，是 Agent 工程中的一个通用设计哲学」

▎常见误区

  • 认为「多轮对话历史越长越好」——实际上，带入过多轮历史会引入噪声和话题漂移，2-3 轮是工程上的经验最优值
  • 把 Query Rewriting 和意图识别合并成一步——这样虽然省了一次 LLM 调用，但会让两个任务的错误模式耦合在一起，难以独立优化

📌 概念题 · Q3

考点标签

Agent 记忆 · 总结记忆 · 异步加工 · 难度：⭐⭐⭐⭐

📝 题目

在 Agent 短期记忆的实现模式中，知识库提到了「总结记忆（Summary Memory）」：引入轻量级模型或触发特定 Prompt，定期对历史对话进行异步摘要。请从「同步 vs 异步」和「信息保真度 vs Token 压缩率」两个维度，解释为什么总结记忆必须采用异步机制，以及它在企业级 Agent 中可能引入哪些新的工程问题？

💡 参考答案

▎一句话结论

总结记忆的异步化本质是「把昂贵的信息压缩操作从用户请求的关键路径上剥离」，但代价是引入了「压缩滞后」和「信息丢失」两个新的工程矛盾。

▎核心原理

  • 同步摘要会阻塞用户响应：LLM 摘要本身需要一次完整的推理调用（耗时 1-3 秒），如果在用户等待回答的过程中同步执行，总时延将翻倍
  • 异步摘要通过消息队列（如 Kafka）将「对话记录」发送给后台 Worker 处理，用户主流程只负责读写最新的摘要结果
  • 摘要的本质是「有损压缩」：它会丢弃技术细节、特定实体、精确数字，因此摘要策略必须区分「可压缩信息」和「不可压缩信息」

▎深入解释

假设一个 HR 客服 Agent 的对话已经进行了 20 轮，用户在第 3 轮提到「我的工号是 88231」，在第 15 轮问「我的社保基数是多少」。如果采用全量记忆，这 20 轮对话全部塞进 Prompt，Token 消耗巨大但信息完整。如果采用总结记忆，摘要可能是「用户在咨询社保相关问题，已提供工号」，但「88231」这个关键实体可能被丢失。这就是总结记忆的核心矛盾：压缩率越高，关键信息丢失的风险越大。正确的工程做法是「混合策略」：将对话中的结构化实体（工号、订单号、日期）通过动态槽位填充单独存储，不参与摘要压缩；将非结构化语义（用户的情绪、偏好、话题脉络）交给异步摘要处理。这样既控制了 Token，又保证了关键实体的精确性。

▎面试加分点

  • 强调「异步摘要的滞后性」：当用户连续快速提问时，摘要可能还没有更新，此时需要降级策略——回退到滑动窗口或全量记忆
  • 可以提到「摘要触发条件」的设计：不是每轮都摘要，而是达到阈值（如 10 轮或 80% 上下文窗口）才触发
  • 加分表达：「总结记忆不是『省 Token 的技术』，而是『信息分层治理的技术』」

▎常见误区

  • 把摘要记忆当作「万能压缩算法」——实际上，它对「精确事实查询」类对话是灾难性的，只适合「话题讨论」类对话
  • 认为异步就是「不阻塞」——实际上，异步引入了「状态不一致窗口」，在这个窗口期内，Agent 读到的摘要可能是过期的

📌 概念题 · Q4

考点标签

Agentic RAG · 自我反思 · 质检循环 · 难度：⭐⭐⭐⭐

📝 题目

Agentic RAG 区别于传统 RAG 的最大亮点是「纠错与反思机制」：在检索完成后、生成回答前，Agent 会启动质检循环，包括文档打分（Document Grading）、幻觉检测（Hallucination Critique）和回答完备性验证。请从「谁来当裁判」这一视角出发，解释这个质检循环的裁判机制是如何实现的，以及为什么「让同一个 LLM 既当运动员又当裁判」在工程上是可以被接受的？

💡 参考答案

▎一句话结论

质检循环的裁判本质上是一个「被赋予不同 Prompt 角色的同一个 LLM」，其可接受性建立在「角色隔离」和「独立上下文窗口」两个工程前提之上。

▎核心原理

  • 文档打分：LLM 以「评估者」角色接收「问题 + 检索到的 Chunk」，输出每个 Chunk 的相关性评分（通常为 0-1 或等级制），过滤低分 Chunk
  • 幻觉检测：LLM 以「事实核查员」角色接收「生成的草稿 + 支撑上下文」，判断草稿中的每个断言是否能被上下文完全支撑
  • 完备性验证：LLM 以「用户代理」角色接收「问题 + 草稿」，判断草稿是否真正回答了用户的问题，若不足则触发 Query 重写和二次检索

▎深入解释

为什么「同一个 LLM 既生成又评估」在工程上可以被接受？关键在于角色隔离。当 LLM 以「生成者」角色工作时，它的目标函数是「生成流畅、相关的回答」；当它切换到「评估者」角色时，目标函数变为「判断相关性」，此时它不再需要生成能力，而是需要判断能力。这两种角色使用完全不同的 System Prompt 和 Few-Shot 示例，在独立的上下文窗口中进行推理。这类似于人类工程师在写代码和 Code Review 时的角色切换——同一个人，但使用不同的思维框架。更深层的原因是：LLM 的「生成能力」和「评估能力」虽然在参数空间中是共享的，但通过 Prompt 的引导，可以激发出不同的行为模式。此外，在工程实践中，质检循环通常使用更便宜的模型（如 GPT-4o-mini 或本地小模型）来降低成本，这也是一种「异构裁判」策略。

▎面试加分点

  • 强调「角色 Prompt 的设计质量」是质检循环成败的关键：一个模糊的评估 Prompt 会导致「裁判和运动员穿同一条裤子」
  • 可以提到：在 LangGraph 中，质检循环通常被建模为「条件边」，根据评估结果动态决定是继续生成还是回退重检
  • 加分表达：「质检循环的本质是给 LLM 装上了一个『元认知』层，让它能够对自己的输出进行二次判断」

▎常见误区

  • 认为「同一个 LLM 评估自己的输出一定不可信」——实际上，大量实验表明，LLM 在「评估」任务上的表现显著优于「生成」任务，因为评估只需要判断而非创造
  • 把质检循环做得过度复杂（如三层嵌套反思）——这会导致 Token 消耗呈指数级增长，而边际收益递减

📌 概念题 · Q5

考点标签

JSON 输出 · 约束解码 · 三层防御 · 难度：⭐⭐⭐

📝 题目

在「大模型稳定输出 JSON」的解决方案中，知识库提出了三层防御体系：Prompt 软约束 → API/模型原生约束 → 后处理兜底。请解释：为什么「约束解码（Constrained Decoding）」被归为比 response_format 更硬核的技术方案？它在生成机制层面与 Prompt 软约束有什么本质区别？

💡 参考答案

▎一句话结论

约束解码是在 Token 生成的过程中实时过滤非法输出，从语法层面「物理性」地杜绝 JSON 格式错误；而 Prompt 软约束和 response_format 都只是在「统计概率」层面引导模型，无法 100% 保证格式正确。

▎核心原理

  • Prompt 软约束的本质是「改变模型的输出概率分布」：通过指令和示例，让模型更倾向于生成合法 JSON，但模型依然有概率输出非法字符
  • 约束解码的本质是「在采样阶段施加硬性规则」：在每一步 Token 生成时，根据 JSON 语法规则（如对象必须以 { 开头、字符串必须用双引号包裹）过滤掉所有不合法的候选 Token
  • 实现方式：通过构建一个有限状态自动机（FSA）或语法解析器，实时追踪当前 JSON 的语法状态，只允许模型从合法的 Token 子集中采样

▎深入解释

可以类比为「考试作弊的两种防止方式」。Prompt 软约束相当于在考前反复强调「不要作弊」，这降低了作弊的概率，但无法完全杜绝。response_format 相当于在考场上增加了监考老师，进一步降低了作弊概率，但监考老师可能有疏漏。约束解码则相当于在考生的笔上装了一个「只能写正确答案」的装置——从物理上杜绝了作弊的可能性。在技术实现上，约束解码通常使用 Outlines、Guidance 等库，它们在模型推理框架（如 vLLM、llama.cpp）中注册了一个「日志处理器（Logits Processor）」，在每一步 Softmax 之后、采样之前，将非法 Token 的概率置为负无穷。这样模型只能在合法 Token 中进行采样，输出的每一个字符都符合 JSON 语法规范。

▎面试加分点

  • 强调「约束解码的代价」：它需要在推理框架中集成语法解析器，增加了推理延迟（通常 5-15%），且只适用于开源模型，商业 API 无法使用
  • 可以提到：约束解码不仅适用于 JSON，还适用于 SQL、正则表达式、编程语言等任何可以用形式语法描述的输出格式
  • 加分表达：「约束解码是唯一能在数学上保证格式正确的方案，其他所有方案都只是概率性的」

▎常见误区

  • 认为 response_format: {"type": "json_object"} 就是约束解码——实际上，它只是 API 层面的「增强版 Prompt 引导」，底层依然是概率性的，OpenAI 官方文档也承认它不能 100% 保证格式
  • 认为约束解码可以完全替代后处理兜底——实际上，即使语法正确，字段类型错误、缺失必填项等语义问题依然存在，Schema 校验和重试机制仍然必要

📌 概念题 · Q6

考点标签

Dify 二开 · 企业落地 · 优先级 · 难度：⭐⭐⭐

📝 题目

在基于 Dify 进行企业级二次开发的实践中，知识库提出了「P0 级：账号体系与权限打通（Auth & RBAC）」和「P0 级：彻底私有化与本地模型集成（Data Privacy）」两个最高优先级。请从「为什么这两个是 P0 而不是 P1」的视角出发，解释它们在企业落地中的「生死线」和「红线」含义，以及如果这两个不做，会导致什么具体后果？

💡 参考答案

▎一句话结论

Auth & RBAC 决定平台「能不能合法上线」，Data Privacy 决定平台「能不能合规存在」——两者都是企业级 Agent 平台的「准生证」，缺少任何一个，平台在交付给业务部门之前就会被安全合规部门一票否决。

▎核心原理

  • Auth & RBAC 的「生死线」含义：Dify 原生只支持邮箱密码和第三方 OAuth，缺少企业级的部门组织架构管理。如果 A 部门的员工能看到 B 部门的 Agent 和知识库，轻则引发内部信息泄露，重则触发合规审计事故
  • Data Privacy 的「红线」含义：企业的财务、研发、合同数据绝对不能上传到外网云端。如果 Dify 默认连接 OpenAI 等外部 API，数据在传输过程中就可能触及合规红线
  • 两者共同点：它们都是「平台能否被企业接受」的前置条件，而非「平台好不好用」的优化项

▎深入解释

想象一个场景：你带领团队用 Dify 搭建了一个内部 Agent 平台，接入了公司的 CRM 数据，并且默认使用 OpenAI 的 API。业务部门试用后反馈很好，但当安全部门做上线审计时，他们会问三个问题：第一，平台的登录体系是否接入了公司的统一身份认证（SSO）？如果没有，员工离职后账号如何回收？第二，平台的权限控制是否能做到「财务部的知识库只有财务部的人能访问」？如果不能，如何防止越权访问？第三，平台的模型调用是否走的是内网本地部署？如果不是，公司的敏感数据是否被发送到了外部服务器？这三个问题中任何一个回答不上来，平台就无法上线。这就是「P0」的含义——它不是「最好做」，而是「不做就上不了线」。相比之下，视觉换肤（P2）虽然能提升用户体验，但即使不做，平台依然可以运行。

▎面试加分点

  • 强调「P0 的判定标准」：不是技术难度，而是「不做是否会导致平台无法交付」。这是一个典型的「技术管理者思维」而非「工程师思维」
  • 可以提到：在实际项目中，P0 工作通常可以在 1-2 周内完成（Dify 的架构支持快速接入 SSO 和本地模型），但如果不做，整个项目可能被无限期搁置
  • 加分表达：「在企业级 AI 平台建设中，安全合规不是功能需求，而是非功能需求中的最高优先级」

▎常见误区

  • 把「视觉换肤」当作 P0——这是典型的「开发者视角」，因为开发者对 Logo 和 UI 最敏感，但业务方和安全方对此的优先级远低于权限和合规
  • 认为「私有化部署」就是「数据安全」——实际上，私有化部署只是数据安全的必要条件，还需要配合网络隔离、访问审计、加密存储等措施

📌 概念题 · Q7

考点标签

KV Cache · 自回归生成 · 注意力机制 · 难度：⭐⭐⭐⭐

📝 题目

在 Transformer 的自回归生成机制中，KV Cache 只缓存历史 Token 的 Key 和 Value，而不缓存 Query。请从「注意力计算中 Q、K、V 的角色分工」这一视角，解释为什么历史的 Query 没有复用价值，以及这种「只缓存 K 和 V」的设计在长文本生成中导致了什么新的瓶颈？

💡 参考答案

▎一句话结论

Query 是「当前 Token 的提问者」，每个新 Token 都有全新的 Query，因此历史 Query 没有任何复用价值；而 Key 和 Value 是「历史 Token 的身份和内容」，它们在后续每一步生成中都会被反复使用，因此必须缓存。

▎核心原理

  • 注意力计算公式 Attention(Q, K, V) = softmax(QK^T/√d_k)V 中，Q 来自当前正在处理的 Token，K 和 V 来自所有历史 Token
  • 自回归生成是「逐 Token 输出」的：每生成一个新 Token，就需要用这个新 Token 的 Q 去和所有历史 Token 的 K 做点积，再加权求和所有历史 Token 的 V
  • 历史 Token 的 K 和 V 在生成过程中是固定不变的（因为历史 Token 的表示不会再更新），因此可以缓存复用；而每个新 Token 的 Q 都是全新的，用完即弃

▎深入解释

用「图书馆检索」来类比：假设你在写一篇论文，需要反复查阅图书馆中的 100 本书。每查一次，你都会带着一个「当前的问题」（Query）去和所有书的「索引标签」（Key）做匹配，找到最相关的书后，从书中提取「实际内容」（Value）。在这个过程中，书的索引标签和实际内容是固定不变的，所以图书馆可以提前把它们整理好（缓存），你每次只需要带着新问题来查询即可。但你的「当前问题」是不断变化的——查完第一章的问题，下一章的问题就完全不同了。因此，图书馆没有必要缓存你的「历史问题」，因为那些问题已经用过了，不会再被使用。这就是为什么 KV Cache 只缓存 K 和 V 而不缓存 Q 的根本原因。

▎面试加分点

  • 强调「KV Cache 带来的新瓶颈」：虽然计算量从 O(N^2) 降到了 O(N)，但显存占用随着上下文长度线性增长，在长文本场景下 KV Cache 的显存可能超过模型权重本身
  • 可以提到：MQA/GQA 技术的本质是「让多个 Q 头共享同一组 K 和 V」，从而减少需要缓存的 K 和 V 的数量
  • 加分表达：「KV Cache 是 Transformer 推理加速的基石，也是长文本推理的瓶颈所在——它完美诠释了『用空间换时间』的工程哲学」

▎常见误区

  • 认为「Q 不需要缓存是因为它不重要」——实际上，Q 恰恰是注意力计算中最关键的部分，只是它「用完即弃」，没有复用价值
  • 认为「缓存 Q 可以加速计算」——实际上，缓存 Q 只会浪费显存，因为历史 Q 永远不会在后续计算中被使用

📌 概念题 · Q8

考点标签

PostgreSQL · JSONB · Agent 状态 · 难度：⭐⭐⭐

📝 题目

在 Agent 架构中，PostgreSQL 的 JSONB 类型被广泛用于存储 Agent 运行状态（State）和聊天历史。请从「JSON 与 JSONB 的存储机制差异」这一视角，解释为什么在 Agent 状态存储场景中必须选择 JSONB 而不是 JSON，以及 JSONB 的 GIN 索引在 Agent 状态检索中解决了什么具体问题？

💡 参考答案

▎一句话结论

JSON 是「纯文本原样存储」，每次读取和筛选都需要重新解析，性能极差且不支持索引；JSONB 是「解析后的二进制存储」，读取极快且支持 GIN 倒排索引，能对嵌套字段做毫秒级条件检索——这正是 Agent 状态高频读写和动态查询场景的刚需。

▎核心原理

  • JSON 类型存储的是原始文本，写入时不做任何处理，但每次读取、条件筛选内部字段时都需要完整的 JSON 解析，CPU 开销大
  • JSONB 类型在写入时将 JSON 解析为二进制格式（类似 BSON），读取时无需重新解析，但写入时略有解析开销
  • JSONB 支持 GIN（Generalized Inverted Index）倒排索引，可以对 JSON 内部的任意嵌套字段建立索引，实现毫秒级条件查询

▎深入解释

Agent 的状态（State）通常是一个嵌套的 JSON 结构，例如 LangGraph 中的 State 可能包含 {"user_info": {"name": "张三", "dept": "财务部"}, "current_task": {"type": "审批", "status": "pending"}, "history": [...]}。如果使用 JSON 类型存储，当需要查询「所有财务部用户的 pending 审批任务」时，PostgreSQL 必须扫描全表，对每一行做完整的 JSON 解析，再提取字段进行比对——这在千万级数据量下是不可接受的。而使用 JSONB + GIN 索引，可以直接在 state->'user_info'->>'dept' 和 state->'current_task'->>'status' 上建立索引，查询时直接走索引，性能提升数个数量级。此外，JSONB 还支持部分更新（如只修改 current_task.status 而不影响其他字段），这在 Agent 状态频繁变更的场景中非常实用。

▎面试加分点

  • 强调「JSONB 的写入开销是可接受的」：虽然 JSONB 写入时需要解析，但 Agent 状态的读写比通常是「读多写少」，读取性能的收益远大于写入的微小开销
  • 可以提到：JSONB 的 GIN 索引支持「存在性查询」（如 ? 操作符）和「包含性查询」（如 @> 操作符），这些在 Agent 状态过滤中非常常用
  • 加分表达：「JSONB 让 PostgreSQL 同时具备了关系型数据库的事务能力和文档数据库的灵活查询能力，是 Agent 状态存储的最佳选择」

▎常见误区

  • 认为「JSON 和 JSONB 只是性能差异，功能上差不多」——实际上，JSON 不支持任何索引，这意味着任何条件查询都会退化为全表扫描
  • 在 JSONB 上滥用 GIN 索引——GIN 索引虽然强大，但会显著增加写入开销和存储空间，应该只为高频查询的字段建立索引

📌 概念题 · Q9

考点标签

混合检索 · 向量相似度 · BM25 · 难度：⭐⭐⭐⭐

📝 题目

在企业级 Agent 的记忆检索中，知识库强调「单纯的向量检索在企业级场景经常失效，必须采用混合检索（Hybrid Search）」，公式为 Score = α · Dense_Score + (1-α) · Sparse_Score (BM25)。请从「向量检索和 BM25 各自的能力边界」这一视角，解释为什么向量检索在「查特定订单号、工号、产品型号」时经常失效，以及混合检索中的 α 参数应该如何根据业务场景调整？

💡 参考答案

▎一句话结论

向量检索擅长「语义相似」但弱于「精确匹配」；BM25 擅长「词面精确匹配」但弱于「语义泛化」。混合检索通过加权融合两者，在精确查询和语义查询之间取得平衡，而 α 参数本质上是一个「语义优先还是精确优先」的业务决策旋钮。

▎核心原理

  • 向量检索（Dense Retrieval）将文本映射为稠密向量，通过余弦相似度或内积计算语义相关性。它擅长处理「同义改写」（如「怎么退款」和「退货流程」），但在处理「精确标识符」（如订单号 ORD-2024-0815）时，Embedding 模型往往无法区分两个相似编号的细微差异
  • BM25（Sparse Retrieval）基于词频和逆文档频率，擅长「精确词面匹配」。查询「ORD-2024-0815」时，BM25 能精准命中包含这个编号的文档，但无法理解「退款」和「退货」是同一件事
  • α 参数控制两者的权重：α 越大，越偏向语义检索；α 越小，越偏向精确匹配

▎深入解释

为什么向量检索在「查订单号」时经常失效？因为 Embedding 模型在训练时，通常会将数字和标识符当作「普通 Token」处理，而两个相似的订单号（如 ORD-2024-0815 和 ORD-2024-0816）在向量空间中可能非常接近，导致检索时无法区分。更糟糕的是，Embedding 模型可能将「ORD-2024-0815」映射为一个与「订单查询」语义相关的向量，而不是与「这个特定订单」相关的向量。这就是为什么在客服场景中，用户输入「帮我查一下 ORD-2024-0815 的物流」，纯向量检索可能返回一堆「物流查询流程」的文档，而不是这个订单的具体信息。混合检索的解决方案是：BM25 精确匹配「ORD-2024-0815」这个字符串，向量检索理解「物流查询」的语义，两者加权融合后，既找到了包含这个订单号的文档，又理解了用户的查询意图。α 的调整策略是：如果业务中「精确查询」占比高（如订单查询、工号查询），α 应调低（如 0.3-0.5）；如果业务中「模糊查询」占比高（如知识问答、政策咨询），α 应调高（如 0.7-0.8）。

▎面试加分点

  • 强调「混合检索不是简单的加权平均，还需要 Rerank」：先通过混合检索召回候选集（如 Top 50），再用重排模型（如 BGE-Rerank）精筛出 Top 5，这是工业界的标准做法
  • 可以提到：α 参数可以通过线上 A/B 测试或离线的召回率评估来动态调优，而不是拍脑袋决定
  • 加分表达：「混合检索的本质是承认单一检索技术的局限性，用工程手段融合多种信号，逼近人类『既懂语义又认字面』的检索能力」

▎常见误区

  • 认为「向量检索可以完全替代 BM25」——实际上，在精确标识符匹配场景中，向量检索的表现远不如 BM25，两者是互补关系而非替代关系
  • 把 α 设为一个固定值（如 0.5）后就再也不调整——实际上，α 应该根据业务场景的数据分布动态调整，甚至可以在不同查询类型上使用不同的 α

📌 概念题 · Q10

考点标签

Token · 词表训练 · BPE · 难度：⭐⭐⭐

📝 题目

知识库提到：「Tokenizer 是通过 BPE（Byte Pair Encoding）算法引擎训练出来的，得到词表和合并规则，形成一本完整的翻译手册。」请从「为什么需要训练词表」和「BPE 如何平衡词表大小与编码效率」两个维度，解释 Tokenizer 的训练过程本质上在解决什么问题，以及为什么中英文的 Token 数量差异（100 个英文单词 ≈ 130-140 Token，100 个汉字 ≈ 100-150 Token）反映了词表设计中的什么权衡？

💡 参考答案

▎一句话结论

Tokenizer 的训练本质上是在「词表大小」和「编码效率」之间寻找最优平衡：BPE 通过统计高频字符对的合并规则，用有限的词表覆盖尽可能多的文本，同时将罕见词拆解为子词单元，避免词表爆炸。

▎核心原理

  • 如果词表包含所有可能的词（词级 Tokenization），词表会极其庞大（英文词汇量超过百万），且无法处理新词和罕见词
  • 如果词表只包含单个字符（字符级 Tokenization），词表很小但编码效率极低，一个单词需要拆成多个 Token，导致序列变长
  • BPE 的折中方案：从字符级开始，统计语料中最高频的相邻字符对，将它们合并为一个新 Token，反复迭代直到达到预设的词表大小（如 50K）

▎深入解释

BPE 的训练过程可以类比为「中文输入法的词库构建」。假设你有一个庞大的中文语料库，你发现「人工智能」这四个字经常连在一起出现，于是你把它作为一个整体加入词库。这样，当用户输入「人工智能」时，只需要一个编码单元，而不是四个。但你不可能把所有可能的词组都加入词库，因为词库太大会导致存储和查询效率下降。BPE 的策略是：只合并「最高频」的字符对，这样可以用有限的词表覆盖大部分常见表达，同时保留字符级 Token 作为兜底，处理罕见词和新词。中英文 Token 数量的差异反映了词表设计中的「语言特性适配」：英文单词之间有空格分隔，BPE 可以轻松合并出完整的常见单词（如「the」「ing」），所以 100 个英文单词约 130-140 Token（部分长单词被拆分为子词）；中文没有空格分隔，BPE 需要从单个汉字开始合并，常见双字词（如「智能」）可以被合并为一个 Token，但三字词和四字词的合并概率递减，所以 100 个汉字约 100-150 Token。这种差异本质上是「词表大小固定时，不同语言的编码效率不同」的体现。

▎面试加分点

  • 强调「BPE 的训练数据决定了词表的领域适配性」：用通用语料训练的 Tokenizer 在医学、法律等专业领域可能表现不佳，因为专业术语会被拆分为多个子词，增加了 Token 消耗
  • 可以提到：现代 Tokenizer（如 GPT-4 的 tiktoken、Llama 的 SentencePiece）在 BPE 基础上增加了正则预处理、Unicode 规范化等步骤，以处理多语言和特殊字符
  • 加分表达：「Tokenizer 是大模型的『第一层』，它的质量直接决定了后续所有计算的效率和成本——一个不好的词表，相当于让模型在『用错字典』的情况下工作」

▎常见误区

  • 认为「Token 就是单词」——实际上，Token 是词表中的最小编码单元，可能是单词、子词、字符，甚至是字节
  • 认为「词表越大越好」——实际上，词表过大会导致 Embedding 矩阵过大（词表大小 × 隐藏维度），增加模型参数量和显存占用，需要在编码效率和模型大小之间权衡

二、应用题（5 道 · 分类型）

🛠 应用题 · Q1 · 架构设计

题型

架构设计

场景标签

智能客服 · 意图识别 · 三级分流 · 冷启动

📝 题目

你正在为某银行的信用卡中心设计一套智能客服 Agent 的意图识别系统。该银行业务涵盖账单查询、额度调整、挂失补卡、投诉、分期办理等 200+ 个意图，日均咨询量约 50 万次。其中，约 60% 是「挂失」「转人工」「账单查询」这类高频强诉求，约 35% 是「我的卡上个月在境外刷了一笔，为什么扣了手续费」这类有一定变体的业务咨询，约 5% 是「你觉得我该不该把这张卡注销了」这类模糊、多意图或带情绪色彩的长尾提问。

当前团队只有 2 名算法工程师和 3 名后端工程师，且线上 GPU 资源有限（仅 4 张 T4），Token 预算要求严格控制在每用户次均 3000 tokens 以内。

请设计一套兼顾响应速度、识别准确率、Token 成本的意图识别架构，并说明如何用「三级分流」落地，以及冷启动阶段如何快速上线。

💡 参考答案

▎解题思路

  1. 先算账：50 万次日均咨询，如果全量走大模型，按每次 3000 tokens 算，日消耗约 15 亿 tokens，T4 集群根本无法承载，且成本不可控。必须让大部分流量在「不经过大模型」的情况下被处理掉。
  2. 按流量分布分层：60% 高频强诉求 → 规则层秒级命中；35% 有变体但语义可枚举 → 向量相似度层处理；5% 复杂长尾 → 大模型兜底。
  3. 冷启动策略：规则层和向量层可以立即上线（无需训练），大模型层用 Few-shot Prompt 快速搭建，后续用真实日志逐步替换为微调模型。

▎详细方案

第一层：规则硬编码（一快）
- 对「转人工」「挂失」「投诉」「销户」等约 30 个强诉求意图，建立关键词/正则规则库。例如：/挂失|丢卡|卡不见了/ → 直接触发挂失流程，或 /转人工|人工客服|找真人/ → 直接分流至人工队列。
- 规则匹配命中后不走大模型，直接返回预设话术或跳转对应业务流程，响应时间控制在 50ms 以内。
- 规则库用 YAML 或数据库表维护，支持运营人员热更新，无需发版。

第二层：向量相似度（二省）
- 将 200+ 意图中约 150 个「语义相对固定但表述有变体」的意图，每个意图人工编写 5~10 条种子句（Seed Sentences），用 Embedding 模型（如 BGE-M3）转为向量存入向量库。
- 用户输入实时转向量，与种子句做余弦相似度匹配。设定双阈值策略：similarity > 0.85 直接触发对应业务；0.70 < similarity < 0.85 进入候选区，交给下一层大模型做精判；similarity < 0.70 直接标记为 OOD（域外意图），走兜底话术。
- 这一层单次调用仅消耗 Embedding 的少量 tokens（约 50~100 tokens），响应时间约 100~200ms，GPU 占用极低。

第三层：大模型推理（三准）
- 仅对向量层无法判定的约 5%~10% 流量调用 LLM。
- Prompt 设计核心：带上 2~3 轮对话历史做 Query Rewriting，防止用户说「那个」「来两个」导致意图丢失；允许返回多意图数组（如 ["退款", "物流查询"]），配合 LangGraph 走多分支并行处理；强制定义 OTHER 分类，要求模型对闲聊或无法识别的输入返回 {"intent": "OTHER"}，严禁强行匹配。
- 使用 response_format: {"type": "json_object"} 保证输出可解析，配合 Pydantic Schema 校验，失败自动重试一次。

冷启动落地路径：
- 第 1 周：上线规则层 + 向量层（种子句人工编写），覆盖约 80% 流量，大模型层用 Few-shot Prompt（每个意图 1~2 个示例）直接接入。
- 第 2~4 周：收集真实日志，将向量层误判的 case 人工标注后补充进种子句库；将大模型层高置信度的输出作为训练数据，逐步微调一个轻量级 Router 模型（如 Qwen-7B），替换大模型层以进一步降低延迟和成本。

▎关键细节 & 踩坑点

  • 规则层不能过度膨胀：如果规则从 30 条涨到 300 条，维护成本会指数级上升，且规则之间会互相冲突。建议规则层只保留「强诉求 + 高准确率（>99%）」的意图，其余一律下沉到向量层。
  • 向量层的阈值需要动态调优：初始阈值 0.85 可能过于激进或保守，上线后要根据真实数据观察「误判率」和「漏判率」的平衡。建议每周用标注数据回测一次阈值。
  • Query Rewriting 是三层共用的：不要只在第三层做上下文改写，向量层也需要带上上一轮对话的意图结果作为辅助信号。例如用户说「那帮我查一下」，向量层需要知道上一轮意图是「账单查询」才能正确匹配。
  • OOD 兜底必须严格：银行客服场景中，用户可能输入「今天天气怎么样」，如果 Agent 强行匹配到「账单查询」会严重损害信任。OTHER 分类的 Prompt 要写死：「如果用户输入与银行业务无关，必须返回 OTHER，不要尝试解释或匹配」。
  • Token 预算监控：在网关层对每次调用的 tokens 做实时统计和告警，确保次均不超过 3000 的预算。如果超了，优先优化第一、二层的覆盖率，把更多流量拦截在大模型之前。

▎可扩展优化

  • 多意图并行处理：当大模型返回多意图数组时，用 LangGraph 的并行分支同时调用「退款流程」和「物流查询流程」，最后合并结果，避免串行等待。
  • 冷热意图自动降级：统计每个意图的日均触发频率，对「冷门意图」自动降低向量层阈值，让更多样本流向大模型层精判；对「热门意图」自动提升阈值，减少误判。
  • 引入轻量级 Router 模型：当数据积累到 10 万条以上标注样本时，微调一个 0.5B~7B 的专属 Router 模型，替代大模型层做意图分流，延迟从秒级降到毫秒级，成本降低 90% 以上。
  • 情绪识别叠加：在第三层增加情绪分析维度（愤怒、焦虑、普通），对高情绪用户自动优先转人工，避免 Agent 在用户情绪激动时给出机械回答引发投诉。

场景分析

场景标签

Dify 二开 · 企业内网 · SSO · RBAC

📝 题目

你所在的一家大型制造企业（员工 3 万人，有财务、研发、生产、HR 等多个部门）计划基于开源 Dify 构建内部 AI Agent 平台。CTO 提出了三个硬性要求：

  1. 平台必须部署在公司内网，所有数据不允许出内网，模型必须使用内网自建的 vLLM 推理服务（部署了 DeepSeek-R1 和 Qwen2.5）。
  2. 员工登录必须使用公司现有的飞书账号体系（OAuth2 SSO），且不同部门的 Agent 和知识库要有严格的权限隔离——财务部的知识库不能被研发部的员工看到。
  3. 平台需要接入公司内部的 ERP 和 OA 审批系统，让 Agent 可以查询工单状态、发起审批流程。

请分析：基于 Dify 二开时，这三个需求的优先级应该如何排序？每个需求对应的具体二开动作是什么？在向 CTO 汇报时，你如何阐述「二开而非从零手写」的商业价值？

💡 参考答案

▎解题思路

  1. 优先级排序的逻辑：先解决「能不能上线」的问题（合规 + 安全），再解决「好不好用」的问题（业务打通），最后解决「像不像自己的」的问题（品牌定制）。所以优先级是：私有化部署 + SSO/RBAC（P0）→ 内网工具接入（P1）→ 视觉换肤（P2）。
  2. 二开动作的拆分：每个需求都对应 Dify 源码中具体的模块，要精确到文件路径或模块名称，体现工程落地的可行性。
  3. 商业价值的阐述：核心是「把基建交给开源，把精力留给业务」，用时间成本和人力成本的数据说话。

▎详细方案

P0-1：彻底的私有化部署与本地模型集成

  • 为什么要改：Dify 原生支持 OpenAI 等外部 API，但企业内网环境不允许出网。且 Dify 默认的 Docker 镜像可能包含一些外部依赖（如遥测、字体 CDN 等），需要剥离。
  • 具体动作：
  • 使用 Docker Compose 或 Kubernetes 将 Dify 全家桶（API、Web、Worker、PostgreSQL、Redis、Weaviate/Milvus）部署到内网服务器。
  • 在 api/core/model_runtime/ 下，配置本地 vLLM 推理服务的统一接口。Dify 本身支持 OpenAI 兼容协议，vLLM 启动时加 --api-key 和 --served-model-name 参数，即可被 Dify 识别为 OpenAI 兼容模型。
  • 修改 Dify 的环境变量和配置文件，关闭所有外部遥测、匿名统计、云端字体加载等出网行为。检查 docker-compose.yaml 中所有镜像是否来自内网镜像仓库（需要提前同步官方镜像到内网 Harbor）。
  • 网络层面，在防火墙/安全组中配置白名单，仅允许 Dify 服务之间互相通信，禁止任何出网流量。

P0-2：飞书 SSO 登录与部门级 RBAC 权限隔离

  • 为什么要改：Dify 原生只支持邮箱密码、GitHub、Google 等登录方式，且权限模型是「工作区 - 成员」的扁平结构，没有「部门 - 角色 - 资源」的层级管控。3 万人的企业中，财务知识库的泄露是合规红线。
  • 具体动作：
  • SSO 对接：修改 api/controllers/auth.py 和 api/services/account_service.py，新增飞书 OAuth2 登录流程。核心逻辑：用户在飞书完成授权后，回调携带 code，后端用 code 换取 access_token，再调用飞书用户信息 API 获取 user_id、name、department_ids，在 Dify 本地用户表中创建或更新用户记录。
  • 部门同步：通过飞书开放平台的「部门列表」API，定期（如每小时）同步组织架构到 Dify 的 tenants 和 tenant_members 表，新增 department_id 字段。
  • RBAC 重构：在 api/models/ 中新增 Role 和 Permission 模型，在 api/core/ 下新增权限校验中间件。核心逻辑：每个知识库、Agent、工具都绑定一个 tenant_id 和 visible_departments 列表，在 API 层做拦截——请求到达 Controller 时，先查当前用户所属部门，再判断该部门是否在资源的可见列表内，不可见则返回 403。
  • 前端适配：在 web/app/components/ 中修改知识库和 Agent 的创建/编辑页面，增加「可见部门」选择器。

P1：接入内网 ERP 和 OA 系统

  • 为什么要改：Agent 如果不能查工单、不能发起审批，就只是一个聊天机器人，无法真正替员工干活。
  • 具体动作：
  • 快速路径：使用 Dify 的「自定义工具」功能，将 ERP 和 OA 系统的 OpenAPI/Swagger JSON 导入，Dify 会自动生成工具调用界面。适合查询类接口（如「查工单状态」）。
  • 深度定制：对于需要复杂逻辑的接口（如「发起 OA 审批」需要先做表单校验、再选审批人、再回调通知），在 api/core/workflow/nodes/ 下开发自定义节点。例如新增 OAApprovalNode，内部实现：调用 OA 系统的创建审批单 API → 轮询审批结果 → 将结果写回工作流状态。
  • 前端配套：在 web/app/components/workflow/nodes/ 下新增对应节点的配置 UI，让业务人员可以像搭积木一样拖拽使用。

P2：视觉换肤与品牌定制

  • 具体动作：修改 web/public/ 下的 Logo、Favicon、登录页背景；修改 web/app/components/base/ 下的主题色变量（CSS Variables）；将 Dify 的文案（如「创建应用」改为「创建 Agent」）统一替换。包装为「XX 集团智能 Agent 平台」。

▎关键细节 & 踩坑点

  • 飞书 SSO 的 token 刷新问题：飞书 OAuth2 的 access_token 有效期通常为 2 小时，refresh_token 有效期 30 天。需要在 Dify 的用户表中存储 refresh_token，并在每次登录时检查有效期，过期则用 refresh_token 静默续期。不要让用户频繁重新登录。
  • RBAC 的性能问题：3 万人的组织架构，如果每次 API 请求都实时查询「用户 → 部门 → 权限」链路，数据库压力会很大。建议将用户的部门信息和权限列表缓存在 Redis 中（TTL 1 小时），权限变更时主动失效缓存。
  • 二开代码的可维护性：不要直接修改 Dify 的核心源码文件（如 auth.py），而是新建文件，通过继承、装饰器或猴子补丁的方式扩展。这样未来 git merge 官方更新时不会产生大量冲突。例如：新建 api/controllers/auth_feishu.py，在路由注册时覆盖原登录路由。
  • 本地模型与 Dify 的兼容性：vLLM 部署的 DeepSeek-R1 需要确认是否支持 Dify 所需的 Function Calling 格式。部分开源模型对工具调用的支持不完善，需要在 Dify 的 model_runtime 中做格式转换适配。

▎可扩展优化

  • 多租户扩展：如果未来要为子公司或外部合作伙伴开放平台，可以在当前 RBAC 基础上引入多租户（Multi-Tenant）架构，每个租户独立的数据空间、独立的模型配额、独立的审计日志。
  • 审计与合规：企业内网 Agent 平台必须记录所有操作日志（谁在什么时间调用了哪个 Agent、输入了什么、输出了什么），建议在网关层统一采集，对接公司的日志分析平台（如 ELK 或 Splunk）。
  • 模型路由与降级：当内网 vLLM 服务负载过高时，自动降级到更轻量的模型（如从 DeepSeek-R1 降级到 Qwen2.5-7B），保证平台可用性。

工程实现

场景标签

Agent Memory · 短期记忆 · 滑动窗口 · 动态槽位

📝 题目

你正在为一个 HR 智能招聘 Agent 实现「短期记忆」模块。该 Agent 的核心场景是：候选人与 Agent 进行多轮对话，Agent 逐步收集候选人的信息（姓名、工作年限、期望薪资、技术栈、到岗时间等），最终生成一份完整的候选人画像。

当前实现中，每次对话都把完整的聊天历史拼进 Prompt，导致以下问题：
- 当对话超过 15 轮时，Token 消耗超过 8000，接近模型上下文上限
- 用户在早期提到的关键信息（如「我期望薪资 25K」）在后期被滑动窗口截断后丢失
- 用户说「改成 30K 吧」时，Agent 无法正确理解「改」指的是修改之前提到的期望薪资

请设计一套结合滑动窗口 + 总结摘要 + 动态槽位填充的短期记忆方案。要求：
1. 给出记忆模块的数据结构设计（伪代码）
2. 说明每一轮对话后记忆的更新流程
3. 解释如何解决上述三个问题

💡 参考答案

▎解题思路

  1. 三种记忆机制各司其职：滑动窗口保留最近的原始对话，保证上下文连贯；总结摘要压缩更早的对话，保留关键信息；动态槽位专门锁定结构化字段（薪资、年限等），解决「改」这类指代问题。
  2. 数据结构设计：短期记忆不是简单的「消息列表」，而是一个包含 raw_messages（滑动窗口）、summary（摘要）、slots（槽位字典）的复合结构。
  3. 更新流程：每轮对话后，先提取槽位，再判断是否需要触发摘要，最后更新滑动窗口。

▎详细方案

数据结构设计（伪代码）：

class ShortTermMemory:
    def __init__(self, session_id: str):
        self.session_id = session_id
        # 1. 滑动窗口：仅保留最近 6 轮原始消息
        self.raw_messages: list[dict] = []  # [{"role": "user", "content": "..."}, ...]
        self.window_size: int = 6  # 6 轮 = 6 条 user + 6 条 assistant

        # 2. 摘要：对窗口之外的历史对话做压缩
        self.summary: str = ""  # 例如："候选人张三，5年Java经验，期望薪资25K..."

        # 3. 动态槽位：结构化关键字段
        self.slots: dict = {
            "name": None,
            "years_of_experience": None,
            "expected_salary": None,
            "tech_stack": [],
            "notice_period": None,
            "current_status": None,
            # ... 其他字段
        }

        # 4. 槽位更新时间戳（用于冲突处理）
        self.slot_updated_at: dict = {}  # {"expected_salary": "2025-01-15T10:30:00"}

每轮对话后的记忆更新流程：

def update_memory(self, user_input: str, assistant_output: str):
    # Step 1: 槽位提取（用轻量级 LLM 调用或规则）
    extracted_slots = self.extract_slots(user_input, self.slots)
    # 例如用户说"改成30K吧"，结合上一轮槽位，提取出 {"expected_salary": 30000}

    # Step 2: 槽位冲突处理
    for key, value in extracted_slots.items():
        if value is not None:
            if self.slots[key] is not None and self.slots[key] != value:
                # 槽位被覆盖，记录变更日志
                self.log_slot_change(key, self.slots[key], value)
            self.slots[key] = value
            self.slot_updated_at[key] = datetime.now().isoformat()

    # Step 3: 更新滑动窗口
    self.raw_messages.append({"role": "user", "content": user_input})
    self.raw_messages.append({"role": "assistant", "content": assistant_output})

    # Step 4: 窗口溢出时触发摘要
    if len(self.raw_messages) > self.window_size:
        # 取最早的 4 条消息做增量摘要
        overflow_messages = self.raw_messages[:4]
        self.summary = self.incremental_summarize(self.summary, overflow_messages)
        # 从窗口中移除已摘要的消息
        self.raw_messages = self.raw_messages[4:]

组装 Prompt 时的逻辑：

def build_prompt(self, current_input: str) -> str:
    prompt_parts = []

    # 1. 系统提示词
    prompt_parts.append("你是 HR 招聘助手...")

    # 2. 槽位状态（结构化展示，让模型知道当前已收集的信息）
    slots_str = json.dumps(self.slots, ensure_ascii=False, indent=2)
    prompt_parts.append(f"当前已收集的候选人信息：\n{slots_str}")

    # 3. 历史摘要（如果有）
    if self.summary:
        prompt_parts.append(f"对话历史摘要：\n{self.summary}")

    # 4. 滑动窗口内的原始对话
    for msg in self.raw_messages:
        prompt_parts.append(f"{msg['role']}: {msg['content']}")

    # 5. 当前用户输入
    prompt_parts.append(f"user: {current_input}")

    return "\n\n".join(prompt_parts)

如何解决三个问题：

  • 问题 1（Token 超限）：滑动窗口将原始对话限制在 6 轮以内，每轮约 200~300 tokens，窗口部分约 1500 tokens；摘要部分控制在 500 tokens 以内；槽位部分约 200 tokens。总 Prompt 控制在 3000 tokens 以内。
  • 问题 2（早期信息丢失）：当消息从滑动窗口溢出时，先经过增量摘要再丢弃。摘要不是简单的截断，而是用轻量级 LLM 提取关键信息（如「候选人提到期望薪资 25K，有 5 年 Java 经验」），确保重要信息不丢失。
  • 问题 3（指代消解）：槽位提取时，将上一轮的槽位状态作为上下文传入。例如用户说「改成 30K 吧」，槽位提取器看到上一轮 expected_salary = 25000，就能推断出「改」指的是修改 expected_salary，将其更新为 30000。

▎关键细节 & 踩坑点

  • 槽位提取器的选择：不要用大模型做槽位提取（太贵太慢），建议用规则 + 轻量级 NER 模型（如 spaCy 或 BERT-NER），或者用一个小参数 LLM（如 Qwen-2B）专门做槽位提取。槽位提取的 Prompt 要包含「上一轮槽位状态」和「当前用户输入」，输出 JSON 格式的槽位更新。
  • 摘要的触发时机：不要在用户对话的主线程中同步做摘要（会增加响应延迟），而是异步触发。当窗口溢出时，将溢出消息放入消息队列，由后台 Worker 做摘要，摘要完成后更新 self.summary。如果用户在下一条消息到来时摘要还没完成，先用旧的摘要 + 完整窗口兜底。
  • 槽位冲突的日志记录：用户可能多次修改同一个槽位（如先说期望 25K，后说 30K），需要记录变更历史，方便后续审计和模型理解上下文。变更日志可以存在 Redis 的 List 中。
  • 窗口大小的动态调整：不同场景的最优窗口大小不同。招聘场景中，候选人的回答通常较长，窗口可以设为 4~6 轮；简单的 FAQ 客服场景，窗口可以设为 8~10 轮。建议将窗口大小做成可配置参数，根据线上数据调优。
  • 槽位与摘要的一致性：当槽位被更新后，摘要中可能还保留旧的槽位值。需要在摘要更新时，以槽位为准做修正。例如摘要中说「期望薪资 25K」，但槽位已经更新为 30K，组装 Prompt 时应该以槽位为准，摘要中的旧值要标注为「历史信息」。

▎可扩展优化

  • 槽位驱动的主动追问：当槽位中有必填字段为空时，Agent 可以主动发起追问。例如 expected_salary 为空时，Agent 主动问「方便透露一下您的期望薪资吗？」。这需要槽位模块暴露「缺失字段列表」给对话策略层。
  • 记忆持久化与恢复：短期记忆存在 Redis 中（TTL 30 分钟），但如果服务重启或用户长时间未响应，需要从 PostgreSQL 中恢复。可以在每次槽位更新时同步写一份快照到 PostgreSQL。
  • 多模态槽位：如果候选人上传了简历 PDF，可以将简历解析后的结构化信息自动填充到槽位中，减少对话轮次。

排障优化

场景标签

Agentic RAG · 延迟优化 · Token 成本 · 反思机制

📝 题目

你们团队基于 LangGraph 构建了一个 Agentic RAG 系统，用于企业内部的 IT 运维知识问答。系统上线后发现两个严重问题：

问题 1：响应延迟过高。 用户从提问到看到完整回答，平均耗时 45 秒。监控显示：单次用户请求平均触发了 6 次 LLM 调用（包括 2 次 Query 重写、1 次路由决策、2 次文档相关性评分、1 次最终生成），每次 LLM 调用平均耗时 5 秒，加上检索和网络开销约 15 秒。

问题 2：Token 成本失控。 单次用户请求平均消耗 12000 tokens（输入 10000 + 输出 2000），是传统 RAG 的 4 倍。其中，每次反思循环都会把完整的检索结果和中间状态重新注入 Prompt，导致输入 Token 膨胀。

用户反馈：「我就问一个简单的『怎么重置 VPN 密码』，为什么等了快一分钟？」

请分析：如何在不显著降低回答质量的前提下，将延迟从 45 秒降到 10 秒以内，Token 消耗从 12000 降到 4000 以内？请给出具体的优化方案和优先级排序。

💡 参考答案

▎解题思路

  1. 先定位瓶颈：延迟的 45 秒中，LLM 调用占 30 秒（6 次 × 5 秒），检索和网络占 15 秒。Token 消耗的 12000 中，输入占 10000，主要来自反思循环中重复注入的检索结果和状态。
  2. 核心策略：减少 LLM 调用次数（合并步骤、引入轻量级模型）+ 压缩 Prompt 体积（避免重复注入、使用摘要代替全量）+ 引入缓存（相似问题直接命中）。
  3. 优先级排序：先做「快速分流」（简单问题不走 Agentic RAG），再做「调用合并」（减少反思循环），最后做「模型分级」（轻量模型做中间步骤）。

▎详细方案

优化 1：入口分流——简单问题走快速通道（最高优先级）

  • 思路：用户问「怎么重置 VPN 密码」这类简单事实性问题，根本不需要 Agentic RAG 的多次反思循环。在入口处增加一个轻量级意图分类器（向量相似度或小模型），将问题分为「简单事实查询」和「复杂推理查询」。
  • 实现：
  • 简单事实查询（约 70% 流量）：直接走传统 RAG 流程——单次检索 + 单次生成，2 次 LLM 调用，延迟降到 10 秒以内。
  • 复杂推理查询（约 30% 流量）：才走完整的 Agentic RAG 流程。
  • 效果：70% 的请求延迟从 45 秒降到 10 秒，Token 从 12000 降到 3000。

优化 2：合并反思循环——从「多轮反思」到「单轮评估」

  • 思路：原来的流程是「检索 → 评分 → 不相关 → 重写 Query → 再检索 → 再评分 → 生成」，每次评分都是一次独立的 LLM 调用。改为「检索 → 一次评估（同时判断相关性和完备性）→ 如果不通过，直接生成」。
  • 实现：
  • 将「文档相关性评分」和「回答完备性验证」合并为一次 LLM 调用，Prompt 中同时输出两个判断：{"relevant": true/false, "complete": true/false, "reason": "..."}。
  • 如果 relevant=false，只做一次 Query 重写和补充检索，然后直接生成，不再二次评估。
  • 如果 complete=false，在生成时明确告知模型「当前信息可能不完整，请基于已有信息回答，并标注不确定的部分」。
  • 效果：LLM 调用次数从 6 次降到 3~4 次，延迟减少约 10~15 秒。

优化 3：轻量级模型做中间步骤

  • 思路：Query 重写、文档评分这些中间步骤不需要最强的模型。用 Qwen-2.5-7B 或更小的模型替代 GPT-4/DeepSeek-R1，只在最终生成时用大模型。
  • 实现：
  • 在 LangGraph 的节点配置中，为不同节点指定不同的模型。例如：rewrite_node 用 Qwen-2.5-7B，grade_node 用 Qwen-2.5-7B，generate_node 用 DeepSeek-R1。
  • 轻量模型的单次调用延迟从 5 秒降到 1~2 秒，Token 消耗也大幅下降。
  • 效果：中间步骤的延迟和 Token 消耗降低 60% 以上。

优化 4：Prompt 压缩——避免全量状态重复注入

  • 思路：反思循环中，每次 LLM 调用都把完整的检索结果（可能 10 个 Chunk，每个 500 tokens）重新注入，导致输入 Token 膨胀。
  • 实现：
  • 检索结果去重：在注入前，对检索到的 Chunk 做去重（基于文本相似度或哈希），避免重复内容。
  • Chunk 截断：每个 Chunk 只保留与当前 Query 最相关的前 200 tokens，而不是注入完整的 500 tokens。
  • 状态摘要：在反思循环中，不注入完整的历史状态，而是注入一个精简的状态摘要（如「上一轮检索了 5 个文档，其中 2 个相关，已提取关键信息：xxx」）。
  • 效果：单次输入 Token 从 10000 降到 4000 左右。

优化 5：语义缓存（Semantic Cache）

  • 思路：IT 运维场景中，大量问题是重复的（如「怎么重置 VPN 密码」可能每天被问 50 次）。对相似度 > 0.95 的问题，直接返回缓存答案。
  • 实现：
  • 用向量数据库存储历史问答对，用户提问时先做相似度匹配，如果命中缓存，直接返回，不走任何 LLM 调用。
  • 缓存 TTL 设置为 7 天（IT 知识更新周期），知识库更新时主动失效相关缓存。
  • 效果：缓存命中率约 30%~40%，这部分请求的延迟降到 200ms 以内，Token 消耗为 0。

▎关键细节 & 踩坑点

  • 入口分流的误判风险：简单问题被误判为复杂问题，只会增加延迟（用户等更久）；复杂问题被误判为简单问题，会导致回答质量下降（用户得到不完整的答案）。因此，分类器的阈值要偏向「宁可多走复杂流程」，即简单问题的置信度阈值设高一些（如 0.9 以上）。
  • 反思循环的「无限循环」问题：如果 Query 重写后检索结果仍然不相关，系统可能陷入「重写 → 检索 → 评分 → 不相关 → 重写」的死循环。必须设置最大迭代次数（如 2 次），超过后直接生成回答并标注「信息可能不完整」。
  • 轻量模型的能力边界：Query 重写用轻量模型是安全的，但「文档相关性评分」如果轻量模型能力不足，可能把相关文档误判为不相关，导致漏检。建议在轻量模型评分不通过时，用大模型做一次复核（仅对边界 case）。
  • 语义缓存的时效性：IT 运维知识可能频繁更新（如 VPN 密码重置流程变更）。缓存必须有版本控制，知识库更新时触发缓存失效。否则用户可能拿到过时的答案。
  • 监控指标：优化后需要持续监控「延迟分位数（P50/P95/P99）」「Token 消耗分布」「缓存命中率」「用户满意度」等指标，确保优化没有牺牲质量。

▎可扩展优化

  • 流式输出：最终生成阶段使用流式输出（Streaming），让用户在 2 秒内看到第一个 Token，而不是等 10 秒才看到完整回答。这能显著改善用户体验，即使总延迟不变。
  • 预取与并行：在入口分流阶段，如果判断为复杂问题，可以并行启动「Query 重写」和「初步检索」，减少串行等待时间。
  • 模型蒸馏：当积累足够多的「简单问题 → 标准答案」数据后，可以蒸馏一个更小的专用模型（如 0.5B），直接处理高频简单问题，进一步降低延迟和成本。
