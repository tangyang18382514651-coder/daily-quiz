一、概念题（10 道）

📌 概念题 · Q1

考点标签

LangGraph · 状态管理 · 时间旅行 · 难度：⭐⭐⭐⭐

📝 题目

在 LangGraph 中，Checkpoint + Memory 组合是实现“时间旅行”（节点回滚、断点续跑）的核心机制。但知识库中提到，生产环境用 Redis 做 Checkpoint 热存储，同时用 PostgreSQL 归档全量流转日志和历史推理数据。为什么不能只用 Redis？Redis 和 PostgreSQL 在 Agent 状态管理中各自扮演什么角色？这种“热冷分离”的架构设计解决了什么核心矛盾？

💡 参考答案

▎一句话结论

Redis 负责“快”——保证多实例共享状态的低延迟读写，支撑实时回滚；PostgreSQL 负责“全”——持久化完整的历史轨迹和推理过程，支撑审计、复盘和长周期数据分析。两者不是替代关系，而是“热数据缓存 + 冷数据归档”的互补架构。

▎核心原理

  • Redis 的角色是“工作内存”：Checkpoint 是 Agent 每一步执行后的状态快照，回滚时需要毫秒级读取。Redis 的纯内存读写特性天然适合这个场景，同时 TTL 自动过期机制避免了状态数据无限堆积。
  • PostgreSQL 的角色是“档案库”：全量流转日志记录了每一次 Prompt、每一次工具调用、每一次状态变更的完整细节。这些数据不需要实时访问，但必须长期保留，用于问题排查、效果评估和合规审计。
  • 热冷分离的核心矛盾：内存昂贵且容量有限，磁盘便宜但速度慢。如果把所有历史 Checkpoint 都堆在 Redis，成本会指数级增长；如果只用 PostgreSQL，回滚操作会因为磁盘 I/O 变得极慢，用户体验不可接受。

▎深入解释

你可以把 Redis 想象成你办公桌上的文件夹——正在处理的案子随手就能翻到，但桌面空间有限，结案的就得归档到档案室（PostgreSQL）。当运营人员说“我要回滚到昨天下午 3 点那个版本”，系统先去 Redis 找，如果 TTL 还没过期就直接恢复（毫秒级）；如果已经过期，就去 PostgreSQL 找到对应的 Checkpoint ID，加载回来再恢复（秒级）。这种设计既保证了高频操作的性能，又不会让内存被历史数据撑爆。

▎面试加分点

  • 能说出“热冷分离”不仅是存储选型问题，更是成本与性能的平衡艺术。
  • 提到 TTL 过期策略与 PostgreSQL 定时清理冷数据（或迁移至对象存储）的联动设计。
  • 理解 Checkpoint ID + trace_id + version 的绑定关系，说明你对状态隔离有深入认知。

▎常见误区

  • 误以为 Redis 可以完全替代关系型数据库做全量存储——Redis 本质是缓存，数据可能丢失（宕机、TTL 过期）。
  • 忽略 PostgreSQL 在审计和复盘中的价值——只知道存，不知道为什么要存。

📌 概念题 · Q2

考点标签

DPO微调 · 过拟合 · LoRA · 难度：⭐⭐⭐⭐

📝 题目

知识库中提到，对客服模型做 DPO 偏好微调时，出现了“过拟合导致泛化能力变差”的问题，解决方案是“降低学习率、减小 LoRA 秩（Rank）、加入早停策略，同时补充高频业务样本”。为什么减小 LoRA 秩能缓解过拟合？补充高频业务样本又是从什么角度解决问题的？这两个策略分别针对过拟合的哪两个不同根因？

💡 参考答案

▎一句话结论

减小 LoRA 秩是通过降低模型可训练参数的自由度来抑制对训练数据的“死记硬背”（模型复杂度层面）；补充高频业务样本是通过增加数据多样性和覆盖面来防止模型学到虚假的统计规律（数据分布层面）。两者一内一外，分别从模型容量和数据质量两个维度对抗过拟合。

▎核心原理

  • LoRA 秩的本质是“低秩近似”的压缩程度：秩越大，可训练的旁路矩阵越接近全参微调，模型越容易记住训练样本的噪声和细节；秩越小，旁路矩阵的表达能力受限，模型被迫只学习最核心的模式，泛化性反而更好。
  • 过拟合的数学本质：模型在训练集上 loss 很低，但在验证集上 loss 开始上升——说明模型学到的不是真正的规律，而是训练集的“特例”。
  • 高频业务样本的作用：DPO 训练数据中如果缺少某些高频场景（如社保查询、薪资计算），模型会对这些场景“生疏”，反而在低频场景上过度拟合。补充这些样本能让训练分布更接近真实业务分布。

▎深入解释

打个比方：让一个学生背 10 道题去考试。如果他记忆力极强（高 LoRA 秩），他可能连题目里的错别字都背下来了，换一种问法就不会做——这就是过拟合。降低 LoRA 秩相当于让他只能用“关键词记忆法”，逼他理解题目背后的知识点。而补充高频业务样本，相当于告诉他“考试重点在第 3、5、8 章”，让他把有限的记忆力用在刀刃上。早停策略则相当于模拟考发现成绩不再提升时就停止训练，避免“走火入魔”。

▎面试加分点

  • 能区分“模型复杂度导致的过拟合”和“数据分布偏差导致的过拟合”。
  • 提到 LoRA 秩的选择是一个超参数调优问题，不是越小越好——太小会导致欠拟合。
  • 理解 DPO 三元组（prompt + chosen + rejected）的质量比数量更重要。

▎常见误区

  • 认为过拟合只能通过降低学习率解决——实际上学习率、秩、数据、早停是组合拳。
  • 误以为 LoRA 秩越小越好——秩太小模型会“学不动”，需要在拟合能力和泛化能力之间找平衡。

📌 概念题 · Q3

考点标签

Agent架构 · 上下文压缩 · 熔断机制 · 难度：⭐⭐⭐⭐⭐

📝 题目

Claude Code 的源码暴露了一套“四阶段上下文压缩系统”，其中第四阶段（终极手段）会调用高性能模型将历史全量打包压缩。更关键的是，源码中写入了一个硬限制：如果自动压缩连续失败 3 次，系统会抛出 CompactionError 并强制将当前 Session 切换为只读模式。这个“熔断机制”在 Agent 工程中解决的核心风险是什么？为什么说它是防止“刷爆 API 账单”的最后防线？

💡 参考答案

▎一句话结论

熔断机制解决的是 Agent 陷入“压缩失败→重试→再失败→再重试”的无限循环，每次重试都在消耗 Token 费用，最终导致 API 账单失控。它通过强制降级为只读模式，切断恶性循环，是工程上对“不确定性”的兜底防御。

▎核心原理

  • 压缩失败的连锁反应：上下文越长，模型注意力越分散，压缩质量越差；压缩质量差导致关键信息丢失，模型后续决策出错；出错后模型可能再次尝试压缩修复，形成恶性循环。
  • Token 消耗的隐性成本：每次压缩调用大模型（尤其是 Stage 4 调用高性能模型）都在消耗大量 Token。如果连续失败 3 次，说明当前 Session 的状态已经混乱到无法自动修复，继续尝试只会白白烧钱。
  • 熔断的设计哲学：宁可“服务降级”（只读模式不能再执行新任务），也不能“服务崩溃”（账单爆了或 API 被封）。

▎深入解释

想象一个场景：你的 Agent 在处理一个超长文档，上下文已经堆到 100K token。它尝试压缩，但压缩后的摘要漏掉了关键信息，导致后续推理出错。Agent 发现错误后，又尝试重新压缩，结果又漏了不同的信息。每次压缩调用 Sonnet 或 Opus 这种高级模型，成本可能是普通调用的 5-10 倍。如果没有熔断，这个循环可能持续几十轮，一晚上烧掉几百美元。Claude Code 的设计者深知这一点，所以用“3 次失败即熔断”的硬规则，把损失控制在可接受范围内。

▎面试加分点

  • 能说出“熔断”不仅是技术问题，更是成本控制问题——这是架构师的视角。
  • 理解“只读模式”的含义：用户还能查看历史记录，但不能发起新的生成任务，需要人工介入修复。
  • 能类比微服务架构中的熔断器模式（Circuit Breaker），说明跨领域的工程思维。

▎常见误区

  • 认为熔断是“程序 bug”——实际上它是故意设计的防御机制。
  • 只看到“连续失败 3 次”的表面规则，不理解背后的成本考量。

📌 概念题 · Q4

考点标签

RAG优化 · 语义分块 · 重排序 · 难度：⭐⭐⭐

📝 题目

知识库中多次强调，RAG 系统的文档分块策略从“固定长度切块”演进到了“语义分块 + 滑动窗口”。固定长度切块的核心缺陷是什么？语义分块相比它解决了什么问题？滑动窗口又是如何进一步增强分块质量的？

💡 参考答案

▎一句话结论

固定长度切块会粗暴地割裂完整的语义单元（如一个段落在中间被切断），导致检索时召回的是“半句话”，大模型无法理解上下文。语义分块通过识别自然段落边界保持语义完整性，滑动窗口则通过相邻块之间的重叠区防止边界信息丢失，两者配合实现了“既不断章取义，又不遗漏边界”。

▎核心原理

  • 固定长度切块的致命缺陷：以 512 token 为单位一刀切，可能正好把一个法律条文的“条件”和“结果”切到两个块里。用户问“什么情况下可以申请劳动仲裁”，检索只召回了“条件”那块，大模型看不到“结果”，只能瞎编。
  • 语义分块的核心逻辑：根据文档的自然结构（段落、章节、标题层级）或语义相似度（相邻句子的 Embedding 距离）来决定切分点，确保每个块是一个完整的语义单元。
  • 滑动窗口的增强作用：即使语义分块已经尽量保持完整，边界处的上下文仍然可能丢失。滑动窗口让相邻块之间有 10%-20% 的重叠，相当于给边界信息上了“双保险”。

▎深入解释

你可以把文档想象成一部小说。固定长度切块相当于每 100 页撕一刀，可能正好把“凶手是——”撕在上一页，下一页开头是“——管家”。语义分块相当于按章节撕，保证每章完整。滑动窗口相当于在每章结尾多印半页上一章的内容，防止你忘了前情提要。在 HR 客服场景中，一个社保政策的“适用条件”和“申请流程”如果被切到两个块，用户问“我能申请吗”时，系统可能只召回“流程”而漏掉“条件”，导致错误回答。

▎面试加分点

  • 能说出“语义分块”的具体实现方式（基于 NLTK 句子分割、基于 Embedding 相似度阈值、基于文档结构标记）。
  • 提到滑动窗口的大小是一个超参数，需要根据文档类型和检索场景调优。
  • 理解分块策略直接影响后续检索和重排的效果，是 RAG 系统的“地基”。

▎常见误区

  • 认为分块越细越好——太细会导致每个块信息量不足，检索时上下文缺失。
  • 忽略滑动窗口带来的存储冗余——重叠区会增加向量库的存储成本，需要在效果和成本之间权衡。

📌 概念题 · Q5

考点标签

大模型推理 · KV Cache · 长上下文 · 难度：⭐⭐⭐⭐

📝 题目

大模型处理长上下文时，KV Cache 是保证推理速度的关键技术。但知识库指出，随着上下文变长，KV Cache 会“零碎地霸占显存”。vLLM 的 PagedAttention 技术通过借鉴操作系统的虚拟内存概念解决了这个问题。为什么传统的 KV Cache 管理方式会产生显存碎片？PagedAttention 的“分页”机制是如何消除碎片的？

💡 参考答案

▎一句话结论

传统 KV Cache 为每个序列分配连续显存块，不同序列的长度差异导致大量“既不够用又无法释放”的碎片空间。PagedAttention 将 KV Cache 切分为固定大小的“页”，按需分配、动态映射，彻底消除了外部碎片，显存利用率提升 2-4 倍。

▎核心原理

  • 显存碎片的成因：假设显存里有 10GB 空闲，但被分割成 100 个 100MB 的小块。一个序列需要 150MB 的连续空间来存 KV Cache，虽然总空闲足够，但找不到连续的 150MB，只能 OOM（Out of Memory）。
  • PagedAttention 的分页逻辑：将 KV Cache 切分为固定大小的 Page（如 4MB 一页）。一个序列的 KV Cache 不需要连续存储，而是通过页表映射到分散的物理页，就像操作系统的虚拟内存。
  • 动态分配与回收：序列变长时按需分配新页，序列结束时立即回收所有页，不会留下碎片。

▎深入解释

把显存想象成停车场。传统方式要求每辆车（序列）必须停在一整排连续的车位上，车走了留下的空位可能不够下一辆车停，久而久之停车场里到处是“缝隙”。PagedAttention 相当于允许一辆车拆成零件，分散停在任何空位，只要有个记录本（页表）记下每个零件的位置就行。这样停车场永远不会有“缝隙”，利用率接近 100%。在 Agent 场景中，同时服务 100 个用户对话，每个对话长度不同，PagedAttention 能让同一块 GPU 显存撑住更多并发。

▎面试加分点

  • 能区分“内部碎片”和“外部碎片”——传统方式产生外部碎片，PagedAttention 可能产生少量内部碎片（最后一页用不满），但总体利用率大幅提升。
  • 提到 PagedAttention 与 FlashAttention 的协同关系——前者解决显存管理，后者解决计算速度。
  • 理解为什么 Agent 场景比单轮问答更需要 PagedAttention——Agent 的多轮对话和长上下文是常态。

▎常见误区

  • 认为 PagedAttention 是 FlashAttention 的替代品——两者解决不同层面的问题，可以叠加使用。
  • 误以为分页会降低访问速度——页表映射有微小开销，但显存利用率提升带来的吞吐量增益远超这个开销。

📌 概念题 · Q6

考点标签

Agent健康检查 · 死循环检测 · 可观测性 · 难度：⭐⭐⭐

📝 题目

知识库中提到，Agent 的健康检查包含三个层次：服务存活（接口能通）、工具连通性（内部接口正常）、逻辑监控（防止死循环和“发疯”）。其中逻辑监控提到“单次对话步骤不超过 5 步就判定为死循环”。这个阈值设定背后的工程考量是什么？为什么不能完全依赖 max_iterations 框架参数，还需要额外配置“固定考题抽测”？

💡 参考答案

▎一句话结论

max_iterations 是硬上限，防止单次对话无限消耗资源；固定考题抽测是软监控，检测 Agent 是否在限定步数内给出了“错误但未超限”的结果。前者防“量变”（资源耗尽），后者防“质变”（逻辑错误），两者互补构成完整的逻辑监控体系。

▎核心原理

  • 硬上限的盲区：假设 max_iterations=5，Agent 在 3 步就给出了一个看似合理但完全错误的答案（如幻觉），框架不会报错，因为它没超限。硬上限只防“跑太久”，不防“跑偏了”。
  • 固定考题抽测的设计逻辑：准备一组已知正确答案的黄金测试用例，定期（如每半小时）让 Agent 自动回答，对比输出与标准答案。如果连续多次匹配失败，说明 Agent 的推理逻辑出了问题（可能是模型更新、Prompt 变更或工具故障导致）。
  • 步数阈值的工程考量：5 步不是拍脑袋定的。正常业务对话（如查社保政策）通常在 2-3 步完成（意图识别→检索→生成）。5 步已经包含了重试和反思的空间。超过 5 步大概率是陷入了“查不到→换关键词再查→还是查不到→再换”的死循环。

▎深入解释

把 Agent 想象成一个工人。max_iterations 相当于规定他最多加班 5 小时，超时就强制下班——防止他累死。固定考题抽测相当于质检员每隔半小时拿一个已知答案的问题去考他，看他是不是在“磨洋工”或者“脑子糊涂了”。如果工人 3 小时就交了活，但质检发现全是错的，那就得拉响警报。在工程实践中，Langfuse、Phoenix 等观测平台已经内置了这种自动评测能力，你只需要配置数据集和告警规则。

▎面试加分点

  • 能说出“硬上限”和“软监控”的互补关系，体现系统化思维。
  • 提到固定考题的选择策略——要覆盖高频场景、边界场景和已知的“翻车”场景。
  • 理解健康检查的最终目标不是“发现问题”，而是“快速定位根因”（是模型问题、工具问题还是数据问题）。

▎常见误区

  • 认为设置了 max_iterations 就万事大吉——这只是第一道防线。
  • 固定考题抽测频率设置过高——太频繁会浪费 Token，太低会延迟发现问题。

📌 概念题 · Q7

考点标签

Agent鉴权 · OAuth 2.0 · 服务账号 · 难度：⭐⭐⭐⭐

📝 题目

知识库中提到了 Agent 与企业旧系统通信的两种鉴权模式：面向用户的“托管代理人模式”（OAuth 2.0）和面向自动化任务的“服务账号模式”（HMAC-SHA256 动态签名）。为什么不能给 Agent 分配一个永久的超级管理员 API Key 来解决所有鉴权问题？这两种模式分别解决了什么安全风险？

💡 参考答案

▎一句话结论

永久超级管理员 Key 一旦泄露，攻击者可以无限制访问所有系统，是安全上的“单点溃坝”。托管代理人模式通过注入用户身份实现“最小权限原则”，服务账号模式通过动态签名防止重放攻击和 Key 泄露后的无限滥用。两者分别解决了“谁能访问”和“请求是否被篡改”两个核心安全问题。

▎核心原理

  • 超级管理员 Key 的致命缺陷：Agent 的代码、配置文件、环境变量都可能成为泄露点。一旦 Key 泄露，攻击者可以伪装成 Agent 访问所有系统，且审计日志只显示“Agent 在操作”，无法追溯到具体攻击者。
  • 托管代理人模式的权限继承：Agent 不拥有自己的权限，而是携带当前用户的 Access Token 去调用后端系统。后端系统根据 Token 中的用户身份和权限决定是否放行。即使 Token 泄露，也只能访问该用户有权限的数据，影响范围可控。
  • HMAC-SHA256 动态签名的防篡改与防重放：每次请求都用时间戳 + 随机数 + 密钥生成唯一签名。即使攻击者截获了请求，签名在几秒后就失效（时间戳过期），且无法伪造（没有密钥）。

▎深入解释

把超级管理员 Key 想象成一把万能钥匙，丢了整个公司所有门都失守。托管代理人模式相当于给每个员工发自己的工卡，Agent 只是“帮员工跑腿”，到每个门前刷的是员工的卡，只能进员工有权进的门。服务账号模式用于没有具体员工的场景（如凌晨自动跑报表），相当于给自动化流程发了一张“限时通行证”，上面写着“仅限今晚 3:00-3:05，从 A 门到 B 门”，超时或路线不对都作废。

▎面试加分点

  • 能区分“用户委托场景”和“机器自动化场景”的鉴权需求差异。
  • 提到 OAuth 2.0 的 scope 机制可以进一步细化 Agent 的权限（如只读 vs 读写）。
  • 理解 HMAC 签名中时间戳和随机数（nonce）各自的作用——时间戳防重放过期请求，nonce 防同一秒内的重复请求。

▎常见误区

  • 认为 OAuth 2.0 只适用于 Web 应用——实际上它是标准的授权框架，Agent 同样适用。
  • 混淆 HMAC 签名和加密——HMAC 只保证完整性和认证，不加密内容本身。

📌 概念题 · Q8

考点标签

Agent工程 · Vibe Coding · 上下文管理 · 难度：⭐⭐⭐

📝 题目

知识库中总结了 Vibe Coding 的几大原则，包括“事不过三”原则（连续 3 次让 AI 修复同一个 Bug 仍报错就喊停）和“动态项目上下文快照”（维护一个 context.md 文件实现新 Chat 的秒级热启动）。为什么 AI 会在修复 Bug 时陷入“思维死胡同”？context.md 文件相比直接让 AI 读取项目代码有什么核心优势？

💡 参考答案

▎一句话结论

AI 在连续修复同一 Bug 时容易陷入“局部最优陷阱”——每次修复只盯着报错的那一行，拆东墙补西墙，引入新 Bug。context.md 通过预编译的架构摘要和已知坑点，让 AI 在新 Chat 中直接站在“全局视角”，避免从头扫描代码导致的长文本注意力溃散。

▎核心原理

  • 思维死胡同的成因：AI 没有真正的“理解”，它是基于上下文做模式匹配。当连续 3 次修复同一 Bug 时，上下文已经被错误尝试和报错信息占满，AI 的注意力被锁死在“修复这个报错”上，失去了对整体逻辑的判断力。
  • context.md 的核心价值：它是一个几百字的“项目大脑摘要”，包含当前架构、已实现功能、正在攻坚的模块、已知的坑。新 Chat 开始时，AI 不需要扫描几万行代码，直接读取这个摘要就能快速建立全局认知。
  • 长文本注意力的衰减：当单个文件超过 300 行或整个上下文超过一定阈值时，AI 对细节的注意力会显著下降。context.md 通过极致压缩信息密度，在注意力最集中的前几百 token 内完成“热启动”。

▎深入解释

把 AI 想象成一个只看眼前三米路的修路工人。Bug 是一个坑，他第一次填了土，坑平了但旁边鼓了个包（新 Bug）。第二次他把包铲平，结果铲到了水管（又一个 Bug）。第三次他修水管，把电线挖断了。你如果不喊停，他能在三米范围内折腾一整天。context.md 相当于在每次新开工前，先给他看一张整个街区的地下管线图，告诉他“水管在这，电线在那，坑在这”，他就能一次性修好。

▎面试加分点

  • 能说出“事不过三”不仅是经验规则，更是防止 Token 浪费和 API 账单失控的工程纪律。
  • 提到 context.md 需要人工维护更新，不能自动生成——因为人知道哪些是“关键信息”，AI 不知道。
  • 理解 Vibe Coding 的本质是“人掌舵，AI 划桨”，context.md 是舵手的航海图。

▎常见误区

  • 认为“事不过三”是死板的规则——如果第 3 次失败后你肉眼分析了根因，发现是 AI 忽略了一个关键文件，你可以把文件内容加入上下文后再试一次。
  • 把 context.md 写成项目 README——README 是给人看的，context.md 是给 AI 看的，应该更精炼、更结构化。

📌 概念题 · Q9

考点标签

Transformer · 残差连接 · 梯度消失 · 难度：⭐⭐⭐⭐

📝 题目

Transformer 的每个 Decoder 块都包含“残差连接 + 层归一化”。残差连接的核心公式是 输出 = x + 变换(x)。为什么这个看似简单的“加法”能防止深层网络的梯度消失？如果去掉残差连接，一个 100 层的 Transformer 在训练时会发生什么？

💡 参考答案

▎一句话结论

残差连接为梯度提供了一条“高速公路”，让反向传播时梯度可以直接从深层传回浅层，不会被多层变换的链式求导“稀释”到接近零。去掉残差连接，100 层 Transformer 的浅层参数几乎收不到有效梯度，训练会停滞或极度缓慢。

▎核心原理

  • 梯度消失的数学本质：反向传播时，每经过一层，梯度要乘以该层变换的导数。如果导数小于 1（大多数情况），经过 100 层连乘后，梯度会指数级衰减到接近零，浅层参数无法更新。
  • 残差连接的“梯度高速公路”：输出 = x + 变换(x) 的导数是 1 + 变换的导数。即使变换的导数接近零，梯度至少还有 1 这条“保底通道”，可以直接传回浅层。
  • 层归一化的配合作用：残差连接保证了梯度能传回去，层归一化保证了每层的输入分布稳定，防止数值爆炸或消失。

▎深入解释

想象一个 100 人的传话游戏。传统方式（无残差）是每个人把听到的话用自己的方式转述给下一个人，到第 100 个人时，原话已经面目全非。残差连接相当于每个人传话时，除了自己的转述，还附上一张写着原话的纸条。即使中间有人乱说，纸条上的原话始终不变。训练时，这张纸条就是“梯度 1”，保证最开始的几个人（浅层）也能收到正确的反馈。没有这张纸条，前面的人永远不知道自己说对了没有，整个训练就卡死了。

▎面试加分点

  • 能说出残差连接不是 Transformer 的原创，而是从 ResNet（残差网络）借鉴的跨领域经典设计。
  • 理解“Pre-LN”（先归一化再变换）和“Post-LN”（先变换再归一化）的区别——现代 Transformer 多用 Pre-LN，训练更稳定。
  • 提到残差连接还有一个隐藏好处：它让网络更容易学习“恒等映射”——如果某一层学不到有用特征，至少可以把输入原样传下去，不拖后腿。

▎常见误区

  • 认为残差连接只是“把输入加回去”——它的核心价值在反向传播，不在前向计算。
  • 误以为层数越深效果一定越好——没有残差连接，深层网络反而不如浅层网络。

📌 概念题 · Q10

考点标签

ReAct · Agent范式 · 思考-行动-观察 · 难度：⭐⭐⭐

📝 题目

知识库中明确指出：“LangChain 启用 ReAct 的唯一标志是使用 create_react_agent 创建 Agent。普通 Chain / LLM 直接调用不启动 ReAct。”为什么 ReAct 必须和 Agent 绑定？普通的 LLM 调用（如 llm.invoke(prompt)）本质上缺少 ReAct 循环中的哪个关键环节？

💡 参考答案

▎一句话结论

ReAct 的核心是“观察→思考→行动→观察”的闭环循环，其中“观察”环节（工具调用结果的反馈）是普通 LLM 调用不具备的。普通调用是“一问一答”的单向链路，LLM 看不到自己输出的结果，无法根据反馈调整下一步行动。Agent 通过工具调用和结果回传，补上了这个闭环。

▎核心原理

  • ReAct 的三要素：思考（Reasoning）——分析当前状态和下一步计划；行动（Acting）——调用工具或执行操作；观察（Observation）——获取行动结果并作为下一轮思考的输入。三者缺一不可。
  • 普通 LLM 调用的局限：llm.invoke(prompt) 只是“给 Prompt，返回文本”。LLM 可以在 Prompt 里“假装”思考和行动，但它看不到真实的工具返回结果，无法形成真正的反馈循环。
  • Agent 如何补全闭环：Agent 框架（如 LangGraph、LangChain Agent）在 LLM 输出“行动指令”后，实际执行工具调用，把结果拼回 Prompt，再次交给 LLM 思考。这个“执行→回传→再思考”的循环就是 ReAct。

▎深入解释

把普通 LLM 调用想象成你问一个人“怎么去北京”，他回答“坐高铁”。你追问“高铁票多少钱”，他可能瞎编一个数，因为他没有真的去查。ReAct Agent 相当于给这个人配了一台能上网的手机。他第一次回答“坐高铁”后，你让他“查一下票价”，他真的打开 12306 查了，看到“二等座 553 元”，然后告诉你“553 元”。这个“真的查了”就是“观察”环节，是 ReAct 和纯文本生成的本质区别。

▎面试加分点

  • 能说出 ReAct 不是 LangChain 的专利，而是一种通用的 Agent 推理范式，AutoGPT、CrewAI 等框架也在使用。
  • 理解“思考”环节可以是隐式的（LLM 内部推理），也可以是显式的（输出 <thinking> 标签），后者更利于调试。
  • 提到 ReAct 的常见问题：如果工具返回的信息太长或格式混乱，会污染 LLM 的上下文，导致后续思考质量下降。

▎常见误区

  • 认为在 Prompt 里写“请一步一步思考”就是 ReAct——这只是 Chain of Thought（CoT），缺少“行动”和“观察”环节。
  • 误以为所有 Agent 都使用 ReAct——ReAct 是 Agent 的一种推理范式，还有 Plan-and-Execute、Reflection 等其他范式。

二、应用题（5 道 · 分类型）

题型

架构设计

场景标签

长对话 Agent Token 成本 上下文压缩 熔断

📝 题目

你负责的智能客服 Agent 需要支持长达数小时的多轮对话，上下文会膨胀到几十万 Token，导致每次请求的推理成本飙升，且长文本下模型注意力分散、回复质量下降。请参考 Claude Code 源码中暴露的“四阶段上下文压缩 + 熔断”机制，设计一套企业级的自动上下文压缩方案。要求明确压缩触发条件、各阶段策略、熔断保护逻辑，并说明如何与 LangGraph 的状态管理结合。

💡 参考答案

▎解题思路

  1. 将上下文压缩抽象为一个独立的“压缩器”模块，在每次 Agent 推理前或推理后检查 Token 用量，超过阈值则触发压缩。
  2. 设计四个递进的压缩阶段，从轻量级去重到重度摘要，逐级释放空间；同时引入熔断计数器，防止压缩死循环刷爆账单。
  3. 利用 LangGraph 的 Checkpoint 机制，在压缩前后分别保存状态快照，保证回滚安全。

▎详细方案

  • 阶段 0：监控与触发
    在 LangGraph 的每个节点执行后，统计当前消息列表的 Token 总数。若超过预设上限（如 32k），且距离上次压缩已过 N 轮，则启动压缩流程。

  • 阶段 1：片段去重（Snip Compact）
    扫描上下文中的重复代码块、相似的系统提示、已失效的工具调用结果，将其替换为占位符或直接删除。此阶段无语义损失，可快速回收 10%~20% 空间。

  • 阶段 2：微清理（Micro Compact）
    移除已被后续操作覆盖的“墓碑数据”——例如用户修改了之前的回答，旧版本内容即可丢弃；同时清理已完成的 Todo 项、过期的缓存引用。此阶段需要业务逻辑配合，标记哪些状态是可丢弃的。

  • 阶段 3：历史折叠（Context Collapse）
    将较早的对话轮次（如前 10 轮）通过轻量模型（如 GPT-3.5）生成摘要，替换原始详细记录。摘要保留关键意图、实体和决策，舍弃冗余措辞。此阶段可大幅压缩 Token，但会丢失细节。

  • 阶段 4：系统级压缩（System Compact）
    当以上阶段仍无法满足要求时，调用高性能模型（如 GPT-4）将整个上下文打包成一个标准格式块，包含任务目标、已完成步骤、当前状态、待办事项。此块作为新一轮对话的“基线上下文”，旧历史全部归档到外部数据库。

  • 熔断机制
    维护一个压缩失败计数器。若单次压缩后 Token 数未减少或反而增加，计数器 +1；若连续失败 3 次，立即终止压缩，将当前 Session 降级为只读模式，并发出告警通知人工介入，防止无限循环消耗 API 费用。

  • 与 LangGraph 集成
    压缩器作为 LangGraph 的一个“系统节点”，在每次进入核心推理节点前被条件边调用。压缩前后通过 graph.update_state() 更新 Checkpoint，记录压缩版本号。若压缩导致关键信息丢失，可利用时间旅行回滚到压缩前状态。

▎关键细节 & 踩坑点

  • 阶段 3 的摘要模型必须使用独立、便宜的模型，避免压缩本身成本过高。
  • 摘要时需保留用户明确的“未完成任务”和“待确认事项”，否则 Agent 会“失忆”。
  • 熔断计数器要持久化在 Redis 中，不能随进程重启清零。

▎可扩展优化

  • 引入自适应阈值：根据对话复杂度动态调整压缩触发 Token 数。
  • 对压缩后的上下文进行“忠实度校验”——用一个小模型判断摘要是否遗漏关键事实，若遗漏则回退。
  • 将压缩历史归档至数据湖，用于后续模型微调或问题复盘。

题型

场景分析题

场景标签

自媒体运营 爬虫 反爬 代理池

📝 题目

某自媒体运营 Agent 每日需定时从小红书抓取职场热点笔记，但近期频繁遭遇 IP 封禁、验证码挑战，导致数据采集成功率从 95% 骤降至 30%。请设计一套稳定的爬虫方案，包括代理池架构、请求限速策略、Cookie 会话维持、以及失败重试与降级兜底机制，确保每日能稳定获取至少 80% 的目标热点。

💡 参考答案

▎解题思路

  1. 分析反爬手段：IP 频率限制、设备指纹检测、行为验证码。
  2. 从代理层、请求层、调度层三个维度构建防御体系。
  3. 设计降级方案：当实时爬取失败时，启用备用数据源（如 RSS、第三方热榜 API）。

▎详细方案

  • 代理池架构
    搭建两级代理池：
  • 短效代理池：从商业代理服务商（如快代理、芝麻代理）按量购买高匿代理 IP，通过 API 实时获取，设置 5 分钟过期。

  • 长效代理池：自建家庭宽带代理（如使用 ADSL 拨号动态换 IP），用于需要维持 Session 的场景。
    代理管理器负责健康检查（每分钟探测代理可用性），淘汰失败率 >30% 的 IP，并自动补充。

  • 请求策略

  • 限速：每个 IP 每分钟最多发起 3 次请求，使用令牌桶算法平滑流量。
  • User-Agent 轮换：维护 50+ 真实浏览器 UA，每次请求随机选取。
  • Cookie 会话：为每个代理 IP 绑定独立的 Cookie Jar，模拟登录态；定期（每 2 小时）通过自动化脚本更新 Cookie。

  • 请求头伪装：完整复制浏览器的 Accept-Language、Referer、Sec-Ch-Ua 等头信息。

  • 调度与重试

  • 采用异步任务队列（如 Celery），将爬取任务拆分为小批量，分配到不同代理执行。
  • 遇到 403/429 状态码时，立即标记该代理 IP 失效，并换 IP 重试（最多 3 次），指数退避（5s, 15s, 45s）。

  • 若连续 5 次失败，触发风控告警，暂停该目标站点的爬取 30 分钟，切换至备用数据源。

  • 降级兜底
    维护一个“热点源优先级列表”：小红书 API > 小红书网页 > 第三方聚合热榜 API（如新榜、飞瓜）> 手动上传 CSV。当主渠道成功率低于 50% 时，自动降级到下一级数据源，保证每日内容生产不中断。

▎关键细节 & 踩坑点

  • 小红书网页版强依赖 JavaScript 渲染，必须使用 Playwright 或 Selenium 模拟浏览器，但资源开销大。可部署无头浏览器集群，通过 WebSocket 与爬虫调度器通信。
  • Cookie 过期检测：若响应内容出现登录页关键词，立即触发 Cookie 刷新流程。
  • 代理 IP 质量参差不齐，需建立“代理评分系统”，根据响应速度、成功率、被封概率动态分配任务权重。

▎可扩展优化

  • 引入验证码识别服务（如 2Captcha），在遇到滑块验证时自动打码，但需控制成本。
  • 使用机器学习模型预测目标站点的风控窗口期，在低风险时段加大爬取频率。
  • 将爬虫模块独立为 MCP Server，供多个 Agent 复用。

工程实现题

Agent 健康监控 Langfuse 自动化评估

📝 题目

你部署了一套 HR 智能客服 Agent，但用户投诉它有时会“胡言乱语”或陷入死循环。请设计一套基于 Langfuse 的 Agent 逻辑健康度监控方案，要求实现“固定考题定时抽测”，并自动告警。请描述：① 如何构建黄金考题集；② 如何配置定时评估任务；③ 如何定义评分标准；④ 如何集成到告警系统（如飞书/钉钉）。

💡 参考答案

▎解题思路

  1. 利用 Langfuse 的 Dataset 和 Evaluation 功能，将标准业务问答作为“锚点”，定时向 Agent 发送请求并自动评分。
  2. 评分维度包括：答案准确性、工具调用正确性、步骤数（防死循环）、响应时间。
  3. 通过 Langfuse 的 Webhook 或 API 拉取评估报告，触发告警。

▎详细方案

  • 构建黄金考题集
    从历史真实对话中筛选 50 个高频业务问题，由业务专家标注标准答案和期望的工具调用链（如“查社保余额”必须调用 query_social_security 工具）。
    在 Langfuse 中创建 Dataset，每条记录包含 input（用户问题）、expected_output（标准答案关键词）、expected_tool_calls（工具名列表）。

  • 配置定时评估任务
    使用 Langfuse 的 Python SDK 编写评估脚本，核心逻辑：
    ```python
    from langfuse import Langfuse
    from my_agent import run_agent # 你的Agent入口

langfuse = Langfuse()
for item in dataset.items:
trace = langfuse.trace(name="health_check")
result = run_agent(item.input)
trace.span(name="agent_response", output=result)
# 计算得分
score = evaluate(result, item.expected_output, item.expected_tool_calls)
trace.score(name="health_score", value=score)
```
将脚本部署为 CronJob（K8s CronJob 或服务器 Crontab），每 30 分钟执行一次。

  • 评分标准设计
  • 答案准确性（40 分）：检查回答是否包含标准答案的关键实体/数字，使用模糊匹配或调用一个小模型判断语义相似度。
  • 工具调用正确性（30 分）：解析 Agent 的中间步骤，检查是否调用了预期工具，且参数正确。
  • 流程健康度（20 分）：若 Agent 执行步骤超过 5 步，扣分；若出现重复调用同一工具 3 次以上，判定为死循环，直接 0 分。

  • 性能（10 分）：首字延迟 >5 秒扣 5 分，总耗时 >30 秒扣 5 分。
    总分低于 60 分视为“不健康”。

  • 告警集成
    在评估脚本末尾，拉取最近一次评估的所有 Trace 得分，若平均分 <60 或任意单条得分 <40，调用飞书/钉钉机器人 Webhook 发送告警卡片，包含失败题目、得分详情、Trace 链接。
    同时，Langfuse 本身支持 Score 告警，可在 Langfuse 后台配置 Webhook，当 health_score 低于阈值时自动触发。

▎关键细节 & 踩坑点

  • 黄金考题需要定期更新，避免 Agent 过拟合到固定考题。可设置每月人工审核 + 自动从近期低分对话中抽取新题。
  • 评估脚本本身要加超时和异常捕获，防止评估任务自身卡死。
  • 若 Agent 是非确定性的，可对每个考题执行 3 次取平均分，减少随机波动。

▎可扩展优化

  • 引入 LLM-as-Judge：用 GPT-4 对回答进行打分，替代简单的关键词匹配，提高评估准确性。
  • 将健康监控扩展为“红蓝对抗”：自动生成对抗性问题测试 Agent 的安全护栏。
  • 利用 Langfuse 的 Prompt Management 功能，当健康度持续下降时自动回滚到上一个稳定版本的 Prompt。

排障优化题

长文本推理 位置编码 RoPE 外推

📝 题目

你们的 Agent 接入了某开源大模型，其训练时最大上下文长度为 8K。业务需要处理 32K 的长文档摘要，直接强行输入超长文本后，模型输出出现大量重复、逻辑断裂、甚至乱码。经排查，问题出在位置编码无法泛化到未训练过的长度。请详细解释 RoPE 位置编码在超长文本时失效的原理，并给出至少两种工程解决方案（如 Linear Scaling、NTK-Aware Scaling、YaRN 等），对比它们的优缺点和适用场景。

💡 参考答案

▎解题思路

  1. 明确问题根因：RoPE 通过旋转角度编码位置，当位置 ID 超出训练范围时，旋转角度过大，导致注意力分数分布异常，模型无法正确区分远近关系。
  2. 解决方案的核心是“压缩”位置索引或“插值”旋转频率，使模型在推理时看到的位置编码落在训练分布内。
  3. 对比不同外推方法的实现复杂度、性能损失和适用场景。

▎详细方案

  • 问题原理
    RoPE 对第 i 个位置、第 d 维度的旋转角度为 θ_i = i * base^{-2d/D}，其中 base 通常为 10000。当 i 从 8K 增加到 32K 时，高频维度的旋转角度成倍增长，导致点积注意力中的相对位置信息被扭曲，模型“看到”的词距失真，从而生成混乱。

  • 方案 1：线性位置插值（Linear Scaling / Position Interpolation）
    将位置索引 i 除以缩放因子 s = 32K / 8K = 4，即 i' = i / s。这样 32K 的位置被压缩回 8K 范围。
    优点：实现极其简单，只需修改推理代码中的位置 ID 计算，无需重新训练。
    缺点：会降低模型对局部细节的分辨率，因为相邻位置的旋转角度差变小了，可能导致近距离依赖减弱。适用于对局部精度要求不高的摘要任务。

  • 方案 2：NTK-Aware Scaling
    不压缩位置索引，而是调整 RoPE 的 base 值。根据神经正切核（NTK）理论，增大 base 可以“拉伸”高频维度，让模型在长位置时仍能保留高频分辨能力。新 base' = base * s^{(D/(D-2))}。
    优点：无需微调，对局部信息保留更好，性能优于线性插值。
    缺点：需要计算新的 base，对某些模型可能需要微调才能达到最佳效果。目前被很多开源模型（如 LLaMA 系列）采用。

  • 方案 3：YaRN（Yet another RoPE extensioN）
    结合 NTK 缩放和温度系数，在注意力计算中引入一个可学习的温度参数 t，对不同维度使用不同的缩放策略，并可选地进行少量微调（如 100 步）。
    优点：效果最优，在多个长文本基准上达到 SOTA，且支持动态扩展。
    缺点：实现较复杂，需要修改模型结构并微调，工程成本较高。

  • 工程落地建议
    优先尝试 NTK-Aware Scaling，因为它即插即用，无需微调，且大多数推理框架（如 vLLM、llama.cpp）已内置支持。只需在启动参数中设置 --rope-scaling '{"type":"dynamic","factor":4.0}' 即可。若效果仍不达标，再采集长文本数据用 YaRN 微调。

▎关键细节 & 踩坑点

  • 使用线性插值时，注意不要对第 0 维（直流分量）进行缩放，否则会破坏位置无关的偏置。
  • 不同的模型架构对缩放的敏感度不同，需通过 Perplexity 测试验证。
  • 长文本推理显存暴增，需配合 FlashAttention 和 KV Cache 量化，否则即使位置编码正确也会 OOM。

▎可扩展优化

  • 结合滑动窗口注意力（如 Mistral 的 Sliding Window），在长文本中只对局部窗口做全注意力，远距离用压缩后的全局摘要，可进一步降低计算量。
  • 使用 LongRoPE 等最新技术，将上下文窗口扩展到 2048K，但需要微调。

题型

综合落地题

智能质检 Agent 产品 从 0 到 1

📝 题目

某保险公司要求你从 0 到 1 交付一个“AI 智能客服质检 Agent”。该 Agent 需自动抽取每日客服对话，检测违规话术（如承诺收益、误导销售）、情绪异常（愤怒、投诉倾向）、业务知识错误（答非所问），并生成质检报告，标记高风险会话供人工复核。请给出完整的技术方案，包括：系统架构、数据流、模型选型、质检规则引擎设计、报告生成与告警，以及如何保证质检结果的可靠性和可解释性。

💡 参考答案

▎解题思路

  1. 将质检流程拆分为“抽取 → 分析 → 判定 → 报告”四个阶段，每个阶段可由独立 Agent 或微服务完成。
  2. 采用“规则引擎 + 小模型 + 大模型”三级漏斗，平衡准确率和成本。
  3. 所有判定必须附带证据片段，确保可解释性，并支持人工申诉闭环。

▎详细方案

  • 系统架构
  • 数据接入层：通过 Kafka 实时接收客服系统的话单（文本或语音转写），每日定时批量抽取全量或抽样会话。
  • 质检引擎：核心模块，包含三个子检测器：
    • 违规话术检测器：基于正则 + 关键词字典（如“保证收益”“绝对安全”）做第一层快速过滤；可疑句子送 RoBERTa 文本分类模型（微调后的违规话术识别）进行二次判定。
    • 情绪异常检测器：使用预训练的情感分析模型（如 uer/roberta-base-finetuned-jd-binary-chinese）识别客户负面情绪；结合对话轮次和客服响应时间，计算“愤怒升级指数”。
    • 业务知识检测器：将客服回答与知识库标准答案做语义相似度匹配（使用 Sentence-BERT），若相似度 <0.5 则标记为“疑似答非所问”；对于复杂问题，调用大模型（GPT-4）进行最终判断，并输出错误类型。
  • 报告生成层：汇总检测结果，生成 JSON 格式的质检报告，包含会话 ID、风险等级、违规点、证据片段、建议处理方式。

  • 人工复核界面：前端展示高风险会话，支持质检员打标“误判/属实”，反馈结果回写数据库，用于模型迭代。

  • 数据流
    每日凌晨，定时任务从数据库拉取前一日所有已完成会话 → 送入质检引擎流水线 → 各检测器并行处理 → 结果写入 PostgreSQL → 高风险会话通过 Webhook 推送到企业微信/钉钉群 → 质检员登录后台复核 → 复核结果更新模型训练集。

  • 模型选型

  • 规则引擎：Python re + AC 自动机，处理 80% 的明显违规。
  • 小模型：RoBERTa-base 微调违规分类，部署在 CPU 上，处理模糊案例。

  • 大模型：GPT-4 或 DeepSeek-V2，仅对低置信度案例（小模型得分 0.4~0.6）进行终判，每日调用量控制在 1000 次以内，成本可控。

  • 质检规则引擎设计
    采用“规则组”概念，每个规则组对应一个检测维度，支持热更新。规则由“触发条件 + 判定逻辑 + 风险分”组成。例如：
    yaml rule: name: "承诺收益" pattern: "保证.*收益|年化.*%以上" context_window: 2 # 检查前后2句 score: 90
    规则引擎输出风险分，最终风险等级 = 各维度最高分。

  • 可靠性与可解释性

  • 每个判定必须附带“证据链”：原文片段 + 触发规则 + 模型置信度。
  • 引入“双审机制”：对于高风险会话，同时用大模型和规则引擎独立判定，若结果不一致则升级为“争议”，人工介入。
  • 建立 A/B 测试框架，每次规则或模型更新后，在 5% 流量上试运行，对比人工抽检一致率，稳定后再全量。

▎关键细节 & 踩坑点

  • 语音转写准确率直接影响质检效果，需在转写后增加纠错模块（如基于 BERT 的文本纠错）。
  • 业务知识检测不能仅靠语义相似度，需结合实体抽取（如疾病名称、药品名）进行精确校验。
  • 质检报告中的“风险分”要避免“狼来了”效应，需根据业务容忍度动态调整阈值，并定期校准。

▎可扩展优化

  • 引入多模态能力：对语音对话直接分析语调、语速，辅助情绪判断。
  • 将质检 Agent 平台化，允许业务人员通过拖拽配置新的检测规则，无需编码。
  • 建立“质检知识图谱”，关联违规话术、产品、场景，实现根因分析。
