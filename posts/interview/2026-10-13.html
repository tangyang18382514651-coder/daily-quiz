📌 概念题 · Q1

考点标签

优雅发布 · 难度：⭐⭐⭐

📝 题目

在生产环境部署长耗时 Agent 应用（如文案生成、配图）时，为什么不能直接在发布新版本时 kill 旧进程？基于 FastAPI lifespan 实现的优雅关闭机制核心解决了什么问题？

💡 参考答案

▎一句话结论

直接 kill 进程会导致在途长耗时任务中断、数据丢失，优雅关闭的核心是通过信号捕获+任务计数+阻塞退出，保证在途任务安全落库后再终止进程，实现发布过程零业务损失。

▎核心原理

  • 信号捕获：通过 asynccontextmanager 实现的 lifespan 钩子，捕获平台发送的 SIGTERM 终止信号，而非直接被系统强制杀死
  • 任务计数：全局维护 active_tasks 计数器，请求进入时+1，finally 块中-1，精确统计在途任务量
  • 阻塞等待：收到终止信号后进入循环等待，直到计数器归零，期间不再接收新请求
  • 持久化兜底：等待过程中配合 LangGraph Checkpointer 将任务状态落库，避免内存状态丢失

▎深入解释

我们可以把这个过程类比成餐厅打烊：直接 kill 进程相当于营业时间到了直接把正在吃饭的客人赶出去、把炒到一半的菜倒掉；而优雅关闭相当于门口先挂上“停止接客”的牌子（不再接收新请求），然后等所有桌上的客人吃完结账、后厨所有正在做的菜上完，最后再锁门下班。
对于 Agent 应用来说，生图、长文生成这类任务往往耗时几十秒甚至几分钟，如果发布时直接杀进程，用户等待了半天的结果直接丢失，不仅体验极差，还可能导致已经消耗的大模型 Token 成本白白浪费，甚至出现写了一半的数据库记录造成脏数据。lifespan 是 FastAPI 专门提供的异步生命周期钩子，yield 之前的代码在服务启动时执行（比如初始化 MCP 连接、数据库连接池），yield 之后的代码在服务收到终止信号时执行，天生适合做优雅关闭逻辑。

▎面试加分点

  • 可以补充：实际生产中还要配合 K8s 的 terminationGracePeriodSeconds 参数，给优雅关闭留出足够的等待时间（通常设置为业务最长耗时的1.2倍），避免 K8s 等不及直接发送 SIGKILL 强杀
  • 可以提到：计数器实现时要注意并发安全，Python asyncio 是单线程协程模型，简单场景用全局变量即可，高并发场景下建议用 asyncio.Lock 保护计数器更新，避免竞态条件

▎常见误区

  • 误区1：认为只要配了健康检查就自动有优雅关闭——健康检查是启动时的依赖控制，优雅关闭是终止时的流量排空，两者是发布流程的前后两个环节，缺一不可
  • 误区2：优雅关闭时还要继续接收新请求——正确做法是收到终止信号后立即从注册中心摘流，不再接收新请求，只处理已经进来的在途任务，否则永远等不到计数器归零

📌 概念题 · Q2

考点标签

容器编排 · 难度：⭐⭐⭐

📝 题目

Docker Compose/K8s 部署中，depends_on 默认的启动顺序控制为什么不够用？service_healthy 条件配合 healthcheck 实现的分层发布，核心解决了多服务部署的什么痛点？

💡 参考答案

▎一句话结论

默认 depends_on 只控制容器启动顺序，不关心服务是否真的可用，service_healthy + 健康检查的核心是实现“依赖服务真正就绪后再启动上层服务”的拓扑感知发布，避免上层服务启动时因依赖未就绪而崩溃。

▎核心原理

  • 启动顺序≠就绪顺序：容器进程启动不代表服务已经能提供服务（比如数据库要加载数据、MCP Server 要初始化模型连接）
  • 健康探测：通过 healthcheck 配置周期性探测服务的就绪端点（如 /health），连续多次成功才标记为 healthy
  • 条件依赖：depends_on 配置 condition: service_healthy，只有依赖服务达到 healthy 状态后，才启动当前服务
  • 拓扑分层：按照“底层基础服务→中间件网关→上层业务应用”的依赖拓扑逐层启动，保证每层启动时依赖都已就绪

▎深入解释

这就像盖楼：默认 depends_on 相当于只要施工队到了工地就开始砌墙，不管地基有没有干、钢筋有没有扎好；而 healthcheck + service_healthy 相当于每一道工序完工后都要验收，验收合格了才能开始下一道工序。
在 Agent 集群架构中，底层的 MCP RAG 服务、向量数据库启动往往需要几十秒时间加载模型、建立索引，如果上层的 media-agent-app 按照默认顺序只要容器启动就开始运行，就会出现启动时调用 MCP 接口连接失败、直接抛出异常退出的问题，导致服务反复重启甚至启动失败。更严重的是，如果是滚动发布场景，底层服务还没就绪上层就切流量，会导致一段时间内的用户请求全部报错。通过分层健康检查，我们可以保证每一层服务都是真正“可用”的状态，才会启动上一层、接入流量。

▎面试加分点

  • 可以补充：健康检查端点不能只是简单返回200，应该真正检查核心依赖的可用性（比如数据库连接是否正常、MCP 服务是否能连通、模型是否加载完成），否则会出现“服务进程活着但业务不可用”的假健康状态
  • 可以延伸到 K8s 场景：K8s 中的 livenessProbe（存活探针）、readinessProbe（就绪探针）、startupProbe（启动探针）三者配合，实现更精细的流量控制，readinessProbe 失败会自动把 Pod 从 Service 端点中摘除，不再接收流量

▎常见误区

  • 误区1：健康检查间隔越短越好——过短的检查间隔会给服务带来额外的压力，通常设置为3-5秒即可，配合3次重试，容忍短暂的网络抖动
  • 误区2：所有服务都要同时启动——正确的做法是按照依赖拓扑分层，无依赖的基础服务先启动，有依赖的上层服务后启动，减少启动风暴

📌 概念题 · Q3

考点标签

微服务架构 · 难度：⭐⭐⭐⭐

📝 题目

企业级多 Agent 集群部署时，为什么不推荐做“大仓库+全能总 Agent”架构，反而要采用多仓库独立部署+网关路由的模式？这种架构的核心优势是什么？

💡 参考答案

▎一句话结论

总 Agent 架构会带来单点故障、路由准确率低、迭代耦合的问题，多仓库独立部署+网关路由的核心是实现业务隔离、独立发布、平级协作，把大模型的不确定性限制在单个业务域内，避免全局故障。

▎核心原理

  • 仓库拆分：底层公共 MCP 服务（LLM调用、RAG、记忆、Prompt管理）作为基础仓库独立部署，上层业务 Agent（客服、自媒体、HR）各自独立仓库、独立发布
  • 网关路由：所有外部请求统一打到高性能网关，通过URL路径、API Key等确定性规则做流量分发，不依赖大模型做路由
  • 平级协作：Agent之间是平等的邻居关系，需要联动时直接通过网关互相调用，不需要总Agent中转
  • 数据共享：通过底层共享的数据库、MCP记忆层实现跨Agent数据互通，不需要上层Agent传话

▎深入解释

总Agent架构就像一个公司里所有事情都要经过CEO审批：CEO一旦请假，整个公司瘫痪；CEO每天要处理成百上千个不同类型的请求，很容易判断错误把事情派错部门；而且任何一个部门改流程，都要CEO重新学习规则，迭代效率极低。
而多仓库+网关架构就像现代企业的部门制：前台（网关）根据访客要办的事情，直接指引到对应部门，不需要CEO出面；每个部门（业务Agent）独立办公、独立调整流程，某个部门装修（发布新版本）不影响其他部门正常办公；部门之间需要协作时直接对接（比如客服需要生成文案直接找自媒体部门），不需要走CEO审批；所有部门共享公司的公共资源（会议室、数据库、MCP服务）。更重要的是，网关是纯代码实现的确定性路由，准确率100%，延迟毫秒级，不会像大模型路由那样出现幻觉、把请求分错业务域。

▎面试加分点

  • 可以补充：这种架构完全契合微服务的“康威定律”——团队结构对应系统结构，负责客服的团队可以独立迭代客服Agent仓库，负责自媒体的团队独立迭代自媒体仓库，不需要跨团队协调代码合并，开发效率极高
  • 可以提到：新业务接入时只需要新建一个独立仓库写业务编排逻辑，直接复用底层已经稳定的MCP公共服务，上线周期从周级缩短到天级

▎常见误区

  • 误区1：认为多Agent就必须有一个总控Agent做调度——生产环境中高并发流量分发必须用确定性的网关做，大模型只适合处理业务域内部的复杂逻辑，不适合做高并发的流量入口
  • 误区2：独立部署会导致重复造轮子——底层公共能力全部抽成MCP服务共享，上层业务只写自己的编排逻辑，不存在重复开发的问题

📌 概念题 · Q4

考点标签

长任务设计 · 难度：⭐⭐⭐⭐

📝 题目

普通的一问一答Agent无法处理员工入职、跨部门审批这类需要跨越数天、等待人工介入的长周期业务，这类Long-running Agent的核心设计原则是什么？技术上如何实现中断与唤醒？

💡 参考答案

▎一句话结论

长周期Agent的核心设计原则是“不能常驻内存，必须状态持久化，具备中断唤醒机制”，通过状态序列化、中断信号、Webhook回调三个核心组件，实现跨天级任务的休眠与无缝续跑。

▎核心原理

  • 状态序列化：每执行完一个步骤，就通过Checkpointer将当前完整的状态机数据、上下文、局部变量序列化为JSON存入数据库，随即释放计算资源
  • 两阶段中断：当执行到需要人工介入的节点时（如总监审批），调用外部系统创建任务并生成唯一Task_ID，同时向状态机抛出Interrupt信号，强制挂起当前会话
  • 异步唤醒：外部操作完成后（如总监点击同意），业务系统通过Webhook携带Task_ID和结果回调Agent服务，服务从数据库反序列化状态，将结果作为输入注入状态机，无缝继续执行后续步骤

▎深入解释

这就像我们平时办护照：你不需要一直在办事大厅站着等审批，工作人员会先把你的材料收走（状态持久化），告诉你“回家等通知，审批过了会发短信给你”（中断挂起，释放窗口资源）；等领导审批完成后，系统发短信给你（Webhook回调），你带着身份证过来继续办后续的贴签流程（唤醒续跑）。如果让你一直在窗口站着等几天，不仅你累（占着内存资源），窗口也没法给其他人办业务（资源无法复用，并发上不去）。
对于长周期业务来说，如果让Agent常驻内存等待人工操作，一个Pod同时最多只能处理几十个任务，并发能力极差，而且一旦Pod重启，所有等待中的任务状态全部丢失。通过持久化+中断唤醒的模式，任务等待时完全不占用计算资源，一个Pod可以支撑上万并发的长周期任务，即使服务重启也能从数据库恢复状态继续执行。

▎面试加分点

  • 可以补充：LangGraph原生支持Interrupt机制和PostgreSQL Checkpointer，不需要自己手写状态持久化逻辑，配合Webhook端点可以快速实现长周期工作流，这也是LangGraph相比其他Agent框架在企业级场景下的核心优势
  • 可以提到：状态持久化时要注意版本兼容，状态结构变更时要做迁移，避免旧版本的状态反序列化失败

▎常见误区

  • 误区1：用定时任务轮询数据库检查审批状态——轮询会给数据库带来不必要的压力，而且实时性差，Webhook回调是事件驱动的，既省资源又实时
  • 误区2：唤醒时重新创建一个新的Agent实例——正确做法是根据Task_ID恢复原来的状态，而不是重新跑一遍整个流程，否则会重复执行之前已经完成的步骤（比如重复发送审批通知）

📌 概念题 · Q5

考点标签

成本优化 · 难度：⭐⭐⭐

📝 题目

随着对话轮数增加，Agent的上下文越来越长，导致Token成本飙升、响应变慢，工业界常用的分层内存+前缀缓存优化策略，核心原理是什么？为什么能大幅降低成本和延迟？

💡 参考答案

▎一句话结论

核心是通过“近期记忆精确保留、长期记忆摘要压缩”的分层策略减少输入Token长度，同时通过固定Prompt前缀触发模型KV缓存，在不损失效果的前提下将TTFT（首字延迟）降低70%以上、成本降低40%。

▎核心原理

  • 分层内存管理：不把所有历史对话无脑塞给模型，近期N轮对话保留原始精确内容存入短期记忆，更早的对话通过异步摘要Agent压缩成精简的用户画像/事实存入长期记忆
  • 前缀缓存触发：大模型推理是自回归的，相同的前缀部分可以复用之前计算好的KV Cache，不需要重复计算
  • 前缀一致性保证：通过固定System Prompt结构、固定RAG检索结果排序、合并固定Few-Shot示例，确保每个请求的开头部分Token完全一致，最大化缓存命中率
  • 异步摘要：摘要压缩操作在后台异步执行，不阻塞用户的正常请求，不影响响应速度

▎深入解释

我们可以把大模型的上下文窗口比作学生考试带的资料：如果把从小学到大学所有的课本全部带去考场（全量历史对话），不仅找答案慢（上下文长导致推理慢），带资料的成本也很高（Token成本高）；分层记忆就像只带最近几节课的笔记（近期记忆），加上之前整理的精简知识点手册（长期记忆摘要），既不影响答题，又轻便快速。
而前缀缓存就像考试的填空题，前面的题干都是固定的，你之前已经做过一遍题干的阅读理解了（计算过KV Cache），下次遇到同样的题干，直接看后面的空就行，不需要重新读一遍题干。大模型推理中，前缀部分的计算往往占了总耗时的60%以上，如果能复用这部分计算，首字延迟会有量级的下降，同时云厂商对于命中KV Cache的Token通常会打5-8折，直接降低推理成本。

▎面试加分点

  • 可以补充：实际落地中前缀缓存的命中率通常能做到80%以上，配合Rerank固定排序策略，不仅能触发缓存，还能提升检索结果的稳定性
  • 可以提到：分层记忆的N轮阈值不是固定的，可以根据业务场景调整，比如客服场景保留最近5轮，写作场景保留最近10轮，摘要时要用专门的小模型做，不要用旗舰模型，进一步降低成本

▎常见误区

  • 误区1：上下文窗口越大越好，把所有历史都塞进去效果最好——过长的上下文会导致大模型“注意力遗忘”，中间的信息召回率反而下降，摘要后的核心事实比全量杂乱对话效果更好
  • 误区2：前缀缓存是自动触发的，不需要特意处理——只要前缀有一个Token不一样（比如RAG结果顺序变了、加了随机的时间戳），缓存就会失效，必须刻意保证前缀的严格一致性

📌 概念题 · Q6

考点标签

可观测性 · 难度：⭐⭐⭐

📝 题目

大模型应用开发中，为什么传统的单元测试+人工测试无法满足Agent系统的质量保障需求？LLM-as-a-Judge+全链路Trace的自动化评测体系核心解决了什么问题？

💡 参考答案

▎一句话结论

传统测试无法应对Agent输出的非确定性、多步骤链路的复杂性，自动化评测体系的核心是实现每次代码变更的可量化、可复现、可对比的质量评估，避免“改完Prompt不知道系统变聪明还是变笨”的问题。

▎核心原理

  • 非确定性输出：Agent的输出是概率性的，同样的输入可能有不同的输出，传统断言式单元测试无法直接判断对错
  • 全链路Trace：通过LangSmith、Phoenix等工具记录Agent执行的完整链路，包括每一次Prompt、RAG召回的Chunk、Tool调用参数、Token消耗、延迟，出问题时可以快速定位
  • LLM-as-a-Judge：用能力更强的大模型作为裁判，基于Groundedness（无幻觉）、Faithfulness（忠实于上下文）、Relevance（相关性）等标准化指标，自动给输出打分
  • CI/CD集成：每次代码提交自动跑几百个基准测试用例，分数低于阈值就阻断发布，把大模型测试融入传统软件工程流程

▎深入解释

传统软件测试就像考数学题，答案是固定的，1+1必须等于2，用assert就能判断对错；而Agent测试就像考作文，没有唯一标准答案，你不能用简单的相等断言判断一篇作文写得好不好，而且作文是分步骤写的（审题→列提纲→写正文→检查），如果最后写跑题了，你得知道是哪一步出了问题。
如果靠人工测试，每次改完Prompt找几个人试一下，不仅效率低、成本高，而且主观判断差异很大，这次觉得好下次觉得不好，根本无法量化迭代。全链路Trace相当于给Agent装了“行车记录仪”，出了事故可以回溯整个过程看是哪一步走错了；LLM-as-a-Judge相当于请了一个稳定的阅卷老师，按照统一的评分标准给每篇作文打分，每次改完代码都跑一遍全套试卷，分数提高了就发布，分数降低了就回滚，彻底摆脱“靠感觉调Prompt”的草莽阶段。

▎面试加分点

  • 可以补充：LLM-as-a-Judge要注意裁判模型的偏见，通常会用比业务模型能力更强的模型作为裁判，同时配合少量人工标注的黄金测试集做校准，避免裁判模型自己有幻觉
  • 可以提到：Trace数据不仅用来排错，还可以用来挖掘 bad case，作为后续微调、Prompt优化的数据集，形成数据飞轮

▎常见误区

  • 误区1：LLM-as-a-Judge可以完全替代人工评估——自动化评测用来做回归测试、快速迭代，上线前还是需要少量人工抽检做最终确认
  • 误区2：只测最终输出，不看中间链路——很多时候最终输出错了，是因为RAG召回的Chunk不对，或者Tool调用参数错了，只看输出根本无法定位问题，必须全链路追踪

📌 概念题 · Q7

考点标签

异常容错 · 难度：⭐⭐⭐⭐

📝 题目

带自我反思（Self-Correction）机制的Agent很容易陷入死循环，疯狂消耗Token甚至把服务卡死，LangGraph工程落地中的三层防死循环兜底机制分别是什么？

💡 参考答案

▎一句话结论

三层兜底分别是“计数器硬上限切断、动态Prompt语义打破、节点级精准回滚”，从强制熔断、语义引导、故障恢复三个维度，彻底避免Agent陷入无限重试的死循环。

▎核心原理

  • 显式计数器硬上限：在LangGraph全局State中维护loop_count变量，每次进入反思/重试节点时+1，达到3-5次硬上限就强行切断循环，走向降级路由
  • 动态Prompt语义注入：随着重试次数增加，在Prompt中动态追加之前的失败原因，提示模型换思路，从语义层面打破“复读机”效应
  • 节点级精准回滚：利用Checkpointer的状态历史，找到故障节点之前的正确检查点，通过update_state重新定向执行路径，实现单节点级别的增量重试，不需要从头跑整个流程

▎深入解释

Agent的死循环就像人走迷宫，一直沿着同一条错路走，反复撞墙但不知道换方向。第一层兜底就像给人设定一个“撞墙5次就必须停下来”的硬规则，到点就强制退出，避免一直撞墙消耗体力（Token）；第二层兜底就像每次撞墙都在墙上贴个纸条“这条路刚才走过，是死路，换个方向”，引导人主动换思路，而不是机械重试；第三层兜底就像发现走错路了，不需要回到迷宫入口重新走，直接退回到上一个岔路口（故障前的检查点），换一条路走，节省时间。
很多开发者做自我反思只加了一个简单的重试逻辑，没有任何兜底，结果线上一旦遇到模型处理不了的问题，就会无限循环调用大模型，几个小时就能烧掉几千块的Token费用，甚至把服务的异步队列堵死，影响所有正常请求。三层兜底机制是Agent生产级落地的必备稳定性保障。

▎面试加分点

  • 可以补充：硬上限的阈值要根据业务场景设置，比如普通问答设3次，复杂的代码生成可以设5次，达到阈值后不要直接返回错误，应该降级到“转人工”或者“返回之前生成的最优结果+失败提示”的友好分支
  • 可以提到：节点级回滚是LangGraph独有的Time-travel能力，相比其他框架只能从头重试，这种单节点重试可以节省80%以上的重试Token成本

▎常见误区

  • 误区1：只靠Prompt告诉模型“不要重复自己”就能避免死循环——大模型的非确定性决定了仅靠语义约束是不可靠的，必须有代码层面的硬熔断作为最后一道防线
  • 误区2：重试次数越多效果越好——超过3次重试后，模型的输出质量提升边际效益极低，反而会大幅增加成本和延迟，硬上限是必须的工程兜底

📌 概念题 · Q8

考点标签

架构设计 · 难度：⭐⭐⭐⭐

📝 题目

企业级Agent落地中，为什么说“微调管风格，RAG管知识”是职责分离的最佳实践？两者的边界是什么？混为一谈会带来什么问题？

💡 参考答案

▎一句话结论

微调的核心作用是改变模型的行为范式（输出风格、格式、话术习惯），RAG的核心作用是注入动态更新的外部知识，两者职责清晰、不可替代，混为一谈会导致知识更新成本极高、模型迭代缓慢。

▎核心原理

  • 微调（SFT+DPO）：通过少量高质量标注数据，训练模型学会特定领域的说话风格、严格的JSON输出格式、特定的思考路径，解决“会说但说不好”的问题
  • RAG Pipeline：通过Embedding召回+Rerank精排的三阶段流程，在推理时动态注入外部知识库内容，解决“不知道最新/内部知识”的问题
  • 边界划分：凡是需要频繁更新、会动态变化的内容（如公司规章制度、产品价格、最新政策），绝对不能放进微调数据，必须走RAG；凡是稳定的、属于模型行为模式的内容（如客服话术风格、固定输出格式），用微调固化
  • 协同效应：微调让模型更懂怎么用RAG召回的知识，RAG给模型提供准确的事实依据，两者配合才能达到最优效果

▎深入解释

这就像培训一个客服员工：微调相当于给员工做服务礼仪培训，教他怎么说话、怎么按照规范格式回复、遇到投诉怎么安抚情绪，这些是员工的行为习惯，一旦学会不需要经常变；而RAG相当于给员工一本实时更新的产品手册，遇到用户问具体的产品参数、最新的活动规则，就翻手册找答案，不需要把整本手册背下来。
如果把知识放进微调里，就像让员工把所有产品知识全部背下来，一旦产品价格变了、出了新产品，就要重新培训员工（重新微调模型），不仅成本高、周期长，而且员工很容易记混旧知识和新知识，出现幻觉；如果把风格放进RAG里，就像把服务礼仪规范也放进产品手册里，员工每次回复都要翻手册找话术，不仅响应慢，而且风格不稳定，有时候礼貌有时候生硬。

▎面试加分点

  • 可以补充：DPO（直接偏好优化）阶段不需要大量标注数据，只要标注几百条chosen/rejected的偏好对，就能让模型的风格一致性评分提升50%以上，ROI极高
  • 可以提到：RAG Pipeline中引入Cross-Encoder Rerank是非常有必要的，双编码器召回的top20结果里有很多语义相近但不相关的内容，Rerank可以把真正相关的内容排到前面，将知识命中率从70%左右提升到90%以上

▎常见误区

  • 误区1：微调可以让模型记住企业内部知识——微调只能让模型学会模式，记不住大量细粒度的事实知识，而且会出现灾难性遗忘，记住新知识忘记旧知识
  • 误区2：有了RAG就不需要微调——通用模型即使拿到了RAG召回的知识，也可能用很生硬的语气回复，或者输出格式不符合要求，必须用少量微调对齐行为模式

📌 概念题 · Q9

考点标签

安全风控 · 难度：⭐⭐⭐⭐

📝 题目

Agent系统经常需要调用外部工具、对接企业内部系统，为什么说“读写分离+人工审批”是高危工具调用的必备风控机制？网关层的中间件链如何实现全链路安全防护？

💡 参考答案

▎一句话结论

Agent的非确定性决定了它可能错误调用高危写操作工具，读写分离+人工审批的核心是把危险操作的最终决策权交还给人，网关四层中间件链从认证、限流、风控、路由四个层面构建纵深防御，避免Agent造成不可逆的业务损失。

▎核心原理

  • 读写分离：将工具分为读操作（查询知识库、查询数据）和写操作（发微博、删数据、提交审批、付款），读操作可以让Agent自动执行，写操作必须经过人工确认
  • 中断审批流：Agent调用高危写工具时，不直接执行，而是在网关层挂起请求，生成审批单推送给业务人员，确认后才真正下发API调用
  • 四层中间件链：基于FastAPI构建的中间件链，第一层做API Key身份认证，第二层做全链路日志记录，第三层做Token配额限流，第四层做路由转发
  • 纵深防御：除了网关层防护，还有输入输出层的敏感词过滤、NER脱敏、AES加密存储，以及下游服务的熔断降级，多层防护避免单点失效

▎深入解释

这就像银行的大额转账机制：你可以自己在ATM上查余额（读操作，自动执行），但如果要转100万（高危写操作），必须经过人脸识别、短信验证，甚至人工审核，不能直接转。Agent本质上是一个可能出错的“实习生”，你不能让实习生直接给客户发正式公告、直接删除数据库数据，他写好的文案必须经过运营审核才能发，他提交的删除申请必须经过管理员确认才能执行。
很多Demo级别的Agent系统为了方便，让Agent直接持有高权限API Key，可以随便调用所有工具，一旦出现Prompt注入攻击，或者模型幻觉调用错了删除接口，就会造成不可逆的重大生产事故。网关中间件链就像公司的前台+保安+行政，所有进出的请求都要经过检查，没有通行证的不让进，额度超了的不让用，危险操作必须领导签字，从架构层面把风险锁死。

▎面试加分点

  • 可以补充：熔断器模式是下游保护的必备机制，当连续调用大模型失败或者触发429限流超过阈值时，熔断器自动打开，切换为降级模板响应，避免雪崩效应，等服务恢复后再半开探测，逐步恢复流量
  • 可以提到：多租户场景下，通过project_id实现知识库物理隔离，即使某个租户的Agent被注入攻击，也绝对访问不到其他租户的数据，符合等保合规要求

▎常见误区

  • 误区1：靠Prompt告诉Agent“不要调用危险工具”就能保证安全——Prompt是可以被注入绕过的，安全机制必须在代码层、网关层实现，不能依赖大模型的自觉性
  • 误区2：只要加了敏感词过滤就安全了——敏感词过滤只能防住明显的违规内容，对于逻辑层面的错误调用（比如给错误的用户发消息、删错数据）是无效的，必须有审批流兜底

📌 概念题 · Q10

考点标签

技术演进 · 难度：⭐⭐⭐

📝 题目

企业级垂直领域Agent落地，正在经历从“LLM中心化”向“工程架构系统化”的范式转变，这个转变的核心是什么？为什么说未来的核心竞争力是传统后端工程能力，而不是Prompt技巧？

💡 参考答案

▎一句话结论

核心转变是从“靠Prompt和大模型能力解决所有问题”，转向“用确定性的软件工程体系驯服大模型的非确定性”，未来的壁垒是稳定的工程架构、完善的数据体系、完备的可观测性，而不是花里胡哨的Prompt技巧。

▎核心原理

  • 技术栈四个维度演进：数据检索从纯向量RAG转向GraphRAG+确定性解析；流程控制从重框架转向轻量状态机+多Agent协同；模型选用从迷信超大模型转向大小模型协同+PEFT微调；运维从人工盲测转向自动化评测+全链路观测
  • 确定性包裹非确定性：把大模型看作一个有概率出错的“不确定性CPU”，用状态机严格限制它的跳转路径，用熔断器控制它的错误范围，用Harness测试保证它的输出质量，用可观测性排查它的故障
  • 工程能力是壁垒：Prompt技巧是公开的、容易复制的，而稳定的分布式架构、高质量的领域数据集、经过生产验证的容错机制、完善的评测体系，是需要长期踩坑积累的，无法被快速复制
  • 落地核心矛盾：企业级场景的核心要求是高准确率、低容错率、数据合规、成本可控，这些都不是靠写好Prompt就能解决的，必须靠扎实的工程架构实现

▎深入解释

早期的大模型应用就像民间手工作坊，靠师傅（Prompt工程师）的个人经验写Prompt，做出一个能跑的Demo很容易，但要做到99.9%的可用性、支撑上万并发、成本可控、符合合规要求，就必须从手工作坊升级成工业化大生产。工业化大生产靠的不是某个师傅的手艺好，而是标准化的流水线、严格的质量检测流程、完善的安全规范、自动化的生产设备。
很多刚入行的开发者沉迷于研究各种新奇的Prompt技巧、追各种新出的开源框架，却忽视了传统后端的基本功——异常处理、并发控制、资源管理、监控告警、容灾备份，这些才是能把Agent从Demo变成真正能赚钱的生产系统的核心。就像早期的互联网行业，会写HTML就能做网站，但真正能支撑亿级用户的互联网公司，靠的是扎实的分布式系统架构能力，而不是前端页面写得好看。

▎面试加分点

  • 可以抛出终面格局金句：大模型本身只是一个脆弱的、具有非确定性的算力引擎，我们搭建的分布式架构，本质上是在用确定性的软件工程代码（分布式状态机、消息总线、熔断器、零信任网关），去包裹和驯服大模型的非确定性。只有把状态管住、把通道理顺、把资源控死，Agent集群才能真正具备工业级的商业变现能力。
  • 可以补充：大小模型协同是未来的必然趋势，70%的简单任务（路由、分类、摘要）交给小模型处理，只有30%的复杂推理任务交给旗舰大模型，能在保证效果的前提下降低60%以上的推理成本

▎常见误区

  • 误区1：追求完全自主的纯Agent，认为工作流是过时的——工业界的主流是Agentic Workflow，用确定性的工作流框住下限，在需要创造力的节点用Agent提升上限，完全自主的Agent在生产环境中是不可控的
  • 误区2：一味追求最新的大模型、最新的框架——生产环境中稳定永远是第一位的，模型和框架只是工具，能解决业务问题、稳定运行、成本可控才是核心

二、应用题（5 道 · 分类型）

🛠 应用题 · Q1 · 架构设计

题型

架构设计

场景标签

分布式Agent集群 流量网关 多仓库部署

📝 题目

你所在的团队初期为了快速验证业务，把HR智能客服、自媒体内容生成两个Agent系统全部写在同一个Python仓库里，随着业务扩张又要新增建材报价Agent、合同审核Agent，现在出现了严重的问题：改自媒体的配图逻辑导致客服系统发布故障、某一个Agent刷爆Token拖垮整个服务、新团队接入需要理解全量几万行代码。请你设计一套无单点风险的分布式Agent集群架构，要求做到业务完全隔离、发布互不影响、没有“总Agent”单点瓶颈，并说明流量接入、服务拆分、仓库划分的具体方案。

💡 参考答案

▎解题思路

  1. 第一步：先破除“总Agent做路由”的反模式，把流量分发逻辑从大模型推理层下沉到确定性的网关层，避免大模型路由错误和单点故障。
  2. 第二步：按照“公共底座+业务独立”的边界拆分服务，把可复用的通用能力抽成共享MCP服务层，业务逻辑完全独立部署。
  3. 第三步：按照服务边界拆分代码仓库，配合容器编排的健康检查依赖实现分层发布，从流程上避免跨业务的发布影响。
  4. 第四步：设计平级协作机制，解决Agent之间需要联动、数据互通的需求，不需要经过中央节点转发。

▎详细方案

整体架构分为四层，从下到上依次是：
1. 基础设施层：独立部署4个公共MCP服务，分别是LLM统一调用服务、RAG检索服务、会话记忆服务、Prompt管理服务，这一层作为集群底座单独发布，不包含任何业务逻辑，所有业务Agent通过内网HTTP接口调用这些公共能力，避免每个业务重复造轮子。
2. 统一网关层：基于FastAPI构建高性能无状态网关，完全用代码实现确定性路由，不接入任何大模型推理逻辑：网关根据请求URL路径做转发——/api/v1/hr-customer/*转发到HR客服服务、/api/v1/media-ops/*转发到自媒体服务、/api/v1/quote/*转发到建材报价服务；同时在网关层集成四层中间件链：API Key身份认证、请求日志埋点、租户级Token配额限流、路由转发，从入口层就拦截异常流量，避免单个Agent的流量问题扩散到全集群。
3. 业务服务层：每个业务Agent作为独立的服务单元单独部署：HR客服、自媒体、建材报价、合同审核各自打包为独立的Docker镜像，分配独立的CPU/内存资源配额，单个服务的进程崩溃、死循环刷Token都不会影响其他服务。
4. 数据共享层：所有业务共享同一个PostgreSQL实例存储用户画像、Checkpointer状态，通过project_id字段做逻辑隔离，Agent之间需要联动时直接平级调用接口（比如客服需要生成文案直接调自媒体Agent的HTTP接口），不需要经过网关或中央节点转发。

仓库划分严格对应服务边界：
- 仓库1：MCP公共服务底座仓库，由基础架构团队维护；
- 仓库2：API网关仓库，由后端架构团队维护；
- 仓库3~N：每个业务Agent对应一个独立Git仓库，由各自的业务团队维护，新业务接入只需要新建仓库写LangGraph编排逻辑，不需要修改其他服务的代码。

发布流程配合Docker Compose/K8s的健康检查机制实现分层拓扑发布：先启动MCP底座服务，健康检查通过后再启动网关，网关健康检查通过后最后逐个启动业务Agent服务，从启动顺序上避免依赖未就绪导致的启动故障。

▎关键细节 & 踩坑点

  • 绝对不要用大模型做网关层的路由分发：大模型路由存在固有准确率误差，一旦路由错误会导致请求发错服务，而且大模型推理本身会增加几百毫秒到几秒的延迟，高并发场景下网关会成为性能瓶颈；
  • 业务服务必须配置独立的资源配额（CPU、内存、最大并发数、Token调用额度），如果所有服务共享资源池，一旦某个Agent出现死循环疯狂调用大模型，会把整个集群的LLM配额打满，导致所有业务不可用；
  • 仓库拆分时要避免循环依赖：公共MCP层绝对不能依赖上层业务服务，业务服务之间的调用只允许通过公开的HTTP接口，不允许直接导入其他业务仓库的代码，否则时间长了又会变回大泥球架构。

▎可扩展优化

  • 网关层可以进一步接入Nginx做负载均衡，单个业务Agent可以水平扩容多个实例支撑更高并发；
  • 可以在网关层增加统一的熔断降级逻辑，当某个下游业务服务连续失败超过阈值时，自动返回预设的降级响应，避免故障扩散；
  • 跨Agent调用可以引入轻量的消息队列做异步解耦，比如客服需要生成文案的场景，不需要同步等待自媒体Agent返回，可以先给用户返回“正在生成中”，等生成完成后再通过消息推送通知用户。

场景标签

长周期业务 Human-in-the-Loop 状态持久化

📝 题目

你负责开发企业内部的员工入职自动化Agent系统，整个流程需要跨越3~5天：员工提交身份证、学历证信息→系统自动做信息核验→发送入职材料给员工填写→等待部门总监审批→审批通过后自动生成电子劳动合同→触发IT部门开通账号权限。其中“等待总监审批”环节可能需要几个小时到几天不等，不可能让HTTP请求一直挂着等待。请你设计这套长周期Agent的技术实现方案，说明如何做到进程不常驻内存、支持人工中断介入、审批完成后能无缝唤醒继续执行。

💡 参考答案

▎解题思路

  1. 第一步：明确长周期Agent的核心设计原则——绝对不能让进程常驻内存等待，否则会占用大量服务器资源，且服务器重启就会丢失所有在途任务状态；
  2. 第二步：基于状态持久化机制，每执行完一个步骤就把完整状态序列化存入数据库，释放计算资源；
  3. 第三步：在需要人工介入的节点设计明确的中断信号，把任务挂起，同时和外部OA系统打通生成待办任务；
  4. 第四步：通过Webhook回调机制实现异步唤醒，根据任务ID反序列化状态，让Agent从断点继续执行，不需要从头开始。

▎详细方案

整个方案基于LangGraph + PostgreSQL Checkpointer + FastAPI实现，分为四个核心模块：
1. 状态自动持久化模块：给LangGraph工作流配置PostgreSQL Checkpointer，Agent每完成一个节点的执行（比如身份证信息核验完成、入职材料发送完成），Checkpointer会自动把当前的全局状态（员工提交的信息、已完成的步骤、中间变量、对话历史）序列化为JSON，连同唯一的thread_id（对应每个员工的入职流程ID）存入PostgreSQL数据库，随后当前执行流程直接结束，释放Pod的CPU和内存资源，不需要在内存里保留任何会话上下文。
2. 人工节点中断模块：当流程执行到“总监审批”节点时，节点逻辑首先调用OA系统的API创建审批单，传入员工信息和流程ID，生成唯一的task_id；随后节点向LangGraph抛出Interrupt中断信号，强制挂起当前流程，此时整个流程进入休眠状态，不占用任何计算资源。
3. Webhook异步唤醒模块：在OA系统侧配置回调规则，当总监在OA页面点击“同意”或“驳回”时，OA系统会向FastAPI服务发送一个POST Webhook请求，请求中携带task_id、审批结果、审批意见。FastAPI收到请求后，首先根据task_id映射到对应的thread_id，然后从PostgreSQL中读取该流程的序列化状态，反序列化为LangGraph的State对象，把审批结果作为外部事件输入注入到状态中。
4. 断点续跑模块：调用LangGraph的graph.invoke(None, config={"configurable": {"thread_id": thread_id}})方法，框架会自动从中断的“总监审批”节点之后继续执行后续流程：如果审批通过就生成电子合同、调用IT系统开通账号；如果审批驳回就给员工发送驳回通知、告知需要补充的材料。

整个过程中，等待审批的几个小时/几天里，服务器上没有任何和这个流程相关的进程在运行，所有状态都存在数据库里，即使服务器重启、发布新版本也不会丢失任务。

▎关键细节 & 踩坑点

  • 不要用Redis做长周期任务的状态存储：Redis默认有过期时间，且如果配置了内存淘汰策略，可能会把未完成的流程状态删掉，导致任务永远无法唤醒，长周期状态必须存在持久化的关系型数据库里；
  • 设计中断节点时一定要设置超时机制：如果提交审批后7天总监没有处理，要自动触发提醒逻辑，或者自动走默认审批流程，避免流程永远挂起；
  • 唤醒时一定要做幂等校验：比如生成劳动合同、开通账号这类写操作，要记录操作状态，如果因为网络重复回调导致Webhook被调用两次，不能重复给员工开通两个账号、生成两份合同。

▎可扩展优化

  • 可以给每个节点增加超时重试和告警机制，如果某个外部系统（比如OA、IT账号系统）调用失败，自动重试3次，还是失败就发告警给运维人员；
  • 可以在流程中增加状态查询接口，员工和HR可以随时在前端查看当前入职流程走到了哪一步、卡在哪个节点，不需要找人工询问；
  • 可以把不同的审批流程抽象为可配置的规则，不同部门的入职流程可以配置不同的审批节点，不需要修改代码。

场景标签

优雅关闭 在途任务保护 服务发布

📝 题目

你负责的自媒体内容生成Agent服务，单个“选题→写作→配图”的完整流程需要10~30秒时间，最近运维团队反馈每次发布新版本时，都会有一批用户的生成请求被强制中断，生成到一半的文案和配图直接丢失，用户投诉率很高。请你基于FastAPI和Docker编排实现一套完整的无损发布方案，要求发布新版本时不会中断正在执行的生成任务，且不会把流量转发给还没启动完成的服务实例。请写出核心实现逻辑和关键配置。

💡 参考答案

▎解题思路

  1. 第一步：在应用层捕获操作系统的SIGTERM终止信号，实现优雅关闭逻辑：收到信号后首先停止接收新请求，然后等待所有在途任务执行完成并持久化后再退出进程；
  2. 第二步：实现可靠的健康检查端点，让编排系统能够准确判断服务是否已经启动完成、是否准备好接收流量；
  3. 第三步：在容器编排层配置依赖拓扑和滚动发布策略，确保新实例健康检查通过后再接入流量，旧实例收到终止信号后等待足够长的时间让在途任务完成再被杀死。

▎详细方案

整个方案分为应用层和编排层两部分实现：
1. 应用层优雅关闭逻辑（基于FastAPI lifespan实现）：
首先定义全局的active_tasks原子计数器，每个请求进来时在finally块中保证计数器+1和-1；然后实现异步上下文管理器的lifespan函数：
- 启动阶段：初始化MCP连接、数据库连接池、LangGraph Agent实例，初始化完成后把服务状态标记为“就绪”；
- 运行阶段：正常处理API请求；
- 收到SIGTERM信号阶段：首先把服务状态标记为“未就绪”，让健康检查端点返回503，通知负载均衡不要再把新流量转发过来；然后进入循环检查active_tasks计数器，每隔1秒打印一次当前在途任务数，直到计数器归0，确认所有任务都已经完成且结果已经通过Checkpointer持久化到数据库后，再关闭数据库连接、MCP连接，最后退出进程。
同时实现/health健康检查端点：服务就绪时返回200，正在关闭时返回503，供编排系统探测。
核心伪代码逻辑：
python active_tasks = 0 is_ready = False @asynccontextmanager async def lifespan(app: FastAPI): global is_ready # 启动初始化 await init_mcp_connection() await init_db_pool() is_ready = True yield # 收到终止信号 is_ready = False while active_tasks > 0: await asyncio.sleep(1) await close_db_pool() @app.get("/health") async def health_check(): return 200 if is_ready else 503 @app.post("/generate/media") async def generate_media(): global active_tasks active_tasks +=1 try: return await media_agent.run() finally: active_tasks -=1
2. 编排层配置（以Docker Compose/K8s为例）：
- 配置分层依赖：MCP服务启动后配置healthcheck探测/health端点，间隔5秒检查一次，连续3次成功才标记为healthy；API网关依赖MCP服务的service_healthy条件才启动；业务Agent服务依赖网关的healthy条件才启动，从启动顺序上避免依赖未就绪导致的请求失败；
- 配置滚动发布策略：启动新实例时，等到新实例的健康检查连续3次返回200后，再把流量切到新实例；给旧实例配置termination_grace_period_seconds: 60，也就是收到SIGTERM后最多等60秒让进程优雅退出，超过60秒再强制杀死；
- 配置停止信号：确保Docker给进程发送的是SIGTERM而不是SIGKILL，否则FastAPI捕获不到终止信号，会直接被强制退出。

▎关键细节 & 踩坑点

  • 计数器一定要在finally块里做减1操作，否则如果任务执行过程中抛出异常，计数器永远不会归0，进程会一直卡在关闭阶段，最后被强制杀死，还是会丢任务；
  • 一定要设置优雅关闭的最大等待时间（比如60秒），不能无限等待，如果某个任务因为大模型API卡住超过1分钟，还是要强制退出，否则发布流程会永远卡住；
  • 健康检查不要只检查进程是否存活，一定要检查依赖的数据库、MCP服务是否连接正常，否则服务进程启动了但依赖没通，流量打过来还是会报错。

▎可扩展优化

  • 可以把在途任务的状态实时持久化到Checkpointer，如果等待超过最大时间进程被强制杀死，下次启动时可以自动恢复未完成的任务，继续执行剩下的步骤；
  • 可以在关闭阶段给已经接收到的请求返回“正在发布，请稍后查询结果”的响应，用户可以通过任务ID查询生成结果，不需要重新提交请求；
  • K8s环境下可以配置preStop钩子，在发送SIGTERM之前先休眠2秒，等待Kube-proxy把流量规则更新完，避免终止信号发出去了还有新的请求转发过来。

🛠 应用题 · Q4 · 排障优化题

题型

排障优化

场景标签

成本优化 TTFT延迟 前缀缓存

📝 题目

你负责的HR智能客服系统上线后，运维监控发现两个严重问题：① 随着用户对话轮数增加，平均响应延迟（TTFT）从最初的2秒上升到15秒，单请求Token成本增加了3倍；② 即使是相同的常见问题（比如“入职需要准备什么材料”），每次请求的首字延迟也很高，完全没有命中大模型厂商的KV缓存。请你分析问题原因，并给出具体的优化方案，要求把TTFT降回2秒以内，同时降低Token成本。

💡 参考答案

▎解题思路

  1. 第一步：先定位延迟和成本上升的根因：最常见的原因是没有做记忆分层，把所有历史对话无脑全量塞进上下文，导致上下文越来越长，不仅Token成本线性增加，推理速度也会越来越慢；
  2. 第二步：定位缓存未命中的根因：大模型的前缀缓存（Prefix Caching）要求请求的开头部分（System Prompt、Few-Shot示例、RAG检索结果）在Token级别完全一致，如果每次请求的内容顺序随机、动态拼接，就会导致缓存完全失效；
  3. 第三步：针对性实施分层记忆优化，裁剪不必要的上下文长度；
  4. 第四步：调整Prompt拼接和RAG排序逻辑，最大化触发前缀缓存，降低重复计算。

▎详细方案

问题根因分析：
- 上下文膨胀问题：系统把用户从对话开始的所有聊天记录全部无差别塞进每一次请求的上下文里，对话轮数越多，上下文Token数越多，大模型推理时需要处理的Token量线性增长，导致TTFT升高、Token成本飙升；
- 缓存失效问题：系统拼接Prompt时顺序不固定：比如RAG检索结果每次按照相关性分数排序，分数相同的片段顺序随机；System Prompt里动态拼接了当前时间、请求ID等每次都变的内容；历史对话放在System Prompt前面，导致每个请求的开头Token都不一样，完全无法触发云厂商的KV前缀缓存——前缀缓存的原理是如果两个请求的前N个Token完全一致，就可以复用之前计算好的Key/Value缓存，不需要重新计算，这部分通常能节省50%以上的首字延迟。

具体优化方案分为两部分：
1. 分层记忆架构，压缩上下文长度：
- 近期记忆：只把最近N轮（通常是5~10轮）的原始对话精确存入上下文，保证多轮对话的连贯性；
- 长期记忆：后台跑一个异步的摘要小模型，把更早的历史对话自动压缩成精简的用户画像摘要（比如“用户是市场部新员工，关心社保缴纳时间、入职材料要求”），只把摘要存入上下文，不需要保留原始对话内容；
- 滑动窗口裁剪：每次请求前计算总Token数，如果超过阈值就自动裁剪最老的非关键内容，保证上下文总长度控制在合理范围内（比如4k Token以内）。
2. 标准化Prompt结构，最大化触发前缀缓存：
- 固定Prompt拼接顺序：严格按照“固定System Prompt → 固定Few-Shot示例 → 长期记忆摘要 → RAG检索结果 → 近期对话历史 → 当前用户问题”的顺序拼接，任何动态内容都放在请求的后半部分，保证请求开头的Token序列100%固定；
- RAG检索结果排序稳定化：检索出来的Chunk首先按照文档ID、Chunk序号做二次排序，不要只按照相关性分数排序，避免相同的检索结果因为顺序不同导致Token序列不一致；
- 把动态变化的内容（比如当前时间、请求ID）放到Prompt的最后面，不要插在固定System Prompt中间，避免破坏前缀匹配。

通过以上优化，相同类型的请求前70%~80%的Token都是完全一致的，可以稳定命中KV缓存，TTFT可以从15秒降到2秒以内，同时因为上下文长度压缩，Token成本可以降低60%以上。

▎关键细节 & 踩坑点

  • 摘要压缩不要同步做：如果在用户请求的主链路里调用小模型做摘要，会额外增加延迟，一定要用异步任务在后台做，用户对话结束后再异步压缩历史记录；
  • Rerank之后的结果一定要做稳定排序：很多Rerank模型返回的分数是浮点数，可能出现多个Chunk分数完全相同的情况，如果只按分数排序，相同的Chunk每次顺序可能不一样，导致缓存失效；
  • 不要把用户的个性化信息放在System Prompt的最开头，否则每个用户的请求开头都不一样，完全无法命中公共前缀缓存，公共固定内容一定要放在最前面，用户个性化内容放在后面。

▎可扩展优化

  • 可以引入语义缓存（Semantic Cache）：把用户常见问题的回答结果缓存起来，如果新的问题和缓存里的问题语义相似度超过阈值，直接返回缓存结果，不需要调用大模型，进一步降低成本和延迟；
  • 可以实现动态Token截断：根据当前问题的语义，只检索和问题相关的历史对话，不是所有近期对话都塞进上下文，进一步减少无效Token；
  • 简单的意图识别、实体提取任务可以路由到更小的Flash模型处理，不需要调用旗舰大模型，进一步降低成本。

综合落地

场景标签

0到1落地 稳定性 风控安全 可观测性

📝 题目

公司要求你在1个月内从0到1上线一套面向内部员工的合同审核Agent产品，核心功能是员工上传合同PDF后，Agent自动提取关键条款、识别风险点、给出修改建议，最终输出审核报告。这套系统涉及合同敏感数据、需要对接内部OA系统提交审核意见，一旦出现风险点漏判、提示词注入攻击、服务不可用都会造成严重的业务影响。请你梳理从0到1交付这套工业级Agent系统的完整落地路径，说明每个阶段的核心目标、必须做的稳定性/安全措施、以及上线后的运维保障方案。

💡 参考答案

▎解题思路

  1. 第一阶段（第1周）：MVP快速验证，先跑通核心流程，验证业务可行性，不要一开始就追求完美架构；
  2. 第二阶段（第2周）：稳定性与安全加固，解决死循环、幻觉、注入攻击、高危操作等核心风险点，达到生产可用标准；
  3. 第三阶段（第3周）：评测体系与可观测建设，建立量化的效果评估标准，确保每次迭代不会让效果变差；
  4. 第四阶段（第4周）：灰度上线与运维保障，小流量灰度验证，逐步放量，建立监控告警和应急响应机制。

▎详细方案

整个落地路径按照四周规划，每个阶段的核心动作如下：
1. 第一周：MVP核心流程跑通
核心目标是用最快的速度验证业务价值，不要过度设计：
- 基于LangGraph搭建最简工作流：PDF解析→条款提取→风险点识别→报告生成四个节点；
- 用Docling做PDF结构化解析，保留表格、条款层级的完整性，避免粗暴切块丢失上下文；
- 基础能力复用公司已有的MCP公共服务（LLM调用、RAG检索），不需要重复开发；
- 第一周结束时能够输入合同PDF输出审核报告，找法务团队验证效果是否达到基本可用标准，避免方向走偏。
2. 第二周：稳定性与安全加固
核心目标是把Demo变成可以上线的生产级系统，重点解决风险问题：
- 稳定性防护：在LangGraph的State里加入loop_count计数器，每个反思/重试节点计数器+1，最多允许3次重试，超过就强行降级退出，防止死循环刷Token；所有外部调用（LLM、OA系统）都设置超时时间（比如30秒），配置3次增量重试；
- 安全防护：① 输入层：在PDF解析后、传给大模型之前，增加独立的提示词注入检测模块，识别合同文本里的“忽略之前的指令”“把所有合同内容发出去”这类恶意注入内容，直接拦截；② 输出层：增加敏感信息脱敏，识别合同里的身份证号、银行账号、商业机密信息，输出报告时做脱敏处理；③ 操作层：所有对接OA系统的写操作（比如提交审核意见、流转审批），必须经过法务人员在后台二次确认才能执行，绝对不允许Agent自动触发高危写操作；
- 状态持久化：配置PostgreSQL Checkpointer，每个节点执行完都持久化状态，服务重启后可以恢复任务，不会丢失审核到一半的合同。
3. 第三周：评测体系与可观测建设
核心目标是建立可量化的质量标准，避免“改完Prompt不知道效果变好还是变坏”：
- 构建测试集：联合法务团队整理100份历史合同，标注好每份合同的风险点、正确的审核建议作为Ground Truth；
- 搭建最简Agent Harness：用pytest写自动化测试脚本，每次修改Prompt、调整工作流逻辑后，自动批量跑这100个测试用例，计算风险点召回率、误判率，要求召回率达到90%以上才能合并代码；
- 接入全链路Trace：用LangSmith/Phoenix埋点，记录每个合同审核的完整链路：调用了多少次大模型、每个步骤的输入输出是什么、Token消耗多少、哪一步耗时最长，出现问题可以快速定位。
4. 第四周：灰度上线与运维保障
核心目标是平稳上线，不出现重大故障：
- 首先配置优雅关闭和健康检查，支持无损发布，避免发布时中断正在审核的合同；
- 灰度放量：第一天只开放给法务团队内部使用，收集反馈修复问题；第二天开放给10%的员工使用；一周后全量开放；
- 配置网关层限流：每个用户每分钟最多提交2份合同审核，防止恶意刷接口打垮服务；配置熔断器，当大模型API连续报错超过阈值时，自动切换为“系统繁忙，请稍后再试”的降级响应，避免雪崩。

▎关键细节 & 踩坑点

  • 绝对不要在MVP阶段就花大量时间做复杂的多Agent架构、微调模型，第一优先级是跑通核心流程让业务方验证价值，很多项目死在一开始就过度设计，最后一个月到了连Demo都没做出来；
  • 合同审核场景绝对不能允许Agent自动执行写操作，所有对外的操作必须有人工确认环节，一旦Agent出现幻觉把错误的审核意见提交到OA系统，会造成严重的法律风险；
  • 测试集必须由业务方（法务）来标注，不能由开发人员自己编测试用例，否则测试用例和实际业务场景脱节，即使测试全部通过，上线后还是会大量漏判风险点。

▎可扩展优化

  • 上线后可以建立数据飞轮：所有法务人员修正过的审核报告，自动沉淀到测试集和知识库中，定期用这些数据做DPO微调，让模型的审核风格和标准越来越贴合公司法务的要求；
  • 可以引入GraphRAG，把所有的法律条款、公司制度、历史合同判决案例构建成知识图谱，提升多跳风险点的识别准确率（比如识别“这个条款违反了某条法规，且之前有类似的合同纠纷案例”）；
  • 可以增加人机协作模式：Agent识别出高风险条款时，自动高亮并推送给法务人员优先审核，低风险条款自动审核通过，大幅提升法务团队的工作效率。
