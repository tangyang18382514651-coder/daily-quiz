📌 概念题 · Q1

考点标签

LLMOps 监控指标 · 难度：⭐⭐⭐

📝 题目

知识库在讨论 LLMOps 运维监控时，特别强调了一个容易被忽视的细节：“不仅要监控 GPU 温度和利用率，更要监控 TTFT（首字延迟时间）、TPOT（每个 Token 生成时间）、显存碎片率。” 请问：为什么 GPU 利用率高反而可能意味着用户体验差？TTFT 和 TPOT 分别衡量的是什么？显存碎片率这个指标为什么在长期运行的 Agent 服务中至关重要？

💡 参考答案

▎一句话结论

GPU 利用率衡量的是“硬件忙不忙”，而 TTFT/TPOT 衡量的是“用户等得急不急”——两者在并发推理场景下经常背离，显存碎片率则是决定服务能否 7×24 小时稳定运行的“慢性病指标”。

▎核心原理

  • TTFT（Time To First Token）：从用户请求发出到第一个 Token 返回的延迟，主要由 Prompt 处理阶段（Prefill）决定，对用户体验影响最大。
  • TPOT（Time Per Output Token）：生成阶段每个 Token 的耗时，由 Decode 阶段的内存带宽决定，决定了“打字机”流式输出的速度。
  • GPU 利用率高不代表响应快：在 vLLM 的 Continuous Batching 机制下，GPU 可能同时处理大量请求，算力被塞满，但每个请求的排队时间变长，TTFT 反而飙升。
  • 显存碎片率：KV Cache 的频繁分配与释放会在显存中产生大量不连续的空洞，长期运行后即使总显存充足，新的长上下文请求也可能因为找不到连续显存块而 OOM。

▎深入解释

这里有一个反直觉的现象：GPU 利用率 95% 不一定比 60% 更好。在 LLM 推理中，GPU 的计算核心（SM）和显存带宽是两个不同的瓶颈。Prefill 阶段是计算密集型的，Decode 阶段是访存密集型的。当并发请求增多时，GPU 利用率确实会升高，但每个请求的 Prefill 会被延迟处理，导致 TTFT 从 200ms 恶化到 3 秒。用户感知到的是“AI 卡住了”，而不是“AI 很忙”。

显存碎片率更像是一个“定时炸弹”。KV Cache 的长度因请求而异——有的用户问一句话，有的用户粘贴了 50 页文档。vLLM 的 PagedAttention 用类似操作系统虚拟内存分页的方式管理 KV Cache，但如果碎片化严重，就会出现“总显存还有 10GB 空闲，但全是不足 2MB 的碎片，一个需要 4GB 连续显存的长请求直接失败”的情况。这解释了为什么很多 Agent 服务运行几周后会突然崩溃，重启后又恢复正常。

▎面试加分点

  • 可以提到 vLLM 的 --gpu-memory-utilization 参数设置过低（如 0.9）会加剧碎片问题，设置过高（如 0.98）又会导致系统级 OOM，需要在实践中找到平衡点。
  • 提到使用 Prometheus + Grafana 对 TTFT 的 P50/P99 分位数进行监控，P99 比平均值更能反映用户体验的“长尾痛苦”。
  • 可以举例：在 HR 语音客服中，TTFT 超过 1 秒会导致候选人觉得“AI 在犹豫”，挂断率显著上升。

▎常见误区

  • 误区：只看 GPU 利用率，认为越高越好，结果并发一高用户体验反而崩了。
  • 误区：认为显存碎片率是硬件问题，无法从软件层面优化。实际上通过调整 KV Cache 的预分配策略和定期滚动重启可以缓解。

📌 概念题 · Q2

考点标签

本地部署选型 · 难度：⭐⭐⭐⭐

📝 题目

知识库给出了本地部署的三种方案：方案 A（轻量级模型 + 4090 单机）、方案 B（70B 旗舰模型 + H200 集群）、方案 C（671B MoE + Blackwell 集群）。其中特别强调了一个原则：“切忌算力焦虑——不要一上来就追求 8 卡 Blackwell 或是非 70B 模型不跑，建议先用方案 A 跑通一到两个高频痛点业务，验证 ROI 后再做硬件升级。” 请问：为什么“先用小模型验证 ROI”比“一步到位上大集群”更符合企业 AI 落地的实际逻辑？ROI 验证的核心指标是什么？

💡 参考答案

▎一句话结论

“算力焦虑”本质上是把“技术先进性”当成了“业务价值”，而 ROI 验证的核心不是模型有多大，而是“每花一块钱算力，能省下多少人力成本或创造多少业务增量”。

▎核心原理

  • 大模型集群的固定成本极高：方案 C 的硬件投入在百万级别，且需要液冷改造、电力扩容等隐性成本，如果业务验证失败，沉没成本巨大。
  • 小模型方案的门槛极低：双卡 4090 总投入 4-8 万元，普通后端工程师即可维护，试错成本几乎可以忽略。
  • ROI 验证的本质是“业务验证”而非“技术验证”：先用小模型跑通流程，验证的是“这个场景 AI 到底能不能产生价值”，而不是“这个模型有多聪明”。
  • 高频痛点业务的选取标准：频率高（每天都有大量重复劳动）、容错率适中（AI 犯错了不会造成严重后果）、效果可量化（可以对比 AI 处理前后的时间和人力消耗）。

▎深入解释

很多企业 AI 项目的失败路径是这样的：CTO 看到行业新闻里“某某银行部署了 671B 大模型”，于是拍板采购了几百万的 H200 集群。结果业务部门发现 AI 生成的报告还需要大量人工修改，ROI 算不过来，项目被砍掉，硬件闲置。这就是典型的“技术驱动”而非“业务驱动”。

正确的路径是：先用方案 A 在客服或 HR 文档检索这种高频场景跑通闭环，花 4 万块钱验证“AI 能不能减少 30% 的重复劳动”。如果验证成功，再逐步升级硬件。知识库中提到的律师事务所案例就是典范——双卡 4090 跑 Qwen 3.5-32B INT4，10 秒内完成 50 页卷宗的大纲提炼，这个 ROI 是立刻可以感知的。

ROI 的核心指标包括：单次任务成本（算力消耗 × 时间）、替代人力比例（原来需要 3 个人做的事，现在需要几个人配合 AI）、错误率（AI 输出需要人工修正的比例）、用户满意度（内部员工或外部客户是否真的愿意用）。

▎面试加分点

  • 可以提到“数据飞轮”效应：先用小模型跑通业务，积累真实的用户反馈数据，这些数据反过来可以用于后续大模型的微调和优化。
  • 可以提到硬件采购的“时间窗口”：GPU 硬件的迭代速度极快（H100 → H200 → B200），过早采购大集群可能面临“到货即落后”的尴尬。
  • 可以强调“重数据轻模型”的原则：80% 的精力花在清洗企业私有数据上，效果提升远比把模型从 32B 升级到 70B 显著。

▎常见误区

  • 误区：认为“模型越大效果一定越好”，忽略了私有数据的质量和 Prompt 工程的影响。
  • 误区：只计算硬件采购成本，忽略了机房电力改造、液冷系统、专业运维团队的隐性成本。

📌 概念题 · Q3

考点标签

LangGraph 容器化 · 难度：⭐⭐⭐⭐

📝 题目

知识库在讨论 LangGraph 多智能体部署时，推荐使用多 Dockerfile 方案而非单一镜像方案，核心理由是：“有些执行特定工具的 Agent 需要非常重的依赖（如 torch、pandas、numpy、CUDA 驱动），如果全部打到一个镜像里，会导致路由 Agent 的镜像也变得极其臃肿（几个 G），极大影响 K8s 弹性伸缩时的容器拉取速度。” 请问：容器镜像大小为什么会影响 K8s 的弹性伸缩效率？除了镜像大小，多 Dockerfile 方案在资源调度和故障隔离方面还有哪些优势？

💡 参考答案

▎一句话结论

容器镜像大小直接决定了 K8s 弹性伸缩的“冷启动延迟”，而多 Dockerfile 方案的本质是“按职责拆分依赖”，让轻量级 Agent 享受秒级扩容，让重量级 Agent 独占 GPU 资源，同时实现故障的物理隔离。

▎核心原理

  • 镜像拉取时间是冷启动延迟的最大瓶颈：一个 5GB 的镜像在普通带宽下拉取可能需要 30-60 秒，而一个 200MB 的镜像只需 2-3 秒。在流量突增时，这个差距决定了用户是等待 3 秒还是等待 1 分钟。
  • 异构算力调度：Router Agent 通常只需要 CPU（轻量级逻辑判断），Data Agent 需要 GPU（重计算）。如果打成一个镜像，K8s 无法对不同 Pod 做差异化的资源请求，要么浪费 GPU 资源给 Router，要么让 Data Agent 抢不到 GPU。
  • 故障隔离：如果 Data Agent 因为 CUDA 版本冲突或 OOM 崩溃，在单一镜像方案下，整个服务可能一起挂掉；多镜像方案下，Router 仍然可以正常路由，只是降级处理数据请求。
  • 安全边界清晰：重量级 Agent 往往需要更多系统权限（如访问 GPU 设备、挂载数据卷），拆开后可以对不同容器施加不同的 SecurityContext 和 RBAC 策略。

▎深入解释

K8s 的弹性伸缩（HPA）触发后，新 Pod 需要经历：调度 → 拉取镜像 → 启动容器 → 健康检查通过 → 开始接收流量。其中镜像拉取时间往往占据了 80% 以上的冷启动延迟。在 ACK Serverless 这种按秒计费的场景下，镜像拉取时间还直接影响成本——你为拉取镜像的那 30 秒也要付算力费用。

多 Dockerfile 方案的精髓在于“依赖分层”。Router Agent 的 Dockerfile 基于 python:3.10-slim，只装 FastAPI 和 LangGraph 核心库，镜像控制在 200-500MB。Data Agent 的 Dockerfile 基于 nvidia/cuda:11.8.0-runtime-ubuntu22.04，装 torch、pandas、numpy，镜像可能有 5-8GB。这样在 K8s 中，Router 的 Deployment 可以设置 replicas: 5 快速扩容，而 Data Agent 的 Deployment 则通过 nvidia.com/gpu: 1 限制资源，走独立的调度路径。

▎面试加分点

  • 可以提到使用多阶段构建（Multi-stage Build）进一步优化镜像大小：在构建阶段安装完整依赖，在运行阶段只拷贝必要的产物。
  • 可以提到镜像预热技术（如 Dragonfly、Kraken 等 P2P 镜像分发方案）在大型集群中可以将镜像拉取时间从分钟级降低到秒级。
  • 可以结合知识库中的“解耦的关键在于 server/ 入口”这一原则，强调每个 Agent 通过 FastAPI 或 gRPC 独立暴露服务，网络通信替代了进程内函数调用。

▎常见误区

  • 误区：认为“镜像大只是首次拉取慢，之后有缓存就好了”，忽略了弹性伸缩时新节点可能没有缓存。
  • 误区：为了省事把所有 Agent 打成一个镜像，结果 Router 因为一个不相关的 CUDA 依赖问题而无法启动。

📌 概念题 · Q4

考点标签

Serverless 选型 · 难度：⭐⭐⭐

📝 题目

知识库中明确区分了 K8s 和 Serverless 的概念：“K8s 是容器编排标准，Serverless 是运维模式”，并给出了阿里云上的三种 Serverless 形态：ACK Serverless（K8s 级）、SAE（应用级）、FC 函数计算（函数级）。请问：这三种 Serverless 形态在“控制粒度”和“运维心智负担”上有什么区别？为什么知识库认为复杂的 Multi-Agent 系统应该选择 ACK Serverless，而不是更简单的 SAE 或 FC？

💡 参考答案

▎一句话结论

FC 是“交一个函数就完事”，SAE 是“交一个镜像就完事”，ACK Serverless 是“交一个完整的 K8s 编排体系”——控制粒度越细，能承载的架构复杂度越高，但运维心智负担也越重。

▎核心原理

  • FC（Function as a Service）：最小粒度，只关心单个函数的输入输出，完全不用管容器和网络。适合 Agent 的“安全沙箱 Tool 端”，如临时执行一段 Python 脚本解析 PDF。
  • SAE（Application as a Service）：中间粒度，传一个 Docker 镜像过去就能跑，自动伸缩，但不需要懂 K8s YAML 语法。适合中小型 Agent Web 应用，如快速上线一个 Dify 对话前端。
  • ACK Serverless（Container as a Service + K8s API）：最大粒度，拥有完整的 K8s API，可以用 Helm、Kubectl 管理，但底层没有服务器节点。适合复杂的 Multi-Agent 平台。
  • 选择 ACK Serverless 的核心原因：Multi-Agent 系统需要异构算力调度（CPU/GPU 混部）、有状态存储（NAS 挂载 Checkpointer）、长连接（WebSocket 语音流）、微服务治理（多个 Agent 节点间的服务发现和流量控制），这些能力只有 K8s 生态能完整提供。

▎深入解释

一个 LangGraph Multi-Agent 系统的部署需求远不止“跑起来”这么简单。你需要：Router Agent 跑在 CPU 容器上（250m CPU / 512Mi 内存），Data Agent 跑在 GPU 容器上（nvidia.com/gpu: 1），两者通过 K8s Service 通信；LangGraph 的 Checkpointer 需要挂载 NAS 持久卷；当某个 Agent 崩溃时需要自动重启；当流量高峰时需要 HPA 自动扩容。这些需求在 SAE 上要么无法实现，要么需要大量 Hack。

FC 的定位则完全不同——它不是用来跑 Agent 主程序的，而是作为 Agent 的“安全沙箱”。当 Agent 需要执行一段高风险代码时，把代码丢给 FC，用完后立即销毁，天然隔离了安全隐患。这种“用完即毁”的模式在 ACK Serverless 中也可以通过 ECI（弹性容器实例）实现，但 FC 的粒度更细、成本更低。

▎面试加分点

  • 可以提到“缩容到 0”这个关键特性：ACK Serverless 支持将 GPU 容器缩容到 0，不用不花钱，这对 GPU 成本控制至关重要。
  • 可以提到 K8s 生态的“标准性”：Helm Chart、GitOps（ArgoCD）、服务网格（Istio）等成熟的工具链可以直接复用，不需要重新发明轮子。
  • 可以结合知识库中的“动态安全沙箱”需求，说明 FC 在 Agent Tool 端的独特价值。

▎常见误区

  • 误区：认为 Serverless 就是“不用管服务器”，所以选最简单的 FC 就好。实际上 FC 的并发限制和执行时间限制（通常 15 分钟）无法承载长连接的 Agent 服务。
  • 误区：认为 ACK Serverless 和标准 K8s 完全一样，忽略了 Serverless 场景下的一些限制（如本地存储的临时性、节点级特性的缺失）。

📌 概念题 · Q5

考点标签

PostgreSQL 复合角色 · 难度：⭐⭐⭐⭐

📝 题目

知识库中提出了一个非常有架构师思维的总结：“PgSQL 既能通过 JSONB 搞定半结构化对话，又能通过 pgvector 搞定向量，还能用传统的 SQL 处理业务。一套数据库解决了三种需求，极大地减少了数据在不同数据库之间同步的延迟，也帮团队省去了运维 Milvus 或 Redis 的成本。” 请问：在什么规模的业务场景下，这种“PostgreSQL 一库三用”的架构是合理且优雅的？在什么场景下它反而会成为性能瓶颈？判断的临界指标是什么？

💡 参考答案

▎一句话结论

“PostgreSQL 一库三用”在中小规模（百万级向量、千级 QPS、数据量百 GB 以内）场景下是极其优雅的架构减法，但当向量检索的 QPS 超过数据库的 CPU/内存承载能力，或者向量数据量突破亿级时，专用向量数据库（Milvus）和专用缓存（Redis）的分离架构就会变成刚需。

▎核心原理

  • PostgreSQL 的优势在于“事务一致性”：JSONB 的 ACID 事务、pgvector 的向量检索、传统 SQL 的业务查询都在同一个事务上下文中，不需要处理跨数据库的最终一致性问题。
  • pgvector 的 HNSW 索引在百万级向量、低并发场景下性能足够：单次查询延迟可以控制在 10-50ms，对 HR 客服和内容运营 Agent 这类内部系统完全够用。
  • 瓶颈出现在两个维度：向量数据量（pgvector 的 HNSW 索引在亿级数据下内存占用巨大，且 Postgres 的 Buffer Pool 管理不如 Milvus 的 GPU 索引高效）和并发量（Postgres 的每个连接都是一个进程，高并发下连接池和锁竞争成为瓶颈）。
  • 临界指标：向量条数 > 1000 万，或向量检索 QPS > 100，或数据总量 > 500GB 时，建议迁移到 Milvus + Redis + PostgreSQL 的分离架构。

▎深入解释

这种“一库三用”的架构在 HR 智能客服和社媒内容运营 Agent 中之所以能成立，是因为这两个场景的数据量都在 PostgreSQL 的舒适区内：对话记录可能只有几十万条，向量数据来自几千份文档的切片（几十万条向量），并发用户数在几十人以内。在这种情况下，引入 Milvus 和 Redis 反而增加了架构复杂度和运维成本，而收益微乎其微。

但当业务增长到需要服务数万用户、向量数据来自数百万份文档时，pgvector 的局限性就会暴露：Postgres 的 MVCC（多版本并发控制）机制在频繁更新的向量索引上会产生大量死元组，需要频繁 VACUUM；HNSW 索引的构建速度远慢于 Milvus 的 GPU 加速索引；Postgres 的单机内存上限（通常 256GB-512GB）也无法承载亿级向量的全内存索引。

▎面试加分点

  • 可以提到 pgvector 的 IVFFlat vs HNSW 索引选择：IVFFlat 建索引快但查询精度依赖 Probes 参数，HNSW 查询快但建索引慢，需要根据数据更新频率选择。
  • 可以提到 PostgreSQL 的 SELECT ... FOR UPDATE 悲观锁在 Agent 并发状态管理中的独特价值——这是 Milvus 和 Redis 都做不到的。
  • 可以强调“架构演进”的思路：先用 PostgreSQL 快速验证业务，数据量上来后再平滑迁移到专用组件，而不是一开始就上最复杂的架构。

▎常见误区

  • 误区：认为“一库三用”是银弹，在任何场景下都应该用 PostgreSQL 替代 Milvus 和 Redis。实际上 pgvector 的召回率在高维向量（>1024 维）和大数据量下会明显下降。
  • 误区：忽略了 PostgreSQL 的连接数限制（通常 max_connections 在 100-500），高并发 Agent 场景下连接池配置不当会导致严重的性能问题。

📌 概念题 · Q6

考点标签

大模型输出模式 · 难度：⭐⭐⭐

📝 题目

知识库总结了大模型的五种输出模式：全量文本、流式输出（SSE）、结构化输出（JSON）、工具调用（Function Calling）、多模态输出。其中特别指出：“国内更擅长用流式体验和强大的 Agent 中间件平台去扬长避短，国外则更执着于榨干底层 API 的确定性（Strict JSON），并率先向端到端音视频/画布流演进。” 请问：为什么国内开发者更依赖“提示词约束 + 后端正则/Pydantic 兜底”的 JSON 输出方案，而国外开发者更信任 API 原生的 Structured Outputs？这两种路线的工程代价和适用场景有什么不同？

💡 参考答案

▎一句话结论

国内路线是“模型不够，工程来凑”——用多层兜底保证 JSON 格式不翻车；国外路线是“模型够强，API 兜底”——用底层采样约束从概率层面杜绝格式错误。前者灵活但脆弱，后者稳健但依赖模型能力。

▎核心原理

  • 国内大模型生态碎片化：不同厂商（通义、文心、智谱、Kimi）的 JSON Mode 实现不一致，开发者无法依赖统一的 API 行为，只能在上层做兼容和兜底。
  • 提示词约束的局限性：在 Prompt 中写“请返回 JSON 格式”本质上是一种“软约束”，模型在长输出或复杂嵌套结构下仍然可能产生非法 JSON（如尾随逗号、注释、未转义字符）。
  • 后端兜底的工程成本：用正则表达式或 Pydantic 做二次校验，本质上是在模型输出之后再做一层“格式防火墙”，这增加了代码复杂度，但能兼容任何模型。
  • 国外 Structured Outputs 的原理：OpenAI 的 response_format: { type: "json_schema" } 通过在采样阶段对 Token 概率分布施加约束（Constraint Decoding），从数学上保证输出一定符合 Schema，不需要后处理。

▎深入解释

国内开发者之所以习惯“提示词 + 兜底”，一个重要的历史原因是：国内大模型 API 的迭代速度极快，但文档和 SDK 的稳定性不足。开发者如果依赖某个厂商的 JSON Mode 特性，一旦该厂商调整了 API 行为，整个 Agent 工作流就会崩溃。因此，“不信任模型，自己做兜底”成了一种防御性编程的习惯。

但这条路线有隐性成本：Pydantic 校验失败后的重试逻辑、正则表达式对嵌套 JSON 的脆弱性、以及每次模型升级后需要重新调整 Prompt 的维护成本。相比之下，国外开发者在 OpenAI/Anthropic 的生态中，可以放心地把 Structured Outputs 当作“百分百可信的微服务 API”，直接消费 JSON 结果，代码更简洁。

▎面试加分点

  • 可以提到“约束解码”（Constrained Decoding）的技术原理：在 Beam Search 或 Greedy Decoding 的每一步，过滤掉不符合 Schema 的 Token，从概率层面保证输出合法性。
  • 可以提到国内 Dify/Coze 等低代码平台对 Function Calling 的“吸收”：大多数开发者不需要手写多轮工具调用的拼装逻辑，平台在底层处理了。
  • 可以强调在 Agent 多节点协作中，结构化输出是“节点间的契约”，一旦某个节点的 JSON 解析失败，整个工作流就会中断，因此兜底机制是必要的防御。

▎常见误区

  • 误区：认为“提示词里写了 JSON 格式就够了”，忽略了模型在长输出时的格式漂移问题。
  • 误区：认为“Structured Outputs 是万能的”，忽略了它可能略微牺牲模型的发散思维能力（严格约束下模型倾向于输出更保守的内容）。

📌 概念题 · Q7

考点标签

Milvus 降级通道 · 难度：⭐⭐⭐

📝 题目

知识库在讨论 Milvus Standalone 的企业级运维时，提出了一个关键的“逃生通道”设计：“在业务代码中留一个开关。万一 Milvus 挂了，系统自动降级切换到 PostgreSQL / MySQL 的传统全文检索，确保员工基本搜索业务不断线。” 请问：为什么这个“降级开关”在企业级 Agent 架构中是必须的？语义检索（向量）和全文检索（关键词）在降级场景下的用户体验差异是什么？实现这个降级开关需要注意哪些工程细节？

💡 参考答案

▎一句话结论

降级开关的本质是“可用性优先于智能性”——当向量数据库不可用时，宁可让用户得到 60 分的关键词搜索结果，也不能让搜索功能完全中断，因为一个“偶尔不准但永远可用”的系统远比一个“精确但经常挂掉”的系统更值得信赖。

▎核心原理

  • 单点故障的必然性：Milvus Standalone 部署在单台虚拟机上，无论配置多高，都存在宕机、重启、网络抖动等不可用时刻，这是单机架构的固有风险。
  • 全文检索的兜底能力：PostgreSQL 的 Full-text Search（tsvector + tsquery）或 MySQL 的 FULLTEXT 索引可以处理关键词匹配，虽然无法理解语义（如“公积金怎么提取”和“如何取出住房公积金”在全文检索下匹配度很低），但能保证基本的相关性。
  • 降级的粒度控制：不是所有请求都需要降级。可以用健康检查（Health Check）探测 Milvus 的状态，只有在下游不可用时才切换，且切换应该是自动的、无感的。
  • 降级后的用户体验管理：前端应该提示用户“当前为简易搜索模式”或降低结果的置信度展示，避免用户误以为语义搜索仍然在工作。

▎深入解释

这个降级开关的设计体现了企业级架构中一个重要的原则：“优雅降级（Graceful Degradation）”。在 HR 智能客服中，如果 Milvus 挂了，候选人的问题“试用期工资怎么算”在全文检索下可能匹配到“试用期管理规范”文档，虽然不如语义检索精准，但至少给出了相关内容，用户不会觉得系统完全不可用。

实现这个降级开关需要注意几个工程细节：健康检查的频率和超时设置（太频繁会增加 Milvus 的负载，太慢会导致降级不及时）；降级后的恢复策略（Milvus 恢复后是自动切回还是需要人工确认）；降级期间的数据一致性（如果用户在降级期间上传了新文档，需要确保恢复后该文档的向量索引被补建）。

▎面试加分点

  • 可以提到“双路检索”的进阶方案：不是简单的切换，而是同时查询 Milvus 和 PostgreSQL，根据 Milvus 的响应时间动态调整权重。
  • 可以提到健康检查的实现方式：在 Milvus 的 Python SDK 中，utility.get_server_version() 或简单的 collection.num_entities 调用可以作为轻量级的健康探针。
  • 可以强调这个降级开关的“配置化”设计：通过环境变量或配置中心控制，不需要修改代码就能切换。

▎常见误区

  • 误区：认为“降级开关是过度设计，Milvus 很稳定不会挂”。实际上单机部署的 Milvus 在内存不足、磁盘满、Docker 守护进程重启等情况下都可能不可用。
  • 误区：降级后直接返回空结果，而不是切换到全文检索。这会让用户觉得系统“坏了”，而不是“降级了”。

📌 概念题 · Q8

考点标签

Agent SQL 安全 · 难度：⭐⭐⭐⭐

📝 题目

知识库中有一条关于 Agent 操作 SQL 数据库的安全规范：“读取数据库可以放行；增删改数据库需要基于人类反馈确认后才能通过；并且要给 Agent 做 SQL 的环境沙箱隔离。” 请问：为什么“读取”和“增删改”需要采取完全不同的安全策略？在 HR 场景中，“人类反馈确认”具体应该如何设计才能既保证安全又不影响效率？SQL 沙箱隔离在技术上可以通过哪些方式实现？

💡 参考答案

▎一句话结论

“读取”是零风险操作，可以全自动放行；“增删改”是不可逆操作，必须引入 Human-in-the-loop 审批机制；而沙箱隔离则是最后一道防线，确保即使 Agent 产生了恶意的 SQL 幻觉，也无法对生产数据造成实质性破坏。

▎核心原理

  • 读取操作的幂等性和零副作用：SELECT 语句不会改变数据库状态，即使 Agent 生成了错误的查询，最坏的结果只是返回了不相关的数据，用户可以忽略或重新查询。
  • 增删改操作的不可逆性：DELETE 和 UPDATE 一旦执行，原始数据就被覆盖或删除。如果没有备份和审批机制，一个错误的 WHERE 条件可能导致全表数据丢失。
  • 人类反馈确认的设计原则：不是每一句 SQL 都需要人工审批，而是根据操作的风险等级分级处理。低风险操作（如 INSERT 一条新记录）可以自动执行并记录日志，高风险操作（如 DELETE、批量 UPDATE）必须经过人工确认。
  • 沙箱隔离的层次：数据库权限隔离（只读账号 + 受限写账号）、事务回滚机制（执行前开启事务，确认后才 COMMIT）、网络隔离（Agent 只能访问沙箱数据库的副本，不能直接连接生产库）。

▎深入解释

在 HR 场景中，“人类反馈确认”可以设计成一个轻量级的审批流：当 Agent 生成了一条 UPDATE 语句（如“把张三的试用期状态改为已通过”），系统先不执行，而是将 SQL 语句、影响行数预估、操作理由推送给 HR 主管的钉钉或企业微信。HR 主管点击“确认”后，SQL 才真正执行。这个确认步骤只需要几秒钟，但能防止 Agent 因为理解错误而误改数据。

SQL 沙箱隔离的技术实现可以分三层：第一层是数据库权限——Agent 使用一个只有 SELECT 权限的账号，写操作必须通过一个独立的 API 网关，由网关校验审批状态后再用高权限账号执行。第二层是数据副本——Agent 的所有操作都在一个实时同步的只读副本上进行，即使 Agent 执行了恶意操作，也不会影响生产数据。第三层是审计日志——所有 Agent 生成的 SQL 都记录完整日志，包括时间、来源、SQL 内容、审批人、执行结果，以便事后追溯。

▎面试加分点

  • 可以提到“预执行检查”：在执行 UPDATE/DELETE 之前，先运行一条对应的 SELECT 语句，展示将受影响的行数和数据预览，让审批人直观地看到操作的影响范围。
  • 可以提到“SQL 白名单”：将 Agent 允许执行的操作限制在预定义的模板内（如“更新试用期状态”只能 UPDATE employee 表的 probation_status 字段），从源头杜绝任意 SQL 的执行。
  • 可以结合知识库中的“读取放行”原则，说明在 RAG 场景中 Agent 的 SQL 查询能力本质上是一种“结构化检索”，与向量检索是互补关系。

▎常见误区

  • 误区：认为“给 Agent 一个只读数据库账号就够了”，忽略了 Agent 可能通过 SQL 注入或恶意构造的查询语句绕过权限限制。
  • 误区：审批机制设计得过于繁琐，每一次写操作都需要多层审批，导致 HR 主管成为瓶颈，最终他们选择“全部同意”，审批形同虚设。

📌 概念题 · Q9

考点标签

Linux GPU 资源调度 · 难度：⭐⭐⭐

📝 题目

知识库在讨论 Linux 与 AI Agent 开发的关系时，特别提到了一个实用技巧：“在启动自媒体 Agent 时，直接在终端敲入 export CUDA_VISIBLE_DEVICES=0，强行规定这个项目只准用 0 号卡，把 1 号卡留给 HR 语音项目。不需要改动一行 Python 代码，在 Linux 系统层就把昂贵的算力资源分配得明明白白。” 请问：CUDA_VISIBLE_DEVICES 环境变量的工作原理是什么？为什么它在多 Agent 共用一个 GPU 服务器的场景中如此重要？除了环境变量，还有哪些方式可以实现 GPU 资源的隔离和调度？

💡 参考答案

▎一句话结论

CUDA_VISIBLE_DEVICES 是在 CUDA 驱动层实现的“设备可见性过滤器”——它在不修改任何代码的前提下，让每个进程只能“看到”被允许使用的 GPU，从而在操作系统层面实现了最轻量的 GPU 资源隔离。

▎核心原理

  • 工作原理：CUDA 运行时在初始化时会读取 CUDA_VISIBLE_DEVICES 环境变量，将其值解析为 GPU 编号列表，然后只对这些 GPU 创建上下文。进程内部看到的“GPU 0”实际上是物理 GPU 编号列表中第一个可见的设备。
  • 隔离的粒度：这个环境变量只能做到“设备级”隔离（整张卡分配给某个进程），无法做到“显存级”隔离（限制进程只能使用某张卡的 50% 显存）。
  • 多 Agent 共存的典型场景：一台 8 卡服务器上可能同时运行 HR 语音客服（占用 0-3 号卡）、自媒体内容生成（占用 4-5 号卡）、Embedding 服务（占用 6 号卡）、测试环境（占用 7 号卡）。通过环境变量，每个服务被“钉”在固定的 GPU 上，互不干扰。
  • 防止 OOM 的关键：如果没有显式的设备分配，多个 Agent 进程可能默认都使用 GPU 0，导致 GPU 0 显存爆掉而 GPU 1-7 闲置。环境变量强制分散了负载。

▎深入解释

这个技巧的优雅之处在于它的“零侵入性”。你不需要修改 Python 代码中的 model.to('cuda:0') 调用，也不需要引入复杂的 GPU 调度框架。只需要在启动脚本中加一行 export CUDA_VISIBLE_DEVICES=0，进程内部的 cuda:0 就会自动映射到物理 GPU 0（或你指定的任何编号）。

但它的局限性也很明显：它只能做“整卡分配”，不能做“显存配额”。如果 HR 语音客服的并发突然升高，它可能会把分配给它的 GPU 0 的显存全部吃光，甚至影响同一张卡上的其他进程。对于更精细的资源隔离，需要借助 MPS（Multi-Process Service）、MIG（Multi-Instance GPU，A100/H100 支持）或容器化的 GPU 调度（K8s 的 nvidia.com/gpu 资源请求）。

▎面试加分点

  • 可以提到 nvidia-smi 配合 watch -n 1 的实时监控技巧，这是 AI 开发者的“肌肉记忆”。
  • 可以提到在 Docker 中传递 GPU 可见性的方式：docker run --gpus '"device=0,1"'，本质上是将环境变量注入容器内部。
  • 可以提到 MIG 技术：A100 可以将一张物理 GPU 切分为 7 个独立的 GPU 实例，每个实例有独立的显存和计算单元，适合多租户共享场景。

▎常见误区

  • 误区：认为设置了 CUDA_VISIBLE_DEVICES 就万事大吉，忽略了 PyTorch 的 DataLoader 可能在 CPU 上产生瓶颈，或者多进程数据加载（num_workers > 0）可能绕过环境变量的限制。
  • 误区：在同一个 Python 进程内动态修改 CUDA_VISIBLE_DEVICES（在 import torch 之后再设置），此时 CUDA 已经初始化，修改不会生效。

📌 概念题 · Q10

考点标签

AI Agent 落地避坑 · 难度：⭐⭐⭐⭐

📝 题目

知识库在“总结与企业落地建议”中提出了三条避坑指南：① 切忌算力焦虑；② 重数据轻模型；③ 注意基础设施配套。其中第二条特别强调：“将 80% 的精力花在清洗企业内部 PDF、Excel、企业 Wiki 等垃圾数据上（消除乱码、做好文本切片 Chunking），其效果提升远比你把模型从 32B 升级到 70B 要显著得多。” 请问：为什么在 RAG 和 Agent 场景中，“数据质量”对最终效果的影响远大于“模型参数规模”？企业内部的“垃圾数据”通常有哪些典型问题？高质量的文本切片（Chunking）需要遵循哪些原则？

💡 参考答案

▎一句话结论

在 RAG 场景中，模型只是“阅读理解器”，数据才是“考试内容”——如果喂给模型的是乱码、碎片化、结构混乱的文本，再大的模型也答不对；而干净、结构化、语义完整的文本切片，能让 32B 小模型的检索效果超过 70B 大模型。

▎核心原理

  • RAG 的“天花板效应”：检索质量决定了生成质量的上限。如果向量检索返回的 Top-K 文档块中不包含正确答案，模型无论多大都无法“无中生有”。数据质量直接决定了检索的召回率和准确率。
  • 企业内部数据的典型问题：PDF 中的乱码（编码不一致导致的中文乱码）、扫描件未做 OCR、Excel 中的合并单元格和公式、Wiki 中的历史版本残留、复制粘贴产生的格式污染（如换行符丢失、空格异常）。
  • Chunking 的核心原则：语义完整性（一个 Chunk 应该包含一个完整的语义单元，而不是机械地按 500 字符截断）、上下文重叠（相邻 Chunk 之间保留 10-15% 的重叠，避免关键信息被切断）、元数据保留（Chunk 需要携带来源文档、章节标题、页码等元数据，用于检索后的溯源和过滤）。
  • 模型规模的边际收益递减：从 7B 到 32B 的提升显著，从 32B 到 70B 的提升在 RAG 场景中可能只有 5-10% 的准确率提升，但硬件成本翻了 3-5 倍。

▎深入解释

“垃圾进，垃圾出”（Garbage In, Garbage Out）是 AI 领域最古老的定律之一，但在 RAG 时代它有了新的含义。一个典型的例子：企业内部有一份 PDF 格式的员工手册，其中包含表格、流程图和脚注。如果直接使用 PyPDF 提取文本，表格会变成混乱的字符排列，流程图会完全丢失，脚注会混入正文。这些“垃圾数据”被切片后存入向量数据库，当用户搜索“年假怎么算”时，向量检索可能匹配到一个包含表格乱码的 Chunk，模型从中无法提取有效信息，只能编造答案。

高质量的 Chunking 需要根据文档类型动态调整策略：对于结构化的政策文档，按章节标题切分；对于 FAQ 类文档，按问答对切分；对于表格密集的文档，需要先将表格转换为 Markdown 格式再切分。同时，Chunk 的大小需要与 Embedding 模型的上下文窗口匹配——太小的 Chunk 缺乏上下文，太大的 Chunk 会稀释语义焦点。

▎面试加分点

  • 可以提到“数据飞轮”的闭环：高质量数据不仅提升检索效果，还能用于后续的模型微调，形成“数据→模型→更多数据→更好模型”的正循环。
  • 可以提到“文档解析流水线”的设计：不是简单的 PDF 转文本，而是“版面分析 → OCR → 表格识别 → Markdown 结构化 → 语义切片”的多级流水线。
  • 可以举知识库中的例子：律师事务所的 50 页卷宗能在 10 秒内完成大纲提炼，前提是卷宗已经被正确地切片和向量化。

▎常见误区

  • 误区：认为“把 PDF 扔给 Embedding 模型就行了”，忽略了 PDF 中表格、图片、多栏排版对文本提取质量的严重影响。
  • 误区：Chunk 切得越小越好。实际上过小的 Chunk 会导致语义碎片化，检索时无法匹配完整的问题意图。
  • 误区：只关注 Chunk 的文本内容，忽略了元数据（来源、时间、权限）的重要性。在企业场景中，权限过滤往往比语义匹配更重要。

🛠 应用题 · Q1 · 架构设计

题型

架构设计

场景标签

LangGraph 多智能体 Docker 镜像拆分 K8s 弹性伸缩 异构算力调度

📝 题目

你正在为一个电商客服团队设计一套 LangGraph 多智能体系统，包含三类 Agent 节点：

  • Router Agent：纯 CPU 计算，负责意图识别和任务分发，代码量小、依赖极少（仅需 langgraph + fastapi），预计请求量巨大，需要极致弹性伸缩。
  • Data Analysis Agent：需要 torch、pandas、numpy、CUDA 驱动，负责对用户订单数据做统计分析和异常检测，偶尔被调用但计算密集。
  • Image Generation Agent：需要 GPU 推理环境 + 扩散模型权重（约 8GB），负责生成商品推荐图，调用频率低但单次资源消耗极大。

知识库中明确推荐：多 Dockerfile 方案优于单一镜像 + 变参启动，核心原因是“如果用方案二全部打到一个镜像里，会导致路由 Agent 的镜像也变得极其臃肿（几个 G），极大影响 K8s 弹性伸缩时的容器拉取速度”。

请设计这套系统的容器化与 K8s 部署架构，重点回答：

  1. 三个 Agent 分别如何设计 Dockerfile？基础镜像如何选型？
  2. 在 K8s 中如何为三类 Agent 配置不同的资源配额和弹性策略？
  3. Router Agent 需要频繁扩容，镜像大小对冷启动时间的影响有多大？如何进一步优化？

💡 参考答案

▎解题思路

  1. 首先按“依赖重量级”对三个 Agent 分层：Router 属于轻量级（纯 CPU、纯 Python），Data Analysis 属于中量级（CPU + 重科学计算库），Image Generation 属于重量级（GPU + 大模型权重文件）。
  2. 依据知识库的“多 Dockerfile 方案”原则，为每个 Agent 编写独立的 Dockerfile，选择不同的基础镜像，确保镜像体积与节点职责匹配。
  3. 在 K8s 层面，利用不同的 Deployment + HPA（Horizontal Pod Autoscaler）策略，让 Router 可以秒级扩容到几十个副本，而 Image Generation 则固定 1-2 个 GPU Pod，避免 GPU 资源浪费。
  4. 针对 Router 的极致弹性需求，进一步通过精简基础镜像（如 python:3.12-slim 甚至 distroless）、多阶段构建、依赖裁剪等手段，把镜像压到 200MB 以内。

▎详细方案

第一层：Dockerfile 分层设计

Router Agent（轻量级，目标镜像 < 300MB）：

FROM python:3.11-slim AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

FROM python:3.11-slim
WORKDIR /app
COPY --from=builder /install /usr/local
COPY agents/router_agent.py .
COPY server/run_router.py .
CMD ["python", "server/run_router.py"]

关键点：使用多阶段构建，第一层装依赖，第二层只拷贝安装产物，避免 pip 缓存和编译工具链残留在最终镜像里。requirements.txt 只包含 langgraph、fastapi、uvicorn、httpx 四个核心库。

Data Analysis Agent（中量级，目标镜像 2-4GB）：

FROM nvidia/cuda:12.1.0-runtime-ubuntu22.04
RUN apt-get update && apt-get install -y python3.11 python3-pip
WORKDIR /app
COPY requirements.txt requirements-gpu.txt .
RUN pip install --no-cache-dir -r requirements.txt -r requirements-gpu.txt
COPY agents/data_agent.py .
COPY server/run_data_agent.py .
CMD ["python", "server/run_data_agent.py"]

关键点：使用 NVIDIA 官方 CUDA runtime 镜像（非 devel 镜像，省掉编译工具链），requirements-gpu.txt 中锁定 torch、pandas、numpy 版本。

Image Generation Agent（重量级，镜像可能 10GB+）：

这里有一个关键决策：模型权重不要打进 Docker 镜像里，而是通过 K8s 的 PV/PVC 挂载到容器内。Docker 镜像只包含推理代码和运行时依赖，权重文件放在独立的 NAS 或云盘上。这样镜像本身控制在 3-5GB，权重文件独立管理，更新模型不需要重新构建镜像。

FROM nvidia/cuda:12.1.0-runtime-ubuntu22.04
RUN apt-get update && apt-get install -y python3.11 python3-pip
WORKDIR /app
COPY requirements.txt requirements-gpu.txt .
RUN pip install --no-cache-dir -r requirements.txt -r requirements-gpu.txt
COPY agents/image_agent.py .
COPY server/run_image_agent.py .
CMD ["python", "server/run_image_agent.py"]

第二层：K8s 资源配置与弹性策略

Agent 资源 Requests 资源 Limits HPA 策略 节点池
Router CPU: 250m, Mem: 512Mi CPU: 1, Mem: 1Gi min=3, max=50, CPU 70% 触发 CPU 节点池（便宜）
Data Analysis CPU: 2, Mem: 8Gi CPU: 4, Mem: 16Gi min=1, max=5, 自定义指标（队列深度） CPU 节点池
Image Generation GPU: 1, Mem: 16Gi GPU: 1, Mem: 32Gi 固定 1-2 个副本，不做 HPA GPU 节点池（T4/A10）

关键点：Router 和 Data Analysis 部署在不同的节点池上，避免 CPU 密集型任务和内存密集型任务互相抢占资源。Image Generation 使用 GPU 节点池，通过 nodeSelector 或 nodeAffinity 绑定。

第三层：Router 冷启动优化

镜像大小对冷启动时间的影响主要体现在两个环节：

  1. 镜像拉取时间：在 K8s 集群中，如果节点本地没有缓存镜像，需要从镜像仓库拉取。假设内网带宽 1Gbps，拉取一个 3GB 镜像需要约 24 秒，而拉取一个 200MB 镜像只需约 1.6 秒。在 HPA 触发扩容时，这 20 多秒的差距意味着用户请求可能排队超时。
  2. 容器启动时间：Python 应用启动本身很快（1-2 秒），但如果镜像里有大量无用文件，文件系统初始化也会变慢。

进一步优化手段：
- 使用 镜像预拉取（DaemonSet 在每台节点上提前拉取常用镜像）
- 使用 BuildKit 的层缓存，确保每次构建只推送变化的层
- 考虑 Serverless 容器（如 ACK Serverless 的 ECI），镜像缓存由云厂商管理

▎关键细节 & 踩坑点

  • 不要用 latest 标签：每次构建用 Git commit hash 或语义化版本号，否则 K8s 无法判断是否需要重新拉取镜像。
  • requirements.txt 必须锁版本：torch==2.1.0 而不是 torch，否则某次构建可能拉到一个不兼容的新版本，导致 Data Agent 启动失败。
  • GPU 节点池的“浪费”问题：Image Generation Agent 如果固定 1 个副本，GPU 利用率可能不到 10%。如果业务允许，可以把它和 Data Analysis Agent 放在同一个 GPU 节点池，通过 nvidia.com/gpu: 1 的 requests 让 K8s 自动调度。
  • 镜像仓库的地域选择：如果 K8s 集群在阿里云成都区，镜像仓库也应该在成都区，否则跨地域拉取会走公网，速度骤降。
  • 多阶段构建中 COPY --from=builder 的路径要对：pip install --prefix=/install 会把包装到 /install/lib/python3.11/site-packages，拷贝时要精确到 site-packages 层级，否则 Python 找不到包。

▎可扩展优化

  • 引入镜像瘦身工具：使用 dive 分析镜像层，找出大文件来源；使用 docker-slim 自动裁剪无用文件。
  • Router Agent 进一步极致化：如果 Router 只做意图分类，可以考虑不用 LangGraph，直接用 FastAPI + 简单的规则引擎，镜像可以压到 100MB 以内，甚至用 Go 重写，镜像只有 20MB。
  • 引入 K8s 的 Pod 预热机制：通过 container.imagePullPolicy: IfNotPresent + 节点预热池，确保扩容时镜像已在本地。
  • 考虑 Knative 或 OpenFunction：如果 Router 的流量有明显的波峰波谷（如电商大促），可以基于请求驱动伸缩到 0，进一步节省成本。

你是一家 200 人规模的中型律师事务所的 IT 顾问。律所的需求如下：

  • 内部有约 5 万份历史诉讼文书（PDF、Word 格式），需要做检索和摘要。
  • 律师每天会上传约 50 份新卷宗，每份 30-100 页不等，需要自动生成大纲和关键论点提取。
  • 数据绝对不能外流（客户隐私 + 律师保密义务）。
  • 律所 IT 团队只有 2 名普通后端工程师，没有 AI 运维经验。
  • 年度 IT 预算约 15 万元人民币（含硬件、软件、维护）。

知识库中给出了三条本地部署路线：

  • 方案 A：轻量级模型（如 Qwen 3.5-32B INT4 量化）+ 双卡 4090 D，硬件成本 4-8 万，普通后端即可维护。

  • 方案 C：671B MoE 模型（FP4/FP8）+ 8 卡 B200，硬件成本百万级，需要机房液冷改造。

知识库同时给出了避坑指南：“切忌算力焦虑：不要一上来就追求 8 卡 Blackwell 或是非 70B 模型不跑。建议企业内部先用方案 A 跑通一到两个高频痛点业务，验证 ROI 后再做硬件升级。”

请分析：

  1. 这家律所应该选择哪条路线？为什么？
  2. 如果选择方案 A，5 万份历史文书 + 每天新增 50 份卷宗的数据规模，单机双卡 4090 D 是否真的够用？请做定量推演。
  3. 你如何说服律所合伙人（不懂技术、只看 ROI）接受这个方案？

💡 参考答案

▎解题思路

  1. 首先从预算、团队能力、数据规模三个维度做“排除法”：方案 B 的 40-60 万硬件成本远超预算，方案 C 的百万级投入更是天方夜谭。方案 A 是唯一在预算内且能被 2 名后端工程师维护的选择。
  2. 定量推演数据规模：5 万份历史文书 + 每天新增 50 份，需要估算向量数据量、存储需求、推理吞吐量，验证双卡 4090 D 是否够用。
  3. 从 ROI 角度说服合伙人：对比“雇佣 3 名初级律师助理做检索摘要”的年成本（约 30-45 万/年）和“一次性投入 6-8 万 + 每年 1-2 万维护”的差距。

▎详细方案

第一层：选型决策

结论：方案 A 是唯一选择，且功能完全够用。

第二层：定量推演

向量数据量估算：

  • 5 万份历史文书，平均每份 20 页，每页约 500 字，总计约 5 亿字。
  • 按每 500 字一个 Chunk 切片，产生约 100 万个 Chunk。
  • 每天新增 50 份卷宗 × 平均 50 页 × 500 字/页 ÷ 500 字/Chunk = 每天新增约 2500 个 Chunk。
  • 一年新增约 90 万个 Chunk，总向量量级在 200 万条以内。

存储需求：

  • 每条向量假设 1024 维，使用 INT8 量化存储，每条约 1KB。
  • 200 万条向量 ≈ 2GB 原始向量数据。
  • 加上 HNSW 索引的额外开销（约 1.5-2 倍），总存储约 4-5GB。
  • 原始文档存储（PDF/Word）假设平均每份 2MB，5 万份 ≈ 100GB。
  • 结论：一台 2TB NVMe SSD 的服务器绰绰有余。

推理吞吐量：

  • 律所 200 人，假设高峰时段 20% 的人同时使用（40 人），每人每分钟发起 1 次查询。
  • 峰值 QPS ≈ 0.7 次/秒，即使算上 Agent 内部的多轮检索（每次查询触发 3-5 次向量检索），向量检索 QPS 也不超过 5。
  • Milvus Standalone 在单机 CPU 上轻松跑出 500+ QPS，完全无压力。
  • LLM 推理：Qwen 3.5-32B INT4 在双卡 4090 D 上，单次摘要生成（500-1000 Token）约需 10-20 秒。40 人同时在线，vLLM 的 Continuous Batching 可以把并发吞吐拉到 5-10 人同时流畅使用。
  • 结论：双卡 4090 D 完全够用，甚至还有余量。

方案 年成本 3 年总成本

▎关键细节 & 踩坑点

  • INT4 量化的精度损失：对于法律文书这种需要精确理解的场景，INT4 量化可能导致关键术语（如“不可抗力”“连带责任”）的理解偏差。建议在摘要生成时用 INT4 保证速度，在关键条款提取时切换到更高精度的推理模式（或用规则引擎兜底）。
  • 数据清洗是最大的隐性成本：5 万份历史文书中可能有扫描件（需要 OCR）、乱码 PDF（需要解析修复）、重复文档（需要去重）。知识库强调“将 80% 的精力花在清洗企业内部 PDF、Excel、企业 Wiki 等垃圾数据上”，这个项目的数据清洗可能需要 2-3 个月。
  • 供电和散热：双卡 4090 D 满载功耗约 450W，普通办公室的插座和空调可能带不动。需要确认机房或办公室的电路是否支持。
  • 合规性：律师行业的数据保密要求极高，需要确认模型权重本身是否允许本地部署（开源模型如 Qwen 允许），以及是否需要做审计日志。

▎可扩展优化

  • 渐进式升级路径：先用方案 A 跑通“卷宗摘要”这一个高频痛点，验证 ROI 后，如果律师反馈需要更强的逻辑推理能力（如合同条款对比分析），再考虑升级到单卡 H200 跑 70B 模型。
  • 混合精度推理：对法律文书中的关键段落（如判决书主文）用 BF16 精度推理，对一般性描述用 INT4 推理，在精度和速度之间动态切换。
  • 引入规则引擎兜底：法律领域有很多硬性规则（如诉讼时效、管辖法院），这些不需要 LLM 推理，用规则引擎直接匹配，既快又准。

场景标签

大模型输出模式 流式输出 SSE 结构化输出 工具调用 多模态输出

📝 题目

你正在开发一个 HR 智能语音客服 Agent，它需要处理以下三种不同类型的用户请求：

  1. 闲聊类（占 60%）：如“你们公司怎么样？”“面试要注意什么？”——需要流式输出，让用户感觉像真人对话。
  2. 信息查询类（占 30%）：如“查一下我的面试进度”“成都分公司的地址是什么？”——需要先调用内部 API 获取数据，再组织语言回复。
  3. 表单填写类（占 10%）：如“帮我提交报销申请”——需要从语音中提取结构化字段（金额、日期、事由），生成 JSON 后调用后端接口。

知识库中总结了五种大模型输出模式：全量文本、流式输出（SSE）、结构化输出（JSON）、工具调用（Function Calling）、多模态输出，并强调“工具调用是 AI Agent 的核心”。

请设计这个语音客服 Agent 的输出层架构，重点回答：

  1. 三种请求类型分别使用哪种输出模式？为什么？
  2. 对于“信息查询类”，工具调用的完整链路是怎样的？请用伪代码或流程图描述。
  3. 流式输出（SSE）和工具调用能否同时使用？如果模型在流式输出过程中突然需要调用工具，应该怎么处理？

💡 参考答案

▎解题思路

  1. 首先明确一个核心原则：输出模式不是全局配置，而是每个请求级别的动态决策。同一个 Agent 在不同类型的对话轮次中，需要切换不同的输出模式。
  2. 闲聊类使用 SSE 流式输出，因为用户体验是第一优先级，首字延迟必须控制在 300ms 以内。
  3. 信息查询类使用工具调用模式，因为模型不能凭空编造数据，必须先拿到 API 返回的真实数据再组织语言。
  4. 表单填写类使用结构化输出（JSON Schema 约束），因为字段必须 100% 可解析，不能有任何格式错误。
  5. 流式输出和工具调用在底层是冲突的——流式输出是“边生成边发送”，而工具调用需要“先决定调用哪个工具，等工具返回后再继续生成”。解决方案是：先让模型在后台静默判断是否需要调用工具，如果需要，则不进入流式模式，而是走工具调用流程；工具返回后再进入流式模式输出最终答案。

▎详细方案

第一层：请求路由与模式选择

# 伪代码：输出模式路由
async def handle_user_request(user_input: str, conversation_history: list):
    # 第一步：意图分类（用轻量级模型或规则引擎，快速判断）
    intent = await classify_intent(user_input)

    if intent == "chitchat":
        # 闲聊类：直接流式输出
        return await stream_chat_response(user_input, conversation_history)

    elif intent == "info_query":
        # 信息查询类：先工具调用，再流式输出
        tool_result = await tool_calling_flow(user_input, conversation_history)
        return await stream_final_answer(user_input, tool_result, conversation_history)

    elif intent == "form_filling":
        # 表单填写类：结构化输出
        return await structured_json_output(user_input, conversation_history)

第二层：信息查询类的工具调用完整链路

async def tool_calling_flow(user_input: str, history: list):
    # 第一步：让模型决定调用哪个工具，以及参数是什么
    tool_call_response = await llm.chat(
        messages=history + [{"role": "user", "content": user_input}],
        tools=[
            {
                "name": "query_interview_progress",
                "description": "查询候选人的面试进度",
                "parameters": {
                    "type": "object",
                    "properties": {
                        "candidate_name": {"type": "string"},
                        "phone_number": {"type": "string"}
                    },
                    "required": ["candidate_name"]
                }
            },
            {
                "name": "query_company_address",
                "description": "查询公司地址",
                "parameters": {
                    "type": "object",
                    "properties": {
                        "city": {"type": "string"}
                    },
                    "required": ["city"]
                }
            }
        ],
        tool_choice="auto"  # 让模型自己决定是否调用工具
    )

    # 第二步：检查模型是否真的发起了工具调用
    if tool_call_response.tool_calls:
        tool_call = tool_call_response.tool_calls[0]

        # 第三步：执行实际的工具函数
        if tool_call.name == "query_interview_progress":
            result = await db.query(
                "SELECT status, next_round_time FROM interviews WHERE candidate_name = ?",
                tool_call.arguments["candidate_name"]
            )
        elif tool_call.name == "query_company_address":
            result = await internal_api.get_address(tool_call.arguments["city"])

        # 第四步：把工具结果喂回给模型，生成最终的自然语言回答
        final_response = await llm.chat(
            messages=history + [
                {"role": "user", "content": user_input},
                {"role": "assistant", "content": None, "tool_calls": [tool_call]},
                {"role": "tool", "tool_call_id": tool_call.id, "content": json.dumps(result)}
            ],
            stream=True  # 最终回答使用流式输出
        )
        return final_response
    else:
        # 模型认为不需要调用工具，直接流式回答
        return tool_call_response

第三层：流式输出与工具调用的冲突处理

这是整个架构中最容易踩坑的地方。核心问题：SSE 流式输出是“边生成边发送”，一旦开始流式输出，就无法中途插入工具调用。 解决方案有三种：

方案 1：预判断（推荐）

在进入流式输出之前，先让模型做一次“静默判断”——用 tool_choice="auto" 但 stream=False，让模型在后台完整生成，判断是否需要调用工具。如果需要，走工具调用流程；如果不需要，再重新发起一次 stream=True 的请求。

代价：多一次 LLM 调用，增加约 200-500ms 延迟。但这是最稳妥的方案。

方案 2：流式输出中检测工具调用标记

在流式输出过程中，实时检测输出内容中是否出现工具调用的特殊标记（如 <tool_call> 标签）。如果检测到，立即中断流式输出，切换到工具调用流程。

代价：需要自定义 Prompt 让模型在需要调用工具时输出特殊标记，且流式输出已经发送的部分内容需要撤回或忽略，用户体验较差。

方案 3：双模型架构

用一个小模型（如 7B）做工具调用判断，用大模型（如 32B）做最终回答生成。小模型快速判断“是否需要调用工具”，如果需要，先走工具调用流程，再把结果交给大模型生成流式回答。

代价：部署两个模型，增加系统复杂度。但延迟最低，适合对响应速度要求极高的场景。

▎关键细节 & 踩坑点

  • SSE 的连接管理：SSE 是单向长连接，如果客户端断开（如用户挂断电话），服务端需要及时检测并停止生成，否则会浪费 GPU 算力。可以通过 request.is_disconnected() 检查连接状态。
  • 工具调用的超时处理：内部 API 可能响应缓慢（如数据库查询卡住），需要给工具调用设置超时（如 3 秒），超时后让模型生成一个“抱歉，系统暂时无法查询，请稍后再试”的兜底回答。
  • JSON Schema 约束的强制力：对于表单填写类，必须使用 API 级别的 JSON Schema 约束（如 OpenAI 的 response_format: {"type": "json_schema", "json_schema": {...}}），而不是仅仅在 Prompt 里写“请返回 JSON”。后者在复杂字段嵌套时容易翻车。
  • 工具调用的参数校验：模型生成的工具参数可能不合法（如日期格式错误、缺少必填字段），需要在执行工具前做一次参数校验，不合法时让模型重新生成。
  • 语音场景的特殊性：语音客服中用户可能说“帮我查一下张三的面试进度”，模型需要从语音转文本的结果中提取“张三”这个名字。如果转文本错误（如“张山”），工具调用会失败。需要做模糊匹配或让模型追问确认。

▎可扩展优化

  • 工具调用的缓存机制：如果用户在短时间内重复查询同一个信息（如“面试进度”），可以缓存工具调用结果，避免重复调用后端 API。
  • 流式输出的 Token 级控制：对于语音合成场景，流式输出可以按句子切分，每生成一个完整句子就交给 TTS 引擎合成语音，进一步降低首字延迟。
  • 多模态输出的引入：如果语音客服需要推送图片（如公司地图、福利介绍），可以在流式输出中插入多模态标记，前端解析后渲染图片。

LLMOps 监控 TTFT/TPOT 显存碎片率 GPU 利用率

📝 题目

你负责的 HR 智能语音客服 Agent 部署在一台 4 卡 H200 服务器上（使用 vLLM 推理框架），最近用户投诉“AI 客服变慢了”，具体表现为：

  • 用户说完话后，AI 要等 3-5 秒才开始回应（正常应该是 1 秒以内）。
  • AI 回答过程中，每个字之间的间隔不均匀，有时很快，有时突然卡顿 1-2 秒。
  • 监控面板显示 GPU 利用率只有 35%，但用户感知的延迟却很高。

知识库中强调：“不仅要监控 GPU 温度和利用率，更要监控 TTFT（首字延迟时间）、TPOT（每个 Token 生成时间）、显存碎片率。”

请分析：

  1. 在这个场景中，最可能的原因是什么？为什么 GPU 利用率只有 35% 但用户感知延迟却很高？
  2. 如何通过 TTFT 和 TPOT 这两个指标来定位问题？
  3. 请给出具体的排查步骤和优化方案。

💡 参考答案

▎解题思路

  1. 首先明确一个关键认知：GPU 利用率低 + 用户感知延迟高，通常意味着瓶颈不在 GPU 计算本身，而在 GPU 之外的其他环节。可能的原因包括：CPU 预处理瓶颈、显存碎片化导致 KV Cache 无法高效分配、请求排队等待、网络传输延迟等。
  2. TTFT（Time To First Token）和 TPOT（Time Per Output Token）是两个关键指标：TTFT 高说明“从用户输入到模型开始输出”的环节有问题（如 Prompt 处理慢、排队等待）；TPOT 高且不稳定说明“生成过程中”有问题（如显存碎片导致 KV Cache 频繁换页）。
  3. 按照“从外到内”的顺序排查：先看请求排队时间，再看 Prompt 处理时间，最后看 Token 生成时间。

▎详细方案

第一层：指标拆解与定位

用户感知延迟 = 排队时间 + TTFT + TPOT × 输出 Token 数

指标 正常值 异常值 对应问题
排队时间 < 100ms 2-3 秒 并发请求超过 vLLM 的 max_num_seqs，请求在队列中等待
TTFT < 500ms 2-3 秒 Prompt 过长、CPU 预处理慢、显存碎片导致 KV Cache 分配慢
TPOT 20-50ms 100-500ms，且波动大 显存碎片化、KV Cache 频繁换页、GPU 内存带宽瓶颈

在这个场景中，用户反映“等 3-5 秒才开始回应”，说明 TTFT 或排队时间是主要瓶颈。而“每个字之间间隔不均匀”说明 TPOT 波动大，可能涉及显存碎片问题。

第二层：具体排查步骤

Step 1：检查请求排队情况

# 查看 vLLM 的请求队列指标
curl http://localhost:8000/metrics | grep vllm_num_requests_waiting
curl http://localhost:8000/metrics | grep vllm_num_requests_running

如果 vllm_num_requests_waiting 经常大于 0，说明请求在排队。语音客服场景中，用户说完话后语音转文本（ASR）需要 1-2 秒，这期间请求已经到达 vLLM，但 vLLM 的 max_num_seqs 设置过小（如默认 256），导致请求排队。

Step 2：检查 TTFT 的构成

TTFT = Prompt 处理时间 + KV Cache 分配时间 + 第一个 Token 生成时间

# 在 vLLM 中开启详细日志
# 查看 Prompt 处理时间
vllm:prompt_processing_time = 2.3s  # 异常！正常应该 < 500ms

Prompt 处理时间过长可能的原因：
- 对话历史过长（如用户已经聊了 50 轮，Prompt 有 10K Token）
- CPU 端的 Tokenizer 处理慢（如果 CPU 核数不足，Tokenizer 成为瓶颈）
- 显存碎片导致 KV Cache 分配需要整理内存

Step 3：检查显存碎片率

# 查看显存使用情况
nvidia-smi --query-gpu=memory.used,memory.total --format=csv

# 查看 vLLM 的显存分配情况
curl http://localhost:8000/metrics | grep vllm_gpu_cache_usage

如果 vllm_gpu_cache_usage 显示 KV Cache 使用率很高（如 > 90%），但实际活跃请求很少，说明存在严重的显存碎片化——之前的长对话请求释放了 KV Cache，但释放的内存块不连续，新请求无法高效利用。

第三层：优化方案

针对排队时间：
- 增大 max_num_seqs（如从 256 增大到 512），让更多请求可以同时进入推理阶段。
- 但注意：max_num_seqs 过大可能导致每个请求的 KV Cache 分配不足，反而降低吞吐。

针对 TTFT 过高：
- 限制对话历史长度：在语音客服场景中，把对话历史截断到最近 10 轮，减少 Prompt 处理时间。
- 使用 Prefix Caching：vLLM 支持自动前缀缓存，如果多个请求共享相同的 System Prompt，可以避免重复计算。
- 增加 CPU 核数：Tokenizer 和 Prompt 预处理在 CPU 端执行，如果 CPU 核数不足（如只有 8 核），会成为瓶颈。

针对 TPOT 波动大：
- 启用 PagedAttention 的显存整理：vLLM 的 PagedAttention 机制本身就是为了减少显存碎片，但如果碎片率过高，可以设置 gpu_memory_utilization 稍低一些（如从 0.9 降到 0.8），留出更多连续显存空间。
- 定期重启推理服务：如果显存碎片率持续升高，最直接的办法是定期重启 vLLM 服务（如每天凌晨低峰期重启），重置显存分配。

▎关键细节 & 踩坑点

  • GPU 利用率低 ≠ 没有瓶颈：GPU 利用率低可能是因为 GPU 在等待 CPU 预处理数据（如 Tokenizer 处理 Prompt），或者等待网络传输（如从 ASR 服务接收音频转文本结果）。不要被“GPU 利用率只有 35%”迷惑，瓶颈可能在别处。
  • TPOT 的波动比平均值更重要：平均 TPOT 可能看起来正常（如 50ms），但如果 P99 TPOT 达到 500ms，用户就会感知到“卡顿”。监控时要看 P50、P95、P99 分位数，而不是只看平均值。
  • 语音场景的特殊性：语音客服中，用户的输入是语音转文本的结果，ASR 的延迟（1-2 秒）会叠加在 LLM 的 TTFT 之上。如果用户感知“等 3-5 秒”，其中 1-2 秒可能是 ASR 的延迟，需要把 ASR 和 LLM 的延迟分开监控。
  • 显存碎片率的监控：vLLM 提供了 vllm_gpu_cache_usage 指标，但碎片率需要自己计算——观察“活跃请求数 × 每个请求的平均 KV Cache 占用”和“实际已分配的 KV Cache 总量”之间的差距，差距越大说明碎片越严重。

▎可扩展优化

  • 引入 TrueFoundry 或 Weights & Biases (Weave)：知识库中推荐的企业级 LLMOps 平台，可以自动收集 TTFT、TPOT、显存碎片率等指标，并提供可视化面板和告警。
  • 动态 Batch Size 调整：根据当前排队长度动态调整 max_num_seqs，高峰期增大以容纳更多请求，低峰期减小以提高单请求的响应速度。
  • 模型量化优化：如果显存碎片问题持续存在，可以考虑将模型从 BF16 量化到 INT8 或 AWQ 量化，减少 KV Cache 的显存占用，从而降低碎片率。
  • 预热机制：在服务启动时预分配一批 KV Cache 块，避免运行时频繁分配和释放导致碎片。
